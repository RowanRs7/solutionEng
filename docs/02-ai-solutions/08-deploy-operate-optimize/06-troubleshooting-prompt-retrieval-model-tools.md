# Prompt、检索、模型与工具的故障定位

## 为什么需要学习

售后助手出现一类投诉：“客户问运费险，助手回答说可以退 20 元运费补贴，实际政策里根本没有这一条。”团队第一反应是改 Prompt，加了“不得编造政策条款”“必须引用原文”两段约束。上线后投诉少了一些，但一周后又出现同类问题，金额变成了 15 元。

第二周他们才做了一件本该最先做的事：拿那条投诉去回放。结果显示检索只命中了 0 段政策——运费险的文档根本不在索引里。模型在空上下文下按训练记忆编了一个合理的数字，而所有 Prompt 约束都拦不住它，因为**约束只能降低编造的概率，不能提供不存在的事实**。

> **核心结论：** “答错了”是症状，不是原因；先判定失败发生在检索、Prompt、模型还是工具，再决定改什么，否则每次修改都只是降低症状复发率。

## 学习目标

完成本课后，你能够：

- 把一条错误答复归入检索、Prompt、模型、工具四层之一，并给出支持该判断的证据。
- 设计至少三个判别实验，用最小改动区分“检索没召回”与“模型没用上”。
- 解释为什么“改 Prompt 后投诉变少”不能证明问题已修复。
- 为一次故障产出可回放的最小输入，并沉淀为回归样本。

## 前置知识

- 回看上一课：[AI Trace 与端到端可观测性](05-ai-tracing-and-observability.md)。
- 了解 RAG 链路：检索片段 → 拼进上下文 → 生成、引用与工具调用。

- 能读懂 Python 字典与条件判断。

## 业务场景

售后助手的四层结构是：检索（政策库 + 订单）、Prompt（系统提示 + 生成约束）、模型（当前版本与参数）、工具（创建退款单、查物流、发短信）。

四层的失败表现高度相似：客服看到的都是“答复不对”。但处置方式完全不同——检索层要修索引与召回，Prompt 层要修指令与示例，模型层要换版本或调参数，工具层要修契约与下游。分不清层次，就会出现“连续改五版 Prompt 仍未修好”的典型局面。

## 核心概念

| 概念 | 含义 | 在本课中的作用 |
| --- | --- | --- |
| *分层排障* | 按数据流顺序逐层验证，先定位层再定位因 | 避免在错误层反复修改 |
| *症状* | 用户可观察到的现象（答错、变慢、拒绝回答） | 排障的起点，不是结论 |
| *判别实验* | 只改变一个变量、能产生明确二选一结果的实验 | 把猜测变成证据 |
| *最小可复现输入* | 能稳定触发问题的最短输入与上下文快照 | 后续修复与回归的基础 |
| *触发条件* | 让缺陷暴露出来的外部条件（特定问法、特定订单） | 解释“为什么时好时坏” |
| *根因* | 缺陷本身（如索引缺文档、工具 schema 不匹配） | 修复对象 |
| *回放* | 用记录的输入与版本重新执行链路 | 验证是否已修复 |
| *假修复* | 症状减少但根因仍在的改动 | 最危险的一类“改进” |

四层的典型证据：

| 层 | 典型症状 | 首查证据 | 判别实验 |
| --- | --- | --- | --- |
| 检索 | 答复缺少条款、引用不存在的政策 | 命中数量、最高相似度、索引版本 | 用同一问题直接调检索服务，看在库文档能否被召回 |
| Prompt | 格式不对、该调用工具却没调用、语气跑偏 | Prompt 版本、实际送入的完整输入 | 固定检索结果，只改 Prompt，看输出是否变化 |
| 模型 | 语义反转、否定句读错、长上下文忽略中段 | 模型名与版本、结束原因、token 数 | 同一输入换模型或换版本，比较输出差异 |
| 工具 | 参数错误、动作未执行、重复执行 | 工具调用参数、结果码、幂等键 | 绕过模型手工调用工具，验证下游与契约 |

## 工作原理

1. **定义可观察症状**：把“答错了”写成可验证的句子，例如“答复称运费险可退 20 元，而政策库无此条款”。
2. **取出该次 trace**：拿到实际送入模型的完整输入、检索命中片段 ID、工具调用参数与结果码。
3. **逐层验证，从数据开始**：先看检索是否命中正确文档，再看 Prompt 是否把矛盾指令写进去，最后才怀疑模型。
4. **做判别实验**：固定其他变量，只改一个。例如“用同一问题直接调检索服务”“固定检索结果只换 Prompt”“同输入换模型”。
5. **区分触发条件与根因**：记录什么问法、什么订单、什么时段会触发；若只有特定订单触发，根因很可能在数据而非模型。
6. **修复并回放**：改完后用同一最小输入回放，确认输出变化；再把该输入加入回归集，防止下次改动重新引入。

第 3 步的顺序不能颠倒。工程团队的直觉是“模型答错了就改模型”，但在这类系统里，**数据缺失与 Prompt 矛盾的出现频率远高于模型能力不足**；先验数据，能省下大量无效试错。

## 架构与选型

| 排障方法 | 适用场景 | 成本 | 局限 |
| --- | --- | --- | --- |
| 逐层验证（数据优先） | 首次遇到的新症状 | 低 | 需要完整的 trace 才能做 |
| 二分法（按请求特征切片） | 只有部分请求出错 | 中 | 需要足够的样本量 |
| 回放（同输入重跑） | 验证是否已修复 | 低 | 依赖记录了版本与输入 |
| 对照实验（换模型/换 Prompt） | 怀疑模型或指令 | 中 | 会引入新的变量 |
| 代码插桩 | 怀疑超时、序列化、鉴权 | 中高 | 需要发布，可能扰动线上 |
| 统计切片（按意图/长度/租户） | 症状与群体相关 | 低 | 相关不等于因果 |

选型依据：**能用已有 trace 判断的，不要发版插桩**；**能用对照实验区分的，不要靠推理**；**只有确认根因在基础设施时才值得进入代码层**。另一个实用原则是“一次只改一层”——同时改检索与 Prompt，即使问题消失，你也不知道是哪一层修好的。

## 最小示例

下面的脚本把排障规则写成可执行的判别器。设计意图是展示“证据 → 候选根因 → 下一个实验”的结构，并让最高优先级的规则（声称已执行但未调用工具）先触发。

环境：Python 3.8+，仅标准库。

```python
# 每条 trace 只保留排障必需字段；真实系统字段更多，但判定逻辑相同
TRACES = [
    {"id": "T-1", "retrieval": {"hit": 0, "top_score": 0.0, "index": "2026-09-01"},
     "policy": {"version": "2026-10-05"}, "answer_claims_policy": True,
     "tool": {"expected": False, "called": False}, "llm": {"finish": "stop"}},
    {"id": "T-2", "retrieval": {"hit": 4, "top_score": 0.42, "index": "2026-09-01"},
     "policy": {"version": "2026-10-05"}, "answer_claims_policy": True,
     "tool": {"expected": False, "called": False}, "llm": {"finish": "stop"}},
    {"id": "T-3", "retrieval": {"hit": 2, "top_score": 0.81, "index": "2026-10-05"},
     "policy": {"version": "2026-10-05"}, "answer_claims_policy": True,
     "tool": {"expected": True, "called": False}, "llm": {"finish": "stop"}},
    {"id": "T-4", "retrieval": {"hit": 3, "top_score": 0.77, "index": "2026-10-05"},
     "policy": {"version": "2026-10-05"}, "answer_claims_policy": True,
     "tool": {"expected": False, "called": False}, "llm": {"finish": "length"}},
]

def diagnose(t):
    """返回 (严重度, 层, 候选根因, 证据, 下一个实验)。规则按严重度从高到低排列。"""
    r, tool, llm = t["retrieval"], t["tool"], t["llm"]

    # P0：对外声称动作已完成，但工具根本没被调用——这是承诺错误，必须最先止血
    if tool["expected"] and not tool["called"] and t["answer_claims_policy"]:
        return ("P0", "工具", "答复声称已提交，但工具未调用",
                "tool.expected=True, tool.called=False",
                "手工调用同参数工具验证下游；检查工具 schema 是否被模型看到")

    # 检索为空却给出了政策结论：事实缺口，不是措辞问题
    if r["hit"] == 0 and t["answer_claims_policy"]:
        return ("P1", "检索", "检索未命中，模型凭空补全政策",
                "retrieval.hit=0, answer_claims_policy=True",
                "直接调检索服务查该问题，确认文档是否在库、切分是否合理")

    # 索引版本落后于政策版本：命中的是旧文档
    if r["index"] != t["policy"]["version"]:
        return ("P1", "检索", "索引版本落后于政策版本",
                f"index={r['index']}, policy={t['policy']['version']}",
                "重建索引并回放同一问题，对比命中片段 ID")

    # 命中但相似度偏低：召回相关但不够精确，容易选中错误条款
    if r["hit"] > 0 and r["top_score"] < 0.6:
        return ("P2", "检索", "召回相关度低，可能选错条款",
                f"top_score={r['top_score']}",
                "固定上下文只换重排策略，观察引用条款是否变化")

    # 输出被长度截断：完整性缺失，条款常被截掉
    if llm["finish"] == "length":
        return ("P2", "模型", "输出被截断，条款可能不完整",
                "finish=length",
                "提高输出上限或要求分层输出，再检查完整性清单")

    return ("P3", "Prompt", "数据与工具均正常，怀疑指令或示例不足",
            "其余检查通过",
            "固定检索结果只改 Prompt，用同一输入对比输出")

for t in TRACES:
    sev, layer, cause, ev, exp = diagnose(t)
    print(f"{t['id']} [{sev}/{layer}] {cause}")
    print(f"  证据: {ev}")
    print(f"  下一个实验: {exp}")
```

输出（本机 `python3` 实测）：

```text
T-1 [P1/检索] 检索未命中，模型凭空补全政策
  证据: retrieval.hit=0, answer_claims_policy=True
  下一个实验: 直接调检索服务查该问题，确认文档是否在库、切分是否合理
T-2 [P1/检索] 索引版本落后于政策版本
  证据: index=2026-09-01, policy=2026-10-05
  下一个实验: 重建索引并回放同一问题，对比命中片段 ID
T-3 [P0/工具] 答复声称已提交，但工具未调用
  证据: tool.expected=True, tool.called=False
  下一个实验: 手工调用同参数工具验证下游；检查工具 schema 是否被模型看到
T-4 [P2/模型] 输出被截断，条款可能不完整
  证据: finish=length
  下一个实验: 提高输出上限或要求分层输出，再检查完整性清单
```

四条 trace 分别命中不同规则，说明**同样的“答错了”投诉可以落在四层中的任何一层**。特别注意 `T-3`：如果只看答复文本，它读起来最“肯定”，但它是唯一一条 P0——系统承诺了没做的事，风险等级高于答错一个数字。

这也是本课最反直觉的一点：<u>答复越流畅，越不能用来判断问题出在哪一层</u>。流畅只说明生成没崩，不说明上下文里有正确事实。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/triage.py`；无需网络。

步骤：

1. 运行 `python3 /tmp/triage.py`，核对四条的层级与下一个实验。
2. 把 `T-1` 的 `retrieval.hit` 改为 3、`top_score` 改为 0.72，观察它落到哪条规则，并解释为什么不再判为检索缺失。
3. 把 `T-2` 的 `index` 改为与 `policy` 一致，观察判定是否转移到“相似度低”。
4. 为 `T-1` 增加一条规则前置：若 `answer_claims_policy` 为 False（模型明确说“未找到政策”），判定应如何变化？请修改脚本并说明理由。
5. 手工构造一条“工具被调用但返回错误码”的 trace，补一条规则，并写出对应的下一个实验。

预期结果：第 2 步说明命中数不为 0 时不能判为“凭空补全”；第 3 步说明规则顺序会改变结论，因此规则必须按严重度排列；第 4 步应当得出“明确拒答是合格行为，不应判为故障”。

验证方法：每条 trace 只能命中一条规则，若命中多条，检查是否缺少优先级排序；构造边界值时观察是否出现规则冲突。

清理方法：`rm /tmp/triage.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 连续改多版 Prompt 仍复现 | 根因在检索或数据，Prompt 只能掩盖 | 检查 trace 中的命中数与片段内容 | 先修检索与索引，再回到 Prompt |
| 投诉变少就认为已修复 | 假修复：约束降低了发作概率 | 用原投诉输入回放，确认输出改变 | 建立回归集，按样本通过率判定 |
| 只有少数订单出错 | 触发条件与订单数据相关 | 按订单特征切片统计错误率 | 定位到具体字段或下游接口 |
| 同一问题不同时间答案不同 | 模型版本或索引在变，或参数随机 | 核对版本三元组与采样参数 | 固定版本、降低随机性、记录版本 |
| 工具动作重复执行 | 重试无幂等键，模型也重复调用 | 查工具侧幂等键与调用次数 | 加幂等键、限制单轮调用次数 |
| 回放结果与线上不一致 | 未记录完整输入或版本 | 对比回放输入与线上 trace 的哈希 | 记录完整输入指纹与版本三元组 |

## 安全与生产注意事项

**<u>排障时把生产 trace、客户对话与订单明细复制到外部工具或个人笔记，会造成二次泄露。</u>** 排障往往需要原样输入，但应使用内网环境与脱敏副本；确需原文时按最小必要原则申请，并记录访问用途与销毁时间。

**<u>为复现问题而临时关闭护栏、放宽权限或延长超时，是故障扩大的常见原因。</u>** 这类改动必须走变更记录、设定自动回滚时限，并在排障结束后核对配置是否恢复；否则“临时调试”会变成长期敞口。

另外两条：对外承诺类问题（声称已退款、已发货）应设独立的告警与人工复核通道，因为其后果不可逆；把排障结论写入知识库时，不要附带真实客户数据作为“示例”。

## 本课总结

- **“答错了”是症状，排障的第一步是把失败归到检索、Prompt、模型或工具中的一层。**
- 先验数据再验模型：缺文档、索引过期、接口超时比模型能力不足更常见。
- 判别实验一次只改一个变量，否则问题消失也无法归因。
- 症状减少不等于修复，必须用原输入回放并纳入回归集。
- 对外承诺类错误优先级最高，应先止血再定位。

## 思考题

如果一条投诉在回放时无法复现（同一输入得到正确答复），你会如何继续排查？请说明你会收集哪些额外证据、如何判断这是概率性缺陷还是环境差异，以及在上线节奏上如何处理。

参考思路：先核对版本三元组与参数是否一致（模型、索引、Prompt 版本、温度）；再收集同一时段的抽样 trace，用统计切片找出错误率偏高的意图或长度区间；若确认是概率性缺陷，应把该输入批量重放 N 次估算失败率，并据此决定是否需要更保守的兜底（如高风险意图强制人工确认）。上线节奏上，不能因为“单次无法复现”就当作已解决。

## 小测

1. 检索命中 0 段而模型给出了具体金额，最可能的根因是：  
   A. Prompt 语气不对　B. 事实缺口导致模型补全　C. 工具参数错误　D. 温度设置过高
2. 为什么“改 Prompt 后投诉变少”不能证明问题已修复？
3. 判别实验为什么要求一次只改一个变量？
4. 索引版本与政策版本不一致会带来什么现象？
5. 场景题：客服反馈“助手说已经帮客户提交退款，但后台没有退款单”。你会按什么顺序排查？请写出前三个动作与判断依据。

## 答案与解析

1. **B。**没有检索到事实时，模型仍可能生成看起来合理的数字，这属于事实缺口；A 影响表达不影响事实来源；C 与金额编造无直接关系；D 会提高随机性，但不是主因——降低温度并不能创造不存在的事实。
2. 因为投诉变少可能只是发作概率下降。约束类改动会降低编造频率，但根因（缺文档、索引过期）依然存在，换个问法或换个订单就会复现；只有用原输入回放确认输出变化并结合回归集通过率，才能判定修复。
3. 因为多个变量同时变化时，结果变化无法归因到某一个原因。即使问题消失，你也无法确定是哪一项起了作用，后续也无法安全回滚或复现。
4. 会出现“检索有命中但依据错误”的现象：命中的是旧条款，答复与现行政策冲突，且忠实度看起来很高。这类问题最难被语义指标发现，必须靠版本比对与命中片段审计。
5. 顺序建议：第一步取该次 trace，确认 `tool.called` 与参数；第二步看工具是否被调用但返回错误码，还是根本没调用；第三步若未调用，检查工具 schema 是否在上下文里、模型是否被要求必须调用。判断依据是“先确认动作是否发生，再确认模型是否被允许/能够调用”，最后才考虑模型能力或指令措辞。若确认未调用却声称完成，属于对外承诺错误，应立即止血（人工复核该类工单）再修复。
