# 并发、吞吐、首 Token 延迟与总延迟

## 为什么需要学习

售后助手的监控面板上只有一个数字：“平均响应时间 2.1 秒”，且长期稳定。但客服主管反复投诉“卡顿”，质检抽查也发现客服会中途手动刷新页面。团队查了两周才发现问题：平均 2.1 秒是由大量 1 秒内完成的短问答与少量 15 秒的长分析混合平均出来的，而后者的首字延迟已经超过 6 秒——用户在那 6 秒里看不到任何内容。

把延迟压成一个平均数，会同时掩盖三件事：用户等待第一个字的感受、逐字输出是否流畅、以及高峰期排队把请求推到了多长的队伍里。

> **核心结论：** 延迟不是一个数字而是四个：排队多久、首个字多快、每个字多快、整段多久；其中任何一个恶化都会让体验崩掉，而平均值通常看不见它们。

## 学习目标

完成本课后，你能够：

- 从请求时间戳拆出首 Token 延迟（TTFT）、每 token 时间（TPOT）与端到端延迟。
- 区分并发、吞吐与 goodput，并解释为什么高吞吐不等于好体验。
- 用 Little 定律把峰值 QPS 与平均时长换算成并发需求，并说明它在什么条件下失效。
- 根据“排队、预填充、解码”三类归因选择对应的优化手段。

## 业务场景

售后助手的交互是“客服提问 → 检索 → 生成 → 人工确认 → 调工具”。其中生成是流式的：客服要在 1 秒内看到第一个字，否则会认为系统卡住；整段答复通常在 8 秒内完成，超过就会打断节奏。

一次请求的耗时实际分布在多处：检索政策与订单（可并行，约 150–400ms）、模型预填充（随输入长度增长）、解码（随输出 token 数增长）、工具调用往返（可能 300ms 到数秒）、以及高峰期排队。团队需要把“卡顿”这个模糊投诉落到具体一段上。

## 核心概念

| 指标 | 定义 | 计算方式 | 对体验的影响 |
| --- | --- | --- | --- |
| *首 Token 延迟* (TTFT) | 从请求到达至收到第一个输出 token 的时间 | 首字时间 − 到达时间 | 决定“是否感觉卡住” |
| *每 token 时间* (TPOT/ITL) | 首字之后相邻 token 的平均间隔 | (末字时间 − 首字时间) ÷ (输出 token 数 − 1) | 决定“读起来是否流畅” |
| *端到端延迟* | 从请求到达到最后一个 token 的时间 | 末字时间 − 到达时间 | 决定“多久能确认完” |
| *并发* | 同一时刻在处理的请求数 | 到达率 × 平均停留时间 | 决定资源占用与排队 |
| *吞吐* | 单位时间完成的 token 或请求数 | 完成量 ÷ 时间窗口 | 决定单位成本 |
| *goodput* | 满足 SLO 的请求吞吐 | 达标请求数 ÷ 时间窗口 | 决定“有用的产能” |
| *尾延迟* | P95/P99 分位上的延迟 | 排序后取分位 | 决定投诉与口碑 |
| *队列时延* | 请求在调度队列中等待的时间 | 开始处理时间 − 入队时间 | 高峰期的主要恶化项 |

<u>高吞吐不等于好体验</u>：把批大小调大可以显著提高 token/秒，代价是每个请求要等更久才能开始；goodput 才是把两者合并后的指标。

## 工作原理

一次售后请求的耗时按顺序分解为六段：

1. **网络与鉴权**：客户端到网关、令牌校验，通常几十毫秒，但要留意跨地域调用。
2. **检索**：政策检索与订单查询可并行发起，取最慢的一支；这一步失败会直接导致后面答错，而不是变慢。
3. **排队**：请求进入推理引擎队列等待可用 KV 与批位置；并发越高、上下文越长，这一段越长。
4. **预填充**：一次前向计算读完整段输入，耗时近似随输入 token 数线性增长；前缀缓存命中可显著缩短。
5. **解码**：逐 token 生成，耗时 ≈ 输出 token 数 × TPOT；TPOT 受批大小与显存带宽影响。
6. **工具往返与人工确认**：工具调用要加网络与下游系统耗时；人工确认属于业务流程，不应计入模型延迟但必须计入端到端体验。

并发模型决定了“等待”是否浪费资源。同步阻塞模型下，一个工作进程在等模型返回的 6 秒里什么也做不了，并发上限等于工作进程数；异步模型在等待期间可以处理其他请求，因此同样的进程数能支撑更高并发——<u>但异步并不会让 GPU 变快</u>，它只是把排队从应用层挪到了引擎层，排队时延依然存在。

Little 定律给出并发与到达率的关系：`并发 ≈ 到达率 × 平均停留时间`。12 QPS、平均 6 秒，对应约 72 个并发。它的前提是系统处于稳定状态且不丢弃请求；一旦触发限流或超时，这个换算会低估真实压力。

## 架构与选型

| 手段 | 主要改善 | 代价 | 何时不该用 |
| --- | --- | --- | --- |
| 流式输出 | TTFT 感知（用户立即看到进展） | 前端与断线重连复杂度上升 | 结果需要整体校验后才允许展示 |
| 前缀缓存 | 预填充耗时 | 需保证前缀稳定，缓存失效会突变 | 前缀每次都变（如时间戳在系统提示里） |
| 限制输出长度 | 端到端延迟与成本 | 答复可能被截断 | 需要完整条款或长解释的场景 |
| 分级路由（小模型先答） | 平均延迟与成本 | 复杂问题质量下降 | 高风险金额与合规判断 |
| 增加副本 | 排队时延 | 固定成本上升 | 瓶颈在单请求解码而非排队 |
| 预取与并行检索 | 检索段耗时 | 可能产生无用调用 | 检索结果高度依赖上一步输出 |

选型的判断依据是“瓶颈在哪一段”。如果 P95 的 TTFT 高但 TPOT 正常，问题通常在排队或预填充；如果 TTFT 正常而 TPOT 抖动，问题在批组成与显存带宽；如果两者都正常但端到端超时，问题多半在工具往返或人工确认环节。

## 最小示例

下面的脚本从五个时间戳样本计算四项指标与 goodput。设计意图是展示“平均值掩盖长尾”：平均 TTFT 是 0.8 秒，看起来达标，但 P95 达到 2.2 秒。

环境：Python 3.8+，仅标准库。

```python
import math

# 每条样本：请求号、到达时间、首字时间、末字时间、输出 token 数（单位：秒）
SAMPLES = [
    ("T-1001", 0.00, 0.45, 3.45, 60),
    ("T-1002", 0.10, 1.20, 6.10, 100),
    ("T-1003", 0.20, 0.30, 1.30, 25),
    ("T-1004", 0.30, 2.50, 9.80, 120),
    ("T-1005", 0.40, 0.55, 2.05, 30),
]

def breakdown(row):
    _, arrive, first, last, n_out = row
    ttft = first - arrive                       # 首字延迟：包含排队 + 预填充
    e2e = last - arrive                         # 端到端：再叠加解码
    # 输出 n 个 token 之间有 n-1 个间隔；用 n-1 而不是 n，避免把预填充时间摊进 TPOT
    tpot = (last - first) / (n_out - 1) if n_out > 1 else 0.0
    return ttft, tpot, e2e

def p95(values):
    """最近秩法。样本很少时 P95 会等于最大值，这是需要警惕的统计假象。"""
    ordered = sorted(values)
    rank = math.ceil(0.95 * len(ordered))       # 秩从 1 开始
    return ordered[rank - 1]

rows = [(row[0], *breakdown(row)) for row in SAMPLES]
for rid, ttft, tpot, e2e in rows:
    print(f"{rid} TTFT {ttft*1000:.0f}ms TPOT {tpot*1000:.0f}ms E2E {e2e*1000:.0f}ms")

avg = lambda xs: sum(xs) / len(xs)              # 平均值只用于对照，不用于判定
print(f"平均 TTFT {avg([r[1] for r in rows])*1000:.0f}ms "
      f"平均 TPOT {avg([r[2] for r in rows])*1000:.0f}ms "
      f"平均 E2E {avg([r[3] for r in rows])*1000:.0f}ms")

print(f"P95 TTFT {p95([r[1] for r in rows])*1000:.0f}ms "
      f"P95 E2E {p95([r[3] for r in rows])*1000:.0f}ms")

# SLO：首字 1 秒内、整段 8 秒内；两者都满足才算“有用产能”
ok = sum(1 for _, ttft, _, e2e in rows if ttft <= 1.0 and e2e <= 8.0)
print(f"满足 SLO 的请求 {ok}/{len(rows)} = {ok/len(rows):.0%}")
```

输出（本机 `python3` 实测）：

```text
T-1001 TTFT 450ms TPOT 51ms E2E 3450ms
T-1002 TTFT 1100ms TPOT 49ms E2E 6000ms
T-1003 TTFT 100ms TPOT 42ms E2E 1100ms
T-1004 TTFT 2200ms TPOT 61ms E2E 9500ms
T-1005 TTFT 150ms TPOT 52ms E2E 1650ms
平均 TTFT 800ms 平均 TPOT 51ms 平均 E2E 4340ms
P95 TTFT 2200ms P95 E2E 9500ms
满足 SLO 的请求 3/5 = 60%
```

三个结论值得记住：平均 TTFT 是 0.8 秒，“看起来达标”，但有两个请求超过 SLO，goodput 只有 60%；`T-1002` 的 TTFT 是 1.1 秒，而它的解码速度并不慢，说明它慢在排队或预填充；`T-1003` 的 TPOT 明显更低，是因为输出短、批竞争小。

另外要注意 <u>P95 在 5 个样本上就是最大值</u>。真实监控至少需要数百个样本才能让 P95 稳定；样本不足时，正确的表述是“观察到一次 2.2 秒”，而不是“P95 = 2.2 秒”。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/latency.py`；无需网络。

步骤：

1. 运行 `python3 /tmp/latency.py`，核对每条样本的 TTFT、TPOT、E2E。
2. 把 `T-1004` 的到达时间从 0.30 改为 0.35，观察 TTFT 与平均值的变化——它们变化的方向是否一致？
3. 给 `SAMPLES` 增加 20 条 TTFT 在 0.3–0.6 秒之间的短请求，重跑，观察 P95 与 goodput 如何被“稀释”。
4. 把 `n_out` 为 25 的那条改为 200，观察 TPOT 与 E2E 的变化，判断这条请求的瓶颈是排队还是解码。
5. 修改 SLO 阈值（如 TTFT 改为 0.5 秒），观察 goodput 变化幅度。

预期结果：第 2 步说明单点变化对平均值影响很小，但对 P95 可能是决定性；第 3 步说明样本分布改变会让分位数与达标率同时变化，因此指标必须绑定样本口径；第 4 步说明输出长度直接决定端到端，长输出必须单独统计。

验证方法：改动后先手算一两条期望值，再与脚本输出比对；若不一致，检查是否误用了 `n_out` 而不是 `n_out - 1`。

清理方法：`rm /tmp/latency.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 平均延迟正常但客服抱怨卡顿 | 指标只统计平均，长尾被短请求稀释 | 按输入长度分桶看 P95/P99 | 改为分位数与分桶监控，并对长请求单独设 SLO |
| 首字很慢但逐字输出流畅 | 排队或预填充耗时，解码正常 | 把 TTFT 拆成排队时间与预填充时间 | 提高副本、缩小前缀、启用前缀缓存 |
| 首字正常但整段超时 | 输出过长或工具往返慢 | 统计输出 token 数与工具耗时占比 | 限制输出、并行化工具调用、拆分任务 |
| 并发升高后 TPOT 明显变差 | 批组成变大，显存带宽成为瓶颈 | 对比不同并发下的 TPOT 曲线 | 限制单批 token 上限，或扩容副本 |
| 客户端已断开但资源仍被占用 | 未处理流式中断，生成继续跑完 | 查看断开连接后是否仍有 token 消耗 | 支持取消传播，断开即终止生成 |

## 安全与生产注意事项

**<u>给模型调用设置很短的超时并自动重试，会在高峰期制造重试风暴，把一次排队变成一次雪崩。</u>** 重试会成倍放大对后端与供应商的请求量，而供应商的限流恰好在这个时刻最紧；应使用带抖动的退避、重试预算与熔断，并让上游降级路径明确可见。

**<u>流式响应被中断后若不停掉生成，既浪费成本也可能在断开后继续向日志写入敏感内容。</u>** 客户端断线、页面刷新、客服切换工单都是常态，必须把取消信号传导到推理层，并确认断开后的残留输出不会进入可被他人检索的存储。

另外两条：延迟监控数据本身可能包含订单号与客户信息，聚合与存储要脱敏；用平均值或单一分位数做 SLO 判定会误导决策，SLO 应写明分位数、样本口径与统计窗口。

## 本课总结

- **延迟由排队、预填充、解码三段构成，TTFT 与 TPOT 分别对应“卡不卡”和“顺不顺”。**
- 平均值会掩盖长尾；判定必须用分位数，且要写明样本口径。
- goodput 把“达标”与“吞吐”合并，是比 tokens/s 更贴近业务产能的指标。
- Little 定律把 QPS 与停留时间换算成并发，但它假设系统稳定且不丢弃请求。
- 优化前先归因：排队高扩容，预填充高改前缀，解码慢控制输出长度或调批。

## 思考题

如果客服主管要求“所有请求必须在 2 秒内返回”，而长分析类请求平均需要 9 秒，你会如何回应？请给出你会提出的替代 SLO、度量方式，以及不同类别请求分别对应的处置策略。

参考思路：把单一承诺拆成分级 SLO——短问答 TTFT ≤ 1 秒且端到端 ≤ 4 秒；长分析请求改为“先返回阶段性摘要、再异步补全”，并对其使用“首个有效结果时间”而非整段完成时间。度量上用分位数与达标率（goodput），并明确统计窗口与样本口径。理由是不应为了满足一个不区分场景的数字而牺牲质量，也不应让用户在没有反馈的情况下等待。

## 小测

1. 首 Token 延迟主要由哪两段构成？  
   A. 解码与工具调用　B. 排队与预填充　C. 鉴权与日志　D. 输出长度与温度
2. 为什么 TPOT 要用“输出 token 数 − 1”作为分母？
3. 高吞吐为什么不等于高 goodput？
4. Little 定律在什么情况下会低估真实并发压力？
5. 场景题：监控显示 P95 TTFT 从 0.8 秒升到 3.2 秒，而 P95 TPOT 基本不变、吞吐也略有上升。你会先查什么？请给出判断与两个候选措施。

## 答案与解析

1. **B。**TTFT 包含请求在队列中的等待与对整个输入的预填充；A 属于首字之后的部分；C 通常只有毫秒级；D 影响生成内容与长度，但不是 TTFT 的主要构成。
2. 因为 n 个 token 之间只有 n−1 个间隔。用 n 作分母会把首字之前的预填充时间摊进 TPOT，导致 TPOT 被高估，尤其在输出很短时误差很大。
3. 因为吞吐统计的是完成量，而 goodput 只统计满足 SLO 的请求。把批大小调大能提高 token/秒，但每个请求等待更久，可能全部超出 SLO——这时吞吐上升而 goodput 下降。
4. 当系统不稳定、触发限流或超时时。此时请求被丢弃或快速失败，平均停留时间变短，公式算出的并发反而偏低，而实际排队与重试压力更大。
5. 先查排队与预填充：TTFT 恶化而 TPOT 稳定，典型原因是并发上升导致排队变长，或输入变长使预填充变慢；吞吐略升说明批更满、排队更久。候选措施是增加副本/提高配额，以及缩短前缀或启用前缀缓存；同时确认是否有上游重试放大了请求量。
