# 托管 API、自建推理与混合部署

## 为什么需要学习

晴空商城的售后助手上线三个月后遇到两个同时发生的麻烦。第一，大促期间托管 API 频繁返回 `429`，客服页面出现长达数十秒的空白；第二，法务在合规评审中提出：助手检索订单时会把收件人手机号、地址和退款凭证一起带进请求，这些数据不能发送到境外第三方。

团队随即分成两派：一派主张“全部自建，数据不出内网”，另一派主张“全部托管，别自己运维 GPU”。两派都没有回答真正的问题——哪些请求必须留在内网，哪些请求出网更划算，以及出网这件事由谁在运行时判定。

> **核心结论：** 三种部署形态不是先进程度排序，而是把 GPU、合规责任和运维负担放在不同位置的三种交易；选型的产物是一组可执行的路由规则，而不是一个阵营。

## 学习目标

完成本课后，你能够：

- 用数据边界、单位成本、扩缩容责任、上线速度、运维负担五个维度对比托管 API、自建推理与混合部署。
- 解释为什么“路由判定”必须发生在模型选择之前，并说明判定需要哪些输入。
- 为一个含个人数据、金额与不同时效要求的售后请求写出可执行的路由条件。
- 识别“自建即合规”“混合即两边都接”两类常见误判。

## 业务场景

售后助手的请求链路是：客服提问 → 检索售后政策与订单 → 生成答复或退款建议 → 人工确认 → 调用工具（创建退款单、发短信）。这条链路里同时存在三类约束：

1. **数据约束**：查询订单会带出手机号、地址；退款建议会带出金额与凭证图片描述。
2. **时效约束**：客服在电话中等待，首字延迟超过 3 秒就会被感知为“卡住”；而“批量复核昨天的退款申请”可以等到明天。
3. **成本约束**：平峰每分钟 20 次请求，大促峰值可达平峰的 8 倍，且峰值只持续两小时。

公司政策写明：客户个人数据不得出境，也不得进入第三方训练语料。这条政策直接决定了部分请求的可行路径集合。

## 核心概念

| 概念 | 含义 | 售后助手里的体现 |
| --- | --- | --- |
| *托管 API* | 由供应商提供模型与推理算力，按 token 计费，你只持有密钥与调用代码 | 生成答复、改写话术 |
| *自建推理* | 你在自己的 GPU 或专属实例上部署推理引擎（如 vLLM、TGI），模型权重与请求都在你的网络内 | 处理含手机号、地址的订单问答 |
| *混合部署* | 同一业务同时使用两条路径，由网关按规则分流 | 敏感请求走内网，通用问答走托管 |
| *数据驻留* | 数据在存储与处理时必须留在指定地理或法律边界内 | 客户地址不得出境 |
| *出网* | 请求离开你的网络边界进入第三方系统 | 把订单手机号发给托管 API 即构成出网 |
| *单位经济* | 折算到每一次业务结果的成本，而非单价 | 每次“已解决工单”的成本，而不是每百万 token 价格 |
| *责任边界* | 故障、限流、模型变更由谁负责修复与通知 | 托管侧 429 由供应商配额决定，自建侧由你的容量决定 |

三种形态的关键差异：

| 维度 | 托管 API | 自建推理 | 混合部署 |
| --- | --- | --- | --- |
| GPU 归属 | 供应商 | 你 | 两者都有 |
| 扩缩容由谁做 | 供应商（受配额上限约束） | 你（需要容量规划） | 你决定分流比例 |
| 计费方式 | 按 token，无固定成本 | 按 GPU 小时，空闲也付费 | 固定成本 + 变动成本 |
| 数据是否离开网络 | 是 | 否（除非你主动外发） | 取决于路由判定 |
| 上线速度 | 小时级 | 天到周（镜像、权重、压测） | 慢于纯托管 |
| 主要风险 | 限流、涨价、模型退役 | 容量不足、显存打满、运维人力 | 路由误判、两套配置漂移 |

<u>“自建更便宜”只在 GPU 长期高利用率时成立</u>：如果一张卡每天只忙 20%，它的固定成本会摊到很少的请求上，单位成本通常高于托管 API。

## 工作原理

1. **请求到达网关**：完成身份校验、租户识别、限流令牌桶扣减，并生成 `trace_id`（第五课展开）。
2. **读取判定输入**：请求携带的字段标签（是否含手机号、地址、金额、凭证）、SLA 等级（实时/延后）、当前内网队列深度、当日预算余额。
3. **合规判定先于成本判定**：若请求含受限字段且策略禁止出网，则可行路径集合只剩内网端点；此步不可被“现在托管更便宜”覆盖。
4. **路径选择**：允许出网且内网排队超过阈值时溢出到托管；非实时任务转入批处理；其余走默认路径。
5. **执行**：内网端点把请求放入队列、拼批、生成并返回 `usage`；托管路径带超时、重试与限流。
6. **统一记账与追踪**：两条路径的 token 用量、延迟、错误码写入同一账本与同一套 trace 结构，否则无法比较。
7. **共享版本**：两条路径必须使用同一 *Prompt 版本* 与同一评测集，否则分流后的效果差异无法归因。

第 3 步和第 7 步是最容易被跳过的。跳过第 3 步，合规就退化为“文档里写着不允许”；跳过第 7 步，你会在半年后发现两条路径的回答风格完全不同，却说不清是哪一侧变了。

## 架构与选型

| 场景 | 推荐形态 | 理由 | 何时不适用 |
| --- | --- | --- | --- |
| 概念验证、日请求量低于一万 | 托管 API | 无固定成本，一周内可验证价值 | 数据不能出网 |
| 强数据驻留、内网、离线环境 | 自建推理 | 数据与权重都在边界内 | 负载低且无合规要求时成本过高 |
| 峰值高、均值低（大促型） | 托管为主 + 峰值预留 | 用变动成本吸收尖峰 | 供应商配额低于峰值需求 |
| 稳定高利用率（如全天 60% 以上） | 自建为主 | 固定成本可摊薄，单价可控 | 缺少 GPU 运维能力 |
| 部分数据可出、部分不可出 | 混合部署 | 用路由把两类请求分开 | 没有统一网关与统一评测 |

选型依据可以归结为一个先算后选的顺序：先确认**哪些请求在法律与合同上根本不能出网**，这划出硬边界；再估算**可出网请求的峰值与均值**，判断托管配额是否够用；最后计算**自建的满载利用率**，只有当它足够高、且团队具备 GPU 运维能力时，自建的单位成本才可能更低。

混合部署不是“两边都接上”就完成了。它要求一个统一的网关、一套统一的 Prompt 版本、一套统一的评测集，否则你得到的是两个互不认识的系统。

## 最小示例

下面的脚本演示路由判定。设计意图是把“能不能出网”（合规，硬约束）与“该不该出网”（成本与延迟，软优化）分成两个阶段，让合规判定无法被成本逻辑覆盖。

环境：Python 3.8+，仅标准库，无网络。

```python
# 三个候选路径：内网推理、托管实时 API、托管批处理
SELF = "self-hosted"
HOSTED = "hosted-api"
BATCH = "hosted-batch"

# 一旦出现这些字段，就视为包含受限个人数据；真实系统应由数据分类服务给出，而非硬编码
RESTRICTED = ("phone", "address", "refund_evidence")

def decide_route(req, policy, queue_depth, budget_left):
    """返回 (路径, 理由)。判定顺序本身是设计的一部分：合规 → 时效 → 容量 → 预算。"""
    # 阶段一：合规硬约束。命中受限字段且策略禁止出网时，可行集只剩内网
    has_restricted = any(f in req["fields"] for f in RESTRICTED)
    if has_restricted and not policy["allow_egress_pii"]:
        return SELF, "含受限个人数据，策略禁止出网"

    # 阶段二：非实时任务用异步批处理换更低单价，前提是业务能接受小时级返回
    if req["sla"] == "deferred":
        return BATCH, "非实时请求，批处理单价更低"

    # 阶段三：内网队列积压时溢出到托管，保护首字延迟；仅对允许出网的请求生效
    if queue_depth > policy["max_self_queue"]:
        return HOSTED, "内网排队超过阈值，溢出到托管"

    # 阶段四：预算耗尽时禁止外呼，宁可排队也不产生不可控账单
    if budget_left <= 0:
        return SELF, "预算耗尽，禁止外呼"

    # 默认走内网：数据不出网是最安全的默认值
    return SELF, "默认路径，数据不出网"

POLICY = {"allow_egress_pii": False, "max_self_queue": 20}

cases = [
    ("告警工单 A", {"fields": ["order_id", "phone"], "sla": "realtime"}, 5, 1000),
    ("批量复核 B", {"fields": ["order_id"], "sla": "deferred"}, 5, 1000),
    ("高峰请求 C", {"fields": ["order_id"], "sla": "realtime"}, 48, 1000),
    ("预算耗尽 D", {"fields": ["order_id"], "sla": "realtime"}, 5, 0),
]

for name, req, depth, budget in cases:
    route, reason = decide_route(req, POLICY, depth, budget)
    print(f"{name}: {route}（{reason}）")
```

输出（本机 `python3` 实测）：

```text
告警工单 A: self-hosted（含受限个人数据，策略禁止出网）
批量复核 B: hosted-batch（非实时请求，批处理单价更低）
高峰请求 C: hosted-api（内网排队超过阈值，溢出到托管）
预算耗尽 D: self-hosted（预算耗尽，禁止外呼）
```

四个用例分别验证一条分支：A 证明合规判定优先级最高（即使内网队列空闲也不外发）；B 说明延迟可接受的任务应牺牲时效换单价；C 说明溢出只发生在允许出网的请求上；D 说明预算护栏的兜底行为是“排队”，而不是“换个便宜模型继续外呼”。

关键设计选择是判定顺序。如果把预算判断放在合规之前，A 在预算耗尽时反而会走内网——看起来结果一样，但一旦预算充足就会立刻外发敏感数据；这类顺序错误在小流量测试中几乎不可能暴露。

## 动手实验

前置条件：Python 3.8+；将上面的脚本保存为 `/tmp/route_demo.py`；不需要任何 API Key。

步骤：

1. 运行 `python3 /tmp/route_demo.py`，核对四个用例的输出。
2. 把 `POLICY["allow_egress_pii"]` 改为 `True`，重跑。预期 A 不再命中合规分支，而是按队列与预算继续判定。
3. 把 `max_self_queue` 改为 `3`，重跑。预期 C、D 的路径发生翻转，观察“预算兜底”与“容量溢出”哪个先触发。
4. 给 `cases` 增加一条 `{"fields": ["id_card"], "sla": "deferred"}` 的用例，判断合规与时效哪个优先，并写下你的理由。

预期结果：第 2 步证明合规开关的作用域覆盖所有后续分支；第 3 步证明判定顺序决定行为；第 4 步应当得出“合规优先于时效”——延迟可以等，数据一旦外发无法收回。

验证方法：每次只改一个输入；若结果未变，检查改动是否落在该用例已提前返回的分支之后。

清理方法：`rm /tmp/route_demo.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 大促期间大量 429，页面空白 | 托管配额按分钟计量，峰值超过 TPM/RPM 上限 | 查看响应头中的剩余配额与重试等待时间，对比峰值 QPS | 申请提额、加令牌桶、把可延后任务转批处理 |
| 自建后账单不降反升 | GPU 利用率低，固定成本摊到少量请求 | 统计日均 GPU 忙时占比与每工单成本 | 提高批处理与缓存命中，或把低峰流量交回托管 |
| 两条路径回答风格完全不同 | Prompt 与模型版本未统一，评测集各自为政 | 对比同一批样本在两条路径的输出 | 建立共享的 Prompt 版本号与统一回归集 |
| 合规评审通过但线上仍外发数据 | 路由依据请求体字段硬编码，新增字段未覆盖 | 抽查网关日志中实际出网的请求字段 | 改为数据分类服务打标，字段白名单而非黑名单 |
| 溢出到托管后延迟反而更高 | 未做链路预热，或托管侧也在排队 | 分别统计两段耗时与排队时间 | 设置溢出上限与回退超时，避免“次优路径更慢” |

## 安全与生产注意事项

**<u>把“自建”当作“合规完成”是高频误判。</u>** 数据即使不出网，仍会出现在网关日志、trace、备份、向量库快照与模型权重中；自建只解决了“传输到第三方”这一条，访问控制、留存期限与审计仍要单独设计。

**<u>混合部署最典型的生产事故是路由判定读错标签。</u>** 当数据分类服务故障、返回空标签时，如果代码把“未知”当作“可出网”，敏感请求会被静默外发。正确做法是失败即拒绝（fail-closed），把未知标签一律当作受限处理。

另外两条需要单独确认：托管 API 的日志留存与训练使用政策必须以合同与官方数据使用说明为准，不能凭市场宣传推断；模型权重、推理镜像与依赖包要纳入供应链管理，签名校验与来源固定缺一不可。

## 本课总结

- **三种形态的差异不在“先进程度”，而在 GPU 归属、数据边界与运维责任的分配。**
- 合规判定必须发生在成本判定之前，且未知标签要按受限处理。
- 自建的单位成本只在高利用率下占优，低利用率时固定成本会推高每次业务结果成本。
- 混合部署的成败取决于统一网关、统一 Prompt 版本与统一评测集，而不是同时接了两条链路。
- 选型的交付物应是一份可执行的路由规则表，而不是一句“我们采用混合架构”。

## 思考题

如果公司要求“客户个人数据一律不得出网”，但内网只有两张 GPU、峰值排队已达 90 秒，而托管侧又不允许接收任何脱敏前的字段，你会如何设计既满足合规又不让客服长时间等待的方案？请给出至少两个候选方案、各自的代价，以及你判断优先级的依据。

参考思路：可考虑（a）在内网做字段脱敏后再出网，但需证明脱敏不可逆并接受“脱敏后仍可关联”的风险；（b）对大促峰值做请求分级，把非敏感意图（物流查询、政策咨询）分流到托管，敏感意图排队并显示预计等待；（c）扩容内网或引入独占实例。判断依据应是“合规不可谈判、体验可分级、容量可采购”这个顺序，而不是先降体验再补合规。

## 小测

1. 关于“自建推理更便宜”，下列哪种说法正确？  
   A. 只要请求量足够大，自建一定更便宜　B. 自建是否更便宜取决于 GPU 满载利用率　C. 自建没有固定成本　D. 自建的单位成本与托管完全相同
2. 为什么路由判定要放在模型选择之前？
3. 混合部署中，“统一 Prompt 版本”为什么是必需条件而不是优化项？
4. 数据分类服务返回未知标签时，为什么应默认按受限处理？
5. 场景题：售后助手要在两小时内处理 12 万条历史退款复核（非实时），同时保持在线客服的实时问答。团队只有两张 GPU，且客户手机号不得出网。请给出你的分流方案与理由。

## 答案与解析

1. **B。**自建的成本结构是固定成本加变动成本，只有 GPU 利用率足够高时才能摊薄；A 忽略了利用率；C 错在自建恰好有固定成本；D 错在两种形态的成本结构不同。
2. 因为模型选择只在“可行路径集合”内才有意义。合规与时效先把集合缩小，再在其中比较价格与能力，否则会出现“选了最便宜的模型，却把受限数据发到了境外”。顺序错了，后面所有优化都建立在非法前提上。
3. 因为混合部署的核心价值是“同一业务在两条路径上表现可比”。版本不统一时，分流比例一变，效果指标就跟着变，无法判断差异来自路径还是来自 Prompt；回滚也会变成两个系统的不同步回滚。
4. 因为分类失败意味着系统不知道请求里有什么。把未知当“可出网”会让最坏情况发生且不可逆；把未知当“受限”只会带来延迟与容量压力，这两种代价的量级完全不同。
5. 参考方案：把 12 万条复核全部转批处理并安排在内网低峰执行，因为其 SLA 是小时级；在线问答只保留敏感意图要求内网处理，非敏感意图（政策咨询、物流查询）可出网。理由是合规要求决定“哪些能出网”，SLA 决定“哪些能等”，容量决定“哪些必须排队”。若两张 GPU 仍不足，应采购独占实例或申请提高配额，而不是把敏感请求脱敏后外发——脱敏后的可关联性需要法务确认，不能由工程单方面决定。
