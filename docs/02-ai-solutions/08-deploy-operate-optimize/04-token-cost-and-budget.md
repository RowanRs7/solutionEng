# Token 用量、预算与成本控制

## 为什么需要学习

售后助手的成本在第三个月突然翻了三倍，而请求量只涨了 20%。排查后发现两个叠加因素：为了让答复更“有依据”，团队把检索片段从 3 条增加到 10 条；为了“记得住上下文”，每轮把完整对话历史都带上。一次多轮对话到第 8 轮时，输入 token 已经是首轮的 6 倍。更糟的是，没有任何一个面板显示“每个已解决工单的成本”，账单出来时只能看到一个总数。

成本问题在 AI 系统里有个特殊之处：**它由每次请求的 token 数决定，而 token 数由产品设计决定**。多带一段历史、多检索三条片段、多要求一段解释，都会直接变成钱，且通常在需求评审时没有任何人提起。

> **核心结论：** 成本不是财务指标，而是产品与架构的约束条件；能用“每解决一个工单花多少钱”表达之前，你无法判断任何优化是否值得做。

## 学习目标

完成本课后，你能够：

- 把一次请求的成本拆成未缓存输入、缓存命中输入与输出三部分。
- 用“每工单成本 × 日均工单量”推算月度成本，并说明为什么这个口径比 token 总量更有用。
- 设计告警、降级与熔断三层预算护栏，并给出各自的阈值依据。
- 评估“少检索几条”“缩短输出”“换小模型”三类降本措施的副作用与禁用场景。

## 业务场景

售后助手每天处理 3 万个工单。单次调用的输入由四部分组成：固定系统提示约 1200 token、检索到的政策与订单片段约 1800 token、对话历史约 600 token、客服当前问题约 80 token；输出约 350 token。

业务方希望“答复更完整”，产品方希望“更便宜”，客服希望“更快”。三者都落在同一组数字上。团队已经踩过一次坑：大促期间因为上游重试，单日调用量翻了 3 倍，而预算护栏只有一个“月度上限告警”，等告警发出时已经花掉了当月预算的 70%。

## 核心概念

| 概念 | 含义 | 计费特征 | 售后助手示例 |
| --- | --- | --- | --- |
| *输入 token* | 每次调用发送给模型的内容总量 | 通常单价低于输出 | 系统提示 + 检索片段 + 历史 + 问题 |
| *输出 token* | 模型生成的内容总量 | 通常单价高于输入 | 答复正文、结构化字段 |
| *缓存命中 token* | 与固定前缀一致、被供应商或引擎复用计算的部分 | 通常按折扣单价计费 | 固定的系统提示与政策摘要前缀 |
| *上下文膨胀* | 每次请求携带的上下文随轮次或片段数增长 | 使输入 token 二次增长 | 第 8 轮带全部历史 |
| *成本归因* | 把花费分摊到业务维度（租户、意图、模型、版本） | 不改变总额，改变可见性 | 按“退款类”与“物流类”分摊 |
| *单位经济* | 折算到一次业务结果的成本 | 与业务价值同尺度 | 每已解决工单成本 |
| *预算护栏* | 在超支前触发的告警、降级与熔断机制 | 影响可用性而非账单 | 日预算 80% 告警、100% 降级 |
| *预算熔断* | 预算耗尽时停止外呼或强制走内网 | 直接改变业务行为 | 停止托管调用，只保留内网路径 |
| *批处理折扣* | 以异步完成换取更低单价 | 单价降低、延迟上升 | 非实时退款复核 |

<u>“按 token 计费”不等于“按请求计费”</u>：同样一次请求，输入长度差 10 倍，成本就差一个量级；因此任何请求级的成本看板都必须同时显示 token 分布，而不只是调用次数。

## 工作原理

1. **采集计量数据**：每次调用从响应中读取 `usage`（输入、输出、缓存命中明细），不要用字符数估算——中文与英文、代码与自然语言的切分比例差异很大。
2. **拆分输入构成**：把输入按“固定前缀、检索片段、历史、当前问题”分段统计，才能知道是哪个设计决策在花钱。
3. **判断缓存可用性**：只有稳定且位于前缀的内容才可能命中缓存；把时间戳、随机 ID 放进系统提示会让缓存永远失效。
4. **统计输出分布**：输出长度通常呈长尾，少数超长答复可能贡献大部分输出费用，需要单独看 P95 与最大值。
5. **按业务维度归因**：至少按“意图、模型版本、租户”三个维度汇总，否则无法判断成本上升是需求变化还是实现退化。
6. **三层护栏**：预算使用到某个比例时告警并通知负责人；接近上限时降级（缩短上下文、切换小模型、转内网）；耗尽时熔断（禁止外呼）。
7. **月度复盘单位成本**：用“每已解决工单成本”而非“总 token 数”评估优化效果，否则节省可能只是把工作量转移到了人工。

## 架构与选型

| 降本手段 | 作用点 | 典型效果 | 副作用 | 何时不该用 |
| --- | --- | --- | --- | --- |
| 稳定前缀 + 前缀缓存 | 输入（缓存命中部分） | 固定提示部分单价显著下降 | 前缀一变即失效 | 前缀内容需要随时变化 |
| 检索片段裁剪与重排 | 输入（检索部分） | 输入 token 明显下降 | 可能漏掉关键条款 | 涉及金额、时效、例外条款时 |
| 历史摘要替代全量历史 | 输入（历史部分） | 随轮次增长变为近似常数 | 早期细节丢失 | 需要精确复述前文承诺 |
| 输出长度与格式约束 | 输出 | 输出 token 下降 | 答复可能不完整 | 需要完整条款或合规声明 |
| 分级路由（小模型先答） | 输入 + 输出单价 | 平均单价下降 | 复杂问题质量下降 | 高风险金额判断、投诉升级 |
| 异步批处理 | 单价 | 单价显著下降 | 延迟上升 | 客服实时等待的场景 |
| 限制重试次数 | 总调用量 | 避免倍数放大 | 失败率上升需兜底 | 下游短暂抖动且可安全重试 |

选型判断的原则是：**先削减不承载信息的 token，再考虑降低单价**。检索里的重复段落、与问题无关的历史、模板化的客套话都不承载信息；而金额上限、例外条件、时限属于必须保留的信息，削减它们是把成本转移到事故上。

## 最小示例

下面的脚本计算单工单成本、月度投影，并演示三层护栏的判定。单价使用**演示用假设值**（真实价格请查官方定价页，见延伸阅读），重点在于计算结构与护栏逻辑。

环境：Python 3.8+，仅标准库。

```python
# 演示用假设单价，单位：每百万 token 的美元价格；不代表任何供应商的实际报价
PRICE = {
    "small": {"input": 0.20, "cached": 0.05, "output": 0.80},
    "large": {"input": 2.00, "cached": 0.50, "output": 8.00},
}

def ticket_cost(model, system, retrieved, history, question, output):
    """按三段计费：未缓存输入、缓存命中输入、输出。分段是为了看清谁在花钱。"""
    cached = system                       # 只有稳定前缀才有机会走缓存单价
    fresh = retrieved + history + question
    p = PRICE[model]
    return (fresh * p["input"] + cached * p["cached"] + output * p["output"]) / 1e6

def monthly(cost, per_day, days=30):
    return cost * per_day * days

def guard(projected, budget):
    """三层护栏：ok → warn → degrade → block。返回动作而非抛异常，避免直接打挂业务。"""
    ratio = projected / budget
    if ratio >= 1.0:
        return "block", "禁止外呼，转内网或人工"
    if ratio >= 0.8:
        return "degrade", "缩短上下文 + 路由小模型"
    if ratio >= 0.6:
        return "warn", "通知负责人并冻结非必要实验"
    return "ok", "无动作"

# 基线：系统提示 1200、检索 1800、历史 600、问题 80、输出 350
base = ticket_cost("small", 1200, 1800, 600, 80, 350)
print(f"小模型单工单成本: ${base:.6f}")
print(f"小模型月成本(3 万/日): ${monthly(base, 30000):.2f}")

# 把检索片段从 1800 裁到 900：只削不承载信息的重复段落
trimmed = ticket_cost("small", 1200, 900, 600, 80, 350)
print(f"检索减半后月成本: ${monthly(trimmed, 30000):.2f}"
      f"（节省 {1 - trimmed / base:.1%}）")

# 换成大模型：单价差异会直接放大到月度账单
big = ticket_cost("large", 1200, 1800, 600, 80, 350)
print(f"大模型月成本(同参数): ${monthly(big, 30000):.2f}")

for budget, label in ((600, "裁剪前"), (600, "裁剪后")):
    projected = monthly(base if label == "裁剪前" else trimmed, 30000)
    action, detail = guard(projected, budget)
    print(f"预算 {budget} 美元 → {label}判定: {action}（{detail}）")
```

输出（本机 `python3` 实测）：

```text
小模型单工单成本: $0.000836
小模型月成本(3 万/日): $752.40
检索减半后月成本: $590.40（节省 21.5%）
大模型月成本(同参数): $7524.00
预算 600 美元 → 裁剪前判定: block（禁止外呼，转内网或人工）
预算 600 美元 → 裁剪后判定: degrade（缩短上下文 + 路由小模型）
```

几点值得注意：第一，**大模型的月度成本是小模型的 10 倍**，而两者在“读政策条款”这类任务上的差距往往没有 10 倍那么大——模型分级是最大的单一杠杆。第二，检索减半只省 21.5%，因为系统提示已被缓存、输出又占不小比例；这说明<u>降本前必须知道成本被哪一段占据</u>，否则容易砍错地方。第三，同一份预算下，裁剪让系统从 `block` 退回到 `degrade`，护栏的作用是留出缓冲，而不是等到超支才报警。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/cost.py`；无需 API Key。

步骤：

1. 运行 `python3 /tmp/cost.py`，核对单工单成本与月度投影。
2. 把 `system` 从 1200 改为 0（模拟没有可缓存前缀），重跑，观察成本上升幅度并解释原因。
3. 把检索片段从 1800 改为 6000（模拟“多检索更保险”），观察月度成本变化。
4. 把输出从 350 改为 900（模拟“要求更完整的解释”），比较与第 3 步哪个影响更大，并说明为什么。
5. 把护栏阈值从 0.6/0.8/1.0 改为 0.9/0.95/1.0，讨论更激进的阈值会带来什么后果。

预期结果：第 2 步说明缓存前缀是低成本设计的一部分；第 3、4 步的对比说明输出 token 单价更高时，输出长度对成本的影响可能超过检索；第 5 步说明阈值越靠近 1.0，留给降级的时间越少，容易直接触发熔断。

验证方法：改动后手算一条期望成本与脚本比对；若差异很大，检查是否把缓存部分重复计入了未缓存输入。

清理方法：`rm /tmp/cost.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 请求量平稳但账单翻倍 | 上下文膨胀：历史或检索片段随版本增加 | 对比两个版本的输入 token 分布 | 加历史摘要、检索去重与重排，限制片段数 |
| 缓存从未命中 | 系统提示含时间戳、随机 ID 或用户信息 | 查看 `usage` 中缓存命中字段是否始终为 0 | 把变量移出前缀，保持前缀稳定 |
| 预算告警发出时已超支 | 只有月度告警，缺少日级与小时级窗口 | 检查告警窗口与聚合维度 | 增加日/小时窗口，并配置降级动作 |
| 单工单成本下降但投诉上升 | 砍掉了承载关键条款的上下文 | 对比裁剪前后的完整性评测 | 恢复关键字段，改为削减重复与无关片段 |
| 成本归因无法对齐财务账单 | 归因维度缺失或与计费口径不一致 | 抽查若干调用能否复算到账单 | 统一以 `usage` 为准，补充批次与重试标识 |
| 重试导致调用量翻倍 | 客户端无重试预算，超时后立即重发 | 统计重试次数与原始请求数之比 | 加退避、重试预算与幂等键 |

## 安全与生产注意事项

**<u>没有预算熔断的系统，一次循环重试或一次提示注入让模型输出变长，就可能产生远超预期的账单。</u>** 成本事故的典型形态是“代码没有 bug、业务也没有增长，只是某个分支开始无限重试”。护栏必须是代码路径上的硬约束，而不是依赖人工看板。

**<u>为了降本而删减检索内容，会直接削弱合规相关条款的完整性，属于以事故换成本。</u>** 金额上限、退货时限、例外条件必须保留；任何削减都应经过完整性评测与人工抽检，并在变更记录里写明放弃了哪些信息。

另外两条：成本归因数据如果直接以手机号或订单号作为标识，会把个人数据扩散到分析平台，应使用内部租户与工单 ID；提示注入还可能诱导模型输出超长内容以放大成本，输出长度上限应作为防护的一部分，而不只是成本优化。

## 本课总结

- **成本由每次请求的 token 结构决定，而 token 结构由产品设计决定。**
- 单工单成本比 token 总量更能指导决策，因为它与业务价值同尺度。
- 输入按“固定前缀、检索、历史、问题”分段统计，才能定位成本增长来源。
- 优先削减不承载信息的 token，再考虑换用更低单价；两者顺序颠倒会引发质量事故。
- 护栏要有告警、降级、熔断三层，且阈值要留出执行降级的时间。

## 思考题

如果业务方要求“答复必须完整引用政策原文”，而这会让输出 token 翻倍、月度成本超出预算 40%，你会提出哪些方案？请给出每个方案对成本、质量与合规的影响，以及你建议的决策依据。

参考思路：可考虑（a）只对涉及金额与时效的答复引用原文，其余改为摘要 + 条款编号；（b）把完整引用改为“可展开的结构化引用”，正文只给结论与编号；（c）提高预算或分级定价。判断依据是“引用原文的目的是可核验”，而可核验不等于全文粘贴；若能把条款编号与版本锁定，就能在降低成本的同时保持可追溯。

## 小测

1. 下列关于 token 计费的说法，正确的是：  
   A. 输入与输出单价通常相同　B. 缓存命中部分通常按折扣单价计费　C. 请求数决定成本　D. 字符数可以准确换算 token
2. 为什么把时间戳放进系统提示会破坏缓存收益？
3. 为什么“单工单成本”比“总 token 数”更适合做优化目标？
4. 预算护栏为什么需要“降级”而不只是“告警”和“熔断”？
5. 场景题：某版本把检索片段从 3 条增加到 10 条，成本上升 45%，但完整性评测分数只提高 2 分。你会批准这个版本吗？请说明判断与替代方案。

## 答案与解析

1. **B。**缓存命中部分通常有折扣单价；A 错在输出单价通常更高；C 错在同样请求数下 token 长度可差一个量级；D 错在字符到 token 的换算依赖分词器与语言，不能通用换算。
2. 因为缓存依赖“前缀完全一致”。时间戳每次不同会让前缀逐字节变化，缓存永远无法命中，于是固定提示每次都按未缓存单价计费，而它往往占总输入的很大一部分。
3. 因为它把成本与业务结果绑定，能分辨“节省”是效率提升还是把工作转移给人工；总 token 数无法反映每单位价值的变化，也无法与预算审批对话。
4. 因为告警只通知、熔断会直接拒绝服务，两者之间缺少“还能继续做但更省”的区间。降级让系统在预算紧张时仍能完成关键业务，同时把成本压回预算内。
5. 不建议直接批准。成本上升 45% 换 2 分提升，投入产出比不合理；替代方案是先做检索去重与重排（往往能在保持完整性的同时减少片段数），再对高价值意图单独放开片段数，并用同一评测集验证。若 2 分提升对应的是关键条款召回，则应保留该部分并单独核算，而不是全量放开。
