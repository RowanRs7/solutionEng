# AI Trace 与端到端可观测性

## 为什么需要学习

一位客服投诉：“昨天下午有个客户问耳机的退货，助手说要寄回，政策明明写着拆封不退。”值班工程师打开日志，只看到一条 `POST /after-sales/answer 200 OK`，耗时 3.4 秒。日志里没有命中哪几段政策、没有模型看到的完整输入、没有工具返回了什么——他无法判断是检索没召回、片段过期，还是模型把否定句读成了肯定句。

指标能告诉你“哪里变慢了”，日志能告诉你“发生了什么事件”，但它们都无法回答 AI 系统最常问的那句话：**这一次答复，模型到底看到了什么，然后做了什么**。这正是 *trace* 要解决的问题。

> **核心结论：** AI 系统的可观测性不是“把日志加长”，而是把一次请求拆成可对齐的环节，并让每个环节的输入、输出、耗时与版本都能被单独检视。

## 学习目标

完成本课后，你能够：

- 为一条售后问答链路画出 span 结构，并说明父子关系与传播方式。
- 用“自耗时”而不是“总耗时”判断瓶颈落在检索、预填充、解码还是工具。
- 写出至少五个必填属性（模型、版本、token、检索命中、工具结果码），并解释各自的排障用途。
- 说明采样与脱敏对“事后能否复原问题”的影响，并给出可执行的折中方案。

## 业务场景

售后助手的一次请求会经过：网关鉴权 → 输入护栏（敏感词、越权检测）→ 政策检索 → 订单检索 → 模型调用（预填充 + 解码）→ 工具调用（创建退款单）→ 返回。

其中任何一环都可能出错：政策库更新后旧片段仍被召回；订单接口超时导致检索为空但模型照样作答；工具参数把金额单位从元写成角。团队需要的不是更多日志行，而是能把“这一次回答”复原成一条时间线的结构。

## 核心概念

| 概念 | 含义 | 在本链路中的位置 |
| --- | --- | --- |
| *trace* | 一次端到端请求的完整记录，由多个 span 组成 | 一次客服提问 |
| *span* | 一个有开始与结束的操作，带名称、属性与父子关系 | 检索、模型调用、工具调用 |
| *自耗时* | span 总耗时减去其子 span 耗时之和 | 判断时间真正花在哪一层 |
| *上下文传播* | 把 trace ID 与父 span ID 通过请求头传给下游 | 网关 → 检索服务 → 推理服务 |
| *GenAI 语义约定* | 对模型调用 span 的属性命名规范（操作名、模型名、token 用量等） | 统一不同厂商的埋点字段 |
| *采样* | 只保留部分 trace 以控制成本 | 高流量下降低存储 |
| *脱敏* | 在写入前遮蔽手机号、地址、证件等敏感字段 | 输入与检索结果 |
| *回放* | 用记录的输入重新执行一次链路，复现问题 | 排障与评测样本生成 |

四类信号回答的问题不同：

| 信号 | 回答的问题 | 对售后助手的作用 | 局限 |
| --- | --- | --- | --- |
| 指标 | 整体是否变慢/变差 | 发现 P95 延迟上升、错误率抬升 | 无法定位单次请求 |
| 日志 | 某个时刻发生了什么事件 | 记录异常、重试、降级 | 缺少环节间的因果与时序 |
| trace | 这一次请求内部各环节的顺序与耗时 | 定位到具体检索或工具 | 不回答“答复是否正确” |
| 评测样本 | 这类问题是否普遍答错 | 把 bad trace 沉淀为回归集 | 需要人工或评分器参与 |

## 工作原理

1. **在入口生成 trace**：网关为每个请求创建 trace ID 与根 span，写入租户、意图、Prompt 版本等业务属性。
2. **逐层创建子 span**：护栏、政策检索、订单检索、模型调用、工具调用各自创建 span，并通过请求头传递 `trace_id` 与父 span ID。
3. **记录输入与输出摘要**：检索 span 记录查询语句、命中片段 ID 与相似度；模型 span 记录模型名、版本、输入/输出 token 数、结束原因；工具 span 记录参数摘要与结果码。
4. **结束时计算耗时与自耗时**：自耗时 = 本 span 时长 − 子 span 时长之和；它把“根 span 3.7 秒”还原成“解码 2.08 秒、工具 0.61 秒”。
5. **写入前脱敏与截断**：对手机号、地址、证件做遮蔽，对超长文本截断但保留前若干字符与哈希，便于比对而不泄露。
6. **采样与保留**：错误请求与慢请求全量保留，正常请求按比例采样；采样决策要在入口做，否则会丢失子 span。
7. **回流为评测样本**：把人工判定为错误的 trace 连同输入、检索结果、模型输出一起归档，成为回归集的一条样本。

第 4 步与第 7 步是区分“有 trace”与“trace 有用”的关键。没有自耗时，你只有一个总分；没有回流，同样的错误会在每次改动后重演。

## 架构与选型

| 方案 | 适用场景 | 优势 | 局限 |
| --- | --- | --- | --- |
| 自建 span 表（写数据库） | 早期、请求量小、需要与业务数据联查 | 完全可控、查询自由 | 需要自己实现采样、索引与保留策略 |
| 标准追踪后端（OpenTelemetry + 后端） | 多服务、需要与现有运维体系打通 | 生态成熟、跨语言、支持上下文传播 | 属性命名需遵守约定，否则各服务字段不一致 |
| LLM 专用可观测平台 | 需要 Prompt/检索/评分一体化视图 | 开箱即用的 AI 视图与评测联动 | 数据出网与留存政策需评估 |
| 只记应用日志 | 原型验证 | 成本最低 | 无法还原时序与环节归属 |

选型依据是三条：**是否需要跨服务追踪**（是则必须用标准上下文传播）、**数据能否出网**（不能则选自建或私有化部署）、**是否需要与评测联动**（需要则优先支持样本导出的方案）。三条都指向同一件事：字段命名要统一，否则后端换了、字段对不上，历史数据就废了。

## 最小示例

下面的脚本用扁平列表模拟真实追踪系统的存储形态（span 通过 `parent` 关联），打印缩进树、计算自耗时，并演示写入前的脱敏。

环境：Python 3.8+，仅标准库。

```python
import re

# 扁平的 span 列表：id / parent / 名称 / 开始 / 结束（秒）/ 属性
SPANS = [
    {"id": "a1", "parent": None, "name": "POST /after-sales/answer", "start": 0.000, "end": 3.700},
    {"id": "b1", "parent": "a1", "name": "guard.input", "start": 0.010, "end": 0.060},
    {"id": "b2", "parent": "a1", "name": "retrieve.policy", "start": 0.070, "end": 0.310},
    {"id": "b3", "parent": "a1", "name": "retrieve.order", "start": 0.320, "end": 0.665},
    {"id": "b4", "parent": "a1", "name": "llm.chat", "start": 0.675, "end": 3.025},
    {"id": "c1", "parent": "b4", "name": "llm.prefill", "start": 0.675, "end": 0.945},
    {"id": "c2", "parent": "b4", "name": "llm.decode", "start": 0.945, "end": 3.025},
    {"id": "b5", "parent": "a1", "name": "tool.create_refund", "start": 3.035, "end": 3.645},
]

children = {}                                    # 先建索引：parent -> 子 span 列表
for s in SPANS:
    children.setdefault(s["parent"], []).append(s)
for kids in children.values():
    kids.sort(key=lambda s: s["start"])          # 按时间排序，树才读得懂

def dur(s):
    return s["end"] - s["start"]

def self_time(s):
    """自耗时 = 总时长 − 子 span 时长之和；子 span 串行时不重叠，可直接相减。"""
    raw = dur(s) - sum(dur(k) for k in children.get(s["id"], []))
    return max(0.0, raw)                         # 浮点误差可能得到 -0.000，钳到 0

def render(node, depth=0):
    print(f"{'  ' * depth}{node['name']:<28}{dur(node)*1000:>7.0f}ms"
          f"  (self {self_time(node)*1000:>5.0f}ms)")
    for kid in children.get(node["id"], []):
        render(kid, depth + 1)

render(SPANS[0])

# 只按“总耗时”排序会总是选中 llm.chat；按自耗时才能找到真正占用时间的那一段
slow = sorted((s for s in SPANS if s["parent"]),
              key=self_time, reverse=True)[:3]
print("自耗时最高的三处: " + "、".join(f"{s['name']}({self_time(s)*1000:.0f}ms)" for s in slow))

# 写入前脱敏：手机号留前 3 后 4，订单号留前缀，便于人工比对又不泄露
PHONE = re.compile(r"(1[3-9]\d)\d{4}(\d{4})")
ORDER = re.compile(r"(SO\d{4})\d{8}")

def redact(text):
    text = PHONE.sub(r"\1****\2", text)         # 13812340000 → 138****0000
    return ORDER.sub(r"\1****", text)           # SO202612345678 → SO2026****

raw = "联系人 13812340000，订单 SO202612345678，退款金额 899 元"
print("脱敏示例: " + redact(raw))
```

输出（本机 `python3` 实测）：

```text
POST /after-sales/answer       3700ms  (self   105ms)
  guard.input                      50ms  (self    50ms)
  retrieve.policy                 240ms  (self   240ms)
  retrieve.order                  345ms  (self   345ms)
  llm.chat                       2350ms  (self     0ms)
    llm.prefill                     270ms  (self   270ms)
    llm.decode                     2080ms  (self  2080ms)
  tool.create_refund              610ms  (self   610ms)
自耗时最高的三处: llm.decode(2080ms)、tool.create_refund(610ms)、retrieve.order(345ms)
脱敏示例: 联系人 138****0000，订单 SO2026****，退款金额 899 元
```

三点值得注意：第一，`llm.chat` 总耗时 2350ms 看起来最大，但它的自耗时是 0——时间全在 `llm.decode` 里，只按总耗时排序会把优化方向指向“换个模型”而不是“控制输出长度”。第二，`retrieve.policy` 与 `retrieve.order` 各约 240ms 和 345ms 且串行执行，这是一处明显的并行化机会。第三，脱敏保留了前 3 后 4，既能与客服核对又不暴露完整号码——<u>如果直接丢弃整段文本，你就失去了事后复原问题的能力</u>。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/trace.py`；无需网络。

步骤：

1. 运行 `python3 /tmp/trace.py`，核对树结构、自耗时与脱敏结果。
2. 把 `tool.create_refund` 的结束时间改为 5.200，重跑，观察根 span 与自耗时排序的变化（注意根 span 结束时间也要同步延长，否则子 span 会超出父 span）。
3. 把 `llm.decode` 拆成两个 span（如 `decode.seg1`、`decode.seg2`），观察自耗时的分配结果。
4. 为 `llm.chat` 增加属性 `{"gen_ai.request.model": "small-2026-08", "gen_ai.usage.input_tokens": 3680}`，并说明这两个字段在排障时分别回答什么问题。
5. 修改 `redact`，让它同时遮蔽地址中的门牌号，并说明为什么不能用“整段哈希”代替脱敏。

预期结果：第 2 步应看到自耗时排序第一的 span 变成工具调用，说明瓶颈从解码转移到工具；第 3 步说明 span 粒度决定了你能细分到什么程度；第 5 步说明哈希不可逆但无法人工核对，脱敏要在“可核对”与“不泄露”之间取平衡。

验证方法：检查每个子 span 的时间区间是否落在父 span 内；若出现负自耗时，通常是子 span 时间越界或重叠。

清理方法：`rm /tmp/trace.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 有 trace 但看不到检索内容 | 只记录了耗时，未记录命中片段 ID 与相似度 | 打开一条 trace 检查属性字段 | 补齐片段 ID、相似度、索引版本 |
| 根 span 耗时远大于子 span 之和 | 缺少中间环节的 span（如排队、序列化） | 对比日志时间戳与 span 边界 | 为未埋点环节补 span，尤其是排队与网络 |
| 采样后错误请求找不到 trace | 采样在入口按固定比例随机，错误也被丢弃 | 检查错误请求是否有 trace | 错误与慢请求全量保留，其余按比例采样 |
| trace 中携带完整手机号与地址 | 脱敏只在应用日志做了，未覆盖追踪链路 | 抽查属性值是否含敏感模式 | 在 span 写入前统一脱敏，字段白名单 |
| 不同服务字段名不一致，无法联查 | 未采用统一的语义约定 | 对比各服务的属性键名 | 统一用 GenAI 语义约定的属性名并做兼容映射 |
| 回放时结果与线上不同 | 未记录 Prompt 版本、模型版本与索引版本 | 检查 trace 是否含版本字段 | 把版本三元组写入根 span |

## 安全与生产注意事项

**<u>trace 中保存完整 Prompt 与检索原文，会形成一个比生产库更容易被访问的敏感数据副本。</u>** 追踪后端通常由多个团队共用、权限更宽、留存更久；手机号、地址、凭证描述一旦写入，等于绕过了原有的访问控制。必须在写入前脱敏，并对字段做白名单。

**<u>为目标请求开启全量采样、又长期不清理，会让存储成本和泄露面同时失控。</u>** 全量保留只应针对错误与慢请求，且要设置留存期限与访问审计；否则“为了排障”会变成“永久保存所有客户对话”。

另外两条：把 trace 导出给外部评测或分析工具前，要确认数据出境与供应商留存政策；版本三元组（Prompt、索引、模型）必须写入根 span，否则回滚与复盘时无法证明当时运行的到底是哪个组合。

## 本课总结

- **可观测性要回答“模型看到了什么、做了什么”，这需要环节级的 span，而不是更长的日志。**
- 自耗时才能定位瓶颈；总耗时排序会把子环节的时间算到父环节头上。
- 必填属性至少包括模型与版本、token 用量、检索命中 ID、工具结果码、Prompt 与索引版本。
- 错误与慢请求应全量保留，正常请求才适合采样。
- 脱敏要在写入前完成，并保留可人工核对的线索。

## 思考题

如果合规要求“客户对话原文不得离开内网”，但排障又需要看到模型输入，你会如何设计可观测性方案？请说明保留什么、遮蔽什么、由谁在什么条件下可以访问，以及如何验证这套机制有效。

参考思路：可以在内网部署追踪后端，原文只在受控存储中短期保留（如 7 天）并做字段级遮蔽；对外只同步结构化的耗时与命中 ID。访问需按工单申请并留审计日志。验证方式是定期抽查 trace 属性是否含敏感模式，并用一次模拟事故演练确认排障人员能否在无原文条件下定位到检索或工具环节。

## 小测

1. 下列哪一项最适合用 trace 而不是指标来回答？  
   A. 今天 P95 延迟是否上升　B. 这一次答复为什么引用了过期政策　C. 本月总 token 消耗　D. 服务是否存活
2. 为什么 `llm.chat` 的总耗时可能很大而自耗时为 0？
3. 采样策略为什么要把错误请求排除在随机采样之外？
4. “版本三元组”指哪三项，为什么必须写入根 span？
5. 场景题：某次投诉的 trace 显示检索命中了两段互相矛盾的政策，模型选择了较旧的一段。你会如何修改埋点与流程，让同类问题下次能被更快发现？

## 答案与解析

1. **B。**trace 保留单次请求的环节输入与输出，能回答“看到了什么”；A、C 属于聚合指标；D 属于健康检查。
2. 因为它的时间全部消耗在子 span（预填充与解码）里。自耗时减去子 span 后接近 0，说明它只是容器，优化应指向具体子环节，而不是“把这个 span 变快”。
3. 因为错误请求正是最需要被检视的样本。随机采样会让它们以同样比例丢失，导致“出问题却没有 trace”；正确做法是错误与慢请求全量保留，其余按比例采样。
4. Prompt 版本、检索索引版本、模型版本。它们共同决定一次请求的实际行为；缺任一项都无法在复盘时证明当时运行的组合，也无法安全回滚。
5. 埋点侧应记录每段片段的来源 ID、版本与生效时间，并在片段冲突时打标；流程侧应增加“检索结果冲突”告警，把冲突样本自动归入评测集，并要求生成环节在冲突时明确提示需人工确认。这样同类问题会在下一次冲突出现时被自动发现，而不是等投诉。
