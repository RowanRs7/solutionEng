# GPU、推理端点与容量

## 为什么需要学习

决定自建推理后，团队买了一台 80GB 显存的机器，按“显存除以模型大小”估出“能跑 5 个 8B 模型副本”，于是把线上流量全切过来。第一周就出现两种现象：白天高峰期客服排队 40 秒，夜间显存占用却不到 30%；某次升级镜像后容器反复重启，日志只有一行 `CUDA out of memory`。

问题不在于 GPU 不够，而在于把显存当成“模型文件的容器”。显存里真正决定能同时服务多少请求的，是随对话长度增长的 KV Cache；而吞吐取决于引擎是否能把不同长度的请求拼进同一批。

> **核心结论：** GPU 容量不是“能装下几个模型”，而是“在目标上下文长度下能同时容纳多少个活跃序列”；这决定了并发上限，也决定了副本数。

## 学习目标

完成本课后，你能够：

- 用“层数 × KV 头数 × 头维度 × 字节数”估算每 token 的 KV Cache 占用。
- 解释连续批处理为什么能提高吞吐，以及它对首字延迟的影响。
- 根据峰值 QPS、平均响应时长与单副本并发上限，推算需要的副本数。
- 说明 `gpu_memory_utilization` 设置过高时为什么会引发 OOM 循环。

## 业务场景

售后助手的自建路径要处理“含手机号的订单问答”。它的请求有两种典型形态：一是短问答，输入约 800 token、输出约 150 token；二是“把这单的物流、退款政策、历史工单一起看”的长上下文请求，输入约 6000 token、输出约 300 token。

工作日平峰每分钟 120 次请求，平均每次 6 秒返回；大促峰值是平峰的 3 倍。团队需要回答三个问题：一张 80GB 卡能同时服务多少请求？峰值需要几张卡？如果上下文从 4k 涨到 8k，容量会怎么变？

## 核心概念

| 概念 | 含义 | 在容量估算中的作用 |
| --- | --- | --- |
| *权重* | 模型参数本身占用的显存，8B 模型 FP16 约 16GB | 与并发无关的固定开销 |
| *KV Cache* | 生成过程中缓存的历史 Key/Value，避免重复计算注意力 | 随“序列数 × 长度”线性增长，是并发的主约束 |
| *PagedAttention* | 把 KV Cache 按固定大小块管理，像操作系统分页一样按需分配 | 减少显存碎片，使实际可容纳序列数接近理论值 |
| *连续批处理* | 每个解码步重新组批，完成的请求立即退出、新请求立即加入 | 提高 GPU 利用率与吞吐，但会增加排队等待 |
| *静态批处理* | 一批请求必须等最长的那个生成完才一起返回 | 实现简单，短请求被长请求拖住 |
| *显存利用率上限* | 引擎允许占用的显存比例（如 0.9），剩余留给激活值与通信缓冲 | 设得过高会 OOM，设得过低浪费容量 |
| *前缀缓存* | 对相同前缀（如固定 system prompt）复用已算好的 KV | 降低预填充耗时，等效提升容量 |
| *副本* | 一个独立的推理进程与显存占用单元 | 扩缩容的最小单位 |

批处理策略的差异：

| 策略 | 短请求等待 | GPU 利用率 | 适用场景 |
| --- | --- | --- | --- |
| 静态批处理 | 被同批最长请求拖住 | 中 | 离线批任务、长度整齐 |
| 连续批处理 | 可立即加入下一解码步 | 高 | 在线服务、长度差异大 |
| 连续批处理 + 分页 KV | 低 | 最高 | 长上下文混合负载 |

## 工作原理

1. **加载权重**：模型参数常驻显存，8B FP16 约占 16GB；量化会降低这部分，但通常牺牲精度。
2. **预留 KV 池**：引擎按显存利用率上限划出一块区域专供 KV Cache，其余留给激活值、CUDA 图与通信缓冲。
3. **请求入队**：请求先进入调度队列；队列长度直接决定排队时延。
4. **预填充**：一次前向计算处理整个输入，生成首个 token。输入越长，这一步越慢，因此它与首字延迟强相关。
5. **逐步解码并组批**：每个解码步把当前所有活跃序列拼成一批；某个序列生成结束后立即退出，队列中的新请求补位。
6. **KV 增长与抢占**：序列每生成一个 token 就追加一份 KV；显存不足时引擎会抢占或让新请求等待，表现为延迟抖动。
7. **扩缩容判定**：依据队列深度与 KV 使用率扩容副本，而不是依据 GPU 计算利用率——后者在批处理下经常显示很高但仍有排队。

## 架构与选型

| 端点形态 | 适用场景 | 不适用场景 | 权衡 |
| --- | --- | --- | --- |
| 专用常驻副本 | 稳定在线流量、要求低首字延迟 | 流量极低或波动极大 | 可用性高，但空闲成本固定 |
| 按需/无服务器 GPU | 突发流量、内部工具 | 严格首字延迟要求 | 无空闲成本，但冷启动可达数十秒 |
| 托管 API | 无合规限制的通用问答 | 数据不得出网 | 无容量规划负担，受配额与价格约束 |
| 混合（内网副本 + 托管溢出） | 敏感与通用流量并存 | 缺少统一网关 | 兼顾合规与峰值，但复杂度最高 |

容量规划的顺序比公式更重要：先确定**目标上下文长度**（它决定单序列 KV 大小），再确定**目标并发**（由峰值 QPS 与平均时长推出），最后才谈**副本数**。反过来先买卡再问“能跑多少”，几乎一定会得到错误结论。

## 最小示例

下面的脚本按“每 token KV → 单序列 KV → 可用 KV → 并发 → 副本数”的顺序估算容量。参数取一个 8B、32 层、8 个 KV 头、头维度 128 的典型结构；真实模型请替换为你使用的模型配置。

环境：Python 3.8+，仅标准库。

```python
LAYERS, KV_HEADS, HEAD_DIM, BYTES = 32, 8, 128, 2   # FP16 每元素 2 字节

def kv_bytes_per_token():
    """每个 token 的 KV 占用：K 与 V 各一份，所以乘 2。"""
    return 2 * LAYERS * KV_HEADS * HEAD_DIM * BYTES

def gib(nbytes):
    return nbytes / 1024 ** 3                        # 用 GiB，避免与厂商标注的 GB 混淆

PER_TOKEN = kv_bytes_per_token()
print(f"每 token KV: {PER_TOKEN} 字节 ({PER_TOKEN/1024:.1f} KiB)")

VRAM, WEIGHTS = 80, 16                              # 80GB 卡，8B FP16 权重约 16GiB
UTIL, RESERVE = 0.9, 2.0                            # 预留 10% 给激活与通信，另留 2GiB 缓冲
usable = VRAM * UTIL - WEIGHTS - RESERVE            # 真正能给 KV Cache 的显存
print(f"可用 KV 显存: {usable:.1f} GiB")

def capacity(seq_tokens, safety=0.7):
    """safety: 实际部署不会把 KV 池打满，留 30% 余量吸收长度波动。"""
    per_seq = seq_tokens * PER_TOKEN
    theoretical = int(usable * 1024 ** 3 // per_seq)
    return per_seq, theoretical, int(theoretical * safety)

for seq in (4096, 8192):
    per_seq, theo, real = capacity(seq)
    print(f"{seq} token → 单序列 {gib(per_seq):.2f} GiB，理论并发 {theo}，安全系数后 {real}")

PEAK_QPS, AVG_SECONDS = 12, 6.0                     # 峰值 12 请求/秒，平均 6 秒完成
need = PEAK_QPS * AVG_SECONDS                       # Little 定律：并发 ≈ 到达率 × 停留时间
print(f"峰值需并发 {need:.0f}（{PEAK_QPS} QPS × {AVG_SECONDS:.0f} 秒）")

for seq in (4096, 8192):
    _, _, real = capacity(seq)
    replicas = -(-int(need) // real)                 # 向上取整，宁可多一个副本
    print(f"{seq} token 上限 → 需要副本数 {replicas}")
```

输出（本机 `python3` 实测）：

```text
每 token KV: 131072 字节 (128.0 KiB)
可用 KV 显存: 54.0 GiB
4096 token → 单序列 0.50 GiB，理论并发 108，安全系数后 75
8192 token → 单序列 1.00 GiB，理论并发 54，安全系数后 37
峰值需并发 72（12 QPS × 6 秒）
4096 token 上限 → 需要副本数 1
8192 token 上限 → 需要副本数 2
```

结果的关键在于：**同样的卡，上下文从 4k 翻到 8k，可承载并发正好减半**，副本需求从 1 变成 2。如果只看“模型能不能装下”，这个变化完全不会被发现，而它恰好是长上下文功能上线后最常见的容量事故来源。

脚本里的 `safety=0.7` 与 `RESERVE=2.0` 不是精确常数，而是把“长度波动、激活峰值、碎片”折算成一个可调的经验余量。调参时应当用压测数据反推，而不是凭感觉取整数。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/capacity.py`；无需 GPU。

步骤：

1. 运行 `python3 /tmp/capacity.py`，核对每 token KV 与两种上下文下的并发数。
2. 把 `UTIL` 从 0.9 改为 0.95，观察可用 KV 与副本数变化，并思考为什么生产环境不建议把利用率设到 0.95 以上。
3. 把 `LAYERS` 改为 48、`KV_HEADS` 改为 8（模拟更大的模型），重跑，记录并发下降幅度。
4. 把 `KV_HEADS` 从 8 改为 32（模拟没有使用分组查询注意力的模型），对比每 token KV 的变化倍数。
5. 把 `AVG_SECONDS` 改为 15，观察副本需求如何变化，并解释这与“用户问得更复杂”之间的关系。

预期结果：第 2 步显示提高利用率只带来约 7% 的容量提升，却显著压缩了抗波动余量；第 3、4 步说明 KV 占用由层数与 KV 头数共同决定；第 5 步说明平均时长翻倍时并发需求近似翻倍。

验证方法：改单个参数后重跑，检查输出是否与手算一致；若不一致，先确认单位是 GiB 还是 GB。

清理方法：`rm /tmp/capacity.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 容器反复重启，日志只有 OOM | 显存利用率上限过高，KV 池挤占激活值空间 | 观察启动后空闲时的显存占用与峰值 | 下调利用率上限，或缩短最大上下文 |
| 高峰期排队 40 秒、夜间显存空转 | 只按平均负载规划副本，未做峰值扩容 | 对比队列深度与显存使用率的时间曲线 | 按队列深度扩缩容，或用溢出到托管的兜底 |
| 长上下文功能上线后吞吐骤降 | 单序列 KV 翻倍，可容纳序列减半 | 用脚本重算 4k 与 8k 的并发上限 | 限制最大输入长度，或增加副本 |
| 短请求延迟被长请求拖高 | 使用静态批处理，或批大小上限过大 | 按输入长度分桶统计延迟 | 改用连续批处理，并限制单批 token 总数 |
| 扩容后延迟没有改善 | 新副本冷启动未完成，或流量未打散 | 查看新副本的首个请求耗时 | 预热副本、保持最小副本数、按连接数打散 |

## 安全与生产注意事项

**<u>把显存利用率设到接近 1.0 会引发 OOM 循环，而重启期间该副本承载的请求全部失败。</u>** 显存需求随输入长度波动，预留空间被吃掉后引擎没有降级手段，只能崩溃；崩溃又触发重启与重新加载权重，形成可用性雪崩。

**<u>单副本部署等于把整个业务押在一次进程崩溃上。</u>** 推理进程、CUDA 驱动、镜像升级任何一环出问题都会导致全量不可用；至少两个副本并配合滚动升级，是最低要求。

另外两条：多个租户共享同一 GPU 时，必须确认显存与算力隔离手段（分区或独立副本），否则一个租户的长请求会拖慢其他人，甚至读到不属于自己的残留缓存；模型权重、tokenizer 与推理镜像要固定来源并校验哈希，未经签名的权重是典型的供应链入口。

## 本课总结

- **决定 GPU 并发上限的是 KV Cache，而不是模型文件大小。**
- KV 占用随上下文长度线性增长，4k 到 8k 会让可承载并发减半。
- 连续批处理提高吞吐，但排队时间会体现为首字延迟，必须与 SLO 一起设定。
- 副本数应由“峰值 QPS × 平均时长”推出的并发需求除以单副本上限，再向上取整。
- 显存利用率与安全系数是抗波动余量，压得越紧，OOM 与排队抖动风险越高。

## 思考题

售后助手准备上线“历史工单全量分析”，输入长度从 800 token 涨到 12000 token。如果坚持单次请求不切分，你会选择扩容、限制长度还是改用其他模型？请给出量化依据、代价与对客服体验的影响。

参考思路：先用本课的公式算出 12k 上下文下的单序列 KV 与可用并发，再结合峰值并发需求推算副本数与成本；如果成本不可接受，可考虑分层策略——短问答走当前模型，长分析走异步批处理或更大显存的实例。判断依据是“这项功能是否需要实时交互”，而不是“能不能跑起来”。

## 小测

1. 显存中随并发请求数线性增长的部分是：  
   A. 模型权重　B. KV Cache　C. CUDA 驱动　D. tokenizer 词表
2. 连续批处理相比静态批处理，主要改善了什么？
3. 为什么把 `gpu_memory_utilization` 设成 0.98 风险很高？
4. 上下文长度从 4k 增加到 8k，理论上可承载的并发会如何变化？
5. 场景题：一张 80GB 卡在 4k 上下文下可承载约 75 个并发序列，峰值需求是 120 并发。你会选择加卡、缩上下文还是溢出到托管？请说明判断顺序。

## 答案与解析

1. **B。**KV Cache 与“活跃序列数 × 序列长度”成正比；A 是固定开销；C 与并发基本无关；D 占用极小且固定。
2. 改善了 GPU 利用率与整体吞吐：完成的请求立即退出，新请求立即补位，短请求不必等长请求结束。代价是排队与抢占会带来看起来随机的延迟抖动。
3. 因为显存需求会随输入长度、批组成与激活峰值波动，预留空间被压缩后引擎没有降级手段，只能 OOM 崩溃；崩溃重启期间该副本上的请求全部失败，容易演变为可用性事故。
4. 近似减半。KV 占用与序列长度成正比，可用 KV 总量不变时可容纳序列数同比减少，这也是长上下文功能上线后最容易忽略的容量影响。
5. 判断顺序建议是：先确认能否用溢出到托管兜底（合规是否允许），再确认业务能否接受缩短上下文或分段摘要（影响质量，需要评测），最后才是加卡（成本决策）。理由是可逆且低成本的手段优先，加卡是最后手段；直接缩上下文而不评测属于以质量换容量，必须走变更评审。
