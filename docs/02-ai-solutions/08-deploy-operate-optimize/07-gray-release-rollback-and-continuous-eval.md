# 灰度、回滚、迁移与持续评测

## 为什么需要学习

售后助手的一次“小改动”上线后，两天内客服投诉量上升了 40%。改动内容是：把系统提示里“优先引用最新政策”改成“必须引用政策原文”，同时重建了向量索引。负责人发现时想回滚，却发现自己只能回滚代码——Prompt 存在配置中心、索引在另一个服务、模型版本由网关固定。他分别操作了三处，中间隔了 40 分钟，期间线上同时跑着“新 Prompt + 旧索引”的组合，而那个组合从未被评测过。

AI 系统的发布单元不是“一次代码部署”，而是**Prompt、索引、模型、参数、工具契约**的组合。任意一项变更都会改变行为，而它们分散在不同系统里；没有统一的版本与回滚点，所谓“回滚”只是把其中一块拨回去。

> **核心结论：** AI 系统的可回滚性取决于“版本三元组能否作为一个整体切换”；做不到这一点，灰度与回滚都只是心理安慰。

## 学习目标

完成本课后，你能够：

- 按变更类型（Prompt、索引、模型、参数、工具契约）选择灰度粒度与回滚动作。
- 用稳定哈希分桶实现按比例放量，并解释为什么不能用随机数分桶。
- 设计一条从离线回归到金丝雀守卫的持续评测流水线，并给出每一关的通过条件。
- 识别“回滚不彻底”与“评测集过拟合”两类典型失效。

## 业务场景

售后助手的发布节奏是每周一次。本周的变更有四项：系统提示改写、政策索引重建、模型从旧版本升到新版本、退款工具新增“部分退款”参数。

风险并不相同：提示改写影响全部意图的表达；索引重建影响所有政策类问答的事实来源；模型升级影响推理风格与工具调用倾向；工具参数变更影响写操作。团队需要一套统一的做法，让每次变更都能小范围验证、快速回滚，并且留下可比较的证据。

## 核心概念

| 概念 | 含义 | 售后助手里的体现 |
| --- | --- | --- |
| *变更单元* | 一次发布中作为一个整体切换的最小集合 | Prompt + 索引 + 模型版本三件套 |
| *版本三元组* | Prompt 版本、索引版本、模型版本 | `p-17 / idx-2026-10-05 / m-2026-09` |
| *金丝雀* | 只放给一小部分流量，观察守卫指标后再放量 | 5% 工单走新版本 |
| *影子流量* | 新版本接收同样输入但不返回给用户，只做对比 | 双跑并比较答复差异 |
| *回滚点* | 可一键恢复到的完整版本组合 | 上一组三元组与其配置 |
| *守卫指标* | 决定继续或回滚的判定指标与阈值 | 任务成功率、投诉率、单工单成本 |
| *评测门禁* | 上线前必须通过的离线评测阈值 | 回归集通过率不低于基线 |
| *回归集* | 覆盖历史故障与关键场景的固定样本 | 含“运费险”那条事故样本 |

变更类型与处置方式的对应关系：

| 变更类型 | 影响面 | 灰度粒度 | 回滚动作 | 必须跑的评测 |
| --- | --- | --- | --- | --- |
| Prompt 文案 | 全部意图的表达与格式 | 按请求百分比 | 切回旧 Prompt 版本指针 | 回归集 + 格式校验 |
| 索引重建 | 政策类问答的事实来源 | 按意图或租户 | 切回旧索引别名 | 检索召回率 + 完整性 |
| 模型升级 | 推理风格、工具调用倾向 | 按百分比 + 影子双跑 | 切回旧模型 ID | 回归集 + 工具调用成功率 |
| 采样参数 | 输出多样性 | 无需灰度，可配置回退 | 恢复参数 | 稳定性抽样 |
| 工具契约 | 写操作与金额 | 按租户白名单，先只读 | 禁用新参数 | 契约测试 + 幂等验证 |

<u>索引与 Prompt 必须作为一个整体回滚</u>：单独回滚其中一个，会得到从未被评测过的组合。

## 工作原理

1. **登记变更单元**：把本次发布涉及的所有版本号写成一份清单，并生成一个 `release_id`。
2. **离线回归**：用回归集跑新组合，比较通过率与关键指标；低于门禁则不允许进入下一步。
3. **影子对比**：把新组合接到真实流量的副本上（不返回给用户），统计答复差异率与工具调用差异，重点看“新版本多做了什么、少做了什么”。
4. **小比例金丝雀**：按稳定分桶放 5% 流量，观察守卫指标；分桶要保证同一工单始终落在同一侧，否则用户会在两个版本之间跳变。
5. **守卫判定**：任一指标越过阈值即回滚；阈值应在发布前写好，而不是看到数据后临时决定。
6. **逐步放量**：5% → 25% → 50% → 100%，每一档都要重新判定，且保留一段观察窗口覆盖长尾请求。
7. **固化与复盘**：把新三元组写入发布记录；把本次发现的问题样本加入回归集，使下一次发布自动覆盖它。

第 3 步与第 5 步是多数团队缺失的。没有影子对比，你只能等用户投诉；没有预置阈值，回滚就会变成“再观察一下”的政治决策。

## 架构与选型

| 发布方式 | 适用场景 | 优势 | 风险 |
| --- | --- | --- | --- |
| 按流量百分比金丝雀 | 大多数 Prompt 与模型变更 | 影响面可控、可量化 | 分桶不稳定会导致体验跳变 |
| 租户白名单 | B 端客户、需要事先沟通 | 可逐个客户验证 | 样本偏差大，早期客户风险高 |
| 影子双跑 | 模型升级、Prompt 大改 | 零用户影响即可对比 | 成本翻倍，且无法验证真实反馈 |
| 按意图灰度 | 只改某类问答（如物流） | 精准、风险局部 | 需要意图识别准确 |
| 全量直接发布 | 纯参数回退、配置修正 | 最快 | 仅适用于可立即回滚且影响极小 |

选型依据是“**影响是否可逆**”：写操作（退款、发券）必须先只读验证、再白名单、最后放量；纯表达类改动可以走百分比金丝雀。另一个依据是“**样本是否需要真实反馈**”：模型风格类改动适合影子双跑，涉及用户满意度的改动必须真实放量。

## 最小示例

下面的脚本实现稳定分桶与守卫判定。设计意图是说明两件事：分桶必须确定性，回滚必须由预置阈值自动触发。

环境：Python 3.8+，仅标准库。

```python
import hashlib

def bucket(key, seed, buckets=100):
    """稳定分桶：同一 key 与 seed 下结果恒定，放量时只会新增用户，不会来回跳。"""
    digest = hashlib.sha256(f"{seed}:{key}".encode()).hexdigest()
    return int(digest[:8], 16) % buckets      # 取前 8 位十六进制，足够分散

def assign(ticket_id, rollout, seed="p-17"):
    b = bucket(ticket_id, seed)
    return ("canary" if b < rollout else "stable"), b

# 5% 放量：观察哪些工单进入金丝雀
ids = [f"SO-{i:04d}" for i in range(1, 21)]
picked = [(tid, b) for tid, (side, b) in ((t, assign(t, 5)) for t in ids) if side == "canary"]
print(f"20 条工单中 {len(picked)} 条进入 canary: " +
      "、".join(f"{tid}(bucket {b})" for tid, b in picked))

# 守卫阈值：方向 + 允许的恶化幅度。发布前写死，避免事后解释
LIMITS = {
    "task_success": ("lower", 0.02),      # 成功率下降 2 个百分点即回滚
    "complaint_rate": ("higher", 0.005),  # 投诉率上升 0.5 个百分点即回滚
    "cost_per_ticket": ("higher", 0.0001),# 单工单成本上升 0.0001 美元即回滚
    "p95_ttft_sec": ("higher", 0.15),     # 首字 P95 恶化 150ms 即回滚
}

BASE = {"task_success": 0.86, "complaint_rate": 0.020,
        "cost_per_ticket": 0.00084, "p95_ttft_sec": 1.10}
CANARY = {"task_success": 0.83, "complaint_rate": 0.021,
          "cost_per_ticket": 0.00102, "p95_ttft_sec": 1.05}

def guard(current, base, limits):
    reasons = []
    for metric, (worse, threshold) in limits.items():
        delta = current[metric] - base[metric]
        if worse == "higher" and delta >= threshold:
            reasons.append(f"{metric} 上升 {delta:.6f}（阈值 {threshold}）")
        elif worse == "lower" and -delta >= threshold:
            reasons.append(f"{metric} 下降 {-delta:.3f}（阈值 {threshold}）")
    return ("rollback" if reasons else "advance"), reasons

action, reasons = guard(CANARY, BASE, LIMITS)
print(f"守卫判定: {action}")
for r in reasons:
    print(f"  - {r}")
```

输出（本机 `python3` 实测）：

```text
20 条工单中 3 条进入 canary: SO-0008(bucket 1)、SO-0009(bucket 0)、SO-0012(bucket 4)
守卫判定: rollback
  - task_success 下降 0.030（阈值 0.02）
  - cost_per_ticket 上升 0.000180（阈值 0.0001）
```

两个设计点在真实系统里经常被做错。第一，**用随机数分桶会让同一工单在刷新时跳到另一侧**，用户看到前后不一致的答复，投诉率反而上升；确定性分桶保证“谁在实验组”在放量过程中只增不减。第二，**守卫阈值必须在发布前固化**：如果等看到数据再讨论“这算不算变差”，回滚就会被拖延成事故。

注意这次判定中投诉率虽然上升但没有越过阈值，而成功率与成本越界——这说明单一指标不足以守护发布，**成本与质量必须同时设阈值**。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/release.py`；无需网络。

步骤：

1. 运行 `python3 /tmp/release.py`，核对进入 canary 的工单与守卫判定。
2. 把 `rollout` 从 5 改为 25，重跑，确认原来进入 canary 的工单仍然在 canary 中（只增不减）。
3. 把 `seed` 改为 `"p-18"`，观察分桶结果完全不同，并解释为什么换 Prompt 版本时不应换 seed。
4. 把 `LIMITS` 中 `task_success` 的阈值改为 0.05，重跑，观察判定是否仍为回滚，并说明放宽阈值的后果。
5. 增加一条 `tool_error_rate` 指标与阈值，构造一个越界场景，确认回滚原因被正确列出。

预期结果：第 2 步验证分桶单调性；第 3 步说明 seed 变化会让实验组重排，导致同一用户体验跳变；第 4 步说明放宽阈值只是推迟发现问题，并未消除退化；第 5 步说明守卫应覆盖写操作类风险。

验证方法：同一输入连续运行两次，输出必须完全一致；若不一致，说明用了随机数或加了时间戳。

清理方法：`rm /tmp/release.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 回滚后问题依旧 | 只回滚了 Prompt，索引/模型仍是新的 | 对比回滚后的三元组与发布记录 | 把三元组做成一个可原子切换的配置 |
| 用户反映答复忽好忽坏 | 分桶用了随机数或按请求而非按用户 | 统计同一工单多次请求的归属 | 改为按稳定键（工单/租户）哈希分桶 |
| 灰度指标正常，全量后崩 | 灰度样本是低峰或低风险意图 | 检查灰度时段的流量构成 | 让灰度覆盖完整时段与意图分布 |
| 评测通过但线上变差 | 评测集与线上分布不一致，或已过拟合 | 比较评测集与线上样本的意图分布 | 定期从线上抽样更新回归集 |
| 回滚耗时 40 分钟 | 各组件分别操作，缺少统一开关 | 演练一次回滚并计时 | 建立配置中心与一键切换 |
| 新版本工具调用翻倍 | 模型升级后倾向重复调用 | 统计单轮调用次数分布 | 加单轮调用上限与幂等键 |

## 安全与生产注意事项

**<u>回滚不彻底会让线上长时间运行一个从未被评测过的版本组合，其风险高于不发布。</u>** 一定要把 Prompt、索引、模型、工具开关放入同一发布单元，并演练“一键回滚 + 计时”，把回滚时间作为发布准入条件之一。

**<u>灰度人群若包含高风险写操作（大额退款、批量发券），一次错误就会产生不可逆的资金影响。</u>** 写操作类变更必须走“只读验证 → 白名单租户 → 限制金额上限 → 放量”的顺序，并保留人工复核环节。

另外两条：评测集本身是资产也是风险，若被用于调参反复优化，会迅速过拟合——应保留一份不参与调优的“留出集”；影子双跑会把真实客户数据复制到新版本链路，需确认数据使用范围与留存政策。

## 本课总结

- **AI 的发布单元是版本三元组，而不是一次代码部署；可回滚性取决于它能否整体切换。**
- 变更类型决定灰度粒度与回滚动作，写操作必须比表达类改动更保守。
- 确定性分桶保证实验组只增不减，避免用户体验跳变。
- 守卫阈值要在发布前写死，且必须同时覆盖质量、成本与写操作风险。
- 回归集要把历史事故变成样本，才能让每次发布自动覆盖上次的坑。

## 思考题

如果团队只有两名工程师，无法为每次发布准备影子双跑与完整回归集，你会如何设计一个“最小可行”的发布流程？请给出你保留的环节、放弃的环节、以及放弃后如何用其他手段补偿风险。

参考思路：保留“版本三元组登记 + 确定性分桶 + 预置守卫阈值 + 一键回滚演练”四项，因为它们决定可逆性；放弃影子双跑（成本翻倍）与逐档放量中的中间档，改为 5% → 100% 两档并延长观察窗口。补偿手段是用线上抽样替代影子对比，并把每次投诉转化为回归样本，让回归集随时间自然增长。关键是承认“没有评测”这件事必须用更强的守卫与更快的回滚来对冲。

## 小测

1. 下列哪项不属于“版本三元组”？  
   A. Prompt 版本　B. 索引版本　C. 模型版本　D. 客服排班表
2. 为什么灰度分桶不能用随机数？
3. 影子双跑的主要价值与主要局限分别是什么？
4. 回滚时为什么不能只回滚 Prompt？
5. 场景题：某次索引重建后，离线召回率提升 5 个点，但你发现灰度期间投诉率上升了 0.6 个百分点（阈值 0.5）。你会继续放量吗？请说明判断与后续动作。

## 答案与解析

1. **D。**三元组指 Prompt、索引、模型版本；排班表属于运营安排，不影响模型行为，也不参与回滚。
2. 因为随机数会让同一用户/工单在两次请求间落到不同版本，体验前后不一致，且实验数据被污染（同一用户同时贡献两组样本）。确定性哈希保证归属稳定，放量时单调扩张。
3. 价值是零用户影响即可对比新旧版本的输出差异，适合模型升级与 Prompt 大改；局限是成本翻倍，且只能看到“输出差异”，无法获得真实用户反馈与满意度信号。
4. 因为线上行为由组合决定。只回滚 Prompt 会得到“旧 Prompt + 新索引”这种从未评测过的组合，可能比两个新组件更糟，也无法用历史数据解释。
5. 不放量，先回滚或冻结。召回率提升是离线指标，投诉率是真实业务信号，且已越过预置阈值；继续放量等于用未验证的收益覆盖已验证的损害。后续动作：回滚到旧索引，抽取投诉样本检查是否命中错误条款，确认修复后再以更小比例验证，并同时观察召回率与投诉率。
