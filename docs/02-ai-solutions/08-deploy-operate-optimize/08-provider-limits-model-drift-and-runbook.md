# 供应商限流、模型退化与 AI Runbook

## 为什么需要学习

某天上午十点，售后助手的错误率从 0.3% 跳到 18%，客服页面不断出现“系统繁忙”。值班工程师的第一反应是重试，客户端原本就配了“失败重发三次”。十分钟后错误率升到 41%——供应商的限流阈值被自己的重试流量进一步打满，连降级路径也因为同一条链路而失效。

同月还发生了另一件事：没有任何报错、没有告警，答复质量却在两周内缓慢下滑。事后比对发现供应商更新了底层模型版本，而团队把模型 ID 写成了“跟随最新”的别名。

这两件事对应 AI 系统最特殊的一类风险：**你的核心依赖不在自己手里，它既会拒绝你，也会悄悄变化**。

> **核心结论：** 对外部依赖的应对不是“加重试”，而是把限流、退化与退役当成常态事件，用退避、预算、熔断、钉版本与 Runbook 组合成可执行的响应。

## 学习目标

完成本课后，你能够：

- 区分限流（429）、配额耗尽、模型退化与供应商区域性故障的信号特征。
- 设计带抖动的指数退避与重试预算，并说明为什么固定间隔重试会放大故障。
- 为一个 AI 系统编写包含分级、决策人、降级模式与验证步骤的 Runbook。
- 说明“钉住模型版本 + 每日金标集跑分”如何发现静默退化。

## 业务场景

售后助手的托管路径依赖一家供应商。它的配额按“每分钟请求数（RPM）”和“每分钟 token 数（TPM）”双重限制，并按订阅或项目分层。大促期间，客服并发从 40 涨到 300，请求变长（检索片段更多），TPM 先于 RPM 被打满。

同时，团队每季度要面对一次模型版本退役通知：旧版本有明确的停止服务日期，新版本在语气与工具调用倾向上略有不同。若不做准备，退役当天就相当于一次未经评测的全量发布。

## 核心概念

| 概念 | 含义 | 信号或表现 |
| --- | --- | --- |
| *限流* | 供应商在单位时间内拒绝超出配额的请求 | HTTP 429，通常带 `Retry-After` |
| *配额耗尽* | 日/月配额或预算用尽，与瞬时速率无关 | 持续 429 或明确错误码，重试无效 |
| *退避* | 失败后按递增间隔重试 | 间隔 0.5s、1s、2s… |
| *抖动* | 在退避间隔上加入随机量 | 避免大量客户端在同一时刻重试 |
| *重试预算* | 限制重试总量占总请求的比例 | 例如不超过 10% |
| *熔断* | 连续失败后直接拒绝，给下游恢复时间 | 打开后立即返回降级结果 |
| *模型退化* | 模型行为在无发布的情况下变差 | 金标集通过率缓慢下降 |
| *弃用* | 供应商宣布某版本停止服务 | 退役日期与替代版本 |
| *Runbook* | 面向值班人员的可执行处置手册 | 分级、判定、动作、验证、升级 |
| *降级模式* | 主路径不可用时仍能完成核心业务的路径 | 转内网模型、只答政策不给建议 |

四类事件必须先分清，因为处置完全不同：

| 事件 | 典型信号 | 首个动作 | 是否应重试 |
| --- | --- | --- | --- |
| 瞬时限流 | 短时 429，随后恢复 | 退避 + 令牌桶限速 | 是，带抖动 |
| 配额耗尽 | 持续 429/明确配额错误 | 降级或申请提额 | 否，重试无意义 |
| 模型退化 | 无错误但质量指标下滑 | 切回钉住的旧版本并复评 | 不适用 |
| 区域故障 | 大面积超时/5xx | 切备用供应商或内网 | 有限，需熔断 |

## 工作原理

1. **识别事件类型**：先看状态码与时间分布。短时 429 且逐步恢复是限流；持续 429 且跨小时不变多半是配额；无错误但指标下滑是退化；5xx 与超时集中出现是故障。
2. **本地限速**：客户端维护令牌桶，按供应商配额留出安全余量（如配额的 80%），避免把限流打到边界。
3. **退避与抖动**：按指数增长等待时间并加入随机抖动，使重试分散；同时读取 `Retry-After` 并以其为下限。
4. **重试预算与熔断**：限制重试总量，连续失败达到阈值时打开熔断，直接返回降级结果，给下游恢复窗口。
5. **降级路径**：主路径不可用时切换到内网模型、缓存答复或“只给政策原文 + 人工确认”，并明确告知用户当前能力受限。
6. **退化检测**：把模型 ID 钉到具体版本，每日用金标集跑分并与基线比较；连续多日下降即视为退化，先切回旧版本再分析。
7. **弃用管理**：维护版本日历，退役前完成“新版本评测 + 灰度 + 回滚点”，把退役变成计划内发布而不是事故。
8. **Runbook 演练**：每季度至少演练一次限流与退化场景，记录从告警到恢复的时长，并据此修订阈值与责任人。

第 2 步与第 6 步是最容易被省略的：没有本地限速，你的流量会持续顶在配额边缘；没有每日跑分，退化只能靠用户投诉发现。

## 架构与选型

| 方案 | 适用场景 | 优势 | 局限 |
| --- | --- | --- | --- |
| 单供应商 + 重试 | 早期、流量可控 | 实现最简单 | 限流与退役风险集中 |
| 单供应商 + 降级到内网 | 有自建能力、合规要求高 | 主备切换、数据不出网 | 内网容量与质量需验证 |
| 双供应商主备 | 对可用性要求高 | 故障时可切换 | 两套 Prompt 与评测、成本上升 |
| 多供应商按意图路由 | 质量与成本差异明显 | 各取所长 | 路由与一致性复杂度高 |
| 异步批处理兜底 | 非实时任务 | 单价低、避开高峰配额 | 延迟高，不适合在线 |

选型依据：**先算清配额与峰值的差距**（峰值 TPM 是否超过配额的 80%），再决定是申请提额、削峰（排队 + 批处理）还是引入备份路径。多供应商不是免费的可靠性，它要求同一套评测集能在两条路径上跑出可比结果，否则切换后你无法判断质量是否可接受。

## 最小示例

下面的脚本量化“抖动”的作用：同样 1000 个失败请求，固定间隔重试会在同一时刻形成尖峰，而全抖动把它摊平。

环境：Python 3.8+，仅标准库。

```python
import random

def waits(n, jitter, seed=1):
    """生成 n 个请求的重试等待时间。jitter=False 模拟固定间隔重试。"""
    rng = random.Random(seed)                 # 固定种子让结果可复现，便于教学与对比
    base = 0.5
    return [rng.uniform(0, base) if jitter else base for _ in range(n)]

def peak_in_window(ws, width=0.1):
    """统计任意 100ms 窗口内的最大请求数——这才是打向下游的真实压力峰值。"""
    hist = {}
    for w in ws:
        key = int(w // width)                 # 向下取整归入窗口
        hist[key] = hist.get(key, 0) + 1
    return max(hist.values()), len(hist)

for jitter in (False, True):
    ws = waits(1000, jitter)
    peak, spread = peak_in_window(ws)
    label = "全抖动" if jitter else "固定间隔"
    print(f"{label}: 峰值 {peak} 次/100ms，分布在 {spread} 个窗口")

# 重试预算：只有 10% 的请求允许重试，其余直接走降级，避免放大故障
FAILED, BUDGET_RATIO = 1000, 0.10
allowed = int(FAILED * BUDGET_RATIO)
print(f"失败 {FAILED} 个，重试预算 {BUDGET_RATIO:.0%} → 仅允许 {allowed} 次重试，"
      f"其余 {FAILED - allowed} 个直接降级")
```

输出（本机 `python3` 实测）：

```text
固定间隔: 峰值 1000 次/100ms，分布在 1 个窗口
全抖动: 峰值 218 次/100ms，分布在 5 个窗口
失败 1000 个，重试预算 10% → 仅允许 100 次重试，其余 900 个直接降级
```

结论很直接：**固定间隔重试会把 1000 个失败请求压进同一个 100ms 窗口**，等于用你的流量替下游制造一次小型 DDoS；全抖动把峰值摊到多个窗口，下游才有恢复机会。而重试预算的作用是给放大效应设上限——当 90% 的失败请求直接降级时，故障半径被限制在单次请求内，而不是链路级。

## 动手实验

前置条件：Python 3.8+；脚本保存为 `/tmp/backoff.py`；无需网络。

步骤：

1. 运行 `python3 /tmp/backoff.py`，比较两种策略的峰值与窗口分布。
2. 把 `BUDGET_RATIO` 改为 0.5，重跑，讨论这对下游压力的影响。
3. 把 `base` 改为 2.0，观察抖动后的峰值是否变化，并解释原因。
4. 让 `jitter` 使用 `rng.uniform(base*0.5, base)`（即“部分抖动”），对比全抖动与固定间隔的结果。
5. 为脚本增加一个“熔断”判断：若前 10 个请求全部失败，则不再发起重试，直接返回降级标记。

预期结果：第 2 步说明重试预算越大，下游承受的额外流量越多；第 3 步说明峰值主要由窗口宽度与并发量决定，退避只影响时间尺度；第 4 步说明部分抖动仍会形成较窄的尖峰。

验证方法：固定种子后重复运行，输出必须一致；若不一致，检查是否用了全局随机源。

清理方法：`rm /tmp/backoff.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 429 后错误率反而上升 | 客户端固定间隔重试，形成同步尖峰 | 统计重试请求的时间分布 | 加抖动、重试预算与熔断 |
| 全天持续 429，退避无效 | 日配额或预算耗尽，与速率无关 | 检查配额用量与错误码类型 | 申请提额或直接降级，停止重试 |
| 质量缓慢下降但无告警 | 模型别名漂移，供应商更新了底层版本 | 核对实际模型版本与每日金标集分数 | 钉住具体版本，建立每日跑分 |
| 退役当天大面积失败 | 未跟踪模型退役日期 | 检查供应商退役公告与配置中的模型 ID | 建立版本日历，提前灰度迁移 |
| 降级后出现越权或泄露 | 降级路径未继承权限与护栏 | 检查降级分支是否绕过鉴权与内容过滤 | 降级路径必须复用同一套安全控制 |
| 切换备用供应商后质量不可比 | 两条路径未共用评测集 | 用同一批样本跑两条路径 | 建立共享回归集与差异阈值 |

## 安全与生产注意事项

**<u>无上限的重试会把一次限流放大成一次全链路故障，且会同时打满你的配额与备用路径。</u>** 重试必须配合抖动、预算与熔断，并在降级路径上直接返回可用结果，而不是继续排队。

**<u>降级模式若绕过了鉴权、内容过滤或金额校验，等于在故障时打开了后门。</u>** 降级只应改变“用哪个模型、答多详细”，不应改变“谁能做什么”；写操作类降级必须保留人工确认。

另外两条：Runbook 中不得写入任何真实密钥、内网地址或客户数据，应引用密钥管理系统中的条目名；模型退役与版本变更要以供应商官方公告为准，并在内部记录复核日期，避免依据过期文档做迁移决策。

## 本课总结

- **外部依赖的失败有四种形态：限流、配额、退化、故障，处置方式各不相同。**
- 重试必须带抖动、预算与熔断；固定间隔重试会放大故障。
- 模型要钉到具体版本，并用每日金标集跑分发现静默退化。
- 把退役日期纳入版本日历，让迁移成为计划内发布。
- Runbook 的价值在于演练过的动作与明确的责任人，而不是文档厚度。

## 思考题

如果供应商通知“当前模型将在 60 天后退役”，而新版本在你关心的“金额与时效类问题”上表现略差、在通用问答上更好，你会如何安排这 60 天？请给出阶段划分、每阶段的验收标准，以及若到期仍未达标时的处置。

参考思路：前两周完成新版本在回归集上的分层评估（按意图切分，重点看金额与时效类）；第 3–4 周做灰度与影子对比，同时尝试 Prompt 与检索侧补偿；第 5–6 周确定是否采用“按意图双版本路由”。验收标准应是分层指标而非总体平均。若到期仍未达标，应降级为“高风险意图强制人工确认 + 新版本仅用于通用问答”，而不是强行全量切换。

## 小测

1. 持续数小时的 429 且退避无效，最可能是：  
   A. 瞬时限流　B. 配额或预算耗尽　C. 模型退化　D. 网络抖动
2. 为什么重试要加入抖动？
3. “钉住模型版本”解决了什么问题？它不能解决什么问题？
4. 熔断与重试预算分别在什么层面限制故障放大？
5. 场景题：大促开始后 5 分钟，错误率从 1% 升到 20%，日志显示大量 429，同时内网降级路径也开始超时。你会按什么顺序处置？请给出前三个动作与判断依据。

## 答案与解析

1. **B。**瞬时限流通常随流量回落而恢复；持续数小时不变、退避无效，说明是配额或预算层面的限制，重试只会浪费配额；C 不会产生 429；D 通常表现为超时而非持续 429。
2. 因为大量客户端会在同一时刻失败，若都用同一个固定间隔重试，就会在同一时刻再次形成尖峰，把下游的恢复窗口再次打掉。抖动把重试分散到不同时间点，显著降低瞬时压力。
3. 它解决了“静默退化与别名漂移”：你能确知线上跑的是哪个版本，并能在退化时切回。它不能解决版本退役（必须迁移）与供应商内部更新同一版本号的情况，仍需每日跑分验证。
4. 重试预算限制的是“总量”——最多有多少请求可以去重试；熔断限制的是“时间”——连续失败后直接停止调用一段时间。前者防止长期放大，后者防止在下游已不可用时继续加压。
5. 顺序：第一步立即关闭或收紧重试（避免放大），因为 429 与降级超时同时出现说明链路已被自身流量压垮；第二步确认是限流还是配额（看时间分布与错误码），据此决定是限速排队还是直接降级；第三步在降级路径上做容量与依赖检查（它为何也超时），并把高风险意图转人工。判断依据是“先止血再定位”，且降级路径本身也需要容量规划，不能假设它无限可用。
