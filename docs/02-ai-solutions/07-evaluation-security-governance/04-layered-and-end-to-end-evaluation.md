# 检索、生成与端到端分层评测

## 为什么需要学习

售后助手的端到端通过率是 0.60。周会上两个团队各执一词：检索组说“召回 0.8 已经不低，问题在生成”，生成组说“检索经常返回半截条款，模型没法答对”。两边都有道理，但没有任何一方能拿出证据，于是各自改了两周，端到端涨到 0.63，谁也说不出是自己的功劳。

更糟的情况是“指标会互相顶”：生成组把答复写得更保守，忠实度上去了，但客服发现答案没有可执行下一步，端到端反而下降。**只看端到端，你永远不知道自己在修哪一层；只看分层指标，你又不知道用户最终是否受益。**

> **核心结论：** 分层评测不是把指标拆细，而是让每一层都能独立重放与归因；端到端指标负责“值不值得发”，分层指标负责“该改哪里”，两者必须跑在同一批样本上。

## 学习目标

完成本课后，你能够：

- 列出检索层、生成层与端到端层各自的指标，并说明每个指标能排除什么。
- 用“检索命中 × 生成正确”的四象限对失败样本归因。
- 由检索召回估算端到端指标的天花板，并解释为什么它是上界而不是目标。
- 用反事实估算排出修复优先级，并说明这种估算会低估哪些情况。

## 业务场景

售后助手的请求链路固定为：客服提问 → 检索售后政策与订单 → 生成答复或退款建议 → 人工确认 → 调用工具。

现在要回答三个决策问题：

1. 下个迭代是投入检索（换 embedding、改分块、加重排），还是投入生成（改 Prompt、换模型）？
2. 政策更新后，端到端下降 5 个点，是知识库没同步，还是模型把新条款读错了？
3. 上报给管理层的数字，应该用端到端通过率，还是用某一层指标？

这三个问题的答案都依赖同一件事：**每次评测必须留下中间产物**——命中了哪些片段、生成了什么、工具调了什么、失败发生在哪一步。

## 核心概念

| 层次 | 指标 | 回答的问题 | 典型门槛示例 |
| --- | --- | --- | --- |
| 检索层 | *召回率*（recall@k） | 该命中的片段出现了吗？ | 90 条样本中 80 条命中 → 0.80 |
| 检索层 | *上下文精确度*（context precision） | 命中的片段里噪声多不多？ | 前 5 条中相关片段占比 |
| 检索层 | *上下文召回*（context recall） | 回答所需的要点在上下文里齐了吗？ | 必答要点覆盖率 |
| 检索层 | *噪声敏感度*（noise sensitivity） | 加入无关片段会不会带偏答案？ | 注入干扰后指标下降幅度 |
| 生成层 | 忠实度、完整性 | 在给定上下文下答得好不好？ | 见第三课 |
| 生成层 | 结构化与工具约束 | 输出格式、参数是否合法？ | JSON schema 通过率 |
| 端到端 | *任务成功率* | 客服能否直接采纳并完成操作？ | 0.60 |
| 端到端 | 人工可发送率 | 人工抽检“可发送”比例 | 抽 50 条，≥ 0.9 |

*误差传播* 指的是上游错误向下游传递并放大：检索没命中正确条款，生成只能在错误上下文里作答，忠实度再高也是错的。*归因* 就是用中间产物判断这次失败“最早坏在哪一层”。*天花板* 是在上游指标不变的前提下，下游指标的理论上界。

一个近似关系值得记住：**端到端通过率 ≈ 检索命中率 × 命中后生成正确率**（假设两者近似独立）。0.80 × 0.75 = 0.60，正好解释了本课的场景数字。它不是精确公式，但足够用来做优先级判断。

<u>不要把端到端通过率当成“质量总分”。</u> 它混合了知识覆盖、检索质量、生成质量、工具契约和人工流程，任何一个环节坏掉都会拉低它，因此它不适合用来定位问题。

## 工作原理

分层评测的执行顺序如下：

1. **冻结输入**：同一批样本、同一份知识库快照、同一模型与 Prompt 版本。任一项变化，跨层对比就失效。
2. **落盘中间产物**：每条样本记录检索返回的片段 ID 与分数、拼接后的上下文、模型原始输出、工具调用参数与结果、耗时与 token 数。没有这层记录，后面只能猜。
3. **逐层打分**：检索层算命中与噪声；生成层算忠实度、完整性与格式合法性；端到端层由人（或经校准的评分器）判断“客服能否直接采纳”。
4. **四象限归因**：把每条样本标记为“命中且答对”“命中但答错”“未命中但答对”“未命中且答错”。第三象限常被忽略，它说明答案解析正确来源不明，不能算检索的功劳。
5. **估算天花板**：在当前召回下，端到端最多接近召回值；再乘上生成层的现实上限，得到“本轮可达到的目标”。
6. **反事实估算优先级**：分别假设“只把生成修到 0.95”“只把检索修到 0.95”，看哪个把端到端推得更高。
7. **回归验证**：改完只盯对应层指标（快速反馈），同时跑端到端（防止局部优化伤害整体）。

第 6 步的结果必须配上警告：反事实估算假设层间独立、且修复成本相同，现实中两者都不成立。它的作用是**排除明显不划算的方向**，不是精确预测。

## 架构与选型

| 评测粒度 | 适用阶段 | 成本 | 主要风险 |
| --- | --- | --- | --- |
| 仅端到端 | 原型验证、快速决策 | 低 | 无法归因，容易反复试错 |
| 端到端 + 检索层 | 知识库频繁更新 | 中 | 只能定位“是不是检索的问题” |
| 端到端 + 检索 + 生成 | 进入生产前的常规配置 | 中高 | 需要保存中间产物与版本 |
| 全层含工具与审批 | 涉及退款金额、越权风险 | 高 | 需要 trace 体系与人工排班 |

选型依据：**变更主要发生在哪一层，就在哪一层加指标**。知识库每周更新，就必须有检索层指标；Prompt 每天改，就必须有生成层指标；工具有资金影响，就必须有工具层断言。

另一个维度是回放方式：离线回放用固定快照，结论稳定、可比较；线上采样反映真实分布，但会混入流量变化。**发布门禁用离线，效果验证用线上**，不要用同一套数字回答两个问题。

## 最小示例

下面的脚本对一批已标注的样本做四象限归因、天花板估算与反事实比较。环境：Python 3.8+，仅标准库。

```python
SAMPLES = [
    {"id": "s01", "retrieval_hit": True,  "answer_ok": True},
    {"id": "s02", "retrieval_hit": True,  "answer_ok": True},
    {"id": "s03", "retrieval_hit": True,  "answer_ok": False},
    {"id": "s04", "retrieval_hit": False, "answer_ok": False},
    {"id": "s05", "retrieval_hit": True,  "answer_ok": True},
    {"id": "s06", "retrieval_hit": True,  "answer_ok": True},
    {"id": "s07", "retrieval_hit": False, "answer_ok": True},   # 未命中却答对：不可依赖
    {"id": "s08", "retrieval_hit": True,  "answer_ok": True},
    {"id": "s09", "retrieval_hit": True,  "answer_ok": False},
    {"id": "s10", "retrieval_hit": True,  "answer_ok": True},
]

n = len(SAMPLES)
hits = sum(1 for s in SAMPLES if s["retrieval_hit"])                  # 检索命中数
end_ok = sum(1 for s in SAMPLES if s["retrieval_hit"] and s["answer_ok"])  # 两层都对才算端到端通过
misses = n - hits                                                     # 检索失败数
gen_fail = hits - end_ok                                              # 命中但生成错

recall = hits / n
conditional = end_ok / hits      # 条件正确率：只在命中样本上算，避免被检索错误污染
e2e = end_ok / n

print(f"样本数: {n}")
print(f"检索命中: {hits} ({recall:.2f})  未命中: {misses} ({misses / n:.2f})")
print(f"命中后答对: {end_ok} 条件正确率: {conditional:.2f}")
print(f"端到端通过: {end_ok} ({e2e:.2f})")
print(f"理论天花板(检索召回): {recall:.2f}")
print("四象限归因:")
print(f"  检索失败: {misses} ({misses / n:.2f})")
print(f"  命中但答错: {gen_fail} ({gen_fail / n:.2f})")
print(f"  命中且答对: {end_ok} ({end_ok / n:.2f})")
print("反事实估算（假设单层修到 0.95）:")
print(f"  只修生成: {hits * 0.95 / n:.4f}")
print(f"  只修检索: {n * 0.95 * conditional / n:.4f}")
```

输出（本机 `python3` 实测）：

```text
样本数: 10
检索命中: 8 (0.80)  未命中: 2 (0.20)
命中后答对: 6 条件正确率: 0.75
端到端通过: 6 (0.60)
理论天花板(检索召回): 0.80
四象限归因:
  检索失败: 2 (0.20)
  命中但答错: 2 (0.20)
  命中且答对: 6 (0.60)
反事实估算（假设单层修到 0.95）:
  只修生成: 0.7600
  只修检索: 0.7125
```

读法：检索与生成各造成 20% 的失败，但把生成修到 0.95 能把端到端推到 0.76，而检索修到 0.95 只有 0.71。所以**本轮优先修生成**。同时注意 `s07`：检索没命中却答对了，这类样本计入“端到端通过”会高估系统可靠性——实际发布判定时应把它算作不可复现的正确，单独计数。

## 动手实验

前置条件：Python 3.8+；保存脚本为 `/tmp/layered_eval.py`。

步骤：

1. 原样运行，核对输出。
2. 把 `s09` 的 `answer_ok` 改为 `True`（模拟修好一条生成失败），观察端到端、条件正确率与反事实结论是否翻转。
3. 把 `s07` 的 `answer_ok` 改为 `False`（模拟把“碰巧答对”判为不可依赖），比较端到端数字变化。
4. 追加 10 条新样本（可复制并改 ID），其中 5 条 `retrieval_hit=False`，观察天花板如何随召回下降。

预期结果：第 2 步后条件正确率升至 0.875、端到端 0.70，反事实结论翻转为优先修检索（0.83 高于 0.76）——说明优先级会随短板位置改变；第 3 步端到端降到 0.50，说明判定口径会显著影响对外数字；第 4 步召回降到 0.65，天花板随之降到 0.65。

验证方法：改动前后把 `样本数`、`检索命中`、`端到端通过` 三个数字与手算结果对照；若不一致，检查是否漏改 `answer_ok` 造成的连锁影响。

清理方法：`rm /tmp/layered_eval.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 端到端低但查不出原因 | 未保存检索片段与中间输出 | 检查 trace 是否有片段 ID、分数、上下文 | 补中间产物落盘，按样本 ID 对齐 |
| 检索指标好，端到端上不去 | 检索命中的片段不是回答所需片段（精确度低） | 抽 10 条看前 5 条片段是否包含关键条款 | 加重排、改分块，引入上下文精确度指标 |
| 换模型后端到端涨，回归却掉 | 只优化了端到端，未看生成层稳定性 | 对比同批次忠实度与格式通过率 | 把生成层指标纳入门禁 |
| 各层指标都好，客服仍不采纳 | 缺“可执行下一步”或语气不可用 | 抽样做人工可发送率评估 | 增加端到端人工维度与必答要素 |
| 政策更新后端到端骤降 | 知识库快照未同步或分块破坏条款 | 核对快照 ID 与命中片段原文 | 把知识库变更纳入评测触发条件 |

## 安全与生产注意事项

**<u>分层日志会把检索内容、订单信息和客户问题完整落盘，这是新的泄露面。</u>** 生产上应对片段正文做脱敏或限权访问，并对日志设置保留期；调试便利不能以长期保存客户数据为代价。

**<u>端到端通过率高会掩盖安全类失败。</u>** 提示注入、越权查询他人订单、诱导承诺退款这类样本在普通业务集里占比很低，端到端分数几乎不受影响。必须单独维护对抗集与安全门禁，并让安全失败具备“一票否决”地位，而不是平均进总分。

两条工程习惯：为每层指标标注快照与版本，否则跨周比较没有意义；把“反事实估算”的假设写进文档，避免有人把估算值当承诺写进 OKR。

## 本课总结

- **端到端回答“值不值得发”，分层指标回答“该改哪里”，二者必须共用同一批样本与快照。**
- 中间产物（片段 ID、上下文、输出、工具参数）是归因的前提，没有它就只能猜。
- 端到端通过率近似等于检索命中率乘以条件正确率，因此检索召回构成理论天花板。
- 四象限归因中，“未命中却答对”应单独计数，不能算作可靠成功。
- 反事实估算用于排除不划算的方向，不能替代真实实验。

## 思考题

如果检索召回已经 0.95，而端到端只有 0.70，你会把资源投到生成层还是去改知识库结构？请说明你会先看哪些证据，以及如何避免“把知识库改坏但指标暂时变好”。

参考思路：先看命中后答错的样本类型——如果集中在长条款、多条件、跨文档组合，说明分块或上下文组织方式不适合，改结构可能比改 Prompt 更根本；如果集中在措辞与格式，优先改生成。避免指标暂时变好的办法是同时跑旧样本与留出集，并保留回滚快照；改动知识库结构必须触发检索层与端到端两层回归，而不是只看召回。

## 小测

1. 端到端通过率 0.72、检索召回 0.90、条件正确率 0.80，下列判断正确的是：

   A. 端到端已达天花板　B. 还有约 0.10 的端到端空间可追　C. 检索是主要瓶颈　D. 应立刻换模型

2. 为什么“未命中但答对”不能算作系统的可靠成功？
3. 上下文精确度低会造成什么后果？它和召回率有什么区别？
4. 反事实估算的两个主要假设是什么？它们为什么会失真？
5. 场景题：政策更新后端到端从 0.72 降到 0.64，检索召回不变、条件正确率下降。你会按什么顺序排查？请写出前三步。

## 答案与解析

1. **B。**0.90 × 0.80 = 0.72，端到端已符合乘法近似，但生成层仍有 0.20 的失败可压缩，理论上限接近 0.90。A 错在忘了生成层上限；C 错在 0.90 已不是最短板；D 错在未定位原因就换模型。
2. 因为它依赖模型记忆或偶然匹配，换问法、换订单、换时间就可能失效，且无法用检索证据解释；把它计入成功会高估可靠性并掩盖检索缺陷。
3. 精确度低意味着上下文里噪声多，模型容易被无关片段带偏，忠实度可能仍高但结论错位；召回率衡量“该找到的找到没”，精确度衡量“找到的里有用占比”。
4. 假设层间独立（各层错误互不影响）与修复成本相同（把任一层修到 0.95 的代价一样）。现实中两层错误相关（检索差会让生成更容易出错），且修检索往往比修生成贵得多，因此估算只能用于方向性判断。
5. 先核对知识库快照与新政策条款是否已生效，确认样本期望是否仍对应旧政策；再抽 20 条条件正确的失败样本，看模型是漏读新条款、把条件读反，还是引用了被分块截断的段落；最后才考虑改 Prompt，并用同一批样本验证。顺序的原则是先排除数据与快照问题，再动生成策略。
