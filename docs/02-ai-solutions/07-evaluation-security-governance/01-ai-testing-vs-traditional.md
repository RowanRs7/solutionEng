# AI 测试与传统测试的差异

## 为什么需要学习

晴空商城的售后智能助手上线两个月后，测试组遇到了一个说不清的问题：同一套 Prompt、同一批 60 条测试问题，周一跑出 52 条通过，周二跑出 47 条通过，代码和模型版本都没有变。客服主管因此拒绝了一次本来正确的政策更新，理由是“测试挂了”。团队花了三天才确认那 5 条差异来自模型输出的自然波动，而不是新政策写错了。

传统断言假设同一输入永远产生同一输出，大模型应用不满足这个前提。不改判定方式，团队只有两种结局：被噪声吓住不敢发布，或因“偶尔失败”忽略真正的退化。

> **核心结论：** AI 测试的对象不是一条输出，而是一个输出的分布；测试的交付物不是“通过/失败”，而是带不确定性区间的指标、可对比的基线，以及针对具体失效模式的判定规则。

## 学习目标

完成本课后，你能够：

- 解释 *非确定性*、*分布漂移* 与 *基线* 三个概念，并指出它们分别如何破坏传统断言的假设。
- 用通过率的标准误判断两个版本的差异是否超出噪声范围。
- 为同一功能设计“确定性断言 + 指标阈值 + 人工抽检”的组合测试方案，并说明各部分覆盖什么。
- 在基线失效时给出复核与重建的动作，而不是直接调低阈值。

## 业务场景

售后智能助手的处理链路是：客服提问 → 检索售后政策与订单 → 生成答复或退款建议 → 人工确认 → 调用工具创建退款单。

测试组要回答三个问题：

1. 政策知识库更新后，助手引用新政策的比例是否下降？
2. 有人把 Prompt 里的“7 天”改成“7 个工作日”，这是修复还是退化？
3. 模型供应商升级了默认模型版本，我们怎么在半小时内判断要不要回滚？

三个问题分别对应“分布是否变”“判定标准是什么”“基线是否可比”；指标定义留给第三、四课。

## 核心概念

| 概念 | 本课程中的含义 | 传统系统里的对应物 | 在售后助手中的例子 |
| --- | --- | --- | --- |
| *非确定性* | 相同输入在不同调用中产生不同输出的性质 | 通常被设计消除（同一请求同一响应） | 同一句“耳机能退吗”，两次答复措辞与条款顺序不同 |
| *分布漂移* | 输入分布、上下文内容或判定标准随时间变化 | 数据迁移、配置变更 | 双十一后“价保”类问题激增，样本集里很少 |
| *基线* | 一组固定输入在固定配置下测得的指标快照，用于对比 | 上一版本的测试报告 | 100 条黄金问答在模型 A、Prompt v3 下的通过率 0.82 |
| *回归阈值* | 允许低于基线多少仍视为通过 | 性能基准的容忍度 | 忠实度从 0.90 掉到 0.86 以上才告警 |
| *确定性断言* | 结果可被机械判定的检查 | 单元测试断言 | 输出必须是合法 JSON；必须含订单号；不得出现“已退款成功” |
| *指标型判定* | 对一批样本算分再与阈值比较 | 覆盖率、性能百分位 | 100 条样本的忠实度均值 ≥ 0.88 |
| *抽样复核* | 人对一小批输出做语义判断 | 验收测试、UAT | 每轮抽 20 条答复由资深客服打“可发送/需修改/不可发送” |

非确定性的来源可以分成三类，它们的应对手段不同：

- *解码随机性*：温度、top-p、并行归约顺序带来的差异，可多次运行取统计量压低。
- *上下文差异*：检索片段、订单状态、时间不同，属于输入变化，测试必须先固定输入。
- *模型侧变化*：供应商升级模型或调整路由，会让基线整体失效，需要版本锁定与变更通知。

<u>把这三类混为一谈，是 AI 测试最常见的失败原因：把输入变化当成噪声，或把噪声当成模型退化。</u>

## 工作原理

一个可用的 AI 测试流程有七个步骤：

1. **固定任务口径**：写清“什么样的答复算对”，含必含字段、禁止表述与可接受写法；没有口径就没有判定。
2. **固定输入样本**：用同一份样本集（第三课讲的 *黄金集*）跑所有版本；检索类功能要同时冻结知识库快照或记录快照 ID。
3. **固定运行配置**：模型名与版本、温度、最大输出长度、Prompt 版本、工具超时都写进运行记录，否则两次数值不可比。
4. **多次运行估噪声**：同一份样本至少跑 2–3 次并记录通过率；若两次摆动 5 个百分点，3 个百分点的“退化”没有意义。
5. **用区间而不是点判断**：通过率的标准误为 √(p(1−p)/n)；100 条样本、通过率 0.8 时标准误约 0.04，95% 区间约 ±8 个百分点。
6. **分层定位**：一旦判定退化，先看是检索层、生成层还是工具层的问题（第四课展开），再决定改 Prompt、改检索还是改样本。
7. **基线版本化与复核**：每次模型或知识库变更后重建基线，并在文档里写清“基线由什么配置产生、什么时候作废”。

第 5 步值得展开。假设 A 版本 120 条样本通过 96 条（0.80），B 版本通过 88 条（0.733）。差值 0.067 看起来像退化，但合并通过率约 0.767 时，差值的标准误约为 0.055，z 值约 1.2，远小于常用的 1.96 门槛。<u>这类差异更应该解释为噪声，此时调整阈值或增加样本量，比改 Prompt 更合理。</u>

## 架构与选型

| 判定手段 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 确定性断言（schema、正则、必含字段、禁止词） | 结构化输出、合规红线、工具参数 | 开放式答复的质量 | 便宜、稳定、可解释；但只能防“不该出现的”，不能证明“答得好” |
| 指标型判定（忠实度、相关性等算分） | 有黄金集、有稳定评分器的 RAG 场景 | 无标注、口径未定的新功能 | 能覆盖语义质量；但分数本身有方差，且依赖评分器 |
| 人工抽样复核 | 高风险答复、口径争议、上线前验收 | 高频回归 | 可信度最高；但慢、贵、不可每日全量执行 |
| 在线监控与 A/B | 判断真实用户影响 | 冷启动阶段没有流量 | 反映真实分布；但反馈滞后，且难以归因 |

选型依据不是“哪种更先进”，而是**失效代价**：退款金额、承诺时效、法律表述不可逆，必须配确定性断言与人工复核；语气与措辞偏好可用指标阈值。

另一个依据是**变更频率**：每天改 Prompt 却只有 40 条样本时，任何阈值都会被噪声击穿，应先扩样本再谈门禁。

## 最小示例

下面用 Python 3 标准库比较两个 Prompt 版本的通过率，并给出差异是否显著的判断。设计意图是：把“看起来退化了”变成“在噪声范围内/超出噪声范围”的可复核结论。

```python
import math

def rate(passed, total):
    """把布尔计数转成通过率；单独成函数便于后面复用到多个版本。"""
    return passed / total

def diff_standard_error(p1, n1, p2, n2):
    """两比例差值的标准误：用合并比例估计共同方差，避免小样本下方差被单侧估计放大。"""
    pooled = (p1 * n1 + p2 * n2) / (n1 + n2)      # 合并通过率，作为共同方差的估计
    variance = pooled * (1 - pooled) * (1 / n1 + 1 / n2)  # 两项独立比例方差之和
    return math.sqrt(variance)

def verdict(p1, n1, p2, n2, z_limit=1.96):
    """|z| 小于 1.96 时认为差异可由抽样噪声解释；这是判定门槛，不是质量门槛。"""
    se = diff_standard_error(p1, n1, p2, n2)
    if se == 0:                                    # 极端情形：两版全部通过或全部失败
        return p1 - p2, 0.0, "差异为零方差，需人工确认样本是否失效"
    z = (p1 - p2) / se
    label = "差异显著，需归因" if abs(z) >= z_limit else "差异在噪声范围内"
    return p1 - p2, z, label

n = 120
a_passed, b_passed = 96, 88           # 同一批 120 条黄金问答，A 为当前线上版本
p1, p2 = rate(a_passed, n), rate(b_passed, n)
delta, z, label = verdict(p1, n, p2, n)

print(f"A 通过率: {p1:.3f} ({a_passed}/{n})")
print(f"B 通过率: {p2:.3f} ({b_passed}/{n})")
print(f"差值: {delta:.4f}  z: {z:.2f}")
print(f"判定: {label}")
```

预期输出（数字由上面的公式手算，可直接核对）：

```text
A 通过率: 0.800 (96/120)
B 通过率: 0.733 (88/120)
差值: 0.0667  z: 1.22
判定: 差异在噪声范围内
```

整体流程是：算两版通过率 → 用合并比例估差值标准误 → 用 z 值粗判。关键设计有三处：用合并比例避免小样本被夸大；把判定门槛（1.96）与质量门槛（基线阈值）分开，防止“统计显著但业务无所谓”变成阻塞；输出中文结论，便于贴进变更记录。

这个检验只回答“差异是否可能来自抽样”，不回答“哪个版本对用户更好”；后者靠分层指标与人工抽样。

## 动手实验

### 任务：观察样本量如何影响结论

前置条件：任意装有 Python 3.8+ 的机器；把上面的脚本保存为 `/tmp/diff_check.py`；不需要网络和 API Key。

步骤：

1. 原样运行 `python3 /tmp/diff_check.py`，确认输出与上面的预期输出一致。
2. 把 `n` 改为 `40`，`a_passed` 改为 `32`，`b_passed` 改为 `29`（保持约 0.80 与 0.725 的比例），再运行一次。
3. 把 `n` 改为 `1200`，`a_passed` 改为 `960`，`b_passed` 改为 `870`，再运行一次。

预期结果：n=40 时 z 明显偏小（差异更不容易判为显著）；n=1200 时同样的比例差得出 z 远大于 1.96，判定为“差异显著，需归因”。

验证方法：三次输出中的通过率比例接近，但 z 值随 n 增大而增大。若你的 z 值方向相反，检查 `a_passed` 与 `b_passed` 是否真的按比例放大，以及是否误改了 `n` 而没有改计数。

清理方法：`rm /tmp/diff_check.py`。实验中不产生其他文件。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 同一套用例每天都有一两条翻转 | 判定依赖精确字符串或近乎精确的语义阈值 | 同配置连跑 3 次，统计翻转条数与位置 | 改用结构化字段 + 阈值；对波动样本单列“抖动清单” |
| 改了 Prompt，指标涨了 10 个点，上线后没变化 | 样本集太小或与线上分布不一致 | 对比样本集的问题类型占比与真实工单分布 | 扩充并重采样黄金集，标注来源与占比 |
| 换个模型版本后所有用例都失败 | 输出格式变了，断言只认旧格式 | 打印首条失败的实际输出 | 先加结构化输出约束，再重设基线 |
| 基线一降再降，测试永远通过 | 用调低阈值代替归因 | 查阈值变更记录与对应复盘 | 冻结阈值，要求每次调整附失效样本分析 |

## 安全与生产注意事项

**<u>不要把“离线评测通过”当成上线许可。</u>** 离线样本是人挑的，攻击者与真实用户不在其中。提示注入、越权工具调用、敏感信息泄露这些风险在通过率里通常看不出来，必须单独设计对抗用例与权限校验（本单元后续课程展开）。

**<u>不要把真实客户对话原样放进评测样本库。</u>** 工单里常有手机号、地址、订单与聊天记录。样本入库前必须脱敏或使用合成改写，并限制访问范围；否则评测环境会变成第二个泄露面。OWASP 在 LLM01:2026 与 LLM03:2026 中分别把提示注入与过度代理列为独立风险类别（2026 版编号；2025 版中过度代理为 LLM06），说明这两类问题需要专门测试，而不是靠业务指标顺带覆盖。

两条生产习惯：模型版本、Prompt 版本、知识库快照 ID 与脚本版本一起写进报告，否则三个月后无人能复现；基线设有效期，供应商发布模型变更后主动作废重测。

## 本课总结

- **AI 测试的判定单位是分布，不是单条输出；通过率必须带样本量与区间才有意义。**
- 非确定性分三类：解码随机性、上下文差异、模型侧变化；只有第一类是噪声，后两类要固定或重建基线。
- 确定性断言负责红线，指标阈值负责语义质量，人工抽检负责高风险与口径争议，三者互补而非替代。
- 统计显著不等于业务重要，判定门槛与质量门槛要分开设定。
- 基线的价值来自可复现：模型、Prompt、知识库快照、样本集、脚本版本缺一不可。

## 思考题

客服团队希望“每次政策更新都自动跑评测并决定是否发布”，但知识库每周更新两三次，政策类样本只有 40 条。你会怎样设计自动发布条件？哪些情况必须转人工？

参考思路：先按风险分级——改文案、改时效、改金额上限、改适用品类差别很大。低风险更新可自动跑“政策引用一致性”并仅在超阈值时放行；金额与时效类强制人工抽检留痕。同时要承认 40 条样本只能支撑“没发现退化”，不是“证明正确”，因此自动发布必须配灰度与回滚。

## 小测

1. 关于 AI 应用的非确定性，下列说法正确的是：

   A. 只要把温度设为 0 就完全消除　B. 通过率是比例，其波动与样本量有关　C. 非确定性只来自模型　D. 出现差异就说明 Prompt 改坏了

2. 为什么“同一套用例连跑三次结果不同”不能直接判定为回归？
3. 简述确定性断言与指标型判定各自覆盖的风险，各举一个售后助手的例子。
4. 基线在什么情况下必须作废重建？至少说出两种。
5. 场景题：产品经理看到 120 条样本的通过率从 0.80 降到 0.73，要求立刻回滚 Prompt。你作为负责评测的工程师，会先做什么、依据是什么？

## 答案与解析

1. **B。**通过率是比例，样本量越小波动越大。A 错在温度设为 0 通常只能降低而不能消除差异（硬件、并行归约、供应商侧路由都可能引入变化）；C 错在上下文与输入变化同样是差异来源；D 错在未排除噪声前无法归因。
2. 因为差异可能来自解码随机性或上下文差异，落在抽样噪声范围内。正确做法是记录三次结果、估噪声幅度，再用区间判断；直接判回归会把噪声当成缺陷。
3. 确定性断言覆盖“不许出现/必须存在”的红线，例如答复必须是合法 JSON、必须包含订单号、不得出现“已退款成功”；指标型判定覆盖语义质量，例如对 100 条样本算忠实度均值，检查是否引用了正确政策条款。
4. 模型版本或供应商路由变化、Prompt 大改导致输出结构变化、知识库重构改变检索命中、样本集本身修订、判定口径变化。任何一种都会让新旧数值不可比。
5. 先确认这批数字是否同配置、同快照、同脚本，再观察历史波动幅度；用差值的标准误判断 0.07 是否显著（本课示例中 z≈1.2，属噪声范围）。若确实显著，再分层定位是检索还是生成，并抽 20 条失败样本人工确认。直接回滚的问题在于：回滚也会引入不确定，且没有证据说明新版本更差。
