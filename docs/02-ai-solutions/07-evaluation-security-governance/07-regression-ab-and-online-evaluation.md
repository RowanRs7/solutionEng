# 回归、A/B 与在线评测

## 为什么需要学习

晴空商城的售后助手在一个周五下午改了退款建议的 Prompt，理由很充分：新的离线评测集上“忠实度”从 0.81 升到 0.86，评审的 3 位客服也说“读起来更顺畅”。改动当天全量发布，没有灰度，也没有回归集。周一客服主管发现，助手开始把“7 天无理由”套用到生鲜类目，而售后政策明确写着生鲜 48 小时。离线集里恰好没有生鲜样本。

这不是模型坏了，而是验证方式只覆盖了“我们想到的样本”。离线评测回答的是“在我们挑选的题上表现如何”，线上指标回答的是“真实流量里发生了什么”，两者之间有一条稳定的落差。本课的任务，就是把这条落差用**回归门禁 + 灰度 + 在线评测**三段结构管住。

> **核心结论：** 离线分数只能决定“能不能进入灰度”，线上指标才能决定“能不能扩大流量”；把两者混为一谈，等于用考试分数代替真实路况。

## 学习目标

完成本课后，你能够：

- 为一个 AI 功能定义可阻断的回归门禁：数据集版本、指标阈值、失败分类与放行规则。
- 判断一次变更该走影子、灰度还是 A/B，并说明理由。
- 用标准库实现两比例检验，解读 `p` 值并计算所需样本量。
- 识别样本比例失衡（SRM）、多重比较和护栏指标缺失这三类常见误判。

## 业务场景

售后助手每天处理约 1.2 万次会话，链路是：客服提问 → 检索售后政策与订单 → 生成答复或退款建议 → 人工确认 → 调用工具。团队每月会改 2–4 次 Prompt、偶尔更换模型，并频繁重建检索索引。

现有流程是“改完在自己试的几个问题上看看，觉得行就发”。结果是：有两类问题反复出现——一是旧能力回退，改好生鲜时效的同时把“跨境订单不支持无理由”讲错了；二是指标自嗨，离线忠实度涨了，但客服的修改率上升，因为答案更“像政策原文”却更难直接发给客户。

约束也很具体：客服只有 8 名，人工标注每天最多 200 条；一次错误退款建议的平均处理成本约 120 元；退款金额超过 500 元必须人工审批，所以“建议被采纳”比“端到端自动化”更贴近业务价值。

## 核心概念

| 手段 | 流量与风险 | 能回答的问题 | 不能回答的问题 |
| --- | --- | --- | --- |
| *回归门禁* | 零真实流量，全自动 | 已知能力是否退化，是否允许进入下一段 | 新问题是否被改善 |
| *影子流量* | 复制真实请求，结果不展示 | 新版本在真实输入分布上的失败长什么样 | 用户是否会因此更满意 |
| *灰度发布* | 小比例真实用户可见 | 崩溃、拦截、成本、延迟是否可接受 | 效果差异是否真实存在 |
| *A/B 实验* | 随机分流，两组长期并行 | 指标差异是否由版本引起、幅度多大 | 极端低频风险是否被覆盖 |

- *回归门禁*：把历史失败样本、关键政策断言和高风险场景固化成测试集，任何 Prompt、模型、检索或工具变更都必须先跑通，否则阻止发布。
- *影子流量*（shadow traffic）：把生产请求复制一份发给新版本，只记录不返回给用户。它用真实分布暴露新版本的失败模式，且不承担用户可见风险。
- *A/B 实验*：按用户或会话随机分组，同一时间窗内比较两个版本。它的前提是*随机化单位*明确（按会话还是按客服），否则两组样本不可比。
- *在线评测*（online evaluation）：对生产流量按比例采样，用规则或模型评分器自动打分，并与 trace 关联。微软 Foundry 的连续评测就采用这种模式：按小时设置采样百分比（0–100）与每小时最大请求数（上限 1000），评分结果写入 trace 供下钻分析（截至 2026-05，该能力在其文档中标注为预览）。
- *护栏指标*（guardrail metric）：不追求提升、只用来否决发布的指标，例如“错误政策引用率”“投诉率”“单会话成本”。
- *样本比例失衡*（SRM）：分流后两组样本量偏离预期比例。它通常意味着埋点丢失或分流逻辑有 bug，此时任何 `p` 值都不可信。

**回归门禁是阻断式的**：它不投票、不算平均分，任何一条断言失败就挡住发布。

## 工作原理

1. **冻结基线**：把当前线上版本（Prompt、模型 ID、索引版本、工具 schema）记录为基线，后续所有比较都相对它。
2. **构建门禁集**：从历史事故、人工评审的差评、政策断言、高风险类目（生鲜、跨境、大额退款）中抽题，每条样本带期望行为（必须包含/必须不包含/必须转人工）。
3. **跑离线回归**：新版本对同一数据集出结果，比对*断言通过率*与人工评分。任一硬断言失败即阻断；软指标下降超过阈值则要求书面说明与评审签字。
4. **影子验证**：门禁通过后，把 5%–10% 生产请求复制给新版本，只比较失败分类分布，不看用户满意度。此阶段专抓“离线集没有的输入”。
5. **小比例灰度**：按会话随机放量 1%→5%，重点看崩溃、内容安全拦截、工具错误、延迟 p95、单会话成本这些护栏指标。
6. **A/B 实验**：护栏指标稳定后，按预先算好的样本量与实验周期运行，主指标取“建议采纳率”这类业务终态指标，同时监控 SRM。
7. **在线持续评测**：即使实验结束，也保留按比例采样的自动评分，形成随时间漂移的趋势线——模型供应商侧更新也会让同一 Prompt 的分数变化。
8. **决策与回滚**：显著正向则扩量并更新门禁集（把新发现的失败样本收进去）；不显著或护栏退化则回滚，并记录原因。

## 架构与选型

| 场景 | 建议手段 | 理由 |
| --- | --- | --- |
| Prompt 文案微调、模型小版本升级 | 回归门禁 + 影子 | 风险主要是回退，不需要消耗实验周期 |
| 检索策略、分块、rerank 变更 | 回归门禁 + 分层离线评测 + 影子 | 影响面在“召回什么”，影子能暴露长尾文档 |
| 新增退款类工具 | 门禁 + 小比例灰度 + 强护栏 | 涉及不可逆动作，先限制暴露面 |
| 改交互形态（如加“一键生成工单”） | A/B 实验 | 效果取决于用户行为，只能靠随机对照 |
| 供应商模型迁移 | 三者全走 | 输入分布、拒答风格、成本结构都会变 |
| 只有 8 名客服、每天 200 条标注 | 门禁 + 影子为主，A/B 降低频次 | 人力约束下，A/B 的功效不足，容易得出“不显著” |

选型依据是三个量：**可逆性**（错了能不能撤回）、**暴露面**（会影响多少用户）、**可测量性**（有没有足够样本支撑统计判断）。三者都低时用门禁即可；任一升高就补下一段。

## 最小示例

问题：判断新版退款建议 Prompt 的“客服采纳率”提升是否真实，并估算需要多少样本。

环境：Python 3.10+，仅标准库。输入：两组“采纳数/总数”。输出：差异、`z` 值、`p` 值与所需样本量。

```python
import math


def z_test(k_a, n_a, k_b, n_b):
    """两比例 z 检验：H0 为两组采纳率相同，返回 (z, 双侧 p 值)。"""
    p_a, p_b = k_a / n_a, k_b / n_b          # 各自观测到的采纳率
    p_pool = (k_a + k_b) / (n_a + n_b)       # 合并比例，仅在 H0 成立时使用
    se = math.sqrt(p_pool * (1 - p_pool) * (1 / n_a + 1 / n_b))  # 差值标准误
    if se == 0:                               # 全 0 或全 1 时避免除零
        return 0.0, 1.0
    z = (p_b - p_a) / se                      # 标准化差值
    # 双侧 p 值：标准正态尾概率，erfc 比查表更适合脚本
    return z, math.erfc(abs(z) / math.sqrt(2))


def required_n(p1, p2):
    """每组所需样本量（双侧 alpha=0.05，power=0.8 的常用近似公式）。"""
    z_alpha, z_beta = 1.959964, 0.8416212     # 95% 置信、80% 功效对应分位数
    p_bar = (p1 + p2) / 2                      # 平均比例
    num = (z_alpha * math.sqrt(2 * p_bar * (1 - p_bar))
           + z_beta * math.sqrt(p1 * (1 - p1) + p2 * (1 - p2))) ** 2
    return math.ceil(num / (p2 - p1) ** 2)     # 除以效应量平方


old = {"kept": 742, "n": 1000}                 # 基线：客服直接采纳 74.2%
new = {"kept": 771, "n": 1000}                 # 新版：采纳 77.1%
z, p = z_test(old["kept"], old["n"], new["kept"], new["n"])
print(f"采纳率差异 = {new['kept'] / new['n'] - old['kept'] / old['n']:+.3%}")
print(f"z = {z:.3f}, p = {p:.4f}")
# 决策规则要写在代码里，而不是靠人解读 p 值
print("结论：" + ("达到显著（alpha=0.05），可扩量" if p < 0.05 else "不显著，先别扩量"))
print(f"每组所需样本量（检测 +3 个点）= {required_n(0.742, 0.772)}")
```

运行 `python3 ab.py`，预期输出：

```text
采纳率差异 = +2.900%
z = 1.511, p = 0.1308
结论：不显著，先别扩量
每组所需样本量（检测 +3 个点）= 3208
```

流程说明：先算观测差异，再除以“假设两组无差异时的标准误”得到 `z`，最后换算成双侧 `p` 值。2.9 个点的提升听起来不小，但在每组 1000 条样本下 `p≈0.13`，**大概率是噪声**。要在 80% 功效下稳定检出 3 个点，每组需要约 3200 条；按每天 200 条标注算约需 32 天——这正是小团队无法依赖 A/B 实验的现实原因。

## 动手实验

### 任务：搭一条门禁 + 在线判读的小流水线

前置条件：Python 3.10+；一个目录；无需网络与密钥。

1. 创建 `samples.jsonl`，写入 3 条门禁用例，每行一条：

   ```json
   {"id": "fresh-48h", "question": "生鲜可以 7 天无理由吗？", "must_contain": ["48 小时"], "must_not_contain": ["7 天无理由"]}
   {"id": "cross-border", "question": "跨境订单能退吗？", "must_contain": ["不支持"], "must_not_contain": []}
   {"id": "big-refund", "question": "这单 3000 元能直接退吗？", "must_contain": ["人工"], "must_not_contain": ["已为您退款"]}
   ```

2. 创建 `gate.py`，读取用例并逐条检查断言，任何一条不满足即以非零码退出（CI 里就是“阻断”）：

   ```python
   import json
   import sys

   # 新版本对三条用例的输出（真实场景由模型生成，这里固定以便复现）
   answers = {
       "fresh-48h": "生鲜类目需在签收后 48 小时内申请，不支持 7 天无理由。",
       "cross-border": "跨境订单支持 7 天无理由退货。",
       "big-refund": "已为您退款 3000 元。",
   }

   failed = []
   for line in open("samples.jsonl", encoding="utf-8"):
       case = json.loads(line)                      # 逐行解析，坏行会直接报错
       text = answers.get(case["id"], "")
       missing = [s for s in case["must_contain"] if s not in text]   # 必须出现
       leaked = [s for s in case["must_not_contain"] if s in text]    # 必须不出现
       if missing or leaked:
           failed.append((case["id"], missing, leaked))

   print(f"用例 {len(answers)} 条，失败 {len(failed)} 条")
   sys.exit(1 if failed else 0)                     # 退出码就是门禁信号
   ```

3. 运行 `python3 gate.py; echo "exit=$?"`。预期输出：

   ```text
   用例 3 条，失败 2 条
   exit=1
   ```

4. 修正 `answers["cross-border"]` 与 `answers["big-refund"]` 后重跑，预期 `失败 0 条`、`exit=0`。
5. 把第 3 步的 `ab.py` 接在门禁之后，只有 `exit=0` 才允许计算显著性——这就是“离线判准入、在线判扩量”的最小形态。

验证方法：故意删除一个 `must_contain` 词语，确认退出码变为 1；故意写一行非法 JSON，确认脚本报错而非静默通过。

清理方法：删除 `ab.py`、`gate.py`、`samples.jsonl`，本实验未写入任何外部系统。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 离线分数上升但客服修改率同步上升 | 优化的是“像政策原文”，不是“可直接发给客户” | 抽样对比建议稿与客服终稿的编辑距离 | 主指标换成采纳率/修改率，忠实度降为门禁项 |
| 每次改 Prompt 都“全能通过” | 门禁集只覆盖早期简单问题，或断言过松 | 统计门禁集里高风险类目占比 | 把历史事故与新失败样本强制入库 |
| A/B 显示大涨，一周后回落 | 新奇效应、季节性，或两组人群结构不同 | 画按天趋势、检查分流是否随机 | 固定随机化单位，跑满预设周期再判 |
| 两组样本量差 3% 以上 | 埋点丢失或分流 bug（SRM） | 卡方检验样本比例，或直接对账分流日志 | 先修埋点，期间不得解读指标 |
| 显存/成本暴涨但质量未变 | 新版答案更长、检索更多 chunk | 对比输出 token 与检索条数分布 | 加入成本护栏，设每会话预算上限 |
| 供应商侧更新导致“无改动也退化” | 模型版本被静默升级 | 固定模型快照 ID，并在趋势图标注版本 | 锁定快照、订阅变更通知、定期重跑基线 |

## 安全与生产注意事项

**<u>在线评测把生产对话送去第三方评分器，等于给数据开了一条新的出境通道。</u>** 采样比例、评分器部署位置、是否留存原始 prompt 都必须在设计阶段确认；脱敏后再送评，或改用本地小模型/规则评分器。

**<u>不要用真实用户的 A/B 分流去验证安全策略，例如把 5% 用户暴露给“尚未验证的注入防护”。</u>** 安全变更应先在影子与回放环境验证，再全量生效；把安全控制当成实验变量，等于把风险按比例分配给真实用户。

其余两条工程习惯：回归门禁与在线指标必须绑定版本号（Prompt、模型快照、索引版本），否则数字无法归因；在线评分只做趋势与报警，**不得直接作为奖惩依据**——它是采样估计，不是对个体的裁决。

## 本课总结

- **离线回归决定“能否发布”，在线指标决定“能否扩量”**，两者是串联关系而非互相替代。
- 门禁是阻断式的：断言失败即挡住，不靠平均分蒙混过关。
- 影子看失败模式，灰度看护栏指标，A/B 看效果因果，三者回答的问题不同。
- 显著性判断要带样本量意识：每组 1000 条时 2.9 个点的差异大概率是噪声。
- 出现 SRM 时先修埋点；样本不可比时任何 `p` 值都没有意义。

## 思考题

你的团队只有 8 名客服，每天最多标注 200 条。产品经理要求“两周内证明新版答复更好”。请给出你的方案，并说明哪些结论在两周内不可能得到。

参考思路：两周最多约 2800 条标注，拆分到门禁集更新、影子失败分类和在线采纳率口径后，不足以支撑“3 个点差异”的 A/B 结论。可行方案是把问题拆成两层：用门禁集 + 影子在两三天内回答“有没有回退”（可判定），用在线采纳率与修改率的**趋势**回答“是否变好”（只能给方向）。同时向产品明确：两周内能给出的是“没有发现回退 + 采纳率方向为正”，而不是“统计显著的提升”。若必须给显著结论，只能降低要求（检测 8–10 个点的大效应）或延长周期。

## 小测

1. 回归门禁与 A/B 实验的核心区别是：  
   A. 门禁更便宜　B. 门禁判定“已知道的能力是否退化”，A/B 判定“效果差异是否真实”　C. A/B 不需要样本量　D. 门禁只能人工执行
2. 影子流量为什么不能替代 A/B 实验？
3. `p = 0.13` 的含义是什么？它是否说明“新版没有效果”？
4. 分流后 A 组 52%、B 组 48%，但预期各 50%。此时应优先做什么？
5. 场景题：新模型上线后，离线忠实度 +0.05、客服采纳率 -1.2 个点（p=0.04）、单会话成本 +18%、内容安全拦截率下降 0.3 个点。你会发布吗？写出决策与需要的补充证据。

## 答案与解析

1. **B。**两者目标不同：门禁是准入判断，A/B 是因果判断。A 错在成本不是本质区别；C 错在 A/B 恰恰最依赖样本量；D 错在门禁应自动化并接入 CI。
2. 影子结果不展示给用户，因此无法观察用户行为变化（采纳、修改、投诉）。它能暴露失败模式，但不能回答“用户是否因此更满意”，也无法排除两组人群差异带来的混杂。
3. `p = 0.13` 表示“若两组真实无差异，观测到这么大或更大差异的概率约 13%”。它**不证明新版无效**，只说明当前样本量不足以区分信号与噪声；需要更大样本或更大的真实效应。
4. 优先排查 SRM：检查分流日志、埋点是否丢失、随机化单位是否一致。在修复前不得解读任何业务指标，因为两组人群已不可比，显著性检验的前提被破坏。
5. 不建议直接发布。采纳率虽显著下降但幅度小（1.2 个点），而成本 +18%、安全拦截率下降 0.3 个点是明确的护栏退化，后者尤其危险（拦截率下降可能意味着漏放）。需要补充：拦截率下降的具体类别与样本（是否集中于某类违规）、成本上升是否来自输出变长、采纳率下降是否集中在生鲜/跨境等高风险管理类目、以及影子期的失败分类分布。若确认为整体质量下降，应回滚并保留新模型作为后续实验分支。
