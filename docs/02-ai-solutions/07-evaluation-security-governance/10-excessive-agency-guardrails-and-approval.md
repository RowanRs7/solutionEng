# 越权工具调用、Guardrail 与审批

## 为什么需要学习

售后助手的退款 Agent 有一段很“贴心”的推理：客户说“东西坏了，我很急”，Agent 查到订单金额 2980 元，认为“符合质量问题全额退款”，于是直接调用 `refund.create`。它没有编造参数，也没有绕过接口鉴权——因为那个工具账号本来就有退款权限。三天后财务对账发现，这类退款中有 17 笔在政策上应走“补发或部分退款”。

问题的性质不是模型算错，而是**我们把“决定做什么”和“被允许做什么”交给了同一个主体**。模型负责提出动作，权限系统负责判断能不能做——只要后者缺位，模型每多一分自主性，就多一分越权空间。OWASP 在 LLM03:2026 Excessive Agency 中把这称为 *过度代理*（excessive agency；2025 版编号为 LLM06），并把根因拆成三条：功能过多、权限过大、自主性过高；对应的缓解也是三条：缩小工具集、最小权限、关键动作保留人工确认。

> **核心结论：** 授权必须在模型之外执行。模型可以提议任何动作，但只有策略引擎和审批人能放行。

## 学习目标

完成本课后，你能够：

- 为一条工具清单按“读 / 低风险写 / 高风险写 / 不可逆”分级，并给出额度与审批规则。
- 写出在工具侧执行、未知输入一律拒绝的决策函数（fail-closed）。
- 解释审批流的暂停、状态序列化与恢复过程，并指出“审批被复用”“超时自动放行”两类漏洞。
- 判断一个场景该用过滤、沙箱还是人工审批，而不是三者混为一谈。

## 业务场景

售后助手可调用的工具只有 5 个，但风险差别极大：

- `order.get`：只读订单，风险低。
- `ticket.note`：往工单写备注，低风险写。
- `refund.create`：发起退款，涉及资金，且**不可逆**。
- `order.address.set`：修改收货地址，可能被用于欺诈改道。
- `payout.export`：导出结算数据，不可逆且涉及批量个人信息，仅财务可用。

现行流程是“Agent 生成建议 → 客服点击确认 → 系统调用工具”。但客服的确认按钮只显示“确认退款”四个字，不显示金额与订单号；超时 30 秒未操作时，前端会自动关闭弹窗并把任务标记为“已取消”，但后端有一次把“已取消”当成了“无异议”，直接执行。这类缝比模型幻觉更常见。

## 核心概念

| 动作级别 | 示例 | 默认策略 | 失效代价 |
| --- | --- | --- | --- |
| 读 | `order.get`、政策检索 | 自动放行，记录 trace | 隐私越权读取 |
| 低风险写 | `ticket.note`、生成草稿 | 自动放行，可回滚 | 工单污染，可人工修正 |
| 高风险写 | `refund.create`（≤500 元） | 额度内自动，超出单人审批 | 资金损失 |
| 不可逆 | 大额退款、`payout.export`、改地址后发货 | 双人审批或直接禁止 | 无法撤销、合规事件 |

- *过度代理*：模型被授予超出任务所需的工具、权限或自主性，从而可能执行未授权动作。
- *Guardrail*：模型之外的约束层，分输入侧（拦恶意与不合规输入）、输出侧（检查内容与外链）、工具侧（校验参数与权限）。三层互相独立，任何一层失效都不应导致越权。
- *审批闸门*（approval gate）：高风险动作必须暂停执行，把**待执行参数**交给有权限的人确认，确认后才继续。
- *fail-closed*：校验不通过、参数缺失、类型不符、审批超时，一律按“拒绝”处理；只有明确通过才执行。
- *沙箱*：把工具执行限制在受控环境里（文件、网络、命令白名单），使注入成功也拿不到主机权限。
- *TOCTOU*：审批时看到的参数与真正执行的参数不一致（time-of-check to time-of-use）。防控方式是把参数哈希绑进审批令牌。
- *审批疲劳*：审批量过大导致人机械点“同意”，审批退化为橡皮章。

**过滤不能替代审批**：过滤器判断“这句话像不像攻击”，审批判断“这个动作是否被授权”。前者可以被绕过，后者是权限事实。

## 工作原理

1. **列工具清单并分级**：每个工具标注级别、影响面、可逆性、所需角色。分级结果写进配置，不写在 Prompt 里。
2. **削减能力**：只给当前任务需要的工具。售后助手不需要“批量导出”“修改支付账户”，这些能力从工具列表里删除，而不是靠提示词禁止。
3. **工具侧校验**：在工具入口按 schema 校验类型、范围、关联关系（订单必须属于当前客户、状态必须可退、金额不得超过订单实付）。模型给的参数一律视为不可信输入。
4. **额度与速率**：自动放行的额度（如 500 元/单、日累计 5000 元）与速率限制在服务端计数，跨会话共享，避免“多轮小额绕过”。
5. **审批闸门**：命中审批规则时暂停，把动作、参数、依据、影响、请求者序列化为一个待办任务（含参数哈希与一次性令牌），交给有权限的人。
6. **恢复执行**：审批通过后按令牌恢复执行；执行前重新校验参数哈希与业务状态，任一变化即作废并重新审批。
7. **幂等与补偿**：写操作携带幂等键（订单号 + 金额 + 动作），重试不产生二次执行；不可逆动作先做可撤销的预占（如冻结额度）。
8. **审计与复盘**：记录谁提议、谁批准、依据是什么、执行结果如何。审批记录与执行记录必须能对上同一次请求。

## 架构与选型

| 手段 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 输入/输出过滤 | 所有入口的基线 | 作为唯一授权手段 | 成本低，误报与漏报并存 |
| 工具侧参数与权限校验 | 所有写操作 | 只读查询也值得做 | 必须实现，无法省略 |
| 额度 + 速率限制 | 资金、消息发送、导出 | 无状态计算类工具 | 简单有效，需跨会话计数 |
| 暂停—审批—恢复 | 高风险写、不可逆动作 | 高频低延迟场景 | 增加时延与人力，需防疲劳 |
| 沙箱执行 | 代码、文件、命令、浏览器 | 纯 API 调用 | 隔离强，集成成本高 |
| 直接禁止 | 与业务无关的能力（改支付账户） | 有合法业务需求时 | 最安全，需业务让步 |

选型依据：**按“最坏损失 × 发生概率”排序，而不是按“模型有多想调用”排序**。不可逆且金额大的动作，即便发生概率低，也必须审批；可回滚的低风险写，用额度与告警即可。

## 最小示例

问题：给 5 个工具实现一个 fail-closed 的决策函数，覆盖自动放行、单人审批、双人审批与拒绝。

环境：Python 3.10+，仅标准库。输入：工具名、参数、调用者角色。输出：决策、所需审批人数、幂等键。

```python
from dataclasses import dataclass, field

# 动作分级：读 / 低风险写 / 高风险写 / 不可逆；auto 为自动放行额度
POLICY = {
    "order.get":         {"tier": "read",         "auto": 0,   "roles": {"agent", "lead"}},
    "ticket.note":       {"tier": "low_write",    "auto": 0,   "roles": {"agent", "lead"}},
    "refund.create":     {"tier": "high_write",   "auto": 500, "roles": {"agent", "lead"}},
    "order.address.set": {"tier": "high_write",   "auto": 0,   "roles": {"lead"}},
    "payout.export":     {"tier": "irreversible", "auto": 0,   "roles": {"finance"}},
}


@dataclass
class Decision:
    verdict: str                  # allow / require_approval / deny
    reason: str
    approvals: int = 0
    idempotency_key: str = ""
    audit: dict = field(default_factory=dict)


def decide(tool, args, actor):
    p = POLICY.get(tool)
    if p is None:                          # 未登记的工具：拒绝，而不是"按默认放行"
        return Decision("deny", f"未登记的工具：{tool}")
    if actor not in p["roles"]:            # 角色白名单，与服务端身份绑定
        return Decision("deny", f"角色 {actor} 无权调用 {tool}")
    if tool == "refund.create":
        amount = args.get("amount")
        if not isinstance(amount, int) or amount <= 0:   # 类型或取值异常 → 转人工，不放行
            return Decision("require_approval", "金额缺失或非法，需人工确认", approvals=1)
        if amount > 5000:                                # 大额：双人审批
            return Decision("require_approval", "金额超过 5000，需双人审批", approvals=2,
                            idempotency_key=f"{tool}:{args.get('order_id')}:{amount}")
        if amount > p["auto"]:                           # 超额度：单人审批
            return Decision("require_approval", "金额超过自动上限 500，需单人审批", approvals=1,
                            idempotency_key=f"{tool}:{args.get('order_id')}:{amount}")
        return Decision("allow", "金额在自动上限内",
                        idempotency_key=f"{tool}:{args.get('order_id')}:{amount}")
    return Decision("allow", f"{p['tier']} 类动作，角色校验通过")


cases = [
    ("refund.create", {"order_id": "SO-1", "amount": 200}, "agent"),
    ("refund.create", {"order_id": "SO-2", "amount": 3000}, "agent"),
    ("refund.create", {"order_id": "SO-3", "amount": 8000}, "lead"),
    ("refund.create", {"order_id": "SO-4", "amount": "三千"}, "agent"),
    ("payout.export", {}, "agent"),
    ("orders.export", {}, "agent"),
]
for tool, args, actor in cases:
    d = decide(tool, args, actor)
    print(f"{tool:18} {str(args):38} {actor:6} -> {d.verdict:16} {d.reason}")
```

预期输出：

```text
refund.create      {'order_id': 'SO-1', 'amount': 200}    agent  -> allow            金额在自动上限内
refund.create      {'order_id': 'SO-2', 'amount': 3000}   agent  -> require_approval 金额超过自动上限 500，需单人审批
refund.create      {'order_id': 'SO-3', 'amount': 8000}   lead   -> require_approval 金额超过 5000，需双人审批
refund.create      {'order_id': 'SO-4', 'amount': '三千'}   agent  -> require_approval 金额缺失或非法，需人工确认
payout.export      {}                                     agent  -> deny             角色 agent 无权调用 payout.export
orders.export      {}                                     agent  -> deny             未登记的工具：orders.export
```

关键在于三条“不信任”：不信任工具名（未登记即拒）、不信任角色（服务端身份为准）、不信任参数类型（`"三千"` 不会被当成 0 或 3000，而是转人工）。**默认分支是拒绝，不是放行**——这是 fail-closed 与“默认允许”的实质区别。

## 动手实验

### 任务：让策略引擎挡住一次越权退款

前置条件：Python 3.10+；把上例保存为 `policy.py`。

1. 运行 `python3 policy.py`，确认 6 条决策与预期一致。
2. 把 `refund.create` 的 `auto` 改为 1000，重跑，观察 200 与 3000 两条的决策是否变化。预期：200 仍放行，3000 仍审批。
3. 新增一条用例 `("refund.create", {"order_id": "SO-5"}, "agent")`（缺 `amount`），确认返回 `require_approval` 而不是异常或放行。
4. 把 `actor` 改成 `"agent2"`（不在角色表里），确认返回 `deny`。
5. 给决策加一个参数哈希：`import hashlib; h = hashlib.sha256(str(sorted(args.items())).encode()).hexdigest()[:12]`，把 `h` 写进审批令牌，模拟“审批绑定待执行参数”。

验证方法：第 3 步必须审批、第 4 步必须拒绝；第 5 步对同一 `args` 重复计算应得到相同哈希，改动金额后哈希必须变化。
清理方法：`rm policy.py`；实验不涉及真实支付接口。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 审批弹窗只显示“确认退款” | 审批 UI 未展示关键参数 | 用测试单检查弹窗字段 | 强制展示金额、订单号、政策依据、影响 |
| 审批后金额被改大 | 审批未绑定参数，执行时重新取值 | 对比审批记录与执行记录的参数 | 参数哈希 + 一次性令牌，变更即重新审批 |
| 超时任务被执行 | 超时被当作“无异议” | 查任务状态机与超时分支 | 超时一律拒绝（fail-closed），要求重新发起 |
| 同一笔订单退了两次 | 无幂等键，模型重试 | 查同一订单的调用次数 | 幂等键 + 状态前置校验（可退状态） |
| 审批人看不到上下文 | 审批任务只带动作，不带依据 | 抽查审批记录字段 | 附政策片段、订单摘要、模型理由、trace ID |
| 同类动作第二次不再提示 | 审批被“记住”（always approve）复用 | 检查审批缓存与作用域 | 只对同一工具+同一参数放行；高风险动作禁止记忆 |
| 客服机械点同意 | 审批疲劳 | 统计审批耗时分布 | 提高自动额度、聚合低风险动作、只对高风险保留审批 |

## 安全与生产注意事项

**<u>审批默认值必须是拒绝：超时、进程重启、审批人离职、参数解析失败，都不能变成“放行”。</u>** 一次失败即放行的实现，会把整条审批链变成装饰品；恢复执行前必须重新校验，而不是信任内存中的旧决策。

**<u>“记住审批结果”是最容易引入越权的功能：审批一旦被复用，就可能作用到另一笔订单、另一个 Agent，甚至另一套权限。</u>** OpenAI Agents SDK 的文档明确提示，本地 shell 与文件编辑工具的“永久同意”按工具类型和名称匹配，**不按 Agent 或执行器隔离**，跨 Agent 共享审批状态时可能直接放行；资金类动作不应启用这类记忆（截至 2026-10，见其 Human-in-the-loop 文档）。

另外两条：**<u>沙箱必须默认禁网并限制文件系统</u>**，否则“工具被注入”会升级为“主机被控”；**<u>不要用自然语言 Prompt 声明额度</u>**，额度必须在服务端计数器里，并且跨会话累计，防止“多轮小额”绕过。

## 本课总结

- **模型只提议，策略引擎才授权**；把两者混在一起，越权就只是时间问题。
- 工具分级（读/低风险写/高风险写/不可逆）是额度与审批规则的输入，分级应写在配置里。
- fail-closed 的核心是默认分支为拒绝，且参数类型异常时转人工而非“宽容解析”。
- 审批必须绑定待执行参数与业务状态；超时、复用、恢复都是常见漏洞点。
- 过滤、沙箱、审批解决三个不同问题，不能互相替代。

## 思考题

如果业务希望“500 元以下自动退款，500–5000 元单人审批，5000 以上双人审批”，但客户投诉率在双人审批后明显上升，你会调整金额线还是调整流程？

参考思路：先确认投诉上升的原因：是等待时间（流程）还是拒绝率（规则）。若主要是等待，可把双人审批改为“单人 + 事后抽检”，同时提高自动额度并保留日累计上限；若是拒绝率上升（说明模型建议本身偏差大），应改评测与 Prompt，而不是松绑审批。金额线不是越松越好，它与欺诈损失、客诉成本共同决定；应给出两套数据（每万元退款的事故数与平均处理时长）后再调，并把调整写进决策记录与回归用例。

## 小测

1. 过度代理的三条根因是：  
   A. 模型太小、数据太少、延迟太高　B. 功能过多、权限过大、自主性过高　C. 提示过长、上下文过短、温度过低　D. 没有日志、没有监控、没有告警
2. 为什么“在系统提示里写最高退款 500 元”不构成额度控制？
3. 审批超时后自动放行会造成什么后果？正确做法是什么？
4. 沙箱解决的是哪一类风险？它能否替代参数校验？
5. 场景题：客服要求给 Agent 增加“批量修改订单地址”的工具，理由是改派送货很常见。你会怎么回应？

## 答案与解析

1. **B。**OWASP LLM03:2026 Excessive Agency（2025 版编号 LLM06）把根因归为功能、权限、自主性三条，缓解分别对应缩小工具集、最小权限、保留人工确认。A、C 是性能与参数问题；D 是观测缺失，虽然相关但不是该风险的根因分类。
2. 因为提示词只是模型可见的文本，模型可以忽略、误解或被注入覆盖，而额度需要服务端计数器与角色绑定。真正的控制在工具入口执行，并可被审计与验证。
3. 超时放行把“没有人反对”当成“有人同意”，在夜间、故障、人员离职时最危险。正确做法是超时即拒绝或保持挂起，并通过通知、升级路径让审批被真正处理；拒绝不等于任务丢失，可重新发起。
4. 沙箱限制执行环境（文件、网络、命令），防的是“工具被利用后拿到主机能力”。它不能替代参数校验，因为沙箱里照样可以发起一笔合法却越权的退款；参数与权限校验必须在业务层。
5. 不建议直接开放。可拆为“单笔改地址 + 仅发货前 + 需工单关联 + 单人审批”，按订单维度限流，并保留原地址快照与通知客户；批量能力应只给有权限的人工角色。若数据证明改派量很大，再评估“自动改派白名单（同城、未发货、金额低于阈值）”，并用影子流量验证误改率。
