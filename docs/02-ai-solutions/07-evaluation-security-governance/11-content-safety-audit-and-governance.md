# 内容安全、审计、版权与 AI 治理

## 为什么需要学习

售后助手被客服要求“写一段催客户寄回旧机的话，语气硬一点”。它生成了一段带威胁意味的文案：“再不寄回，我们将联系你的单位并保留追究法律责任的权利。”客服觉得“挺有效”，直接发了出去。三天后客户投诉到平台，运营才发现：内容安全策略里只有“拦截违法内容”，没有“拦截不当施压话术”；日志里只有一句 `blocked=false`，没有记录是谁在什么版本下放行的。

同月法务问“供应商生成的商品图授权链条在哪”，工程答不上来；监管问“生成内容怎么标识”，团队只在前端加了一行提示，导出成图片后标识就消失了。

这些问题不属于模型能力，而属于**治理**：谁批准、依据什么、留了什么证据、出了问题怎么回溯。OWASP 把“系统提示泄露”“不当输出处理”列入 LLM 风险清单，NIST AI RMF 则把“Govern（治理）”放在四个职能之首——治理不是文档，而是让每条控制可执行、可审计、可追责。

> **核心结论：** 内容安全决定“能不能发”，审计决定“事后能不能说清”，版权与标识决定“发了会不会侵权或违规”，三者共同构成可运营的 AI 产品。

## 学习目标

完成本课后，你能够：

- 为一类高风险内容（威胁性催收、贬损竞品、医疗建议）写出判定标准与四段处置路径。
- 设计审计事件的最小字段集，并解释“只记录结果”为什么无法复盘。
- 用标准库实现哈希链审计日志，并演示篡改检测与其局限。
- 把版权来源、AI 标识与治理职责映射为可检查的控制点。

## 业务场景

晴空商城的售后助手每月产生约 36 万条答复，其中约 4% 会被客服直接复制给客户。内容风险集中在四类：

- 不当施压：威胁、羞辱、暗示上报征信或联系单位。
- 越界承诺：承诺“一定全额退款”“保证三天到账”，超出政策授权。
- 贬损对比：应客服要求写“某品牌质量差”的对比话术。
- 敏感建议：对健康、法律问题给出确定性结论。

治理侧的要求来自三个方向：平台的内容审核规则、法务的版权与标识要求、监管的问询与备案材料。团队现状是：策略写在 Prompt 里、拦截结果记在应用日志里、审计靠人工翻聊天记录。

## 核心概念

| 治理事项 | 需要回答的问题 | 可检查的控制点 |
| --- | --- | --- |
| 内容安全 | 哪些内容禁止、哪些需改写、哪些需提示？ | 策略表 + 分类器 + 处置动作 + 申诉通道 |
| 审计留痕 | 谁、在什么版本下、依据什么、做了什么决定？ | 事件 schema + 追加日志 + 保留期 |
| 版权 | 输入素材与输出内容的权利来源？ | 素材登记 + 许可记录 + 相似性检查 |
| AI 标识 | 生成内容是否可被识别为生成？ | 显式标识 + 元数据隐式标识 + 导出覆盖 |
| 治理流程 | 谁批准上线、谁复核风险、出问题谁负责？ | 风险登记表 + 评审记录 + 定期复核 |

- *内容安全*：对输入与输出做合规判定与处置，覆盖违法内容、不当施压、越界承诺等，不限于“涉黄涉政”。
- *审计留痕*：以事件为单位记录关键操作，使事后能重建“当时系统看到了什么、依据什么规则、谁批准”。
- *不可否认性*：通过只追加存储与哈希链，使“事后悄悄改记录”可被发现。
- *AI 标识*：区分显式标识（用户可感知的提示）与隐式标识（写在文件元数据中的生成属性）。
- *风险登记表*：把风险、影响、可能性、控制措施、责任人、复核日期写成一张可持续更新的表。
- *治理流程*：立项评审、变更审批、上线门禁、定期复核、事件复盘五个节点的组合。

**内容安全策略必须是“可判定”的**：写“语气要得体”无法执行，写“不得出现威胁性表述，命中即降级为安抚模板并转人工”才能被测试。

## 工作原理

1. **定义策略分级**：把内容分为禁止（违法、歧视、威胁）、受限（越界承诺、医疗法律建议）、需提示（推测性结论、AI 生成说明）三级，每级对应处置动作。
2. **双向检查**：输入侧拦恶意与违规请求，输出侧检查生成结果；只在输入侧拦，会被“正常问题诱导出违规答案”绕过。
3. **处置动作**：拦截并给出替代话术、降级为模板、加显著提示、转人工、留证。**不要只做“拦截”**——客服需要一条能继续工作的路径，否则会绕过系统。
4. **申诉与复核**：对误判提供人工复核入口与时限，记录误判样本用于迭代阈值；这也是监管常问的“投诉举报机制”。
5. **生成审计事件**：每次发布、拦截、审批、工具调用都写一条事件，包含版本号（Prompt/模型/策略）与参数哈希，保证可回溯到具体配置。
6. **追加与校验**：事件写入只追加存储，并用哈希链串联；校验任务定期重算，发现断链即告警。
7. **版权与来源**：登记输入素材的来源与许可（客服上传的截图、供应商图片、抓取的网页），输出侧对高风险内容做相似性抽查，禁止把无授权素材用于对外文案。
8. **AI 标识**：在交互界面与生成内容上添加显式标识，同时在文件元数据写入生成属性；导出、下载、复制路径都要覆盖，否则标识在流转中消失。
9. **治理闭环**：风险登记表 → 变更评审 → 上线门禁（回归 + 安全用例）→ 监控与告警 → 事件复盘 → 更新策略与登记表。

## 架构与选型

| 控制手段 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 关键词/正则策略 | 明确禁词、固定话术 | 语义级不当施压 | 快、可解释，但绕过容易 |
| 分类模型审核 | 语气、威胁、越界承诺 | 极低延迟、强离线 | 覆盖好，需持续标注与阈值管理 |
| 模板降级 | 高风险类目（催收、医疗） | 需要个性化解释的场景 | 稳定但生硬，需维护模板库 |
| 人工复核队列 | 误判申诉、高风险命中 | 全量审核（人力不可承受） | 质量高，成本随时延上升 |
| 哈希链 + 只追加存储 | 审计与合规证据 | 高吞吐写入且可接受最终一致 | 成本低，需防“整链重写” |
| 外部时间戳/锚点 | 需要对外举证的场景 | 内部排障 | 增强不可否认性，引入第三方依赖 |

选型依据：按**后果严重度 × 可检测性**分配投入。威胁性话术一旦发给客户就是公关与合规事件，值得用分类模型 + 模板降级；低风险项用固定文案加导出检查即可。

## 最小示例

问题：审计日志如何做到“事后改动可被发现”，以及它防不住什么？

环境：Python 3.10+，仅标准库。输入：三条事件。输出：链校验结果、篡改后的校验结果。

```python
import hashlib
import json


def canon(obj):
    """稳定序列化：键排序 + 紧凑分隔符，保证同一内容哈希一致"""
    return json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"))


def append(chain, event):
    """把事件追加为哈希链的一环：hash = sha256(prev_hash + 事件正文)"""
    prev = chain[-1]["hash"] if chain else "0" * 64   # 创世记录用全零前驱
    body = canon({**event, "prev_hash": prev})
    chain.append({**event, "prev_hash": prev,
                  "hash": hashlib.sha256(body.encode("utf-8")).hexdigest()})
    return chain


def verify(chain):
    """逐环重算：prev_hash 断链或正文被改动都会失败"""
    prev = "0" * 64
    for i, rec in enumerate(chain, start=1):
        if rec["prev_hash"] != prev:
            return f"第 {i} 条断链：prev_hash 不匹配"
        body = canon({k: v for k, v in rec.items() if k != "hash"})
        if hashlib.sha256(body.encode("utf-8")).hexdigest() != rec["hash"]:
            return f"第 {i} 条正文被改动"
        prev = rec["hash"]
    return "校验通过"


chain = []
append(chain, {"ts": "2026-10-19T09:00:00Z", "actor": "li.lead",
               "action": "prompt.publish", "target": "aftersale-v7",
               "reason": "修复生鲜时效", "result": "approved"})
append(chain, {"ts": "2026-10-19T09:12:00Z", "actor": "assistant",
               "action": "safety.block", "target": "session-8812",
               "reason": "威胁性催收话术", "result": "blocked"})
append(chain, {"ts": "2026-10-19T10:03:00Z", "actor": "wang.agent",
               "action": "refund.approve", "target": "SO-2026-0917",
               "reason": "质量问题全额退款", "result": "approved"})
print("初始：", verify(chain))
print("链长：", len(chain), "| 第 2 条哈希：", chain[1]["hash"][:16])

chain[1]["result"] = "allowed"           # 模拟有人把“已拦截”改成“已放行”
print("篡改第 2 条后：", verify(chain))

chain2 = [dict(r) for r in chain]        # 复制一份再改回原值
chain2[1]["result"] = "blocked"
print("改回原值后：", verify(chain2))
```

预期输出：

```text
初始： 校验通过
链长： 3 | 第 2 条哈希： 18be461fad9deae2
篡改第 2 条后： 第 2 条正文被改动
改回原值后： 校验通过
```

注意最后一行：改回原值后校验又通过了。**哈希链只能发现“与当前链条不一致的改动”，不能阻止有权限者重算整条链**；要对外举证，需把链头定期写入独立存储、第三方时间戳或不可变存储（WORM）。

## 动手实验

### 任务：复现三种篡改并观察链的反应

前置条件：Python 3.10+；把上例保存为 `audit.py`。

1. 运行 `python3 audit.py`，确认输出与上节一致。
2. 删除中间一条（`del chain[1]`）后重跑 `verify`。预期：`第 2 条断链：prev_hash 不匹配`——因为第 3 条的 `prev_hash` 仍指向被删记录的哈希。
3. 恢复后，同时改第 2 条正文并**重算第 2、3 条哈希**（模拟内部人重写链条），预期 `校验通过`。把这一步结论记下来：链式哈希不防重写。
4. 给 `append` 增加 `"policy_version": "safety-2026-10"` 字段，重跑，确认链仍然校验通过（新增字段属于正文的一部分，必须重算）。
5. 用 `json.dumps(chain, ensure_ascii=False, indent=2)` 导出，检查其中是否含个人信息；把含手机号的字段替换为哈希后再入库。

验证方法：第 2 步必须断链；第 3 步必须通过（证明局限）；第 5 步导出的内容中不得出现明文手机号。
清理方法：`rm audit.py chain.json`；实验不写入任何外部存储。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 出了事故说不清是谁改的配置 | 审计只记录结果，没有操作者与版本 | 抽查事件字段是否含 actor/version | 补齐 actor、target、policy_version、trace_id |
| 审计库被应用账号删改 | 应用与审计共用高权限账号 | 检查账号权限与是否只追加 | 审计写入用独立通道，禁止 UPDATE/DELETE |
| 导出的图片没有 AI 标识 | 只做了界面提示，未写元数据/未覆盖导出 | 下载图片检查元数据与画面 | 显式 + 隐式标识，导出路径单独校验 |
| 内容安全误伤严重 | 阈值过严且无申诉通道 | 统计误判率与客服绕过行为 | 分级处置 + 人工复核 + 阈值按类目调整 |

## 安全与生产注意事项

**<u>审计日志本身是一份高价值敏感数据集，必须按最高等级保护：脱敏、加密、限权、限期。</u>** 为了复盘把所有 prompt 原文都写进审计库，等于用合规手段制造了一个新的泄露源。

**<u>由应用进程写入的审计日志不具备不可否认性：应用账号能改数据，也能改校验逻辑。</u>** 必须使用独立写入通道、只追加存储与外部锚点；否则“有日志”只是心理安慰。

**<u>只做界面提示不构成 AI 标识：导出、截图、复制、二次分发都会让标识丢失。</u>** 《人工智能生成合成内容标识办法》要求显式标识与元数据隐式标识并存，并覆盖下载、复制、导出场景（2025-09-01 施行）。

另外两条：**<u>版权风险主要来自输入素材与输出相似性</u>**，素材登记与上线前检查比事后声明有效；**<u>治理流程若无触发条件就会退化为文档</u>**，至少把“新增工具、调整拒答阈值、更换模型、发生对外投诉”设为强制评审事件。

## 本课总结

- **内容安全要可判定、可处置、可申诉**：只有“拦截”而没有替代路径，等于逼客服绕过系统。
- 审计的价值在于能重建“谁、在什么版本、依据什么、做了什么决定”；只记结果等于没记。
- 哈希链能发现改动，但不能阻止有权限者重写整链；对外举证需要外部锚点与不可变存储。
- 版权与 AI 标识是产品上线的前置条件，要覆盖导出与流转，而不是只做界面提示。
- 治理是把风险登记、变更评审、上线门禁、监控与复盘连成闭环，并写清触发条件与责任人。

## 思考题

监管问：“你们如何保证 AI 不会生成威胁客户的内容？”如果你只有一份策略文档和一次抽查记录，应该补什么才能给出可信回答？

参考思路：把“保证”拆成可验证的三层证据。第一层是策略与判定标准（哪些表述属于威胁，阈值多少）；第二层是执行证据（分类器版本、拦截率、转人工率、误判复核记录、回归用例通过率）；第三层是响应证据（投诉入口、处置时限、事件复盘与策略更新记录）。同时承认残余风险：给出抽样估计与未覆盖类目。可信的回答不是“我们保证不会”，而是“有这些控制、数据与响应机制，残余风险如下”。

## 小测

1. 只记录 `blocked=true/false` 的审计日志，最大的问题是：  
   A. 存储成本高　B. 无法知道谁在什么版本下做了什么决定　C. 哈希无法计算　D. 不符合性能要求
2. 为什么内容安全要同时检查输入与输出？
3. 哈希链审计能防住“内部人重写整条链”吗？为什么？
4. AI 标识为什么必须覆盖导出与复制场景？
5. 场景题：客服要求助手生成“催客户寄回旧机”的话术，其中包含“否则将联系你的单位”。你如何设计处置路径与审计记录？

## 答案与解析

1. **B。**审计的目的是事后重建决策过程，缺 actor、版本、依据就无法复盘。A 反了——字段越少成本越低；C 哈希照样可算，只是信息量不足；D 与性能无关。
2. 因为违规内容常由“看似正常”的输入诱导产生（如“帮我写一段强硬的话”），只在输入侧拦截会漏掉输出端的问题；输出侧检查还能覆盖模型幻觉与检索污染带来的违规内容。
3. 不能。哈希链只能保证“链条与内容一致”，有写权限的人可以改内容后重算后续所有哈希。要提升强度需把链头锚定到外部（第三方时间戳、不可变存储、独立账号写入）。
4. 因为标识的价值在于“任何人拿到这份内容都能判断它是生成的”。只做界面提示，导出为图片或复制到别处后标识消失，等于没有标识；法规也要求覆盖下载、复制、导出。
5. 处置路径：识别为“不当施压”→降级为合规催收模板（说明寄回时限与流程，不含威胁）→提示客服该话术已被替换→如客服坚持需要强硬措辞，转主管复核。审计记录应包含：会话 ID、触发规则与阈值、原始生成内容（脱敏）、替换后的模板版本、处理人、时间与最终发送状态。这样既能复盘，也能统计该类触发的频率并调整模板。
