# 敏感数据、隐私与数据泄露

## 为什么需要学习

一次内部抽查里，晴空商城的安全同学在售后助手的日志库里搜到了 2.3 万条完整手机号、1.1 万条收货地址和 47 条身份证号。它们不是被攻击拿走的，而是系统“正常工作”时写进去的：调试日志打印了完整 prompt，trace 保存了检索到的订单原文，评测脚本把生产对话拉到了本地。更麻烦的是，负责标注的外包团队也在同一个共享盘里拿到了这批数据。

同月还发生了一次更直接的泄露：客服把 B 客户的订单号贴进助手，助手基于“最近会话缓存”返回了 A 客户的退款进度。没有人被入侵，只是缓存键少带了一个租户 ID。

> **核心结论：** AI 应用的隐私风险大多不是“模型记住了数据”，而是我们把数据复制到了更多地方——上下文、日志、trace、评测集、供应商侧，每一份都是一条独立的泄露路径。

## 学习目标

完成本课后，你能够：

- 为一条具体数据流（客户提问、订单、检索文档、日志、评测集）标注等级与处理要求。
- 区分脱敏、假名化与匿名化，并说明为什么“可还原”决定了它不能对外共享。
- 实现“入模前脱敏 → 出模后回填 → 输出泄露检测”的管线，并指出映射表必须如何保管。
- 说明供应商侧（模型与评测服务）的留存、区域与训练使用边界要落到哪些配置和条款上。

## 前置知识

- 回看上一课：[Prompt Injection 与数据外泄](08-prompt-injection-and-data-exfiltration.md)。
- 知道 HTTP 请求、日志、缓存的基本概念，理解“数据副本”会在多处产生。

## 业务场景

售后助手处理的数据可以分成四层：

1. 客户身份数据：姓名、手机号、收货地址、身份证号（用于跨境清关或大额退款核验）。
2. 交易数据：订单号、金额、支付方式、物流单号。
3. 会话数据：客户原话、客服备注、上传的截图与邮件内容。
4. 衍生数据：模型输入输出、trace、评测集、标注结果、模型评分。

业务约束很现实：客服必须看到完整地址才能判断“是否在配送范围”；退款核验确实需要身份证后四位；模型供应商默认会为“滥用监控”保留一段时间的请求日志，需要在合同与配置层面确认；客服主管要求“任何投诉都能在 5 分钟内还原当时助手看到了什么”——这与“少留数据”直接冲突。

## 核心概念

| 等级 | 示例 | 处理要求 |
| --- | --- | --- |
| L1 公开 | 售后政策原文、公开帮助页 | 可进检索库，允许缓存 |
| L2 内部 | 客服话术模板、订单状态枚举 | 需登录访问，禁止外部分享 |
| L3 个人信息 | 姓名、手机号、地址、订单号 | 入模前脱敏；日志与评测集不得存明文 |
| L4 敏感个人信息 | 身份证号、银行卡、人脸/截图 | 默认不入模；必须入模时单独授权、单独留存、单独审计 |

- *个人信息*：可识别到具体自然人的信息。*敏感个人信息* 是其中一旦泄露易导致人格尊严或人身财产安全受损的部分（如身份证、金融账户、生物识别）。
- *脱敏*（masking）：用占位符或掩码替换原值，如 `[PHONE_1]`；目的是让使用方看不到原值。
- *假名化*（pseudonymization）：用稳定假名替换标识，**保留还原能力**，因此仍属个人信息，不能随意对外共享。
- *匿名化*（anonymization）：处理到无法识别且不能复原，才可能脱离个人信息范围；实践门槛很高。
- *令牌化*（tokenization）：把敏感值换成随机令牌，原值存在受控的令牌库。它是假名化的一种工程实现。
- *供应商边界*：模型 API、评测服务、标注平台都是独立的数据处理边界。默认认为“数据一出边界即失控”，除非配置与合同能证明不是。
- *影子 AI*：员工绕开审批，把客户对话粘进个人版 AI 工具。它是泄露事故的高频来源，且不在你的日志里。

**可还原性决定共享权限**：能还原的映射表在谁手里，谁就实质上持有原始数据。

## 工作原理

1. **盘点数据流**：画清楚数据从哪进、经过哪些组件、存到哪、谁能读。重点是三处易漏点：缓存、trace、评测快照。
2. **分级打标**：在 schema 层给字段标等级，而不是靠人记。字段一旦标为 L3/L4，后续管线自动套用规则。
3. **采集最小化**：助手不需要身份证全码，就需要后四位；不需要完整地址，就需要“是否在配送范围”的判断结果。**先问“这个字段在决策中起什么作用”**。
4. **入模前脱敏**：在拼装上下文前替换为令牌，保留业务所需的尾部信息（如“尾号 1234”）。检索文档同样要脱敏——很多事故是知识库里存了客户信息。
5. **检索与缓存隔离**：查询必须带租户与客服身份，缓存键包含租户 ID 与权限范围；权限过滤下沉到检索层，不靠提示词。可回看[权限感知检索](../04-rag-and-knowledge/08-permission-aware-retrieval.md)。
6. **出模后回填并检测**：用映射表把令牌换回原值，只发给有权看到的角色；同时扫描输出中的表外号码与证件号，命中即阻断。
7. **留存与删除**：为每类数据定义保留期与删除方式（含向量库中的副本、备份、评测集）。删除请求要能贯通到这些副本，否则“已删除”只是界面上的假象。
8. **供应商配置与合同**：确认是否用于训练、日志保留期、数据区域与子处理者；能关的关掉，关不掉的写进合同。

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 正则 + 校验位（手机号、身份证） | 结构固定的标识 | 姓名、地址、自由文本 | 快且可解释，漏报高，需持续补规则 |
| NER/分类模型识别 | 姓名、地址、混合文本 | 极低延迟、强离线场景 | 覆盖率好，但会误把“张伟路”当地名/人名 |
| 供应商内置 PII 检测 | 已用该供应商的托管 API | 需要本地处理、合规要求境内 | 省开发，但检测结果可能回传，边界更复杂 |
| 令牌化服务 + 短期缓存 | 需要还原（如短信通知） | 只需展示聚合结论 | 安全性取决于令牌库的权限与 TTL |
| 直接不入模（改走白名单字段） | 身份证、银行卡全码 | 需要模型理解原文的场景 | 最安全，但要求重构信息流 |
| 本地小模型脱敏 | 数据不能出境的场景 | 团队无 GPU、无运维能力 | 边界清晰，成本与准确率需自建评测 |

选型依据：**先削减“要不要进模型”，再选择“怎么脱敏”**。技术上最优雅的脱敏，也比不上根本不需要那个字段。

## 最小示例

问题：把一段含手机号与身份证的客服对话送进模型，答复后再回填，并检测模型是否凭空带出别人的号码。

环境：Python 3.10+，仅标准库。输入：原始对话、模型草稿。输出：脱敏文本、映射表、回填结果、泄露检查结果。

```python
import re

PHONE = re.compile(r"1[3-9]\d{9}")             # 中国大陆手机号
IDCARD = re.compile(r"\d{17}[\dXx]")           # 18 位身份证（简化，未验证校验位）


def mask(text):
    """返回 (脱敏文本, 映射表)。映射表是敏感资产，只能存在于受控进程内。"""
    mapping, counters = {}, {}

    def apply(pattern, label, s):
        def _sub(m):
            counters[label] = counters.get(label, 0) + 1
            token = f"[{label}_{counters[label]}]"   # 每类单独计数，token 语义稳定
            mapping[token] = m.group(0)
            return token
        return pattern.sub(_sub, s)

    # 先长后短：身份证里含 11 位数字串，先替换可避免被手机号规则切碎
    text = apply(IDCARD, "IDCARD", text)
    text = apply(PHONE, "PHONE", text)
    return text, mapping


def restore(text, mapping):
    """回填并报告未解析的 token：模型改写 token 时必须转人工。"""
    unresolved = set(re.findall(r"\[(?:PHONE|IDCARD)_\d+\]", text)) - set(mapping)
    for token, original in mapping.items():
        text = text.replace(token, original)
    return text, sorted(unresolved)


def leak_scan(reply, mapping):
    """只允许出现映射表内的号码；表外号码一律视为泄露。"""
    allowed = set(mapping.values())
    found = set(PHONE.findall(reply)) | set(IDCARD.findall(reply))
    return sorted(found - allowed)


dialog = "客户张伟，手机 13800001234，身份证 11010119900307123X，订单 SO-2026-0917 要退。"
masked, mapping = mask(dialog)
print("送模型的文本：", masked)
print("映射表键：", sorted(mapping))

draft = "已收到 SO-2026-0917 的退货申请，将短信通知 [PHONE_1]。"
final, unresolved = restore(draft, mapping)
print("回填后答复：", final)
print("未解析 token：", unresolved, "| 泄露检查：", leak_scan(final, mapping))

bad = "已通知 13900002222 与 13800001234 确认收货。"
print("异常答复泄露：", leak_scan(bad, mapping))
```

预期输出：

```text
送模型的文本： 客户张伟，手机 [PHONE_1]，身份证 [IDCARD_1]，订单 SO-2026-0917 要退。
映射表键： ['[IDCARD_1]', '[PHONE_1]']
回填后答复： 已收到 SO-2026-0917 的退货申请，将短信通知 13800001234。
未解析 token： [] | 泄露检查： []
异常答复泄露： ['13900002222']
```

设计要点：先长后短避免规则互相切碎；每类独立计数让 token 语义稳定；`unresolved` 捕捉模型改写 token 的情况；`leak_scan` 用“白名单集合”而不是“黑名单正则”，才能发现模型编造出的**别人**的号码。

## 动手实验

### 任务：验证脱敏管线与日志泄露

前置条件：Python 3.10+；把上例保存为 `pii.py`。

1. 运行 `python3 pii.py`，确认输出与上节一致。
2. 交换两条替换顺序（先 `PHONE` 再 `IDCARD`）重跑，记录 `送模型的文本` 变成了什么。预期：身份证被截成 `110101[PHONE_x]X`，业务上已不可用。
3. 恢复正确顺序，然后在 `mask` 之后打印 `len(mapping)`，并把 `mapping` 写成 `mapping.json`（模拟“为了排障把映射表落了盘”），检查文件内容。预期：文件里是明文手机号与身份证。
4. 用一个畸形 token 测试回填：把草稿改成 `[PHONE_9]`，重跑，确认 `未解析 token` 输出 `['[PHONE_9]']`。
5. 用 `grep -c "13800001234" mapping.json` 验证第 3 步的泄露，然后**删除该文件**。

验证方法：第 2 步必须出现被切碎的身份证；第 3 步必须能搜到明文；第 4 步必须报告未解析 token。
清理方法：`rm pii.py mapping.json`；实验中使用的号码与证件号均为示例值，未调用任何外部 API。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 身份证被识别成手机号 | 正则顺序错误，短规则先命中 | 打印脱敏后文本逐段对照 | 先长后短，并在替换后校验残留格式 |
| 日志里能搜到客户手机号 | debug 日志打印原始 prompt / trace 存全文 | 在日志平台按正则抽样搜索 | 日志在写入前脱敏，禁止打印原始上下文 |
| 模型答复的号码与客户不符 | 缓存跨租户命中或检索未做权限过滤 | 检查缓存键与检索查询条件 | 缓存键带租户与权限；检索层强制过滤 |
| 回填后出现 `[PHONE_1]` 字面量 | 模型改写或翻译了 token | 统计未解析 token 数量 | 严格匹配 + 未解析即转人工；token 设计更醒目 |
| “已删除”但向量库仍能召回 | 只删了业务库，忘了索引、备份、评测集 | 按客户 ID 全链路检索 | 建立删除清单：业务库/向量库/缓存/备份/评测集 |
| 外包标注数据泄露 | 直接把生产对话导出给标注团队 | 查标注数据的来源与脱敏状态 | 标注集预先脱敏，签署协议，最小字段 |
| 供应商侧数据被用于训练 | 未核对合同与配置，默认开通 | 查控制台配置与合同条款 | 关闭训练用途，确认区域与保留期，留证 |

## 安全与生产注意事项

**<u>脱敏后的映射表本身就是最高等级的敏感资产；把它写进日志、缓存或工单备注，等于没有脱敏。</u>** 映射表应只存在于受控进程内存或具备严格权限与短 TTL 的令牌服务中，并纳入访问审计。

**<u>日志、trace 与评测集是 AI 应用最大的泄露面，而它们通常不受业务库的权限与删除流程管辖。</u>** 上线前就要定义这三处的字段白名单与保留期；否则“删除用户数据”永远删不干净。

另外两条：**<u>不要把匿名化当成“改个名字”</u>**——能用时间、订单、地址重新识别仍是个人信息；**<u>合规可能要求最短留存</u>**，例如《标识办法》要求特定情形留存日志不少于六个月（2025-09-01 施行），不能一律“越短越好”。

## 本课总结

- **隐私事故多来自数据副本扩散**：上下文、日志、trace、评测集、供应商侧，每一处都要单独治理。
- 先决定“字段要不要进模型”，再决定“怎么脱敏”；削减字段永远优于加密字段。
- 脱敏、假名化、匿名化的分界线是**能否还原**，可还原就意味着仍受个人信息规则约束。
- 映射表是敏感资产；回填与泄露检测必须成对出现，否则脱敏只是把风险挪了个位置。
- 删除请求要按清单贯通到索引、缓存、备份与评测集，否则“已删除”不可信。

## 思考题

客服主管要求“5 分钟内还原助手当时看到的内容”，安全团队要求“日志不留明文手机号”。这两个要求能同时满足吗？请给出设计。

参考思路：可以。把“还原能力”与“明文留存”解耦：日志只存脱敏文本 + 映射表 ID + 时间戳，映射表存于受控的令牌服务（短 TTL、按工单号索引、访问留审计）。投诉时用映射表 ID 在授权下临时还原，并对这次还原本身记一条审计事件。代价是：超过 TTL 的历史投诉无法还原，需要业务确认可接受窗口（例如 7 天），并把更长周期的证据需求转成“摘要留存”。若业务坚持 90 天可还原，就必须接受映射表长期存在，此时应提高其加密与访问控制等级，而不是退回明文日志。

## 小测

1. 下列哪项最接近匿名化？  
   A. 把手机号换成 `[PHONE_1]` 并保留映射表　B. 把用户 ID 换成随机哈希但保留订单关联　C. 聚合到“某城市某月退款率”且无法回溯个体　D. 把姓名替换成“张先生”
2. 为什么“入模前脱敏”还要覆盖检索到的文档？
3. 泄露检测为什么用“映射表白名单”而不是“匹配敏感词”？
4. 删除请求需要贯通哪些副本？
5. 场景题：产品希望把近 30 天会话导出给外部标注团队做质量评估。请列出你的批准条件与替代方案。

## 答案与解析

1. **C。**聚合且不可回溯才可能脱离个人信息范围。A 是令牌化（可还原）；B 是假名化/哈希，仍可通过订单关联重识别；D 只是把姓名泛化，地址与订单仍可定位到人。
2. 因为知识库常由工单、评价、邮件同步而来，本身就含客户信息；只脱敏当前提问，等于把泄露点留在检索结果里。而且检索到的内容会进入上下文与日志，成为新的副本。
3. 因为模型可能编造或从缓存带出**别的**客户的号码，黑名单只能拦住已知值。白名单要求“输出中的号码必须来自本次映射表”，才能发现来源不明的数据。
4. 业务库、检索索引/向量库、缓存（含会话与语义缓存）、备份、日志与 trace、评测集与标注集、下游数据仓库与报表。漏掉任一处都会导致“界面已删、实际仍在”。
5. 批准条件：数据集预先脱敏（去掉姓名、电话、地址、身份证，仅留订单号哈希）、签署保密与不二次传播协议、限定字段与用途、限定访问人员与期限、导出留审计、结束后销毁并留证。替代方案：在境内受控环境内做标注、用合成或历史已脱敏数据、或让外部团队只做“评分不看原文”的盲评。
