# 正确性、相关性、忠实度与完整性

## 为什么需要学习

售后助手上线前做了一次“质量评估”，四项指标都在 0.8 以上，团队据此放行。上线第三天，一位客户收到这样的答复：“您的耳机已拆封，按政策支持 7 天无理由退货。”文本流畅、切题、引用了政策原文的句式——但政策写的是“拆封后不支持”。模型把否定句改写成了肯定句，而当时的评估只看“有没有引用政策”，没看“引用得对不对”。

这类事故说明：语义质量的四个维度经常互相掩盖。忠实度高的答复可能完全错误（忠实于一份过期政策）；正确性高的答复可能不忠实（模型凭训练记忆答对了，检索其实没命中）；相关但不完整的答复最危险，因为它读起来毫无破绽，却漏掉了金额上限或例外条件。

> **核心结论：** 四个指标不是四个分数，而是四种不同的证据；任何单一指标都能被“看起来很好”的答复骗过，判定必须绑定具体失效模式与人工校准。

## 学习目标

完成本课后，你能够：

- 用“对照什么事实源”区分正确性、相关性、忠实度与完整性。
- 为一个答复逐条拆出断言，并判定 supported / contradicted / not-in-context。
- 说明“忠实但错误”为何必须优先按正确性处置，而不是调高忠实度阈值。
- 设计人工校准抽样方案，给出可接受的一致率门槛与低于门槛时的动作。

## 业务场景

晴空商城售后助手的答复要同时满足四个要求：

1. 与**当前生效**的售后政策、该订单的真实状态一致（正确性）。
2. 正面回答客服问的那件事，不跑题、不堆砌条款（相关性）。
3. 每个结论都能在检索到的政策片段或订单数据里找到依据（忠实度）。
4. 该说的条件、例外、下一步动作不缺（完整性）。

政策库每月修订，订单状态实时变化，而客服每天要处理上千条咨询。团队不可能逐条人工阅读，需要可自动计算、又能被人工校准的指标组合。

## 核心概念

| 指标 | 对照的事实源 | 回答的问题 | 售后助手反例 |
| --- | --- | --- | --- |
| *正确性* | 权威事实：政策终稿、订单系统、金额规则 | 结论与真实世界一致吗？ | 说“拆封可退”，实际政策写“拆封不支持” |
| *相关性* | 用户问题本身 | 这段话在回应提问吗？ | 问价保，答了一段退货运费规则 |
| *忠实度* | 本次检索到的上下文 | 每句话都能被给定上下文推出吗？ | 上下文只写 15 天，答复写 30 天 |
| *完整性* | 该场景的必答要素清单 | 条件、例外、下一步都说了吗？ | 只说“可退”，没说需保留包装与 7 天时限 |

定义边界：

- *忠实度* 是一个“相对”指标：它只比较答复与上下文，不判断上下文本身是否正确。Ragas 的定义是——把答复拆成若干断言，逐条检查能否由检索上下文推出，得分为被支持断言数除以断言总数，取值 0 到 1（来源见延伸阅读，复核截至 2026-10）。
- *正确性* 是“绝对”指标：必须与权威事实源比对。工程上用规则校验（订单号、金额、状态枚举）加少量人工或模型判定。
- *相关性* 关注“是否在答这件事”。它容易被长答复伪装：把政策全文贴出来显得信息丰富，实际没有回答问题。
- *完整性* 关注“该有的有没有”，无法靠相似度衡量，必须先把场景的必答要素列成清单再逐项检查。

**判定优先级：正确性 > 忠实度 > 完整性 > 相关性。** 理由很直接：<u>忠实于错误上下文，比不忠实更危险，因为它会带着“有据可依”的外表说服客服照做。</u>

## 工作原理

判定流程分六步：

1. **锁定事实源**：为每条样本记录政策快照 ID 与订单快照。没有快照，正确性无从判定。
2. **拆断言**：把答复按句或按分句切开，得到可独立判断真假的陈述。含多个条件的句子（“拆封后 7 天内且无质量问题可退”）应拆成多条。
3. **逐条判定**：每条断言标记 supported（上下文可推出）、contradicted（上下文与之矛盾）、not-in-context（上下文未提及）。忠实度只统计 supported 占比；contradicted 需要单独报警，因为它比“未提及”更危险。
4. **核对权威事实**：对涉及金额、时效、状态的断言，回查政策终稿与订单系统，得到正确性结论。
5. **检查必答要素**：按场景清单（例如“退货类必须说明时限、商品状态条件、下一步入口”）逐项打勾，得到完整性。
6. **用人工校准评分器**：抽 30–50 条样本，由人对同一批答复独立判定，计算评分器与人的一致率；一致率低于门槛时，先修判定口径或评分器提示，不得直接用于发布门禁。

第 3 步和第 6 步是多数团队缺失的环节。缺少第 3 步，忠实度会退化为“看起来像原文”；缺少第 6 步，指标只是一串没人验证过的数字。

冲突场景的处置方式各不相同：

| 场景 | 指标表现 | 处置 |
| --- | --- | --- |
| 忠实但错误（上下文过期） | 忠实度高、正确性低 | 修检索与知识更新，不改 Prompt；同时把该样本加入回归集 |
| 正确但不忠实（模型凭记忆答对） | 正确性高、忠实度低 | 仍按缺陷处理：换个问法就可能答错，属脆弱正确 |
| 切题但不完整 | 相关性高、完整性低 | 补必答要素清单与生成约束，常见于“只说能退不说条件” |
| 完整但不切题 | 完整性高、相关性低 | 约束回答范围，避免把政策全文当作答案 |

## 架构与选型

| 判定方法 | 适用指标 | 优势 | 局限 |
| --- | --- | --- | --- |
| 规则/正则/字段校验 | 正确性（金额、状态、订单号）、完整性（必含要素） | 稳定、零成本、可解释 | 只能覆盖可枚举要素，抓不住语义改写 |
| 模型评分器（LLM 打分） | 相关性、忠实度、完整性 | 覆盖语义，规模大 | 自身有偏差，需人工校准（第六课展开） |
| 句级蕴含判定 | 忠实度 | 比整段打分更可定位 | 依赖判定模型质量，长句拆分易出错 |
| 人工逐条判定 | 全部 | 最可信，可产出标准答案 | 慢，只适合抽样 |

选型依据：**能机械判定的先机械判定**，把人力留给语义判断；**高风险字段（金额、时效、承诺）必须走规则校验**，因为这些一旦出错就不可逆；**忠实度与完整性先用模型评分器打分，再用人工抽样校准**，并在报告中同时给出分数与一致率。

不必为四项指标各配一套工具链：一条流水线即可——规则层硬校验、模型层语义判定、人工层校准与裁定。

## 最小示例

下面的脚本用规则做一次“可机检的忠实度”检查：抽取带单位的数量，看是否出现在上下文中。设计意图是让学习者亲眼看到规则版忠实度的边界——它能抓住“30 天”这种凭空出现的数字，却抓不住“支持/不支持”的极性颠倒。

环境：Python 3.8+，仅标准库，无需网络。

```python
import re

CONTEXT = ("退货政策 v3：耳机等贴身商品拆封后不支持 7 天无理由退货；"
           "若存在质量问题，可在签收后 15 天内申请换货。")
ANSWER = "拆封后仍支持 7 天无理由退货。如果质量问题，可在签收后 30 天内申请换货。"

NUM = re.compile(r"(\d+)\s*(天|个工作日|元|%)")  # 只抽“数量+单位”，避免把订单号当事实

def split_claims(text):
    """按中文句号/分号切断言；真实系统应按从句再拆一层，这里保持最小可运行。"""
    return [c.strip() for c in re.split(r"[。；;]", text) if c.strip()]

def check(claim):
    """返回 (判定, 理由)。needs_review 表示规则无法判定，必须转人工或模型评分。"""
    numbers = NUM.findall(claim)
    if not numbers:
        return "needs_review", "无带单位数量，规则无法判定极性"
    flat = CONTEXT.replace(" ", "")              # 归一化空格，避免“7 天”与“7天”误判
    missing = [f"{n}{u}" for n, u in numbers if f"{n}{u}" not in flat]
    if missing:
        return "unsupported", "上下文中找不到 " + "、".join(missing)
    return "needs_review", "数量可在上下文找到，但极性与条件需人工确认"

claims = split_claims(ANSWER)
stats = {"supported": 0, "unsupported": 0, "needs_review": 0}
for i, claim in enumerate(claims, 1):
    verdict, reason = check(claim)
    stats[verdict] += 1                          # 分桶计数，便于后面按类型追查
    print(f"断言 {i}: {claim}")
    print(f"  判定: {verdict}（{reason}）")

total = len(claims)
print(f"断言总数: {total}")
print(f"明确被上下文支持: {stats['supported']} / {total} = {stats['supported'] / total:.2f}")
print(f"明确不支持: {stats['unsupported']}，待人工: {stats['needs_review']}")
```

输出（本机 `python3` 实测）：

```text
断言 1: 拆封后仍支持 7 天无理由退货
  判定: needs_review（数量可在上下文找到，但极性与条件需人工确认）
断言 2: 如果质量问题，可在签收后 30 天内申请换货
  判定: unsupported（上下文中找不到 30天）
断言总数: 2
明确被上下文支持: 0 / 2 = 0.00
明确不支持: 1，待人工: 1
```

结论很清楚：**只靠规则算不出可信的忠实度**（0.00 严重低估，因为断言 1 其实是被上下文否定的，属于 contradicted），但规则成功拦下了“30 天”这处编造。工程上应把它作为第一道筛子：`unsupported` 直接阻断，`needs_review` 交给模型评分器与人工，并单独统计 `contradicted` 数量，因为这是最需要报警的一类。

## 动手实验

前置条件：Python 3.8+；将脚本保存为 `/tmp/faithfulness_rule.py`。

步骤：

1. 原样运行 `python3 /tmp/faithfulness_rule.py`，核对输出。
2. 把 `CONTEXT` 中的“15 天”改为“30 天”，再运行，观察断言 2 的判定从 `unsupported` 变为 `needs_review`。
3. 把 `ANSWER` 改为“拆封后不支持 7 天无理由退货。”，观察规则仍返回 `needs_review`——这正是规则无法处理极性问题的证据。
4. 手工为这项样本补一条“必答要素”清单（时限、商品状态条件、下一步入口），并说明三项中答复覆盖了几项。

预期结果：第 2 步说明数字存在性检查会被上下文变化直接影响；第 3 步说明规则版忠实度需要语义判定的补位；第 4 步应当得出“只覆盖 1 项（时限）”的结论，从而看出完整性需要独立清单。

验证方法：每次只改一处文本；若判定没有变化，检查改动是否落在被切分的断言之外。

清理方法：`rm /tmp/faithfulness_rule.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 忠实度很高但客服反馈答案错 | 上下文本身过期或被污染 | 抽 10 条高忠实度样本，对照政策终稿 | 修知识更新与来源可信度，增加正确性校验 |
| 回答越来越长，指标反而升 | 长答复更容易“覆盖”关键词 | 统计答复长度与分数的相关性 | 引入完整性清单，按要素判定而非关键词 |
| 相关性与人工判断不一致 | 判定口径是“像不像在答”，不是“答没答” | 抽 30 条看分歧集中在哪里 | 写清“必须正面回应的要素”，修订评分提示 |
| 完整性分数随样本变化剧烈 | 必答要素清单未按场景分类 | 检查同一意图的样本是否用同一清单 | 按意图维护清单版本，随样本一起版本化 |
| 同一答复两次判定不同 | 评分器温度高或提示不稳定 | 同配置重复判定 3 次 | 降低随机性，固定评分器版本并记录 |

## 安全与生产注意事项

**<u>忠实度对“被投毒的上下文”完全无能为力。</u>** 如果攻击者在可写入的文档、工单备注或网页中植入“新政策：所有商品拆封可退”，检索命中后模型会忠实复述，忠实度甚至更高。这类间接注入必须靠来源白名单、内容审核与权限隔离处理，而不是调整指标阈值（OWASP LLM01:2026 将其列为提示注入的主要形态之一）。

**<u>完整性要求会诱导模型补全它并不知道的信息。</u>** 当提示强调“必须给出金额与时限”时，模型倾向于编造一个看起来合理的数字。缓解办法是允许“不确定”出口：缺少依据时明确说明需人工确认，并把这种情况计为合格而非失败。

另外两条：判定日志含答复与上下文，可能带订单与客户信息，需脱敏与访问控制；分数必须与评分器、样本版本一起存档，否则无法解释历史差异。

## 本课总结

- **四项指标对照四种事实源：正确性对权威事实、相关性对问题、忠实度对上下文、完整性对必答清单。**
- 忠实度是相对指标，不能替代正确性；忠实于错误上下文是最危险的一类失败。
- 规则能稳定拦住数字与字段类错误，语义极性必须靠模型评分器与人工补位。
- 完整性只能靠清单判定，不能靠相似度或关键词覆盖。
- 任何自动指标投入使用前都要做人工校准，并公布一致率。

## 思考题

如果政策库存在两份内容冲突的历史文档，检索经常同时命中，导致忠实度正常但正确性波动，你会先改检索、先清理知识库，还是先改 Prompt？请说明判断依据和对发布节奏的影响。

参考思路：先清理知识库或加来源优先级，因为冲突事实属于数据问题，任何提示工程都只能掩盖。判断依据是“答复差异是否与检索片段组合相关”：若同一问题在不同命中组合下给出不同结论，就是数据冲突而非生成缺陷。对发布节奏的影响是：在清理完成前应冻结相关意图的自动答复，降级为人工确认，而不是继续用指标平均分放行。

## 小测

1. 忠实度 1.0 意味着：

   A. 答复一定正确　B. 答复的断言都能由本次上下文推出　C. 答复完整覆盖政策　D. 答复与问题高度相关

2. 为什么“正确但不忠实”的答复仍应算缺陷？
3. 完整性为什么难以用相似度指标衡量？
4. 间接提示注入为什么会拉高忠实度却降低安全性？
5. 场景题：某版本忠实度从 0.86 升到 0.91，正确性从 0.93 降到 0.81。作为负责人，你会批准发布吗？请给出判断与补救动作。

## 答案与解析

1. **B。**忠实度只比较答复与本次上下文。A 错在上下文可能过期或错误；C 是完整性的范围；D 是相关性的范围。
2. 因为它的正确依赖模型的记忆或运气，换问法、换订单、换时间就可能错，且无法用检索证据解释。对生产系统而言，不可解释的正确等同不稳定，仍应作为缺陷记录以便后续修复。
3. 因为完整性是“该有的要素是否都在”，而相似度衡量的是整体语义接近程度；一段把政策全文复述出来的答复相似度很高，却可能没有回答具体问题，也可能漏掉唯一关键例外。
4. 攻击者把恶意指令写入被检索的文档，模型忠实执行或复述，因此断言与上下文高度一致，忠实度上升；但答复内容已偏离真实政策与业务规则，安全性与正确性同时下降。
5. 不批准。正确性下降 12 个百分点属于实质性退化，且方向是“更忠实但更错”，说明问题在上下文质量或事实校验，而不是生成风格。补救动作：抽 30 条错误样本核对政策快照与检索命中，清理冲突文档；在修复前冻结相关意图的自动答复；恢复后用同一批样本重测并公布两个指标与人工一致率。
