# 用户任务、业务流程与人工介入点

## 为什么需要学习

晴空商城的政策助手在试点第三天出了一次事故：模型把「拆封耳机扣 15% 折旧」写成「可全额退款」，客服看到措辞通顺、语气专业，直接复制发给了客户。三天后财务对账，才发现同批次有 17 单被超额退款。复盘时没人指责模型——问题在于流程里根本没有「谁按最后一个按钮」这一环。

> **核心结论：** 人工介入不是给 AI 打的补丁，而是流程设计的一部分；介入点的位置决定了错误的代价。

## 学习目标

完成本课后，你能够：

- 解释 *用户任务*、*任务分解*、*确认点*、*接管* 与 *升级路径* 的含义。
- 按自动化等级为每个子任务选择「建议 / 草稿 / 执行」三种介入方式。
- 写出带触发条件、责任人和时限的接管与升级规则。

- 回看上一课：[规则系统、搜索、传统机器学习与 LLM 的选择](02-rules-search-ml-or-llm.md)。
- 了解客服工单的基本流转：受理、处理、回复、归档。
- 知道不可逆操作（退款、改地址）与可逆操作（生成草稿）的区别。

## 业务场景

晴空商城的售后流程目前是：客户在商城 App 提问 → 进入客服工单池 → 客服查订单、查政策 → 回复或发起退款 → 归档。

引入助手后，可能的分工是：系统检索政策与订单并生成答复草稿，客服确认发送；高额退款由系统给出建议，客服提交、主管审批。问题在于——哪些环节可以让系统直接做，哪些必须停一下？

## 核心概念

*用户任务* 指用户为达成目标而做的一件事，例如「弄清我的耳机能不能退」。*任务分解* 是把这件事拆成可分别承担的子步骤：识别意图、取订单、取政策、判断资格、组织措辞、发送、必要时补偿。

| 自动化等级 | 谁按最后一个按钮 | 适用条件 | 失败的后果 |
| --- | --- | --- | --- |
| 建议（assist） | 人，且人须自行判断 | 判断依据复杂、责任重大 | 人可能忽略建议，但责任清晰 |
| 草稿（draft） | 人确认后发送 | 表达需要生成、口径需要统一 | 人可能盲目复制，需抽检 |
| 执行（act） | 系统 | 可逆、低额、有强校验与回滚 | 可能批量出错，需限流与熔断 |

*确认点* 是流程中必须先获得明确同意才能继续的节点；*接管* 是人工中途接手并继续完成剩余步骤；*升级路径* 规定接管者解决不了时交给谁、多久内交接。

<u>「有个人在流程里」不等于人在回路。</u> 如果确认界面只给一个「同意」按钮、不给依据、不给修改入口，人只是装饰。微软人机交互准则中 G1（说清系统能做什么）、G2（说清做得有多好）、G9（支持高效纠正）、G10（不确定时收窄范围）、G16（说明操作后果）与 G17（提供全局控制）正是针对这种「名义上有人、实际上无人」的设计（复核日期 2026-10-19）。

**介入点的价值来自「能改」和「能拒」，而不是「被通知」。**

## 工作原理

设计流程时按顺序完成七步：

1. **列出用户任务链。** 从客户提问到工单归档，逐条写成动词短语，不写系统名。
2. **标注动作性质。** 读（查订单）、写（发消息）、不可逆写（退款）、承诺（赔付口径），四类风险不同。
3. **确定自动化等级。** 读操作可自动；对外发送默认草稿；不可逆写必须人工确认；承诺类只给建议。
4. **设计确认点。** 每个确认点要呈现三样东西：系统建议、依据（条款编号/订单事实）、可修改入口。缺一项就是形式确认。
5. **定义接管触发。** 常见触发包括置信度低于阈值、缺少引用、命中风险词、金额超限、用户明确要求转人工、连续两轮未解决。
6. **定义升级路径。** 一线客服 → 售后主管 → 财务/法务，每一级写清时限与交接内容（会话摘要、已核实事实、建议动作）。
7. **定义度量与演练。** 接管率、草稿改写率、确认耗时、升级超时率；每季度做一次「模型给错答案」的桌面演练，确认通道真的通。

第 5 步常被写成「模型不确定时转人工」，但「不确定」不可测量。必须落成具体信号：有没有引用、置信分是多少、是否命中金额阈值。NIST AI RMF 附录 C 指出，人类在 AI 团队中的角色可以从完全自主到完全手动，组织必须明确区分并记录这些角色，同时收集「人推翻 AI 输出的频率与理由」作为评估依据（复核日期 2026-10-19）。

## 架构与选型

| 流程环节 | 推荐介入方式 | 理由 | 不应采用的方案 |
| --- | --- | --- | --- |
| 识别意图与分类 | 自动 | 错了可当场纠正，成本低 | 每条都人工分派 |
| 取订单与物流 | 自动 | 事实查询，无需生成 | 让模型复述订单号 |
| 政策资格判断 | 规则判定 + 自动解释 | 必须可复现、可审计 | 纯模型判断 |
| 生成答复文本 | 草稿 + 人工发送 | 对外口径需要统一 | 直接自动发送 |
| 小额退款（如 < 100 元） | 草稿 + 客服确认 | 有金额上限与抽检 | 无人确认自动打款 |
| 高额退款或补偿 | 建议 + 双重审批 | 不可逆、影响面大 | 单人在聊天窗口口头同意 |
| 投诉与情绪升级 | 直接接管 | 需要人情判断与授权 | 由模型继续对话 |

选择介入方式的核心依据是「错误是否可逆」与「错误的影响面」。可逆且影响单人时，自动化能显著提效；不可逆或影响面大时，宁可牺牲速度也要保留确认。若确认耗时超过人工处理时间，说明确认点设计有问题，应改为抽检而非逐条确认。

## 最小示例

用一段脚本把「风险分级决定谁按最后按钮」写成可测试的规则。

```python
# 风险分级决定「谁按最后一个按钮」
HIGH_RISK = {"create_refund", "change_address", "cancel_order", "issue_coupon"}

def decide(action, amount, confidence, policy_cited):
    if action in HIGH_RISK and amount > 500:
        return "human_approve"      # 高金额写操作，必须人工确认
    if confidence < 0.7 or not policy_cited:
        return "handoff"            # 信心不足或缺依据，转人工处理
    return "draft_with_notice"      # 只给草稿，客服点发送

cases = [
    ("create_refund", 1280, 0.92, True),
    ("create_refund", 128, 0.88, True),
    ("answer_policy", 0, 0.55, True),
    ("answer_policy", 0, 0.91, False),
]
for c in cases:
    print(f"{c[0]:15s} 金额={c[1]:>5} 置信={c[2]:.2f} 引用={c[3]!s:5s} -> {decide(*c)}")
```

运行 `python3 hitl.py`：

```text
create_refund   金额= 1280 置信=0.92 引用=True  -> human_approve
create_refund   金额=  128 置信=0.88 引用=True  -> draft_with_notice
answer_policy   金额=    0 置信=0.55 引用=True  -> handoff
answer_policy   金额=    0 置信=0.91 引用=False -> handoff
```

设计意图：判断顺序先看「动作 + 金额」再看「置信度」，因为高额写操作即使置信度再高也不能自动执行；「无引用」直接转人工，避免模型用通顺语言掩盖依据缺失。注意阈值 500 与 0.7 都是业务参数，必须由业务方确认，而不是工程师拍定。

## 动手实验

### 前置条件

- 能运行 `python3`。
- 一张白纸或表格工具，用于画任务链。

### 步骤

1. 写下从「客户提问」到「工单归档」的 8–12 个步骤。
2. 为每步标注动作性质：读、写、不可逆写、承诺。
3. 为每步填一个自动化等级，并写一句「为什么不能更高」。
4. 为每个「草稿」与「执行」环节补上接管触发条件与责任人。
5. 用脚本验证：任取 3 种输入，输出是否符合你预期的介入方式。

### 预期结果

得到一张覆盖完整流程的表，其中至少有一个环节被刻意降级（例如高额退款从「执行」降为「建议」），并写明降级理由。

### 验证方法

- 请一位客服同事走查：确认点是否给出了依据、是否能在 10 秒内改完并发送。
- 检查每个接管触发是否可被日志计算出来；不能计算的触发等于没有。

### 清理方法

删除临时脚本；把任务链表归档到需求文档，作为验收标准的输入。表格中不得写入真实客户姓名与手机号。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 确认按钮点得飞快，从不看内容 | 确认点只给结论不给依据 | 统计确认平均耗时与改写率 | 展示条款编号与订单事实，强制可编辑 |
| 接管后客服重新问一遍客户 | 交接时丢失上下文 | 抽查接管工单的前三条消息 | 接管时附带会话摘要与已核实事实 |
| 升级后无人响应 | 升级路径没有责任人和时限 | 统计升级超时率 | 写明 SLA 与兜底值班人 |
| 人工复核成本高于收益 | 逐条确认而非抽检 | 计算确认耗时 × 单量 | 低风险改为抽检，高风险保留确认 |
| 只测了正常路径 | 未设计异常分支 | 检查是否有「无引用」「检索为空」「接口超时」分支 | 为每个失败分支定义界面与动作 |

## 安全与生产注意事项

**<u>警惕自动化偏见：人看到通顺的 AI 文本会倾向于直接采纳。</u>** 当确认点的默认选项是「同意」、依据又需要额外点击才能看到时，人工审核会退化为盖章。缓解办法包括：默认不通过、把关键差异高亮、定期抽检已发送草稿、统计改写率作为质量指标。

**<u>接管通道不能依赖同一条模型链路。</u>** 如果转人工按钮背后的会话摘要也由模型生成，模型服务故障时人工既接不到上下文也接不到单。应保证接管入口、工单系统和订单查询在模型不可用时仍能正常工作，并提供「仅看原始消息」的降级视图。

此外，升级路径要能在非工作时间生效，并明确谁有权批准超限金额。把审批权限写在个人聊天窗口里，事后无法审计。

## 本课总结

- **人工介入的位置比介入的有无更重要。** 事后抽检与事前确认解决的是不同风险。
- **确认点必须同时给出建议、依据和修改入口**，否则只是形式审核。
- **自动化等级应按动作的可逆性与影响面选择**，而不是按模型准确率选择。
- **接管触发条件必须可被日志计算**，抽象表述等于没有触发。
- 度量接管率与改写率，才能知道人在回路里是否真的起了作用。

## 思考题

如果客服团队只有 3 人，日均 800 个会话，而每个草稿确认平均需要 40 秒，这套「草稿 + 人工确认」的流程还成立吗？你会如何重新设计介入点？

参考思路：40 秒 × 800 = 8.9 小时/天，接近 3 人的全部工时，说明逐条确认不可行。可改为：按风险分层，只有高金额与高情绪会话强制确认，其余抽检 10%；把确认界面压缩到「看依据 + 一键发送」；或者把介入点前移到「规则判定」由系统直接处理确定性高的子集。

## 小测

1. 「草稿 + 人工确认」属于哪种自动化等级？  
   A. 建议　B. 草稿　C. 执行　D. 全自动
2. 一个合格的确认点必须提供哪三样东西？
3. 为什么「模型不确定时转人工」不能直接作为接管条件？
4. 接管时如果丢失上下文，会造成什么后果？
5. 场景题：晴空商城希望「客户一提出退款就自动退款，事后抽检」。请指出这个设计的问题，并说明你会把介入点放在哪里。

## 答案与解析

1. **B。** 由人确认后发送，属于草稿等级。A 建议不代写文本；C、D 由系统直接执行，风险更高。
2. 系统建议、判断依据（条款编号或订单事实）、可修改入口。三者缺一，人只能选择「同意」或「放弃」，无法真正纠正。
3. 因为「不确定」没有可测量的定义，无法写进系统逻辑，也无法事后统计。必须落成信号：有无引用、置信分阈值、命中风险词、金额超限。
4. 客服需要重新向客户确认已说过的事实，体验下降；更严重的是可能基于不完整信息做出与系统建议相反的决定，产生新的错误。
5. 问题：退款不可逆且可能被诱导，事后抽检无法挽回已造成的损失；自动退款还绕过了资格与金额校验。介入点应放在「生成退款建议 + 规则校验」之后、「调用退款接口」之前，由客服确认；并对金额设上限与审批。

### 动手实验参考

合格答案的三个特征：每个环节都有明确的动作性质；至少一个环节被降级并说明理由；每个触发条件都能从日志中计算。只画流程图而不标注等级与触发条件，不算完成。
