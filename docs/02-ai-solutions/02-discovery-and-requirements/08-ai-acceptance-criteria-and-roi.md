# AI 验收标准、ROI 与优先级

## 为什么需要学习

售后助手试点结束，评审会上出现三种说法：产品说「效果不错，可以推广」，财务说「一年要花 60 万」，客服主管说「比以前快一点，但改写太费时间」。没有人能回答最关键的问题：达到什么程度算验收通过？投入产出是否值得？还有两个候选项目在排队，凭什么是它先做？

> **核心结论：** 验收标准要能在开始前写死、在结束时被第三方复现；ROI 要能被敏感性分析推翻；优先级要同时看价值与就绪度。

## 学习目标

完成本课后，你能够：

- 把「效果不错」改写成含场景、阈值、样本量与验证方式的验收标准。
- 计算年化收益、年化成本、净收益与静态回本期，并做一次敏感性分析。
- 用统一维度对多个候选需求排序，并说明排序结论的适用条件。

## 前置知识

- 回看上一课：[准确性、延迟、成本与业务指标](07-accuracy-latency-cost-and-metrics.md)。
- 了解工单量、平均处理时长、人力成本等基础业务口径。
- 知道「回本期」指累计净收益抵平初始投入所需时间。
- 能运行 `python3`，示例只用标准库。

## 业务场景

售后助手已完成试点：一次解决率、改写率、p95 延迟都有数据。管理层要决定是否扩大范围，并同时评估另两个候选：智能质检（抽检客服录音）与商品描述自动生成。预算只够一个方向，团队需要给出可被质询的结论。

## 核心概念

*可测验收标准* 由五部分组成：场景（什么条件）、动作（做什么）、期望结果（含阈值）、样本量（测多少）、验证方式（谁来测、怎么判）。*单位经济* 是单个业务单位的收支关系；*ROI* 是净收益与投入的比值；*静态回本期* 是不计折现的回本时间。

| 验收维度 | 标准写法示例 | 验证方法 | 常见错误 |
| --- | --- | --- | --- |
| 功能 | 给定含有效订单号的物流问题，返回状态与预计到达时间 | 50 条真实样本回放 | 只写「能回答物流问题」 |
| 质量 | 政策类回答引用有效率 ≥ 98%，无引用占比 ≤ 2% | 人工评审 100 条抽样 | 用「准确率 90%」笼统表述 |
| 安全 | 1000 次越权请求中，泄露他人订单的比例为 0 | 红队测试 | 只在正常输入上验证 |
| 运营 | p95 端到端延迟 ≤ 3 秒，错误率 ≤ 1% | 生产埋点统计 7 天 | 用平均值代替分位数 |
| 业务 | 试点组一次解决率较对照组提升 ≥ 5 个百分点 | 同期对照组比较 | 只看绝对值不看对照 |

<u>「显著提升」不是验收标准。</u> 它没有阈值、没有样本量、没有对照，任何人解读都能通过。合格的标准应让第三方在不知道结论的情况下重跑一次并得到相同判断。

## 工作原理

从需求到决策按七步走：

1. **写验收标准。** 每个维度至少一条，全部包含场景、阈值、样本量与验证方式；同时写一条「不通过时怎么办」。
2. **确定基线与对照组。** 没有基线就没有提升。基线应来自试点前的同期数据，对照组与试点组在时段、品类、坐席经验上尽量可比。
3. **冻结评测样本。** 从真实数据分层抽样，冻结后不得因结果不理想而调整；对抗样本与信息缺失样本单列。
4. **估算收益。** 收益 = 节省工时 × 人力单价 + 增量收入 + 风险损失下降。节省工时要用实测的「每单净节省时间」，而不是理论值。
5. **估算成本。** 一次性投入（开发、接入、评测集建设、培训）+ 年化运行成本（模型调用、检索、存储、人工复核、运维）。
6. **算净收益与回本期，再做敏感性分析。** 至少变动三个假设：自动化率、每单节省时间、模型单价，观察回本期是否仍可接受。
7. **排序并记录条件。** 用价值、成本、风险、就绪度四维排序；写明「本结论在什么条件下成立」，例如单量不低于每月 1.5 万。

第 2 步和第 6 步决定结论的可信度。没有对照组，指标改善可能来自季节性或流程调整；没有敏感性分析，一个乐观假设就能让任何项目「回本」。

## 架构与选型

| 情形 | 验收策略 | ROI 口径 | 适用前提 |
| --- | --- | --- | --- |
| 降本型（客服提效） | 对照组的每单处理时长 | 节省工时 × 人力成本 | 有可比对照组 |
| 增量收入型（转化提升） | A/B 实验的转化差异 | 增量毛利 − 增量成本 | 流量足够做随机分流 |
| 风险规避型（合规审查） | 漏检率与误报率 | 以风险敞口下降估算，须注明假设 | 有历史损失数据 |
| 体验型（响应速度） | p95 与满意度 | 难货币化，用护栏指标 | 与主指标同时评估 |
| 平台/基础设施型 | 复用项目数与接入成本 | 分摊到受益项目 | 至少 2 个明确受益方 |

选择哪种口径取决于价值来源。降本型最容易算但容易高估（忽略改写与复核）；风险规避型的数字最不可靠，应写成区间并说明假设来源。<u>把所有项目都换算成一个 ROI 数字再排序，会系统性偏袒容易量化的项目。</u>

## 最小示例

下面的脚本计算年化收益、单位成本、净收益与静态回本期，并给出是否满足门槛的结论。

```python
def evaluate(monthly_tickets, auto_rate, minutes_saved, hourly_cost,
             llm_cost, review_rate, review_minutes, build_cost, monthly_run):
    auto_tickets = monthly_tickets * 12 * auto_rate          # 一年被 AI 处理的会话数
    saved_hours = auto_tickets * minutes_saved / 60
    gross = saved_hours * hourly_cost                         # 节省工时的货币价值
    unit_cost = llm_cost + review_rate * review_minutes / 60 * hourly_cost
    variable = auto_tickets * unit_cost                        # 变动成本随量增长
    net = gross - variable - monthly_run * 12                  # 年净收益
    payback = build_cost / (net / 12) if net > 0 else None
    return {"gross": gross, "variable": variable, "net": net,
            "unit_cost": unit_cost, "payback_months": payback}

result = evaluate(monthly_tickets=24000, auto_rate=0.45, minutes_saved=6, hourly_cost=45,
                  llm_cost=0.01, review_rate=0.35, review_minutes=1.5,
                  build_cost=380000, monthly_run=6000)

print(f"年节省价值 {result['gross']:,.0f} 元")
print(f"年变动成本 {result['variable']:,.0f} 元，单个会话 {result['unit_cost']:.4f} 元")
print(f"年净收益 {result['net']:,.0f} 元，静态回本期 {result['payback_months']:.1f} 个月")
print("结论：", "满足 12 个月回本门槛" if result["payback_months"] <= 12 else "不满足回本门槛")
```

运行 `python3 roi.py`：

```text
年节省价值 583,200 元
年变动成本 52,326 元，单个会话 0.4037 元
年净收益 458,874 元，静态回本期 9.9 个月
结论： 满足 12 个月回本门槛
```

这份结果看起来很漂亮，但请立刻做敏感性分析：把 `auto_rate` 从 0.45 降到 0.25、`minutes_saved` 从 6 降到 3，回本期会拉长到两年以上。因此正确的验收结论不是「值得做」，而是「在自动化率 ≥ 40% 且每单净节省 ≥ 5 分钟时值得做，这两个参数必须作为试点验收门槛」。这也是把 ROI 与验收标准绑定的原因。

## 动手实验

### 前置条件

- 一份试点前后对照数据，或教学用的近似数据。
- 能运行 `python3` 或使用表格工具。

### 步骤

1. 为售后助手写 5 条验收标准，覆盖功能、质量、安全、运营、业务各一条。
2. 用脚本算出基准 ROI，再分别把自动化率、节省时间、模型单价调成悲观值，记录回本期。
3. 写出「结论成立的条件」一句话，把关键参数变成门槛。
4. 为三个候选项目（助手、质检、文案）按价值/成本/风险/就绪度打分并排序。
5. 检查排序是否因「易量化」而偏袒某一项，必要时调整维度权重。

### 预期结果

5 条可执行验收标准 + 三组敏感性结果 + 一份带条件的排序结论。

### 验证方法

- 请不了解项目的人按验收标准判断一次，结论应与团队一致。
- 检查每条标准的样本量是否足以支撑结论；10 条样本无法支撑 98% 的比例。
- 检查悲观情形下是否仍有人愿意继续投入，若答案是否定，条件必须前置。

### 清理方法

删除临时脚本；验收标准与 ROI 假设归档为需求文档附录，并注明数据来源与查询日期。样本中不得包含可识别个人身份的信息。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 验收时双方各执一词 | 标准无阈值或样本量 | 回看标准是否可被第三方复现 | 补场景、阈值、样本量、判定人 |
| ROI 很好但上线后亏损 | 收益按理论值估，成本漏项 | 对比实测节省时间与账单 | 用实测值重算并补全成本 |
| 指标提升但无法归因 | 无对照组，受季节影响 | 取同期对照组数据 | 建对照组或做 A/B |
| 排序总偏向某类项目 | 只比 ROI，忽略就绪度与风险 | 检查维度与权重 | 加入就绪度与风险，说明权重来源 |
| 样本太少结论不稳 | 用 10 条样本判断 98% 指标 | 计算置信区间或扩大样本 | 按比例要求确定样本量 |

## 安全与生产注意事项

**<u>验收样本常含真实个人信息，必须脱敏并限定访问。</u>** 为了评估质量，团队往往会把真实会话、订单号、手机号复制到表格甚至外部工具里；这些副本通常缺少访问控制与留存管理。应在抽样阶段就做替换与脱敏，并把样本库纳入正式的数据资产管理。

**<u>不要用 ROI 覆盖不可逆风险。</u>** 高回报可以解释成本，但不能解释一次错误承诺造成的合规处罚或客户流失。验收标准中必须保留与收益无关的安全与合规门槛，且这些门槛不参与权衡。

另外，验收结论要记录「未达标时的处置」：是缩小范围、延长试点还是退出。没有处置预案的验收，最后往往变成降低标准。

## 本课总结

- **验收标准 = 场景 + 阈值 + 样本量 + 验证方式**，缺一项就无法复现。
- **没有基线就没有提升**，对照组是归因的前提。
- **ROI 要配敏感性分析**，并把关键假设转成阶段门槛。
- **排序要同时看价值、成本、风险与就绪度**，避免只奖励容易量化的项目。
- 安全与合规门槛不能参与收益权衡。

## 思考题

如果售后助手的 ROI 达标，但客服团队反映「改写草稿让我们更累」，你会把哪一项加入验收标准？它应该如何度量，又该如何与 ROI 一起决策？

参考思路：加入「每单净节省时间」与「改写率」作为业务门槛，用试点组与对照组的实测工时差度量。若净节省时间为负，即使 ROI 为正也应暂停推广，因为 ROI 假设的节省并未真实发生，长期还会带来人员流失成本。

## 小测

1. 下列哪条最接近合格的验收标准？  
   A. 回答准确率显著提升　B. 政策类回答引用有效率 ≥ 98%，抽样 100 条　C. 客服觉得好用　D. 模型响应很快
2. 为什么 ROI 计算必须做敏感性分析？
3. 「静态回本期」的含义是什么？
4. 排序时只使用 ROI 会带来什么偏差？
5. 场景题：智能质检项目 ROI 高，但需要访问全部客服录音，且合规尚未出具意见。你会在优先级排序中如何处理？

## 答案与解析

1. **B。** 有阈值、有样本量、可复现。A 无阈值；C 不可测；D 无指标定义。
2. 因为 ROI 依赖多个假设（自动化率、节省时间、单价），任一假设偏乐观都会让结论翻转；敏感性分析能指出结论成立的条件。
3. 用累计净收益抵平初始投入所需的时间，不计资金时间价值。它适合快速比较，但不能替代考虑折现的长期测算。
4. 会系统性偏袒容易量化的降本型项目，压低体验型与风险规避型项目，即使后者对业务更关键。
5. 应把「合规意见」作为就绪度门槛，未通过则排序下调或列为「待条件满足」。ROI 高不能替代合规审查，尤其涉及录音这类敏感数据。

### 动手实验参考

合格的验收标准应让第三方独立判断；合格的 ROI 分析应给出悲观情形下的回本期与「结论成立条件」；合格的排序应说明权重来源，并至少指出一个可能被低估的项目。
