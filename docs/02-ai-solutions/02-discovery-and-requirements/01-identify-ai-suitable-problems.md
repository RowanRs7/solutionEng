# 识别适合 AI 的业务问题

## 为什么需要学习

晴空商城的客服主管提出：「售后咨询太多了，直接用大模型接管吧。」这句话里藏着三个未经验证的假设：问题足够重复、答错可以接受、数据已经就绪。团队先花两周做了自动退款审批的原型，上线评审时被财务和法务同时否决——退款金额、承诺口径、责任归属都不允许「大致正确」。同一批人换成先做政策问答助手，三个月后在试点中把首次响应时间从 40 分钟压到 2 分钟。

> **核心结论：** 适合 AI 的问题不是最想自动化的问题，而是频率够高、错了能兜住、数据够用、且有人接得住的问题。

## 学习目标

完成本课后，你能够：

- 解释 *任务频率*、*容错空间*、*数据可得性*、*人工兜底* 四个筛选维度的含义。
- 用四维打分表对候选任务给出「先做 / 补条件再做 / 不建议」的结论。
- 识别一个需求描述中被隐藏的错误假设，并把它转成需要验证的问题。

## 前置知识

- 回看上一单元：[AI 基础](../01-ai-foundations/00-overview.md)。
- 理解「模型输出是概率性的」，同一输入可能得到不同结果。
- 知道业务系统里存在订单、工单、知识库等结构化与非结构化数据。
- 本课不要求编程经验，示例只需能用 `python3` 运行。

## 业务场景

晴空商城售后团队有 12 名客服，日均 800 个会话。主管整理后发现：

- 约 60% 的会话是政策类问题（七天无理由、运费谁承担、拆封能否退）。
- 约 25% 需要查订单与物流状态。
- 剩余部分是投诉、特殊协商和情绪安抚。

管理层给了三个候选方向：政策问答助手、自动退款审批、大促文案生成。团队必须说明先做哪一个，以及为什么另外两个现在不做。

## 核心概念

| 维度 | 要回答的问题 | 有利信号 | 不利信号 |
| --- | --- | --- | --- |
| *任务频率* | 这类请求每天/每周发生多少次 | 每天几十次以上，话术高度相似 | 一年几次的特殊协商 |
| *容错空间* | 答错一次的代价有多大、能否撤回 | 答错可由人工纠正，损失可逆 | 直接打款、对外承诺、法律责任 |
| *数据可得性* | 回答问题所需数据现在是否拿得到 | 政策文档、订单接口已存在且有权访问 | 数据散落在个人 Excel、需要新建采集 |
| *人工兜底* | 出错时人能否在秒级接管 | 有现成工单流和客服在线 | 无人值守、夜间无值班 |

上表四个维度合起来决定 *AI 适配度*——一个任务被 AI 承担后，整体风险仍在组织可接受范围内的程度。适配度不看技术炫酷程度，只看这四项的组合。

另一个常被忽略的概念是 *自动化等级*：同一个任务可以只是「给建议」「生成草稿」或「直接执行」。等级越高，对容错和兜底的要求越严。<u>先把等级降一档，往往比换更强的模型更能解决问题。</u>

**任务频率决定收益上限，容错与兜底决定风险下限，数据决定这件事今天能不能开始。**

## 工作原理

筛选按固定顺序进行，每一步都可能直接终止候选：

1. **列出任务而不是系统。** 「售后智能助手」是系统，「根据政策判断拆封耳机能否退」才是任务。粒度要细到可以用一句话说清输入和输出。
2. **量化频率。** 从工单系统导出最近 8 周的分类计数。没有分类就先抽样 200 条人工打标，估算比例。频率乘上单次人工耗时，就是理论上限收益。
3. **量化错误代价。** 分别问三件事：错误可逆吗？单次最大损失是多少？影响面是一个客户还是一批客户？可逆且低额的任务才适合高自动化等级。
4. **盘点数据。** 对每个必需字段回答「有没有、准不准、多久更新、谁授权」。政策文档属于低频变更但需版本化；订单状态属于高频变化必须实时查。
5. **设计兜底。** 明确谁接管、多快接管、接管时看到什么上下文。没有兜底通道的任务，无论模型多准都不应进入生产。
6. **打分并给出结论。** 用统一权重算出总分，同时保留每项原始分，方便后续复盘是哪一维拖后腿。

第 3 步和第 5 步经常被跳过，但它们恰恰决定项目是「提效」还是「制造事故」。NIST AI 风险管理框架把「预期用途、业务价值、错误成本、人工监督流程」都列为绘制风险上下文时必须记录的内容，并明确要求在有可行替代方案时进行比较——这与本课的筛选逻辑一致（见延伸阅读，复核日期 2026-10-19）。

## 架构与选型

| 四维组合 | 典型任务 | 建议做法 |
| --- | --- | --- |
| 高频 + 高容错 + 数据齐 + 有兜底 | 售后政策问答、物流状态解释 | 可做，先以「草稿 + 人工发送」起步 |
| 高频 + 低容错 + 数据齐 + 有兜底 | 退款审批、补偿承诺 | 只做「建议」，最终动作留给人 |
| 低频 + 高容错 | 大促文案、内部周报 | 可做但收益小，排在后面 |
| 高频 + 低容错 + 数据缺失 | 跨系统的赔付判定 | 先补数据和流程，不立项 |

选型依据不是「哪一维分数最高」，而是**最短的那一维**。一维不达标时，正确动作是把该维补齐（补数据、加人工审核、缩小范围），而不是提高模型规格。当四维都勉强及格时，优先缩小任务范围以抬高容错空间，例如只回答「七天无理由」而不涉及「拆封后折旧扣款」。

## 最小示例

下面的脚本把四维判断变成可复盘的加权评分。权重可按行业调整，但要事先写定，避免事后凑分。

```python
# 四维筛选：把「感觉适合」变成可复盘的评分
criteria = {                 # 维度名 -> (权重, 判断问题)
    "frequency": (0.30, "这类请求每周发生多少次"),
    "tolerance": (0.30, "答错一次的代价有多大"),
    "data":      (0.25, "回答问题所需的数据现在拿得到吗"),
    "fallback":  (0.15, "出错时人能不能在几秒内接管"),
}
cases = {                    # 每项 1-5 分，5 分表示对 AI 最有利
    "售后政策问答": {"frequency": 5, "tolerance": 4, "data": 4, "fallback": 5},
    "自动退款审批": {"frequency": 4, "tolerance": 2, "data": 3, "fallback": 3},
    "大促文案生成": {"frequency": 2, "tolerance": 5, "data": 2, "fallback": 4},
}
for name, scores in cases.items():
    total = sum(scores[k] * w for k, (w, _) in criteria.items())   # 加权和
    verdict = "先做" if total >= 4.0 else "补条件再做" if total >= 3.0 else "不建议"
    print(f"{name:8s} 得分 {total:.2f} -> {verdict}")
```

运行 `python3 score.py`，得到：

```text
售后政策问答   得分 4.45 -> 先做
自动退款审批   得分 3.00 -> 补条件再做
大促文案生成   得分 3.20 -> 补条件再做
```

两点设计意图：评分只用于排序，不用于证明「分数高就一定成功」；自动退款审批卡在 3.00 恰好说明它「看起来该做，但容错和兜底拖了后腿」——这比直接判死更有讨论价值，团队可以追问：把等级降到「只出建议」能否把容错分抬到 4 分？

## 动手实验

### 前置条件

- 能运行 `python3` 的环境。
- 一支笔和纸，或任意表格工具。

### 步骤

1. 从你熟悉的业务里挑 3 个候选任务，写成「输入 → 输出」的短句。
2. 为每个任务在四个维度上打 1–5 分，并在旁边写一句打分依据（例如「容错 2：错误会直接打款」）。
3. 把上面脚本的 `cases` 替换成你的三个任务，运行脚本。
4. 找出扣分最多的那一维，写一句「要补什么条件才能升一档」。

### 预期结果

每个任务得到 1.00–5.00 的分数与结论；至少有一个任务因某一维低于 3 分而落入「补条件再做」。

### 验证方法

- 让另一位同事只看你的打分依据能否复现同样的分数。若不能，说明依据写得太模糊。
- 检查是否所有维度都打了 4 分以上：如果全是高分，通常是标准太松，而不是任务真的完美。

### 清理方法

删除临时脚本；评分表归档到需求文档中，作为后续阶段复盘的输入。不要把真实客户数据写进表格。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 每个候选都「适合 AI」 | 打分维度太松，缺少反面依据 | 抽查任意一条分数的书面依据 | 为每维写出「低于 3 分的具体情形」再重打 |
| 频率估计偏差巨大 | 按印象而非工单数据估算 | 与工单系统近 8 周计数对比 | 抽样 200 条人工打标后外推 |
| 上线后错误无人纠正 | 容错被高估，兜底通道未建 | 检查是否存在接管入口和值班安排 | 降低自动化等级，先做草稿 |
| 数据「都有」但取不到 | 只确认存在，未确认权限与接口 | 让工程师当场演示一次取数 | 把取数验证列入立项门槛 |
| 筛完仍不知先做哪个 | 只算总分，未看短板 | 逐项查看最低分维度 | 按短板可补齐程度排序 |

## 安全与生产注意事项

**<u>不要因为任务频率高就把它当作该自动化的任务。</u>** 高频只说明收益上限大，不代表风险可接受；退款、赔付、账号操作这类高频低容错动作，恰恰是最容易在压力下被「顺手自动化」的。

**<u>数据可见不等于数据可用。</u>** 客服能看到客户手机号和收货地址，不代表 AI 系统有权读取、留存或把它们拼进提示词。可访问性、留存期限、脱敏要求和审计记录需要在立项时就写清，而不是上线前补。

此外，兜底通道必须真的有人值守。夜间或大促期间无人接管时，系统应主动降级为「仅收集信息、次日回复」，而不是继续给出可能错误的答复。

## 本课总结

- **四维筛选的作用是排除，而不是加分。** 频率、容错、数据、兜底中任一维不过关，都应该先补条件。
- **容错和兜底决定风险下限。** 可逆、低额、有人接的任务才适合提高自动化等级。
- **数据盘点要问到权限和时效。** 「有这份文档」和「能实时取到并有权使用」是两件事。
- **先降自动化等级，再考虑换模型。** 草稿态往往能同时解决准确率和责任归属问题。
- 评分要能被他人在没有你的情况下复现，否则只是把主观判断包装成数字。

## 思考题

晴空商城计划上线「自动判断是否支持七天无理由退货，并直接生成退款单」。四个维度上你会怎么打分？如果业务方坚持要「直接生成」，你会提出哪些前置条件？

参考思路：政策判断本身频率高、数据齐，但退款单属于写操作，容错分应显著偏低，除非引入金额上限、白名单品类和人工抽检。可提出的前置条件包括：只生成待确认草稿、单笔金额上限、按品类灰度、保留完整审计日志、错误率超过阈值自动回退到全人工。

## 小测

1. 下列哪一项最直接降低任务的 AI 适配度？  
   A. 请求量很大　B. 答错后无法撤回　C. 有现成的政策文档　D. 客服团队人数多
2. 「数据可得性」需要确认的四件事是什么？
3. 为什么把自动化等级从「直接执行」降到「生成草稿」通常比换更强的模型更有效？
4. 频率估计应该优先依据什么？
5. 场景题：晴空商城想把「客户投诉的情绪安抚」交给 AI，投诉量每天约 30 起，答错的影响主要是客户更生气，客服主管认为「反正有人会接手」。请用四维框架给出你的判断和一条建议。

## 答案与解析

1. **B。** 容错空间直接决定风险下限。A 提高收益上限但不降低适配度；C 是有利条件；D 与适配度无关，人数多只说明人力成本高。
2. 有没有、准不准（质量）、多久更新（时效）、谁授权（权限与合规）。四者缺一，任务就应判为「数据不达标」。
3. 因为草稿态把「不可逆的对外动作」变回「可审阅的建议」，同时消除责任归属争议；换模型只改变出错概率，不改变出错后果。概率无法降到零，后果可以设计。
4. 工单系统的真实计数。没有分类数据时抽样打标再外推，而不是凭印象。印象估计在低频高情绪的场景里偏差最大。
5. 参考：频率中等（30 起/天偏低），容错中低（情绪问题容易升级为舆情），数据几乎不可得（客户情绪历史难以结构化），兜底尚可（客服在线）。结论是「补条件再做」，建议先做「识别高情绪会话并优先排队 + 给客服生成安抚话术草稿」，而不是让 AI 直接回复客户。

### 动手实验参考

合理答案不唯一。合格的标准是：每个分数都有书面依据；最低分维度被明确指出；至少写出一条可执行的补齐动作（如「接入订单只读接口」「增加 2 名夜间值班」）。
