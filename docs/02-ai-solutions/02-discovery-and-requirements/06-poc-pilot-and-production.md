# PoC、试点与生产项目的区别

## 为什么需要学习

晴空商城去年试过一版售后助手：PoC 用了三周，答对率 78%，评审会上所有人都很兴奋，预算顺利批下来。六个月后项目被叫停——试点阶段的真实会话里，只有 12% 的客服愿意用它，因为「改它的草稿比自己写还慢」。回头看，PoC 定的标准是「能答出来」，试点定的标准是「答得对」，而真正决定生死的「客服愿意用」从头到尾没人测。今年重启这个项目时，团队把三个阶段的门槛和退出条件写在了最前面。

> **核心结论：** 三个阶段回答三个不同的问题——能不能做、值不值得用、能不能长期运营；用前一个阶段的标准验收后一个阶段，是最常见的失败来源。

## 学习目标

完成本课后，你能够：

- 说明 PoC、试点、生产三阶段在目标、用户、数据和退出条件上的差别。
- 为一个 AI 需求写出分阶段的进入门槛与退出条件。
- 判断一个阶段结论是否足以支撑进入下一阶段。

## 前置知识

- 回看上一课：[AI 可行性、风险与依赖评估](05-feasibility-risk-and-dependency.md)。
- 了解灰度发布与回滚的基本概念。
- 知道「可用性」「准确率」「采纳率」是不同层面的指标。
- 不需要编程经验，示例可用 `python3` 运行。

## 业务场景

售后助手已经完成可行性评估。管理层希望「三个月上线」，但没说清三个月后交付的是演示、可用版本，还是可运营的服务。团队需要把「上线」拆成三段落地的路径，并为每段定义谁用、用多少、达到什么条件才继续投入。

## 核心概念

*PoC（概念验证）* 用最小成本回答「这件事技术上能不能做到」，参与者通常是内部人员，数据是小规模样本。*试点（pilot）* 在真实业务流程中让少量真实用户使用，回答「在真实条件下是否值得用」。*生产* 回答「能否长期稳定运营并承担责任」。

| 阶段 | 回答的问题 | 使用者 | 数据 | 成功标准 | 典型投入 | 退出条件 |
| --- | --- | --- | --- | --- | --- | --- |
| PoC | 能不能做到 | 项目组 | 小样本、可公开或脱敏 | 能力存在，错误有改进空间 | 人周级 | 达不到能力下限，或成本明显不可接受 |
| 试点 | 真实场景下值不值得用 | 一个小组的真实客服 | 真实流量的一部分 | 业务指标改善，用户愿意继续用 | 人月级 | 采纳率不达标，或错误率越线无法缓解 |
| 生产 | 能否稳定运营 | 全量或大部分用户 | 全量，含异常与长尾 | SLO、合规、成本、业务指标同时达标 | 持续投入 | 不设退出，设降级与下线机制 |

*影子模式* 指系统在后台生成结果但不影响业务，用于在真实流量上比较质量与延迟。*门槛（gate）* 是进入下一阶段必须满足的条件集合，*退出条件* 则是提前止损的判据。二者都要在阶段开始前写定，否则会变成事后解释。

<u>PoC 通过不等于方案可行。</u> PoC 证明的是「在有利条件下能跑通」，试点要证明的是「在不利条件下仍然有用」。

## 工作原理

阶段推进按固定节奏进行：

1. **定义本阶段唯一要回答的问题。** 一个问题，一个结论；不要在同一阶段同时验证能力、成本和采纳率。
2. **写进入条件。** 例如试点开始前必须完成：评测集冻结、数据授权到位、接管通道可用、回滚方案演练过一次。
3. **写成功门槛与退出条件。** 门槛用可测指标表达，退出条件要能在阶段中途触发，而不是等到期末。
4. **控制暴露面。** PoC 用脱敏样本；试点限定团队、时段与流量比例；生产按灰度逐步放大。
5. **收集使用证据。** 除准确率外，记录采纳率、改写率、单次处理时长、客服主观负担；这些决定「值不值得用」。
6. **阶段复盘并决策。** 结论只能是三种：进入下一阶段、留在本阶段补条件、退出。不允许「继续观察」而不改任何条件。

第 4 步的暴露面控制是 AI 项目特有的要求：模型的错误不是崩溃而是「看起来对的错话」，扩散速度快。试点应把影响限制在可回溯的小范围，并保留人工复核作为兜底。NIST AI RMF 的 Measure 2.4 要求在生产中持续监控系统行为，Manage 4.1 要求部署后监控包含申诉、覆盖与停用机制，这正是「生产」与「试点」的分界（复核日期 2026-10-19）。

## 架构与选型

| 判断情形 | 建议阶段 | 理由 |
| --- | --- | --- |
| 只想验证某类问题模型能否答对 | PoC | 成本最低，无需接入业务系统 |
| 已有可用原型，想验证客服是否愿意用 | 试点 | 采纳率只能在真实流程中测 |
| 试点指标达标，但只覆盖一个品类 | 扩大试点而非直接生产 | 长尾与异常尚未暴露 |
| 需要对外承诺口径 | 生产（含审批与审计） | 责任与合规要求在这一层才成立 |
| 关键依赖不稳定 | 留在试点并补降级 | 生产要求可用性承诺 |
| 业务方要求「先上线再优化」 | 影子模式 | 不改变业务结果，同时获得真实数据 |

选型的核心是「本阶段要买的答案值多少钱」。PoC 适合买「技术可行性」，试点适合买「用户意愿与业务效果」，生产则是在持续付费买「稳定性与责任」。

## 最小示例

用脚本把三阶段门槛写成可执行检查，避免评审时各说各话。

```python
GATES = {
    "poc":        {"goal": "证明能力存在",   "threshold": {"task_success": 0.60, "cost_per_call": 1.00}},
    "pilot":      {"goal": "证明业务可用",   "threshold": {"task_success": 0.85, "p95_latency": 5.0, "cost_per_call": 0.30}},
    "production": {"goal": "证明可持续运营", "threshold": {"task_success": 0.90, "p95_latency": 3.0, "cost_per_call": 0.20, "availability": 0.999}},
}

def check(phase, measured, higher_is_better=("task_success", "availability")):
    gate = GATES[phase]
    ok = True
    for metric, limit in gate["threshold"].items():
        value = measured.get(metric)
        if value is None:
            print(f"  {phase:10s} {metric:14s} 缺失 -> 无法判定")
            ok = False
            continue
        passed = value >= limit if metric in higher_is_better else value <= limit
        ok = ok and passed
        print(f"  {phase:10s} {metric:14s} 实测 {value:<6} 门槛 {limit:<6} {'通过' if passed else '未通过'}")
    return ok

# PoC 阶段只关心「能不能做出来」，不要求延迟和成本
print("PoC 实测：", check("poc", {"task_success": 0.78, "cost_per_call": 0.9}))
# 试点阶段用真实流量压测
print("试点实测：", check("pilot", {"task_success": 0.86, "p95_latency": 6.2, "cost_per_call": 0.24}))
```

运行 `python3 gates.py`：

```text
  poc        task_success   实测 0.78   门槛 0.6    通过
  poc        cost_per_call  实测 0.9    门槛 1.0    通过
PoC 实测： True
  pilot      task_success   实测 0.86   门槛 0.85   通过
  pilot      p95_latency    实测 6.2    门槛 5.0    未通过
  pilot      cost_per_call  实测 0.24   门槛 0.3    通过
试点实测： False
```

注意试点结论是「未通过」，尽管准确率已达标。这正是分阶段门槛的价值：延迟不达标会直接摧毁采纳率，不能因为「主要指标好看」就放行。脚本同时演示了「缺失指标不得默认为通过」——没有测量就等于没有证据。

## 动手实验

### 前置条件

- 已有一份可行性评估与至少 3 个候选指标。
- 能运行 `python3` 或使用表格工具。

### 步骤

1. 为你的项目写三行：PoC 回答什么、试点回答什么、生产要承诺什么。
2. 为每阶段写 2–3 个门槛指标与阈值，并注明数据来源。
3. 为每阶段写一条退出条件，要求能在阶段中途触发。
4. 用脚本跑一次：故意缺失一个指标，确认结论是「无法判定」。
5. 写一句「谁有权决定退出」，落到具体角色。

### 预期结果

三阶段门槛表 + 三条退出条件 + 一个明确的决策人；脚本对缺失指标返回未通过。

### 验证方法

- 让业务方确认门槛是否与他们的目标一致（例如客服更在意处理时长而非准确率）。
- 检查退出条件是否有人敢执行：如果阈值永远不可能触发，说明设得太松。

### 清理方法

删除临时脚本；门槛表纳入项目计划，每次阶段评审时更新实测值。不要把真实用户数据写入示例文件。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| PoC 通过后直接全量上线 | 混淆「能跑通」与「可运营」 | 检查是否有试点阶段与采纳率数据 | 补试点，限定团队与流量 |
| 试点无限期延长 | 未定义退出条件与决策人 | 查项目计划是否写了止损线 | 写退出条件并指定决策角色 |
| 上线后客服不用 | 验收只看准确率不看采纳率 | 统计使用率与改写耗时 | 把采纳率纳入试点门槛 |
| 指标好看但业务无感 | 只测模型层，未测业务层 | 对比试点前后一次解决率 | 补业务指标与对照组 |
| 出问题无法回滚 | 未做灰度与开关 | 演练一次关闭 AI 功能 | 加功能开关与一键降级 |

## 安全与生产注意事项

**<u>不要用真实客户数据做 PoC。</u>** PoC 环境通常缺少访问控制、审计与留存管理，把生产数据复制进去等于绕开全部保护。应使用脱敏样本或合成数据，并在扩到试点前完成数据授权与访问审计。

**<u>没有功能开关和回滚演练的「生产」不是生产。</u>** 模型行为异常时，第一动作应是关闭或降级该功能，而不是现场改提示词。开关粒度要能覆盖「全部关闭」「仅关写操作」「仅保留检索」，并在上线前实际演练一次。

另外，试点阶段的错误样本要保留并纳入回归集，否则同一类错误会在生产再次出现。阶段推进的评审材料应包含这些样本，而不只是成功率数字。

## 本课总结

- **三阶段回答三个不同问题：能不能做、值不值得用、能不能长期运营。**
- **门槛与退出条件必须在阶段开始前写定**，否则会退化为事后解释。
- **PoC 面向内部，试点面向真实用户，生产面向责任与稳定性。**
- **采纳率、改写率是试点阶段的核心证据**，准确率不足以保证被使用。
- 生产阶段必须预备功能开关与降级路径，并演练过至少一次。

## 思考题

如果管理层要求「跳过试点，直接小流量生产」，你会接受吗？如果接受，需要哪些额外条件才能把风险控制在可接受范围？

参考思路：可以把「小流量生产」当成试点的一种形式，但必须补齐：功能开关与一键降级、限定用户与时段、明确退出条件、按会话抽检、客服知情同意、以及每日指标复盘。若这些条件无法满足，则应拒绝跳阶段。

## 小测

1. PoC 阶段最应该测什么？  
   A. 采纳率　B. 能力下限与可行性　C. 全量 SLO　D. 客服满意度
2. 为什么试点阶段必须使用真实用户？
3. 「缺失指标默认为通过」会带来什么后果？
4. 生产阶段相比试点，新增的核心责任是什么？
5. 场景题：助手在试点中准确率 88%（门槛 85%），但客服平均每单多花 20 秒修改草稿。请判断是否应进入生产，并说明理由。

## 答案与解析

1. **B。** PoC 只回答能力问题。A、D 需要真实用户；C 依赖生产环境的容量与运维能力。
2. 因为试点要验证的是「在真实流程中是否值得用」，采纳率、修改成本、异常处理都只能在真实用户与真实流量中观察。
3. 会把「没有证据」误判为「证据充分」，导致带着未验证的风险进入下一阶段。缺失应判为「无法判定」，即不通过。
4. 稳定性承诺与责任：SLO、审计、合规、故障响应、降级与下线机制，以及对外的承诺口径。
5. 不应直接进入生产。准确率达标但单次处理时长增加，会直接压低采纳率；应先优化草稿质量或调整介入点（例如只对高价值场景出草稿），把「每单净节省时间」作为新的试点门槛。

### 动手实验参考

合格的门槛表应满足：每阶段一个问题；指标含数据来源；至少一条退出条件可在阶段中期触发；明确写出决策人角色。把「继续优化」当作退出条件不算完成。
