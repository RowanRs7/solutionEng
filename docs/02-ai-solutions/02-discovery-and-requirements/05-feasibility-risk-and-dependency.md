# AI 可行性、风险与依赖评估

## 为什么需要学习

晴空商城的助手在 PoC 演示里答对了 9 个问题中的 7 个，评审顺利通过。试点第一周却接连出状况：订单接口在晚高峰超时，答复卡住 30 秒；供应商通知某个模型版本将停止服务，团队发现自己把提示词调成了那个版本的「方言」；政策文档更新后，检索仍在命中旧条款。

> **核心结论：** 可行性是「在真实约束下能否稳定达标」，不是「演示时能否跑通一次」。

## 学习目标

完成本课后，你能够：

- 区分能力可行性、数据可行性、集成可行性、成本可行性与合规可行性。
- 列出至少 5 类 AI 项目特有失败模式及其可观测信号。
- 产出含概率、影响、责任人、缓解措施与复核条件（检查时点）的风险登记表。

## 前置知识

- 回看上一课：[输入、输出、上下文与数据条件](04-inputs-outputs-context-and-data.md)。
- 了解供应商 API 常见限制：限流、超时、版本变更、按量计费。
- 知道「演示环境」和「生产环境」在流量、权限、数据上通常不同。
- 能阅读表格并做简单加权计算。

## 业务场景

售后助手要用到三方：大模型供应商、订单与物流接口（内部）、政策文档库（内部）。此外还依赖客服团队的排班来承接转人工。管理层问：这套东西三个月能不能上？技术负责人需要一份可被质询的评估，而不是一句「应该没问题」。

## 核心概念

| 可行性维度 | 要证明什么 | 需要的证据 | 不通过的典型表现 |
| --- | --- | --- | --- |
| 能力 | 在目标场景下达到可用准确率 | 真实问题集上的分层评测结果 | 只在挑选过的例子上表现好 |
| 数据 | 所需字段可获取、够新、有权使用 | 取数演示 + 权限确认 + 版本记录 | 「文档有，但没人知道哪版是准的」 |
| 集成 | 能与现有系统稳定对接 | 接口压测、超时与重试验证 | 单次调用正常，并发就超时 |
| 成本 | 单位经济在预算内 | 真实 token 用量 × 单价 + 人工复核成本 | 只算模型调用费，漏掉人力 |
| 合规 | 满足隐私、留存、审计与对外承诺要求 | 数据流图 + 法务/安全书面意见 | 上线前才发现需要额外授权 |

*失败模式* 指系统在真实使用中反复出现的错误类型，例如「无依据时编造条款」「检索命中过期版本」「工具调用超时后重复执行」。*依赖* 指方案成立所必需的外部条件，包括供应商、接口、数据供给方与人员。*降级路径* 是依赖失效时的替代行为，例如模型不可用时返回模板答复并转人工。

<u>把「供应商不会变」当作假设，是 AI 项目最常见的隐性依赖。</u> 模型版本、限流额度、计价方式、可用区域都可能调整，且通常不以保证形式承诺。需求阶段就应问：如果明天这个模型不可用，我们多久能切到备用？

## 工作原理

评估按「证据优先」的顺序推进：

1. **写清通过标准。** 在测之前定下门槛：任务成功率、p95 延迟、单位成本、人工接管率。标准要能被第三方复现。
2. **构造真实评测集。** 从工单里分层抽样，覆盖高频问题、边界问题、恶意诱导与信息缺失四类，而不是挑顺手的例子。
3. **逐维取证。** 能力看评测结果；数据看取数演示与版本；集成做压测与故障注入；成本按真实 token 用量估算；合规取得书面意见。
4. **列失败模式并映射信号。** 每条失败模式都要有可观测指标，例如「无引用回答占比」「检索命中旧版本次数」「工具重复调用率」。
5. **登记依赖与到期风险。** 记录供应商、接口、数据源的责任人与复核时点，包括证书到期、额度上限、版本生命周期。
6. **定缓解与降级。** 高概率高影响项必须在本阶段缓解；无法缓解的写入「接受并监控」，并说明谁接受。
7. **设复核触发。** 明确什么条件下重做评估：模型换版、政策大改、单量翻倍、错误率越线。

NIST AI RMF 把这套动作拆成 map、measure、manage 三个函数：map 建立上下文与风险清单，measure 用可重复的方法量化并记录测试集与指标，manage 则要求「在存在可行非 AI 替代方案时进行比较」，并为撤销或停用系统准备机制（复核日期 2026-10-19）。本课的第 1–4 步对应 map 与 measure，5–7 步对应 manage。

## 架构与选型

| 依赖类型 | 典型风险 | 缓解措施 | 降级路径 |
| --- | --- | --- | --- |
| 模型供应商 | 版本退役、限流、涨价 | 锁定版本、双供应商适配层、用量监控 | 切换备用模型；退回规则 + 模板 |
| 内部订单接口 | 晚高峰超时 | 2 秒超时、缓存、异步补偿 | 告知「稍后查询」并转人工 |
| 政策文档库 | 版本混乱、更新滞后 | 版本号 + 生效日期 + 发布流程 | 命中不确定时不给结论 |
| 检索索引 | 索引与文档不同步 | 增量同步 + 每日对账 | 回退到关键词检索 |
| 人工承接 | 排班不足、夜间无人 | SLA + 值班表 + 告警 | 只收集信息，次日回复 |
| 合规授权 | 授权范围不足 | 立项即拉安全与法务 | 缩小范围或暂停上线 |

选型时优先选择「依赖少且可替换」的方案。同一能力有两家可用时，多写一层适配的成本远低于被单一供应商锁死的成本；反过来，为了「技术先进」引入三个新依赖，会让可行性的举证责任成倍增加。

## 最小示例

把风险登记表写成可计算的结构，按「可能性 × 影响」排序，避免只凭印象排序。

```python
risks = [
    {"id": "R1", "risk": "模型编造售后政策条款",       "likelihood": 4, "impact": 5, "control": "强制引用；无引用直接转人工"},
    {"id": "R2", "risk": "订单接口超时拖住整条答复链",   "likelihood": 3, "impact": 3, "control": "2 秒超时；降级为模板答复"},
    {"id": "R3", "risk": "供应商换模型版本，话术漂移",   "likelihood": 3, "impact": 2, "control": "锁定版本；回归集每次发布必跑"},
    {"id": "R4", "risk": "客服用模型话术越权承诺赔偿",   "likelihood": 2, "impact": 5, "control": "草稿态；高额退款强制人工确认"},
]

def level(score):
    return "高" if score >= 15 else "中" if score >= 8 else "低"

for r in sorted(risks, key=lambda x: x["likelihood"] * x["impact"], reverse=True):
    score = r["likelihood"] * r["impact"]
    action = "本阶段必须缓解" if score >= 15 else "试点前缓解" if score >= 8 else "接受并监控"
    print(f'{r["id"]} {score:2d}分 {level(score)}风险 {r["risk"]} -> {action}')
```

运行 `python3 risk.py`：

```text
R1 20分 高风险 模型编造售后政策条款 -> 本阶段必须缓解
R4 10分 中风险 客服用模型话术越权承诺赔偿 -> 试点前缓解
R2  9分 中风险 订单接口超时拖住整条答复链 -> 试点前缓解
R3  6分 低风险 供应商换模型版本，话术漂移 -> 接受并监控
```

设计意图：打分用于排序与分配精力，最终动作还要看「能否缓解」。R4 概率只有 2 但影响 5，仍应优先于 R3；R1 必须在本阶段解决，因为它直接决定系统能不能给结论。阈值只是起点，业务方应确认「接受并监控」由谁签字。

## 动手实验

### 前置条件

- 你的场景中至少有一个外部依赖与一个内部依赖。
- 能运行 `python3` 或使用表格工具。

### 步骤

1. 列出 5–8 条失败模式，按「能力 / 数据 / 集成 / 成本 / 合规」归类。
2. 为每条打可能性与影响（1–5 分），并写出可观测信号。
3. 标注缓解措施、责任人与复核时点。
4. 用脚本排序，检查前两名是否都有明确缓解方案。
5. 为每个外部依赖写一条降级路径，并注明验证方式（例如「断网演练」）。

### 预期结果

得到一张排序后的风险表；能力与合规两类至少各有一条被标为「本阶段必须缓解」。

### 验证方法

- 请一位不在项目里的人看表：能否说出每条风险的触发信号？说不出的条目需要重写。
- 检查是否有「接受并监控」但没有监控指标的情况，这属于未完成。

### 清理方法

删除临时脚本；风险表纳入需求文档并随评审更新。表中不得出现供应商报价截图等可能过期的材料，改为记录查询日期与来源链接。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| PoC 很好，试点崩 | 评测集挑选过，未覆盖边界与恶意输入 | 对比评测集来源是否来自真实工单 | 分层抽样并加入对抗样本 |
| 上线后成本超预算 | 只算模型费，漏人工复核与重试 | 按真实会话统计 token 与复核时长 | 补全单位经济并设预算告警 |
| 供应商变更导致全面返工 | 未做适配层，提示词绑定单版本 | 检查更换模型需要改几处 | 抽出适配层，锁版本，跑回归集 |
| 风险表填完没人用 | 无责任人、无复核时点 | 抽查三条是否有人认领 | 每条指定负责人与检查日期 |
| 合规问题上线前才暴露 | 立项未拉安全与法务 | 查需求评审记录是否含合规意见 | 把合规列为立项门槛 |

## 安全与生产注意事项

**<u>第三方条款与数据流向必须在上线前书面确认。</u>** 把客户对话、订单信息发送到外部服务，涉及数据处理协议、留存期限与地域限制；「默认不会用于训练」需要以合同或官方条款为依据，而不是听说。合规判断由安全与法务作出，架构师负责提供准确的数据流图。

**<u>没有降级路径的系统不应该上线。</u>** 模型限流、接口故障、索引损坏都会发生；若这些情况下系统只会报错白屏，人工通道也会被连带拖垮。降级必须是预先设计并演练过的行为，而不是故障时临时决定。

此外，供应商版本生命周期要纳入日历：在版本退役前完成迁移与回归测试，不要等公告到期才处理。价格与额度的变化也应设监控，避免账单异常时才被发现。

## 本课总结

- **可行性靠证据，不靠演示。** 评测集来源、取数演示、压测记录都是可被质询的证据。
- **成本要算全。** 模型调用费通常不是主要成本，人工复核与重试才是。
- **风险要能排序也要能认领。** 没有责任人与复核时点的风险表只是清单。
- **依赖必须可替换或有降级**，尤其是模型供应商与关键内部接口。
- 合规不是上线前的检查项，而是立项时的输入。

## 思考题

如果供应商宣布当前模型将在 90 天后停止服务，而团队正在试点高峰，你会如何安排迁移？哪些工作必须现在做，哪些可以并行？

参考思路：立即冻结依赖该版本的新功能，建立回归集作为迁移验收基线，在适配层接入候选模型并做并行对比（影子流量）；同时更新风险表与对外口径。迁移与业务优化可以并行，但回归集与适配层必须现在完成。

## 小测

1. 下列哪项最不能作为「能力可行」的证据？  
   A. 真实工单抽样的评测结果　B. 演示会上答对 8/9 题　C. 分层错误分析　D. 与基线方案对比
2. 为什么单位成本估算必须包含人工复核？
3. 「锁定模型版本」缓解的是哪类风险？
4. 一条合格的风险登记应包含哪些字段？
5. 场景题：团队发现订单接口在晚高峰 p99 达到 12 秒，助手会一直等待。请给出至少两条缓解措施和一条降级路径。

## 答案与解析

1. **B。** 演示样本通常经过挑选，无法代表真实分布。A、C、D 都提供了可复现的证据或对比基线。
2. 因为人工复核常是成本主项，且随自动化率变化。漏掉它会得出「越用越便宜」的错误结论，实际上量越大复核成本越高。
3. 供应商版本变更导致的输出漂移与迁移风险。锁定版本争取时间，但不能消除风险，仍需回归集与迁移计划。
4. 编号、风险描述、可能性、影响、分值、可观测信号、缓解措施、责任人、复核时点、接受者（针对接受并监控项）。
5. 缓解：为订单查询设 2 秒超时并异步重试；对查询结果做短时缓存；把订单查询与生成解耦，先返回「正在查询」。降级：超时后返回模板答复并转人工，同时记录超时率作为发布门槛指标。

### 动手实验参考

合格的风险表有三个特征：每条都有可观测信号；前两名高风险都有明确的阶段内缓解动作；每个外部依赖都有降级路径与验证方式。只写「加强监控」不算缓解措施。
