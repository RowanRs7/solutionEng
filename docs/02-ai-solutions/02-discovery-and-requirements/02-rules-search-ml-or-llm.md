# 规则系统、搜索、传统机器学习与 LLM 的选择

## 为什么需要学习

确认了「售后政策问答值得做」之后，团队的第二个分歧往往更激烈：有人主张直接上大模型，有人坚持先把规则引擎补完。两边都有真实依据——规则引擎能覆盖 70% 的常见问题，但每加一个品类就要改一次代码；大模型一句话就能回应任何问法，却在上线第一周把「拆封耳机扣 15% 折旧」说成了「全额退款」，客服照抄后赔了 3000 元。

> **核心结论：** 方案选择不是选最强的技术，而是让每个子问题走它最便宜、最可解释、最不容易错的那条路径。

## 学习目标

完成本课后，你能够：

- 解释 *规则系统*、*检索*、*传统机器学习* 与 *LLM* 四类方案各自的能力边界。
- 用可解释性、数据需求、单次成本、长尾覆盖四个维度比较候选方案。
- 为一个混合需求画出「先规则、再检索、后生成」的路由顺序，并说明每一步的失败降级。

## 前置知识

- 回看上一课：[识别适合 AI 的业务问题](01-identify-ai-suitable-problems.md)。
- 理解大模型按概率生成文本，不能保证事实正确。
- 知道「检索」指按关键词或语义从文档集合中找出相关片段。
- 能用 Python 写简单的 `if`/正则判断。

## 业务场景

晴空商城的售后会话可以粗分为三类：查订单状态、问政策条款、开放式投诉与协商。现有资产包括订单查询接口、一份 40 页的售后政策文档、一个维护了三年的规则引擎（约 120 条规则），以及一个可调用的大模型接口。

上一课结论是先做政策问答助手。现在要回答的是：这三类会话分别交给谁处理，边界在哪里。

## 核心概念

| 维度 | *规则系统* | *检索* | *传统机器学习* | *LLM* |
| --- | --- | --- | --- | --- |
| 主要能力 | 精确匹配已知条件 | 找出相关原文片段 | 从历史样本学分类/打分 | 理解表达并组织语言 |
| 可解释性 | 高（能指出命中哪条规则） | 中高（能给出出处） | 中（特征重要度有限） | 低（理由可能是事后编造） |
| 数据需求 | 无，靠人工编写 | 需要干净文档与索引 | 需要标注样本，通常上千条起 | 无需训练，但需要好的提示与上下文 |
| 单次成本 | 极低 | 低 | 低 | 相对高，随 token 增长 |
| 长尾覆盖 | 差，未写到的问法就失效 | 中，取决于文档是否覆盖 | 中，取决于训练分布 | 好，能处理未见过的表达 |
| 变更速度 | 慢，改规则要发版 | 快，改文档即可 | 慢，要重训与评估 | 快，改提示或上下文即可 |
| 典型失败 | 词表漏配、规则冲突 | 检索到过期或无关条款 | 分布漂移后静默退化 | 编造条款、口径不一致 |

*混合编排* 指把上述方案按顺序组合：确定性判断交给规则，需要依据的交给检索，需要自然语言表达的交给 LLM。<u>把「找事实」和「组织语言」拆开，是这类系统最重要的设计决定。</u>

## 工作原理

分层路由按「越确定越靠前」的顺序执行：

1. **抽取结构化线索。** 从会话里识别订单号、商品类目、时间等可结构化字段。抽不到就进入下一层，不要在这里调用模型。
2. **命中确定性事实查询。** 有订单号且问的是物流/签收，直接查订单接口并套模板回复。这条路径没有生成环节，也就没有幻觉。
3. **命中政策范围。** 用关键词或语义检索在政策文档中定位条款，连同条款原文一起交给下一步。检索为空时不得让模型「凭常识回答」。
4. **需要组织语言时调用 LLM。** 输入限定为「用户问题 + 检索到的条款原文 + 输出格式要求」，并要求引用条款编号。
5. **生成后校验。** 检查是否带引用、金额是否与条款一致、是否出现文档中不存在的承诺；不通过则降级为「转人工」。
6. **记录路由结果。** 每次请求记录走了哪条路径，用于计算各层覆盖率与误路由率。没有这份数据，后续无法判断该扩规则还是该改提示。

第 2、3 步的顺序不能颠倒：先查事实再谈政策，否则模型会拿一段政策去解释一个它并不知道的订单。NIST AI RMF 的 Map 2.1 要求在需求阶段就写明「用哪类方法完成哪个任务」，正是因为方法一旦混用，后续的评估指标也会跟着失真（复核日期 2026-10-19）。

## 架构与选型

| 子问题 | 首选方案 | 理由 | 不适用时 |
| --- | --- | --- | --- |
| 订单状态、物流节点 | 规则 + 接口查询 | 答案是唯一事实，无需生成 | 接口不可用时返回「稍后查询」而非猜测 |
| 政策条款问答 | 检索 + LLM 组织语言 | 需要原文依据，问法多样 | 检索无结果时转人工 |
| 是否满足退货条件 | 规则判定 + LLM 解释 | 判定必须可复现、可审计 | 边界情形交人工复核 |
| 投诉情绪安抚 | LLM 起草 + 人工发送 | 表达开放，但对外承诺风险高 | 高情绪会话直接转人工 |
| 品类自动归类 | 传统机器学习 | 有历史标注、量大、容忍小错 | 新品类冷启动期用规则兜底 |

选型的分界线是「答案是否唯一」。唯一答案用规则或检索，多解表达用 LLM；有大量历史标注且需要规模化判断时，传统机器学习往往比 LLM 更便宜也更稳定。反过来，<u>用 LLM 去替代一条已经写清楚的业务规则，通常只会增加成本和不确定性，不会提升效果</u>。

## 最小示例

下面用两个路由版本说明「关键词覆盖」为什么是规则方案的真正成本。

```python
import re

def naive_route(query):
    # 版本 A：只认「退款」这个词
    return "rule:refund" if "退款" in query else "llm:compose_reply"

def layered_route(query, has_order_id):
    if has_order_id and re.search(r"物流|到哪|签收|发货", query):
        return "rule:order_status"        # 能查到结构化事实，不走模型
    if re.search(r"退|换|运费|保修|几天", query):
        return "search:policy_index"      # 需要政策原文作依据
    return "llm:compose_reply"            # 开放表达，交给模型组织语言

cases = [
    ("我的订单 20261018001 发货了吗", True),
    ("耳机拆封后还能退吗", False),
    ("你们服务态度太差了，我要投诉", False),
]
for q, oid in cases:
    print(f"{q!r:32s} A版={naive_route(q):20s} B版={layered_route(q, oid)}")
```

运行 `python3 route.py`：

```text
'我的订单 20261018001 发货了吗'          A版=llm:compose_reply    B版=rule:order_status
'耳机拆封后还能退吗'                      A版=llm:compose_reply    B版=search:policy_index
'你们服务态度太差了，我要投诉'                 A版=llm:compose_reply    B版=llm:compose_reply
```

A 版把前两条都推给了模型：一条本可以直接查库，一条本可以检索到明确条款。这不是模型能力问题，而是路由设计问题。B 版仍不完美——它认不出「拆封后能不能退」这类同义表达，也拦不住把「发票能不能退」误判为政策问题；因此真实系统通常还要在第 3 层加入语义检索作为兜底，并统计误路由率。

## 动手实验

### 前置条件

- Python 3 环境，无需第三方库。
- 一份可公开发布的 20 条脱敏客服问题样本（可自己改写）。

### 步骤

1. 把 20 条问题按「事实查询 / 政策依据 / 开放表达」人工标注为期望路径。
2. 用 `layered_route` 对 20 条逐条路由，记录实际路径。
3. 统计三类错误：本可走规则却走了模型、本需检索却直接生成、本该转人工却自动回复。
4. 为每一类错误写一条补丁：扩关键词、加语义检索、加风险词拦截。

### 预期结果

得到一张 20 行 × 3 列的路由对照表，以及至少 2 条明确可执行的补丁。

### 验证方法

- 让别人只看关键词表推断路由结果，与脚本输出比对。不一致说明规则难以维护。
- 检查是否存在「检索为空却仍返回答复」的分支，这属于必须修复的缺陷。

### 清理方法

删除临时脚本与样本副本。若样本来自真实工单，必须先脱敏，且不得提交到仓库。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 简单问题也慢且贵 | 所有请求都送进 LLM | 统计各路径占比 | 补齐规则与检索层，模型只做兜底 |
| 规则越加越多难以维护 | 用关键词堆砌代替语义判断 | 统计规则总数与近三月变更次数 | 把同义表达交给检索，规则只保留确定性判定 |
| 政策答案时对时错 | 检索命中过期文档 | 抽查引用条款的版本号 | 文档带版本与生效日期，检索按生效时间过滤 |
| 模型给出文档里没有的承诺 | 提示词未限制「只能依据给定条款」 | 检查无引用回答的比例 | 强制引用 + 无引用即转人工 |
| 换了模型后效果突然变差 | 提示词与路由依赖了旧模型的表达习惯 | 回归集在新模型上重跑 | 固定版本，发布前跑回归集 |

## 安全与生产注意事项

**<u>不要让生成环节直接触发写操作。</u>** 退款、改地址、发券都属于不可逆动作，应由规则判定 + 人工确认完成；模型只能生成建议文本。否则一次提示词漂移就可能变成批量错误退款。

**<u>检索为空时必须显式失败，而不是让模型自由发挥。</u>** 「检索不到相关条款」是一个合法的业务状态，必须映射到「转人工」或「告知用户稍后回复」；把它交给模型补全，等于用幻觉填补制度空白。

另外要防止规则与模型的口径打架：同一条政策在规则引擎和提示词里各写一遍，迟早不一致。应指定唯一权威来源（通常是政策文档），规则只引用条款编号。

## 本课总结

- **四类方案不是替代关系，而是分层关系。** 越确定的问题越应放在前面用便宜的手段解决。
- **可解释性来自路径设计，不来自模型解释。** 引用条款编号比让模型「说明理由」可靠。
- **规则的真实成本是词表覆盖与长期维护**，不是首次编写。评估规则方案时要算变更成本。
- **LLM 的强项是理解表达与组织语言**，把它用在需要唯一答案的判定上是错配。
- 每条路径都要定义失败降级，尤其是检索为空和校验不通过两种情形。

## 思考题

如果晴空商城的政策文档从 40 页增长到 400 页，且每月更新，原先的「关键词命中 + 检索」方案会遇到什么问题？你会如何调整分层顺序和评估方式？

参考思路：关键词覆盖会迅速失效，检索召回与排序成为主要瓶颈，需要引入语义检索、按文档版本与生效日期过滤、以及对检索结果做相关性排序。评估重点从「路由是否命中」转为「检索是否召回正确条款」与「引用是否支持结论」，并为文档更新建立回归集。

## 小测

1. 下列哪类任务最适合用规则系统而非 LLM？  
   A. 把客户投诉改写成温和措辞　B. 判断订单是否已发货　C. 归纳一段长对话　D. 生成三种退款话术
2. 为什么「检索为空」必须作为显式失败处理？
3. 传统机器学习相对 LLM 的主要优势是什么？在什么条件下成立？
4. 混合编排中「先查事实、再谈政策」的原因是什么？
5. 场景题：晴空商城想在会话里自动识别「要求退款」并立即调用退款接口。请指出这个设计至少两个问题，并给出替代方案。

## 答案与解析

1. **B。** 发货状态是唯一事实，规则加接口即可确定回答。A、C、D 都需要自然语言理解或生成，属于 LLM 的适用区。
2. 因为空结果意味着「没有依据」。若继续生成，模型会用语料中的通用说法填补，产生无法追溯的承诺；显式失败才能把风险交回给人。
3. 在量大、标注充足、判断标准稳定的任务上更便宜、更稳定、更容易做批量评估。条件是没有明显分布漂移；一旦业务规则变化导致样本分布改变，模型会静默退化，需要监控与重训。
4. 因为两者依赖不同的事实来源。订单事实来自订单系统，政策依据来自政策文档；顺序颠倒会让模型用政策语言解释一个它并不掌握的订单状态。
5. 问题一：把不可逆写操作交给概率系统，容错为零却无人工确认。问题二：缺少金额上限与权限校验，可能被诱导超额退款。替代方案：模型只识别意图并生成「建议退款」草稿，由规则校验金额与资格，客服确认后调用接口，并记录完整审计日志。

### 动手实验参考

合格的路由表应能看出「误路由」集中在哪一类表达上，并把补丁写成可执行动作（例如「新增 12 个同义说法」或「第 3 层改为语义检索，阈值 0.6」）。只写「继续优化」不算完成。
