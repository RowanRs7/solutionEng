# 准确性、延迟、成本与业务指标

## 为什么需要学习

评审会上，工程师报告「准确率 92%」，财务问「一单多少钱」，客服主管问「客户还要等多久」，三个问题都没被回答。上线后第一个月，账单是预算的三倍，p95 延迟 8 秒，而客服最关心的「一次解决率」几乎没有变化——因为模型答对了，但答的不是客户问的那件事。

> **核心结论：** 准确率只是模型层的一个数字；不做指标分层，就无法知道系统到底改善了业务。

## 学习目标

完成本课后，你能够：

- 区分模型层、系统层与业务层指标，并说明各自的采集方式。
- 用 token 用量与人工复核时长计算「每个已解决工单」的成本。
- 用 p50/p95 等分位数而不是平均值描述延迟，并解释尾部延迟的业务影响。

## 前置知识

- 回看上一课：[PoC、试点与生产项目的区别](06-poc-pilot-and-production.md)。
- 了解百分位数的含义：p95 表示 95% 的请求快于该值。
- 知道模型按输入与输出 token 分别计价，长提示会推高成本。
- 能运行 `python3`，示例只用标准库。

## 业务场景

售后助手试点一个月，数据摆在不同人手里：工程师有准确率与延迟日志，财务有模型账单，客服主管有一次解决率与工单时长。三方对「效果好不好」的判断互相矛盾。团队需要一个统一的指标口径，才能在下一阶段决定继续投入还是收敛范围。

## 核心概念

| 层级 | 指标 | 定义 | 采集方式 | 主要责任方 |
| --- | --- | --- | --- | --- |
| 模型层 | 任务成功率 | 在评测集上判断正确且引用有效 | 回归集离线评测 | 算法/工程 |
| 模型层 | 忠实度 | 回答内容能被引用条款支持 | 人工评审抽样 | 算法/业务 |
| 系统层 | p50 / p95 延迟 | 一半/95% 请求的端到端耗时 | 服务端埋点 | 工程/运维 |
| 系统层 | 错误率与降级率 | 报错、超时、转人工的比例 | 日志聚合 | 运维 |
| 业务层 | 一次解决率 | 同一会话内无需二次咨询即解决 | 工单回访/标记 | 业务负责人 |
| 业务层 | 草稿采纳率与改写率 | 客服直接发送 vs 修改后发送 | 客服端埋点 | 业务负责人 |
| 业务层 | 单位成本 | 每个已解决工单的总成本 | 账单 + 人力工时 | 财务/产品 |

*单位经济* 指单个业务单位（一个会话、一个已解决工单、一个客户）的收入与成本关系。*取舍曲线* 描述在不同配置下准确率、延迟与成本如何互相让步：扩大检索上下文能提准确率但增延迟与成本，缩小上下文反过来。

<u>只报平均值是延迟指标最常见的错误。</u> 平均值 1.8 秒的系统可能有 5% 的请求超过 8 秒，而这 5% 恰好是最复杂的会话——客户最需要帮助的时候系统最慢。

关于价格：截至 2026-10-19，各家供应商的计价单位与单价差异较大且调整频繁，本课不引用具体报价，示例中的单价为教学假设值，实际估算请以供应商官方价目表为准。

## 工作原理

指标体系建设按「自外向内」的顺序推进：

1. **先定业务指标。** 与业务方确认一个主指标（如售后工单的「首次响应时长」或「一次解决率」）与一个护栏指标（如投诉率不升高）。
2. **拆系统指标。** 主指标受哪些系统行为影响？若客户等待时间长，则看端到端 p95、检索耗时、模型首 token 延迟。
3. **拆模型指标。** 系统指标不达标时，才回到模型层看任务成功率、忠实度、格式合格率。
4. **定义采样与口径。** 明确统计窗口、样本来源、分母是什么（会话数还是工单数）、排除哪些流量（测试账号、内部会话）。
5. **算单位成本。** 成本 =（输入 token × 输入单价 + 输出 token × 输出单价）+ 人工复核成本 + 重试与失败成本，再除以已解决工单数。
6. **画取舍曲线。** 在若干配置下同时测准确率、p95 与单位成本，找出满足业务门槛的最小成本点。
7. **设告警与复盘节奏。** 指标越线触发谁、多久复盘一次、是否触发回滚。

第 4 步经常被忽略，导致同一个「准确率」在不同报表里分母不同。第 6 步是决策依据：如果业务能接受 3 秒延迟，就不必为 1.5 秒付出双倍成本。NIST AI RMF 的 Measure 2.1 要求记录测试集、指标与工具细节，Measure 3.1 要求持续跟踪已识别风险，正是为了让这些数字可复现、可比较（复核日期 2026-10-19）。

## 架构与选型

| 优化手段 | 改善的指标 | 副作用 | 适用前提 |
| --- | --- | --- | --- |
| 压缩上下文、减少检索片段 | 延迟、成本 | 准确率与忠实度下降 | 问题集中在少数条款时 |
| 换更小的模型 | 成本、延迟 | 复杂表达与长上下文能力下降 | 已用评测集验证达标 |
| 流式输出 | 感知延迟 | 不改变总耗时，错误也更早暴露 | 用户界面支持逐步展示 |
| 缓存高频问答 | 延迟、成本 | 政策更新后可能返回旧答案 | 缓存带版本与失效策略 |
| 增加人工复核 | 准确率、合规 | 成本上升、处理时长增加 | 高风险动作必须 |
| 批处理离线任务 | 成本 | 无法实时响应 | 非即时场景（如日报） |

选型的依据是业务门槛而不是单项最优。当业务要求「2 分钟内首响」时，成本可以适度让步；当业务按会话计费、毛利很薄时，则应优先压缩上下文并提高缓存命中率。<u>在没有评测集的情况下调这些参数，等于用生产流量做实验。</u>

## 最小示例

下面同时计算分位延迟与单位成本，展示「模型很便宜、人力很贵」这一常见结构。

```python
import math

latencies = [1.2, 1.4, 1.5, 1.6, 1.8, 1.9, 2.0, 2.1, 2.2, 2.4, 2.5, 2.7,
             2.9, 3.1, 3.4, 3.6, 4.0, 4.6, 5.2, 7.8]   # 单位：秒

def percentile(values, p):
    ordered = sorted(values)
    idx = max(0, math.ceil(p / 100 * len(ordered)) - 1)   # 最近秩法
    return ordered[idx]

in_tokens, out_tokens = 3200, 380
in_price, out_price = 2.0, 8.0            # 假设单价：元/百万 token，非真实报价
llm_cost = (in_tokens * in_price + out_tokens * out_price) / 1_000_000

review_rate, review_seconds, hourly = 0.35, 90, 45.0
review_cost = review_seconds / 3600 * hourly * review_rate
resolution_rate = 0.72                     # 72% 的会话一次解决

per_conversation = llm_cost + review_cost
per_resolved = per_conversation / resolution_rate

print(f"p50={percentile(latencies,50):.1f}s p95={percentile(latencies,95):.1f}s")
print(f"单次会话模型成本 {llm_cost:.4f} 元，人工复核 {review_cost:.4f} 元")
print(f"每个已解决工单 {per_resolved:.4f} 元；人力占比 {review_cost/per_conversation:.1%}")
```

运行 `python3 metrics.py`：

```text
p50=2.4s p95=5.2s
单次会话模型成本 0.0094 元，人工复核 0.3937 元
每个已解决工单 0.5600 元；人力占比 97.7%
```

三个结论：模型成本不到一分钱，人工复核占 97.7%，说明优化重点不在模型单价；除以一次解决率后单工单成本从 0.40 元升到 0.56 元，未解决的会话同样花钱；p50 与 p95 相差一倍以上，只报平均值会掩盖尾部体验。注意分母口径——如果换成「会话数」，成本会显得更低，但业务价值只体现在已解决工单上。

## 动手实验

### 前置条件

- 一份 20 条以上的脱敏延迟记录（可用教学数据）。
- 一份会话数与已解决数的统计。

### 步骤

1. 计算 p50、p90、p95，并与平均值对比，写出差异。
2. 按上面的公式估算单位成本，列出成本构成占比。
3. 把一次解决率改为 0.6 与 0.8 各算一次，观察单位成本变化。
4. 写一句：如果要把 p95 从 5.2 秒降到 3 秒，你愿意牺牲哪个指标、牺牲多少。

### 预期结果

得到延迟分位数、成本构成与敏感性分析三份结果；能指出成本主项与延迟尾部来源。

### 验证方法

- 让别人用你的口径重算一遍，数字应一致；不一致说明分母或窗口没写清。
- 检查是否所有指标都有采集方式；没有埋点的指标不能作为验收依据。

### 清理方法

删除临时脚本；把口径说明写入需求文档。延迟日志中不得包含客户原文。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 准确率高但业务无改善 | 只测模型层，未对齐业务指标 | 对比试点前后一次解决率 | 补业务指标与对照组 |
| 账单远超预算 | 只算模型费，忽略重试与人工 | 对齐账单与调用量 | 全量计入并设预算告警 |
| 平均延迟正常但客户抱怨慢 | 只报平均值 | 查看 p95 与最慢请求分布 | 改为分位数并优化尾部 |
| 不同报表数字打架 | 分母、窗口、排除规则不一致 | 交叉核对口径定义 | 统一口径并写入文档 |
| 优化后效果反而下降 | 无评测集，凭感觉调参 | 回放历史评测集 | 先建基线再调参 |

## 安全与生产注意事项

**<u>不要为了让指标好看而取消人工复核或抽检。</u>** 复核成本高、耗时明显，很容易在成本压力下被「优化」掉；但这会同时移除错误发现机制，让指标在短期内改善、真实风险上升。

**<u>成本指标必须按租户或业务线分摊，并监控长尾。</u>** 平均值会掩盖少数超长会话的消耗；当某个客户或某类问题反复触发超长上下文时，成本与延迟会同时失控，却不会出现在平均数字里。

此外，指标面板要能区分「模型不可用时的降级流量」，否则故障期间的低延迟会被误读为性能提升。

## 本课总结

- **指标必须分层：业务层决定价值，系统层决定体验，模型层解释原因。**
- **延迟用分位数描述**，p95 往往比平均值更能反映客户感受。
- **单位成本要除以已解决量**，并计入人工复核与失败重试。
- **取舍曲线是决策工具**：先确定业务能接受的门槛，再找最便宜的配置。
- 口径（分母、窗口、排除规则）不一致会让所有比较失效。

## 思考题

如果业务方要求「把 p95 延迟从 5.2 秒压到 2 秒，同时不增加成本」，你会先动哪三个杠杆？各自可能损失什么？

参考思路：先减少检索片段与上下文长度（损失召回与忠实度）、对流式输出改善感知延迟（不改变总耗时）、对高频问题加缓存（需处理版本失效）。若三者仍不足，则需承认目标不可同时满足，并与业务方讨论放宽延迟或增加预算。

## 小测

1. 下列哪个指标属于业务层？  
   A. 忠实度　B. 一次解决率　C. p95 延迟　D. 格式合格率
2. 为什么延迟指标要看 p95 而不是只看平均值？
3. 单位成本计算中为什么必须除以一次解决率？
4. 把上下文从 10 段减到 3 段，通常会同时改善什么、牺牲什么？
5. 场景题：团队报告「准确率 92%，成本每会话 0.01 元」，据此申请扩大规模。请指出这份报告至少缺少哪两类信息，并说明它们如何改变结论。

## 答案与解析

1. **B。** 一次解决率直接反映业务效果。A、D 属于模型层；C 属于系统层。
2. 因为平均值掩盖尾部。少数慢请求常对应最复杂的会话，客户体验由最慢的那部分决定；只看平均值会误判系统已达标。
3. 未解决的会话同样消耗模型与人力成本，却不产生业务价值。不除以解决率会低估真实成本，导致「越用越便宜」的错误预期。
4. 改善延迟与成本，牺牲召回率与忠实度（可能漏掉关键条款）。是否可接受取决于评测集上准确率的下降幅度。
5. 缺少：业务层效果（一次解决率、采纳率、处理时长变化）与完整成本构成（人工复核、失败重试、长尾消耗）。若采纳率低或需大量改写，那么准确率再高也无法带来业务收益，扩大规模只会放大成本。

### 动手实验参考

合格的分析应能指出成本主项、延迟尾部来源，并给出一个带条件的取舍建议（例如「p95 降到 3 秒需牺牲约 3 个百分点的准确率」）。只报告数字而不给结论，不算完成。
