# 工具与 Agent 阶段综合测评

## 学习目标

检验能否把九课串成一份可评审的设计：每类动作都有契约与权限，编排形状与诉求分布匹配，失败可识别、可收敛、可复盘。建议闭卷做概念题，再对照参考答案自评。

## 知识检查清单

- [ ] 能画出“请求 → 工具调用 → 回填 → 再请求”的循环，说清 `tool_call_id` 与 `arguments`，并列出四个以上终止条件。（第 1 课）
- [ ] 能写出含边界与副作用的描述、收紧的 Schema 与统一返回信封。（第 2 课）
- [ ] 能按“主体 × 操作 × 对象”判断调用是否允许，识别三类过度授权并为高影响动作配审批令牌。（第 3 课）
- [ ] 能用控制流归属区分 workflow 与 agent，并按诉求分布给出编排选择。（第 4 课）
- [ ] 能写出状态、事件、守卫与超时去向，说明参数快照如何防“批小用大”。（第 5 课）
- [ ] 能把任务拆成带完成判据的计划项，区分有效反思与无信号的自评。（第 6 课）
- [ ] 能区分会话状态、短期与长期记忆，并给出写入、过期与删除策略。（第 7 课）
- [ ] 能说明 MCP 中 host、client、server 的职责，以及 MCP 不接管的权限与终止责任。（第 8 课）
- [ ] 能设计分层超时、重试预算与幂等键，并识别“结果未知”这一独立状态。（第 9 课）

## 概念题

共 40 分：第 1–8 题四选一，每题 2 分；第 9–16 题简答，每题 3 分。四选一也要写一句依据；简答按“结论 + 机制 + 边界”作答。

1. 【第 1 课】模型返回 `tool_call`，`arguments` 是 `{"order_id": "SO-2026-0001"}` 字符串。应用的下一步是？
   A. 直接当对象传给下游 API
   B. 解析 JSON、按 Schema 校验、以鉴权主体做对象级授权，通过后执行
   C. 先执行，失败再回填错误
   D. 让模型重新输出直到格式正确

2. 【第 1 课】关于循环终止，最可靠的做法是？
   A. 相信模型输出的“已完成”结语
   B. 只在工具报错时终止
   C. 组合硬轮数、预算与超时、审批拒绝、业务终态，任一触发即收敛
   D. 固定 10 轮，达到即视为成功

3. 【第 2 课】`get_order` 返回 60 行明细，含内部风控标签。回填给模型时应？
   A. 原样回填，让模型自己挑
   B. 裁剪到决策所需字段，去掉敏感标签，附来源与时间
   C. 只回填 `{"ok": true}`
   D. 改写成一大段自然语言摘要

4. 【第 2 课】开启供应商“严格模式”后，服务端还要校验参数吗？
   A. 不需要，严格模式保证 Schema 合规
   B. 需要；它只降低跑偏，不判断业务合法性，也不承担授权、归属与幂等
   C. 只校验类型，枚举交给模型
   D. 只在前端校验一次

5. 【第 3 课】客服在工单后台代客户提交退款，权限设计正确的是？
   A. 用服务账号，因为客服有权限
   B. 主体取自真实客户，操作人记为客服，对象级授权校验订单与工单归属，全程审计
   C. 用客服账号，跳过对象级授权
   D. 让模型在参数里传 `user_id`

6. 【第 3 课】审批令牌防“批小用大”的关键是？
   A. 有效期设为 7 天
   B. 绑定审批时的参数快照（金额上限、对象 ID、参数哈希），执行前比对不一致即拒绝
   C. 审批人在群里回复“同意”
   D. 只校验一次，之后复用

7. 【第 4 课】76% 报修是四类固定症状，24% 是长尾。最合适的编排是？
   A. 全部交给一个 agent 自由选工具
   B. 全部写成 workflow，长尾也逐条枚举
   C. 主干 workflow 覆盖固定症状，长尾进受限 agent，不可逆动作留在确定性一侧
   D. 每个症状拆一个 agent

8. 【第 4 课】判断编排属于 workflow 还是 agent 的最直接标准是？
   A. 是否调用大模型
   B. 是否调用多个工具
   C. 下一步由代码决定，还是由模型在循环中依据反馈决定
   D. 是否设置人工审批

9. 【第 5 课】审批断点必须包含哪四类要素？缺“参数快照”会发生什么？

10. 【第 5 课】为什么超时是“正常状态”而非异常？给出三种超时去向，并说明“一直 pending”的代价。

11. 【第 6 课】把四类反思信号按可信度排序，并解释为什么“九轮自我反思”通常无益。

12. 【第 6 课】计划项为什么要带完成判据？说明计划漂移与“必须重规划”的区别。

13. 【第 7 课】区分会话状态、短期记忆与长期记忆；客户要求“删除我的数据”时该删哪些，为什么删除能力要在设计期做？

14. 【第 8 课】说明 MCP 中 host、client、server 的职责，并指出 MCP 不接管哪些责任。

15. 【第 9 课】“备件出库”读超时。给出超时分层、重试预算与幂等键，并说明为什么必须区分“失败”与“结果未知”。

16. 【第 9 课】沙箱与审计是不是越严越好？举两个“过度设计”制造新问题的例子，并说明审计至少要有哪些字段。

### 常见错答分析

| 题目 | 常见错答 | 为什么不充分 | 纠正方向 |
| --- | --- | --- | --- |
| 1–2 | 认为模型会自己校验参数、判断完成。 | 模型只产出意图，没有执行权与权限概念；自评不构成终止判据。 | 校验、授权、终止写进应用代码，多条件组合。 |
| 3–4 | 把完整响应回填，或把严格模式当安全边界。 | 噪声淹没关键事实并扩大泄露面；生成合规不等于执行安全。 | 按决策所需裁剪；服务端校验不可省。 |
| 5–6 | 用服务账号图省事，审批做成口头同意。 | 失去可归因性；审批不绑定参数就约束不了执行内容。 | 主体来自鉴权；令牌绑定快照。 |
| 7–8 | 以“用了模型”“工具多”判断 agent，或全量 agent 化。 | 混淆技术选型与控制流归属，牺牲可测性。 | 按控制流判断，不可逆动作确定性化。 |
| 13–16 | 长期记忆塞进会话表；超时即重试；日志越全越好。 | 作用域错配导致删不干净；读超时不等于没执行；全量日志是泄露面。 | 按作用域拆存储；同键重试加对账。 |

## 场景分析

> **本测评刻意换场景，检验迁移。** 下面不是晴空商城，但同属“AI 助手接工具、按流程办事”的领域；每小问后标注对应课程。

“恒锐精密制造”有三座工厂、约 1200 台设备。设备档案在自建 EAM，备件库存在 ERP，维保外包给四家服务商，工单在「维保通」。操作工用车间平板报修：“3 号线 2 号空压机异响，下午要停产检修。”

已知条件：

- 过去三个月 12400 张工单中，76% 是“异响、漏油、温度高、报警码”四类；24% 是连锁故障、老旧设备无手册等长尾。
- 设备档案查询毫秒级；维修知识库检索 200–800 毫秒。
- 派工接口 P99 约 4 秒，偶发 `502` 与 `429`；同设备同故障 30 分钟内重复报修常见。
- 备件出库走 ERP，单次 2–6 秒，必须审批；单次上限 5000 元，超限升级到设备主管。
- 四家服务商分 4 小时、8 小时、次日三档；关键设备停机损失约每分钟 800 元。
- 车间 Wi-Fi 可能中断 10–30 分钟，恢复后补传。审计要求：谁批准了停机与备件出库。

请回答：

1. 列出 5–7 个工具，标注读/写、幂等键与是否需要审批；指出哪些参数必须来自权威数据而不能由模型填写。（对应：[01-function-calling-mechanics.md](01-function-calling-mechanics.md) 的循环与分工；[03-tool-permissions-and-least-privilege.md](03-tool-permissions-and-least-privilege.md) 的三元组）
2. 把“创建派工单”写成强描述 + 严格 Schema + 统一信封，并给出至少两条必须挡在执行前的约束。（对应：[02-tool-schemas-and-descriptions.md](02-tool-schemas-and-descriptions.md)）
3. 按 76/24 的分布选编排形状：写出主干 workflow 的节点与终止条件，说明受限 agent 的边界，以及哪些动作不许 agent 自行决定。（对应：[04-workflow-vs-agent.md](04-workflow-vs-agent.md)；[06-agent-planning-execution-and-reflection.md](06-agent-planning-execution-and-reflection.md)）

5. 给出断网补传与重复报修的去重方案，以及 `502` 与 `429` 的不同处理；说明读超时为什么属于“结果未知”。（对应：[09-tool-reliability-sandbox-and-failure-modes.md](09-tool-reliability-sandbox-and-failure-modes.md)）

## 架构师交付物练习

产出《设备维保助手工具与编排设计说明书》，每张表都要能被当场追问。结构提示：每行只写一个可验证的决定；数字不确定标“待测”，并写责任人与期限。

1. **工具契约表**：工具名、读/写、关键参数与约束、信封字段、幂等键。
2. **权限与审批表**：主体、操作、对象、判定依据、审批人、令牌绑定内容。
3. **编排表**：诉求类别、占比、编排方式、工具白名单、终止条件与预算、失败兜底。
4. **状态机表**：状态、允许事件、守卫、超时行为（过期/升级/转人工）。
5. **可靠性与审计表**：依赖、分层超时、重试预算、幂等键、已知失败模式、审计字段。
6. **边界与开放问题**：不做的事、待测数字、依赖方与确认期限。

## 参考答案与解析

### 概念题答案

1. **B。** `arguments` 是 JSON 文本，须解析、校验、按鉴权主体授权后再执行。A 把文本当对象；C 先执行已有副作用；D 解决不了越权。
2. **C。** 终止是应用职责，靠多条件组合。A 把模型结语当判据；B 成功路径空转烧预算；D 到轮即成功是伪造终态。
3. **B。** 回填服务于下一个决策，字段越少越准。A 噪声淹没事实并扩大泄露面；C 丢了状态与金额；D 摘要二次失真。
4. **B。** 严格模式只保证按 Schema 生成，不判断业务合法性与归属。A 把生成合规当执行安全；C、D 仍放非法对象进执行。
5. **B。** 代操作要同时留下“代表谁”与“谁在操作”。A 失去可归因性；C 跳过对象级授权即越权；D 把权限交给模型参数。
6. **B。** 只有快照比对才拦得住“批 200 执行 900”。A 长有效期货放大风险；C 群聊回复不可核验；D 可换参重放。
7. **C。** 固定诉求用 workflow 换确定性，长尾用受限 agent，不可逆动作留给确定性一侧。A 牺牲可测性；B 长尾无法枚举；D 只增加调用与错误传播。
8. **C。** 边界在控制流归属：代码写死是 workflow，模型在循环中决定是 agent。A 混淆“用了模型”与“模型控制”；B 提示链也调多工具；D 审批只是控制点。
9. 四要素：状态持久化、事件与守卫、参数快照（含哈希）、时限与恢复协议。缺快照时批准的是“意图”而非具体值，执行可换金额或对象。
10. 依赖会慢、人会不回，超时必然发生。去向有逾期可重发、升级、转人工。一直 pending 会占住资源，让工单与审批单长期不一致。
11. 可信度递减：机器可判定 → 规则/数据校验 → 人工反馈 → 模型自评。自评不引入外部信息，九轮只是重复表态。
12. 没有判据就看不出该不该进下一步，也无法归因失败。计划漂移是新信息未回写计划；重规划是前提被推翻时整体重写。
13. 会话状态是流程变量与待办；短期记忆是会话内消息与工具结果；长期记忆是跨会话事实与偏好。删除要覆盖三类存储及派生索引，索引重建只能设计期做。
14. host 是发起连接的模型应用，负责用户同意与权限；client 是与某个 server 对应的连接器；server 提供资源、提示与工具。MCP 只标准化暴露与发现，权限、审批、终止仍在 host。
15. 分层：单工具 3–5 秒、单轮 30–60 秒、整链路 60–120 秒、审批按业务时限。重试只对可重试错误并受预算约束；幂等键用业务标识。读超时说明下游可能已出库，属结果未知，须同键查询。
16. 不是。无差别全量重试把一次超时变三次出库；全量日志把令牌留住，本身成泄露面。审计至少要能定位主体、审批人、参数快照与结果。

### 场景分析参考思路

- **问 1**：`get_equipment`、`search_repair_knowledge`、`check_spare_stock`（读）；`create_dispatch`（写，幂等键 = 设备号 + 故障码 + 时间窗）、`request_part_issue`、`request_downtime`（写，需审批）。设备归属、合同等级、备件单价必须来自 EAM/ERP，否则模型能挑便宜设备或更快的时效。
- **问 2**：描述写“为已确认故障创建派工单（写），查状态请用 `get_equipment`”；Schema 用枚举与格式收敛故障码、设备号并拒绝未声明字段；信封含 `ok`、`error_code`、`retryable`、`dispatch_id`。硬约束：故障码命中枚举，报修时间不晚于当前。
- **问 3**：主干为识别故障码 → 查设备与合同 → 检索手册 → 生成步骤 → 按时效派工 → 回填；终止于派工成功、审批拒绝、超时、预算耗尽。长尾进受限 agent（白名单、步数 ≤ 6）；停机与出库不许 agent 决定。
- **问 4**：状态为草稿、待审批、已批准、已出库、已拒绝、已过期；事件为 `submit`、`approve`、`reject`、`expire`、`execute`；守卫为审批人 ≠ 发起人、金额 ≤ 5000、哈希一致；30 分钟转 `expired`，二次超时升级。快照让“批准 3000 元 A 型”执行不成“9000 元 B 型”。
- **问 5**：去重键 `(equipment_id, fault_code, 时间窗)`，30 分钟内同故障返回已有工单；补传带客户端序号，由唯一约束吸收。`502` 有预算重试，`429` 按 `Retry-After`；读超时属结果未知，同键查询或进对账。
- **问 6**：可记设备历史结论与服务商等级（来源为工单与合同），不可记模型的“疑似故障”推测或他厂记录。先做分组路由，因为单 agent 更便宜、错误更可见；确需拆时每角色独立主体与结果契约。
- **常见错误**：设备号交给模型；只设单工具超时；审批只记“已同意”；重复报修当新工单。

| 权限与审批 | 主体 = 报修操作工；操作 = 申请备件出库；对象 = 指定备件行；依据 = EAM 归属 + ERP 库存；审批人 = 设备主管（> 5000 元）；令牌绑定金额、备件行与哈希。 |
| 编排 | 固定症状占 76% 走 workflow；长尾 24% 进受限 agent，步数 ≤ 6；停机与出库不进 agent。 |
| 状态机 | 待审批 → 已批准 → 已出库；守卫含审批人合法、金额未超、参数未变；30 分钟转 `expired`，二次超时升级。 |
| 可靠性与审计 | 派工 P99 4 秒，单工具超时 5 秒、整链路 90 秒；重试 2 次、累计 ≤ 6 秒；审计含主体、审批人、参数快照、结果与 `trace_id`。 |
| 边界与开放问题 | 不做自动停机决策；价格与时效以 ERP/EAM 为准；补传窗口“待测”，责任人为车间 IT，期限两周。 |

合理答案可以有不同工具划分或数字，但必须标明未经确认的假设，不能把建议写成已批准承诺。
