# 会话状态、短期记忆与长期记忆

## 为什么需要学习

客户第二次来电时说：“我上次讲过，退款退回银行卡，不要优惠券。”助手已经忘了——上一通电话结束时，会话表里的记录被清空，因为没有字段保存这条偏好。同一个助手还在另一件事上过度记忆：半年前某次工具返回里有个“疑似异常”的内部标签，被它写进客户画像，之后每次服务都带着这个成见。

两个方向都出错：**该记的没记，不该记的记太久**。会话与记忆不是“把历史存下来”这么简单，它是一组关于作用域、写入者、保留期与可删除性的决策。

> **核心结论：** 记忆是写操作，必须和业务数据一样治理——谁能写、写多久、谁能读、如何删。

## 学习目标

完成本课后，你能够：

- 用作用域与生命周期区分会话状态、短期记忆与长期记忆，并各举一例。
- 为一条记忆设计写入规则：允许来源、字段白名单、过期时间。
- 说明摘要压缩与截断对回答质量的影响，并给出选择依据。
- 识别记忆污染与跨租户串话的风险点与验证方法。

## 业务场景

售后助手的使用形态有三种：网页自助（一次会话几分钟）、客服工单（可能跨天）、电话回访（跨周）。同一位客户 `C-1001` 的偏好（退款到银行卡、只在工作日联系）应跨会话生效；而“这一单正在申请退款”属于会话内状态，单子结束即失效。

团队还要回答一个具体问题：客户在页面上点“删除我的数据”，系统要删掉哪些表里的哪些行。

## 核心概念

| 术语 | 含义 | 本场景中的体现 |
| --- | --- | --- |
| *会话*（session/thread） | 一段连续交互的容器，有唯一 ID | 网页客服窗口的一次对话 |
| *短期记忆* | 会话内的消息历史与中间状态 | 已查过哪些订单、当前在等审批 |
| *检查点*（checkpoint） | 把会话状态持久化以便恢复 | 挂起等审批后继续 |
| *长期记忆* | 跨会话保留的、与用户相关的事实 | 退款偏好、联系方式偏好 |
| *命名空间* | 长期记忆的隔离维度 | 按 `user_id` 或租户划分 |
| *写入策略* | 决定“什么内容、何时、以什么来源写入” | 只写用户确认过的事实 |
| *记忆污染* | 错误或恶意内容被长期保留 | 注入文本被当作客户属性记住 |
| *上下文压缩* | 用摘要或裁剪控制历史长度 | 长会话保留最近 N 轮 + 摘要 |

三类存储常被混为一谈，实际边界如下：

| 维度 | 会话状态 | 短期记忆 | 长期记忆 |
| --- | --- | --- | --- |
| 作用域 | 单次会话 | 单次会话 | 跨会话，按用户/租户 |
| 典型内容 | 步骤、待审批项、临时变量 | 消息历史、工具结果 | 偏好、已验证事实、历史结论 |
| 生命周期 | 分钟到小时 | 会话结束即失效 | 天到年，需保留期策略 |
| 写入者 | 应用代码 | 应用代码 | 受控的抽取过程或显式确认 |
| 主要风险 | 恢复不一致 | 上下文超限、噪声 | 污染、越权、难删除 |

## 工作原理

一条记忆从产生到被召回要走六步：

1. **建立会话。** 生成会话 ID，绑定已验证的用户身份，设置闲置过期时间。会话 ID 不能由客户端随意指定他人 ID。
2. **逐轮写入。** 每轮把用户消息、助手回复、工具结果写入历史；同时维护结构化状态（当前订单、审批进度），避免把这些事实只留在自然语言里。
3. **压缩。** 接近上下文上限时，用摘要替换早期消息，或按“最近 N 轮 + 关键事实”裁剪。摘要会丢细节，涉及金额、时效的数字应保留在结构化状态而不是摘要里。
4. **抽取长期记忆。** 会话结束或用户明确表达偏好时，抽取候选记忆。抽取结果必须带来源（用户确认 / 订单校验 / 工具推断）与置信度。
5. **写入校验。** 只接受白名单来源；对手机号、地址、证件号等字段做过滤或加密存储；设置过期时间与可见命名空间。
6. **召回与注入。** 召回时先按命名空间过滤（当前用户、当前租户），再按相关性排序，只注入少量高价值条目。注入内容要标明“这是历史记忆，可能过期”。

关键权衡在压缩方式：

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 全量保留 | 信息不丢 | 很快超限，成本与延迟上升 |
| 截断最近 N 轮 | 简单、可预测 | 早期承诺与约束被丢掉 |
| 摘要 | 保留语义 | 数字易失真，摘要本身也可能出错 |
| 结构化事实 + 摘要 | 关键数字进状态，叙述进摘要 | 需要设计状态字段 |

## 架构与选型

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| 供应商托管会话（会话 ID + 服务端历史） | 快速上线、单供应商 | 数据落在供应商侧，跨供应商迁移困难 |
| 自建会话表（数据库） | 需要审计、与业务库同事务 | 需处理并发、清理与索引 |
| Redis/缓存 | 高频、短生命周期、延迟敏感 | 持久性弱，需要降级策略 |
| 长期记忆库（向量或文档存储） | 跨会话个性化 | 需要写入治理与删除链路 |

选型判断：**会话状态跟业务走，长期记忆跟合规走。** 会话状态应与订单、工单在同一事务边界内，便于审计；长期记忆则要能回答“这条是谁写的、依据什么、什么时候删”。

## 最小示例

下面的示例实现会话过期、记忆写入过滤与按用户召回。运行环境 Python 3.9+。

```python
import re
from datetime import datetime, timedelta, timezone

NOW = datetime(2026, 10, 19, 10, 0, tzinfo=timezone.utc)
SESSIONS, MEMORY = {}, []
ALLOWED_SOURCES = {"user_confirmed", "order_verified"}   # 1) 只接受可追溯的来源
PHONE = re.compile(r"1[3-9]\d{9}")                        # 2) 粗粒度 PII 采样

def get_session(session_id, user_id, now, ttl_minutes=30):
    """会话按身份绑定，避免客户端拿别人的 session_id 读历史。"""
    s = SESSIONS.get(session_id)
    if s and s["expires_at"] > now and s["user_id"] == user_id:
        return s
    s = {"user_id": user_id, "messages": [], "state": {},
         "expires_at": now + timedelta(minutes=ttl_minutes)}
    SESSIONS[session_id] = s
    return s

def append_turn(session_id, user_id, role, content, now):
    s = get_session(session_id, user_id, now)
    s["messages"].append({"role": role, "content": content})
    s["expires_at"] = now + timedelta(minutes=30)         # 3) 活跃即续期
    return s

def remember(user_id, key, value, source, now, ttl_days=90):
    """写入长期记忆：来源白名单 + PII 过滤 + 同键覆盖。"""
    if source not in ALLOWED_SOURCES:                      # 4) 工具推断不得入长期记忆
        return "skip:unverified_source"
    if PHONE.search(str(value)):
        return "skip:pii"
    MEMORY[:] = [m for m in MEMORY if not (m["user_id"] == user_id and m["key"] == key)]
    MEMORY.append({"user_id": user_id, "key": key, "value": value, "source": source,
                   "expires_at": now + timedelta(days=ttl_days)})
    return "stored"

def recall(user_id, query, now, top_k=2):
    """召回：先按用户命名空间隔离，再过滤过期，最后按相关性排序。"""
    hits = [m for m in MEMORY if m["user_id"] == user_id and m["expires_at"] > now]
    hits.sort(key=lambda m: query in str(m["value"]), reverse=True)
    return hits[:top_k]

s = append_turn("s-1", "C-1001", "user", "退款请退回银行卡，不要优惠券", NOW)
print("会话消息数:", len(s["messages"]))
print("确认来源:", remember("C-1001", "refund_channel", "退回银行卡", "user_confirmed", NOW))
print("未确认来源:", remember("C-1001", "fraud_label", "疑似异常", "tool_inference", NOW))
print("含手机号:", remember("C-1001", "contact", "13800001111", "user_confirmed", NOW))
print("本人召回:", [m["key"] for m in recall("C-1001", "退款", NOW)])
print("他人召回:", [m["key"] for m in recall("C-2002", "退款", NOW)])
print("半年后召回:", [m["key"] for m in recall("C-1001", "退款", NOW + timedelta(days=200))])
```

预期输出：

```text
会话消息数: 1
确认来源: stored
未确认来源: skip:unverified_source
含手机号: skip:pii
本人召回: ['refund_channel']
他人召回: []
半年后召回: []
```

读法：第二、三行说明写入侧的两道闸门；第四、五行说明读侧的名字空间隔离；最后一行说明过期策略生效后记忆不再影响服务。真实系统还应把“谁删除了哪条记忆”记入审计。

## 动手实验

**前置条件**：Python 3.9+，保存为 `memory.py`。

**步骤**：

1. 运行，核对七行输出。
2. 把 `ttl_days` 改成 1，重新运行“半年后召回”，确认过期逻辑。
3. 增加 `forget(user_id, key)`，实现“删除我的数据”并验证召回变空。
4. 在会话里追加 30 轮消息，实现“保留最近 10 轮 + 一条摘要”的压缩，观察 tokens 估算变化。

**预期结果**：步骤 3 删除后本人召回为空；步骤 4 中消息列表长度稳定在 11 条左右，摘要仍保留关键金额与时效。

**验证方法**：对 `remember`/`recall` 写单元测试，覆盖来源非法、PII、过期、跨用户四类；对压缩函数断言“关键字段不被丢弃”。

**清理方法**：删除脚本；示例数据为虚构，无真实个人信息。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 客户重复陈述同一偏好 | 偏好只存在会话内，会话结束即丢 | 检查该字段是否存在长期记忆库 | 抽取为带来源的长期记忆 |
| 助手引用过时的结论 | 长期记忆无过期，或未标注时间 | 抽样查看记忆条目的创建时间 | 加 TTL 与“可能过期”标注 |
| A 客户看到 B 客户的信息 | 召回未按命名空间过滤 | 用两个用户交叉查询 | 强制按 `user_id`/租户前缀过滤 |
| 长会话后半段答非所问 | 历史超限被静默截断 | 统计注入消息数与截断点 | 摘要 + 结构化状态，关键数字不进摘要 |
| 记忆里出现内部标签 | 工具推断被写入长期记忆 | 查记忆条目的 `source` 字段 | 来源白名单，只接受用户确认或权威校验 |

## 安全与生产注意事项

**<u>记忆是持久化的注入载体：一次污染会长期影响后续所有会话。</u>** 如果助手把网页摘要、工单正文里的“客户已同意全额退款”当成事实写入记忆，后续每次服务都会带着这个错误前提。控制手段是来源白名单、写入前人工或规则复核，以及给记忆条目保留可追溯的原文链接。

**<u>跨租户串话与超期保留都是合规事故，而不只是体验问题。</u>** 召回必须先做租户/用户过滤再做相似度排序；删除请求要能覆盖会话表、记忆库与向量索引三处，并留下删除证明。OpenAI Agents SDK 的会话文档也提示：会话存储本身是一个信任边界，本地文件型存储不应被当作多租户隔离手段。

## 本课总结

- **会话状态、短期记忆、长期记忆的作用域不同**，混用会造成“该记的没记、不该记的删不掉”。
- 记忆写入要有来源白名单、PII 过滤与过期时间，写入过程要可审计。
- 压缩方式影响回答质量：关键数字放结构化状态，叙述放摘要。
- 召回先隔离命名空间，再做相关性排序。
- 删除能力要在设计阶段就纳入，而不是上线后补。

## 思考题

产品希望“记住客户偏好以提升体验”，合规要求“最小化收集且可删除”。请给出一份记忆字段清单（不超过 6 个字段），并说明每个字段的来源、保留期与删除方式。

参考思路：优先保留与服务直接相关且用户明确表达过的字段，例如退款渠道偏好、联系时段、发票抬头类型；保留期按业务必要设置（如 90 天或账户存续期），删除时同步清理会话、记忆库与索引副本，并提供可验证的删除记录。评价标准看两点：字段是否都有明确来源、删除链路是否覆盖所有副本。

## 小测

1. 会话状态与长期记忆的核心区别是什么？
2. 下列哪项最不应写入长期记忆？  
   A. 用户确认的退款渠道偏好　B. 订单校验得到的发票抬头　C. 某次工具推断的“高风险客户”标签　D. 用户选择的联系时段
3. 为什么召回时要先做命名空间过滤再做相似度排序？
4. 摘要压缩的主要风险是什么？
5. 场景题：客户在网页点“删除我的数据”，工程只删了会话表。请指出遗漏与验证方法。

## 答案与解析

1. 作用域与生命周期：会话状态服务单次会话、随会话结束失效；长期记忆跨会话保留，需要来源、保留期与删除策略。两者在写入者与风险上也不同。
2. **C。** 工具推断缺少用户确认与权威依据，一旦写错会长期影响服务，且难以追溯。A、B、D 都有明确来源或用户意图。
3. 因为相似度排序会把语义相近但属于他人的内容排到前面，若先排序再过滤，实现上容易漏掉过滤步骤；先隔离再排序，可保证任何返回结果都在授权范围内。
4. 数字与条件容易被改写或省略（金额、时效、例外条款），而模型可能把摘要当作事实。缓解方式是把关键字段放进结构化状态，并在注入时标注来源与时间。
5. 遗漏通常包括长期记忆库、向量索引副本、缓存与备份副本。验证方法：删除后分别按用户 ID 查询各存储，确认均为空；再用同一用户发起新会话，确认无法召回旧偏好；最后检查审计日志是否记录删除范围与时间。
