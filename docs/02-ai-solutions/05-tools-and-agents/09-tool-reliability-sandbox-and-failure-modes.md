# 工具超时、重试、沙箱、审计与失败模式

## 为什么需要学习

大促当天，售后助手的退款调用返回超时。框架按默认策略重试了两次，客户因此收到三笔退款；另一头，订单查询卡在 30 秒没有返回，助手一直在“思考”，客服看着转圈页面打电话投诉。

第三件事更隐蔽：为了“稳妥”，团队给每个工具都加了三次重试、全量日志和沙箱，结果一次普通查询要 6 秒，日志里存满了手机号，而真正需要的审计字段（谁批准、批准了什么）反而没有。

可靠性设计不是“多加几层保护”，而是**在正确的位置加正确的限制**。

> **核心结论：** 超时、重试、幂等、补偿、沙箱、审计各自解决不同问题；加错位置比不加更危险。

## 学习目标

完成本课后，你能够：

- 为一次工具调用设定分层超时与重试预算，并说明退避与抖动的作用。
- 判断哪些失败可重试、哪些必须直接失败，并为写操作设计幂等键与补偿。
- 为沙箱划定最小权限边界，为审计定义必填字段。
- 识别六种常见失败模式与三种过度设计表现。

## 业务场景

晴空商城的退款链路有四个外部依赖：订单库（自建，毫秒级）、支付网关（第三方，1–5 秒，偶发超时）、物流查询（第三方，高峰期限流）、发票服务（财务 SaaS，需审计）。

大促期间支付网关的 P99 从 2 秒涨到 12 秒；物流接口开始返回 429；客服需要能回答“这笔退款到底成功了没有”。

## 核心概念

| 术语 | 含义 | 在本场景中的体现 |
| --- | --- | --- |
| *超时* | 等待上限，必须分层设置 | 单工具 3 秒、整条链路 15 秒 |
| *重试预算* | 允许的重试次数与累计等待上限 | 最多 3 次、累计 ≤ 8 秒 |
| *指数退避* | 间隔逐次放大，避免雪崩 | 200ms → 400ms → 800ms |
| *抖动*（jitter） | 在间隔上加随机量，打散重试峰值 | 0.5–1 倍随机 |
| *幂等键* | 让重复请求被下游识别为同一笔 | `ord-SO-2026-0001-v1` |
| *补偿* | 失败后回退已完成的步骤 | 退款成功但订单未标记，反向修复 |
| *沙箱* | 限制工具可触达的资源与网络 | 只读文件系统、无出站网络 |
| *审计* | 记录谁在何时以何依据做了什么 | 主体、审批人、参数、结果 |

超时必须在多个层次上设置，缺一层就会被上一层拖死：

| 层次 | 典型值 | 缺了会怎样 |
| --- | --- | --- |
| 单次工具调用 | 3–5 秒 | 一个慢接口拖住整轮 |
| 单轮模型请求 | 30–60 秒 | 模型长时间无输出，用户无反馈 |
| 整条任务链路 | 60–120 秒 | 会话悬挂，资源不释放 |
| 人工审批等待 | 30 分钟–2 天 | 任务永远停在“处理中” |

## 工作原理

一次可靠的写操作调用遵循下面的顺序：

1. **先定预算。** 明确这次调用能等多久、可失败几次。预算由业务服务等级推出来，不是拍脑袋。
2. **生成幂等键。** 在发起前生成，随重试复用。键应包含业务唯一标识与版本（如订单号 + 请求序号），不能每次重试都新建。
3. **分类失败。** 超时、限流、5xx 视为可重试；参数错误、权限不足、业务拒绝（订单不存在、已退款）不可重试。
4. **退避重试。** 只在预算内重试，间隔指数增长并加抖动。抖动不是优化，而是防止所有实例在同一毫秒重试造成二次雪崩。
5. **失败收敛。** 预算耗尽后返回明确状态：已确定失败、结果未知、需人工核查。**“结果未知”是必须存在的状态**，不能强行归类。
6. **补偿与对账。** 对“结果未知”的写操作，用幂等键查询下游真实状态；确认失败的做反向补偿；确认成功的补完后续步骤。
7. **审计落库。** 记录主体、参数快照、幂等键、尝试次数、最终状态、审批人与依据。审计日志要能独立回答“这笔钱为什么退了”。

沙箱的边界取决于工具性质：能执行任意代码或访问文件系统的工具必须隔离（受限文件系统、无网络、限时执行）；纯查询类工具有时只需网络白名单与只读凭据。**沙箱不是越严越好**，限制过度会让正常任务失败，反而诱发绕过行为。

## 架构与选型

| 设计项 | 轻量做法 | 强化做法 | 何时需要强化 |
| --- | --- | --- | --- |
| 超时 | 统一 30 秒 | 分层超时 + 取消传播 | 有交互式等待或长任务 |
| 重试 | 固定 3 次 | 分类 + 预算 + 抖动 | 依赖外部服务且流量大 |
| 幂等 | 下游天然幂等 | 显式幂等键 + 去重表 | 涉及资金、库存 |
| 补偿 | 人工处理 | 自动对账 + 反向操作脚本 | 失败可检测且损失可量化 |
| 沙箱 | 只读凭据 | 容器隔离 + 网络白名单 | 工具能执行代码或读写文件 |
| 审计 | 应用日志 | 结构化审计表 + 保留期 | 有合规或资金要求 |

过度设计有三种典型表现：对所有工具一律重试（把确定性失败变成重复副作用）；把审计做成全量日志倾倒（有数据没结论）；给只读工具加重量级沙箱（成本高、收益低）。

## 最小示例

下面的重试器只用标准库，演示三个关键行为：可重试才重试、预算耗尽即放弃、幂等键全程复用。运行环境 Python 3.9+。

```python
import random

RETRYABLE = {"timeout", "rate_limited", "unavailable"}   # 1) 只有这些值得重试

class ToolError(Exception):
    def __init__(self, code):
        self.code = code

LOG, DELAYS = [], []

def call_tool(func, idem_key, max_attempts=3, timeout_ms=800, rng=None):
    rng = rng or random.Random(7)                        # 2) 固定种子，输出可复现
    spent = 0
    for attempt in range(1, max_attempts + 1):
        try:
            data = func(attempt, idem_key)               # 3) 每次尝试复用同一幂等键
            LOG.append((attempt, "ok"))
            return {"ok": True, "data": data, "attempts": attempt, "idem_key": idem_key}
        except ToolError as exc:
            LOG.append((attempt, exc.code))
            if exc.code not in RETRYABLE:                # 4) 确定性失败立即返回
                return {"ok": False, "error_code": exc.code,
                        "retryable": False, "attempts": attempt}
            delay = min(200 * 2 ** (attempt - 1), 1000) * (0.5 + rng.random() / 2)  # 5) 退避 + 抖动
            spent += delay
            if attempt == max_attempts or spent > timeout_ms:   # 6) 预算兜底
                return {"ok": False, "error_code": exc.code,
                        "retryable": True, "attempts": attempt}
            DELAYS.append(round(delay))

def flaky(attempt, idem_key):
    if attempt < 3:                                      # 前两次超时，第三次成功
        raise ToolError("timeout")
    return {"refund_id": "RF-1001"}

def broken(attempt, idem_key):
    raise ToolError("invalid_request")                   # 参数类错误，重试无意义

def slow(attempt, idem_key):
    raise ToolError("unavailable")                       # 服务持续不可用

print("重试成功:", call_tool(flaky, "ord-SO-2026-0001-v1"))
print("不重试:", call_tool(broken, "ord-SO-2026-0001-v1"))
print("预算耗尽:", call_tool(slow, "ord-SO-2026-0001-v1", max_attempts=4, timeout_ms=400))
print("退避序列:", DELAYS)
print("调用日志:", LOG)
```

预期输出：

```text
重试成功: {'ok': True, 'data': {'refund_id': 'RF-1001'}, 'attempts': 3, 'idem_key': 'ord-SO-2026-0001-v1'}
不重试: {'ok': False, 'error_code': 'invalid_request', 'retryable': False, 'attempts': 1}
预算耗尽: {'ok': False, 'error_code': 'unavailable', 'retryable': True, 'attempts': 3}
退避序列: [132, 230, 132, 230]
调用日志: [(1, 'timeout'), (2, 'timeout'), (3, 'ok'), (1, 'invalid_request'), (1, 'unavailable'), (2, 'unavailable'), (3, 'unavailable')]
```

读法：第二行说明参数错误只尝试一次；第三行说明“预算耗尽”返回的是可重试标记，调用方应据此转人工或稍后再试，而不是继续循环；退避序列里同一轮的两次延迟不同，来自抖动。

## 动手实验

**前置条件**：Python 3.9+，保存为 `retry_budget.py`。

**步骤**：

1. 运行并核对五行输出。
2. 把 `RETRYABLE` 里的 `timeout` 删掉，观察“超时”是否退化为一次即失败。
3. 把 `rng = random.Random(7)` 换成 `random.Random()`，多跑几次，观察退避序列的波动。
4. 给 `call_tool` 增加“结果未知”状态：当最后一次失败是 `timeout` 时返回 `status="unknown"`，并写一段“用幂等键查询下游状态”的伪代码。

**预期结果**：步骤 2 中 `flaky` 只尝试一次；步骤 3 中退避值每次不同但幅度受控；步骤 4 中新增状态能区分“确定失败”与“可能已执行”。

**验证方法**：为每个失败码断言重试次数；统计“结果未知”占比，作为对账任务的输入。

**清理方法**：删除脚本与 `__pycache__`；示例不访问真实支付接口。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 重复退款 | 非幂等写操作被自动重试 | 用同一幂等键重放，看下游是否去重 | 幂等键落库复用，写操作默认不自动重试 |
| 超时后状态不明却继续下一步 | 缺少“结果未知”状态 | 检查返回结构是否有 unknown 分支 | 显式建模 unknown，触发对账或人工 |
| 重试造成服务雪崩 | 无退避抖动，所有实例同时重试 | 观察重试时刻分布是否集中 | 指数退避 + 抖动 + 熔断 |
| 审计只有应用日志 | 未定义必填字段 | 抽查日志能否回答“谁批准了什么” | 结构化审计表，字段固定 |
| 沙箱频繁误杀正常任务 | 限制过严或规则不区分工具 | 统计沙箱拒绝原因分布 | 按工具分级隔离，最小必要权限 |

## 安全与生产注意事项

**<u>对不可逆写操作自动重试是资金事故的常见来源。</u>** 超时只说明“没收到响应”，不代表“没有执行”。写操作应默认不自动重试，改由幂等键 + 状态查询确认；确实要重试时必须复用同一幂等键，并在下游做去重。

**<u>审计日志本身可能成为敏感数据的泄露渠道。</u>** 把完整请求体、手机号、地址原样写入日志，会让审计系统变成第二份客户数据库。审计应记录必要字段（主体、参数摘要或脱敏值、决策依据、结果），并对日志做访问控制与保留期管理。

另外两点：沙箱要默认拒绝出站网络与任意文件写入，仅对需要的工具开口；杀链路上的熔断策略要基于错误率而不是单次失败，否则正常波动也会触发。

## 本课总结

- **超时要分层**：单工具、单轮、整链路、人工等待各有一层，缺一层就被拖死。
- 重试只针对可重试错误，并受预算约束；指数退避与抖动是防雪崩的必需项。
- 幂等键让重试安全；“结果未知”是独立状态，必须由对账或人工收尾。
- 沙箱按工具性质分级，审计按必填字段结构化，两者都不是越全越好。
- 过度设计与缺少保护同样危险：一律重试、全量日志、过度隔离都在制造新问题。

## 思考题

支付网关在大促期间 P99 从 2 秒涨到 12 秒，而你的单工具超时设的是 3 秒。你会调高超时、缩短超时并依赖重试、还是引入异步受理？请写出判断依据、对用户可见行为的影响，以及对账方案。

参考思路：先看“超时后重试”是否安全（有幂等键则可行），再看用户能否等待（交互式界面宜异步受理并返回任务号）。异步受理把不确定性显性化，配合任务状态查询与对账最稳；单纯调高超时会拖住整条链路。评价标准是：用户能否知道当前状态、失败能否被检测。

## 小测

1. 为什么超时要分层设置？
2. 下列哪类错误应当重试？  
   A. `invalid_request`　B. `permission_denied`　C. `rate_limited`　D. `already_refunded`
3. 幂等键为什么要在重试之间复用？
4. 什么是“结果未知”状态，为什么必须建模？
5. 场景题：为提速，团队把订单查询与退款提交都设成“失败重试 3 次”。请指出问题并给出修正方案。

## 答案与解析

1. 因为不同层次的等待会互相叠加：单工具不设上限，整轮就会被一个慢接口拖住；整链路不设上限，会话资源无法释放。分层后每层都能独立取消与兜底。
2. **C。** 限流是暂时性状态，退避后重试有意义。A 是参数问题，重试只会重复错误；B 是授权问题，需人工或修配置；D 是业务终态，重试永远失败。
3. 因为下游用幂等键判断“这是同一笔请求”。若每次重试生成新键，下游会认为它是新请求，从而重复执行，资金与库存场景后果严重。
4. 指调用超时或连接中断，无法确定对方是否已执行。它与“确定失败”处理方式不同：前者需要对账或查询确认，后者可以安全放弃或转人工。不建模就会被迫二选一，两边都可能出错。
5. 问题在于把写操作与读操作同等对待：查询可安全重试，退款提交在超时后重试可能重复退款。修正为查询类保留重试与退避；退款提交默认不自动重试，改为幂等键 + 状态查询 + 明确 unknown 状态，必要时异步受理。
