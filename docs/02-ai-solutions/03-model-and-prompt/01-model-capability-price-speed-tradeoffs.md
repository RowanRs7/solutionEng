# 模型能力、价格、速度与上下文权衡

## 为什么需要学习

晴空商城的「售后智能助手」上线前，团队里有两派意见：一派坚持用最强的旗舰模型，理由是“退款算错要赔钱”；另一派拿最小模型试了一周，发现回答虽然快，但经常把“7 天无理由”和“15 天质量问题换货”搞混。

两派都没说错，但都在用单一维度做决定。真实约束有四个：回答要多准（能力）、每次会话花多少钱（单价）、客服等多久（延迟）、能塞多少政策与订单（上下文）。这四项互相拉扯，抬高其中一项通常要付出另外三项的代价。

> **核心结论：** 选模型不是选最强的，而是在能力可接受的前提下，找到单位业务成本最低、延迟满足 SLO 的那个组合。

## 学习目标

完成本课后，你能够：

- 用能力、单价、延迟、上下文四个维度写出一张模型对比表。
- 计算“一次售后会话”的 token 成本，并折算成日成本与月成本。
- 解释 *服务层级* 与 *批处理* 如何在不换模型的情况下改变价格和等待时间。
- 判断某个业务环节应使用交互式调用、异步批处理还是容量预留。

- 回看上一单元：[AI 需求发现与定义](../02-discovery-and-requirements/00-overview.md)。
- 理解 token 是文本被切分后的计量单位，输入和输出分开计价。

## 业务场景

售后助手的处理链路是：客服提问 → 检索售后政策与订单 → 生成答复或退款建议 → 人工确认 → 调用工具。上线目标由业务方给出：

- 日均会话约 12,000 次，每次会话含 5 轮对话。
- 页面等待目标：首字不超过 2 秒，整段答复不超过 6 秒。
- 单会话成本上限 0.05 元，否则每月预算不可接受。
- 答复必须引用政策条款编号，并给出订单号。
- 退款金额超过 500 元时只给建议，不进自动执行。

这些数字把“选哪个模型”变成了可以计算的题，而不是审美之争。

## 核心概念

*能力档位*（capability tier）指厂商按推理深度划分的产品梯队，通常分为轻量、通用、旗舰三档；同一档位内还会分普通生成模型和*推理模型*（先产出大量不可见的推理 token 再作答）。*单位任务成本*是本课最重要的概念：把输入 token、缓存命中 token、输出 token 分别乘以对应单价后求和，再除以一次业务任务——**比较成本时要用“每次售后会话”，不要用“每百万 token”，因为后者不可比。**

| 维度 | 观察什么 | 变贵的代价 | 晴空商城的具体表现 |
| --- | --- | --- | --- |
| 能力 | 政策条款准确性、多步推理、工具调用正确率 | 旗舰模型单价通常是轻量档的数倍到数十倍 | 轻量档把 15 天换货说成 7 天退货 |
| 单价 | 输入、输出、缓存读三档价格分开看 | 输出 token 单价普遍高于输入 | 长答复比长上下文更烧钱 |
| 延迟 | 首 Token 延迟（TTFT）、端到端延迟 | 推理模型与高推理强度显著变慢 | 客服等 20 秒就会绕过助手直接用旧流程 |
| 上下文 | 上下文窗口、最大输入、最大输出 | 窗口越大越容易掩盖检索质量问题 | 塞入 40 条政策后关键条款被“淹没” |

截至 2026-10-19，主流旗舰推理模型的上下文窗口已达百万 token 量级（例如 Azure OpenAI 文档列出 GPT-6 系列为 1,050,000 token 上下文、922,000 最大输入、128,000 最大输出），具体数值随模型版本变化，必须以部署当日的官方文档为准。

还有两个常被忽略的杠杆：

- *服务层级*（service tier）：同一模型提供不同优先级。以 Amazon Bedrock 为例，`flex` 层级用更长处理换取价格折扣，`priority` 层级用溢价换取更快响应，`standard` 是默认层，`reserved` 则是按月或按季度预留吞吐（其文档给出的可用性目标是 99.5%）。
- *批处理*：把大量请求打包异步提交，服务商在空闲容量上执行，价格通常显著低于在线调用，但不能用于用户正在等待的交互。

## 工作原理

1. **拆业务任务**：把售后会话拆成“意图识别 → 政策检索 → 答复生成 → 退款建议”四段，每段的输入输出长度不同。
2. **估 token**：用真实抽样会话统计每段的输入 token（含系统提示、政策片段、订单字段）与输出 token，取 P50 与 P95。
3. **套单价**：分别乘输入、缓存读、输出单价，得到单任务成本；再乘日会话量得到日成本。
4. **定延迟预算**：把 6 秒拆给检索、模型、工具调用、人工确认四个环节，模型只拿其中一段。
5. **选服务层级**：交互路径用 `standard` 或 `priority`；离线批量评估、历史工单重跑用 `flex` 或批处理。
6. **用评测验证**：在黄金样本集上比较候选模型的准确率与成本，只有准确率不达线时才升档。

**降档前必须用评测集证明能力仍达标；升档前必须用成本模型证明预算仍可承受。**

## 架构与选型

| 业务环节 | 建议档位与调用方式 | 理由 | 不适用情形 |
| --- | --- | --- | --- |
| 意图分类、字段抽取 | 轻量档 + 在线调用 | 任务窄、输出短，成本与延迟都敏感 | 需要跨多条政策推理时准确率不够 |
| 政策答复生成 | 通用档 + 在线调用 | 需要读懂条款并引用编号 | 输入超过窗口或需要多轮工具调用 |
| 退款建议与争议判断 | 旗舰档或推理模型 + 在线调用 | 错误代价高，值得付溢价 | 高并发峰值下延迟会超 SLO |
| 历史工单批量复盘 | 通用档 + 批处理或 `flex` 层 | 可等待数小时，换取明显折扣 | 结果要当天回写客服页面 |
| 大促期间峰值流量 | `reserved` 预留容量 | 保证吞吐不因排队抖动 | 平常日均流量低，预留会闲置 |

选型依据按顺序判断：先用评测集确定能力下限，再用 SLO 确定延迟上限，最后在满足前两项的候选里选单位任务成本最低者。<u>不要先挑模型再改预算，那会把约束倒挂成结论。</u>

## 最小示例

下面用标准库计算一次售后会话的成本。价格是**假设值**，只为演示算式；真实单价以厂商定价页为准。

```python
# 假设单价，单位：元 / 百万 token。换成官方定价即可复用同一算式。
PRICE = {
    "input": 2.0,       # 未命中缓存的输入 token
    "cache_read": 0.5,  # 命中提示缓存的输入 token，通常远低于输入价
    "output": 8.0,      # 输出 token，含推理模型的推理 token
}

def session_cost(uncached_in: int, cached_in: int, out: int) -> float:
    # 三个分项分别计价，避免把缓存命中的 token 按全价重复计算
    return (
        uncached_in / 1_000_000 * PRICE["input"]
        + cached_in / 1_000_000 * PRICE["cache_read"]
        + out / 1_000_000 * PRICE["output"]
    )

# 一次典型会话：政策与系统提示 4000 token 命中缓存，本轮新增 2000，输出 600
one = session_cost(uncached_in=2000, cached_in=4000, out=600)
sessions_per_day = 12_000

print(f"单会话成本：{one:.4f} 元")
print(f"日成本（{sessions_per_day} 会话）：{one * sessions_per_day:.2f} 元")
print(f"月成本（30 天）：{one * sessions_per_day * 30:.2f} 元")
```

预期输出（按上述假设价格手算，可直接运行核对）：

```text
单会话成本：0.0108 元
日成本（12000 会话）：129.60 元
月成本（30 天）：3888.00 元
```

整体流程是：先按用途把 token 分成三类，再分别计价求和，最后乘流量放大成预算。关键设计选择是把 `cache_read` 单独列价——若把 4000 个缓存 token 按输入全价计算，单会话成本会变成 0.0168 元，高出 55%，足以让选型结论反转。

## 动手实验

**前置条件**：Python 3.9+，无需联网或 API Key。

**步骤**：

1. 把上面的代码保存为 `cost_model.py`。
2. 复制三行结果作为基线。
3. 把 `PRICE["output"]` 改为 `30.0`（模拟旗舰推理模型），重新运行。
4. 恢复输出价，再把 `PRICE["input"]` 改为 `0.4`（模拟轻量档），重新运行。
5. 用每次的日成本除以基线日成本，记录倍数。

**预期结果**：基线单会话 0.0108 元、日成本 129.60 元；把输出价改成 30 后单会话 0.0240 元、日成本 288.00 元，约为基线的 2.22 倍；把输入价改成 0.4 后单会话 0.0076 元、日成本 91.20 元，约为基线的 0.70 倍。可见<u>输出价变化的影响远大于输入价</u>。

**验证方法**：单会话成本应等于三个分项之和；把 `cached_in` 设为 0 时，结果应等于“全部按输入价计算”的朴素算法。

**清理方法**：删除 `cost_model.py`，本实验不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 账单远高于估算 | 只算了输入 token，漏了输出与推理 token | 对照账单的输入/输出/缓存三列 | 用完整三段算式重算，并把推理 token 计入输出 |
| 首字很快但整段很慢 | 用了流式输出但模型推理时间长 | 分别记录 TTFT 与总时长 | 降低推理强度，或让模型先给短前言再展开 |
| 高峰期频繁超时 | 只用了默认层级且无预留容量 | 看错误码与排队指标是否集中在峰值 | 峰值走 `priority` 或预留容量，非峰值回默认层 |
| 加了政策文档后准确率下降 | 上下文过长，关键条款被稀释 | 对比“检索 3 条”和“塞 40 条”的准确率 | 缩小检索范围，而不是换更贵的模型 |
| 换小模型后偶发答错却查不出来 | 评测集只覆盖简单问题 | 按政策条款分类统计错误率 | 补黄金样本，按条款维度定位薄弱点 |

## 安全与生产注意事项

**<u>把上下文塞到窗口上限会静默丢信息。</u>** 多数接口在超长输入时会截断或报错，截断的往往是中间段落，恰好是政策条款所在的检索结果区。缓解方法是给输入设硬预算、超限时先裁剪低分检索结果，并在响应里记录实际使用 token。

**<u>单价写死在代码里会让成本随厂商调价悄悄失控。</u>** 价格表和模型名应放在配置中心并带生效日期，配合每日成本告警；否则一次调价就能让月成本翻倍而无人察觉。

另外，退款建议涉及金额与账户，属于敏感数据，调用前要脱敏并只传必要字段，日志里不要留完整订单与身份证信息。

## 本课总结

- **选型是四维约束下的最优化，不是四维中任一维的最大化。**
- 成本要按“每次业务会话”计算，输入、缓存读、输出三段分别计价。
- 延迟要拆成首 Token 延迟和端到端延迟，分别设 SLO。
- 服务层级与批处理能在不换模型的前提下改变价格与等待时间。
- 降档靠评测集证明，升档靠成本模型证明，两者都缺一不可。

## 思考题

客服主管提出：“大促期间先保证不超时，答错一点可以接受；平常宁可贵一点也要准。”请说明你会如何设计路由与阈值，并写出需要监控的指标与可能出错的地方。

参考思路：按流量与风险分两条路径——大促走通用档加 `priority` 层级并降低推理强度，平常走旗舰档；阈值用“是否涉及退款金额”和“政策条款是否唯一”两个可判定条件，而不是让模型自己判断。需要监控降级比例、降级期间的答错率、路由误判案例；风险是阈值条件本身写错，导致高额退款问题被降级处理。

## 小测

1. 比较两个模型的成本时，为什么用“每百万 token 单价”直接对比是不充分的？
2. 首 Token 延迟（TTFT）低，是否意味着用户等待时间短？
3. 批处理适合下列哪一项？  
   A. 客服页面实时答复　B. 夜间重跑历史工单　C. 用户点击退款后的即时校验　D. 登录鉴权
4. *服务层级* 改变的是什么——模型能力，还是同一模型下的优先级与价格？
5. 场景题：团队想把每次会话的政策检索结果从 3 条增加到 40 条，同时把模型从旗舰档换成轻量档，理由是“上下文长了信息就全了”。请指出这个判断的问题。

## 答案与解析

1. 因为业务成本取决于单次任务的输入输出 token 结构。输出单价通常是输入的数倍，长上下文任务与短输出任务的成本结构完全不同；只有乘上真实 token 用量才能比较。只比单价会得出“轻量档一定便宜 10 倍”的错误结论。
2. 不是。TTFT 只衡量“第一个字出来要多久”，推理模型可能先输出很短的前言再长时间思考，整段答复仍可能超过 6 秒。必须同时看端到端延迟的 P95。
3. **B。** 批处理是异步的，适合可等待的离线任务。A 和 C 都有用户在前台等待，批处理窗口不可接受；D 与模型调用无关。
4. 改变的是同一模型下的优先级、可用性与价格；`flex` 更便宜更慢，`priority` 更贵更快，`reserved` 是容量承诺。能力由模型本身决定，换层级不会让模型变聪明。
5. 这个判断混淆了两个维度。加长上下文不会自动提升准确性，反而可能让关键条款被稀释；同时换轻量档会削弱对多条款的推理能力，两个改动叠加后准确率通常下降。正确做法是先验证检索质量（3 条是否命中正确条款），再在评测集上单独评估“上下文长度”和“能力档位”各自的边际收益。
