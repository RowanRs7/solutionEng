# 模型路由、降级与何时停止优化 Prompt

## 为什么需要学习

售后助手的提示词已经改到第 14 版。前 5 版效果提升明显，第 6 到第 10 版每版只涨零点几个百分点，最近 4 版几乎没动，但提示词从 600 字涨到了 3,800 字，输入 token 翻了三倍。

更糟的是，团队把所有请求都送给了同一个旗舰模型：查“退款到哪一步了”这种简单问题也要等 8 秒。大促当天上游限流，整个入口一起挂掉，没有任何备用路径。

两件事要一起解决：**流量要分层走，故障要有退路；提示词要知道什么时候该停。**

> **核心结论：** 路由把“平均成本”降下来，降级把“最坏情况”兜住；而提示词优化的终点不是“再改一版”，是“换一种模式”。

## 学习目标

完成本课后，你能够：

- 用确定性特征（金额、是否含图、条款是否冲突）写出一条路由规则。
- 设计三级降级链，并说明每一级触发条件与用户可见变化。
- 解释熔断、容量层级与降级的关系。
- 用收益曲线与失败类型分布判断“该停止改提示词，改什么”。

## 业务场景

售后助手每天 12,000 次会话，请求差异极大：

- 简单查询（退款进度、物流状态）约占 55%，几乎不需要推理。
- 常规政策答复约占 30%，需要检索与引用。
- 争议判断约占 12%，涉及条款冲突与金额。
- 含图片的定损约占 3%，必须看图。

大促期间流量会涨到 3 倍，上游可能限流。业务方要求：宁可答得慢一点、宁可转人工，也不能整站不可用。

## 核心概念

*模型路由*（model routing）指按请求特征把流量分发到不同模型或档位。*降级*（fallback / degradation）指主路径不可用时切换到备用路径，可能牺牲质量、延迟或功能。*熔断*（circuit breaker）指连续失败后快速失败，避免把故障放大。*质量阈值* 是判断“是否值得为更好的模型付费”的量化门槛。

| 情况 | 路由/降级动作 | 用户可见变化 | 代价 |
| --- | --- | --- | --- |
| 简单查询 | 轻量档 | 几乎无感，更快 | 复杂问题会答不全（已被规则排除） |
| 高额但规则明确 | 通用档 + 强制人工确认 | 多一步人工 | 人力成本 |
| 条款冲突 + 高额 | 推理档 | 稍慢 | 成本数倍 |
| 含图片 | 视觉档 | 无感 | 图像 token 成本 |
| 上游限流 | 切备用供应商或备用模型 | 可能风格变化 | 需双模型评测与运维 |
| 连续失败 | 熔断 + 模板答复/转人工 | 功能降级 | 体验受损但可控 |
| 大促峰值 | `priority` 层级或预留容量 | 无感 | 溢价或预付承诺 |

## 工作原理

1. **先分类再路由**：用确定性特征做判定（金额、是否含图、条款是否命中多条、租户等级），<u>不要让模型自己决定用哪个模型</u>。
2. **设质量阈值**：定义“备用模型的质量差多少还可以接受”，把它写成可测的指标。
3. **建降级链**：主模型 → 备用模型（同族不同档）→ 备用供应商 → 模板答复/转人工。
4. **配熔断**：连续 N 次超时或 5xx 就短时快速失败，冷却后放少量探针恢复。
5. **容量分层**：峰值走 `priority` 或预留容量，非峰值回默认层；可等待的离线任务走 `flex`。
6. **记录实际服务模型**：每个响应标注真正服务的模型与层级，否则无法归因。
7. **离线评估路由**：定期用评测集检查“被路由到低档的请求”准确率是否仍达标。
8. **定期复评**：模型下架、价格调整、新档位发布都要重新跑一次路由效果。

截至 2026-10-19，Amazon Bedrock 的智能提示词路由文档给出了一种可参考的形态：单一无服务器端点在同一模型族内按“预测的回答质量”分流，并允许设置一个*备用模型*与“质量差异”阈值（例如阈值 10% 表示只有另一模型预测质量高出 10% 以上才切换）；响应中会返回实际服务的模型。文档同时列出限制：该能力仅针对英文提示优化、无法依据应用自身的性能数据调整决策，且对独特场景不一定最优。

## 架构与选型

| 路由依据 | 适用 | 优点 | 风险 |
| --- | --- | --- | --- |
| 确定性业务特征（金额、是否含图） | 多数业务系统 | 可解释、可审计、可测 | 特征覆盖不到长尾 |
| 输入长度与结构化程度 | 技术型分流 | 实现简单 | 与“难度”不总相关 |
| 厂商智能路由（预测质量） | 同族模型、英文场景 | 少维护，自动分流 | 黑盒、受语言与训练数据限制 |
| 租户/套餐等级 | SaaS 多租户 | 与商业模型一致 | 低等级租户体验下降 |
| 服务层级（priority/flex） | 峰值与离线任务 | 不换模型即可调节 | 价格与延迟需预算 |

选型依据：**能用确定性规则表达的分流，优先自己写**；只有在“同一任务、难以用规则描述难度”时才考虑厂商智能路由，并保留自己的评测兜底。

## 最小示例

下面是一段可运行的路由决策与饱和检测脚本。

```python
def route(has_image: bool, amount: int, policy_conflict: bool) -> tuple[str, str]:
    # 高风险优先：条款冲突且金额高，值得付推理溢价
    if policy_conflict and amount > 500:
        return "reasoning", "条款冲突且金额高：值得付推理溢价"
    # 其次看模态：必须看图才能定损
    if has_image:
        return "vision", "需要看图定损"
    # 金额高但规则明确：普通模型 + 人工审核兜底
    if amount > 500:
        return "general", "高额但规则明确：普通模型 + 人工审核"
    # 其余走轻量档：低风险、高频、成本敏感
    return "light", "低风险查询：轻量档即可"

cases = [
    {"has_image": False, "amount": 0, "policy_conflict": False},
    {"has_image": False, "amount": 800, "policy_conflict": False},
    {"has_image": True, "amount": 800, "policy_conflict": True},
]
for c in cases:
    tier, reason = route(**c)
    print(f"{c} → {tier}（{reason}）")

# 提示词收益曲线：每轮迭代后的评测集准确率
SCORES = [0.710, 0.790, 0.820, 0.830, 0.831]
deltas = [round(b - a, 3) for a, b in zip(SCORES, SCORES[1:])]
print("每轮提升:", deltas)
print("是否饱和:", "是，停止优化提示词" if deltas[-1] < 0.005 else "否，继续迭代")
```

预期输出：

```text
{'has_image': False, 'amount': 0, 'policy_conflict': False} → light（低风险查询：轻量档即可）
{'has_image': False, 'amount': 800, 'policy_conflict': False} → general（高额但规则明确：普通模型 + 人工审核）
{'has_image': True, 'amount': 800, 'policy_conflict': True} → reasoning（条款冲突且金额高：值得付推理溢价）
每轮提升: [0.08, 0.03, 0.01, 0.001]
是否饱和: 是，停止优化提示词
```

这段代码暴露了一个真实缺陷：第三条请求既含图片又涉及条款冲突，却被路由到 `reasoning`，图像信息被丢弃。<u>路由的优先级顺序本身就是设计决策</u>，正确做法是要么路由到同时支持视觉与推理的模型，要么把任务拆成“看图定损”与“条款判断”两步分别路由。

## 动手实验

**前置条件**：Python 3.9+，无需 API Key。

**步骤**：

1. 保存代码为 `router.py`，运行并核对输出。
2. 调整优先级：把 `has_image` 判断提到最前，重跑，观察第三条结果的变化，并判断哪种顺序更符合业务。
3. 增加一条规则：`policy_conflict` 为真但金额 ≤ 500 时走 `general`，验证不误用推理档。
4. 给 `route` 增加一个返回值表示“是否需要人工确认”，并在第三条与第二条上验证。
5. 把 `SCORES` 换成你自己的评测结果，确认饱和判断是否成立。

**预期结果**：第 2 步第三条变成 `vision`，说明“看图”被满足但“条款冲突”被忽略；第 3 步验证低额冲突不必付推理溢价；第 4 步应只在金额大于 500 时返回 `True`。

**验证方法**：用 50 条带标注的样本跑路由，统计“被分到低档且判断错误”的比例；超过阈值说明分流规则过于激进。

**清理方法**：删除 `router.py`，不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 简单问题也很慢 | 所有流量走旗舰档 | 按请求类型看延迟分布 | 增加轻量档路由，用评测集守住准确率 |
| 降级后错误率飙升 | 备用模型能力差距过大且无质量阈值 | 对比主备模型在同一评测集的结果 | 设质量差异阈值，超阈值不降级 |
| 上游限流时整站不可用 | 没有备用路径与熔断 | 注入故障演练 | 加降级链与熔断，冷却后小流量探针 |
| 改了 10 版提示词仍在原地 | 问题不在提示词 | 看错误类型分布：检索错、规则缺失还是能力不足 | 换模式：补检索、加代码规则、加工具 |
| 响应无法归因 | 没记录实际服务的模型与层级 | 抽查响应日志字段 | 每个响应记录模型、层级、模板指纹 |
| 路由规则越加越乱 | 缺少统一特征定义与优先级 | 列出所有规则与触发条件 | 固定优先级顺序，写单元测试覆盖组合 |

## 安全与生产注意事项

**<u>降级路径可能绕过安全校验。</u>** 备用模型或模板答复常常是简化实现，容易漏掉人工审核、敏感词过滤或引用校验；降级前要确认它同样执行硬性控制，否则故障期间就是风险敞口。

**<u>把路由决策交给模型自己会形成不可审计的权限扩散。</u>** 模型可能把高额退款请求“判断为简单”而走轻量路径，应使用确定性特征，并记录每次路由的依据。

此外，大促前要做降级演练：人为切到备用链路，观察答复质量、转人工比例与告警是否按预期工作；没有演练过的降级路径，等同于没有。

## 本课总结

- 路由按业务特征分层，确定性规则优先于模型判断。
- 降级链要三级以上：备用模型、备用供应商、模板答复或人工。
- 熔断防止故障放大，容量层级用于峰值，两者与降级配合使用。
- 每个响应必须记录实际服务的模型与层级，否则无法归因与计费。
- 提示词优化有收益曲线；当每轮提升低于阈值，应改检索、改代码规则、加工具或换模式，而不是继续加字数。

## 思考题

评测显示：提示词第 14 版的准确率是 83.1%，错误样本中 60% 是“政策条款检索错了”，25% 是“模型不知道该调用哪个工具”。你会先做什么？请给出顺序与理由。

参考思路：先修检索（占错误 60%，且属检索层问题，改提示词无效）；再补工具描述与工具选择示例，或把“选工具”改成代码按意图路由。提示词层只保留表达与拒答规则。理由是错误类型决定修复层次，改错层次会白费迭代。

## 小测

1. 为什么路由决策不应交给模型自己判断？
2. *质量阈值* 在降级中的作用是什么？
3. 下列哪种情况最该考虑“停止优化提示词”？  
   A. 输出 JSON 偶尔缺字段　B. 错误中多数是检索没命中正确条款　C. 拒答话术语气不够礼貌　D. 示例格式不统一
4. 熔断器被触发后，正确的恢复方式是什么？
5. 场景题：大促期间上游限流，备用模型质量明显较差。你会如何决定是否降级？

## 答案与解析

1. 因为它是权限与成本决策，需要可审计、可测试。模型自判会引入不可解释的偏差，且可能把高风险请求判成简单请求，绕过人工审核。
2. 它量化“备用模型比主模型差多少还可以接受”。低于阈值才允许降级，避免为了可用性牺牲过多准确性；阈值应来自评测集而非主观感觉。
3. **B。** 检索层错误改提示词收益极低，应改切分、Top-K、重排或查询改写。A、D 属提示词/结构化输出问题；C 是话术微调，仍属提示词范围。
4. 冷却一段时间后放少量探针流量，成功率达到阈值再逐步放量；不要立即全量恢复，否则会在上游仍不稳定时再次打满。
5. 先看业务分级：高额退款与投诉类不允许降级到低质量模型，直接转人工或排队；低风险查询可降级并明确告知“当前为简化答复”。同时设定降级比例上限与告警，避免全量降级后无人察觉质量下滑。
