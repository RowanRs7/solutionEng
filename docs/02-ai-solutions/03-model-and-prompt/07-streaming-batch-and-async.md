# 流式响应、批处理与异步任务

## 为什么需要学习

售后助手的答复平均需要 4.5 秒，客服盯着转圈的加载图标，超过 5 秒就开始怀疑系统卡死，反复点击重试——于是同一次会话被请求了三次，成本和数据库压力都翻倍。

另一头，运营想让助手把过去半年的 3 万条工单重新分类，跑一次要几小时。如果还用页面同步接口，浏览器早就超时了，网关也会掐断连接。

两个问题看似都是“慢”，解法完全不同：**前台要的是“马上有反馈”，后台要的是“别占连接”。**

> **核心结论：** 有人在等，就用流式把等待变短；没人在等，就用批处理把成本压低。两者都不解决“慢”，只解决“慢得可接受”。

## 学习目标

完成本课后，你能够：

- 为一个页面交互写出首 Token 与总时长的预算分配。
- 说明 *SSE* 的报文结构与单向限制，并写出可解析的事件循环。
- 解释流式输出与结构化输出校验的冲突，并给出可行的组合方案。
- 设计批处理任务的输入组织、幂等键、进度查询与失败重跑。

## 业务场景

售后助手有两条互不相同的链路：

- **交互链路**：客服在页面提问，期望 2 秒内看到第一个字，整段不超过 6 秒；中途可以点“停止生成”。
- **离线链路**：每周把上周工单重新分类并做质量抽检，共 3 万条，允许跑 2 小时，要求成本尽量低、失败可重跑。

## 核心概念

*流式输出*（streaming）指模型边生成边把增量返回，客户端逐步渲染；*SSE*（Server-Sent Events）是浏览器原生支持的文本事件流协议，服务端以 `text/event-stream` 响应，事件之间用空行分隔。*批处理*（batch）是把大量请求打包异步提交，服务商在空闲容量上执行，结果写入指定存储。*异步任务*是“提交—查询—回收”的模式，强调任务标识与状态机。*超时预算*是把总等待时间分配给检索、模型、工具与重试的额度。

| 方式 | 用户是否在等 | 典型延迟 | 成本 | 失败处理 |
| --- | --- | --- | --- | --- |
| 同步一次性返回 | 是 | 一次完整生成时间 | 标准价 | 重试整次请求 |
| 流式（SSE） | 是 | 首字快，总时长不变 | 标准价 | 断线可续、已展示内容不可撤回 |
| 批处理 | 否 | 小时级 | 通常显著更低 | 整批重跑或按失败清单重跑 |
| 异步任务队列 | 否（可查进度） | 秒到小时 | 标准价 | 幂等重试、任务状态机 |
| 容量预留 | 都可能 | 稳定 | 预付承诺 | 溢出到标准层 |

## 工作原理

1. **先判定有没有人在等**：有人等走交互链路，没人等走离线链路。
2. **切分超时预算**：交互预算 6 秒 = 检索 1.2 秒 + 模型首字 1.5 秒 + 生成 2.5 秒 + 余量 0.8 秒。
3. **选择传输方式**：交互用 SSE；离线用批处理；涉及多步骤且耗时长用异步任务队列。
4. **处理增量渲染**：SSE 客户端按空行切分事件，遇到结束标记停止；<u>不要假设一次读取就能拿到完整事件</u>，必须缓冲半截数据。
5. **解决流式与校验的冲突**：文本可以边流边显示，但**结构化结果必须等流结束后再整体校验**，或在流中用增量解析器逐段拼装。
6. **处理取消与断线**：客服点“停止”要同时取消服务端请求；断线重连要能续上或标记为不完整。
7. **离线任务收尾**：提交时带幂等键，结果写对象存储，用事件通知或轮询回收，失败条目录入重跑清单。

截至 2026-10-19，MDN 文档说明 SSE 是单向连接（客户端不能通过该连接向服务端发事件）、事件流以空行分隔，并且在不使用 HTTP/2 时浏览器对同域连接数有很低的上限（文档给出的历史限制为 6 条）；Amazon Bedrock 的批处理文档则说明批任务为异步执行、输入输出走对象存储、不支持预置吞吐模型，且使用 `Converse` 调用类型时不支持工具调用。

## 架构与选型

| 需求 | 建议方案 | 理由 | 不适用 |
| --- | --- | --- | --- |
| 客服页面实时答复 | SSE 流式 + 结构化结果单独返回 | 首字快，且不牺牲可校验性 | 需要双向交互（改用 WebSocket） |
| 需要边生成边调工具 | 流式 + 工具调用事件 | 可展示“正在查订单” | 工具调用与结构化输出并行受限时需拆分 |
| 3 万条工单重新分类 | 批处理 | 成本最低，允许小时级 | 结果必须当天回写页面 |
| 单条耗时的多步任务 | 异步任务 + 进度查询 | 不占连接，可断点续 | 用户期待即时结果 |
| 大促保吞吐 | 容量预留 / 优先级层 | 避免排队抖动 | 平时流量低会浪费 |

选型依据：**先看“是否有人在等”，再看“能不能容忍失败重跑”**；两者都偏向离线时，批处理是最省的选项。

## 最小示例

下面是一次真实形态的 SSE 响应（`text/event-stream`）：

```text
event: delta
data: {"text": "订单 QK-2026-004821"}

event: delta
data: {"text": "符合七天无理由退货，"}

event: delta
data: {"text": "建议退款 800 元，需人工审核。"}

data: [DONE]

```

用标准库解析它的关键点有两个：按空行切块、缓冲半截数据。

```python
import json

# 把服务端返回的原始字节流准备好；真实场景来自 HTTP 分块读取
RAW = (
    'event: delta\ndata: {"text": "订单 QK-2026-004821"}\n\n'
    'event: delta\ndata: {"text": "符合七天无理由退货，"}\n\n'
    'event: delta\ndata: {"text": "建议退款 800 元，需人工审核。"}\n\n'
    'data: [DONE]\n\n'
).encode("utf-8")

def iter_events(stream: bytes):
    buffer = ""
    # 事件以空行分隔，因此按 \n\n 切块；真实流里最后一块可能不完整，需要保留
    for block in stream.decode("utf-8").split("\n\n"):
        if not block.strip():
            continue
        for line in block.splitlines():
            if line.startswith("data:"):
                payload = line[len("data:"):].strip()
                if payload == "[DONE]":
                    return  # 结束标记：停止读取，避免把心跳当成正文
                buffer += json.loads(payload)["text"]
                yield payload, buffer

count = 0
for payload, sofar in iter_events(RAW):
    count += 1
    print(f"增量 {count}: {json.loads(payload)['text']}")
print("完整答复:", sofar)
print("事件数:", count)
```

预期输出：

```text
增量 1: 订单 QK-2026-004821
增量 2: 符合七天无理由退货，
增量 3: 建议退款 800 元，需人工审核。
完整答复: 订单 QK-2026-004821符合七天无理由退货，建议退款 800 元，需人工审核。
事件数: 3
```

关键设计选择：`[DONE]` 用 `return` 而不是 `break`，因为结束标记之后可能还有心跳或空块，继续解析会抛异常。真实实现的差别在于：`iter_events` 的入参应换成“按块到达的字节迭代器”，并在每次 `read` 后保留不完整的尾部再拼接。

关于结构化输出：如果答复既要流式展示、又要给退款服务一份 JSON，常见做法是**两段式**——先流式输出 `reply_text` 让人看，流结束后再返回一个完整 JSON 事件供程序校验。把 JSON 边流边解析也可以，但必须用增量解析器，且**校验只能在流结束后做**，否则会拿半个对象去判断。

## 动手实验

**前置条件**：Python 3.9+，无需 API Key。

**步骤**：

1. 保存代码为 `sse_demo.py`，运行并核对输出。
2. 把 `RAW` 最后一块改成 `'data: {"text": "…"}\n\n'`（去掉 `[DONE]`），观察循环是否正常结束。
3. 在 `RAW` 中插入一条只含 `"data": ""` 的空块与一条心跳注释块（`": ping\n\n"`），修改解析逻辑跳过它们。
4. 模拟“半截事件”：把一条 `data:` 行从中间截断并分两次给解析器，验证缓冲逻辑。
5. 把答复合成为完整 JSON 字符串，写一个只在流结束后调用的 `validate()`。

**预期结果**：第 2 步不报错但会缺少结束信号（生产环境应报“流未正常结束”）；第 3 步需要显式跳过非 `data:` 行；第 4 步若按 `\n\n` 切块，半截块会被丢弃或误解析，说明必须保留尾部缓冲。

**验证方法**：统计“收到结束标记的比例”，应接近 100%；低于 99% 说明连接管理有问题。

**清理方法**：删除 `sse_demo.py`，不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 页面一直转圈，日志显示已返回 | 网关缓冲了流式响应 | 用 `curl -N` 看是否逐段到达 | 关闭代理缓冲，设置正确的 `Content-Type` |
| 中文被拆成乱码 | 按字节切分而不是按 UTF-8 字符解码 | 检查是否逐个 chunk 解码 | 保留字节缓冲，按完整 UTF-8 序列解码 |
| 重连后答复重复出现 | 客户端未记录已渲染位置 | 对比重连前后的事件 id | 用事件 id 去重，或重连时重新生成 |
| 批任务结果缺行 | 单条失败未记录，整批被当成成功 | 统计输入行数与输出行数 | 输出失败清单，按清单重跑 |
| 批任务重复扣费 | 重复提交且无幂等键 | 检查提交记录是否有去重字段 | 用业务幂等键 + 任务状态机 |
| 长任务被网关掐断 | 用了同步接口做小时级任务 | 查看网关超时与任务时长 | 改异步任务 + 进度查询 |

## 安全与生产注意事项

**<u>流式输出一旦展示就无法撤回。</u>** 模型可能在流到一半时说出不该说的内容（内部规则、他人订单片段），此时前端已经渲染。缓解方式是延迟展示敏感段落、对结构化结果做结束校验后再“确认发送”，并在前端支持立即截断。

**<u>批处理把大量原始数据写入对象存储与任务日志，扩大了泄露面。</u>** 输入文件常含订单号、电话、地址，必须加密存储、限定访问角色、设置保留期与清理任务；不要把含个人信息的批次文件放在公共桶里。

此外，取消请求时服务端必须真正停止生成（否则继续计费），并对“取消率突增”设告警——它往往意味着前端在反复重试。

## 本课总结

- 交互用流式把“等待”变短，离线用批处理把“成本”压低，两者目标不同。
- SSE 是单向文本协议，按空行分块，必须处理半截事件、心跳与结束标记。
- 结构化校验只能在流结束后做，流式展示与结构化返回可以拆成两段。
- 超时预算是设计出来的，不是等故障后加上去的。
- 离线任务要有幂等键、失败清单与结果回收机制，否则重跑会重复扣费。

## 思考题

如果客服希望在生成过程中随时打断并追问“刚才那条政策是哪一年的”，你会如何设计协议与状态？请说明流式连接、会话状态与取消语义。

参考思路：流式通道只负责服务端到客户端的增量；追问走独立的普通请求，携带同一会话 id 与已完成的消息历史。打断时先取消生成并记录已产出部分为“不完整”，再处理追问；需要明确“取消后是否保留半截答复”的产品语义，并在日志里区分完成与中断。

## 小测

1. SSE 为什么不能用于“边生成边让用户修改参数并实时生效”？
2. 首 Token 延迟降低，是否一定能降低用户感知的等待？
3. 下列哪项最适合批处理？  
   A. 客服页面答复　B. 历史工单重新分类　C. 退款结果实时校验　D. 登录鉴权
4. 为什么流式输出与严格结构化校验存在冲突？
5. 场景题：批任务输入 3 万行，输出只有 29,412 行，团队打算整批重跑。你会怎么建议？

## 答案与解析

1. 因为 SSE 是单向的：服务端到客户端，客户端无法在同一条连接上回传事件。需要双向交互应改用 WebSocket 或另开普通请求。
2. 不一定。首 Token 早只改变“开始有反馈”的时间；如果总时长仍很长而内容不是逐步可读（例如先长时间推理再一次性输出），用户仍然感到慢。要同时优化 TTFT 与可读的增量节奏。
3. **B。** 允许小时级延迟且量大，成本优势明显。A 有用户在等；C 需要立即反馈；D 与模型调用无关。
4. 因为结构化校验需要完整对象（字段齐全、类型正确），而流式到达的是片段；在流中校验只能看到半个对象，结论不可靠。解法是等流结束再校验，或用增量解析器拼装后再校验。
5. 先不要整批重跑。应按幂等键对比输入与输出，找出缺失的 588 条，分析是超长输入、单条失败还是输出写盘中断；只重跑缺失清单，并补上“逐条记录失败原因”的机制，避免下次仍无法定位。
