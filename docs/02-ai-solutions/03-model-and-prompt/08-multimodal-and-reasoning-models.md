# 多模态输入与推理模型边界

## 为什么需要学习

售后助手最常见的一类请求是：“屏幕裂了，能换吗？”后面附一张照片。团队的第一版只把文字传给模型，模型礼貌地回答“请描述损坏情况”，客服只好自己看图、自己判断。第二版把照片直接塞进去，成本涨了三倍，而且模型经常把“贴膜划痕”说成“屏幕裂纹”。

另一次，客服上传了 12 页的保修条款 PDF 问“这算不算人为损坏”。模型读了前三页就下结论，漏掉了第七页的除外条款。

多模态不是“能传图就行”，推理模型也不是“越贵越准”。**先判断任务需要哪种输入、哪种推理深度，再决定用什么模型。**

## 学习目标

完成本课后，你能够：

- 为图文、文档、音频三类输入分别列出必要的前置处理步骤。
- 解释推理 token 的计价方式与对上下文、延迟的影响。
- 用成本与准确率两个维度判断是否值得启用推理模型。
- 识别推理模型在工具调用、流式首字与输出上限上的限制。

## 前置知识

- 回看上一课：[流式响应、批处理与异步任务](07-streaming-batch-and-async.md)。
- 知道图像在传输上通常是 URL 或 base64。
- 了解 PDF 可能是“文字层”或“扫描件”，处理方式不同。
- 理解 token 是计费与上下文占用的单位。

## 业务场景

晴空商城售后助手要处理三类非纯文本输入：

1. **破损照片**：判断是否属于质量问题，决定换货还是维修。
2. **发票与保修卡**：抽取购买日期、商品型号、保修期限，用于计算是否过保。
3. **客服通话录音**：转写后作为工单摘要的输入，减少客服手写。

同时，争议判断（例如“脱胶是否算人为损坏”）需要对照政策条款做多步推理，团队在考虑是否换成推理模型。

## 核心概念

*多模态输入*指模型除文本外还能接受图像、音频、文档等模态。*视觉理解*指模型直接“看图”判断，*文档抽取*指从版面中定位并结构化提取字段，两者失败模式不同。*推理模型*指在给出可见答案前先生成大量不可见 *推理 token* 的模型；这些 token 不出现在答复里，但**占用上下文窗口并按输出 token 计价**。*推理强度*（reasoning effort）是控制思考量的参数。

| 输入类型 | 适合的做法 | 主要风险 | 成本特点 |
| --- | --- | --- | --- |
| 破损照片 | 视觉理解 + 明确的判定标准 | 光照、角度、贴膜干扰导致误判 | 按图像折算 token，分辨率越高越贵 |
| 发票/保修卡 | 先 OCR 或版面解析，再抽取字段 | 扫描件缺字、表格串行 | 文本化后成本可控 |
| 长条款 PDF | 先切分 + 检索，再让模型读相关段落 | 整本塞入导致关键页被忽略 | 全文塞入成本最高 |
| 通话录音 | 先转写，再摘要 | 转写错误、说话人混淆 | 转写与生成两次计费 |
| 争议推理 | 推理模型 + 政策条款 | 推理 token 费用高、延迟长 | 输出成本可能数倍于普通模型 |

## 工作原理

1. **判断是否需要该模态**：能用文字说清（“外壳有 3 厘米裂纹”）就不必传图；图像只在“必须看”时使用。
2. **做前置处理**：图像压缩到必要分辨率、裁掉无关背景；文档先判断有无文字层，扫描件走 OCR；音频先转写并标注说话人。
3. **把判断标准写进提示词**：例如“贴膜划痕不算屏幕裂纹；需可见裂纹且影响显示”，否则模型只能自由发挥。
4. **选择模型档位**：简单抽取用普通模型；需要多步对比条款、计算时限的用推理模型。
5. **设定推理强度**：低强度用于有一定推理但延迟敏感的环节，高强度只留给高价值判断。
6. **为推理 token 留空间**：输出上限要覆盖“推理 + 可见答案”，否则会拿到不完整结果。
7. **验证**：用带标注的样本分别测普通模型与推理模型的准确率与成本，再决定是否升级。

截至 2026-10-19，Azure OpenAI 文档说明：推理模型生成的推理 token 不出现在消息内容里，但占用上下文窗口并按输出 token 计费；可通过 `reasoning_effort`（取值包括 `none`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`，因模型而异）控制思考量；当触达上下文或输出上限时响应会以 `status: "incomplete"` 返回，且费用已产生。文档还建议在摸索阶段至少为推理与输出预留约 25,000 token，并指出部分模型在 Chat Completions 上无法同时使用工具与推理，需要改用 Responses API 或把推理强度设为 `none`。

## 架构与选型

| 任务 | 建议模型 | 理由 | 不适用/代价 |
| --- | --- | --- | --- |
| 破损照片分类 | 视觉能力的通用模型 | 速度与成本可控 | 需要精确测量尺寸时不适用 |
| 发票字段抽取 | 普通模型 + OCR 前置 | 输出短、结构固定 | 版面极复杂时需要专用文档模型 |
| 过保判定 | 普通模型 + 确定性日期计算 | 日期比较应交给代码 | 让模型算日期容易出错 |
| 政策除外条款判断 | 推理模型（中高强度） | 需要多条款对比与反例排除 | 延迟高、成本可能数倍 |
| 通话摘要 | 普通模型 + 转写 | 摘要属生成任务 | 需要逐句合规审查时不适用 |
| 低延迟语音问答 | 推理强度设为 `none` | 首字时间是硬指标 | 复杂判断会失去推理收益 |

选型依据：**能用确定性规则或检索解决的，不要交给推理模型**；只有“需要比较多个条件并排除例外”的任务才值得付推理溢价。

## 最小示例

先看一段多模态请求的消息结构（字段形态与主流接口一致，图片用 base64 内联）：

```json
{
  "model": "example-vision-general",
  "messages": [
    {"role": "system", "content": "你是售后定损助手。贴膜划痕不算屏幕裂纹；只有可见裂纹且影响显示才判为质量问题。"},
    {"role": "user", "content": [
      {"type": "text", "text": "这属于质量问题吗？订单 QK-2026-004821。"},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,<BASE64>"}}
    ]}
  ]
}
```

真正需要算清的是“推理值不值”。下面的脚本比较同一任务在普通模型与推理模型下的成本：

```python
# 假设单价（元 / 百万 token）；推理 token 按输出价计费
P = {"input": 2.0, "output": 8.0}

def cost(prompt_tokens: int, visible_tokens: int, reasoning_tokens: int = 0) -> float:
    # 关键：reasoning_tokens 计入输出，否则会严重低估推理模型成本
    return (prompt_tokens * P["input"] + (visible_tokens + reasoning_tokens) * P["output"]) / 1_000_000

plain = cost(3000, 500)              # 普通模型：3000 输入 + 500 输出
light = cost(3000, 500, 600)         # 低推理强度：约 600 个推理 token
deep = cost(3000, 500, 6000)         # 深度思考：约 6000 个推理 token

print(f"普通模型:        {plain:.4f} 元")
print(f"推理(effort=low): {light:.4f} 元  ({light/plain:.1f} 倍)")
print(f"推理(深度思考):    {deep:.4f} 元  ({deep/plain:.1f} 倍)")
```

预期输出：

```text
普通模型:        0.0100 元
推理(effort=low): 0.0148 元  (1.5 倍)
推理(深度思考):    0.0580 元  (5.8 倍)
```

关键设计选择：把推理 token 显式作为参数传进成本函数，而不是藏在“输出”里。这样当团队讨论“要不要开高强度”时，看到的是 5.8 倍的差距，而不是一句“好像贵一点”。真正的判断还要除以准确率提升：如果准确率只从 88% 提到 90%，这 5.8 倍通常不值得全量启用，只应作用于争议类请求。

## 动手实验

**前置条件**：Python 3.9+，无需 API Key 与图片素材。

**步骤**：

1. 保存代码为 `reasoning_cost.py`，运行并核对输出。
2. 把 `deep` 的推理 token 改为 20000，模拟高强度思考，记录新成本与倍数。
3. 增加一个变量 `accuracy`，计算“每次正确判断的成本”＝单次成本 / 准确率，分别对普通模型（假设 0.88）与推理模型（假设 0.90）求值。
4. 按“只有 12% 的请求进入争议判断”做加权，计算混合方案的每 1000 次请求成本。
5. 把单价换成你所在平台的真实价格后重跑。

**预期结果**：第 2 步成本约 0.1700 元、约 17 倍；第 3 步会看到普通模型每次正确约 0.0114 元，推理模型约 0.0644 元，差距比单次成本更大；第 4 步混合方案显著低于全量推理。

**验证方法**：加权结果应等于“普通 × 88% + 推理 × 12%”；若不等，说明比例或公式有误。

**清理方法**：删除 `reasoning_cost.py`，不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 贴膜划痕被判成屏幕裂纹 | 未给判定标准，或图片分辨率过高放大细节 | 用同一批样本对比“给标准/不给标准” | 在提示词中写清判定边界，必要时降采样 |
| 长 PDF 结论引用了错误页 | 全文塞入，关键页被稀释 | 对比“全文”与“检索相关段落”的准确率 | 先切分检索，再让模型只读相关段落 |
| 推理模型答复经常为空或截断 | 输出上限没覆盖推理 token | 检查结束原因与状态字段 | 提高输出上限，预留至少 2.5 万 token 起步 |
| 升级模型后工具调用报错 | 某些模型在特定接口上不能同时用工具与推理 | 查看错误信息与接口类型 | 换用支持工具+推理的接口，或把推理强度设为 `none` |
| 首字很慢，客服以为卡死 | 推理阶段没有可见输出 | 记录首 Token 时间 | 让模型先给一句短前言，或降低推理强度 |
| 发票字段抽取错行 | 扫描件未做 OCR 或表格未按列解析 | 抽 20 张人工核对 | 先 OCR + 版面分析，再交给模型结构化 |

## 安全与生产注意事项

**<u>用户上传的图片与文档是不可信输入，可能携带指令或恶意内容。</u>** 图片中可以有文字诱导模型改变行为，PDF 里可以藏提示词；必须把多模态内容当作数据处理、隔离在标签内，并在输出侧做过滤。

**<u>原始照片、录音与发票含个人敏感信息，直接送第三方模型会扩大合规风险。</u>** 应先脱敏（裁掉人脸、遮住证件号）、明确保留期限与用途，并在合同与数据流图上标注数据出境与留存情况。

另外，推理模型可能生成“看起来有理”的推理摘要，但摘要不等于真实推理过程，不能作为审计依据；审计应依赖输入、输出与规则命中记录。

## 本课总结

- 多模态的第一步是判断“是否真的需要该模态”，而不是先传上去再说。
- 不同模态的失败模式不同：图像怕干扰，文档怕版面，音频怕转写。
- 推理 token 不可见但计入输出成本与上下文，成本可能数倍于普通模型。
- 推理强度是可调旋钮，应按请求风险分级启用，而不是全量打开。
- 能交给代码的确定性计算（日期、金额）不要交给模型，包括推理模型。

## 思考题

如果客服每天只遇到约 50 个争议判断，但每个判断都可能涉及上千元赔付，你会如何设计模型策略？请说明成本、延迟与人工介入的取舍。

参考思路：争议量小、单次错误代价高，适合全量走推理模型 + 人工确认，成本相对于赔付金额可忽略；延迟可容忍（客服可以等待十几秒），因此不必牺牲推理强度。相反，破损照片分类量大、单价低，应使用普通视觉模型并配合抽检。

## 小测

1. 推理 token 会出现在模型答复里吗？它如何计费？
2. 为什么把 12 页保修条款整本塞进上下文通常不是好做法？
3. 下列哪项最适合交给推理模型？  
   A. 计算保修到期日　B. 判断“脱胶是否属于人为损坏”　C. 抽取发票金额　D. 把录音转成文字
4. `reasoning_effort` 调低会带来什么变化？
5. 场景题：团队想把所有请求都换成高强度推理模型，理由是“准确率更高”。请给出反驳与替代方案。

## 答案与解析

1. 不会出现在可见答复里，但它占用上下文窗口，并按输出 token 计费；所以“答案很短”不代表“这次很便宜”。
2. 因为关键除外条款可能被大量无关条款稀释，模型容易只读开头就下结论；应先切分并用检索定位相关段落，再让模型在较小上下文中判断。
3. **B。** 需要比较多条款并排除例外，属于推理型判断。A 应交给代码做日期计算；C 属抽取任务，普通模型加 OCR 即可；D 属转写任务，与推理模型无关。
4. 推理 token 通常减少，成本下降、首字更快，但复杂任务的准确率可能下降；它不改变模型的知识范围，只改变“想多久”。
5. 反驳：准确率提升往往只有几个百分点，而成本可能是数倍，延迟也显著上升，对简单抽取类请求是纯浪费。替代方案是按风险路由：只有争议判断、条款冲突、金额争议走推理模型，其余走普通模型，并用评测集分别验证两类请求的准确率。
