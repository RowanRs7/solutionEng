# 输出解析、校验、修复与重试

## 为什么需要学习

结构化输出上线后，售后助手的解析失败率从 12% 降到 1.8%，但值班同学发现新的麻烦：那 1.8% 里，有超过一半其实是“可以救”的——多了一个句号、字段名大小写不一致、金额写成字符串。而原来的做法是一律报错转人工，人工队列被无意义地填满。

另一头也有风险：有人写了个“失败就无限重试”的循环，结果一次上游故障把配额打满，整个入口半小时不可用。

> **核心结论：** 修复要“有界、有分层、有兜底”；重试不是容错，重试加兜底才是。

## 学习目标

完成本课后，你能够：

- 按语法、结构、语义、业务四层归类一次解析失败。
- 区分可重试失败与不可重试失败，并给出对应处理。
- 写出带错误信息回传、最多重试 N 次的修复循环。
- 为重试耗尽设计兜底话术与人工接管，并定义监控指标。

## 前置知识

- 回看上一课：[结构化输出与 JSON Schema](05-structured-output-and-json-schema.md)。
- 会使用 Python `json` 模块，并知道 `JSONDecodeError` 带位置信息。
- 了解 HTTP 错误码中“可重试”和“不可重试”的区别（如 429 与 400）。
- 知道响应可能因为长度上限被截断。

## 业务场景

售后助手每天的 12,000 次会话里，约有 200 次输出不合格。团队需要一套明确的处理规则：

- 能修的自动修，不要让客服重问一遍。
- 修不了的要给出可用答复，而不是白屏。
- 每次重试都花钱，必须设上限。
- 失败的原始输出要留样，供后续改进提示词。

## 核心概念

*解析失败*指模型输出无法被下游消费。*校验层次*是从便宜到昂贵的四道关：语法（是不是合法 JSON）、结构（字段与类型是否符合 Schema）、语义（枚举值、引用是否成立）、业务（金额、权限、适用性）。*修复提示*是把上一次的错误信息回传给模型，要求它只改错误部分。*重试预算*是允许的重试次数与时间上限；*兜底*是预算耗尽后的确定行为。

| 层次 | 典型症状 | 能否重试 | 处理方式 |
| --- | --- | --- | --- |
| 语法 | 前后带说明文字、代码围栏、单引号 | 通常可以 | 先做轻量清洗（去围栏、截取首尾花括号）再解析 |
| 结构 | 缺字段、类型不符、多余字段 | 通常可以 | 错误回传 + 一次修复重试 |
| 语义 | 枚举值不在列表、条款编号不存在 | 有时可以 | 修复一次；引用类错误先纠正检索 |
| 业务 | 金额超限、越权动作 | 不应靠重试 | 直接拒绝并转人工，重试只会重复犯错 |
| 空响应/截断 | `finish_reason` 为长度上限、`status` 为 incomplete | 视原因 | 提高输出上限或缩短要求后再试一次 |

截至 2026-10-19，Azure OpenAI 推理模型文档明确说明：当生成触达上下文上限或 token 上限时，响应会以 `status: "incomplete"` 返回，并给出 `incomplete_details.reason`；此时费用已产生（输入与推理 token 都已计费）却拿不到答案，因此**必须检查响应状态**，不能把它当成空结果。

## 工作原理

1. **捕获原始输出**：保存文本、模型名、模板指纹、token 用量与结束原因，先落日志再解析。
2. **轻量清洗**：去掉 Markdown 代码围栏、截取第一个完整 JSON 对象；这一步能救回相当一部分语法错误。
3. **分层校验**：语法 → 结构 → 语义 → 业务，失败就记录具体层次与字段。
4. **判断可修性**：业务类错误与权限类错误直接终止；语法与结构类错误进入修复。
5. **构造修复提示**：把“原始输出 + 错误清单 + Schema”一起给出，要求“只输出修正后的 JSON，不要解释”。
6. **受预算约束重试**：最多 1–2 次，用指数退避；仍失败则兜底。
7. **兜底与留样**：返回预设话术或转人工，把失败样本加入评测集。

**重试次数要写进配置并配告警，不能写死在循环里。**

## 架构与选型

| 策略 | 适用 | 优点 | 代价 |
| --- | --- | --- | --- |
| 不重试，直接兜底 | 低价值、高频、可用模板答复 | 成本最可控 | 修得回来的错误也被丢弃 |
| 清洗 + 一次修复重试 | 多数结构化输出场景 | 修复率高、成本可控 | 需要维护错误分类逻辑 |
| 带错误回传的多轮修复 | 复杂嵌套结构、字段多 | 修复更精准 | token 成本上升，可能反复出错 |
| 换模型重试 | 疑似模型能力不足 | 能跨过能力边界 | 成本与延迟明显上升，需双模型运维 |
| 直接转人工 | 高风险业务动作 | 风险最低 | 人力成本高 |

选型依据：**先看失败层次，再看业务价值**。钱相关的动作不重试；纯格式问题值得一次修复；同一请求反复失败说明提示词或 Schema 设计有问题，应该改设计而不是加重试。

## 最小示例

下面用预置响应模拟一次真实的“解析 → 校验 → 修复 → 兜底”循环，不调用外部 API。

```python
import json

REQUIRED = ["decision", "refund_amount", "policy_ids", "needs_human", "reply_text"]
ALLOWED = {"refund", "exchange", "repair", "reject", "ask_more"}

def parse_and_validate(text: str):
    # 第一层：语法。失败时把位置信息一起带出去，便于判断是截断还是多余文本
    try:
        obj = json.loads(text)
    except json.JSONDecodeError as e:
        return None, [f"非法 JSON: {e.msg} (位置 {e.pos})"]
    # 第二层：结构。缺字段与类型错误分开表述，修复提示才能精准
    errors = [f"缺少字段: {k}" for k in REQUIRED if k not in obj]
    # 第三层：语义。枚举必须落在白名单内
    if obj.get("decision") not in ALLOWED:
        errors.append(f"decision 非法: {obj.get('decision')}")
    # 第三层：条件依赖。退款场景必须带数字金额
    if obj.get("decision") == "refund" and not isinstance(obj.get("refund_amount"), (int, float)):
        errors.append("refund 场景 refund_amount 必须是数字")
    return (obj if not errors else None), errors

# 模拟模型的三次返回：带尾随文字 → 枚举写成中文 → 完全合规
CANNED = [
    '{"decision": "refund", "refund_amount": 800, "policy_ids": ["P-03"], "needs_human": true, "reply_text": "ok"} 以上是结果',
    '{"decision": "退款", "refund_amount": 800, "policy_ids": ["P-03"], "needs_human": true, "reply_text": "ok"}',
    '{"decision": "refund", "refund_amount": 800, "policy_ids": ["P-03"], "needs_human": true, "reply_text": "ok"}',
]

def call_model(attempt: int, errors: list) -> str:
    # 真实实现中，这里会把上一轮的 errors 拼进修复提示后重新请求
    return CANNED[attempt]

MAX_ATTEMPTS = 3
errors: list = []
for attempt in range(MAX_ATTEMPTS):
    raw = call_model(attempt, errors)
    obj, errors = parse_and_validate(raw)
    if obj is not None:
        print(f"第 {attempt + 1} 次尝试：通过")
        break
    print(f"第 {attempt + 1} 次尝试：失败 → {'; '.join(errors)}")
else:
    print("达到重试上限，走兜底：转人工")
```

预期输出：

```text
第 1 次尝试：失败 → 非法 JSON: Extra data (位置 110)
第 2 次尝试：失败 → decision 非法: 退款
第 3 次尝试：通过
```

关键设计选择：错误信息被设计成“可直接塞进修复提示的句子”，包含字段名与实际值。若只返回 `False`，修复提示就只能说“请重试”，模型往往原样再错一次。

## 动手实验

**前置条件**：Python 3.9+，无需 API Key。

**步骤**：

1. 保存代码为 `repair_loop.py`，运行并核对三次尝试的输出。
2. 把 `MAX_ATTEMPTS` 改为 2，确认走兜底分支。
3. 在 `parse_and_validate` 前加一个 `clean()`：去掉 Markdown 代码围栏，并截取“第一个 `{` 到最后一个 `}`”之间的内容，再解析，观察第 1 次是否能直接通过。
4. 增加一条业务校验：`refund_amount > 500` 时 `needs_human` 必须为 `True`。
5. 让第 3 条预置响应把 `needs_human` 设为 `False`，确认业务校验拦截且不再重试。

**预期结果**：第 2 步输出“达到重试上限”；第 3 步截取后第 1 次即可通过（失败原因从“非法 JSON”变成“一次都没重试”）；第 4、5 步说明<u>业务类错误应当直接终止，而不是继续重试</u>。

**验证方法**：统计每一项失败的“层次标签”，若业务类错误占比超过 10%，说明提示词里的规则没讲清，应先改提示词而不是加重试。

**清理方法**：删除 `repair_loop.py`，不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 重试几次结果都一样 | 修复提示只复述要求，没带具体错误 | 打印修复提示全文 | 把字段名、实际值、期望值写进提示 |
| 修复率很高但成本也涨了 | 无上限重试或每次都全量重生成 | 统计每次请求平均调用次数 | 设 1–2 次上限，只让模型改错误字段 |
| 偶发空答复且无报错 | 响应被截断，`status`/结束原因未检查 | 检查结束原因与状态字段 | 提高输出上限或缩短要求，并对截断做显式分支 |
| 429 被当成格式错误重试 | 未区分网络类与内容类错误 | 查看错误码分布 | 网络类做指数退避，内容类做修复 |
| 人工队列被格式问题淹没 | 兜底策略过于保守 | 抽样看人工队列的失败样本 | 先加清洗与一次修复，再转人工 |

## 安全与生产注意事项

**<u>无上限重试会把一次故障放大成配额耗尽。</u>** 上游限流时，重试风暴会让所有租户一起不可用；必须有次数上限、退避与熔断，并对重试率设告警。

**<u>把原始输出直接回显给客服会泄露内部提示与数据结构。</u>** 建议展示兜底话术，原始输出只进内部日志，并限制访问权限。

另外，“修复”这一步同样会消耗 token 且可能被注入内容影响：修复提示里的原始输出应视为不可信数据，用标签包裹，不要让它改变修复指令本身。

## 本课总结

- 解析失败要分层：语法、结构、语义、业务，处理方式各不相同。
- 能修的（语法、结构）用错误回传修一次；不能修的（业务、权限）直接拒绝。
- 重试必须有次数与时间预算，并配退避与告警。
- 预算耗尽要有确定兜底：模板答复或转人工。
- 失败样本要留样进评测集，改提示词比加重试更划算。

## 思考题

如果业务要求“解析失败率必须低于 0.1%”，你会优先改 Schema、改提示词，还是加重试？请说明判断顺序与验证方式。

参考思路：先看失败分布——语法类多说明输出未受约束，应上严格 Schema；结构类多说明字段设计或示例不清，应改提示词；语义与业务类多说明规则没讲清或校验过严。重试只能降低“已产生错误”的可见影响，不能降低根因发生率，所以应放在最后。

## 小测

1. 为什么业务类错误不应重试？
2. 修复提示中最重要的内容是什么？
3. 下列哪项属于“结构”层失败？  
   A. 输出带 Markdown 代码围栏　B. 缺少 `policy_ids` 字段　C. 金额超过订单金额　D. 条款编号不存在
4. 响应 `status` 为 incomplete 时应先做什么？
5. 场景题：某天解析失败率从 1.8% 突然升到 9%，模板与模型都没改。请给出排查顺序。

## 答案与解析

1. 因为重试不会改变业务事实（金额超限、无权限），只会重复同一结论并多花钱；正确做法是拒绝、转人工并记录规则命中。
2. 具体错误清单：字段名、实际值、期望值。只复述“请输出合法 JSON”等于没给信息，模型容易原样再错。
3. **B。** 缺字段属于 Schema 结构不符。A 是语法层（可清洗）；C 是业务层；D 是语义层的引用完整性问题。
4. 先看 `incomplete_details.reason`：是输出上限还是上下文上限；据此提高输出预算或缩短要求，并把该情况作为独立分支处理，而不是当成空结果重试。
5. 先看失败层次分布与上游状态（是否限流、是否换了部署版本）；再看输入是否变长（检索 Top-K 或政策更新导致截断）；然后核对模板指纹与模型版本是否被悄然更新；最后抽样原始输出确认是语法还是业务错误。顺序原则是“先排除外部变化，再怀疑内容变化”。
