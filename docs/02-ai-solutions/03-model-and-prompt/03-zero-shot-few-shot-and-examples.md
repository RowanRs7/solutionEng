# Zero-shot、Few-shot 与示例设计

## 为什么需要学习

售后助手要把客服的一句话分到五个处理类目：退货、换货、维修、运费争议、其他。团队先写了 zero-shot 提示词，结果“运费谁出”这类问题常被判成“退货”；于是有人往提示词里塞了 8 个示例，准确率上去了，但新问题又来了——模型开始把所有提到“七天”的问题都判成退货，因为 8 个示例里有 5 个是退货。

这是示例设计最典型的两个失败：示例不够时模型靠猜，示例偏斜时模型照抄分布。示例不是越多越好，而是要覆盖真实输入的空间。

> **核心结论：** Few-shot 的作用是“校准输出格式与判断边界”，不是“补充业务知识”；示例集的分布偏差会被模型原样学走。

## 学习目标

完成本课后，你能够：

- 区分 *zero-shot*、*few-shot* 与 *动态示例检索*，并说明各自成本与适用条件。
- 用真实语料分布检查示例集的类别覆盖度，指出缺失类目。
- 写出格式统一、标注边界、含反例的示例组。
- 解释示例数量增加时收益为何递减，以及过拟合示例的具体表现。

## 前置知识

- 回看上一课：[指令层级与 System Prompt](02-instruction-hierarchy-and-system-prompts.md)。
- 知道 LLM 是逐 token 生成，提示词中靠前与靠后的内容影响力不同。
- 手上有一批真实用户输入（哪怕是 30 条历史工单）。
- 能读懂分类任务的“类目/标签”概念。

## 业务场景

晴空商城售后助手的第一步是*意图分类*：把客服的自然语言诉求映射到可执行动作（查订单、走退货、走换货、报修、判运费责任、转人工）。分类错，后面全错——判成退货就会生成退货单，而用户其实只想知道运费谁承担。

业务方给了 200 条历史工单作为抽样语料，五个类目的真实占比是：退货 35%、换货 22%、维修 18%、运费争议 15%、其他 10%。团队准备写提示词。

## 核心概念

*Zero-shot* 指提示词中只给任务说明、不给任何输入输出配对；*few-shot* 指给出若干条配对示例（*shot* 就是一个配对），让模型从示例中推断格式与判断尺度，这一机制常被称为 *in-context learning*（上下文学习，不修改模型权重）。*动态示例检索* 则是在每次请求时按输入相似度从示例库挑最相关的几条，而不是固定塞同一批示例。

| 方式 | 提示词成本 | 典型收益 | 主要风险 | 晴空商城适用性 |
| --- | --- | --- | --- | --- |
| Zero-shot | 最低 | 建基线最快 | 边界模糊、格式不稳 | 先跑基线，量出错在哪 |
| 固定 few-shot | 中等（每次请求都带） | 格式与判定尺度明显稳定 | 示例偏斜导致过拟合 | 类目少、示例稳定时首选 |
| 动态示例检索 | 中等，需检索组件 | 长尾输入也能拿到相似示例 | 检索错就会示范错 | 语料多样、类目多时使用 |
| 微调 | 推理成本低 | 大量样本下最稳 | 迭代慢、需数据治理 | 分类量大且规则长期稳定后考虑 |

**示例数量与收益不是线性关系：从 0 到 3 条通常提升最大，3 到 8 条边际收益明显下降，超过 10 条往往只增加 token 成本。**

## 工作原理

1. **先跑 zero-shot 基线**：记录每个类目的准确率与混淆矩阵，找出“哪两类在互相混淆”，而不是只看总体准确率。
2. **确定示例目标**：如果错在格式（JSON 字段缺失），示例用来锁格式；如果错在边界（运费 vs 退货），示例用来示范边界。
3. **按覆盖度选示例**：每个类目至少 2 条，长尾类目用“看起来像别的类目”的难例，而不是最典型的例子。
4. **统一格式与分隔符**：所有示例用同一种结构，输入输出分隔符一致；避免示例里的分隔符与真实对话的角色标记撞车。
5. **加入反例与拒答示例**：给“信息不足，需要追问订单号”这类示例，模型才知道何时不该猜。
6. **回归评估**：把示例集当成代码管理，每次改动都在固定测试集上比较，按类目看变化。

**示例的选择标准是“覆盖判断边界”，不是“看起来漂亮”。**

## 架构与选型

| 场景 | 建议 | 理由 | 不适用情形 |
| --- | --- | --- | --- |
| 类目 ≤ 5、边界清晰 | 固定 3–5 条 few-shot | 成本可控，格式稳定 | 输入长度差异极大时 |
| 类目多、长尾明显 | 动态示例检索（按相似度取 3 条） | 每条输入都能拿到贴近的示范 | 没有足够示例库，或检索质量差 |
| 输出必须严格符合 Schema | 示例 + 结构化输出约束 | 示例稳格式，Schema 保底线 | 模型不支持结构化输出时需自行校验 |
| 规则频繁变化 | zero-shot + 清晰规则清单 | 改规则比改示例快 | 边界仍需示例才能讲清 |
| 日调用量极大且类目固定 | 微调小模型 | 单次成本最低、延迟稳定 | 缺少标注数据或团队无运维能力 |

选型依据：**先用 zero-shot 定位错误类型，再决定示例是为了“格式”还是“边界”而加**；两者需求不同，示例设计也不同。

## 最小示例

先看一段 few-shot 提示词片段，注意三点：格式统一、含一条“需要追问”的示例、含一条易混类目的边界示例。

```text
把客服诉求分类为：退货 / 换货 / 维修 / 运费争议 / 其他。只输出类目名。

诉求：收到货发现屏幕有裂纹，想换个新的
类目：换货

诉求：下单三天了还没发货，运费能退吗
类目：运费争议

诉求：这个能退吗
类目：需要追问订单号

诉求：用了一个月突然不充电了
类目：维修
```

第二段代码用来检查示例集的覆盖度，避免“8 个示例里 5 个是退货”这种偏斜。

```python
# 示例集中各类目的条数（人工统计），与真实语料占比对比
EXAMPLES = {"退货": 3, "换货": 2, "维修": 1, "运费争议": 0, "其他": 0}
GOLDEN = {"退货": 0.35, "换货": 0.22, "维修": 0.18, "运费争议": 0.15, "其他": 0.10}

print(f"{'类目':<6}{'示例数':>5}{'真实占比':>9}  状态")
for label, share in GOLDEN.items():
    n = EXAMPLES.get(label, 0)
    # 判定规则：占比超过 10% 的类目若没有任何示例，视为覆盖缺口
    status = "缺失" if n == 0 and share >= 0.10 else ("偏少" if n <= 1 else "ok")
    print(f"{label:<6}{n:>5}{share:>9.2f}  {status}")
```

预期输出：

```text
类目      示例数     真实占比  状态
退货        3     0.35  ok
换货        2     0.22  ok
维修        1     0.18  偏少
运费争议      0     0.15  缺失
其他        0     0.10  缺失
```

整体流程是：把“示例数”和“真实占比”放在同一张表里对照，占比不低却没有示例的类目直接暴露。关键设计选择是把判定阈值写成显式常量（这里 10%），团队可以争论阈值，但不会争论“有没有缺口”。

## 动手实验

**前置条件**：Python 3.9+，无需 API Key。

**步骤**：

1. 保存代码为 `example_coverage.py`。
2. 运行，确认“运费争议”和“其他”被标为缺失。
3. 把 `EXAMPLES` 改成 `{"退货": 5, "换货": 1, "维修": 1, "运费争议": 1, "其他": 0}`，重新运行。
4. 观察状态列：退货仍为 ok，但请自行补一列“示例占比”，计算它与 `GOLDEN` 的差值。
5. 把 200 条历史工单按类目统计真实占比，替换 `GOLDEN` 后重跑。

**预期结果**：第 3 步中“换货”变为偏少，“其他”仍缺失；第 4 步会看到退货示例占比约 62%，而真实占比 35%，差 27 个百分点——这正是模型“把什么都判成退货”的成因。

**验证方法**：所有真实占比 ≥10% 的类目都应有 ≥2 条示例；示例占比与真实占比的差值建议控制在 10 个百分点内。

**清理方法**：删除 `example_coverage.py`，不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 模型把所有相似问题判成同一类 | 示例分布偏斜，某类目示例过多 | 对比示例占比与真实占比 | 按覆盖度补示例，削减主导类目示例 |
| 输出字段时有时无 | 示例格式不统一 | 逐条检查示例的输出结构 | 统一示例结构，必要时叠加结构化输出 |
| 新类目上线后旧类目准确率下降 | 新示例挤占注意力，或类目名与旧类目相近 | 按类目看混淆矩阵 | 精简示例数量，加入两类边界难例 |
| 模型连“需要追问”的情况也硬分类 | 缺少拒答/追问示例 | 统计信息不足样本的误分率 | 增加追问示例，并在规则中写明缺失信息时不得猜测 |
| 提示词越写越长，成本上升但效果不变 | 示例数量超过边际收益点 | 做 0/3/5/8 条的对比实验 | 固化 3–5 条，其余交给动态检索 |

## 安全与生产注意事项

**<u>示例里写真实订单号、手机号和地址会造成数据泄露。</u>** 示例会进入每次请求并可能出现在日志、缓存与厂商侧，必须使用脱敏或虚构数据，并纳入代码审查。

**<u>示例可能被用户通过“照抄示例格式”反向利用。</u>** 若示例中包含内部字段名或枚举值，攻击者可据此构造合法格式的越权请求；对外可见的输出格式应只暴露必要字段。

此外，示例文件属于提示词资产，应和模板一起版本化；删除示例时同步清理缓存键，否则旧前缀仍会被命中。

## 本课总结

- Zero-shot 用来建基线并定位错误类型，few-shot 用来校准格式与判断边界。
- 示例集是“分布”，模型会原样学走其中的偏斜。
- 每个真实占比不低的类目都应有示例，长尾优先放难例而非典型例。
- 示例数量收益递减，3–5 条通常够用，更多应转向动态检索。
- 示例必须脱敏、统一格式、含追问与反例，并纳入版本管理。

## 思考题

如果业务新增“价保”类目，而你手上只有 4 条价保工单，你会先加示例还是先写规则？请说明判断依据，以及如何验证改动没有伤到旧类目。

参考思路：4 条样本不足以支撑微调，但足够做 few-shot 难例；先用 2 条价保示例 + 明确规则（时间窗、比价口径）上线，再用混淆矩阵确认价保与“退货/运费争议”的互混是否下降，最后比较改动前后的按类目准确率，确认旧类目没有回退。

## 小测

1. Few-shot 中的“shot”指什么？
2. 为什么示例从 3 条增加到 8 条，效果往往提升有限？
3. 下列哪种示例最值得加入？  
   A. 最典型的退货案例　B. 看起来像换货其实是退货的难例　C. 最长的一条工单　D. 带真实手机号的案例
4. 动态示例检索的主要风险是什么？
5. 场景题：模型总把“运费谁承担”判成“退货”。你会先改示例数量还是先改示例构成？为什么？

## 答案与解析

1. 一个“输入 + 期望输出”的配对样例。多条配对构成 few-shot 提示，用来示范格式与判断尺度，不改变模型权重。
2. 因为示例的边际价值来自“补齐边界与格式”，一旦主要边界被覆盖，再加相似示例只是重复同样信息，同时占用上下文并提高成本，还可能强化分布偏斜。
3. **B。** 难例补的是判断边界，收益最高。A 只是重复已有信息；C 的长度不构成价值；D 会造成敏感数据泄露。
4. 检索可能取到与当前输入表面相似但语义不同的示例，等于给模型一个错误示范；此外检索延迟与示例库维护也会增加复杂度。
5. 先改构成。问题不是示例数量不足，而是缺少“运费争议 vs 退货”的边界示例，甚至可能退货示例过多造成偏斜。应先补 1–2 条边界难例并核对分布，再用固定测试集验证；盲目加量通常会让偏斜更严重。
