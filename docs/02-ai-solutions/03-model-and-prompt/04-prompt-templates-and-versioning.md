# Prompt 模板、变量与版本管理

## 为什么需要学习

售后助手的提示词最初是一段贴在代码里的长字符串。三个月后，团队遇到了三种麻烦：

- 周五改了一句规则，周一发现答复格式全变了，但没人知道改前是什么样。
- 客服反馈“政策引错了”，排查两天才发现是模板变量名写错，`policy_text` 一直是空的。
- 想回滚，发现回滚代码就等于回滚整个服务，只能硬着头皮往前修。

提示词不是代码注释，而是会直接改变系统行为的“程序”。它需要模板、变量校验、版本号和回归验证，和代码享受同等待遇。

> **核心结论：** 提示词一旦上线就是生产配置：必须能追溯“哪个版本、带哪些变量、配哪个模型”，并且能独立回滚。

## 学习目标

完成本课后，你能够：

- 写出一个变量缺失会明确报错的模板，并计算可追溯的模板指纹。
- 区分“模板版本”“模型版本”“检索配置版本”，说明三者为何要联合发布。
- 设计一次包含回归集、灰度和回滚的提示词变更流程。
- 识别把用户输入直接拼进模板带来的格式与注入风险。

## 业务场景

售后助手目前有三条链路共用提示词：客服工作台、买家自助入口、批量复盘任务。三条链路的规则与格式要求不同，但历史上共用同一个字符串，改动互相牵连。

团队决定把提示词拆成模板资产：每个模板有唯一名称、版本号、必填变量清单和自测样本；发布时与模型版本、检索策略一起记录；出问题能按版本号回滚，而不是回滚整个服务。

## 核心概念

*提示词模板*（prompt template）是带占位符的固定文本，运行时注入变量。*变量* 是模板中被替换的部分，分必填与可选；*模板指纹* 是模板内容的哈希，用来判断“线上跑的到底是哪一版”。*版本三元组* 指一次请求实际生效的三个版本：模板版本、模型版本、检索配置版本（切分大小、Top-K、重排规则）。

| 资产 | 变化频率 | 谁改 | 失效影响 |
| --- | --- | --- | --- |
| 模板文本 | 高（每周） | 提示词负责人 | 答复风格、格式、拒答行为 |
| 变量清单与类型 | 中 | 后端 | 缺变量导致空上下文、答非所问 |
| 模型版本 | 低（季度） | 平台/架构 | 全局风格与准确率变化 |
| 检索配置 | 中 | 检索负责人 | 引用的政策条款错误 |
| 示例集 | 中 | 提示词负责人 | 分类边界漂移 |

**只给提示词打版本号是不够的：同一条提示词配上不同模型或不同检索配置，行为完全不同。**

## 工作原理

1. **拆结构**：模板按“角色 → 硬规则 → 上下文（政策/订单）→ 示例 → 任务 → 输出格式 → 兜底”分段，每段职责单一。
2. **声明变量**：列出必填与可选变量、类型、来源系统、长度上限；缺失必填变量直接拒绝渲染。
3. **隔离数据**：用标签包裹外部内容（`<policy>`、`<order>`），避免数据被解析成模板指令。
4. **计算指纹**：对模板文本取哈希，作为缓存键与日志字段，便于比对线上与仓库。
5. **回归验证**：固定测试集覆盖每类意图与拒答场景，比较改动前后的逐条结果。
6. **灰度发布**：按流量比例或客服分组替换模板，观察准确率、拒答率、平均 token 与延迟。
7. **保留旧版**：旧版本至少保留一个发布周期，回滚只需要改一个版本号。

**模板改动必须单独可回滚，不能和业务代码绑在同一次发布里。**

## 架构与选型

| 存放方式 | 适用 | 优点 | 不适用/代价 |
| --- | --- | --- | --- |
| 代码内字符串常量 | 原型、单入口小项目 | 零基础设施 | 改一句话就要发版，无法灰度 |
| 仓库内模板文件 + 渲染层 | 多数生产项目 | 可评审、可 diff、可按版本号加载 | 需要自建加载与缓存逻辑 |
| 配置中心/数据库存储 | 需要非研发人员调整 | 改完即生效，可做 A/B | 缺少评审容易误改，需权限与审计 |
| 厂商提示词管理服务 | 已在用某云平台 | 与模型、缓存打通，少维护 | 绑定供应商，迁移成本高 |

选型依据：**变更频率与变更人决定存放位置**。研发主导、变更经评审的，放仓库；运营主导、需要热更新的，放配置中心并强制审批与审计。

## 最小示例

下面是一个最小模板 + 渲染函数，包含必填校验与指纹计算。

```python
from string import Template
import hashlib

# 模板用 $变量 占位；正文中若需要字面量 $，写成 $$ 转义
TEMPLATE_TEXT = """你是晴空商城售后助手（提示词版本 $prompt_version）。
规则：$rules
<order>$order_json</order>
<policy>$policy_text</policy>
客服问题：$question
"""
TEMPLATE = Template(TEMPLATE_TEXT)
REQUIRED = ["rules", "order_json", "policy_text", "question"]

def template_hash(text: str) -> str:
    # 取前 8 位十六进制作为指纹：足够区分版本，又能直接放进日志和缓存键
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:8]

def render(prompt_version: str, values: dict) -> str:
    # 先校验再渲染：缺变量就报错，避免把空上下文送给模型
    missing = [k for k in REQUIRED if not values.get(k)]
    if missing:
        raise ValueError(f"缺少必填变量: {missing}")
    return TEMPLATE.substitute(
        prompt_version=prompt_version,
        **{k: values[k] for k in REQUIRED},
    )

print("模板指纹:", template_hash(TEMPLATE_TEXT))
print(render("v7", {
    "rules": "退款>500 元只给建议并转人工",
    "order_json": '{"order_id":"QK-2026-004821","amount":800}',
    "policy_text": "P-03 七天无理由退货",
    "question": "这单能退吗",
}))
try:
    render("v7", {"rules": "x", "order_json": "{}"})
except ValueError as e:
    print("预期失败:", e)
```

预期输出：

```text
模板指纹: db8bba39
你是晴空商城售后助手（提示词版本 v7）。
规则：退款>500 元只给建议并转人工
<order>{"order_id":"QK-2026-004821","amount":800}</order>
<policy>P-03 七天无理由退货</policy>
客服问题：这单能退吗

预期失败: 缺少必填变量: ['policy_text', 'question']
```

关键设计选择：用 `string.Template` 而不是 f-string。f-string 会让用户输入里的 `{}` 参与解析，甚至直接抛异常；`Template` 只在固定位置替换声明过的变量，渲染结果可预测。

前缀顺序也有成本含义：稳定的内容（系统规则、工具定义）放前面，可变内容（订单、问题）放后面，才能命中厂商的*提示缓存*。Amazon Bedrock 文档说明缓存按 `tools → system → messages` 顺链生效，改动靠前的段落会让靠后的缓存全部失效，因此**调整模板顺序可能比改一句话更贵**。

## 动手实验

**前置条件**：Python 3.9+，无需 API Key。

**步骤**：

1. 保存代码为 `prompt_template.py`，运行并记录指纹。
2. 把模板里的“规则：”改为“硬性规则：”，重跑，观察指纹变化。
3. 在 `values` 中把 `policy_text` 改为空字符串，确认抛出异常。
4. 把 `question` 的值改为包含 `$prompt_version` 的文本，观察是否被二次替换。
5. 给模板加一个可选变量 `$channel`，用默认值处理缺失情况。

**预期结果**：第 2 步指纹改变（说明指纹能反映内容变更）；第 3 步抛出 `缺少必填变量`；第 4 步不会发生二次替换，因为 `substitute` 只解析模板本身；第 5 步应通过“先填默认值再校验”的方式实现。

**验证方法**：同一模板文本两次计算指纹必须相同；不同模板文本指纹必须不同。若第 4 步出现了替换，说明实现用了不安全的反复渲染，需要修正。

**清理方法**：删除 `prompt_template.py`，不产生外部资源。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 答复里出现“根据政策 ”，后面空白 | 模板变量为空但未校验 | 打印渲染后的完整提示词 | 增加必填校验，缺失即拒绝请求 |
| 改了提示词但线上没变化 | 加载了缓存或旧版本号 | 对比响应日志里的模板指纹 | 指纹纳入响应与日志，按指纹核对 |
| 回滚后行为仍异常 | 只回滚了模板，模型或检索配置没回滚 | 检查版本三元组记录 | 三者绑定发布，回滚时一起切换 |
| 用户输入里有 `{}` 导致渲染报错 | 使用 f-string 拼接用户数据 | 构造含花括号的输入复现 | 改用 `Template` 或先在数据侧转义 |
| 提示缓存命中率低 | 模板把可变内容放在最前 | 检查内容顺序与缓存命中指标 | 静态内容前置，动态内容后置 |

## 安全与生产注意事项

**<u>允许非研发人员直接在线修改提示词而不留审计，等于开放了一条无记录的行为变更通道。</u>** 每次修改都要记录改动人、时间、前后指纹与审批单号，否则事故复盘无法定位。

**<u>模板里写死密钥、内部系统地址或未脱敏示例会造成泄露。</u>** 模板会被渲染、缓存、写日志，也可能被用户诱导回显；敏感值应通过服务端注入，且不进入提示词。

此外，模板发布应与评测绑定：没有通过回归集的模板不允许进入灰度，避免“改一句试试”直接面向生产流量。

## 本课总结

- 提示词是生产配置，需要模板结构、变量校验、版本号与指纹。
- 版本要按“模板 + 模型 + 检索配置”三元组记录，单打模板版本不足以复现行为。
- 变量缺失必须在渲染前拦截，不能把空上下文交给模型。
- 静态内容前置、动态内容后置，既利于缓存也利于模型关注重点。
- 变更流程应是：评审 → 回归 → 灰度 → 观察 → 保留旧版以便回滚。

## 思考题

如果团队既想“运营能当天改话术”，又想“任何改动都能审计和回滚”，你会怎么设计存放与发布机制？请写出关键控制点。

参考思路：模板放配置中心但强制走“草稿—评审—发布”三态；每次发布自动生成指纹与版本号，关联回归结果；生产只读取已发布版本，回滚只需切换版本指针；同时保留仓库镜像做 diff 与灾备。

## 小测

1. 模板指纹的作用是什么？
2. 为什么说“只给提示词打版本号”不足以复现一次请求的行为？
3. 下列哪种存放方式最适合“运营当天改话术且需审计”？  
   A. 代码内字符串常量　B. 配置中心 + 审批与版本指针　C. 直接改数据库字段　D. 写在文档里
4. 为什么用户输入不适合用 f-string 拼进模板？
5. 场景题：一次模板改动上线后，答复格式从 JSON 变成散文。请给出排查顺序与回滚方案。

## 答案与解析

1. 用内容哈希标识“这一版模板到底是什么”，可放进日志、响应与缓存键，用来核对线上与仓库是否一致，也便于定位缓存污染。
2. 因为行为还取决于模型版本与检索配置（切分、Top-K、重排）。同一模板配不同模型或不同检索结果，输出会明显不同，缺一不可复现。
3. **B。** 配置中心能热更新，配合审批与版本指针可审计、可回滚。A 需要发版；C 缺少评审与记录；D 不参与运行时加载。
4. f-string 会把用户输入中的花括号当作格式语法参与解析，可能抛异常或被意外替换，导致模板结构被破坏，也放大注入风险。
5. 先核对响应日志里的模板指纹与版本三元组，确认是否真的加载了新模板；再看渲染后的完整提示词是否缺少输出格式段或变量为空；确认原因后把版本指针切回上一版（模板、模型、检索一起切），并用回归集验证格式恢复，最后把该样本加入回归集。
