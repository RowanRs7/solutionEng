# 模型客户端、供应商适配层与 AI Gateway

## 为什么需要学习

晴空商城的售后助手最初只接了一家模型供应商。三个月后出现三个新需求：为控制成本，简单问题走便宜的小模型；供应商 A 在境内、供应商 B 在境外，需要按数据合规要求路由；高峰期供应商 A 限流时自动切换。

如果代码里散落着 `if vendor == "a"`，这三个需求会变成几十处改动，而且每处都要重新处理超时、重试、Token 统计。更麻烦的是，没人能回答“昨天答复质量下降，是换了模型、换了 Prompt，还是回退到了备用供应商”。

> **核心结论：** 适配层把“不同供应商”收敛成一个接口，网关把“鉴权、配额、审计、密钥”收敛成一个入口；两者解决的是不同问题，不能相互替代。

## 学习目标

完成本课后，你能够：

- 定义一个与供应商无关的模型调用接口，覆盖文本、工具调用与用量字段。
- 把供应商错误归一化为固定的错误分类，并区分为可重试与不可重试。
- 设计带*抖动*的指数退避重试，并说明重试预算如何被 deadline 约束。
- 判断某项能力属于适配层、网关还是业务应用，并说明理由。

## 前置知识

- 回看上一课：[FastAPI 接入模型服务](02-fastapi-and-model-integration.md)。
- 知道 HTTP `429`、`5xx` 与 `Idempotency-Key` 的基本含义。
- 了解模型请求中的 `messages`、`tools` 与 `usage` 字段用途。
- 理解“幂等”是指同一请求重复执行的结果一致。

## 业务场景

售后助手要在三种情况下选择模型：普通政策问答（便宜、快）、复杂退款判断（强推理、贵）、批量夜间归档（可排队、可慢）。供应商 A 支持工具调用但限流严格，供应商 B 上下文更长但延迟高。客服主管还要求：“高峰期可以降级，但必须让我知道这轮答复不是主模型给的。”

这三条要求分别落在三个位置：**统一接口**（适配层）、**路由与回退**（适配层或网关）、**降级标记与审计**（网关 + 应用）。

## 核心概念

| 概念 | 含义 | 谁负责 | 常见误区 |
| --- | --- | --- | --- |
| *适配层*（adapter） | 把各供应商的请求/响应/错误翻译成统一模型的代码层 | 应用内库或独立服务 | 以为它只做字段改名 |
| *统一响应模型* | 与供应商无关的结果结构：文本、工具意图、用量、结束原因 | 适配层 | 直接返回供应商原始 JSON |
| *错误分类*（error taxonomy） | 把错误归为 `rate_limit`、`timeout`、`auth`、`invalid_request`、`content_filter`、`upstream_5xx` 等 | 适配层 | 用字符串匹配错误消息 |
| *路由*（routing） | 按问题类型、租户、成本选择模型别名 | 适配层/网关 | 在业务代码里写死模型名 |
| *回退*（fallback） | 主模型失败或超预算时切换备用模型 | 适配层 | 无标记地静默切换 |
| *熔断*（circuit breaker） | 连续失败后暂时停止调用某供应商 | 网关/适配层 | 用重试代替熔断 |
| *AI Gateway* | 统一的模型流量入口，负责密钥托管、鉴权、配额、日志、缓存 | 平台团队 | 让它承担业务规则判断 |

一张表看清分层差异：

| 能力 | 适配层 | AI Gateway | 业务应用 |
| --- | --- | --- | --- |
| 供应商字段翻译 | ✅ | ✅（也可只在网关做） | ❌ |
| 密钥托管与轮换 | ❌ | ✅ | ❌ |
| 租户限流与配额 | ❌ | ✅ | ❌ |
| 模型路由与回退 | ✅ | ✅ | 决定“优先级” |
| 工具权限判断 | 只做参数校验 | 可做统一拦截 | ✅ 最终裁决 |
| 业务规则（能否退款） | ❌ | ❌ | ✅ |

**适配层的核心产出不是“少写几行 if”，而是一个可测试的接口**：供应商行为可以被打桩，重试与回退逻辑可以被单元测试覆盖。

## 工作原理

1. **接收统一请求**：业务侧只传 `model_alias`（如 `fast-model`）、消息、工具清单与预算，不传供应商名。
2. **解析别名**：路由表把别名映射为候选链，例如 `fast-model → [vendor-a/small, vendor-b/small]`，并带上各自的价格与上下文上限。
3. **组装供应商请求**：按该供应商的字段规范转换消息与工具定义；缺失能力（如不支持工具调用）时在链中跳过。
4. **发送并计时**：携带 `deadline` 与 `trace_id`；连接超时与读取超时分别设置。
5. **归一化错误**：把 HTTP 状态、错误体、网络异常映射为固定分类；分类决定后续动作。
6. **重试决策**：仅对 `rate_limit`、`timeout`、`upstream_5xx` 重试；`auth`、`invalid_request`、`content_filter` 立即失败——重试不会变好。
7. **退避与抖动**：第 n 次重试等待约 `base × 2^n`，再乘随机系数；避免同一时刻大量客户端同时重试造成二次拥塞。
8. **检查预算**：若下一次重试预计超出 deadline，直接返回当前错误，不再等待。
9. **归一化响应**：抽取文本、工具调用意图、`finish_reason`、Token 用量与模型标识。
10. **记录与计量**：每次尝试都记一条（含供应商、耗时、结果），最终结果单独记一条，供成本归属与质量分析。

网关在这一流程外再包一层：校验调用方身份、检查租户配额、注入供应商密钥、缓存可复用结果、把请求与响应写入审计。**网关不知道“这个客服能不能退这单”，那仍然是应用的职责。**

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 直接调各家 SDK | 单供应商、验证阶段 | 多供应商、需要统一治理 | 最快；差异散落，切换成本极高 |
| 应用内自建适配层 | 1–2 个供应商、团队有工程能力 | 多团队共用、需要统一配额 | 控制力强；每个应用各写一遍网关能力 |
| 开源/自托管 AI Gateway | 多供应商、需要统一密钥与配额 | 极简场景（多一层运维） | 功能齐；需要评估升级与故障域 |
| 商业网关或云厂商托管 | 合规要求明确、缺少平台团队 | 数据不能出网、需深度定制 | 上线快；成本与锁定风险 |

选型依据：**供应商数量 ≥ 2 且预计会变** → 适配层必须有；**多个应用共用同一批密钥与配额** → 需要网关；**有数据出境或私有化要求** → 网关必须能自托管。反过来，如果只有一个内部应用、一个供应商、没有配额要求，先写一个薄适配层即可，不必引入网关。

还要评估*故障域*：网关在关键路径上，多一跳就多一个可能失败的点。若采用网关，必须给它单独的 SLO、容量余量与降级开关（如“网关不可用时应用可直连只读备用供应商”）。

## 最小示例

下面的脚本用标准库模拟适配层：两个供应商、统一错误分类、按候选链回退、带抖动的指数退避。

```python
import random, time

class ProviderError(Exception):
    def __init__(self, kind: str, detail: str = ""):
        self.kind = kind            # 归一化错误类型：与供应商的报错格式无关
        self.detail = detail

RETRYABLE = {"rate_limit", "timeout", "upstream_5xx"}   # 只有这些值得重试

def vendor_a(payload):
    # 模拟供应商 A 触发限流；真实实现中这里解析 429 响应
    raise ProviderError("rate_limit", "429 too many requests")

def vendor_b(payload):
    # 模拟供应商 B 成功返回；真实实现中这里把原始响应翻译成统一结构
    return {"text": "订单 A1024 支持 7 天无理由退货", "model": "vendor-b-large",
            "usage": {"in": 812, "out": 96}}

ADAPTERS = {"vendor-a": vendor_a, "vendor-b": vendor_b}

def invoke(model_alias, payload, max_attempts=3):
    chain = {"fast-model": ["vendor-a", "vendor-b"]}[model_alias]
    attempts = []
    for i in range(max_attempts):
        name = chain[min(i, len(chain) - 1)]     # 失败后沿候选链下移，而不是原地重试同一家
        try:
            out = ADAPTERS[name](payload)
            attempts.append({"attempt": i + 1, "vendor": name, "result": "ok"})
            return {"ok": True, "data": out, "attempts": attempts}
        except ProviderError as err:
            retryable = err.kind in RETRYABLE   # 分类决定动作，而不是异常类型
            attempts.append({"attempt": i + 1, "vendor": name,
                             "result": err.kind, "retryable": retryable})
            if not retryable:                   # 参数错误重试只会浪费配额
                break
            delay = min(2 ** i * 0.01, 0.08) * random.uniform(0.5, 1.5)
            time.sleep(delay)                   # 抖动退避：避免重试同时到达
    return {"ok": False, "attempts": attempts}

result = invoke("fast-model", {"question": "订单 A1024 能退吗"})
for a in result["attempts"]:
    print(a)
print("final:", result["ok"], result.get("data", {}).get("text"))
```

预期输出（已实跑，抖动系数会让等待时间略有变化）：

```text
{'attempt': 1, 'vendor': 'vendor-a', 'result': 'rate_limit', 'retryable': True}
{'attempt': 2, 'vendor': 'vendor-b', 'result': 'ok'}
final: True 订单 A1024 支持 7 天无理由退货
```

真实实现还需要三样东西：一是把 `attempts` 写进审计事件（否则“降级了”这件事无人知晓）；二是重试前用 `deadline` 做预算判断；三是给 `vendor-a` 加熔断，避免每次请求都先撞一次限流。

## 动手实验

**前置条件**：`python3`（3.9+），无需网络与密钥。

**步骤**：

1. 保存脚本为 `/tmp/aiarch/adapter.py`，运行 `python3 /tmp/aiarch/adapter.py`。
2. 把 `vendor_a` 改为 `raise ProviderError("invalid_request")`，再运行，观察是否只尝试一次。
3. 把 `RETRYABLE` 改成空集合，重复第 1 步，观察行为变化。
4. 在 `invoke` 中加入 `deadline_ms` 参数，当剩余预算小于预估退避时间时提前返回。

**预期结果**：第 1 步两次尝试后成功；第 2 步只有一条 `invalid_request` 记录且 `ok=False`；第 3 步不再回退到 `vendor-b`；第 4 步在预算不足时输出失败而不 sleep。

**验证方法**：检查 `attempts` 列表长度与每次的 `vendor` 是否沿候选链移动；用 `time.perf_counter()` 包围调用，确认总耗时不因重试无限增长。

**清理方法**：删除 `/tmp/aiarch/adapter.py`；无外部资源残留。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 切换供应商后答复格式错乱 | 适配层只改了字段名，未统一 `finish_reason` 与工具意图结构 | 对比两家响应归一化后的键是否一致 | 定义统一响应模型并加契约测试 |
| 高峰期重试风暴 | 无抖动、无预算、所有客户端同时重试 | 看重试次数与供应商 `429` 曲线是否同步上升 | 指数退避 + 抖动 + 熔断 |
| 参数错误也重试三次 | 按异常类型而非错误分类判断 | 查看审计中同一 `invalid_request` 的尝试次数 | 归一化错误分类，非可重试立即失败 |
| 成本突然翻倍 | 回退链把简单问题也送到贵模型 | 按 `model_alias` 与实际 `model` 统计调用量 | 路由与回退分开配置，回退需预算与标记 |
| 网关故障导致全站不可用 | 网关是单点，应用无直连兜底 | 人为关闭网关观察影响面 | 网关多副本 + 应用侧只读兜底 + 明确降级开关 |

## 安全与生产注意事项

**<u>把供应商密钥分发到每个业务应用，等于把密钥泄露面扩大到整个集群。</u>**密钥应集中在网关或密钥管理服务，业务只持有网关的短期凭据；轮换时用双密钥过渡并监控旧密钥调用量。

**<u>回退到备用模型却不做标记，会让质量下降变成“看不见的静默故障”。</u>**响应中必须带实际使用的模型与是否降级的标记，审计与看板按供应商维度拆分成功率与用户反馈。

**<u>对非幂等操作（如调用退款工具）做自动重试，可能造成重复执行。</u>**重试只应覆盖“读取类”调用；写操作必须具备幂等键，并由业务侧确认重试安全。

此外，跨境路由会把客服问题与订单信息发送到境外服务。路由表必须能按租户或数据类型限制可用的供应商，并把该限制写成可测试的配置，而不是文档里的口头约定。

## 本课总结

- **适配层解决“供应商差异”**：统一请求、响应与错误分类，让业务只面对模型别名。
- **网关解决“治理”**：身份、密钥、配额、审计、缓存，不承担业务规则。
- **重试要分类、要退避、要抖动、要预算**，四者缺一都会放大故障。
- **回退必须有标记**，否则质量下降无法被观测，也无法归因。
- **网关是关键路径上的组件**，必须设计故障域与兜底路径。

## 思考题

如果业务方要求“任何情况下都要有答复”，而技术团队认为“没有可靠依据时应该拒答”，你会如何在适配层与网关之间划分责任，使两种诉求都能被实现并被审计？请说明拒答、降级、回退三种结果的判定位置。

参考思路：适配层负责“技术可用性”（重试、回退、超时后返回明确错误），业务应用负责“内容可用性”（依据不足时拒答并给出转人工路径），网关负责记录最终结果类型与所用模型。三者都不应单方面把“失败”包装成“成功答复”。

## 小测

1. 下列哪项最应该由 AI Gateway 负责？  
   A. 判断客服是否有权查看该订单　B. 集中托管供应商密钥并轮换  
   C. 决定退款金额上限　D. 生成答复文本
2. 为什么重试需要“抖动”（jitter）？
3. 适配层把 `content_filter` 归类为不可重试，理由是什么？
4. 回退到备用模型后，响应中至少应记录哪两项信息？
5. 场景题：供应商 A 在 10:00 开始大量返回 `503`，你的系统有重试与回退。请说明接下来 5 分钟内你会观察哪些指标、如何判断是“供应商故障”还是“自身流量突增”。

## 答案与解析

1. **B。**密钥托管与轮换是典型的平台横切能力。A 与 C 需要业务数据与规则，属于业务系统；D 是模型职责。
2. 因为失败往往同时发生在大量客户端上，若退避时间一致，重试会按同一节奏再次打满上游，形成二次拥塞。随机抖动把重试打散到不同时刻，这是分布式系统重试的标准做法。
3. `content_filter` 表示请求或响应被策略拦截，重试同样的输入不会改变结果，只会增加成本与延迟；正确做法是记录原因并走人工或改写输入的流程。
4. 实际使用的模型（含供应商）与是否发生降级。缺少前者无法做成本归属与质量对比，缺少后者无法解释“为什么这次答复变差”。
5. 观察：按供应商拆分的错误率与延迟、重试次数、候选链切换次数、入口 QPS 与租户级流量。若入口 QPS 平稳而 A 的错误率陡增，判断为供应商故障并触发熔断；若某租户 QPS 异常升高且错误随之上升，判断为自身流量问题，应先限流再考虑回退。
