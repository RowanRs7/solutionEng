# 生产级 AI 请求的完整链路

## 为什么需要学习

晴空商城的“售后智能助手”在演示环境里表现不错：粘贴订单号、问一句“能退吗”，几秒后给出答复。上线两周后，客服主管反馈三类问题：偶尔十几秒没有任何反应；有的答复引用了早已下线的旧政策；某次退款建议被重复提交，财务收到两条退款单。开发人员打开日志，只能看到一条 `POST /chat 200`，无法回答“慢在哪一步、用了哪份政策、谁批准了工具调用”。

这类问题的共同原因是：**一个 AI 请求被当成一次函数调用，而不是一条有阶段、有预算、有证据的链路**。模型只是链路中的一段，前面有身份、准入、检索，后面有工具、校验与审计；任何一段没有契约，整条链路就不可运维。

> **核心结论：** 生产级 AI 请求的可靠性来自阶段划分与每段的显式契约，而不是换一个更强的模型。

## 学习目标

完成本课后，你能够：

- 描述一次 AI 请求从接入到审计经过的阶段，并说明每段的输入输出。
- 为每个阶段写明超时值、失败策略、降级方式和责任团队。
- 用*请求信封*与*剩余预算*解释为什么总延迟可被约束。
- 判断某项能力应放在边缘网关、应用服务还是业务系统中。
- 识别链路上最容易造成事故的三个位置，并给出缓解措施。

## 前置知识

- 回看上一单元：[工具调用、Workflow 与 Agent](../05-tools-and-agents/00-overview.md)。
- 理解 HTTP 请求/响应、状态码与连接超时的含义。

- 用过任意模型服务的 `curl` 调用，见过 `messages` 与 `tools` 字段。

## 业务场景

晴空商城的售后流程是：客服在工单页提问 → 系统检索售后政策与订单 → 生成答复或退款建议 → 客服人工确认 → 调用退款工具。本课只写这条链路的“骨架”，不写 Prompt 技巧，也不写检索算法（分别在第三、四单元）。

三个硬约束决定了链路形态：

- 客服盯着屏幕，**首字超过 3 秒就会转人工**，因此不能把全部计算做完再返回。
- 退款工具**不可重放**，同一笔订单重复调用会产生真实的资金损失。
- 审计必须能回答“谁在何时、依据哪份政策、看到模型给出的什么建议”，用于事后复盘与合规检查。

## 核心概念

| 阶段 | 职责 | 典型实现 | 缺失时的表现 |
| --- | --- | --- | --- |
| *边缘网关* | TLS 终止、鉴权、限流、路由、注入 `trace_id` | API Gateway、Ingress、自建网关 | 每个服务各自解析令牌，口径不一致 |
| *准入控制* | 配额、并发上限、租户开关 | 限流中间件、配额服务 | 一个租户的批量脚本拖垮全站 |
| *会话装配* | 取历史消息，按 Token 预算裁剪 | 会话存储 + 裁剪策略 | 上下文超长报错，或旧消息污染当前问题 |
| *检索* | 按权限召回政策与订单事实 | 向量库、关键词库、订单 API | 引用不存在的政策，产生“幻觉依据” |
| *模型调用* | 生成答复或工具调用意图 | 供应商 API、自建推理 | 直接暴露供应商错误与内部凭据 |
| *工具执行* | 鉴权、参数校验、幂等、执行 | 内部服务、MCP 工具 | 越权操作、重复退款 |
| *审计与计费* | 记录证据、统计 Token 与成本 | 事件总线、日志、指标 | 事后无法复盘，账单无法归属 |

两个贯穿全链路的概念：

- *请求信封*（request envelope）：随请求传递的元数据，至少包含 `trace_id`、`tenant_id`、`user_id`、`session_id`、*配置版本坐标*（本课记为 `bundle`）与 `deadline_ms`。
- *截止时间*（deadline）：从接入时刻起算的**绝对**剩余时间预算；与之相对的*超时*（timeout）只是单跳上限。<u>把每跳的 timeout 当作 deadline 传递，会让总延迟随跳数线性放大</u>——三跳各 10 秒，用户就要等 30 秒。

**网关不是“AI 功能”的容器。** 它擅长与业务无关的横切能力（身份、限流、日志、脱敏），不擅长判断“这个客服能不能退这单”。

## 工作原理

一次请求按下列顺序推进，每一步都必须能在审计事件中看到开始时间、耗时与结果：

1. **接入与身份**：边缘网关校验访问令牌，解析出租户与用户，生成 `trace_id`，写入请求信封；未通过直接返回 `401`，不进入后续阶段。
2. **准入**：检查租户配额与并发占用，超限返回 `429` 并在响应头给出 `Retry-After`；被拒绝的请求同样记一条审计，否则无法解释“用户说点了没反应”。
3. **会话装配**：读取会话历史，按模型上下文预算裁剪；裁剪规则要固定，否则同一问题在长会话中会得到不同结果。
4. **检索**：先按用户权限过滤，再召回政策片段与订单事实；每条片段带上 `doc_id`、版本与生效区间。
5. **组装 Prompt**：模板版本 + 检索片段 + 工具清单 + 输出格式约束，一并写入信封的配置坐标。
6. **模型调用**：经*适配层*（统一供应商差异的中间层，见第 3 课）发出请求，传入的是**剩余预算**而非固定超时。
7. **工具调用**：模型返回工具意图后，先做权限判断与参数校验，再用幂等键执行；结果回填后可再进入一次模型调用。
8. **输出校验**：检查结构是否合法、引用是否存在于本次检索结果、是否包含敏感字段、是否需要人工确认。
9. **审计与计费**：写一条事件，包含阶段耗时、模型与 Prompt 版本、Token 用量、工具调用与最终去向（自动答复 / 转人工）。
10. **返回或流式推送**：首字尽早推给前端，后续增量补发（见第 4 课）。

这十步里最关键的是第 6 步之前的**预算分配**：总 deadline 减去已消耗，剩下的才是模型可用的时间。若剩余不足，链路应主动降级而不是硬等——例如跳过工具、返回“已转人工”。

## 架构与选型

| 方案 | 适用 | 不适用 | 主要权衡 |
| --- | --- | --- | --- |
| 全部逻辑在单体应用内 | 单租户、日请求数千、团队 2–3 人 | 多租户、需要统一配额与审计 | 起步快；横切能力重复实现，难以统一治理 |
| 应用服务 + 独立 AI Gateway | 多租户 SaaS、多供应商、需审计合规 | 极低延迟要求（网关多一跳） | 统一鉴权/限流/日志/脱敏；网关成为关键路径，需高可用 |
| 托管 Agent 平台 | 快速验证、无强定制需求 | 深度定制工具权限、私有化部署 | 上线快；可观测性与数据驻留受平台限制 |

选型依据按顺序问四个问题：租户数量与隔离要求、是否需要跨供应商切换、审计留存是否有强制要求、团队能否承担网关的运维成本。前两个问题任一为“是”，独立网关通常划算；四个都为“否”，先做单体。

需要提醒的是，**网关只做策略执行，不做策略决定**。“这个客服是否有权退这单”必须由业务系统回答；网关可以缓存结论（短 TTL），但不能替代。

## 最小示例

下面的脚本用标准库模拟一次请求的预算推进：每个阶段有固定耗时，一旦某阶段耗时超过剩余预算就跳过并停止。

```python
import json
from dataclasses import asdict, dataclass, field

@dataclass
class Envelope:
    # 请求信封：随链路传递的最小元数据集
    trace_id: str
    tenant_id: str
    user_id: str
    session_id: str
    bundle: str          # 配置版本坐标：Prompt + 模型 + 知识库快照
    deadline_ms: int     # 绝对预算，不是单跳超时
    spent: dict = field(default_factory=dict)

# 阶段名与预估耗时（毫秒）；真实系统里耗时来自观测，不是拍脑袋
STAGES = [("auth", 120), ("retrieve", 950), ("model", 1100), ("tools", 700)]
TOTAL_DEADLINE = 3000    # 客服 3 秒首字目标的预算上限

env = Envelope("tr-7f3a", "t-qk", "u-2881", "s-91",
               "after-sales@2026.10.3", TOTAL_DEADLINE)
elapsed = 0
for name, cost in STAGES:
    remaining = TOTAL_DEADLINE - elapsed      # 每步都重算，避免预算被“各跳独立超时”吃光
    if cost > remaining:                       # 预算不足：显式跳过，而不是硬等
        env.spent[name] = 0
        print(f"[{name}] SKIP cost={cost}ms remaining={remaining}ms reason=budget")
        break
    elapsed += cost
    env.spent[name] = cost
    print(f"[{name}] ok cost={cost}ms remaining={TOTAL_DEADLINE - elapsed}ms")

print(json.dumps(asdict(env), ensure_ascii=False, indent=2))
```

预期输出（本仓库已用 `python3` 实跑，末尾的 JSON 为信封内容，此处省略部分字段）：

```text
[auth] ok cost=120ms remaining=2880ms
[retrieve] ok cost=950ms remaining=1930ms
[model] ok cost=1100ms remaining=830ms
[tools] ok cost=700ms remaining=130ms
{ "trace_id": "tr-7f3a", "bundle": "after-sales@2026.10.3",
  "spent": {"auth": 120, "retrieve": 950, "model": 1100, "tools": 700} }
```

把 `TOTAL_DEADLINE` 改成 `2500`，`tools` 阶段就会被标记 `SKIP`。这个“跳过”动作正是生产中应触发的降级：本轮不调用退款工具，改为返回建议并转人工。

## 动手实验

**前置条件**：本机有 `python3`（3.9+），无需网络与任何 API Key。

**步骤**：

1. 把上面的脚本保存为 `/tmp/aiarch/budget.py`。
2. 运行 `python3 /tmp/aiarch/budget.py`，记录四个阶段的 `remaining` 序列。
3. 把 `TOTAL_DEADLINE` 改为 `2500`，再运行一次。
4. 把 `STAGES` 中 `retrieve` 耗时改为 `1600`，观察模型阶段是否被压缩。

**预期结果**：`remaining` 单调递减；预算不足的阶段输出 `SKIP` 且不写入 `spent`。

**验证方法**：检查任意时刻 `sum(spent.values()) + remaining == deadline_ms`；把脚本中的阶段耗时相加，结果应小于等于 `deadline_ms` 才全部执行。

**清理方法**：删除 `/tmp/aiarch/budget.py` 即可，不产生其他文件与网络副作用。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 首字要 8–12 秒 | 检索与模型串行，且检索未命中缓存 | 看审计事件里 `retrieve` 与 `model` 的耗时 | 并行化可并行的检索、加缓存、缩短 Prompt |
| 偶发 `502`，日志无细节 | 上游超时被网关统一改写 | 用 `trace_id` 找最后一个成功阶段 | 区分 `504`（上游超时）与 `502`（上游错误），保留上游错误码 |
| 同一订单出现两条退款单 | 工具无幂等键，重试即重放 | 查审计中同一 `tool_call` 的出现次数 | 幂等键 + 人工确认 + 工具侧去重 |
| 答复引用了不存在的政策条款 | 检索片段未带版本，或引用未校验 | 抽查响应中的 `doc_id` 是否在本次召回集内 | 引用白名单校验，缺失则拒答 |
| 客服说“点提交没反应”，审计无记录 | 请求在准入阶段被拒且未记事件 | 按时间窗口查网关访问日志 | 被拒请求也写审计，返回明确错误码 |

## 安全与生产注意事项

**<u>原样保存完整 Prompt、检索原文与用户输入，会把个人信息、订单详情甚至密钥扩散到日志系统。</u>**审计需要的是“证据索引”，不是全文镜像：保存 `doc_id`、版本、哈希与决策结果，敏感字段按级别脱敏，并给日志系统单独设定访问控制与保留期。

**<u>服务间直连模型供应商会绕过网关的鉴权、配额与脱敏，形成一条影子链路。</u>**必须用网络策略限制出站目标，供应商密钥只下发给适配层，不进入业务容器；同时监控“无 `trace_id` 的模型调用”这一类异常指标。

**<u>把权限判断写在 Prompt 里（如“你只能退款 500 元以下”）等于没有权限控制。</u>**模型可能被注入或误判，权限必须由工具执行侧强制校验。

## 本课总结

- **AI 请求是一条分阶段链路**，模型只是其中一段，前后都需要契约。
- **请求信封**承载 `trace_id`、租户、用户与配置版本，是排障与审计的锚点。
- **deadline 是绝对预算**，跨跳传递；单跳 timeout 不能替代它。
- 网关负责横切策略的**执行**，业务规则与权限的**决定**仍归业务系统。
- 每个阶段都要有超时、降级与责任归属，否则事故只能靠猜。

## 思考题

检索服务偶发超时。你更愿意“降级为无检索直接生成”，还是“直接失败并提示转人工”？请写出你的判断依据，并说明对不同问题类型（政策咨询、订单查询、金额计算）是否应有不同策略。

参考思路：先判断错误代价。政策与金额类问题在缺少依据时生成，等于制造看似可信的错误信息，失败并转人工更安全；订单查询可以降级为“我这边的订单接口暂时不可用，请稍后重试”，不生成事实性内容。策略还应与用户可见提示、SLO 指标（转人工率）和审计记录联动，而不是一个全局开关。

## 小测

1. 下列关于 deadline 的说法，哪一项正确？  
   A. 每跳设置相同超时即可等价于 deadline  
   B. deadline 是绝对剩余预算，应随请求传递并逐跳扣减  
   C. deadline 只对模型调用生效  
   D. deadline 越长系统越可靠
2. 网关最不适合承担下列哪项职责？  
   A. 校验访问令牌　B. 统一注入 `trace_id`　C. 判断某客服能否退某笔订单　D. 租户限流
3. 审计事件里最不应该原样保存的是什么？
4. 为什么被限流拒绝的请求也要写审计？
5. 场景题：产品经理要求“取消人工确认，让模型直接退款以提升效率”。作为架构师，你会提出哪些前置条件？请至少写三条，并说明理由。

## 答案与解析

1. **B。**deadline 是接入时刻算起的绝对预算，逐跳扣减才能约束总延迟。A 错在每跳重置会把总时间放大为各跳之和；C 错在检索与工具同样消耗预算；D 错在预算越长，用户等待越久，可靠性不等于时间充裕。
2. **C。**“能否退这单”取决于订单状态、金额规则与用户角色，必须由业务系统裁决；网关可以缓存结论，但不能成为规则来源。A、B、D 都是与业务无关的横切能力，正适合网关。
3. 完整 Prompt 与检索原文中的个人信息。审计需要可追溯的证据索引（`doc_id`、版本、哈希、决策），原文镜像会扩大泄露面并增加合规负担。
4. 因为“没有响应”也是一种用户可见结果。缺少拒绝记录时，无法区分“用户没点”“被限流”“网关故障”，排障与容量规划都会失去依据。
5. 参考要点：退款工具必须有幂等键与金额上限；必须有可撤销的时间窗或事后复核；必须有完整的“谁批准、依据哪份政策”审计；必须有失败补偿与对账流程；还需要业务方书面接受资金损失风险。理由统一指向一点：**模型输出是建议，不是授权**。
