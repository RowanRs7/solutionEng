# 限流、配额、多租户与成本归属

## 为什么需要学习

晴空商城的售后助手上线后第二个月，一家大客户用脚本批量调用接口做“自动回复”，瞬时达到 3000 QPS。网关没有租户级限制，模型供应商先返回 `429`，重试又把压力放大，最后所有租户一起变慢，客服页面转圈。月底账单出来，模型费用是上月的 4 倍，但没人说得清是哪个租户、哪个功能、哪次发布造成的。

这三个问题分别对应三件事：**限流保护系统不被压垮**、**配额约束每个租户的消费额度**、**成本归属让每一笔支出可解释**。它们常被混为一谈，但服务对象完全不同。

> **核心结论：** 限流管“此刻能不能进”，配额管“这个周期还能用多少”，成本归属管“钱花在哪里、值不值”。

## 学习目标

完成本课后，你能够：

- 区分限流、配额与预算告警，并说明各自拒绝时的响应语义。
- 用令牌桶实现租户级限流，解释容量与补充速率对突发流量的影响。
- 为多租户系统选择限流键，避免伪造与被绕过。
- 设计成本记账维度，计算单位成本（如每次解决工单的成本）并设置告警阈值。

## 业务场景

售后助手有三类调用方：客服工作台（人操作，低频高价值）、批量复核任务（可排队、可慢）、大客户 API（量大、要求稳定）。租户套餐按“每月包含 Token 额度 + 峰值 QPS”售卖。

财务要求月底能回答三个问题：每个租户消耗多少、哪个功能最贵、单次解决工单的成本是多少。运营要求：某租户接近额度时提前告警，而不是突然中断；高峰期批量任务应自动降速，不能和客服抢容量。

## 核心概念

| 概念 | 含义 | 拒绝时 | 作用对象 |
| --- | --- | --- | --- |
| *限流*（rate limiting） | 单位时间内允许的请求数或 Token 数 | `429` + `Retry-After` | 瞬时保护 |
| *并发限制* | 同时进行的请求上限 | `429` 或排队 | 保护连接与显存 |
| *配额*（quota） | 一个周期内可消费的总量 | `402`/`403` 或降级 | 商业约束 |
| *预算告警* | 用量达到阈值时通知 | 不拒绝，只提醒 | 运营与财务 |
| *令牌桶* | 以固定速率补充令牌，桶容量决定突发 | 桶空则拒绝 | 平滑突发 |
| *滑动窗口* | 统计最近 N 秒内的请求数 | 超阈值拒绝 | 精确控制速率 |
| *多租户* | 多个客户共享同一套系统但数据与额度隔离 | — | 隔离与公平 |
| *成本归属* | 把费用分摊到租户、功能与版本 | — | 分析与定价 |

| 算法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| 固定窗口计数 | 实现最简单 | 窗口边界会出现两倍突发 | 粗粒度内部限流 |
| 令牌桶 | 允许受控突发，长期速率稳定 | 需要保存桶状态 | 对外 API、租户限流 |
| 滑动窗口 | 速率精确 | 存储与计算开销较高 | 计费敏感的限流 |
| 并发限制 | 直接保护下游容量 | 不限制总量 | 模型调用、数据库连接 |

**限流键的选择决定它是否有效。** 用请求头里的 `X-Tenant-Id` 做键，调用方改个头就绕过了；必须用访问令牌中已验证的租户声明。同一租户内部还要有用户级限流，否则一个客服的脚本仍能拖垮自己的租户。

## 工作原理

1. **身份解析**：网关校验令牌，从令牌声明中取 `tenant_id`、`user_id`、套餐等级，绝不信任请求体自报的租户。
2. **多层准入**：依次检查全局并发、租户 QPS、用户 QPS、功能开关；任一层拒绝即返回 `429`，并给出最小重试间隔。
3. **配额预扣**：按请求预估 Token 上限（如输入长度 + 最大输出）预扣额度，避免“先花后记”导致超支。
4. **调用与计量**：记录实际输入/输出 Token、模型、耗时、bundle 坐标。
5. **结算**：用实际用量替换预扣值，差额退回；失败请求按规则退还（如上游故障不计费）。
6. **记账**：写入成本事件，维度包含租户、用户、功能、模型、Prompt 版本、是否缓存命中。
7. **聚合**：按小时/天汇总出账单与看板；计算单位成本（每次会话、每张解决工单）。
8. **告警**：额度使用到 50%/80%/100% 分级通知；异常增速（如 1 小时用掉日额度）单独告警。
9. **降级而非硬停**：接近额度时优先降级（缓存优先、小模型、批量任务排队），最后才拒绝。
10. **对账**：把内部计量与供应商账单按天比对，差异超过阈值触发排查。

预扣与结算的顺序很重要。<u>只做事后统计、不做预扣</u>，会让一个失控脚本在发现前把月度额度烧完；而只预扣不结算，会让额度余额随着失败请求不断漂移。

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 单机内存限流 | 单实例、内部服务 | 多副本（各算各的，实际额度翻倍） | 零依赖；不一致 |
| 集中式（Redis 等）限流 | 多副本、需要全局一致 | 极低延迟要求 | 一致；多一次网络往返与单点风险 |
| 网关内置限流 | 统一入口、按租户 | 需要按业务功能细粒度 | 运维简单；表达能力受产品限制 |
| 按 Token 计费配额 | 模型成本占主导 | 请求数才是瓶颈 | 贴近成本；预估困难 |
| 按请求数配额 | 廉价模型、固定成本 | 长上下文差异大 | 简单；可能被长 Prompt 钻空子 |

选型依据：**副本数与一致性要求**（多副本必须集中式）；**计费单位**（成本随 Token 波动则用 Token 配额）；**是否需要商业套餐**（需要则配额必须与合同绑定并支持调整）。还要考虑故障模式：限流存储不可用时应“放行”还是“拒绝”？<u>对内部低风险流量可放行并告警，对高风险或计费敏感流量应拒绝</u>，这个选择必须显式写入设计。

## 最小示例

下面的脚本用标准库实现令牌桶，模拟 20 QPS 的突发流量撞上 5 QPS 的租户上限。

```python
from dataclasses import dataclass

@dataclass
class TokenBucket:
    capacity: int          # 桶容量：允许的突发量
    refill_per_s: float    # 补充速率：长期平均速率上限
    tokens: float = 0.0
    last: float = 0.0

    def __post_init__(self):
        self.tokens = float(self.capacity)   # 初始满桶，避免冷启动误伤

    def allow(self, now: float, cost: int = 1) -> bool:
        # 先按经过时间补充，再判断；顺序反了会少补
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.refill_per_s)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost              # 只在允许时扣，拒绝不消耗令牌
            return True
        return False

bucket = TokenBucket(capacity=10, refill_per_s=5)
results = []
for i in range(40):
    now = i * 0.05                           # 每 0.05 秒一个请求 = 20 QPS
    results.append((now, bucket.allow(now)))
rejected = [t for t, ok in results if not ok]
print("requests=40 allowed=%d rejected=%d" % (40 - len(rejected), len(rejected)))
print("first_reject_at=%.2fs last_reject_at=%.2fs" % (rejected[0], rejected[-1]))
```

预期输出（已实跑）：

```text
requests=40 allowed=19 rejected=21
first_reject_at=0.65s last_reject_at=1.95s
```

前 0.65 秒没有拒绝，因为桶里的 10 个令牌吸收了突发；此后补充速率 5/s 跟不上 20 QPS，开始持续拒绝。这正是“允许短时突发、约束长期速率”的含义：把 `capacity` 调大，突发容忍更强，但恢复期的过载风险也更大。

成本记账只需要把用量乘以单价：

```python
PRICE_IN, PRICE_OUT = 1.0, 3.0        # 元 / 百万 Token，示例数字，非真实价格
def cost(in_tok, out_tok):
    return (in_tok * PRICE_IN + out_tok * PRICE_OUT) / 1_000_000

rows = [("t-qk", "policy-qa", 812, 96), ("t-qk", "refund-advice", 2400, 320),
        ("t-xh", "policy-qa", 640, 88)]
total = {}
for tenant, feature, i, o in rows:
    total[tenant] = total.get(tenant, 0.0) + cost(i, o)
print("t-qk=¥%.6f t-xh=¥%.6f per-ticket=¥%.6f"
      % (total["t-qk"], total["t-xh"], sum(total.values()) / len(rows)))
```

预期输出：`t-qk=¥0.004460 t-xh=¥0.000904 per-ticket=¥0.001788`。**上面的单价只是演示数字**；真实单价随供应商与模型变化，接入时必须从官方定价页读取，并把价格表本身纳入版本管理（截至 2026-10，各厂商定价页需重新核对）。

## 动手实验

**前置条件**：`python3`（3.9+），无需外部服务。

**步骤**：

1. 保存令牌桶脚本为 `/tmp/aiarch/ratelimit.py`，运行 `python3 /tmp/aiarch/ratelimit.py`。
2. 把 `capacity` 改为 `2`，再运行，观察首次拒绝时间是否提前。
3. 把请求间隔从 `0.05` 改为 `0.2`（5 QPS），观察是否全部通过。
4. 统计三种 `capacity`（2、10、50）下的拒绝数，画出“突发容忍 vs 恢复期过载”的对照。

**预期结果**：第 2 步几乎立即开始拒绝；第 3 步全部通过；第 4 步拒绝数随容量增大而减少，但恢复期的瞬时放行量增大。

**验证方法**：在任意时间点验证 `tokens` 不超过 `capacity` 且不为负；把 `refill_per_s` 设为 0，验证拒绝数等于 `总数 - capacity`。

**清理方法**：删除 `/tmp/aiarch/ratelimit.py`；若使用 Redis 实验，删除对应前缀的键。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 所有租户同时变慢 | 只有全局限流，无租户隔离 | 按租户看 QPS 分布 | 增加租户级限流与并发上限 |
| 改个头就能绕过限流 | 用请求头而非令牌声明做键 | 伪造 `X-Tenant-Id` 重放 | 用已验证声明，忽略客户端自报 |
| 月度额度提前用尽 | 只做事后统计，无预扣 | 对比余额曲线与用量曲线 | 预扣 + 结算 + 阈值告警 |
| 失败请求也扣了钱 | 结算未按失败原因退还 | 抽样对比失败请求的扣费记录 | 按错误分类退还，记录退还原因 |
| 账单与供应商对不上 | 用量来自不同来源（内部估算 vs 供应商账单） | 按天对账差异 | 以供应商账单为准修正计量，差异告警 |
| 限流存储故障导致全站拒绝 | 共享存储无降级策略 | 停掉存储观察行为 | 定义 fail-open/fail-closed 边界并演练 |

## 安全与生产注意事项

**<u>用客户端可控的字段（请求头、请求体、查询参数）作为租户键，攻击者可以伪装成他人或绕过配额。</u>**租户键必须来自已验证令牌或双向 TLS 证书。

**<u>只按请求数限流，不按 Token 限流，会让一个超长上下文的请求消耗掉普通请求几十倍的算力。</u>**应按“请求数 + Token 预算”双维度限制，并对单次请求的最大输入长度设上限。

**<u>成本日志里保存完整 Prompt 与答复，会把个人信息复制到一个通常缺少访问控制的分析系统。</u>**成本事件只需租户、功能、Token 数、模型与版本坐标；内容抽样需单独脱敏并限定保留期。

## 本课总结

- **限流、配额、预算告警解决不同问题**，拒绝语义也不同，不能共用一个开关。
- **令牌桶用容量换突发容忍**，补充速率决定长期上限。
- **限流键必须来自可信身份**，否则隔离形同虚设。
- **预扣 + 结算**是避免超支与余额漂移的最小组合。
- **成本归属要能回答单位成本**，否则降本只能靠“少用”。

## 思考题

套餐按“月度 Token 额度 + 峰值 QPS”售卖，但客户的实际流量是每月最后三天集中爆发。你会如何在“公平使用”“收入可预测”和“客户体验”之间设计配额与限流策略？请说明预扣、告警、降级与超额计费的组合。

参考思路：额度按月累计但允许短期透支到上限，超额按阶梯计费；峰值 QPS 按合同硬限，月度额度按软限（先降级后拒绝）；提前按历史曲线预测并通知客户；对爆发型客户推荐预留容量套餐，而不是在高峰期临时放开。

## 小测

1. 令牌桶中 `capacity` 与 `refill_per_s` 分别控制什么？  
   A. 容量控制长期速率，速率控制突发　B. 容量控制突发上限，速率控制长期平均  
   C. 两者都只影响拒绝率　D. 两者等价
2. 为什么配额需要“预扣”而不是“事后统计”？
3. 下列哪一项最适合用并发限制而不是 QPS 限流？  
   A. 客服工作台请求数　B. 单个模型端点的在途请求数　C. 租户月度 Token 额度　D. 用户登录次数
4. 内部计量与供应商账单不一致时，应以哪个为准？为什么？
5. 场景题：某租户投诉“我们的请求被无故拒绝”，但你查到拒绝率与该租户 QPS 同步上升。请写出你的排查与沟通要点。

## 答案与解析

1. **B。**容量决定短时间内可放行的突发量，补充速率决定长期平均吞吐。A 把两者说反了；C 错在它们直接影响的是允许速率而非仅仅拒绝率；D 错在两者作用不同。
2. 因为事后统计存在时间差：一次失控脚本可以在发现前消耗掉大量额度。预扣在调用前锁定上限，结算时按实际用量退差，既防超支又不浪费。
3. **B。**并发限制直接保护下游连接与算力。A、D 是请求频率问题，适合 QPS 限流；C 是周期额度，属于配额。
4. 以供应商账单为准。内部计量基于估算或采样，供应商账单是计费事实；但内部数据用于实时控制与归因，两者需要建立映射并监控差异。
5. 先确认拒绝是限流还是配额，再看该租户是否超过合同 QPS 或存在重试放大（同一 `request_id` 重复到达）。沟通时给出拒绝时间窗、触发阈值、实际 QPS 与合同额度，并提供降级或扩容选项，而不是只说“系统限制”。
