# Prompt、模型、知识库版本与缓存

## 为什么需要学习

周五下午，有人在管理后台把系统提示里的一句“必要时建议人工复核”改成了“直接给出退款结论”。周一客服发现答复变得激进，但没人能说清是哪次改动、影响多少会话。想回滚时，发现 Prompt 存在数据库某一行的文本里，没有历史版本；知识库上周也更新过政策，无法判断问题来自 Prompt 还是文档。

另一个方向的浪费同样常见：每天有大量重复问题（“七天无理由怎么算”），每次都完整调用模型；于是有人加了缓存，结果政策更新后，缓存继续返回旧条款，客服照着旧政策承诺了不该承诺的退款。

> **核心结论：** 能回滚的不是某个 Prompt 文件，而是一组*版本坐标*；缓存若不含这组坐标，就是把旧结论固化成了新事实。

## 学习目标

完成本课后，你能够：

- 列出一次 AI 发布需要记录的版本坐标，并写出可回滚的发布清单。
- 区分精确缓存与语义缓存，说明各自命中条件与失效风险。
- 设计包含版本、租户与规范化输入的缓存键，并验证版本变化会使键失效。
- 说明供应商侧提示缓存的收益边界，以及它与应用级缓存的区别。

## 业务场景

售后助手有三类可版本化对象：System Prompt（政策口径与语气）、模型（主模型与备用模型）、知识库快照（售后政策文档集）。运营希望“周三更新双十一退货政策，只影响新会话，且出问题能在 10 分钟内回到上一版”。

客服还希望重复问题快一点：早班有 40% 的问题是同一批（退货时限、运费谁承担）。这些问题的答案在政策不变时是稳定的，适合缓存；而“我的订单 A1024 到哪了”必须实时查询，不能缓存。

## 核心概念

| 对象 | 版本标识示例 | 变更频率 | 回滚粒度 |
| --- | --- | --- | --- |
| System Prompt | `prompt:after-sales@v12` | 每周 | 整体替换 |
| 模型 | `vendor-b/large-2026-08` | 季度 | 切换别名指向 |
| 知识库快照 | `kb-2026-10-08` | 每周或事件驱动 | 切回旧快照 |
| 检索配置 | `retrieval:top8-rerank-v3` | 月 | 配置回退 |
| 工具契约 | `tools:refund@v4` | 月 | 版本共存 |

- *版本坐标*（bundle）：把上述标识组合成一个不可变引用，如 `after-sales@2026.10.3`。**一次请求必须能回答“用了哪一组坐标”。**
- *发布清单*（manifest）：记录坐标到具体内容的映射、发布时间、负责人与回滚目标。
- *精确缓存*：键完全相同才命中，结果确定，失效可控。
- *语义缓存*：用向量相似度判断“问题是否等价”，命中率更高，但可能把不同问题当成同一个，<u>在金额、时效、订单相关问题上风险最高</u>。
- *提示缓存*（provider-side prefix cache）：供应商对相同前缀的输入做计算复用，计费与命中规则由供应商定义，**它不是应用级结果缓存**。

| 缓存类型 | 命中条件 | 收益 | 主要风险 | 适用内容 |
| --- | --- | --- | --- | --- |
| 精确缓存 | 规范化后的输入 + 版本坐标完全一致 | 稳定、可预测 | 命中率受输入差异影响 | 高频政策问答 |
| 语义缓存 | 向量相似度超过阈值 | 命中率高 | 误命中、跨版本污染 | 语气类、科普类 |
| 提示缓存 | 相同前缀（系统提示、长文档） | 降低首字延迟与输入费用 | 依赖供应商实现 | 固定长前缀 |
| 不缓存 | — | 永远最新 | 成本与延迟高 | 订单状态、余额、库存 |

## 工作原理

1. **定义坐标**：把 Prompt、模型、知识库快照、检索配置、工具契约各自版本化，组合成 bundle。
2. **发布**：新内容以不可变方式写入（新文件或新行），生成 manifest，记录坐标、差异摘要、负责人与回滚目标。
3. **灰度**：按租户或流量比例把请求路由到新坐标；同一会话保持坐标稳定，避免一轮对话内混用两版。
4. **请求解析**：接入层根据路由规则解析出本次 bundle，写入请求信封与审计。
5. **构造缓存键**：`hash(规范化输入 + bundle + 租户 + 语言 + 用户可见范围)`；缺少任一维度都可能串数据。
6. **查缓存**：命中则直接返回，并记录“命中”指标；未命中进入模型调用。
7. **写缓存**：只缓存“与时间无关”的结果；设置 TTL，且 TTL 不超过 bundle 的生命周期。
8. **失效**：bundle 变更时按前缀批量失效；知识库紧急撤回时提供“按文档 ID 失效”的补充通道。
9. **观察**：对比新旧 bundle 的命中率、用户反馈、转人工率与错误率，异常则回滚。
10. **回滚**：把路由指回旧 bundle；缓存因键含坐标而自然不再命中，无需手工清理。

回滚速度取决于两点：manifest 是否真的可复现（依赖的外部资源是否仍在），以及缓存键是否包含坐标。**如果缓存键只有问题文本，回滚后仍会返回旧答案**，这是最常见的“回滚无效”原因。

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 版本写在代码仓库（Prompt 即代码） | 有评审流程、变更少 | 运营需自助改文案 | 可审计、可 review；改一句话也要发版 |
| 版本存数据库 + 管理后台 | 运营频繁调整 | 缺少审批与灰度能力时 | 灵活；需自己实现审批、灰度、回滚 |
| 配置中心 + 发布清单 | 多服务共享配置、需要灰度 | 小团队（增加组件） | 灰度与回滚成熟；引入新依赖 |
| 不做缓存 | 强实时、低频 | 高频重复问题 | 永远最新；成本高 |
| 精确缓存 + 短 TTL | 大多数政策问答 | 答案随用户状态变化 | 简单可靠；命中率中等 |
| 语义缓存 | 语气、常识类问答 | 金额、时效、订单类 | 命中率高；误命中代价大 |

选型依据：**变更频率与谁改**（运营自助则必须有后台与审批）；**错误代价**（涉及资金与时效则不用语义缓存）；**回滚时间要求**（要求分钟级则必须坐标化 + 缓存键含版本）。

不是所有内容都值得版本化：临时实验可以直接用独立命名空间，但要设置过期时间，避免“实验版本”变成事实上的生产版本。

## 最小示例

下面的脚本演示缓存键如何随版本坐标变化，同时验证空白差异不会造成重复缓存。

```python
import hashlib, json

def cache_key(question, bundle, tenant, kb_snapshot):
    # 规范化输入：合并连续空白，避免同一问题因空格不同而重复缓存
    norm = " ".join(question.split())
    material = {"q": norm, "bundle": bundle, "tenant": tenant, "kb": kb_snapshot}
    # canonical JSON：键排序 + 紧凑分隔符，保证同一语义得到同一摘要
    canon = json.dumps(material, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canon.encode()).hexdigest()[:16], material

k1, m1 = cache_key("订单 A1024  能退吗", "after-sales@2026.10.3", "t-qk", "kb-2026-10-01")
k2, _  = cache_key("订单 A1024 能退吗", "after-sales@2026.10.3", "t-qk", "kb-2026-10-01")
k3, _  = cache_key("订单 A1024 能退吗", "after-sales@2026.10.4", "t-qk", "kb-2026-10-08")
k4, _  = cache_key("订单 A1024 能退吗", "after-sales@2026.10.3", "t-xh", "kb-2026-10-01")
print("blank-normalized same:", k1 == k2, k1)
print("after bundle/kb bump:", k3, "changed:", k3 != k1)
print("other tenant:", k4, "changed:", k4 != k1)
print(json.dumps(m1, ensure_ascii=False, sort_keys=True))
```

预期输出（已实跑；哈希值固定可复现）：

```text
blank-normalized same: True f29fdde386fb73d0
after bundle/kb bump: e934045df534e39d changed: True
other tenant: eb73a7693bac0b30 changed: True
{"bundle": "after-sales@2026.10.3", "kb": "kb-2026-10-01", "q": "订单 A1024 能退吗", "tenant": "t-qk"}
```

如果把 `bundle` 与 `kb_snapshot` 从 `material` 中删掉，前两行会变成 `changed: False`——这正是“回滚无效”的原始形态：缓存键不知道版本变了。

## 动手实验

**前置条件**：`python3`（3.9+），无需外部服务。

**步骤**：

1. 保存脚本为 `/tmp/aiarch/cachekey.py`，运行 `python3 /tmp/aiarch/cachekey.py`。
2. 去掉 `bundle` 与 `kb_snapshot`，观察 `k3` 与 `k1` 是否相等。
3. 加入 `locale` 维度（如 `zh-CN`），验证它同样改变键。
4. 模拟一次“发布”：把 `bundle` 从 `2026.10.3` 改为 `2026.10.4`，统计同一批 10 个问题中有多少缓存键发生变化。

**预期结果**：第 2 步 `k3 == k1`（说明缺版本会污染）；第 3 步键变化；第 4 步全部 10 个键都变化，等同于“整体失效”。

**验证方法**：对同一输入连续调用两次，键必须完全一致；对任一坐标做微小改动，键必须变化。

**清理方法**：删除 `/tmp/aiarch/cachekey.py`；若使用了真实缓存服务，删除带实验前缀的键。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 回滚后答复仍像新版本 | 缓存键不含版本坐标 | 抽查命中记录的键构成 | 键加入 bundle 与知识库快照 |
| 同一问题换来不同答案 | 语义缓存误命中，或灰度中坐标不固定 | 查两次请求的 bundle 与命中项 | 关闭语义缓存用于金额类；会话内锁定坐标 |
| 政策更新后仍引用旧条款 | TTL 过长，或未按文档 ID 失效 | 对比缓存写入时间与政策生效时间 | 缩短 TTL + 文档级失效通道 |
| 缓存跨租户串数据 | 键缺少租户/权限维度 | 用两个租户构造相同问题 | 键加入 `tenant` 与可见范围 |
| 发布后无法复现旧结果 | 旧 Prompt 被覆盖，manifest 指向已删除内容 | 按 manifest 找旧坐标对应内容 | 版本不可变存储，禁止原地修改 |

## 安全与生产注意事项

**<u>缓存键缺少租户或权限维度，会把 A 租户的政策与订单信息返回给 B 租户。</u>**键必须包含租户与可见范围，缓存值本身也不应包含超出调用者权限的内容。

**<u>语义缓存会把“看起来相似”的问题当成同一个，在退款金额、时效承诺上造成实质损失。</u>**涉及金额、期限、承诺类问答应禁用语义缓存，或只缓存“检索结果”而不缓存“最终答复”。

**<u>缓存中长期保存模型输出与用户问题，等于新建了一份不受管制的数据副本。</u>**应设置 TTL、加密与访问控制，并在用户行使删除权时同步清理缓存。

## 本课总结

- **版本坐标是回滚的最小单位**：Prompt、模型、知识库、检索配置、工具契约要一起定位。
- **发布清单必须可复现**：旧内容不可原地覆盖，否则“回滚”只是改了个名字。
- **缓存键必须包含版本、租户与规范化输入**，否则回滚与隔离都会失效。
- **语义缓存不是免费的命中率**：金额与时效类问题应禁用或降级为缓存检索结果。
- **供应商的提示缓存与应用结果缓存是两件事**，收益与失效规则不同。

## 思考题

运营希望“政策更新后立刻生效，同时不要浪费已有缓存”。在缓存键包含知识库快照的前提下，你会如何在“立即失效”与“保留命中率”之间设计过渡？请说明灰度期、会话一致性与审计三方面的处理。

参考思路：新快照使用新坐标，新会话走新坐标、老会话锁定旧坐标直至结束；缓存按坐标前缀分片，切换即切换前缀，无需删除；审计记录每条答复的坐标，便于对比两版差异；紧急撤回时再提供按文档 ID 的定点失效。

## 小测

1. 下列哪一项不属于本课定义的版本坐标？  
   A. System Prompt 版本　B. 模型标识　C. 客服的工号　D. 知识库快照
2. 为什么缓存键必须包含租户标识？
3. 语义缓存最适合下列哪类问题？  
   A. 订单金额计算　B. 退货时限是否包含节假日　C. “运费谁承担”这类通用政策解释　D. 库存数量
4. 供应商侧的提示缓存（prefix cache）与应用级结果缓存有什么本质区别？
5. 场景题：周五上线新政策后，客服反馈“部分会话仍按旧政策答复，部分已是新政策”。请写出你的排查顺序与最可能的两个原因。

## 答案与解析

1. **C。**工号是操作者身份，不属于模型行为坐标；它应出现在审计里，而不是决定生成结果的版本集合。
2. 因为不同租户的知识库、政策与权限不同，相同问题可能对应不同答案；缺少租户维度会造成跨租户数据泄漏，也可能违反数据隔离约定。
3. **C。**通用政策解释的答案在版本内稳定，允许“表述不同但语义等价”的命中。A、B、D 涉及金额、时效与实时状态，误命中代价高。
4. 提示缓存复用相同前缀的**计算结果**，减少输入侧延迟与费用，但仍会生成输出；应用级结果缓存直接复用**最终答复**，跳过模型调用。前者对输出内容无影响，后者必须处理版本与失效。
5. 先按 `bundle` 维度统计答复分布，确认是否灰度未完成；再查缓存键是否含知识库快照、TTL 是否过长；最后检查老会话是否按设计锁定旧坐标。最可能的两个原因：灰度按租户分批导致同时存在两版；缓存键缺少快照维度导致旧答案继续命中。
