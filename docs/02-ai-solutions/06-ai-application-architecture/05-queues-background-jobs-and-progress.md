# 队列、后台任务与长任务进度

## 为什么需要学习

晴空商城要做一次“历史退款工单批量复核”：把过去三个月的 3000 条工单交给助手逐条判断是否符合新政策。第一版实现是一个 HTTP 接口，在请求里循环调用模型。上线后出现三个连锁问题：网关 60 秒超时，前端显示失败但服务端仍在跑；客服以为没成功而重复提交，产生三份重复建议；跑批到一半进程重启，没有任何记录说明跑到哪一条。

同步接口适合“几秒内能给出结果”的操作，其他情况都需要任务化。任务化的核心不是引入一个队列产品，而是**把一次操作变成有状态、可重试、可观测的实体**。

> **核心结论：** 异步化不是性能优化，而是把“一次请求”变成“一个可追踪的生命周期”。

## 学习目标

完成本课后，你能够：

- 用等待预算、失败重试需求、是否产生外部副作用三项，判断同步还是异步。
- 写出任务状态机，列出合法迁移与终态，并说明非法迁移为什么必须被拒绝。
- 解释至少一次投递与幂等消费的关系，并为重复消费设计防护。
- 为长任务设计进度模型（总数/已完成/当前阶段）与取消语义。
- 说明死信队列的触发条件与人工处理流程。

## 前置知识

- 回看上一课：[会话、消息、状态与流式输出](04-session-state-and-streaming.md)。
- 理解 HTTP 请求有超时上限，长连接不等于无限等待。
- 知道“至少一次投递”意味着消息可能重复到达。
- 了解数据库唯一约束与事务的基本用法。

## 业务场景

批量复核任务的真实约束：3000 条工单，每条需要 1–3 次模型调用，单条耗时 2–8 秒，总计约 3–6 小时；期间可能遇到供应商限流、单条工单数据缺失、进程发布重启。运营需要看到“已完成 1200 / 3000，当前处理到 3 月 15 日的工单”，并且能随时暂停。

同时，退款建议必须**人工确认后**才执行（见第 9 课），所以任务只产出建议，不直接调用退款工具——这一点决定了任务可以安全重试。

## 核心概念

| 概念 | 含义 | 本课的用法 | 常见误区 |
| --- | --- | --- | --- |
| *任务*（job） | 一次可独立追踪的异步执行单元 | 一条 `job` 记录 + 状态 + 进度 | 用 HTTP 请求 ID 当任务 ID |
| *工作队列* | 存放待执行任务的中间件 | 入队、出队、确认、重投 | 以为入队就等于执行成功 |
| *工作者*（worker） | 消费队列并执行任务的进程 | 独立部署、可水平扩展 | 与 Web 进程混部，互相抢资源 |
| *至少一次投递* | 消息可能重复送达，但不会静默丢失 | 消费端必须幂等 | 假设“只会来一次” |
| *可见性超时* | 消息被取走后对其他人不可见的时间 | 超过则重新投递 | 设得比任务耗时短，导致并发重复执行 |
| *幂等消费* | 同一任务重复执行结果一致 | 以 `job_id + step` 做唯一键 | 用内存标记去重，重启即失效 |
| *死信队列*（DLQ） | 超过重试上限后归档的队列 | 人工排查与批量重放 | 直接丢弃，问题永久消失 |
| *进度* | 已完成量与当前阶段的投影 | 单独字段，可轮询 | 只打日志，前端无法展示 |

同步与异步的判断标准可以固化成一张表：

| 判断项 | 倾向同步 | 倾向异步 |
| --- | --- | --- |
| 预计耗时 | < 3 秒 | > 10 秒，或方差极大 |
| 用户是否需要立即看到 | 是（可流式） | 否（可稍后查看） |
| 失败后是否需要重试 | 重试由用户发起即可 | 需要自动退避重试 |
| 是否需要跨请求续跑 | 否 | 是（进程重启仍要继续） |
| 是否产生外部副作用 | 无或可回滚 | 有（必须幂等 + 人工确认） |

<u>“接口先返回 202，然后在请求里 `sleep` 等任务跑完”不是异步</u>，它只是把超时问题藏起来：连接仍被占用，重启仍会丢任务。

## 工作原理

1. **受理**：接口校验参数，用业务幂等键（如 `batch_id`）创建任务记录，状态 `queued`，返回 `202` 与 `job_id`。
2. **入队**：把 `job_id` 写入队列；消息体只放标识，不放整份业务数据，避免消息过大与数据副本失控。
3. **取任务**：worker 取走消息，队列开始*可见性超时*计时；worker 先抢占任务（`queued → running`），抢不到说明别人已在跑。
4. **分片执行**：把 3000 条拆成小批（如 20 条一批），每批完成即更新进度并记录检查点。
5. **确认**：整批完成后 ack 消息；若 worker 崩溃，可见性超时到期后消息重投，另一个 worker 从检查点继续。
6. **失败处理**：可重试错误（限流、超时）进入 `retry_wait`，按指数退避安排下次执行；不可重试错误（数据缺失、参数非法）直接 `failed`。
7. **耗尽重试**：达到 `max_attempts` 后转入 `dead` 并投递到死信队列，附上最后一次错误与上下文。
8. **进度投影**：进度更新与任务状态分开存储，前端轮询读取；进度只能是近似值，不能作为“完成”的判据。
9. **取消**：置 `canceled` 标记，worker 在每个分片边界检查标记并停止；已产生的副作用需要补偿或明确保留。
10. **完成通知**：任务终态后发出事件或 Webhook，运营页面不必持续轮询。

状态机的合法迁移必须写死并测试：

| 当前状态 | 允许迁移到 | 说明 |
| --- | --- | --- |
| `queued` | `running`、`canceled` | 取消发生在开始前，无副作用 |
| `running` | `succeeded`、`failed`、`canceled` | 运行中取消需在分片边界生效 |
| `failed` | `retry_wait`、`dead` | 是否可重试由错误分类决定 |
| `retry_wait` | `running`、`canceled` | 等待期间仍可取消 |
| `succeeded` / `canceled` / `dead` | 无 | 终态不可回退，重跑应创建新任务 |

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 框架内置后台任务（如 FastAPI `BackgroundTasks`） | 发通知、写日志等秒级副作用 | 需要重试、持久化、跨重启续跑 | 零额外组件；进程退出即丢失，无重试 |
| 独立队列 + worker | 大多数长任务 | 需要复杂编排与人工审批节点 | 成熟、可扩展；需运维队列与 worker |
| 工作流引擎（含步骤与补偿） | 多步骤、需人工审批、需回滚 | 简单批处理 | 可视化与补偿强；学习与运维成本高 |
| 数据库轮询表 | 低吞吐、想避免新组件 | 高频任务 | 简单；有轮询延迟与锁竞争 |

选型依据：**任务是否需要跨重启续跑**（是则不能用进程内后台任务）；**是否需要人工审批节点**（是则考虑工作流引擎）；**吞吐量级**（万级/天用队列，百级/天可用数据库表）。还要考虑团队的运维能力：引入队列意味着要监控堆积、消费延迟与死信数量。

## 最小示例

下面的脚本用标准库实现任务状态机与退避计算，并验证非法迁移会被拒绝。

```python
from dataclasses import dataclass, field

ALLOWED = {
    "queued":     {"running", "canceled"},
    "running":    {"succeeded", "failed", "canceled"},
    "failed":     {"retry_wait", "dead"},      # 能否重试由错误分类决定
    "retry_wait": {"running", "canceled"},
    "succeeded":  set(),                        # 终态：不允许再变
    "canceled":   set(),
    "dead":       set(),
}

@dataclass
class Job:
    job_id: str
    state: str = "queued"
    attempt: int = 0
    max_attempts: int = 3
    history: list = field(default_factory=list)

    def move(self, to: str) -> None:
        # 所有状态变更走同一入口，非法迁移直接失败，而不是写脏数据
        if to not in ALLOWED[self.state]:
            raise ValueError(f"illegal transition {self.state} -> {to}")
        self.history.append((self.state, to))
        self.state = to

def backoff_ms(attempt: int, base: int = 500, cap: int = 30000) -> int:
    # 指数增长并封顶：既给上游恢复时间，也避免等待超过业务可接受范围
    return min(base * (2 ** attempt), cap)

job = Job("job-refund-3000")
job.move("running"); job.attempt += 1
job.move("failed")
for i in range(3):
    print(f"attempt={job.attempt} wait={backoff_ms(i)}ms")
job.move("retry_wait"); job.move("running"); job.attempt += 1
job.move("succeeded")
print("state:", job.state, "transitions:", job.history)
try:
    job.move("running")        # 终态回退：应当被拒绝
except ValueError as err:
    print("rejected:", err)
```

预期输出（已实跑）：

```text
attempt=1 wait=500ms
attempt=1 wait=1000ms
attempt=1 wait=2000ms
state: succeeded transitions: [('queued', 'running'), ('running', 'failed'), ('failed', 'retry_wait'), ('retry_wait', 'running'), ('running', 'succeeded')]
rejected: illegal transition succeeded -> running
```

真实实现还需要三处补强：状态迁移与业务写入放在同一事务；每个分片用 `job_id + 分片号` 做唯一键，保证重复消费不重复产出；`history` 落库而不是留在内存，否则重启后无法审计。

## 动手实验

**前置条件**：`python3`（3.9+），无需队列服务。

**步骤**：

1. 保存脚本为 `/tmp/aiarch/job.py`，运行 `python3 /tmp/aiarch/job.py`。
2. 在 `ALLOWED` 中删除 `"canceled"` 到任何状态的迁移，测试从 `running` 取消后再尝试重启。
3. 给 `Job` 增加 `progress` 字段（`done`、`total`、`stage`），在每次 `move("running")` 后打印进度。
4. 增加 `max_attempts=1` 的用例，验证第二次失败应进入 `dead` 而不是 `retry_wait`。

**预期结果**：第 1 步得到上述输出；第 2 步取消后任何重启尝试都抛 `ValueError`；第 3 步进度随分片单调递增；第 4 步失败后进入 `dead`。

**验证方法**：对每个终态尝试所有迁移，应当全部被拒绝；重复调用同一分片处理函数两次，检查产出是否只有一份（用唯一键模拟）。

**清理方法**：删除 `/tmp/aiarch/job.py`；若实验中启动了队列容器，用 `docker compose down` 停止并删除卷。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 前端报超时，后台仍在跑 | 长任务放在同步请求里 | 对比网关超时与任务耗时 | 改为 `202 + job_id`，前端轮询或订阅 |
| 同一批工单被处理两次 | 可见性超时短于任务耗时，消息重投 | 查两个 worker 的日志时间重叠 | 延长可见性超时或心跳续租 + 幂等消费 |
| 任务永久卡在 `running` | worker 崩溃且无超时回收 | 查 `updated_at` 长时间未更新 | 增加心跳与僵尸任务回收 |
| 重试耗尽后问题消失 | 无死信队列，异常被吞 | 统计 `dead` 数量与错误分布 | DLQ + 告警 + 人工重放流程 |
| 进度条回退或乱跳 | 多 worker 各自写进度，无版本控制 | 查进度更新时间与写入者 | 单一汇总投影或带版本的条件更新 |
| 取消后仍产生退款建议 | 取消只在入口生效，执行中不检查 | 查取消时间与最后一次写入时间 | 分片边界检查取消标记 + 补偿 |

## 安全与生产注意事项

**<u>把完整工单内容（含手机号、地址）直接放进队列消息，会让消息中间件成为新的个人信息副本。</u>**消息体只放标识与必要参数，worker 按权限回源读取；队列设置保留期与访问控制，生产环境禁止把消息内容打到日志。

**<u>任务重试与“人工确认后执行”的顺序搞反，会造成重复退款。</u>**副作用必须由具备幂等键的独立步骤执行，且重试只覆盖“生成建议”，不覆盖“执行资金操作”。

**<u>取消语义不明确会让运营以为已停止，实际仍在消耗配额。</u>**应明确“取消”是立即生效还是分片边界生效，并在界面与审计中显示实际停止位置。

## 本课总结

- **异步化的判据是耗时、重试需求与副作用**，不是“看起来慢”。
- **任务是有生命周期的实体**：状态机、检查点、终态与死信缺一不可。
- **至少一次投递意味着必须幂等**，去重键要落库而不是放内存。
- **进度是投影**，只能说明大概位置，不能当作完成判据。
- **取消与重试的语义要写清楚**，尤其涉及资金或对外通知时。

## 思考题

运营要求“批量复核中途可以改政策，改完从当前进度继续”。这会给任务状态机、幂等键与结果可解释性带来什么影响？请说明你会如何在“可继续”与“结果一致”之间取舍。

参考思路：政策版本必须进入任务的分片记录，续跑时新分片使用新版本，已完成的保留旧版本；结果要能标注“依据哪一版政策”，否则同一批结论无法解释。若业务要求整批一致，则应创建新任务重跑，而不是在原任务上混用版本。

## 小测

1. 下列哪种场景最适合用进程内后台任务（如 `BackgroundTasks`）？  
   A. 需要跨重启续跑的批量复核　B. 生成一条站内通知 C. 需要三次重试的退款执行 D. 需要人工审批的工单
2. 可见性超时设置得比任务耗时短会发生什么？
3. 为什么队列消息里不建议放完整业务数据？
4. 死信队列的作用是什么？
5. 场景题：批量任务跑到 60% 时供应商开始持续 `429`。请写出你会如何调整重试与进度，以及如何向运营解释当前状态。

## 答案与解析

1. **B。**通知是秒级、可丢失可重发的副作用。A 需要持久化与续跑，C 需要重试与幂等，D 需要审批节点，都超出进程内任务能力。
2. 消息会在任务尚未完成时被重新投递给另一个 worker，导致同一任务被并发执行；若消费端不幂等，就会产生重复产出或重复副作用。
3. 一是消息体积与序列化成本；二是数据副本扩散，难以统一更新与删除；三是消息中间件的访问控制通常弱于业务库。只放标识，由 worker 回源读取更安全。
4. 收集超过重试上限的任务及其错误上下文，避免问题被静默丢弃，并提供人工排查与批量重放的入口。
5. 调整：对 `429` 使用较长退避并降低并发，避免加剧限流；进度改为“已处理/总数 + 当前等待原因”，不要把等待时间算作卡死；超过重试上限的分片进 DLQ 而不是让整批失败。向运营说明：任务仍在推进、当前处于供应商限流等待、预计完成时间区间，以及可选的“降低并发换稳定”取舍。
