# 云端、开源、本地与混合模型方案

## 为什么需要学习

售后助手的方案评审会上出现了三个互不相让的意见。安全团队说“客户地址和支付信息不能出内网”；财务说“按 token 计费的成本比预算高 40%”；平台团队说“自建推理服务大促肯定挂”。三方都对，但都在用自己的单一维度做决定。

这类决策不能靠谁声音大，而要靠三条硬条件的组合：**数据能不能出域、流量是否稳定、团队能不能运维。**本课把四种常见形态放进同一张比较表，并给出“混合路由”这种折中方案必须补齐的工程约束。

> **核心结论：** 模型来源不是立场问题，而是数据、流量与运维能力三项约束的交集；混合方案只有在“路由可评测、降级可执行”时才是方案，否则只是两套系统并行。

## 学习目标

完成本课后，你能够：

- 解释 *托管 API*、*开源权重*、*私有化部署*、*本地运行*、*混合路由*、*数据出域*、*供应商锁定*。
- 用三维度决策表为具体业务选出方案，并说出淘汰其他方案的理由。
- 写出一个路由策略，包含敏感等级、任务分级、降级路径与拒绝条件。
- 列出至少四项开源方案常被低估的成本。

## 业务场景

晴空商城售后助手服务三类请求：

- 客户对话与政策问答：内容含订单号、商品、可能的地址片段，属于 *内部* 级以上数据。
- 退款建议与金额：涉及支付信息，属于 *受限* 数据，不能出内网。
- 营销话术与知识库摘要：公开内容，可用最强模型追求质量。

同时业务有明显波峰：大促期间请求量是平日的 5 倍，凌晨几乎为零。

本课只看这个侧面：**同一套业务里，不同请求应该走不同模型来源，而这条“分流”本身要被评测、被审计、能降级。**

## 核心概念

*托管 API* 是由厂商提供的模型服务，按 token 或按请求计费，运维由厂商承担，能力与规格随厂商版本更新。代表形态是各家的大模型 API。

*开源权重* 指模型参数可下载、可自行部署的模型。开源权重不等于无约束：许可证可能对商用、再分发、署名或使用场景有额外要求，**必须逐条核对许可证原文与官方模型卡**。

*私有化部署* 是把模型部署在自有或专属环境里，数据不出内网。它与“开源权重”不是同义词：私有化也可以部署商业授权模型。

*本地运行* 指在开发者机器或边缘设备上运行模型，适合开发调试、离线场景与小规模内部工具。这类工具通常提供与主流 API 兼容的接口（例如 Ollama 支持本地与云端模型，并提供兼容 OpenAI 的调用方式），便于在同一套代码里切换。

*混合路由* 是按请求属性把流量分发到不同模型来源的机制。它要解决的核心问题是：敏感请求不能出去，简单请求不必用最贵的模型，云侧故障时业务不能停。

*数据出域* 指数据离开组织控制的网络或合规边界。只要请求发到外部服务，就要按出域处理，无论对方是否承诺不训练。

四类形态的核心对照如下：

| 维度 | 托管 API | 开源权重自托管 | 本地/边缘运行 | 混合路由 |
| --- | --- | --- | --- | --- |
| 数据边界 | 出域，需合同与合规评估 | 可控，取决于部署位置 | 完全本地 | 部分出域，需分流规则 |
| 上线速度 | 最快 | 中到慢（环境、容量、调优） | 最快 | 慢（两套都要建） |
| 单位成本 | 随用量线性增长 | 高固定成本、低边际成本 | 极低 | 取决于分流比例 |
| 峰值弹性 | 受厂商配额限制 | 需提前扩容，弹性差 | 无弹性 | 可借云侧兜峰 |
| 能力上限 | 通常最强 | 取决于所选模型 | 受限 | 分层，可能出现体验不一致 |
| 运维负担 | 低 | 高（GPU、值班、升级） | 低 | 最高 |
| 锁定风险 | 较高（接口与行为绑定） | 低（权重可控） | 低 | 中 |

## 工作原理

混合路由按以下顺序决策：

1. **打标**：请求进入网关时确定数据等级（公开/内部/受限）与任务级别（难/易）。
2. **过滤**：受限请求只允许进入本地或私有化目标，不满足则拒绝，不做“看起来更聪明”的例外。
3. **选择**：在允许的目标集合内，按任务级别选模型（难题走强模型，简单题走小模型）。
4. **门禁**：目标模型必须通过同一套评测集的最低分要求，否则不参与分流。
5. **降级**：首选目标超时或报错时，按预设顺序切到备选，并记录降级原因。
6. **审计**：每次请求记录数据等级、目标、模型版本、token 数与降级标记，供合规与成本复盘。
7. **回归**：任何一个目标升级模型版本，都要重跑评测，确认分流后的整体质量没有下降。

### 为什么“混合”最容易失控

- 同一问题在不同目标上得到不同答案，用户感知为“时好时坏”。
- 分流规则写在代码里、没有审计日志，事后无法证明敏感数据没有出域。
- 两个目标的能力不对齐，降级时格式不兼容（一个返回 JSON，一个返回 Markdown）。
- 成本模型只算了 token，没算人力、GPU 折旧与空闲资源。

**结论：混合方案的可行性取决于“评测门禁 + 统一输出契约 + 审计日志”三件事是否先建好。**

## 架构与选型

| 条件组合 | 推荐方案 | 淘汰理由 |
| --- | --- | --- |
| 数据受限 + 流量稳定 + 有平台团队 | 私有化部署（开源权重或商业授权） | 托管 API 直接违反数据边界 |
| 数据受限 + 流量很小 | 本地/边缘 + 人工兜底 | 自建集群利用率太低，成本不划算 |
| 数据可出域 + 流量波动大 | 托管 API | 自建需要为峰值付费，闲时浪费 |
| 公开内容 + 质量优先 | 托管 API（强模型） | 本地模型质量不足 |
| 混合数据等级 + 明显波峰 | 混合路由（敏感走本地，公开走云，云侧兜峰） | 单一方案无法同时满足合规、成本与弹性 |

选型依据：**先定数据边界（不可谈判），再看流量曲线（决定弹性需求），最后看团队能力（决定运维上限）。**顺序颠倒就会出现“为了省钱把敏感数据发出去”或“为了合规把业务拖垮”两类事故。

必须核对的外部事实：模型许可证条款、厂商的数据使用与保留政策、区域可用性、配额与限流、接口版本与弃用计划。这些都在变化，**以官方文档与合同为准**，并在架构决策记录里写明核对日期。

## 最小示例

下面的脚本实现一个可审计的路由决策。核心是“白名单式许可 + 显式降级”，而不是让默认值决定结果。

```python
POLICIES = {                                    # 敏感等级 -> 允许的目标（顺序即优先级）
    "restricted": ["onprem-small"],             # 客户身份、支付信息：绝不出内网
    "internal": ["cloud-primary", "onprem-small"],
    "public": ["cloud-primary", "cloud-fast"],
}
TIER_TARGET = {"hard": "cloud-primary", "easy": "cloud-fast"}

def decide(sensitivity, tier, degraded=False):
    allowed = POLICIES.get(sensitivity)
    if not allowed:                             # 未知等级必须拒绝，不能默认放行
        return "reject", "unknown sensitivity"
    if degraded:                                # 云侧故障时只允许本地兜底
        local = [t for t in allowed if t.startswith("onprem")]
        return (local[0], "degraded: cloud unavailable") if local else ("reject", "no local fallback")
    wanted = TIER_TARGET.get(tier, "cloud-primary")
    if wanted in allowed:                       # 目标在许可集合内才走
        return wanted, "ok"
    return allowed[0], f"downgrade from {wanted}"

for case in [("restricted", "hard"), ("internal", "hard"), ("public", "easy"), ("internal", "easy")]:
    print(case, "->", decide(*case))

print(("internal", "hard", True), "->", decide("internal", "hard", degraded=True))
print(("restricted", "easy", True), "->", decide("restricted", "easy", degraded=True))
```

预期输出（实测）：

```text
('restricted', 'hard') -> ('onprem-small', 'downgrade from cloud-primary')
('internal', 'hard') -> ('cloud-primary', 'ok')
('public', 'easy') -> ('cloud-fast', 'ok')
('internal', 'easy') -> ('cloud-primary', 'downgrade from cloud-fast')
('internal', 'hard', True) -> ('onprem-small', 'degraded: cloud unavailable')
('restricted', 'easy', True) -> ('onprem-small', 'degraded: cloud unavailable')
```

请特别看第 4 行：`(internal, easy)` 本想去 `cloud-fast`，但 `internal` 的许可清单里没有它，于是落到清单首项 `cloud-primary`。这在事实上是“升级到更强的模型”，却被打上了 `downgrade` 的标签——**说明用列表顺序做兜底会掩盖真实语义。**生产实现应把“兜底目标”与“降级原因”显式建模，而不是靠排序推断；这也正是审计日志要记录原因字符串的原因。

如果要用本地服务验证同一套代码可切换目标，下面是请求形态示意（**未实跑**，因需要本地模型服务）：

```http
POST /v1/chat/completions HTTP/1.1
Host: localhost:11434
Content-Type: application/json
Authorization: Bearer ${LOCAL_MODEL_TOKEN}

{"model": "local-small", "messages": [{"role": "user", "content": "签收 5 天能退吗"}], "stream": false}
```

预期响应为 OpenAI 兼容结构，包含 `choices[0].message.content` 与 `usage` 字段；实际字段以所部署服务的文档为准。

## 动手实验

**前置条件**：Python 3.9+，无网络。

1. 保存脚本为 `router.py` 并运行，对照预期输出确认六行决策。
2. 把 `POLICIES["restricted"]` 改成 `["cloud-primary"]`，重跑，观察受限请求被送往云端——这就是“一次配置改动造成的数据出域”。
3. 在 `decide` 中加入 `if sensitivity == "restricted" and tier == "hard": return "reject", "needs human"`，重跑，观察拒绝路径。
4. 为每个返回值加审计字段（数据等级、目标、原因），打印成一行 JSON，模拟审计日志。
5. **验证方法**：断言“所有 `restricted` 请求的目标都以 `onprem` 开头”，作为可执行的安全策略测试。
6. **清理方法**：删除 `router.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 同一问题答案质量忽高忽低 | 混合路由缺少统一评测门禁 | 按目标分组统计人工评分 | 设定最低分要求，不达标不参与分流 |
| 合规审计无法证明数据未出域 | 路由决策没有审计日志 | 抽查敏感请求的目标记录 | 记录等级、目标、原因、模型版本 |
| 降级后前端解析失败 | 两个目标输出格式不一致 | 对比降级前后的响应 schema | 统一输出契约 + schema 校验 |
| 开源模型上线后收到许可证质询 | 未核对商用与再分发条款 | 检查许可证原文与模型卡 | 换模型或取得授权，留存核对记录 |
| 自建集群大促期间排队严重 | 只按日常流量规划容量 | 回看历史峰值与扩容耗时 | 云侧兜峰 + 排队可见化 + 限流 |
| 成本核算与实际账单差距大 | 漏算 GPU 空闲、人力与出网流量 | 按月做全成本对账 | 把固定成本与人力纳入模型 |

## 安全与生产注意事项

**<u>混合路由的配置错误会直接把受限数据送出域，而且往往是“默认允许”造成的。</u>**缓解方法：策略默认拒绝、白名单显式授权、配置变更走评审与自动化校验，并用可执行测试断言“受限请求目标必须在本地集合内”。

**<u>把 API 密钥或模型访问令牌硬编码进前端代码、示例脚本或仓库，等于公开凭据。</u>**缓解方法：密钥只存在服务端密钥管理中，前端永不持有；示例代码使用环境变量占位符；开启用量告警与密钥轮换。

补充一点：开源权重虽可自主部署，但升级、漏洞修复与安全对齐需自建流程，不能假设“下载即安全”。

## 本课总结

- **方案选择由数据边界、流量形态、团队能力三项条件共同决定，数据边界不可谈判。**
- 托管 API 快而省心，但出域与锁定风险高；自托管可控，但固定成本与运维负担重。
- 开源权重不等于可自由商用，许可证与模型卡必须逐条核对。
- 混合路由成立的前提是统一输出契约、评测门禁与审计日志，否则只是两套系统并行。
- 降级路径必须显式设计并可测试，不能靠列表顺序或默认值推断。

## 思考题

晴空商城计划把“退款建议”从云端迁到私有化部署，理由是合规。请列出迁移前必须完成的三项测量与两项制度安排，并说明如果私有化模型的建议准确率低于云端 3 个百分点，你会如何决策。

参考思路：测量包括：同等评测集上的准确率与格式合法率、峰值并发下 P95 首字延迟、全成本（GPU、空闲率、人力）。制度安排：模型版本与许可证核对记录、变更与回滚流程。决策思路：先判断 3 个百分点是否落在业务可接受区间，以及是否集中在高风险样本；若集中在高风险类别，应保留云端做“第二意见”但不上传敏感字段（例如只传脱敏摘要），或改为私有化模型 + 规则校验 + 人工确认的组合，而不是简单二选一。

## 小测

1. 为什么“开源权重”不等于“可以自由商用”？
2. 混合路由必须配套哪三样东西才能成立？
3. 判断：数据量小就一定要自建，因为长期更便宜。对还是错？
4. 下列哪种场景最适合本地/边缘运行？  
   A. 大促峰值流量　B. 离线演示与开发调试　C. 需要最强模型能力的公开内容生成　D. 跨区域高可用
5. 场景题：审计发现 200 条受限请求中有 3 条被送到云端。请给出定位与修复步骤。

## 答案与解析

1. 因为许可证可以对商用、再分发、署名、使用场景附加条件，不同模型差异很大。开源指的是权重可获取，不是权利无限制；必须核对许可证原文与模型卡。
2. 统一输出契约（保证切换后下游可解析）、评测门禁（保证各目标质量达标）、审计日志（保证可追溯与合规证明）。
3. **错。**自建有高固定成本（GPU、空闲资源、人力），小流量下单位成本通常更高。是否自建主要取决于数据边界与合规要求，而不是数据量。
4. **B。**本地运行适合开发调试与离线场景。峰值流量需要弹性，最强能力通常来自云端强模型，跨区域高可用需要多区域部署能力。
5. 定位：查审计日志里这 3 条的数据等级判定（是否漏标）、路由策略版本（是否被改动）、以及是否走了降级路径（云侧故障时误兜底到云端）。修复：策略改为默认拒绝并加自动化断言测试；把等级判定前移到网关入口并记录依据；对降级路径单独做安全评审；补一条告警规则“受限等级请求命中非本地目标即报警”。
