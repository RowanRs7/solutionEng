# Token、上下文窗口与注意力

## 为什么需要学习

售后助手的第二版把“系统提示 + 政策全文 + 订单详情 + 最近 20 轮对话 + 客户上传的工单备注”全部拼进一次请求。上线第一周出现三种故障：部分长工单直接返回 `context_length_exceeded` 类的报错；账单环比上涨 3.8 倍；还有答复明确写着“根据政策，7 天内可退”，而政策原文写的是“15 天”，因为时效条款在拼接时被截断了一半。

这三个故障的共同原因不是模型，而是没有人管理 *上下文预算*。上下文窗口不是“能塞多少塞多少”的容器，它同时是成本单位、延迟单位和信息稀释的来源。

> **核心结论：** 每一次请求的上下文都是一份预算表：谁占多少 token、超了先裁谁、给输出留多少，必须在上线前写死并监控。

## 学习目标

完成本课后，你能够：

- 解释 *token*、*分词器*、*上下文窗口*、*输入预算*、*输出预留*、*前缀缓存*。
- 用“每字约 1 token（中文）/ 每 4 字符约 1 token（英文）”做快速估算，并说明它的误差范围。
- 为售后助手写出上下文预算表，包含额度、优先级与裁剪顺序。
- 说明长上下文的三个代价（成本、延迟、信息稀释），以及用检索代替全量拼接的判断标准。

## 业务场景

客服点开一条工单，助手需要以下材料才能答好：

- 系统规则：角色、口径、禁止事项、输出格式。
- 政策片段：与问题相关的 2–4 段条款（不是全部 42 份文档）。
- 订单快照：订单号、金额、签收时间、商品类目。
- 对话历史：最近若干轮，以及客户情绪相关的表述。
- 输出：一段答复或一个结构化建议（JSON）。

总有一个上限。本课要解决的问题是：**在固定上限内，怎么分配这五类内容，才不会既超限又丢关键信息。**

## 核心概念

*token* 是计费与长度的基本单位。*分词器* 决定一段文本被切成多少个 token，不同模型的分词器不同，同一个句子在两家厂商的 token 数可能相差 10%–30%。

*上下文窗口* 是一次请求能容纳的 token 总数上限，通常包含输入与输出。不同厂商、不同模型的窗口大小差异很大，而且会随版本变化，**必须以所用模型的官方规格页为准**，不要在架构文档里写死一个数字。

*输入预算* 是分配给提示词、检索片段、历史对话的额度。*输出预留* 是留给模型生成的空间。二者加上安全余量必须小于上下文窗口。

<u>“安全余量”不是谨慎，而是必需：</u>用启发式方法估算的 token 数与真实分词结果常有偏差，如果没有余量，就会出现“预算刚好塞满、输出被截断”的故障。

*前缀缓存* 是厂商提供的优化：当多次请求共享同一段很长的前缀（例如固定的系统规则与政策头部）时，可复用已计算的部分，降低延迟与成本。是否支持、如何计费、最小可缓存长度都由厂商定义，需按官方文档核对。

| 内容类型 | 估算方式 | 典型额度占比 | 裁剪策略 |
| --- | --- | --- | --- |
| 系统规则与输出格式 | 中文按字、英文按 4 字符 | 10%–20% | 不放宽，但可精简措辞 |
| 检索到的政策片段 | 按片段计 | 20%–30% | 减少片段数、按相关度排序截断 |
| 订单与业务数据 | 结构化字段 | 5%–10% | 只取必要字段 |
| 对话历史 | 按轮次计 | 10%–30% | 从最旧开始丢弃或摘要 |
| 输出预留 | 按期望长度 ×1.5 | 15%–25% | 明确 `max_tokens`，不可压缩 |

## 工作原理

1. **确定上限**：查当前模型的官方规格页，记录上下文窗口与最大输出长度，写进配置而不是代码常量。
2. **估算输入**：用分词器或官方 token 计数接口算出每块内容的真实 token 数；没有接口时用启发式估算，并保留余量。
3. **分配预算**：按“规则 > 业务数据 > 政策片段 > 对话历史”的优先级给出额度。
4. **组装顺序**：把最稳定的内容放最前（利于前缀缓存），把最关键的约束放在靠近末尾的位置，避免被中段稀释。
5. **裁剪**：超预算时按优先级从低到高裁，历史对话先摘要再丢弃，政策片段先减数量再减单段长度。
6. **校验**：组装后重新计数，确认 `输入 + 输出预留 + 余量 ≤ 窗口`，否则拒绝请求并走降级路径。
7. **记录与监控**：日志里记录输入/输出 token 数、命中缓存的比例、被裁剪的块名，按功能维度汇总成本。

### 为什么长上下文更贵、更慢、更容易丢信息

- **更贵**：计费按 token 线性增长，长输入直接抬高每条请求成本。
- **更慢**：注意力的计算量随序列长度增长（标准实现是平方级），首 token 延迟明显上升。
- **更易丢信息**：序列越长，单个位置获得的注意力权重越被摊薄，中段的关键约束容易被忽略；这也解释了“文档一多就开始漏条款”。
- **更易被干扰**：噪声片段越多，模型越可能把不相关条款和当前问题拼在一起。

**结论：长上下文适合“必须整体理解的少量文档”，不适合“从大库里找一条规则”——后者应该用检索。**

## 架构与选型

| 结构 | 适用场景 | 不适用场景 | 权衡 |
| --- | --- | --- | --- |
| 小上下文 + 检索 | 政策问答、知识库问答 | 需要跨文档整体推理的合同审阅 | 便宜、可引用；依赖召回质量 |
| 长上下文全量拼接 | 单份长文档摘要、少量固定材料 | 高并发、成本敏感、库很大 | 实现简单；成本与延迟高 |
| 分层摘要 | 长对话、长期工单 | 需要逐字引用原文 | 省 token；摘要会丢细节 |
| 前缀缓存 + 固定前缀 | 系统规则很长、请求量大的场景 | 前缀经常变化 | 降本提速；受厂商实现约束 |

选型依据按顺序：**内容总量能否被检索收敛到 1–2 成？请求量与成本上限是多少？关键信息是否要求逐字引用？**能检索就不要全量拼接；要引用就必须保留原文片段；历史很长就用摘要 + 关键事实清单。

## 最小示例

下面的预算分配器用启发式估算 token，按优先级裁剪，并打印结果。文件保存为 `budget.py`。

```python
import math

LIMIT = 128_000          # 教学假设值，不代表任何厂商当前规格，请查官方规格页
OUTPUT_RESERVE = 2_000   # 给模型输出预留的空间
SAFETY = 0.9             # 只使用 90% 的可用额度，抵消估算误差

def estimate_tokens(text):
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")  # 粗略统计汉字
    others = len(text) - cjk
    return math.ceil(cjk * 1.0 + others / 4)   # 汉字约 1:1，英文约 4 字符 1 token

def build(blocks, limit=LIMIT, reserve=OUTPUT_RESERVE):
    budget = int((limit - reserve) * SAFETY)   # 可用额度 = (窗口 - 输出预留) × 安全系数
    used, kept, dropped = 0, [], []
    for name, priority, text in sorted(blocks, key=lambda b: b[1]):  # 优先级数字小的先满足
        cost = estimate_tokens(text)
        if used + cost <= budget:
            kept.append(name)
            used += cost
        else:
            dropped.append((name, cost))       # 放不下就记录，便于排查丢的是什么
    return used, budget, kept, dropped

blocks = [
    ("policy_chunk_1", 1, "退换货时效：签收后 7 天内可申请无理由退货。" * 20),
    ("order_snapshot", 1, "订单号 20261019001；实付 899 元；状态：已签收。" * 5),
    ("chat_history", 3, "客户说收到货有划痕，客服已致歉。" * 8000),   # 故意超长以触发裁剪
    ("policy_chunk_2", 2, "运费承担：质量问题由卖家承担。" * 20),
]

used, budget, kept, dropped = build(blocks)
print("budget:", budget, "used:", used, "left:", budget - used)
print("kept:", kept)
print("dropped:", dropped)
```

预期输出（实测，`python3 budget.py`）：

```text
budget: 113400 used: 737 left: 112663
kept: ['policy_chunk_1', 'order_snapshot', 'policy_chunk_2']
dropped: [('chat_history', 116000)]
```

三个设计意图：`budget` 用乘法算出可用额度，而不是直接等于窗口；`sorted(..., key=lambda b: b[1])` 保证低优先级内容先被裁；`dropped` 记录被裁块的名称与成本，这就是生产里排查“为什么模型没看到这条信息”的第一手证据。注意 `chat_history` 的估算成本 116000 是**估算值**，真实值必须用分词器核对。

## 动手实验

**前置条件**：Python 3.9+；无需网络。

1. 保存代码并运行，记录 `budget`、`used`、`dropped`。
2. 把 `chat_history` 的重复次数从 8000 改成 200，重跑。预期 `dropped: []`，`used` 明显上升但仍小于 `budget`。
3. 把 `SAFETY` 改成 `1.0`，观察 `budget` 变为 126000——这说明余量来自你的配置，而不是系统保证。
4. **验证方法**：在 `build` 末尾加 `assert used <= budget`，再随机构造 10 组块大小，确认断言从不失败。
5. **清理方法**：删除 `budget.py`。实验不产生网络请求。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 请求报上下文超限 | 只算输入不算输出，或没留余量 | 记录实际输入/输出 token 数并相加 | 增加输出预留与安全余量，超限走降级 |
| 答复 JSON 被截断，下游解析失败 | `max_tokens` 小于实际输出需求 | 统计输出长度的 P95 与最大值 | 提高输出预留、要求模型精简格式 |
| 成本按周翻倍 | 全量拼接政策库，未做检索 | 按功能统计输入 token 分布 | 改检索式上下文，启用前缀缓存 |
| 中文 token 数被低估约三成 | 用“字符数 ÷ 4”套中文 | 抽样对比估算值与分词器结果 | 中文按 1 字 ≈ 1 token 估，或用官方计数接口 |
| 关键条款偶发丢失 | 条款位于长输入中段，注意力被稀释 | 同一问题在长/短两种上下文下对比 | 减少片段数、把硬约束改代码校验 |
| 对话越久越慢 | 历史无限增长 | 画出轮次与延迟的关系 | 历史摘要化，只保留事实清单 |

## 安全与生产注意事项

**<u>上下文里混入其他客户的数据，等于把数据泄露交给模型去“合理使用”。</u>**拼接前必须按当前工单的客户与订单做严格过滤，检索层也要带租户隔离条件；日志中记录引用来源，便于事后审计是谁的数据进了哪次请求。

**<u>没有输出预留会导致半截 JSON 被下游当作成功写入。</u>**一旦解析器容错，就可能写入残缺字段（例如金额为空）。缓解方法：输出必须通过 schema 校验并在失败时拒绝写入，同时把“输出被截断”作为独立告警项。

补充两点：上下文里可能被塞入恶意指令，客户留言与工单备注要作为数据而非指令处理；前缀缓存虽能降本，但需要确认缓存内容不跨租户复用，具体行为以厂商文档为准。

## 本课总结

- **上下文窗口同时是成本单位、延迟单位和信息稀释来源，必须按预算管理。**
- token 估算只是近似，中文约 1 字 1 token、英文约 4 字符 1 token，误差需靠余量与官方计数接口收敛。
- 预算分配按“规则 > 业务数据 > 政策片段 > 对话历史”，裁剪顺序与之相反。
- 长上下文适合少量必读文档，不适合从大库里找一条规则；后者用检索更便宜也更准。
- 必须为输出预留空间并校验结果，否则会出现“半截 JSON 被当成功”的隐蔽故障。

## 思考题

晴空商城想把政策库从 42 份文档压到“一份 20 万 token 的总政策汇编”，直接放进上下文，从而省掉检索系统。请评估这个决定：它在什么条件下可行，在什么条件下会导致哪类故障，你会用什么实验来验证？

参考思路：可行条件是单次请求并发低、成本可接受、且问题确实需要跨文档整体推理（例如判断某商品是否属于例外品类）。风险是：成本随每次请求线性增长、首 token 延迟上升、中段条款被稀释导致漏答。验证实验：取 50 条真实工单，分别跑“全量汇编”和“检索片段”，比较引用正确率、P95 延迟与单条成本；再故意问一个只在中段出现一次的条款，观察两者差异。

## 小测

1. 上下文窗口通常包含哪些 token？
2. 为什么中文用“字符数 ÷ 4”估算 token 会严重偏低？
3. 判断：只要模型支持很长的上下文，就应该把所有资料都放进去。对还是错？
4. 前缀缓存主要优化什么？  
   A. 输出准确性　B. 共享前缀的重复计算　C. 检索召回率　D. 分词精度
5. 场景题：某条请求偶发返回 `context_length_exceeded`，但你的估算显示只用了 80% 的窗口。列出三个最可能的原因和对应验证方法。

## 答案与解析

1. 输入（系统提示、检索片段、历史、业务数据）与模型生成的输出，二者共享同一个窗口；具体是否分开计限额要看厂商规格。
2. 中文一个汉字常对应一个 token，而“÷4”是按英文的字符/词根比例估算，套到中文会把 token 数低估数倍，导致预算规划失真、请求超限。
3. **错。**长上下文带来成本、延迟与信息稀释三类代价；能用检索收敛内容时应优先检索，长上下文只用于“必须整体理解”的少数场景。
4. **B。**它复用相同前缀的已计算结果，从而降低延迟与费用。它不改变模型准确性，也不影响召回率与分词。
5. 原因与验证：① 输出预留不足，实际生成比预期长——核对响应中的输出 token 数；② 分词器与估算偏差大，中文与专业术语被切得更碎——用官方计数接口重算；③ 拼接内容在运行时比设计时多（例如历史轮次未截断、检索片段数漂移）——把组装后的各块 token 数打进日志逐块比对。
