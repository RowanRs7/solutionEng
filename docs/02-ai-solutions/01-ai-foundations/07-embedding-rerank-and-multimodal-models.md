# 语言、Embedding、重排与多模态模型

## 为什么需要学习

售后助手的检索最初用关键词匹配：客户写“东西有瑕疵想退货，运费谁出”，系统匹配到的是“赠品不参与无理由退货”，因为两者都含“退货”二字；而真正该命中的“质量问题退货，运费由卖家承担”因为不含“瑕疵”被漏掉。改成向量检索后命中对了，却又出现新问题：召回的前三名里有一段“发票在退款后 3 个工作日开具”，语义相近但与问题无关，模型把它拼进了答复。

再往后，客户开始上传破损照片和发票扫描件，纯文本方案直接失效。

> **核心结论：** 检索质量由“召回”和“精排”两步共同决定，embedding 只解决“大致找得到”，重排才解决“确实答得上”。

## 学习目标

完成本课后，你能够：

- 解释 *embedding*、*向量维度*、*余弦相似度*、*近似最近邻（ANN）*、*双塔模型*、*交叉编码器*、*重排*。
- 说明向量召回在什么情况下必然失效，并给出至少三种补偿手段。
- 为“政策问答”设计“向量召回 + 重排 + 阈值过滤”的链路，并说明阈值的作用。
- 区分图像、文档、语音三类输入的处理路径与能力边界。

## 业务场景

售后助手的知识库包含：42 份政策文档、历史优质工单答复 800 条、商品保修条款。客户的问题有三种典型形态：

- 短口语问句：“这能退吗，运费谁出？”
- 带专有名词：“XX 型号吹风机的保修期多久？”
- 带附件：“照片里这样算破损吗？”（附 2 张图）

本课只看一个侧面：**同一批知识，如何被“找出来”，以及不同模态的输入如何进入同一条链路。**

## 核心概念

*embedding* 是把文本（或图像、音频）映射成固定长度向量的过程，语义相近的内容向量也相近。向量长度叫 *向量维度*，由模型决定，不同模型的维度与语义空间互不兼容。

*余弦相似度* 衡量两个向量的夹角，取值 −1 到 1，越大越相似。用它之前通常先把向量归一化为单位长度，这样点积就等于余弦相似度。

*近似最近邻（ANN）* 是在海量向量中快速找“最相似的 k 个”的索引技术，牺牲少量精度换取速度。它只负责“候选集合”，不判断候选是否真的回答了问题。

*双塔模型* 把查询与文档分别编码成向量再比较，速度快、可预先建索引，适合召回。*交叉编码器* 把查询与文档拼在一起送入模型，直接输出相关性分数，精度高但必须逐对计算，适合 *重排*（rerank）。

*重排* 是在召回结果上做第二次排序：用更强的模型或交叉特征，把真正相关的片段排到前面，并把明显无关的片段过滤掉。

| 对照面 | 向量召回（双塔） | 重排（交叉编码器/交叉特征） |
| --- | --- | --- |
| 计算时机 | 查询时只编码查询 | 每个候选都要单独算 |
| 延迟 | 毫秒级 | 随候选数线性增长 |
| 精度 | 大致相关 | 精确判断“是否回答问题” |
| 典型数量 | 召回 20–100 条 | 精排前 10–20 条 |
| 主要失效 | 语义相近但无关、专有名词弱 | 候选里本来就没有正确答案 |
| 成本 | 低 | 中到高，需控制候选数 |

## 工作原理

### 文本检索链路

1. **分块**：把文档切成 200–600 字的片段，保留标题、小节号、生效日期作为元数据。
2. **向量化**：用同一个 embedding 模型把所有片段编码成向量并入库，同时保存原文与元数据。
3. **查询处理**：对客户问题做归一化（去口语、补指代），必要时生成 1–2 个改写查询。
4. **召回**：用 ANN 取 top-20 到 top-50，可同时跑关键词检索（BM25）做混合召回。
5. **重排**：用交叉编码器或业务规则对候选打分，取 top-3 到 top-5。
6. **阈值过滤**：低于相关性阈值的候选直接丢弃，宁可少给也不要给错。
7. **组装上下文**：只把通过的片段按“相关度 + 条款优先级”排序后放进提示词，并附片段 id。

### 多模态输入的处理路径

| 输入 | 处理路径 | 能力边界 |
| --- | --- | --- |
| 图片（破损照片） | 多模态模型直接看图描述与判断；或先做检测/分类再交给语言模型 | 分辨率与拍摄角度影响很大；不能凭照片断定责任归属 |
| 扫描件/PDF | 解析文本层；无文本层时做 OCR 或按页转成图像交给多模态模型 | 表格与印章易错；页数与大小有上限 |
| 语音（客服录音） | 先转写成文本，再走文本链路 | 口音、噪声、方言会显著降低准确率；转写错误会一路传递 |
| 混合文档 | 文本 + 图像分别处理，最后按页或按段合并 | 需要保留页级引用，便于核对 |

**关键判断：多模态模型擅长“描述与粗判”，不擅长“定责与精算”。**照片可以说“有明显裂纹”，但不能作为“符合换货条件”的唯一依据。

## 架构与选型

| 场景 | 推荐结构 | 理由 |
| --- | --- | --- |
| 政策条款问答 | 混合召回（向量 + 关键词）+ 重排 + 阈值 | 专有名词靠关键词，口语表达靠向量 |
| 商品型号/订单号查询 | 关键词或精确匹配优先，向量兜底 | 编号类信息向量化后区分度低 |
| 长文档摘要 | 分块摘要 + 层次合并 | 单块送入避免稀释 |
| 破损照片初判 | 多模态模型描述 + 人工确认 | 定责不可自动化 |
| 客服录音质检 | 转写 + 文本检索 + 抽样复核 | 转写误差需人工兜底 |

选型依据：**先看查询里有没有强标识（编号、专名），再看表达是否口语化，最后看数据量与延迟预算。**强标识优先关键词；口语化严重必须上向量；对准确率要求高就加重排；候选数不能太大，否则重排延迟不可接受。

embedding 模型的规格（维度、最大输入长度、支持语言、计费方式）差异很大且会更新，**必须以厂商文档为准**；同一索引里绝不要混用不同模型产生的向量。

## 最小示例

下面的脚本演示“向量召回 + 交叉特征重排”。向量只有 3 维，只为可手算。

```python
import math

DOCS = [                                        # (id, 原文, 3 维向量)
    ("p1", "签收后 7 天内可申请无理由退货", [0.9, 0.1, 0.0]),
    ("p2", "质量问题退货，运费由卖家承担", [0.8, 0.2, 0.1]),
    ("p3", "赠品不参与无理由退货", [0.1, 0.9, 0.2]),
    ("p4", "发票将在退款完成后 3 个工作日开具", [0.0, 0.2, 0.9]),
]
QUERY = "东西有瑕疵想退货，运费谁出"
QUERY_VEC = [0.85, 0.15, 0.05]                  # 假设是同一个 embedding 模型编码出来的

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb) if na and nb else 0.0

recalled = sorted(DOCS, key=lambda d: cosine(QUERY_VEC, d[2]), reverse=True)[:3]
print("recall (vector):", [(d[0], round(cosine(QUERY_VEC, d[2]), 3)) for d in recalled])

KEYWORDS = ["退货", "运费", "瑕疵"]              # 简化版交叉特征，替代真实的重排模型
reranked = sorted(recalled, key=lambda d: sum(k in d[1] for k in KEYWORDS), reverse=True)
print("rerank (cross signal):", [(d[0], sum(k in d[1] for k in KEYWORDS)) for d in reranked])
```

预期输出（实测）：

```text
recall (vector): [('p1', 0.996), ('p2', 0.996), ('p3', 0.287)]
rerank (cross signal): [('p2', 2), ('p1', 1), ('p3', 1)]
```

读法很关键：召回阶段 p1 与 p2 的余弦相似度**完全并列**（都是 0.996），向量无法区分“7 天无理由”和“质量问题运费”哪条更贴合问题；重排阶段 p2 因为同时命中“退货”“运费”被提到第一位。这说明：**向量负责把候选捞进来，重排负责把答案挑出来。**同时注意 p4（发票）在向量召回里被排除了——它的向量与查询差异够大，这一步省掉了后面的无效计算。

## 动手实验

**前置条件**：Python 3.9+，无网络。

1. 保存脚本为 `embed.py` 并运行，记录召回与重排的排序差异。
2. 把 `QUERY_VEC` 改成 `[0.1, 0.9, 0.2]`（模拟“赠品能退吗”），观察召回首位是否变成 p3。
3. 把召回截断从 `[:3]` 改成 `[:1]`，再运行重排，观察 p2 是否被彻底排除——这就是“召回漏了，重排救不回来”。
4. **验证方法**：为 `cosine` 加断言，验证相同向量的相似度为 1、正交向量接近 0。
5. **清理方法**：删除 `embed.py`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 检索结果语义相近但答非所问 | 只有召回没有重排与阈值 | 人工看 top-5 的相关性分布 | 增加重排与最低相关性阈值 |
| 型号/订单号搜不到 | 编号类信息被向量化，区分度低 | 对比关键词检索与向量检索的命中 | 混合召回，编号走精确匹配 |
| 更换 embedding 模型后效果骤降 | 新查询用新模型、旧索引是旧模型 | 检查索引与查询的模型版本是否一致 | 全量重建索引，版本写入元数据 |
| 重排后延迟翻倍 | 候选数过多（如 top-100 逐对打分） | 记录各阶段耗时 | 召回与精排数量分离：召回 50、精排 10 |
| OCR 结果错字导致答错 | 扫描件质量差、印章遮挡 | 抽样比对 OCR 文本与原件 | 关键字段人工核对，保留页级引用 |
| 图片判断被客户投诉 | 把多模态“描述”当成“定责结论” | 检查答复是否把图像结论写成条件判定 | 图像只做描述，定责走政策 + 人工 |

## 安全与生产注意事项

**<u>把不同来源或不同模型的向量混进同一个索引，会造成静默的检索质量下降。</u>**向量空间不可比，混用后相似度分数失去意义，而报错不会出现。缓解方法：索引元数据里记录模型名与版本，写入时校验，升级时全量重建。

**<u>客户上传的照片、发票、录音属于敏感个人信息，未经脱敏直接入库会带来合规风险。</u>**缓解方法：入库前做字段白名单与脱敏，设置保留期限与访问控制，转写文本与图像都要有删除路径。

补充两点：重排模型与 embedding 模型同样会随版本变化，评测集要覆盖“难负例”（看似相关其实无关），否则重排提升会在真实流量里被高估；多模态能力的输入限制（支持的格式、页数、大小）以厂商文档为准，不要把限制写成代码里的隐式假设。

## 本课总结

- **embedding 解决“找得到”，重排解决“答得上”，两者缺一不可。**
- 向量召回对语义近似敏感、对编号与专名弱，混合召回是常态而非可选项。
- 召回数量决定延迟上限，精排数量决定准确率上限，两者要分开设置。
- 多模态擅长描述与粗判，涉及定责与精算必须回到政策规则与人工确认。
- 索引必须记录 embedding 模型版本，跨模型混用会造成无法察觉的质量下降。

## 思考题

如果客户问题里同时包含“订单号 + 口语化描述 + 一张破损照片”，你会如何设计检索入口？请说明各模态的优先级、可能出现的冲突，以及冲突时的处理原则。

参考思路：先用订单号做精确查询拿到订单事实（这类信息不依赖语义检索），再对口语描述做向量 + 关键词混合召回政策条款，最后让多模态模型只产出“照片中可观察到的现象”描述。冲突原则：结构化事实优先于语义检索，可观察描述优先于推断结论；三者不一致时输出“需人工核实”，而不是选一个看起来最合理的版本。

## 小测

1. 为什么重排不能替代召回？
2. 余弦相似度在使用前为什么常要求向量归一化？
3. 判断：embedding 模型升级后可以直接复用旧索引。对还是错？
4. 下列哪种查询最适合优先用关键词检索？  
   A. “这个能退吗”　B. “SKU-88231 保修多久”　C. “东西有点问题”　D. “不太满意”
5. 场景题：上线后检索 P95 延迟从 120ms 涨到 900ms，召回质量没变。请给出排查顺序。

## 答案与解析

1. 因为重排只能对“已经召回的候选”排序。若正确片段没进入候选集合，重排无论多强都无法把它找回来；召回决定上限，重排决定上限内的排序质量。
2. 归一化后向量长度都是 1，点积直接等于余弦相似度，计算更省；同时避免“长文档向量模长大”导致的分数偏差，使不同长度文本可比。
3. **错。**不同模型产生的向量不在同一语义空间，新旧混用会让相似度失去意义，且不会报错，只会静默降质。必须全量重建索引。
4. **B。**编号是强标识，关键词/精确匹配区分度最高。A、C、D 都是口语化表达，向量检索更有优势。
5. 排查顺序：先看各阶段耗时占比（查询编码、ANN 检索、重排），确认瓶颈在哪；再查候选数是否被调大（召回 top-k 与重排数量）；再看索引规模与是否缺少合适的 ANN 索引；最后查是否新增了同步调用（例如在线调用重排服务）。修复方向：拆分召回与精排数量、给重排加超时与降级、把非必要步骤改为异步。
