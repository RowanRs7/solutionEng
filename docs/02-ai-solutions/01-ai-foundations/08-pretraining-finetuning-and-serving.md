# 预训练、微调、推理与模型服务

## 为什么需要学习

晴空商城想把售后政策“训进模型”。团队收集了 3000 条历史答复做了微调，上线第一天效果不错；两周后政策从“7 天无理由”改成“15 天”，模型依旧自信地回答 7 天——因为知识被写进了参数，而参数不会自己更新。同一时期，另一个小组为了省钱自建推理服务，结果单卡并发撑不住，用户在客服页面等了 12 秒才看到第一个字。

这两个问题都属于“训练与服务”的边界判断：**微调改变的是行为与格式，不改变知识的时效性；推理服务的延迟主要由排队与批处理策略决定，而不只是模型大小。**

> **核心结论：** 用微调改行为，用检索改知识，用服务工程改延迟与成本——三者混用是最贵的错误。

## 学习目标

完成本课后，你能够：

- 解释 *继续预训练*、*监督微调（SFT）*、*LoRA*、*偏好优化*、*KV 缓存*、*连续批处理*、*量化*。
- 为一个业务需求判断该用提示词、检索、微调还是换模型，并说明理由。
- 解释 *首 token 延迟* 与 *每 token 延迟* 的差别，以及批处理与量化对它们的影响。
- 用脚本校验 SFT 训练数据的结构与长度，识别常见脏数据。

## 业务场景

售后助手有三类改进需求，性质完全不同：

- **知识更新**：政策条款变更、新增例外品类。要求“明天就生效”。
- **行为规范**：答复必须先说结论、必须带引用、语气要克制。要求“每次都一样”。
- **输出格式**：稳定的 JSON 字段，供工单系统解析。要求“解析成功率 99.9%”。

此外还有运行层要求：大促期间并发上涨 5 倍，P95 首字延迟不超过 2 秒，单条成本不超过预算。

本课只看这个侧面：**哪些需求该用训练解决，哪些该用检索或结构解决，以及服务端如何把这些能力稳定交付出去。**

## 核心概念

*继续预训练* 是在已有模型上用大量领域文本继续做“预测下一个 token”，让它更熟悉某个领域的语言分布（例如医疗、法律、企业内部文档）。它消耗数据多、成本高，且**不保证学到具体事实**。

*监督微调（SFT）* 是用“输入 → 期望输出”的样本继续训练，让模型学会按特定格式与风格回答。

*LoRA* 是一种参数高效微调方法：冻结原模型，只训练少量低秩矩阵。训练快、显存小、产物是一个可插拔的适配器。*QLoRA* 在此基础上把基座量化后训练，进一步降低显存需求。

*偏好优化*（如 RLHF、DPO）用“哪个回答更好”的比较数据调整模型倾向，主要改变风格、拒绝行为与安全性，而不是注入知识。

*KV 缓存* 是推理时的关键优化：已生成 token 的中间结果被缓存复用，避免每步重算整段序列，因此生成第 N 个 token 比生成第 1 个 token 便宜得多。

*连续批处理* 是服务端把不同请求的动态合并成批，边生成边插入新请求，显著提升吞吐。代价是单请求延迟会受同批其他请求影响。

*量化* 是把权重与计算从高精度（如 16 位浮点）压到 8 位或 4 位，减少显存占用、提升吞吐，但可能带来质量下降，尤其是长输出与格式严格的任务。

| 方法 | 解决的问题 | 数据需求 | 知识更新 | 典型成本 |
| --- | --- | --- | --- | --- |
| 提示词工程 | 表达方式、输出结构 | 几条示例 | 无 | 最低 |
| 检索增强（RAG） | 事实与时效 | 文档 + 评测集 | 立即生效 | 低 |
| SFT | 格式、语气、任务模式 | 数百到数万条高质量样本 | 弱且会过时 | 中 |
| LoRA | 同 SFT，但资源更省 | 同上 | 弱且会过时 | 中低 |
| 继续预训练 | 领域语言分布 | 千万 token 级 | 有限 | 高 |
| 偏好优化 | 风格、拒答、安全倾向 | 成对比较数据 | 无 | 中高 |

## 工作原理

### 训练侧

1. **定义目标**：明确要改变的是行为还是知识。知识类需求直接走检索，不做训练。
2. **准备数据**：把真实工单整理成 `messages` 结构，去除个人信息，剔除互相矛盾的样本。
3. **切分评测集**：留出一部分样本永不参与训练，用于前后对比。
4. **选择方法**：样本少、资源紧用 LoRA；需要改变拒答与风格再加偏好优化。
5. **训练与早停**：监控验证集损失，避免过拟合到训练样本的表达。
6. **行为评测**：除了损失，还要测格式合法率、引用正确率、拒答率与人工偏好。
7. **版本化交付**：基座版本 + 适配器版本 + 数据版本一起记录，可回滚。

### 推理侧

1. 请求进入队列，服务端做鉴权、限流与长度检查。
2. 调度器把多个请求合并成批（连续批处理），分配显存。
3. 对提示词做前向计算，得到首个 token（决定 *首 token 延迟*）。
4. 逐 token 生成，复用 KV 缓存（决定 *每 token 延迟*）。
5. 流式返回已生成的片段，直到结束或达到上限。
6. 释放显存并记录 token 数、延迟与失败原因。

**关键结论：吞吐由批处理与显存效率决定，单请求延迟由排队时间 + 首 token 计算 + 生成长度决定。**把并发调高但显存不足时，排队会抵消批处理带来的收益。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要权衡 |
| --- | --- | --- | --- |
| 托管 API | 快速上线、流量波动大、无 GPU 团队 | 数据不可出境、需极致成本控制 | 免运维；单价与限流受厂商约束 |
| 自建推理（如 vLLM 类服务） | 稳定高并发、需要私有化、需要定制 | 团队无运维能力、流量很小 | 单位成本可降；需容量规划与值班 |
| 本地/边缘运行（如 Ollama 类工具） | 开发调试、离线演示、个人助理 | 生产高并发、严格 SLA | 部署简单；能力与吞吐受限 |
| 微调专用模型 | 格式固定、量大、行为要求严格 | 知识频繁变化、样本不足 | 行为可控；维护成本高 |

选型依据：**先看数据能否出域，再看流量是否稳定，最后看团队是否有运维能力。**流量小且波动大时，托管 API 的总成本通常更低；流量稳定且合规要求私有化时，自建才有意义。微调只在“提示词 + 检索已经无法满足格式或一致性要求”时才考虑。

具体模型的可微调方式、支持的适配器类型、上下文与并发限制都在变化，**以厂商文档为准**。例如 OpenAI 的监督微调指南说明了数据格式、训练与部署流程，不同模型系列的支持范围不同。

## 最小示例

下面的脚本校验 SFT 训练数据的结构与规模。数据保存为 `train.jsonl`（每行一个样本）：

```json
{"messages": [{"role": "system", "content": "你是售后助手，只能依据给定政策回答。"}, {"role": "user", "content": "签收第 5 天能无理由退货吗"}, {"role": "assistant", "content": "可以，签收后 7 天内商品完好即可申请。"}]}
{"messages": [{"role": "user", "content": "运费谁出"}, {"role": "assistant", "content": "质量问题由卖家承担。"}]}
{"messages": [{"role": "assistant", "content": "缺少用户问题。"}, {"role": "user", "content": "顺序反了"}]}
```

```python
import json
import math

ROLES = {"system", "user", "assistant"}          # 角色白名单，防止脏字段进入训练

def estimate_tokens(text):
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    return math.ceil(cjk + (len(text) - cjk) / 4)  # 中文 1:1，英文 4 字符 1 token

samples = [
    {"messages": [
        {"role": "system", "content": "你是售后助手，只能依据给定政策回答。"},
        {"role": "user", "content": "签收第 5 天能无理由退货吗"},
        {"role": "assistant", "content": "可以，签收后 7 天内商品完好即可申请。"}]},
    {"messages": [
        {"role": "user", "content": "运费谁出"},
        {"role": "assistant", "content": "质量问题由卖家承担。"}]},
    {"messages": [
        {"role": "assistant", "content": "缺少用户问题。"},
        {"role": "user", "content": "顺序反了"}]},
]

problems, seen, total = [], set(), 0
for index, sample in enumerate(samples, start=1):
    msgs = sample.get("messages", [])
    if not msgs or msgs[-1].get("role") != "assistant":   # 最后一条必须是助手回复，否则没有学习目标
        problems.append((index, "last message is not assistant"))
    for msg in msgs:
        if msg.get("role") not in ROLES:                  # 未知角色直接报错
            problems.append((index, f"bad role {msg.get('role')}"))
        total += estimate_tokens(msg.get("content", ""))
    key = json.dumps(msgs, ensure_ascii=False, sort_keys=True)
    if key in seen:                                       # 完全重复会放大过拟合
        problems.append((index, "duplicate sample"))
    seen.add(key)

print("samples:", len(samples), "estimated tokens:", total)
print("problems:", len(problems))
for index, reason in problems:
    print(f"- sample {index}: {reason}")
```

预期输出（实测）：

```text
samples: 3 estimated tokens: 71
problems: 1
- sample 3: last message is not assistant
```

三个设计意图：**训练目标必须是最后一条助手回复**，否则模型学不到“问什么答什么”；角色白名单可以拦住拼写错误与多余字段；重复样本检测很便宜，但能避免模型把某一句答复背下来。这个脚本只覆盖结构，不覆盖质量——真实项目还必须检查“同义问题是否得到冲突答案”“答复是否引用了已废止政策”。

## 动手实验

**前置条件**：Python 3.9+，无 GPU、无网络。

1. 保存代码为 `sft.py` 并运行，记录输出。
2. 把第三条样本的角色顺序改正（user 在前、assistant 在后），重跑，预期 `problems: 0`。
3. 复制第一条样本粘贴两次，重跑，预期出现 `duplicate sample`。
4. 在 `system` 内容里加入 5000 字政策全文，观察 `estimated tokens` 暴涨——这就是“把知识塞进微调数据”的代价。
5. **验证方法**：断言 `total > 0` 且 `len(problems) <= len(samples)`，用于防止解析异常导致的静默空集。
6. **清理方法**：删除 `sft.py` 与 `train.jsonl`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 微调后仍答错政策时效 | 用训练改知识，而知识需要检索 | 改政策文档后看模型是否跟着变 | 知识走检索，训练只改行为 |
| 微调后通用能力明显下降 | 数据单一或训练过久导致遗忘 | 对比微调前后在通用测试集上的表现 | 降低训练步数、混入通用样本、用 LoRA |
| 损失下降但人工评分没提升 | 训练数据质量差或评测维度不匹配 | 检查样本是否有矛盾、评测是否只看损失 | 清洗数据，加入格式与引用指标 |
| 首 token 延迟 10 秒以上 | 排队严重或提示词过长 | 记录排队时间与输入 token 数 | 扩容、缩短输入、启用前缀缓存 |
| 量化后 JSON 解析失败率上升 | 低精度导致格式约束能力下降 | 对比量化前后的格式合法率 | 换更高精度或加强 schema 校验 |
| 训练数据里出现客户手机号 | 数据未脱敏 | 正则扫描训练集 | 上线前强制脱敏与人工抽检 |

## 安全与生产注意事项

**<u>把未脱敏的客户对话直接用于微调，会让个人信息永久固化进模型权重，事后无法逐条删除。</u>**缓解方法：训练前做规则扫描 + 人工抽检，建立数据来源台账与授权记录，敏感字段一律替换为占位符。

**<u>自建推理服务若没有鉴权、配额与租户隔离，一个失控的客户端就能拖垮全部业务。</u>**缓解方法：网关层做鉴权与速率限制，按租户分配配额，设置最长输入输出上限与超时，并准备降级到小模型或排队页面的方案。

补充两点：量化与模型升级都必须跑同一套回归评测，否则“省钱”可能以格式崩坏为代价；训练数据与模型版本要绑定记录，出问题时可回答“这个行为来自哪批数据”。

## 本课总结

- **微调改行为，检索改知识，服务工程改延迟与成本——三者不能互相替代。**
- SFT 与 LoRA 学习的是“怎么答”，知识会随政策变化而过时，因此必须与检索配合。
- 推理延迟由排队、首 token 计算与生成长度共同决定，KV 缓存与连续批处理影响吞吐而非单请求体验。
- 量化降低显存与成本，但要用格式合法率与人工评分验证，不能只看吞吐。
- 选型顺序：数据能否出域 → 流量是否稳定 → 团队是否有运维能力 → 是否需要微调。

## 思考题

售后团队希望“大促期间把自建推理服务的并发提高 3 倍，同时保持 P95 首字延迟不变”。请判断这在什么条件下可行，需要哪些前置测量，以及你会优先调整哪三个杠杆。

参考思路：可行性取决于当前是否已显存打满、批处理效率高不高、输入长度是否有压缩空间。前置测量：各阶段耗时分布（排队、首 token、生成）、显存利用率、平均输入输出长度、批大小与吞吐曲线。三个杠杆：压缩输入（检索替代全量拼接、前缀缓存）、按任务分级（简单问题路由到小模型）、弹性扩容 + 排队可见化（前端明确等待状态）。

## 小测

1. 想让模型“记住昨天发布的新政策”，应该用哪种手段？
2. LoRA 相比全参数微调的主要优势是什么？
3. 判断：连续批处理能降低单个请求的首 token 延迟。对还是错？
4. 下列哪项最适合用偏好优化？  
   A. 注入产品价格　B. 调整拒答与语气倾向　C. 提升检索召回　D. 降低显存占用
5. 场景题：微调后模型在内部测试集上得分提升，但上线一周投诉变多。请给出三个排查方向。

## 答案与解析

1. 检索（RAG）。知识属于事实与时效问题，改参数既慢又不保证准确，而且下次变更还要重训。微调可以用来统一“如何表述这条政策”，但不能作为知识来源。
2. 只训练少量低秩参数，显存与时间成本低，产物是可插拔适配器，便于多任务并存与回滚；同时更不容易破坏基座模型的通用能力。
3. **错。**连续批处理主要提升吞吐（单位时间处理的请求数），同批请求会互相等待，单请求延迟可能反而上升；首 token 延迟更多受排队与输入长度影响。
4. **B。**偏好优化用比较数据调整倾向性，适合拒答边界与语气。A 属于知识注入（应走检索），C 属于检索系统，D 属于量化或部署优化。
5. 方向一：测试集与真实流量分布不一致（内部样本偏简单、偏标准表达），需用线上失败样本重建评测集。方向二：知识类问题被训练“背下来”而政策已变更，需把事实改回检索。方向三：格式或引用要求在实际渠道（多轮、带附件）下未被满足，需按渠道分层统计解析失败率与引用命中率。
