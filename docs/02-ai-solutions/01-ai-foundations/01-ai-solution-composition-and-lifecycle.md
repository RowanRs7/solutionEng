# AI 解决方案的组成与生命周期

## 为什么需要学习

晴空商城在客服平台里接入了一个大模型接口，售后退款答复的初稿从 6 分钟缩短到 40 秒，团队宣布“AI 上线成功”。三周后问题集中爆发：客服发现答复引用了已经下线的“七天无理由”旧口径；运营发现没人能证明答复准确率是多少；财务发现退款建议里出现过一笔 0 元退款；运维发现月底账单比预期高四倍，却说不清钱花在哪个环节。

这些故障没有一个来自“模型不会说话”。它们分别来自知识过期、缺少评测、工具参数没有校验、成本没有预算。也就是说，团队只交付了模型调用，没有交付一个 AI 解决方案。

> **核心结论：** AI 解决方案是一个由模型、数据、检索、工具、流程、评测、运维组成的系统；任何一层缺失，都会以业务事故的形式在其他层暴露出来。

## 学习目标

完成本课后，你能够：

- 解释 *AI 解决方案*、*能力层*、*评测基线*、*生命周期证据* 四个概念。
- 用一张对照表说明 AI 方案与传统方案在七个组成层上的差异。
- 把“售后智能助手”的六个业务步骤逐个落到组成层，并指出每层的负责人和验证方式。
- 判断一个具体工作事项属于生命周期的哪个阶段，以及该阶段应产出什么证据。

## 业务场景

晴空商城的“售后智能助手”要完成一段固定链路：

1. 客服在工单页输入客户问题，例如“收到货第三天发现屏幕有亮点，能退吗”。
2. 系统检索售后政策（退换货条款、时效、例外）与该客户的订单记录。
3. 模型基于检索结果生成答复草稿，或给出退款/换货建议。
4. 客服人工确认、修改或驳回。
5. 确认后调用工具：创建退款单、通知仓库、写入工单备注。
6. 全过程留痕，供复盘与抽检。

本课不谈“怎么写 Prompt”，也不谈“选哪个模型”，只看一个问题：把这条链路做成可交付、可复核的方案，需要哪些层，每层靠什么证据证明自己完成了。

## 核心概念

*AI 解决方案* 是为达成某个业务目标，把模型能力与数据、检索、工具、流程、评价和运行机制组合起来的整体交付物。它与“一个能跑通的 Demo”的区别在于：每一层都有明确的负责人、边界和验证方式。

*能力层* 是方案中承担单一职责的一组组件。分层不是为了画图好看，而是为了让故障可以定位：答复引用了旧政策，是检索层或数据层的问题；退款金额算错，是工具层参数校验的问题；没人知道准不准，是评测层缺失。

*评测基线* 是在上线前用固定样本测出的一组数字（准确率、引用正确率、拒答率、P95 延迟、单次成本），作为后续每次改动的比较起点。没有基线，任何“效果变好了”都只是感觉。

*生命周期证据* 是某个阶段结束时可以拿给别人检查的实物：访谈记录、口径清单、接口契约、评测报告、灰度数据、告警配置。

| 组成层 | 在售后助手中承担什么 | 缺失后的典型事故 |
| --- | --- | --- |
| 模型层 | 理解问题、组织答复语言、生成建议 | 答复生硬、格式不稳定、拒答过度 |
| 数据层 | 订单、客户、政策口径、历史工单 | 引用过期政策，或查到别人的订单 |
| 检索层 | 从政策库与订单里找出相关片段 | 检索不到关键条款，答复凭空发挥 |
| 工具层 | 创建退款单、查物流、写工单 | 参数越权、重复退款、脏数据入库 |
| 流程层 | 人工确认、异常分支、重试与兜底 | 模型直接动钱，没人拦得住 |
| 评测层 | 固定样本集与指标口径 | 无法回答“准不准”，改版后回归靠运气 |
| 运维层 | 日志、追踪、成本、延迟、降级 | 账单失控、故障无法定位、无法回滚 |

### 与传统方案逐层对照

| 对照面 | 传统集成方案 | AI 解决方案 | 新增工程负担 |
| --- | --- | --- | --- |
| 输入 | 结构化的表单与固定字段 | 自由文本、图片、多轮对话 | 输入归一化、意图澄清 |
| 输出 | 确定的结构与状态码 | 有概率波动的自然语言或结构化建议 | 输出校验、兜底文案、重试 |
| 正确性 | 由逻辑与测试用例保证 | 由样本集与统计指标近似估计 | 评测集维护、抽检机制 |
| 失败表现 | 报错、超时，可复现 | 自信地说错、漏答、答非所问 | 幻觉检测、引用核对 |
| 变更影响 | 代码版本可回归 | 模型版本、Prompt、检索参数都会改变行为 | 版本锁定、回归评测 |
| 成本结构 | 服务器与带宽为主 | 按 token 计费，随上下文线性增长 | 预算、缓存、上下文裁剪 |
| 权限边界 | 接口级权限 | 还要约束模型能看什么、能调什么 | 工具白名单、数据脱敏 |

**结论：AI 方案不是多了一个组件，而是多了一类“输出不完全可信”的组件，因此必须多出评测层与流程兜底层。**

## 工作原理

一个 AI 方案的成型过程按以下顺序推进，每一步都产生下一步要用的证据：

1. **判断适合性**：先确认问题是否真的需要生成式能力。能用规则、模板、搜索解决的，不要上模型。输出物是“为什么必须用模型”的一段说明。
2. **固定业务口径**：把政策、例外、审批阈值写成唯一来源（例如政策库的版本化文档）。口径不稳定，后面所有评测都无意义。
3. **准备数据与知识**：整理订单查询接口、政策文档、历史工单，明确哪些字段可见、保留多久、谁能访问。
4. **选模型与接入方式**：确认能力（长文本、结构化输出、多模态）、延迟、成本、合规约束，再决定托管 API、开源权重或混合路由。
5. **接检索与工具**：检索层负责“找出依据”，工具层负责“执行动作”。两者都必须有明确的输入校验与超时。
6. **编排流程**：定义人工确认点、异常分支、重试次数和降级文案。模型永远处在“建议”位置，动钱的动作必须经过人。
7. **建立评测基线**：用 50–200 条真实工单构成样本集，测准确率、引用正确率、拒答率、延迟与成本。
8. **灰度与运行**：小流量上线，采集失败样本，形成“坏案例库”，再进入下一轮迭代。

## 架构与选型

| 方案形态 | 适用场景 | 不适用场景 | 主要权衡 |
| --- | --- | --- | --- |
| 纯 Prompt + 单次模型调用 | 生成话术、改写、摘要等低风险任务 | 需要事实准确、需要执行动作 | 最快最便宜，但无法保证事实 |
| 检索增强（RAG） | 政策问答、订单解释、知识密集答复 | 知识无法文档化、检索质量无保障 | 可引用可溯源，但检索质量成为瓶颈 |
| RAG + 工具调用 | 需要查实时状态、需要执行退款等动作 | 动作不可逆且无人工审核 | 能力完整，但权限与幂等成本最高 |
| 微调专用模型 | 格式高度固定、语气统一、量大且稳定 | 知识经常变化、样本量不足 | 行为可控，但知识更新仍需检索 |
| 规则优先 + 模型兜底 | 高频、可枚举的标准问题 | 长尾复杂咨询占多数 | 成本最低、最可预测，覆盖率受限 |

选型依据按顺序检查：**先问输出错了会怎样，再问事实从哪里来，最后才问用哪个模型。**

## 最小示例

下面是一张“组成卡”，用 JSON 记录售后助手每一层的负责人与证据。文件保存为 `solution-card.json`：

```json
{
  "solution": "aftersales-assistant",
  "layers": {
    "model": {"owner": "ai-platform", "evidence": "model-version-lock-2026-10.md"},
    "data": {"owner": "data-team", "evidence": "policy-catalog-v3, order-api-contract"},
    "retrieval": {"owner": "ai-platform", "evidence": "recall-report-2026-10.json"},
    "tools": {"owner": "refund-team", "evidence": "tool-scope-list, idempotency-spec"},
    "workflow": {"owner": "customer-service", "evidence": "human-approval-flow-v2"},
    "eval": {"owner": "qa", "evidence": "baseline-200-cases-2026-10.json"},
    "ops": {"owner": "sre", "evidence": "dashboards, budget-alert-80pct"}
  }
}
```

用标准库检查这张卡是否完整：

```python
import json

REQUIRED = ["model", "data", "retrieval", "tools", "workflow", "eval", "ops"]

with open("solution-card.json", encoding="utf-8") as handle:
    card = json.load(handle)          # 读取组成卡，避免把结构写死在脚本里

layers = card.get("layers", {})
problems = []

for name in REQUIRED:                  # 逐层检查，缺层即为方案缺口
    layer = layers.get(name)
    if layer is None:
        problems.append(f"missing layer: {name}")
        continue
    for field in ("owner", "evidence"):  # 有负责人没有证据同样不算完成
        if not layer.get(field):
            problems.append(f"{name}: missing {field}")

print("layers checked:", len(REQUIRED))
print("problems:", len(problems))
for item in problems:
    print("-", item)
```

预期输出：

```text
layers checked: 7
problems: 0
```

把 `"eval"` 整段删掉再运行，预期输出会变成 `problems: 1` 并打印 `- missing layer: eval`。这说明脚本检查的是“方案是否具备可验证结构”，而不是模型效果。

## 动手实验

**前置条件**：Python 3.9+；一个空目录；不需要任何 API Key。

1. 在空目录创建 `solution-card.json`，先只填 `model` 与 `data` 两层。
2. 保存上面的检查脚本为 `check_card.py`。
3. 运行 `python3 check_card.py`。
4. 预期结果：输出 `problems: 5`，并列出缺失的 `retrieval`、`tools`、`workflow`、`eval`、`ops`。
5. 逐层补齐，每补一层重跑一次，观察问题数单调下降。
6. **验证方法**：把某一层的 `evidence` 置空字符串，确认脚本能报出 `missing evidence`，说明检查逻辑有效。
7. **清理方法**：删除实验目录，或执行 `rm solution-card.json check_card.py`。该实验不产生网络请求，也不写入任何外部系统。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| Demo 很好，上线后投诉变多 | 只有模型层，缺评测与流程兜底 | 检查是否存在固定样本集和人工确认点 | 先补评测基线，再放量 |
| 答复引用过期政策 | 数据层口径未版本化，或检索命中旧文档 | 抽 20 条答复，核对引用文档版本号 | 建立唯一政策源，旧文档下架 |
| 同一退款被创建两次 | 工具层缺幂等键，重试直接重复执行 | 查工具日志中相同订单号的调用次数 | 引入幂等键与人工确认 |
| 月底成本翻倍且无法归因 | 运维层没有按功能/租户的用量记录 | 检查日志里是否带请求来源与 token 数 | 按维度打标，设置预算告警 |
| 改版后“感觉变差”但无法证明 | 没有基线，也没有回归评测 | 询问改版前后的同一指标数值 | 固化评测集与指标口径 |

## 安全与生产注意事项

**<u>没有工具权限边界，模型就会成为越权执行器。</u>**售后助手能查订单、能创建退款，一旦工具清单过宽，一个被污染的输入就可能触发超出业务范围的调用。缓解方法：工具白名单、按角色限定可调用工具、金额与数量上限、所有写操作要求人工确认与幂等键。

**<u>没有评测基线和灰度计划就全量上线，等于拿真实客户做实验。</u>**必须先有小流量灰度、坏案例回收和快速回滚路径，并记录每次模型或 Prompt 变更的版本号，否则事故发生时无法判断是哪个变更引起的。

## 本课总结

- **AI 解决方案由模型、数据、检索、工具、流程、评测、运维七层组成，缺任何一层都会在业务侧暴露。**
- AI 方案与传统方案最大的差别是输出不完全可信，因此评测层与流程兜底层是必需品，不是加分项。
- 组成卡把“我们做了 AI”变成“每层有负责人、有证据”，这是可交付与 Demo 的分界线。
- 生命周期按“判断适合性 → 固定口径 → 备数据 → 选模型 → 接检索与工具 → 编排流程 → 建基线 → 灰度运行”推进，每步都要产出可检查的证据。
- 选型顺序是**先看错了会怎样，再看事实从哪来，最后才看用哪个模型**。

## 思考题

晴空商城希望把“客服确认”这一步也交给模型自动完成，以进一步压缩处理时间。请从组成层角度分析：这需要哪些层先达到什么条件，才具备讨论的资格？如果条件不具备，你可以提出什么替代方案？

参考思路：需要工具层具备幂等与金额上限、流程层具备可中断的自动执行与回滚、评测层能量化“错误自动退款”，运维层具备实时拦截与审计。条件不满足时，可先做“自动填写、人工一键确认”，把人的点击保留为最后闸门。

## 小测

1. 下列哪一项最可能属于“评测层缺失”导致的问题？  
   A. 答复语气不够礼貌　B. 没人能说出准确率是多少　C. 接口返回 500　D. 检索结果为空
2. 为什么“数据层”要先于“模型层”固定口径？
3. 工具层与流程层的职责边界是什么？
4. 判断：只要模型足够强，就可以省掉人工确认环节。对还是错？
5. 场景题：团队报告“售后助手准确率 92%”，但样本只是最近 30 条工单，且都由同一位客服挑选。你会先质疑什么，如何改进？

## 答案与解析

1. **B。**评测层负责给出可复现的指标和口径。A 属于体验调优，C 属于可用性故障，D 属于检索或数据问题，都不会因为“有了评测集”而自动解决。
2. 因为评测与检索都以口径为基准。如果政策本身有两个版本，同一个问题可以得到两个“正确”答案，模型再强也无法被验证；先固定唯一来源，后续指标才有意义。
3. 工具层负责“能做什么、参数如何校验、失败如何返回”，是能力与安全边界；流程层负责“什么时候允许做、谁批准、异常怎么退”，是决策与兜底边界。把两者混在一起，就会出现“模型既判断又执行”的危险结构。
4. **错。**模型强只降低出错概率，不改变“输出不完全可信”的本质。不可逆动作（退款、通知仓库）必须保留人工确认或严格的分层授权，这属于流程层设计，与模型能力无关。
5. 先质疑样本的代表性与采样方式：30 条太少，且由单人挑选会系统性偏向“容易判断的工单”，无法代表长尾复杂咨询。改进方向是按问题类型分层抽样、覆盖已知失败案例、固定样本集并记录版本，同时给出指标定义（什么叫“准确”）与置信区间，而不是单一百分比。
