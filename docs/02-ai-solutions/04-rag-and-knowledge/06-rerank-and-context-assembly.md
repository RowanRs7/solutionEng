# Rerank、结果筛选与上下文组装

## 为什么需要学习

上一课的小实验暴露了一个真实结果：混合检索用 RRF 融合后，正确条款被排到第三位，第一名是“运费承担”——两路都没错，却都不够准。如果直接把前 60 条塞进 Prompt，模型会同时看到退货、运费、换货、发票四类规则，然后自信地混着回答。

晴空商城的第一版一次塞 12 个片段、约 5000 token，成本是后来的 6 倍，错误却更多了——模型会引用“运费由商城承担”回答“耳机能不能退”。更糟的是，遇到知识库没有覆盖的问题，它仍会编出看似合理的答案。

> **核心结论：** 检索负责“把可能的证据找回来”，rerank 负责“把最可能的证据排到前面”，上下文组装负责“在预算内把证据讲清楚”；三者缺一，模型就只能靠猜。

## 学习目标

完成本课后，你能够：

- 解释 *bi-encoder* 与 *cross-encoder* 的机制差异，并估算引入 rerank 后的延迟与成本。
- 设计一套同时含绝对阈值、相对阈值与去重的筛选规则，并说明每条规则挡掉什么。
- 在给定 token 预算下写出组装逻辑：排序、引用编号与兜底话术。
- 识别“证据不足时硬答”这一最危险的生产故障，并给出可验证的拦截方法。

## 业务场景

售后智能助手的回答要经人工确认后才调用退款工具，因此“答错”的代价既有赔付风险也有合规风险。客服主管提了三条验收要求：回答必须能指到具体条款；政策没有覆盖的问题必须明确说“未找到”，不能编；单次检索 + 组装的额外延迟不超过 400 毫秒。

三条要求分别对应本课的筛选、兜底与预算。

## 核心概念

*Rerank（重排）* 是对候选集重新打分的第二阶段排序。*Cross-encoder* 把“问题 + 片段”拼成一个输入送进模型，直接输出相关性，因此能捕捉两者之间的细粒度交互；*bi-encoder* 则是把问题和片段分别编码成向量再算相似度，可以在入库时预先算好。

| 维度 | Bi-encoder（向量检索） | Cross-encoder（rerank） |
| --- | --- | --- |
| 计算时机 | 文档向量可离线预算 | 每次查询对每对文本实时计算 |
| 单次成本 | 一次向量比较 | 一次模型前向，量级高得多 |
| 精度 | 中，受向量容量限制 | 高，能看懂否定与条件 |
| 可扩展性 | 支持百万级候选 | 只适合几十到几百条候选 |
| 典型用法 | 召回 | 对 top-50 重排取 top-8 |

其他术语：*relevance score* 是 rerank 模型给出的相关性分数；*绝对阈值* 是固定下限，*相对阈值* 是与最高分的差距比例；*token 预算* 是分配给上下文的 token 上限；*lost in the middle* 指相关信息位于长上下文中间时更容易被模型忽略的现象；*上下文污染* 指无关片段把正确答案挤出去或误导模型。

| 筛选手段 | 挡掉什么 | 风险 |
| --- | --- | --- |
| 绝对阈值 | 明显不相关的候选 | 阈值过高会“永远找不到”，过低等于没筛 |
| 相对阈值 | 明显不如第一名的候选 | 只有一个正确答案时表现好，多个并列答案时会误杀 |
| 正文去重 | 重叠片段、同段多切 | 过度去重可能删掉必要补充 |
| token 预算 | 超长上下文带来的成本与噪声 | 预算太小会丢掉关键证据 |

## 工作原理

1. **收候选**：从混合检索取较宽的一批（例如 50–100 条），保留来源与元数据。
2. **粗筛**：先用相似度或融合分过滤，减少送进 rerank 的条数。
3. **构造查询-片段对**：把用户问题（或改写后的问题）与片段正文按模型要求拼接，标题前缀一并送入，让模型看到“这是哪一条”。
4. **逐对打分**：cross-encoder 输出相关性分数；托管服务通常返回每条文档的 `index` 与 `relevance_score`，按分数降序即为重排结果。
5. **筛阈值**：先卡绝对下限，再卡与第一名的相对差距；两条规则同时生效，避免“矮子里拔将军”。
6. **去重与多样性**：正文互相包含的只保留高分者；必要时做轻微多样化，避免 5 条都是同一款条款的不同切法。
7. **按预算装箱**：按分数从高到低装，装不下就丢弃，**绝不截断片段正文**——被截断的条款比没有更危险。
8. **排位置并编号**：为每条片段加引用编号与来源标题；片段较多时把最强证据放在首位与末位，减少“中间遗忘”。
9. **兜底判断**：若无候选通过阈值，或最高分仍低于业务下限，直接返回“未找到相关政策，已转人工”，不进入生成。

第 9 步是整条链路里最容易被省略、也最贵的一步。**没有兜底的 RAG 系统会在证据缺失时稳定地编造。**

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 不做 rerank，只用向量分 | 候选少、问题简单、延迟极敏感 | 条款相似度高、需要区分“可退/不可退” | 省一次模型调用；精度上限低 |
| 托管 rerank API | 想快速上线、多语言 | 数据不能出内网 | 免运维；按调用量计费、受版本影响 |
| 自托管 cross-encoder | 隐私要求高、调用量大 | 没有 GPU 与推理运维能力 | 可控；需自己调优与扩容 |
| 用 LLM 打分 | 需要复杂判断（如“是否适用本类目”） | 延迟与成本紧张 | 灵活；输出不稳定、难标定阈值 |
| 规则为主 + 少量 rerank | 条款编号、类目匹配可规则化 | 语义判断占比高 | 可解释、便宜；覆盖面有限 |

选型依据：**候选规模**（几百条以上别用 LLM 逐条打分）、**数据边界**（能否外发政策全文）、**延迟预算**（rerank 常是最慢一跳）。晴空商城先用规则卡类目与租户，再 rerank 30 条候选，最后按预算组装。

## 最小示例

下面的脚本实现“阈值筛选 + 去重 + token 预算装箱 + 引用编号 + 兜底话术”，是上下文组装阶段最常被写错的一段逻辑。

```python
import math

CANDIDATES = [
    {"id": "c1", "section": "第三条 运费承担", "score": 0.91,
     "text": "因质量问题退货，运费由商城承担；非质量原因退货，运费由消费者承担。"},
    {"id": "c2", "section": "第二条 适用范围", "score": 0.88,
     "text": "已激活或已使用的电子产品不适用七天无理由退货。"},
    {"id": "c3", "section": "第三条 运费承担", "score": 0.72,
     "text": "偏远地区退货运费按实际发生额结算。"},
    {"id": "c4", "section": "第五条 发票", "score": 0.41,
     "text": "电子发票在订单完成后可在订单详情页申请。"},
    {"id": "c5", "section": "第七条 赠品", "score": 0.38,
     "text": "赠品随主商品一并退回，不单独退款。"},
    {"id": "c6", "section": "第三条 运费承担", "score": 0.70,
     "text": "非质量原因退货，运费由消费者承担。"},          # 与 c1 正文部分重合
    {"id": "c7", "section": "第六条 换货", "score": 0.65,
     "text": "质量问题换货需在签收后七日内申请，换货商品需保持完好。"},
    {"id": "c8", "section": "第四条 退款时效", "score": 0.55,
     "text": "退款在审核通过后一至三个工作日到账。"},
]

MIN_SCORE = 0.5      # 绝对阈值：低于它视为与本问题无关
REL_MARGIN = 0.35    # 相对阈值：与最高分差距超过 35% 的丢弃
BUDGET = 120         # 上下文 token 预算（示意值）

def est_tokens(text):
    # 粗略估算：中文约 1.5 字符/token；生产环境必须换成真实 tokenizer
    return math.ceil(len(text) / 1.5)

def dedupe(cands):
    # 正文互相包含视为重复片段，保留分高的一条
    kept = []
    for c in cands:
        if any(c["text"] in k["text"] or k["text"] in c["text"] for k in kept):
            continue
        kept.append(c)
    return kept

def select(cands, min_score=MIN_SCORE, margin=REL_MARGIN, budget=BUDGET):
    top = max(c["score"] for c in cands)
    # 两道筛选：绝对阈值挡“无关”，相对阈值挡“明显不如最好”
    cands = [c for c in cands if c["score"] >= min_score and c["score"] >= top * (1 - margin)]
    cands.sort(key=lambda c: c["score"], reverse=True)
    cands = dedupe(cands)

    picked, used, dropped = [], 0, []
    for c in cands:
        cost = est_tokens(c["text"]) + 8        # +8 给标题行与引用编号留余量
        if used + cost <= budget:
            picked.append(c)
            used += cost
        else:
            dropped.append(c["id"])             # 超预算整条丢弃，绝不截断正文
    return picked, used, dropped

picked, used, dropped = select(CANDIDATES)

# 位置策略：片段较多时把最强证据放首尾，补充证据放中间
ordered = picked[:1] + picked[2:] + picked[1:2] if len(picked) >= 4 else picked

print(f"预算 {BUDGET} token，实际使用 {used}，丢弃 {dropped}")
print("--- 组装后的上下文 ---")
for i, c in enumerate(ordered, start=1):
    print(f"[{i}] 来源：{c['section']}（相关度 {c['score']:.2f}）")
    print(f"    {c['text']}")
print("--- 结束 ---")
print("若以上证据不足以回答，应回复“未找到相关政策”并转人工，而不是推测。")
```

预期输出（已用 `python3 assemble_demo.py` 实际运行）：

```text
预算 120 token，实际使用 100，丢弃 []
--- 组装后的上下文 ---
[1] 来源：第三条 运费承担（相关度 0.91）
    因质量问题退货，运费由商城承担；非质量原因退货，运费由消费者承担。
[2] 来源：第三条 运费承担（相关度 0.72）
    偏远地区退货运费按实际发生额结算。
[3] 来源：第六条 换货（相关度 0.65）
    质量问题换货需在签收后七日内申请，换货商品需保持完好。
[4] 来源：第二条 适用范围（相关度 0.88）
    已激活或已使用的电子产品不适用七天无理由退货。
--- 结束 ---
若以上证据不足以回答，应回复“未找到相关政策”并转人工，而不是推测。
```

四点读法。第一，c4（0.41）与 c5（0.38）被绝对阈值挡掉——它们不是坏文档，只是与“运费谁出”无关。第二，c6 被去重规则合并进 c1，避免同一段话占两个名额。第三，最强的 0.91 在首位、次强的 0.88 被移到末位，中间放补充条款（片段少时影响不大）。第四，引用编号 `[1]–[4]` 与来源标题一起出现，为后续答案溯源提供锚点。

`REL_MARGIN = 0.35` 意味着 0.88 这条差点被卡掉（0.91 × 0.65 = 0.59，仍然通过）。<u>相对阈值最怕“只有一条真正相关”的场景被误伤，因此必须配合离线评测确定，而不是凭直觉写 0.8</u>。

## 动手实验

**前置条件**：Python 3.9+，无需网络与模型服务。

1. 保存脚本为 `assemble_demo.py`，运行并核对输出。
2. 把 `BUDGET` 改为 60，观察哪条被丢弃，确认正文没有被截断。
3. 把 `MIN_SCORE` 改为 0.95，观察结果变为空，验证兜底分支应被触发。
4. 把 `REL_MARGIN` 改为 0.05，观察 0.88 那条被误杀，理解相对阈值的风险。
5. 删除 `assemble_demo.py`。

**预期结果**：预算收紧时整条丢弃而非截断；阈值过高时输出为空，应走“未找到”分支；相对阈值过严会丢掉第二相关但仍有用的证据。

**验证方法**：统计线上“组装后片段数 = 0”的比例，它应与“知识库确实无覆盖”的比例接近；若远高于后者，说明阈值过严。另抽查 20 条回答，检查每个引用编号是否都能在上下文中找到对应片段。

**清理方法**：删除脚本；实验不调用付费接口。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 回答引用了一个不存在的条款 | 上下文被截断，编号与正文错位 | 打印最终 Prompt，逐条核对编号 | 整条丢弃而非截断，编号由组装器统一生成 |
| 政策没覆盖的问题也给出确定答案 | 缺少“无候选”兜底分支 | 构造 20 个域外问题测一遍 | 阈值不通过时直接返回“未找到”并转人工 |
| 引入 rerank 后延迟超标 | rerank 候选过多或串行调用 | 看链路耗时分解，统计候选条数 | 先粗筛到 30 条以内，与检索并行预热 |
| 阈值在不同类目下都不合适 | 用一套固定阈值覆盖所有场景 | 按类目统计分数分布 | 分类目标定阈值，或改用相对阈值 |
| 上下文里 5 条都是同一段话 | 未去重，重叠片段同时入选 | 统计前 5 条正文重合度 | 正文包含关系去重，保留高分那条 |

## 安全与生产注意事项

**<u>使用外部 rerank 服务意味着把用户问题与政策片段全文发到第三方，其中可能含订单号、赔付口径等敏感内容。</u>**上线前必须确认数据处理条款与地域，对片段做字段级脱敏，或改用自托管模型。

**<u>上下文拼接若不做边界标记与转义，片段内的文字可以伪造引用编号、冒充系统指令，或诱导模型忽略筛选规则。</u>**每条片段要有明确的分隔符与来源标记，片段内容只能作为引用材料，不能被解释为指令。

阈值与预算的改动要有记录与回归测试；rerank 不可用时降级为融合排序 + 更严格阈值，而不是放开全部候选。

## 本课总结

- **Bi-encoder 负责召回，cross-encoder 负责精度；rerank 只在候选集很小的时候才划算。**
- 阈值要两条：绝对阈值挡无关，相对阈值挡“明显更差”，且必须按场景标定。
- 预算不足时整条丢弃，绝不截断条款正文；编号与来源由组装器统一生成。
- 片段较多时把最强证据放首尾；片段少时按分数降序即可。
- **没有“未找到”分支的 RAG 一定会在证据缺失时编造。**

## 思考题

晴空商城计划把“退款金额建议”交给智能助手：检索赔付条款后给出建议金额，再交人工确认。请设计筛选与组装策略，说明：金额类问题需要哪些额外证据、rerank 分数不足时如何降级、如何避免把“最高不超过订单金额百分之十”误解为固定比例，以及用什么办法验证金额建议的正确率。

参考思路：金额依赖订单事实，必须用工具取数而不是检索；证据要含条款原文与适用范围；分数不足时只输出“需人工核定”不给数字；条款要成对呈现限定语；用带标准答案的历史工单做回归，按金额误差分档统计。

## 小测

1. 为什么 cross-encoder 不能像 bi-encoder 那样在入库时预先算好？
2. 关于 token 预算，下列哪种做法最危险？  
   A. 超预算的片段整条丢弃　B. 把片段截断到刚好放得下　C. 按分数从高到低装箱　D. 给标题与编号预留额度
3. 绝对阈值与相对阈值分别解决什么问题？
4. 检索返回 0 条通过阈值的候选时，系统应该输出什么？为什么不能“让模型自己判断”？
5. 场景题：上线 rerank 后，客服发现“能不能退”类问题命中率提升，但“多久到账”类问题反而变差。你会先查什么？

## 答案与解析

1. 因为 cross-encoder 的输入是“问题 + 片段”的拼接，打分依赖具体问题的组合，无法预先计算；bi-encoder 对片段单独编码，可以离线算好向量。
2. **B。**截断会让条款缺少前提或结论，模型仍会把它当作完整证据使用，比丢弃更危险。A、C、D 都是常规做法。
3. 绝对阈值解决“哪些候选根本不相关”，保证无覆盖时能说“未找到”；相对阈值解决“候选间的差距”，避免把明显更差的片段也塞进去。
4. 应返回“未找到相关条款，已转人工”，并记录该问题用于补文档。不能交给模型判断，因为模型在空上下文下仍会生成流畅答案，而它没有任何事实依据。
5. 先看该问题的正确片段在 rerank 前的排名，以及它的分数是否被阈值卡掉。“多久到账”的正确答案往往措辞平淡、与问句字面相似度低，容易被高阈值误杀；可用该类目标注集看分数分布，再决定单独设阈值还是改用相对阈值。
