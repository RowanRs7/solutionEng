# 文档加载、解析、清洗与元数据

## 为什么需要学习

晴空商城的售后知识分散在五处：帮助中心的 HTML 政策页、法务给的 PDF 合同模板、运营维护的 Excel 运费与时效表、商品部的 Word 说明书、以及客服系统里的历史工单。团队第一版直接“把 PDF 丢进去”，上线后出现三类问题：运费表在向量化后变成一列乱码数字，客服问“新疆包邮吗”拿到的是“首重 12 元”这种缺失了表头的碎片；旧版政策和新版政策同时被召回，模型把已作废的“30 天无理由”当成现行规则；扫描版 PDF 解析后是空文本，而系统没有任何报错。

这些问题全部发生在“检索之前”。**上一课调索引、这一课调数据；检索质量的一半来自干净、可追溯的输入。**

> **核心结论：** 入库流水线的目标不是“把文件读进来”，而是产出带出处、带权限、带版本、可重复生成的片段。

## 学习目标

完成本课后，你能够：

- 为 HTML、PDF、Word、Excel、工单五类来源各写出一条解析策略和一条失败兜底。
- 设计至少 6 个元数据字段，分别支撑检索过滤、答案溯源和文档生命周期。
- 用内容指纹实现幂等写入，并说明为什么不能只靠文件名判重。
- 定位“解析成功但内容已损坏”的静默故障。

## 业务场景

售后智能助手的知识源每周更新：政策页由运营在后台改，运费表由物流组用 Excel 维护，说明书来自供应商 PDF，工单每天新增数千条。检索侧的要求是：客服提问“耳机拆封能退吗”，必须命中**当前生效**、**该商家所属租户**、**对应商品类目**的条款，并在回答里给出可点击的出处。

晴空商城因此定了三条数据规则：任何片段都必须能追溯到“哪份文档的第几节第几版”；任何片段都必须带租户与生效区间；政策下架后，检索必须立即停止返回它。

## 核心概念

*加载* 是把文件或接口内容读成原始字节与基础属性；*解析* 是把原始内容还原成有结构的文本（标题、段落、表格单元格）；*清洗* 是删除噪声并统一格式；*元数据* 是随片段一起存储的结构化属性。

| 术语 | 含义 | 晴空商城示例 |
| --- | --- | --- |
| *加载器* | 针对某类来源的读取组件 | 帮助中心抓取器、共享盘 PDF 扫描器 |
| *OCR* | 把图片文字识别为文本 | 扫描版发票模板 PDF |
| *规范化* | 统一编码、空白、全半角、标点 | 把全角空格与多个换行压成单个空格 |
| *内容指纹* | 由正文计算出的稳定哈希 | 判断政策是否真的改过 |
| *幂等写入* | 同一输入重复执行不产生重复数据 | 重跑导入任务不产生重复片段 |
| *文档生命周期* | 文档从生效到作废的状态流转 | 草稿 → 生效 → 被替代 → 归档 |
| *ACL* | 片段的可见范围 | 仅售后组可见的内部赔付口径 |

不同格式的风险并不相同，解析策略必须按格式设计：

| 来源 | 典型解析风险 | 建议做法 |
| --- | --- | --- |
| HTML 政策页 | 导航、页脚、脚本混入正文；换行被压成空格 | 按标签白名单抽取，只保留标题与段落 |
| 原生 PDF | 双栏错序、页眉页脚重复、表格被拍平 | 按阅读顺序抽取，表格单独还原为结构化行 |
| 扫描 PDF | 无文本层，解析结果为空 | 先检测文本层，为空则走 OCR 并标记置信度 |
| Word 说明书 | 修订痕迹、批注、自动编号 | 只取正文，丢弃批注与修订历史 |
| Excel 运费表 | 合并单元格、多级表头 | 每个数据行重复带上表头字段再成文 |
| 历史工单 | 个人信息、内部黑话、模板化套话 | 脱敏后入库，模板句剔除 |

## 工作原理

1. **登记来源**：记录来源类型、URL 或文件路径、抓取时间、内容哈希；同一次运行可重放。
2. **判断格式与文本层**：读取文件头而非仅看后缀；PDF 检查是否含文本层，为空则转 OCR 分支。
3. **结构化解析**：按格式抽成“标题 → 段落 → 表格行”的中间结构，**不要先拼成一个大字符串再切**，否则标题与正文的从属关系无法恢复。
4. **清洗与规范化**：删除页眉页脚、合并断行、统一全半角与空白、保留条款编号；对中文要特别处理跨行拼接产生的多余空格。
5. **补元数据**：从正文与来源系统中抽取租户、类目、生效日期、版本、ACL、出处定位（页码或锚点）。
6. **计算内容指纹**：对规范化后的正文取哈希，与库中已有记录比较，未变则跳过，变了则走新版本。
7. **写入与状态流转**：新版本写入并标记生效，旧版本置为“被替代”，检索时默认只查生效版本。
8. **记录质量指标**：空文本率、OCR 置信度分布、表格还原率、去重命中率；这些指标异常时先停下流水线。

第 3 步决定了下游能否做上下文保留（下一课），第 8 步决定了故障能否被发现。

## 架构与选型

| 方案 | 适用 | 不适用 | 权衡 |
| --- | --- | --- | --- |
| 定时批处理全量重建 | 文档量小、更新频率低 | 政策要求分钟级生效 | 实现简单；每次全量开销大、容易丢增量 |
| 事件驱动增量 | 有明确变更事件（发布、审批通过） | 来源系统不支持回调 | 新鲜度高；需处理乱序与重复事件 |
| 批处理 + 增量混合 | 大多数企业知识库 | 团队无力维护两条链路 | 兼顾成本与新鲜度；状态机要设计清楚 |
| 托管文档解析服务 | 格式复杂、团队不想维护解析器 | 数据不能出内网 | 省人力；按页计费、需评估数据边界 |
| 自建解析器 | 格式固定、可完全控制 | 格式多样且频繁变化 | 可控可测；维护成本随格式增加 |

选型依据是“**变更能否被事件感知**”和“**数据能否离开内网**”。晴空商城选混合方案：政策页与 Excel 走事件驱动，供应商 PDF 与工单走每日批处理。

## 最小示例

下面用 Python 3 标准库从一段政策 HTML 中抽取标题与条款，并附上元数据，输出可直接入库的 JSON。代码省略了 PDF 与 Excel 分支，但结构与本课流程一致。

```python
import json, re
from html.parser import HTMLParser

RAW = """<html><body>
<nav>首页 | 帮助中心 | 联系客服</nav>
<h1>晴空商城七天无理由退货政策</h1>
<p>生效日期：2026-03-01　　版本：v3</p>
<h2>第二条 适用范围</h2>
<p>本政策适用于晴空商城自营商品。已激活或已使用的
电子产品不适用七天无理由退货。</p>
<h2>第三条 运费承担</h2>
<p>因质量问题退货，运费由商城承担；非质量原因，运费由消费者承担。</p>
<footer>© 2026 晴空商城 版权所有</footer>
<script>trackPageView()</script>
</body></html>"""

class PolicyParser(HTMLParser):
    """标签白名单解析：只留标题与段落，丢掉导航、页脚、脚本。"""
    SKIP = {"nav", "footer", "script", "style"}
    KEEP = {"h1", "h2", "h3", "p"}

    def __init__(self):
        super().__init__()
        self.skip_depth = 0      # >0 表示正处在被丢弃的标签内部
        self.current = None      # 当前正在收集文本的标签
        self.blocks = []         # [(tag, text)]

    def handle_starttag(self, tag, attrs):
        if tag in self.SKIP:
            self.skip_depth += 1
        elif tag in self.KEEP and self.skip_depth == 0:
            self.current = tag
            self.blocks.append((tag, ""))   # 先占位，后续按顺序追加文本

    def handle_endtag(self, tag):
        if tag in self.SKIP and self.skip_depth:
            self.skip_depth -= 1
        elif tag in self.KEEP:
            self.current = None

    def handle_data(self, data):
        # 只有处在白名单标签内才收集，天然忽略页脚与脚本
        if self.skip_depth or not self.current:
            return
        tag, text = self.blocks[-1]
        self.blocks[-1] = (tag, text + data)

def normalize(text):
    # 统一全角空格并压缩空白，避免同一句话出现两种写法
    text = text.replace("\u3000", " ")
    text = re.sub(r"\s+", " ", text)
    return text.strip()

def build_chunks(blocks, meta):
    """按 h2 条款聚合段落，标题成为 chunk 的前缀，上下文不丢。"""
    chunks, section = [], None
    for tag, raw in blocks:
        text = normalize(raw)
        if not text:
            continue
        if tag == "h2":
            section = text              # 记录当前条款标题
            continue
        if tag == "h1":
            meta["title"] = text        # 文档标题写回元数据，供溯源展示
            continue
        if section:                     # 没有归属条款的正文不入库
            chunks.append({"section": section, "text": text, **meta})
    return chunks

parser = PolicyParser()
parser.feed(RAW)

meta = {"tenant_id": "qingkong", "doc_id": "policy-return-v3",
        "effective_from": "2026-03-01", "doc_type": "policy"}
result = {"meta": meta, "chunks": build_chunks(parser.blocks, meta)}
print(json.dumps(result, ensure_ascii=False, indent=2))
```

预期输出（已用 `python3 ingest_demo.py` 实际运行，节选关键字段）：

```json
{
  "meta": {"tenant_id": "qingkong", "doc_id": "policy-return-v3",
           "effective_from": "2026-03-01", "doc_type": "policy",
           "title": "晴空商城七天无理由退货政策"},
  "chunks": [
    {"section": "第二条 适用范围",
     "text": "本政策适用于晴空商城自营商品。已激活或已使用的 电子产品不适用七天无理由退货。",
     "tenant_id": "qingkong", "doc_id": "policy-return-v3",
     "effective_from": "2026-03-01", "doc_type": "policy",
     "title": "晴空商城七天无理由退货政策"}
  ]
}
```

注意输出里 `已使用的 电子产品` 多了一个空格：HTML 源码在句中断行，被 `\s+` 压成了单个空格。这不是排版问题——<u>中文分词会把“的 电子”切成两个 token，BM25 于是匹配不到“的电子”</u>。修复规则是：**移除中文字符之间的空格，只在西文单词之间保留空格。**这段输出故意保留了原始故障现象，便于你在实验中先复现再修复。

## 动手实验

**前置条件**：Python 3.9+，无需网络与服务。

1. 保存代码为 `ingest_demo.py` 并运行，确认输出与上面一致。
2. 在 `normalize` 中加一条规则：若空格两侧都是中文字符（`\u4e00-\u9fff`），删除该空格；重跑并确认句子变为“已使用的电子产品”。
3. 删掉 `RAW` 中的 `<h2>第三条 运费承担</h2>` 再运行，观察该段文字是否消失，理解“无归属条款不入库”的取舍。
4. 给 `meta` 增加 `status`、`version`、`acl_group` 三个字段，重跑确认它们出现在每个片段中。
5. 删除 `ingest_demo.py`。

**预期结果**：第 2 步后正文通顺且无多余空格；第 3 步第三条的段落被丢弃，说明缺标题会导致内容丢失——这正是需要质量指标告警的原因。

**验证方法**：为每份文档统计“解析后字符数 / 原始字符数”比值，比值低于 0.3 视为可疑并人工抽查；对表格单独统计还原行数。

**清理方法**：删除临时脚本；实验不写数据库。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 检索到的运费表数字与表头错位 | 表格被拍平成一行文本，列关系丢失 | 打印该片段原文看是否还有表头 | 每行重复表头字段，或转为“字段: 值”成文 |
| 扫描件对应的政策从不被召回 | 无文本层，解析结果为空且未告警 | 统计每份文档解析后字符数 | 加文本层检测与 OCR 兜底，空文本直接失败 |
| 新旧政策同时出现 | 未存版本与生效区间，检索未过滤状态 | 查片段元数据是否含 `version`、`status` | 建状态机，检索默认只查生效版本 |
| 同一文档出现重复片段 | 只按文件名判重 | 比较正文指纹与片段数 | 用规范化正文哈希做主键，写入走幂等 |
| 中文关键词搜不到 | 跨行拼接引入空格、全半角不一致 | 抽取 20 条片段人工阅读 | 加中文空格清理与全半角归一 |
| 页脚版权句频繁被召回 | 解析时未按标签白名单过滤 | 搜“版权所有”看命中数 | 白名单解析，丢弃 `nav`/`footer`/`script` |

## 安全与生产注意事项

**<u>工单与聊天记录直接入库会把手机号、地址、身份证片段带进向量库和模型上下文，形成新的数据泄露面。</u>**入库前必须做字段级脱敏，并保留“已脱敏”标记；脱敏规则变更后要能重跑历史数据。

**<u>解析会切断权限继承：源文档在网盘里是受限的，抽成片段后 ACL 若未一并写入，检索就会把受限内容返回给所有人。</u>**权限必须随片段落库，并在检索时作为强制过滤条件。

另外两点：解析器面对不可信文件要设资源上限（文件大小、页数、解压后体积、超时），否则一个超大 PDF 就能拖垮整条流水线；文档正文属于不可信输入，其中出现的“忽略以上指令”之类文字不应被当成系统指令（防注入设计见评测与安全单元）。

## 本课总结

- **检索质量的一半在入库前决定；解析与清洗是产品问题，不是脚本细节。**
- 按格式设计解析策略：HTML 走标签白名单，PDF 先查文本层，表格必须保留行列关系。
- 元数据要同时支撑三件事：过滤（租户、类目）、溯源（文档、版本、定位）、生命周期（状态、生效区间）。
- 用规范化正文的指纹做幂等写入，文件名和时间戳都不可靠。
- 空文本率、表格还原率等质量指标必须告警，否则故障会静默存在。

## 思考题

晴空商城要把“客服工单”也纳入知识库以支持“历史相似问题”推荐，但工单里既有客户隐私，又有客服个人化的口语表达，还有大量模板话术。请设计这条支线的入库方案：脱敏在哪一步做、模板句如何识别、工单的元数据与政策文档有何不同、如何避免把错误处理方式（例如违规赔付）当成“最佳实践”传播。

参考思路：脱敏放在解析之后、指纹计算之前，保证指纹不依赖隐私字段；模板句用聚类或高频 n-gram 识别后剔除；工单元数据需带处理结论、是否升级、是否投诉等标签，且默认降低权重；错误处理方式要用人工标注的质量标签过滤，不能仅凭“被引用次数多”当作正确。

## 小测

1. 为什么解析时应先保留“标题 → 段落”的结构，而不是先拼成一个大字符串再切分？
2. 下列哪一项最适合作为判重依据？  
   A. 文件名　B. 文件大小　C. 规范化正文的内容指纹　D. 抓取时间
3. 扫描版 PDF 入库后“一切正常但从未被检索到”，最可能的原因是什么？
4. 元数据中的 `effective_from` 与 `status` 分别解决什么问题？
5. 场景题：运营把 Excel 运费表拆成“华东/华北/华南”三块，每块有独立表头。解析后客服问“华南首重多少”却答“未找到”。你会如何修改入库逻辑？

## 答案与解析

1. 因为切分需要标题提供的上下文。一旦拼成大字符串，条款与其标题的从属关系不可恢复，后续无法做到“每片段带标题前缀”，检索命中的片段会缺少“这是哪一条”的信息。
2. **C。**正文指纹能反映内容是否真的变化。文件名常被复用或改写；文件大小对微小改动不敏感；抓取时间每次运行都不同，无法判重。
3. 该 PDF 没有文本层，解析得到的正文为空，于是既没有片段也没有报错。应检测文本层是否为空，走 OCR 分支，并把“空文本”作为失败而非成功。
4. `effective_from` 决定“这条规则从什么时候开始适用”，用于时间过滤与新老政策区分；`status` 决定“这条记录当前是否可被检索”，用于下架、替代与归档。
5. 每个区块的表格要各自携带自己的表头成文（例如“区域: 华南；首重: X 元”），并把区域写入元数据；同时保证切分不跨越三个区块的边界，避免华南的表头配华北的数字。
