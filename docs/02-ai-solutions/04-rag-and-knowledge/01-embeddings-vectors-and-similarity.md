# Embedding、向量与语义相似度

## 为什么需要学习

晴空商城的售后客服每天处理大量“能不能退”“运费谁出”的问题。团队最初用数据库 `LIKE` 查政策标题，结果很差：客户说“耳机拆封了还能退吗”，而政策原文写的是“已激活或已使用的商品不适用七天无理由”。两句话没有共同关键词，关键词检索召回为零，客服只能手工翻文档。

这类问题不是“再写一个更好的 SQL”能解决的，它需要一种把“意思”变成可计算对象的方法。Embedding 就是这一步的入口，也是整个 RAG 链路最早、最难返工的一环。

> **核心结论：** Embedding 把文本映射成向量，向量之间的距离代表语义接近程度；选错模型或算错相似度，后面的索引和 Prompt 都无法补救。

## 学习目标

完成本课后，你能够：

- 用自己的话解释 *embedding*、*向量维度*、*语义相似度*，并说明它们与关键词匹配的区别。
- 给定一组归一化向量，手算或写出代码验证余弦相似度与内积的一致性。
- 依据语言覆盖、维度、单次输入上限和成本，为一个中文售后知识库选出候选 embedding 模型并说明理由。
- 识别“相似度高但答案无关”这类误判，并说明应如何验证。

## 前置知识

- 回看上一单元：[模型选择与 Prompt 设计](../03-model-and-prompt/00-overview.md)。
- 知道“向量”就是一串有序数字，能做加法和乘法。
- 了解模型有输入长度上限，超出部分会被截断或报错。
- 不要求会训练模型，也不要求线性代数基础。

## 业务场景

售后智能助手的检索对象有三类：售后政策（条款式文档）、商品资料（说明书、规格）、历史工单（客服与客户的对话记录）。客服输入一个问题，系统要把问题编码成向量，在政策库里找出最相关的几条条款，再交给模型生成答复或退款建议，最后经人工确认后调用退款工具。

本课只处理这条链路的第一环：**把文本变成向量，并用一个可靠的分数判断“像不像”**。晴空商城的约束是：政策库约 1.2 万条条款，主要语言为中文，夹杂英文商品名；问答必须在 300 毫秒内完成检索；不允许把客户手机号写进政策库。

## 核心概念

*Embedding* 是模型输出的定长浮点向量，语义相近的文本在向量空间中距离更近。*向量维度* 是这个向量的分量个数；*语义相似度* 是用某种数学度量算出的接近程度，它不等于“答案正确”。

| 概念 | 含义 | 晴空商城示例 |
| --- | --- | --- |
| *Embedding 模型* | 把文本编码为向量的模型，编码器通常是 Transformer | `text-embedding-3-small` 一类托管模型，或自托管的开源模型 |
| *向量维度* | 每个向量的分量个数，决定存储与计算成本 | 1536 维、3072 维 |
| *归一化* | 把向量缩放到长度为 1，只保留方向 | 入库前统一做 `l2_normalize` |
| *余弦相似度* | 两向量夹角的余弦，取值 -1 到 1 | 客服问题与政策条款的匹配分 |
| *内积* | 对应分量相乘再求和；归一化后等于余弦 | 向量库最快的排序算子 |
| *非对称检索* | 问题短、文档长，两者分布不同 | 12 字提问 vs 200 字条款 |

不同度量不是同一件事的不同写法，它们的取值和排序行为都不同：

| 度量 | 关注点 | 取值与阈值含义 | 适用情形 |
| --- | --- | --- | --- |
| 余弦相似度 | 方向 | 越接近 1 越相似，与长度无关 | 文本检索默认选择 |
| 内积 | 方向 + 长度 | 无固定上界，长向量天然占优 | 向量已归一化，或需要长度信号 |
| 欧氏距离（L2） | 绝对位置 | 越小越相似，受长度影响 | 图像、聚类、需要真实距离时 |

<u>“相似度 0.8 以上就相关”这句话只在特定模型、特定语言、特定切分粒度下成立</u>，换个模型阈值就要重测。**阈值是实验结论，不是通用常数。**

## 工作原理

1. **分词**：模型用自己的 *tokenizer* 把文本切成子词单元，中文常按字或常用词切，英文按子词切；这一步决定了模型能“看见”什么。
2. **截断检查**：超过模型单次输入上限的部分会被截断。托管模型常见上限为 8192 token，超出就静默丢失，必须提前检查。
3. **前向计算**：文本经过编码器多层注意力，得到每个 token 的上下文相关表示。
4. **池化**：把 token 序列压成一个向量，常见做法是对 `[CLS]` 位或所有 token 取平均；具体策略由模型卡定义，调用方不能自行更改。
5. **归一化（可选但推荐）**：把向量缩放到单位长度，使内积等于余弦，便于用最快的算子排序。
6. **入库**：向量连同文档 ID、租户、版本等元数据写入存储（索引细节见下一课）。
7. **查询编码**：用户问题用**同一个模型、同一套预处理**编码成向量。
8. **打分排序**：计算问题向量与候选向量的相似度，取 top-k 交给后续环节。

第 7 步是关键：query 与 document 必须由同一模型的同一版本产生。<u>混用模型版本不会报错，只会安静地把排序结果变成噪声。</u>

## 架构与选型

| 方案 | 适用 | 不适用 | 主要权衡 |
| --- | --- | --- | --- |
| 托管 embedding API | 中文为主、数据量中等、想快速上线 | 数据不能出内网；请求量极大且成本敏感 | 免运维、质量稳定；按量计费、受供应商版本变更影响 |
| 开源自托管（GPU） | 有隐私或合规硬约束；需要离线 | 团队没有推理运维能力 | 可控、可微调；显存与人力成本高 |
| 小维度模型 | 千万级以上向量、内存吃紧 | 语义细粒度要求高 | 省存储、检索快；区分度下降 |
| 大维度模型 | 条款相似、表述接近，需要细分 | 只是做粗分类 | 效果好；存储与计算成本上升 |

选型依据按顺序问四个问题：**目标语言与领域是否被覆盖、单条文档是否超出输入上限、维度带来的存储成本能否承受、是否需要跨语言检索**。截至 2026-10-19，Microsoft Foundry 文档列出的 `text-embedding-3-large` 为 3072 维、`text-embedding-3-small` 为 1536 维，单次请求上限均为 8192 token，一次调用最多提交 2048 条输入，并支持用 `dimensions` 参数降维；文档同时给出 MIRACL 平均分 54.9 / 44.0 与 MTEB 平均分 64.6 / 62.3（large / small），并说明降维后仍可优于 1536 维的上一代模型。这些数字只说明“多语言检索有差异”，不能直接当作中文售后场景的结论，仍需自建评测集（见本单元后续课程）。

<u>不要用“排行榜第一”作为唯一依据</u>：排行榜任务与售后政策条款匹配的分布差异很大。

## 最小示例

下面的代码只用 Python 3 标准库，用来验证三件事：余弦与内积在归一化后是否一致、L2 的排序是否与余弦一致、阈值落在哪里。向量是手工构造的示意值，真实场景由 embedding 模型产生。

```python
import math

def dot(a, b):
    # 内积：既是“未归一化相似度”，也是向量库排序最快的算子
    return sum(x * y for x, y in zip(a, b))

def norm(v):
    # 向量长度，用于归一化和 L2 距离
    return math.sqrt(dot(v, v))

def cosine(a, b):
    # 余弦只比较方向，除以两个长度消除尺度影响
    return dot(a, b) / (norm(a) * norm(b))

def unit(v):
    # 归一化：把向量缩放到长度 1，之后内积等价于余弦
    n = norm(v)
    return [x / n for x in v]

query = [0.9, 0.1, 0.0]          # 客服问题：“拆封的耳机能退吗”
docs = {
    "policy-return": [0.8, 0.2, 0.1],   # 退换货条款：最相关
    "policy-freight": [0.1, 0.9, 0.2],  # 运费说明：不相关
    "policy-invoice": [0.0, 0.2, 0.9],  # 发票说明：不相关
}

print("name            cosine   dot   dot_after_unit   l2")
uq = unit(query)
for name, vec in docs.items():
    # 同一批向量用四种方式打分，观察排序是否一致
    print(
        f"{name:15s} {cosine(query, vec):.4f}  {dot(query, vec):.4f}  "
        f"{dot(uq, unit(vec)):.4f}          {math.dist(query, vec):.4f}"
    )
```

预期输出（已在本地以 `python3 emb_demo.py` 实际运行）：

```text
name            cosine   dot   dot_after_unit   l2
policy-return   0.9838  0.7400  0.9838          0.1732
policy-freight  0.2143  0.1800  0.2143          1.1489
policy-invoice  0.0240  0.0200  0.0240          1.2767
```

三列结论：余弦与“归一化后内积”逐位相同；未归一化的内积数值完全不同但排序一致（因为本例向量长度接近）；L2 排序方向相反，数值越小越相似。**所以“用哪个度量”必须和向量库的索引算子、以及是否归一化一起确定，不能混着比阈值。**

## 动手实验

**前置条件**：Python 3.9+，无需网络与任何第三方包。

1. 把上面的代码保存为 `emb_demo.py`。
2. 给 `docs` 增加一条“看起来很像但答案无关”的向量，例如 `"policy-warranty": [0.7, 0.3, 0.3]`。
3. 运行 `python3 emb_demo.py`，记录每条候选的余弦值。
4. 把 `query` 改成 `[9.0, 1.0, 0.0]`（同一方向、放大 10 倍）后重跑。
5. 删除临时文件：`rm emb_demo.py`。

**预期结果**：第 3 步中 warranty 条款拿到较高的余弦值（约 0.9 量级），说明“词语相近”与“条款适用”是两件事；第 4 步中所有余弦值不变，而未归一化内积整体放大约 10 倍。

**验证方法**：对比第 3、4 步两次输出的 cosine 列是否完全一致；若不一致，说明代码被改坏或误用了别的度量。归一化前后检查 `dot_after_unit` 是否等于 `cosine`。

**清理方法**：删除 `emb_demo.py`；实验不写入任何数据库、不产生外部费用。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 线上检索结果明显差于离线测试 | query 与文档使用了不同模型或不同版本 | 打印两侧的模型名与版本，抽样 20 条比对 | 固定模型与版本，写入配置并在入库时记录 |
| 相似度分数都在 0.7 以上，无法区分 | 向量未归一化却用内积；或模型对短文本区分度低 | 统计 top-100 分数分布，看是否有区分度 | 统一归一化并改用余弦；换更适合短问句的模型 |
| 中文问题召回英文商品资料失败 | 模型跨语言能力不足 | 用 30 条中英混排问题测召回率 | 换多语言模型，或为商品资料补中文摘要再入库 |
| 长条款后半段总是检索不到 | 单条文本超过模型输入上限被截断 | 检查文档 token 数是否超过 8192 | 先切分再编码（见第 3、4 课） |
| 阈值调了多次仍不稳定 | 阈值是从别的模型或语料搬来的 | 用自建标注集画不同阈值的准确率/召回率曲线 | 每个模型、每种语料单独标定阈值 |

## 安全与生产注意事项

**<u>向量不是匿名化手段：embedding 可能被用于反推原文片段或敏感属性，政策库中不要放入手机号、身份证号、完整地址等个人数据。</u>**若业务必须覆盖订单相关内容，应只存脱敏后的字段，并把原始明细留在受控的业务库中按需查询。

**<u>多租户共用同一向量集合会造成越权召回：检索时若只按相似度排序而不加租户过滤，A 商家的政策可能出现在 B 商家的回答里。</u>**租户标识必须作为强制过滤条件写进检索语句，而不是交给模型“注意一下”。

另外两点工程约束：模型版本变更会导致旧向量失效，升级时必须全量重建并保留双写窗口；调用托管 API 时按量计费，批量重嵌入前先估算费用与耗时上限。

## 本课总结

- **Embedding 把语义变成向量，检索质量的上限在编码这一步就被决定。**
- 余弦看方向、内积看方向与长度、L2 看绝对位置；归一化后内积等于余弦，阈值必须与度量方式绑定。
- query 与文档必须用同一模型、同一版本、同一预处理方式编码。
- 选型先看语言与领域覆盖，再看输入上限与维度成本，最后才看排行榜。
- **相似度高不等于答案正确，阈值必须在自己的标注集上标定。**

## 思考题

晴空商城希望“一次编码，同时支持中文提问检索中文政策、英文提问检索英文说明书”。你会选择单一多语言模型，还是两个单语模型加一层翻译？请从召回质量、运维复杂度、成本、失败时的可解释性四方面给出取舍，并说明你会用什么实验来验证选择。

参考思路：单一多语言模型链路短、失败模式少，但跨语言对齐质量需要用真实中英问题对测；两个单语模型加翻译会引入翻译误差和第二跳延迟，且“翻译错”难以归因。可行验证是构造 100 条中英对照问题，比较两种方案的 recall@5 与首条命中率，并统计翻译失败样例。

## 小测

1. 两个文本的 embedding 余弦相似度为 0.95，能否直接判定后者是前者的正确答案？为什么？
2. 归一化之后，内积与余弦相似度的关系是：  
   A. 完全无关　B. 数值相等　C. 内积是余弦的平方　D. 余弦是内积的两倍
3. 为什么 query 和文档必须用同一个 embedding 模型编码？
4. 单条政策条款有 12000 个 token，而你选的模型单次上限是 8192 token，直接编码会发生什么？
5. 场景题：运营反馈“搜索‘电池鼓包’找不到安全须知，但搜‘电池膨胀’能找到”。最可能的原因是什么，你会先做什么验证？

## 答案与解析

1. **不能。**余弦只衡量语义接近，不衡量“是否回答了问题”。同主题不同结论的条款（例如“可退”与“不可退”）向量可能非常接近，这是 RAG 需要 rerank 与引用校验的原因。
2. **B。**归一化后两向量长度为 1，内积公式退化为余弦。A 错在忽略归一化前提；C、D 是把不同度量混为一谈。
3. 不同模型的向量空间彼此独立，坐标系不同。混用后距离失去意义，而且**不会报错**，只会让排序变成随机效果，因此必须在配置层固定并在入库元数据中记录模型版本。
4. 超出部分会被截断，条款后半段内容丢失且无任何错误提示。应改为先按条款切分再分别编码，而不是增大模型。
5. 最可能是该模型对“电池鼓包 / 电池膨胀”这组近义表达覆盖不足，或安全须知文档被切分到不含“电池”字样的片段。先取的验证是：把两条提问分别编码，看与安全须知向量的分数差；再检查安全须知切分后的片段是否保留标题上下文。
