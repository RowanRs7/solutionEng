# 权限感知检索与多租户隔离

## 为什么需要学习

晴空商城的售后智能助手上线第一周，客服小林搜“这个订单能不能退”，助手回答时带出了一句“内部备注：该客户投诉过三次，可超额补偿”。这条备注属于客服主管的私有记录，小林没有权限。问题不在模型，而在检索：向量库把所有切片放在同一个索引里，代码先取回 top-10，再用应用层代码过滤掉无权文档。被过滤掉的文档虽然没进上下文，但检索时它们已经参与了排序，把真正相关的政策文档挤出了榜单。

> **核心结论：** 权限必须在检索之前裁剪候选集，任何“先召回、后过滤”的做法既会越权，也会降低召回质量。

## 学习目标

完成本课后，你能够：

- 说明 *安全裁剪* 与 *后置裁剪* 在泄露面和召回质量上的差异。
- 为多租户知识库选择隔离策略（独立索引、分区字段、ACL 过滤）。
- 写出包含主体、租户、组集合与过滤表达式的检索请求契约。
- 用标准库复现“后置裁剪导致召回被挤占”的现象并验证修复。

## 业务场景

晴空商城有三类知识：面向所有客服的售后政策、按客服等级（一线/主管）分级的内部备注、按租户隔离的商家规则。助手的用户既有晴空自营客服，也有接入平台的第三方商家客服。一个商家客服绝不能看到另一商家的规则，一线客服也不能看到主管备注。

这些约束带来三个具体问题：

- 检索请求怎么携带“我是谁、我属于哪个租户、我在哪些组”？
- 过滤发生在哪一层，才能既安全又不牺牲召回？
- 源系统的权限变了，索引里的 ACL 什么时候跟上？

## 核心概念

*权限感知检索*（permission-aware retrieval）指检索过程本身就知道调用者能读什么，而不是检索完再删。*安全裁剪*（security trimming）是在候选集上按主体权限剪除文档；*后置裁剪*（post-filtering）则是先取 top-k 再删，二者相差一个“何时生效”。

*租户隔离*是权限的一个特例：不同客户的数据不仅在文档级不可见，最好在存储与索引级也不共享资源。*ACL 元数据*是随文档一起入库的权限声明，通常是“允许的主体或组列表”。*权限源*指真正决定权限的系统（如 IAM、订单系统、工单系统），索引中的 ACL 只是它的副本，因此存在 *权限同步延迟*。

*越权检索*（over-retrieval）指系统取回了调用者无权访问的文档，哪怕最终没有展示。它仍然是事故：日志、缓存、链路追踪、模型供应商都可能留下副本。

| 隔离策略 | 隔离强度 | 成本 | 查询复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 每租户独立索引/库 | 最强 | 高（N 份资源） | 低 | 强监管、大客户专属部署 |
| 共享索引 + 租户分区字段 | 中强 | 低 | 中 | 多数 SaaS |
| 共享索引 + 文档级 ACL 过滤 | 强（可精细共享） | 中 | 高（组展开） | 企业知识库 |
| 应用层后置裁剪 | 弱 | 低 | 低 | 仅作兜底，不可单独使用 |

## 工作原理

一次安全的检索请求按以下顺序执行：

1. **服务端取身份**：从会话令牌解析主体、租户与组，绝不接受前端传入的 `tenant_id` 或 `user_id`。
2. **展开有效主体集**：递归展开嵌套组，得到“用户 + 所属组”的完整集合；组数量可能有上限，超出时要显式报错而不是静默截断。
3. **构造过滤表达式**：`tenant == T AND acl ANY(groups)`，并把它下推到检索引擎的原生过滤器。常见实现是把 ACL 存成可过滤的多值字段，用 `group_ids/any(g: search.in(g, 'cs_l1,cs_all'))` 这类表达式匹配；组很多时，`search.in` 明显快于一长串 `eq or eq`。
4. **在过滤后的候选集上取 top-k**：注意不同引擎的实现差异——有的先 ANN 再过滤，过滤后可能剩不满 k 条，需要调大候选倍数（over-fetch）或换用支持过滤的索引。
5. **应用层双检**：对返回文档再校验一次租户与 ACL，防御索引里的陈旧或缺失字段。
6. **组装上下文**：只把通过双检的切片交给模型，并保留来源 ID 供引用使用。
7. **渲染与缓存**：引用卡片、检索缓存、日志都按同一主体维度隔离。
8. **审计**：记录主体、过滤表达式、返回的文档 ID 与拒绝原因。

第 4 步是实践中最容易翻车的地方：<u>如果索引不支持前置过滤，过滤后候选集可能只剩两三条，团队会误以为“加了权限效果变差”，于是把过滤挪回应用层——这一步就把安全设计改回了事故设计。</u>

## 架构与选型

主流检索引擎通常提供三种做法，可以组合使用：

| 做法 | 机制 | 优点 | 风险 | 何时选择 |
| --- | --- | --- | --- | --- |
| 字符串安全过滤器 | 把主体或组 ID 写进索引字段，查询时用过滤表达式匹配 | 与 API 版本无关、通用、易实现 | 组很多时表达式膨胀；组变更需重刷 | 自定义身份体系、推送式索引 |
| 原生 ACL/RBAC 元数据 | 入库时保存权限元数据，查询时由引擎比对令牌声明 | 少写权限代码、性能好 | 多为预览能力，绑定云厂商 | 已使用该云的身份体系 |
| 物理隔离 | 每租户独立索引或实例 | 泄露面最小 | 资源成本、运维复杂度 | 强监管、租户数量可控 |

以 Azure AI Search 为例：官方文档把“安全筛选器”描述为字符串比较、不绑定 API 版本的做法；而基于 Entra 令牌的原生 ACL/RBAC、Purview 敏感度标签、SharePoint ACL 同步，在 2026-09-17 更新的文档中仍标注为预览功能，查询时需要携带 `x-ms-query-source-authorization` 头，且权限变更只有在同步进索引后才生效（截至 2026-10-19）。这意味着：**不要把预览能力当成唯一的权限边界，生产系统应保留应用层双检。**

该文档还有两处提示值得记住：安全筛选器只做字符串匹配，<u>不做身份认证与授权，主体是谁必须由应用自己解析后传入</u>；把 ACL 字段设为不可检索（`retrievable: false`）只能避免它随结果返回，并不是字段级加密或内容模糊化。

## 最小示例

下面的脚本用标准库复现“后置裁剪把召回挤占掉”的现象。评分用关键词命中数模拟相似度，结论与真实向量检索一致。

```python
DOCS = [
    {"id": "d1", "tenant": "qk", "acl": {"cs_all"}, "text": "7 天无理由退货"},
    {"id": "d2", "tenant": "qk", "acl": {"cs_l2"},  "text": "内部备注：退款 退货 需主管特批"},
    {"id": "d3", "tenant": "qk", "acl": {"cs_l1"},  "text": "退款审核流程：主管复核"},
    {"id": "d4", "tenant": "qk", "acl": {"cs_l1"},  "text": "超时未发货处理"},
    {"id": "d5", "tenant": "ah", "acl": {"cs_l1"},  "text": "另一租户：退款 退货 政策"},
]
KEYWORDS = ["退货", "退款"]
USER = {"sub": "u-1001", "tenant": "qk", "groups": {"cs_l1", "cs_all"}}

def score(doc):                     # 用关键词命中数近似相似度得分
    return sum(1 for kw in KEYWORDS if kw in doc["text"])

def can_read(doc):                  # 租户必须一致，且 ACL 与用户组有交集
    return doc["tenant"] == USER["tenant"] and bool(doc["acl"] & USER["groups"])

ranked = sorted(DOCS, key=score, reverse=True)

post = [d["id"] for d in ranked[:3] if can_read(d)]          # A：先取 top-3 再裁剪
pre = [d["id"] for d in [x for x in ranked if can_read(x)][:3]]  # B：先过滤再取 top-3
leak = [d["id"] for d in ranked[:3]]                          # C：忘记过滤

print("排序结果（含无权文档）：", [(d["id"], score(d)) for d in ranked])
print("A 后置裁剪 top-3 ->", post, f"（可用 {len(post)} 条，召回被挤占）")
print("B 前置过滤 top-3 ->", pre, f"（可用 {len(pre)} 条）")
print("C 未过滤      ->", leak, "（d2 内部备注、d5 跨租户文档进入上下文）")
```

预期输出（本机 `python3` 实跑一致）：

```text
排序结果（含无权文档）： [('d2', 2), ('d5', 2), ('d1', 1), ('d3', 1), ('d4', 0)]
A 后置裁剪 top-3 -> ['d1'] （可用 1 条，召回被挤占）
B 前置过滤 top-3 -> ['d1', 'd3', 'd4'] （可用 3 条）
C 未过滤      -> ['d2', 'd5', 'd1'] （d2 内部备注、d5 跨租户文档进入上下文）
```

三行输出对应三种命运：A 是“看起来安全但质量塌了”，B 是安全与质量兼得，C 是直接越权。注意 d2 和 d5 的分数并列最高，这正是真实场景的样子——内部备注往往比公开政策更“像答案”，所以越权文档天然抢占 top-k。

## 动手实验

前置条件：Python 3.9+，无需第三方包。把上一节代码保存为 `acl_demo.py`。

步骤：

1. 运行一次，确认输出与上文一致。
2. 把 `USER["groups"]` 中的 `cs_all` 去掉，观察 `d1` 是否还能被读到，并解释原因。
3. 给 `d2` 加上 `"stale": True` 字段，模拟 ACL 同步延迟；在 `can_read` 里增加 `and not doc.get("stale")`，观察结果变化。
4. 把 `ranked[:3]` 改成 `ranked[:10]`，观察后置裁剪的可用条数如何随 k 变化。

预期结果：第 2 步后 `d1` 消失，因为其 ACL 只含 `cs_all`，与用户组无交集；第 3 步后即使 d2 的租户与组都匹配也会被双检拒绝；第 4 步后置裁剪能凑够条数，但代价是检索引擎要先返回大量无权文档，泄露面反而更大。

验证方法：对每个输出行手工计算“候选集 ∩ 可读集合”，与脚本结果对照；再断言 B 的任何输出都满足 `can_read` 为真。

清理方法：删除 `acl_demo.py`。本实验不访问真实索引，不涉及真实个人信息。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 过滤后结果很少或为空 | 引擎先 ANN 后过滤，候选倍数不足；或 ACL 字段缺失 | 对比过滤前后的候选数量 | 提高 over-fetch、改为可过滤索引、补齐 ACL 字段 |
| 不同租户互相看到文档 | 租户取自前端参数或被默认值填充 | 篡改请求参数看是否影响结果 | 租户只从服务端会话解析 |
| 用户突然看不到应有文档 | 嵌套组未展开、组数量被截断 | 对比源系统与索引中的有效组集合 | 展开嵌套组、超限报错、缓存组关系 |
| 权限回收后仍能检索到 | ACL 同步延迟 | 对比源权限变更时间与索引更新时间 | 缩短同步周期、查询时双检、暴露同步水位 |
| 缓存命中他人结果 | 缓存键不含租户或主体 | 检查缓存 key 构成 | key 至少含租户、主体、权限版本 |

## 安全与生产注意事项

**<u>把“用户只能看自己的订单”写进 Prompt 让模型自觉遵守，不构成访问控制。</u>** 提示词可被注入绕过，模型也无从知道索引里还有哪些文档；访问决策必须发生在检索之前，且由服务端执行。

**<u>检索缓存、日志、评测样本如果跨用户共享，等于把越权数据复制到了第二个地方。</u>** 缓存键必须包含租户与主体（或权限版本），日志同样要按租户分区并设置保留期限。

还有两条边界：**<u>向量库管理员凭据不得被检索服务直接使用</u>**，否则任何代码缺陷都会绕过全部过滤；ACL 字段要随文档生命周期一起删除，文档下架而 ACL 残留会让旧权限继续生效。

## 本课总结

- 权限生效的时点决定一切：先裁剪再取 top-k 才是安全检索。
- 后置裁剪既会泄露（日志、缓存、链路追踪）又会降低召回，因为高分的越权文档抢占了名额。
- 多租户隔离是资源、成本与合规的三角权衡，独立索引不是唯一答案。
- 索引里的 ACL 只是权限源的副本，同步延迟必须被监控和双检兜底。
- 过滤表达式应由服务端构造，任何来自客户端的身份字段都应被忽略。

## 思考题

平台方希望“商家可以把自己的规则共享给合作商家”，共享关系每天都在变。请设计一种既能支持动态共享、又不把过滤表达式撑爆的方案，并说明权限变更后多快必须生效。

参考思路：把“共享”建模为组（如 `merchant:qk:shared-with:ah`），文档 ACL 只存组 ID，组关系由身份服务维护，过滤表达式长度与共享对象数量解耦；同时用组关系版本号做缓存失效。生效时间取决于业务承诺，可给出分级 SLO：权限回收立即生效（查询时双检），授权生效允许分钟级延迟并提示用户。

## 小测

1. 安全裁剪与后置裁剪的核心差别是什么？
2. 下列哪种做法最可能造成越权？  
   A. 服务端从令牌解析租户　B. 查询时把 ACL 下推到引擎过滤器　C. 先取 top-10 再在应用层删掉无权文档　D. 对返回结果做二次校验
3. 为什么“过滤后结果变少”常常不是过滤本身的错？
4. 索引中的 ACL 与权限源不一致时，系统应该如何表现？
5. 场景题：商家客服报告“搜索自己的规则时，偶尔会看到另一个商家的规则标题”。请列出至少三个排查方向。

## 答案与解析

1. 安全裁剪在候选集上先剪除无权文档，再计算 top-k；后置裁剪先召回再删除。前者不泄露也保召回，后者两者都受损。
2. **C。** 它把无权文档先取回了，会进入日志、缓存和链路追踪，且挤占 top-k。A、B、D 都是本课推荐的正确做法。
3. 因为引擎常常先做近邻搜索再过滤，被剪掉的文档已经占用了候选名额；正确做法是增大候选倍数或使用支持前置过滤的索引。
4. 应偏保守：以权限源为准，宁可少返回（并提示“权限同步中”），也不要凭索引里的旧 ACL 放行；同时监控同步水位并告警。
5. 排查方向包括：租户过滤是否取自前端参数；索引中是否存在 ACL 字段为空的历史文档；结果卡片渲染是否绕过了双检；检索缓存 key 是否缺租户维度；是否存在跨租户的共享索引别名指向错误。
