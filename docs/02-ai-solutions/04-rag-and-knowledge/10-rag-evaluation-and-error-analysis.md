# RAG 评测与错误分析

## 为什么需要学习

售后智能助手的第一次演示很成功：产品经理挑的 8 个问题，7 个答得不错。上线两周后客服反馈“一半回答不相关”，但团队无法反驳，因为他们手上只有那 8 道题。后来有人改了一版 Prompt，客服满意度看起来涨了，可退款类问题开始答错——没人知道是新 Prompt 的功劳，还是那一周政策刚更新。

> **核心结论：** RAG 的效果必须拆成“检索对不对”和“生成忠不忠”两层来量，否则你永远不知道该改哪一层。

## 学习目标

完成本课后，你能够：

- 区分检索层指标（Recall@k、MRR、上下文精确率/召回率）与生成层指标（忠实度、答案相关性）。
- 用黄金集为一条 RAG 链路计算分层指标，并按规则完成错误归因。
- 设计一个包含回归门禁和留出集的评测流程。
- 判断指标变化是真实改进还是噪声或过拟合。

## 前置知识

- 回看上一课：[增量索引、删除与数据同步](09-incremental-indexing-and-sync.md)。
- 了解 RAG 链路：查询改写 → 检索 → 重排 → 上下文组装 → 生成。
- 知道准确率、召回率的基本含义。
- 能读懂 JSON，能写简单的 Python 统计脚本。

## 业务场景

晴空商城要为售后智能助手建立评测基线。业务方关心三件事：客服能不能直接使用答案、答案有没有依据、政策类问题的覆盖率。工程方关心：改检索参数、换重排模型、调 Prompt 之后，效果有没有退化。

评测数据来自真实工单，每条样本包含：用户问题、标准答案（或标准文档）、实际检索结果、实际回答、引用情况、以及这条问题在真实流量中的占比。合规要求：进入评测集的工单必须脱敏，且不得整体外发给第三方模型。

## 核心概念

*黄金集*（golden set）是人工确认过正确答案与正确来源的样本集合；*留出集*（holdout）是从不参与调参、只在发布前使用的那一部分。*分层评测*指对检索、重排、生成分别打分，而不是只给最终答案一个好坏。

检索层常用指标：*Recall@k* 衡量标准文档有多少出现在前 k 条；*MRR*（平均倒数排名）衡量第一个正确结果排得多靠前；*上下文精确率*看返回的片段里有多少是真正相关的，*上下文召回率*看标准答案需要的信息有多少被检索到。生成层常用 *忠实度*（回答中的断言是否被上下文支持）与 *答案相关性*（回答是否切题）。

*错误归因*是把一条失败样本定位到具体环节的方法。*LLM 作为裁判*（LLM-as-judge）用模型给回答打分，成本低但需要人工对齐。*回归门禁*指指标低于基线时阻止发布。

| 指标 | 层级 | 回答什么问题 | 计算方式 | 失败时先查 |
| --- | --- | --- | --- | --- |
| Recall@k | 检索 | 该找到的文档找到了吗 | 命中数 ÷ 标准文档数 | 切分、查询改写、过滤条件 |
| MRR | 检索/重排 | 正确结果排得够前吗 | 首个命中排名的倒数均值 | 重排模型、混合检索权重 |
| 上下文精确率 | 重排 | 上下文里噪声多不多 | 相关片段 ÷ 返回片段 | 重排阈值、top-k 过大 |
| 上下文召回率 | 检索 | 依据材料齐不齐 | 被覆盖要点 ÷ 标准要点 | 切分粒度、多路召回 |
| 忠实度 | 生成 | 有没有超出上下文编造 | 被支持的断言 ÷ 总断言 | Prompt、引用校验 |
| 答案相关性 | 生成 | 是否答非所问 | 裁判或人工评分 | 查询理解、上下文顺序 |

## 工作原理

一个可持续的评测闭环包含以下步骤：

1. **采样建集**：按真实流量分布分层抽样（类目 × 问题类型 × 难度），再补充少量合成难例，比例要写进文档。
2. **标注三件套**：问题、标准答案要点、标准来源文档 ID。三者缺一，就无法区分检索错和生成错。
3. **埋点留痕**：每次请求记录改写后的查询、检索 ID 与得分、重排后顺序、送入模型的上下文、最终答案与引用。
4. **分层打分**：先算检索层指标，再算生成层指标；不要只对最终答案打一个分。
5. **规则归因**：按“检索未命中 → 排序靠后 → 生成不忠实 → 缺少引用 → 拒答错误”的顺序判定，顺序保证归因稳定。
6. **按业务权重汇总**：用曝光占比加权，避免高频简单问题掩盖低频高风险问题。
7. **定位改进项**：用错误分布决定下一步改检索还是改生成，而不是凭直觉。
8. **回归门禁**：新版本在留出集上不得低于基线阈值，且关键子集（退款、生鲜、跨境）单独设阈值。

第 5 步值得展开：<u>归因顺序错了，结论就会错——先判“检索未命中”能避免把检索问题误记成生成问题；很多团队一看到答案错就去改 Prompt，实际上 60% 的错在检索。</u>

## 架构与选型

| 方法 | 成本 | 覆盖能力 | 稳定性 | 适用 |
| --- | --- | --- | --- | --- |
| 规则/字符串指标 | 低 | 只能测重合度 | 高 | 有标准答案的抽取类问题 |
| 模型裁判（带评分细则） | 中 | 能测忠实度、相关性 | 中，需对齐 | 主观性较强的开放回答 |
| 人工评审 | 高 | 最可靠 | 高 | 基线校准、争议样本、上线前抽检 |
| 线上隐式信号 | 低 | 反映真实满意度 | 有偏 | 持续监控，不替代离线评测 |

选型依据：**人工校准基线，模型裁判做规模，规则指标做门禁。** 只靠模型裁判会在换模型时整体漂移；只靠规则会漏掉“语义正确但表述不同”的情况。

## 最小示例

下面的脚本用 6 条样本演示分层打分与规则归因。数据是手工构造的，结构与真实埋点一致。

```python
# 每条样本：标准文档 gold、实际返回 retrieved、生成是否被上下文支持 supported、是否带引用 cited
CASES = [
    {"q": "生鲜能退吗",   "gold": ["d-fresh"],  "retrieved": ["d-fresh", "d-x"], "supported": True,  "cited": True,  "w": 3},
    {"q": "退款多久到账", "gold": ["d-refund"], "retrieved": ["d-x", "d-refund"], "supported": True,  "cited": True,  "w": 3},
    {"q": "价保怎么申请", "gold": ["d-price"],  "retrieved": ["d-x", "d-y"],     "supported": True,  "cited": False, "w": 2},
    {"q": "大客户补偿",   "gold": ["d-vip"],    "retrieved": [],                  "supported": True,  "cited": False, "w": 1},
    {"q": "跨境税费怎么退", "gold": ["d-tax-1", "d-tax-2"], "retrieved": ["d-tax-1"], "supported": False, "cited": True, "w": 2},
    {"q": "发票丢了能退吗", "gold": ["d-inv"],  "retrieved": ["d-inv"],           "supported": False, "cited": True, "w": 2},
]

def recall_at_k(case, k=3):
    if not case["gold"]:                       # 没有标准文档的样本不计入召回
        return 1.0
    hit = sum(1 for g in case["gold"] if g in case["retrieved"][:k])
    return hit / len(case["gold"])

def mrr(case):
    # 第一个命中的标准文档排在第几位，取其倒数
    for rank, doc in enumerate(case["retrieved"], start=1):
        if doc in case["gold"]:
            return 1.0 / rank
    return 0.0

def bucket(case):
    # 归因顺序固定：先检索，再排序，最后生成
    if recall_at_k(case) == 0:
        return "retrieval_miss"
    if mrr(case) < 0.5:
        return "ranking_low"
    if not case["supported"]:
        return "generation_unsupported"
    if not case["cited"]:
        return "missing_citation"
    return "ok"

rows = [(c["q"], recall_at_k(c), mrr(c), bucket(c), c["w"]) for c in CASES]
print(f"{'问题':<10}{'R@3':>6}{'MRR':>7}  {'归因':<24}权重")
for q, r, m, b, w in rows:
    print(f"{q:<10}{r:>6.2f}{m:>7.2f}  {b:<24}{w:>4}")

print(f"\n平均 R@3={sum(r for _, r, _, _, _ in rows) / len(rows):.2f} 平均 MRR={sum(m for _, _, m, _, _ in rows) / len(rows):.2f}")
print(f"加权通过率={sum(w for _, _, _, b, w in rows if b == 'ok') / sum(w for *_, w in rows):.0%}")
print("错误分布：", {b: sum(b == x for *_, x, _ in rows) for b in sorted({r[3] for r in rows})})
```

预期输出（本机 `python3` 实跑一致）：

```text
问题           R@3    MRR  归因                      权重
生鲜能退吗       1.00   1.00  ok                         3
退款多久到账      1.00   0.50  ok                         3
价保怎么申请      0.00   0.00  retrieval_miss             2
大客户补偿       0.00   0.00  retrieval_miss             1
跨境税费怎么退     0.50   1.00  generation_unsupported     2
发票丢了能退吗     1.00   1.00  generation_unsupported     2

平均 R@3=0.58 平均 MRR=0.58
加权通过率=46%
错误分布： {'generation_unsupported': 2, 'ok': 2, 'retrieval_miss': 2}
```

两个细节：`退款多久到账` 的 MRR 只有 0.50，说明正确答案排在第二，属于“能答但容易被噪声带偏”，应列入重排优化；`跨境税费怎么退` 的 Recall@3 是 0.50，只找到两个标准文档中的一个，属于检索覆盖不足，改 Prompt 没有用。

## 动手实验

前置条件：Python 3.9+，无需第三方包。把代码保存为 `rag_eval.py`。

步骤：

1. 运行一次，确认输出与上文一致。
2. 把 `recall_at_k` 的 `k` 改为 5，观察 R@3 与归因是否变化。
3. 在第一条样本的 `retrieved` 前面插入两条无关文档，观察 MRR 如何下降。
4. 把 `bucket` 中的生成层判断提到检索判断之前，观察“价保怎么申请”的归因如何变化，并说明这种顺序为什么会掩盖真正的检索问题。

预期结果：第 2 步若无新增命中，各样本召回不变；第 3 步 MRR 从 1.00 降到 0.33；第 4 步该样本归因从 `retrieval_miss` 变为 `missing_citation`，看起来像“补个引用就好”，实际是检索完全没命中。

验证方法：手工核算一条样本的 R@3 与 MRR，与脚本对照；再统计“错误分布”的和是否等于样本数。

清理方法：删除 `rag_eval.py`。真实评测数据应存放在受控存储中，不可提交到代码仓库。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 指标很高但客服不满意 | 测试集只覆盖简单问题或已过时分布 | 对比测试集与真实工单的问题分布 | 按流量分层重采样，补高风险子集 |
| 每改一次都“有提升” | 反复在同一测试集上调参 | 检查是否有未使用过的留出集 | 冻结留出集，只在发布前使用 |
| 检索与生成问题分不清 | 没有记录检索结果，只有最终答案 | 查看请求日志是否含 retrieved IDs | 补齐链路埋点，按归因顺序判定 |
| 模型裁判与人工结论不一致 | 裁判与被测模型相同、缺评分细则 | 抽 50 条做人工对齐 | 给明确定义与反例，换裁判模型，多裁判投票 |
| 指标抖动大 | 样本量太小或单次采样 | 计算置信区间或分桶看方差 | 扩样本、多次采样、报告区间而非单点 |

## 安全与生产注意事项

**<u>评测集里的真实订单号、地址、手机号若直接送入外部裁判模型，等同于二次泄露。</u>** 入库前必须脱敏，并对裁判服务做数据处理协议评估；能不外发就不外发，优先本地模型或规则指标。

**<u>用同一份评测集反复调参会让它失去度量能力，团队据此做的上线决策会把风险带进生产。</u>** 留出集要真正留出，访问要有记录，避免“悄悄看一眼”变成事实上的调参。

另外两点：**<u>评测样本本身也是数据资产，要按租户与敏感级别隔离</u>**，否则评测平台会成为新的越权入口；对外披露“准确率”时要说明数据集来源与口径，避免用 8 道演示题代表线上效果。

## 本课总结

- 没有分层指标，就无法判断该改检索还是改生成。
- 黄金集的三件套（问题、答案要点、标准来源）决定了归因能力。
- 归因要有固定顺序，否则同一现象会得出互相矛盾的结论。
- 加权汇总能防止高频简单问题掩盖低频高风险错误。
- 留出集与回归门禁是评测体系可信的前提。

## 思考题

业务方要求“下季度把准确率从 60% 提到 85%”。在不增加标注人力、且政策每月更新的前提下，你会如何拆解这个目标，并说明哪些提升来自检索、哪些来自生成？

参考思路：先把 25 个百分点按错误分布拆到各环节——若当前 60% 的错误来自检索未命中，则优先改切分与混合检索；若主要来自不忠实生成，则改 Prompt 与引用校验。再设定分阶段指标（Recall@5、忠实度、拒答正确率），用增量索引保证政策更新后评测集同步刷新，避免用旧基线衡量新数据。

## 小测

1. 为什么不能只用最终答案的正确率评估 RAG？
2. 下列哪个指标最能反映“上下文里噪声太多”？  
   A. Recall@k　B. 上下文精确率　C. 忠实度　D. 答案相关性
3. 归因顺序为什么把“检索未命中”放在最前？
4. 留出集与训练/调参集的区别是什么？
5. 场景题：上线后发现“跨境税费”类问题答错率明显高于其他类目，但整体指标正常。请给出至少三个排查与改进方向。

## 答案与解析

1. 因为最终答案错可能源于检索缺失，也可能源于生成不忠实，二者修复手段完全不同；只看最终分数会让团队反复改错地方。
2. **B。** 上下文精确率衡量返回片段中相关片段的比例，直接反映噪声。A 关注是否找到，C 关注是否编造，D 关注是否切题。
3. 检索没命中时，模型没有任何依据，此时讨论忠实度或措辞没有意义；先判检索能把问题定位到最上游、可修复的环节。
4. 留出集不参与任何调参决策，只在发布前评估；调参集可以反复使用。二者混用会让指标虚高。
5. 排查方向：该类目文档是否覆盖不足（看上下文召回率）；切分是否把税率表切碎（看召回片段是否含关键数字）；是否存在类目专属术语未被查询改写覆盖；该类问题在黄金集中样本是否过少；是否需要类目路由到专用索引。
