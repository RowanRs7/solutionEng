# 增量索引、删除与数据同步

## 为什么需要学习

十月一日，晴空商城把生鲜类目的无理由退货期限从 7 天改成“不支持”。政策文档在知识库里当天就更新了，但助手到十月中还在回答“7 天内可退”，因为索引只做过一次全量导入。同一周，一个下架商品仍被推荐给客户；更严重的是，一位用户注销后，他的历史工单切片仍留在索引里，被合规审计抓了出来。

> **核心结论：** 索引是源数据的派生副本，不是一次性快照；删除必须和新增一样是一等公民，增量任务必须能安全重跑。

## 学习目标

完成本课后，你能够：

- 比较全量重建、定时扫描、CDC 流式与事件驱动四种同步方式。
- 用内容指纹设计出幂等的增量同步计划，并解释为什么切片 ID 要带指纹。
- 说明删除传播的三种做法及其失效场景。
- 写出“源—索引对账”的检查项，发现残留与漏更。

## 前置知识

- 回看上一课：[权限感知检索与多租户隔离](08-permission-aware-retrieval.md)。
- 了解文档入库链路：抽取 → 清洗 → 切分 → 向量化 → 写入。
- 知道什么是幂等操作，能读懂哈希函数的用途。
- 接触过至少一种消息队列或定时任务的基本概念。

## 业务场景

售后智能助手的知识来自四处：政策 wiki（每天有人编辑）、工单结案摘要（每小时新增）、商品与类目信息（从商品中心同步，会下架）、商家自定义规则（第三方向平台推送）。四处的更新节奏、删除语义、权限归属都不同。

助手必须满足三条业务约束：

- 政策改版后，新答案在 15 分钟内生效，旧版本不得再被引用。
- 商品下架后，检索不到它的任何切片，包括历史版本的切片。
- 用户注销或工单删除后，相关切片在 24 小时内从主索引、缓存与备份中消失。

## 核心概念

*增量索引*只处理自上次同步以来发生变化的文档；*水位线*（watermark）是“处理到哪个时间点”的标记。*内容指纹*（fingerprint）是对正文计算的哈希，用来判断内容是否真的变了——时间戳变了但内容没变时，指纹能省掉一次昂贵的向量化。*变更数据捕获*（CDC）从数据库日志或事件流中读取变更，延迟低但要求源系统支持。

*幂等 upsert* 指同一批变更重复执行多次，结果与执行一次相同。*删除传播*指删除动作从源系统一路传导到切片、向量、缓存与备份。*软删除*不物理删除，而是打标记后由同步任务处理，好处是可恢复、可审计。*别名切换*通过把读流量指向新索引、再原子切换别名来完成大规模重建，避免读到半成品。

| 同步方式 | 新鲜度 | 每次成本 | 复杂度 | 主要风险 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 全量重建 | 取决于周期 | 高（重嵌全部切片） | 低 | 周期内数据过期 | 小知识库、模型升级 |
| 定时扫描 + 时间戳 | 分钟到小时 | 低 | 中 | 同秒更新丢失、时钟漂移 | 文档型知识库 |
| CDC 流式 | 秒级 | 低 | 高 | 顺序错乱、重复消费 | 数据库驱动的业务数据 |
| 事件驱动 | 秒级 | 低 | 中高 | 事件丢失、无补偿 | 已有事件总线的系统 |

## 工作原理

一次完整的增量同步包含以下步骤：

1. **发现变更**：按水位线扫描 `updated_at`，或消费变更事件。注意时间戳精度，同秒多次更新要用序列号补齐。
2. **计算指纹**：对清洗后的正文算哈希，与索引中记录的指纹比较；相同则跳过，这一条能省掉大部分向量化费用。
3. **切分与向量化**：只对新增或变更的文档执行，切片 ID 形如 `doc_id@序号@指纹`。
4. **写入**：以切片 ID 为键做幂等 upsert；变更文档先删除旧指纹下的切片，再写新切片。
5. **删除传播**：文档下架时删除其全部切片；软删除场景由同步任务扫描标记列后执行物理删除。
6. **缓存失效**：按文档 ID 失效检索缓存与答案缓存，避免“索引已更新、缓存还答旧话”。
7. **对账**：比对源文档数、索引文档数、切片数，并抽样比对正文摘要与版本号。
8. **推进水位线**：只有在本批写入确认成功后推进，失败则重放同一批（依赖幂等性保证安全）。

删除有三种实现，失败方式各不相同：

- **硬删除**：源删即索引删。快，但误删不可恢复，且要求源系统能发出删除事件。
- **软删除标记**：源系统打 `is_deleted`，同步任务据此删索引。可恢复、可审计，是多数系统的首选。
- **TTL 过期**：切片带过期时间自动淘汰。适合日志类数据，不适合需要精确对齐业务状态的文档。

<u>没有“删除检测”的同步任务看起来一切正常，直到有人检索到已删除内容。这类问题不会报错，只会以合规事故的形式出现。</u>

## 架构与选型

| 场景 | 推荐方案 | 理由 |
| --- | --- | --- |
| 政策 wiki，日更、量小 | 定时扫描 + 内容指纹 | 实现简单，指纹可过滤大量无效变更 |
| 订单/工单摘要，高频写入 | CDC 或事件驱动 | 时间戳扫描会漏掉同秒更新，延迟也高 |
| 商品全量下架或迁移 | 新索引重建 + 别名切换 | 避免用户读到半新半旧的索引 |
| 用户注销、数据删除请求 | 软删除 + 删除传播清单 | 需要可证明“已删除”的审计证据 |
| Embedding 模型升级 | 全量重嵌 + 版本化索引 | 新旧向量不可混用，必须整体切换 |

选型依据：数据量与更新频率决定成本，删除的合规要求决定复杂度，源系统能力决定可行性。**不要为了“实时”上 CDC，先用定时任务把正确性做对，再优化延迟。**

## 最小示例

下面的脚本实现第 1–4 步的核心逻辑：用指纹判断变更，用带指纹的切片 ID 保证旧切片被显式清理，并保证任务可重复执行。

```python
import hashlib

SOURCE = {
    "policy-refund": {"content": "无理由退货 7 天，需未拆封"},
    "policy-ship":   {"content": "48 小时内发货，超时补偿 5 元"},
    "faq-1":         {"content": "如何修改收货地址"},
}
STATE = {}   # 相当于索引元数据表：doc_id -> {"fp": 指纹, "chunks": [切片 ID]}

def fingerprint(doc):
    # 对正文取哈希前缀；内容不变则指纹不变，可跳过重新向量化
    return hashlib.sha256(doc["content"].encode("utf-8")).hexdigest()[:8]

def chunk_ids(doc_id, fp):
    # 指纹写进切片 ID：内容一变，新旧 ID 不再相同，旧切片必须显式删除
    return [f"{doc_id}@{i}@{fp}" for i in range(2)]

def plan(source, state):
    creates, updates, stale, deletes = [], [], [], []
    for doc_id, doc in source.items():
        fp = fingerprint(doc)
        if doc_id not in state:
            creates.append((doc_id, chunk_ids(doc_id, fp)))
        elif state[doc_id]["fp"] != fp:
            updates.append((doc_id, chunk_ids(doc_id, fp)))
            stale.extend(state[doc_id]["chunks"])      # 旧切片必须清理
    for doc_id in state:
        if doc_id not in source:
            deletes.append(doc_id)
            stale.extend(state[doc_id]["chunks"])      # 文档下架：删掉全部切片
    return creates, updates, stale, deletes

def apply(source, state):
    creates, updates, stale, deletes = plan(source, state)
    for doc_id in deletes:                             # 先删文档，再写新内容
        state.pop(doc_id, None)
    for doc_id, chunks in creates + updates:
        state[doc_id] = {"fp": fingerprint(source[doc_id]), "chunks": chunks}
    return creates, updates, stale, deletes

for label in ("第 1 次（空索引）", "第 2 次（无变化）"):
    c, u, s, d = apply(SOURCE, STATE)
    print(f"{label}：新建 {[x[0] for x in c]} 更新 {[x[0] for x in u]} 删除切片 {s} 删除文档 {d}")

SOURCE["policy-refund"]["content"] = "无理由退货 15 天，需未拆封"   # 政策改版
del SOURCE["faq-1"]                                                  # 文档下架
SOURCE["faq-2"] = {"content": "如何申请价保"}                         # 新增文档
c, u, s, d = apply(SOURCE, STATE)
print(f"第 3 次（改/删/增）：新建 {[x[0] for x in c]} 更新 {[x[0] for x in u]} 删除切片 {s} 删除文档 {d}")
print("索引现有文档：", sorted(STATE))
```

预期输出（本机 `python3` 实跑一致）：

```text
第 1 次（空索引）：新建 ['policy-refund', 'policy-ship', 'faq-1'] 更新 [] 删除切片 [] 删除文档 []
第 2 次（无变化）：新建 [] 更新 [] 删除切片 [] 删除文档 []
第 3 次（改/删/增）：新建 ['faq-2'] 更新 ['policy-refund'] 删除切片 ['policy-refund@0@b5c9e363', 'policy-refund@1@b5c9e363', 'faq-1@0@085964a3', 'faq-1@1@085964a3'] 删除文档 ['faq-1']
索引现有文档： ['faq-2', 'policy-refund', 'policy-ship']
```

三个设计意图值得注意：第 2 次运行输出全空，说明任务幂等；第 3 次运行里 `stale` 列表同时包含改版文档的旧切片和下架文档的全部切片，说明删除是“按切片”而非“按文档”执行的；`faq-1` 从 `STATE` 中消失，说明元数据与向量两边都被清理。

## 动手实验

前置条件：Python 3.9+，无需第三方包。把代码保存为 `sync_demo.py`。

步骤：

1. 运行一次，确认输出与上文一致。
2. 把 `policy-refund` 的正文改一个字符，重跑，观察指纹与切片 ID 是否变化。
3. 只改 `SOURCE` 中某个文档的 `updated_at`（示例未使用该字段），说明为什么“时间戳变了但内容没变”时指纹能避免重嵌。
4. 模拟 Embedding 模型升级：在 `chunk_ids` 里加上模型版本前缀，观察是否所有切片都被重建。

预期结果：第 2 步生成新指纹与新切片 ID，旧切片进入 `stale`；第 3 步中指纹不变，`plan` 不产生任何动作；第 4 步所有文档都变成“更新”，这正是模型升级应有的行为。

验证方法：连续执行两次并比较输出，第二次必须全空；统计每轮 `stale` 的切片数是否等于上一轮该文档的切片数。

清理方法：删除 `sync_demo.py`。真实的同步任务还应清理临时导出文件与消息队列中的测试消息。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 索引里出现重复切片 | 切片 ID 不稳定或写入非幂等 | 统计同一文档的切片数量 | ID 含内容指纹，写入改为幂等 upsert |
| 已删除文档仍能被检索 | 只删源数据、未传播到索引 | 用被删文档的关键词检索 | 增加删除传播与对账任务 |
| 政策更新后仍答旧内容 | 水位线字段不可靠、同秒更新丢失 | 对比源更新时间与索引记录时间 | 用序列号或 CDC 替代裸时间戳 |
| 索引半新半旧 | 原地更新且中途失败 | 检查是否存在版本号混杂 | 新索引重建 + 别名原子切换 |
| 每轮都全量重嵌，费用高 | 未做指纹比较 | 统计向量化调用次数 | 先比指纹，只处理真实变更 |

## 安全与生产注意事项

**<u>删除请求没有传播到向量索引、检索缓存与备份，等于用户数据仍被保留，构成合规事故。</u>** 删除清单要覆盖所有副本，并保留可审计的执行记录；定期用被删内容做“反向检索”验证，比读日志更可靠。

**<u>用超级管理员账号跑同步任务且无审计，一次配置错误就能清空生产索引。</u>** 同步账号应遵守最小权限，删除操作要有限速与二次确认，索引变更要可回滚。

另外两点：**<u>增量任务读取的源表可能包含敏感字段，抽取阶段就要做字段裁剪</u>**，不要让明文进入向量库；同步日志里避免打印文档正文，改打印文档 ID 与指纹。

## 本课总结

- 索引是派生数据，必须有持续对账机制，而不是一次性导入。
- 内容指纹把“是否变更”和“时间戳”解耦，是控制向量化成本的关键。
- 切片 ID 携带内容指纹，才能保证旧切片被显式删除而非残留。
- 删除有三条路径（硬删、软删、TTL），选择取决于合规要求与源系统能力。
- 幂等与水位线是重跑安全的两根支柱，缺一不可。

## 思考题

如果源系统既没有 CDC，也没有可靠的 `updated_at`，只有每天一次的数据库全量快照，你会如何设计同步方案，并把“删除”和“更新”都处理正确？

参考思路：用全量快照两两做差：以文档 ID 为键比对内容指纹，新增/变更/消失三类分别映射到创建、更新、删除；代价是每天一次全量哈希与一次差异计算，但不需要源系统配合。若快照过大，可分片哈希或只对元数据比对后再按需取正文。

3. 水位线为什么不能只用 `updated_at` 时间戳？
4. 软删除相比硬删除的最大优势是什么？
5. 场景题：合规团队要求“证明某用户的工单切片已被删除”。请给出至少两个可执行的验证手段。

## 答案与解析

1. 指纹进入 ID 后，内容变化会生成全新 ID，旧切片不会因为“同 ID 覆盖”而残留；同时让重复写入天然幂等，也便于按指纹批量清理。
2. **B。** 全量重嵌期间新旧向量不可混用，需要新索引承载并原子切换。A、C、D 都是单文档级变更，增量处理即可。
3. 同一秒内的多次更新可能共享一个时间戳，导致后一次被跳过；时钟漂移与批量导入也会让时间戳失去单调性。应配合序列号、版本号或 CDC。
4. 可恢复、可审计：删除意图被显式记录，误删能还原，也能向审计方证明“何时、因何删除”。
5. 用被删工单的关键词与实体做反向检索（应无命中）；核对索引元数据表中该文档的记录已消失；比对缓存与备份的清理记录；抽取一批历史切片人工核对。三者结合才算证据链。
