# Graph RAG、长上下文与微调的选择

## 为什么需要学习

客服问：“订单 A1001 用花呗付的，退款按哪个时效？”向量检索只返回了订单片段，因为“花呗”和“退款时效”之间隔着一跳关系。第二个声音说：“模型上下文已经很能装了，把全部政策塞进去就行。”第三个声音说：“微调一下，让它记住政策。”

这三种方案都真实存在，也都各有明确的失效条件。选错的代价不是效果差一点，而是成本翻几倍、答案过期、甚至越过权限边界。

> **核心结论：** 选型的核心不是“哪种技术更强”，而是“知识多久变一次、问题需要几跳、答案能否被追溯”。

## 学习目标

完成本课后，你能够：

- 用“更新频率、跳数、可追溯性”三个维度比较 RAG、Graph RAG、长上下文与微调。
- 解释 Graph RAG 的索引流程与 Local / Global / DRIFT 三种查询模式的差别。
- 估计长上下文方案的 token 成本与“中间信息丢失”风险。
- 判断哪些问题应该用微调解决，哪些必须留给检索。

- 回看上一课：[RAG 评测与错误分析](10-rag-evaluation-and-error-analysis.md)。
- 了解向量检索与 RAG 的基本链路。
- 知道知识图谱中“实体”“关系”“跳数”的含义。
- 了解微调（SFT）是在任务数据上继续训练模型权重。

## 业务场景

晴空商城的售后知识有三类结构：

- 政策条文：层级清晰、更新频繁，适合按条款检索。
- 订单与商品：关系型数据，退款规则取决于“商品类目 × 支付渠道 × 签收时间”。
- 历史工单：非结构化，用于找相似案例。

客服的问题也分三类：单点事实（“生鲜能退吗”）、多跳推理（“花呗付的生鲜，退款多久到账”）、全局概览（“这个月退款延迟主要集中在哪些类目”）。用同一种检索方式回答这三类问题，必然有一类效果很差。

## 核心概念

*Graph RAG* 是先对文档做实体与关系抽取、构建知识图谱，再在图上检索的 RAG 变体。*实体消歧*指把“花呗”“支付宝花呗”识别为同一实体。*社区检测*把图中连接紧密的节点聚成簇，*社区报告*是让模型为每个簇生成的摘要。

*Local Search* 从与问题相关的实体出发，把图的邻域信息和原始文本片段一起送入模型，适合围绕具体实体的问题。*Global Search* 对全部社区报告做 map-reduce 汇总，适合“整体上有什么规律”这类数据集级问题，官方文档明确说它资源开销大。*DRIFT Search* 在局部检索中引入社区信息，扩大检索起点。

*长上下文*指把大量文档直接放进上下文窗口。*Lost in the Middle* 现象指模型对上下文中部信息的利用弱于开头和结尾（Liu 等，2023）。*微调*通过调整权重让模型学习任务的模式；它擅长风格、格式、工具调用习惯，不擅长承载高频变化的事实。

| 方案 | 知识新鲜度 | 多跳能力 | 可追溯性 | 初始成本 | 每次更新成本 | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| 向量 RAG | 高（改完即可检索） | 弱（单跳为主） | 强（回到原文） | 低 | 低 | 政策问答、FAQ |
| Graph RAG | 中（更新需重建图） | 强（显式关系） | 中强（可回到边与原文） | 高（抽取+摘要） | 高（社区重建） | 实体关系密集、多跳 |
| 长上下文全塞 | 高 | 中（依赖模型阅读） | 弱（难定位到具体条款） | 低 | 低（但每次推理贵） | 小规模、一次性分析 |
| 微调 | 低（需重训） | 弱 | 弱（知识在权重里） | 中高 | 高（重训+回归） | 风格、格式、工具使用 |

## 工作原理

Graph RAG 的索引侧通常包含四步：

1. **切分与抽取**：对每个文本单元调用模型抽取实体、关系与断言，产出三元组。
2. **实体消歧与合并**：把同义实体归并，否则图会被重复节点切碎。
3. **社区检测**：在图上做层次聚类，得到多粒度的社区。
4. **社区摘要**：为每个社区生成报告，供全局查询使用。

查询侧按问题类型分流：

- **Local**：定位问题中的实体，取其邻域与对应原文片段，适合“这个订单的退款时效”。
- **Global**：对社区报告做 map-reduce，适合“整体趋势是什么”。
- **DRIFT**：以局部检索为主，同时引入社区洞察扩展子问题。

长上下文的边界要算三笔账：**token 成本随文档量线性增长；上下文越长，中部信息越容易被忽略；文档全塞进去就绕过了检索层的过滤与引用机制。** 它适合“一次性、可人工核对”的分析，不适合高频在线问答。

微调的边界同样清晰：它能学风格、格式、领域语气和工具调用习惯，也能让小模型模仿大模型的输出。但 Azure 官方文档明确指出，微调会增加训练与托管成本，且<u>无法替代对最新信息的检索，也无法替代应用层的安全控制</u>（截至 2026-10-19）。政策每月改版时，微调出来的“记忆”会立刻过期。

## 架构与选型

| 判断维度 | 选向量 RAG | 选 Graph RAG | 选长上下文 | 选微调 |
| --- | --- | --- | --- | --- |
| 知识更新频率 | 高 | 中 | 低 | 极低 |
| 问题跳数 | 1 跳 | 2 跳以上 | 不确定 | 不涉及 |
| 是否需要引用原文 | 必需 | 需要 | 弱 | 不需要 |
| 数据规模 | 中到大 | 中 | 小 | 与规模无关 |
| 主要成本 | 检索与生成 | 抽取与社区重建 | 推理 token | 训练与回归 |
| 典型信号 | 客服问政策 | 售后规则依赖商品/渠道/时间 | 一次性合同比对 | 输出格式总不统一 |

选型顺序建议：**先用向量 RAG 把基线做出来，用评测数据确认错误集中在多跳还是格式，再决定是否引入图或微调。** 没有评测基线的架构升级，通常只是把成本换成了不确定性。

混合方案往往最实用：向量检索负责召回原文，图检索负责补充跨实体关系，微调只负责输出格式与工具调用规范。

## 最小示例

下面的脚本用三元组模拟两跳检索：问题实体是“订单A1001”，需要沿“支付渠道 → 退款时效”找到退款依据。向量检索只能命中订单自身片段。

```python
EDGES = [
    ("订单A1001", "支付渠道", "花呗",       "chunk-order"),
    ("花呗",      "退款时效", "3 个工作日",  "chunk-channel"),
    ("订单A1001", "商品类目", "生鲜",       "chunk-order"),
    ("生鲜",      "无理由退货", "不支持",    "chunk-fresh"),
    ("订单A1001", "收货时间", "2026-10-10", "chunk-order"),
]
QUESTION_ENTITY = "订单A1001"

graph = {}
for head, rel, tail, chunk in EDGES:
    graph.setdefault(head, []).append((rel, tail, chunk))
    graph.setdefault(tail, []).append((rel, head, chunk))   # 反向边，支持双向扩展

def hop(start, depth, allowed):
    seen, frontier, hits = {start}, [start], []
    for _ in range(depth):
        nxt = []
        for node in frontier:
            for rel, tail, chunk in graph.get(node, []):
                if rel not in allowed:      # 只沿业务允许的关系扩展，避免图爆炸
                    continue
                hits.append((rel, tail, chunk))
                if tail not in seen:
                    seen.add(tail)
                    nxt.append(tail)
        frontier = nxt
    return hits

hits = hop(QUESTION_ENTITY, depth=2, allowed={"支付渠道", "退款时效"})
print("两跳扩展命中：")
for rel, tail, chunk in hits:
    print(f"  -{rel}-> {tail}  ({chunk})")

vector_hits = sorted({c for h, _, _, c in EDGES if QUESTION_ENTITY in h})
print("向量检索 top-k：", vector_hits, "（缺少退款时效依据）")
print("图检索补充：", sorted({c for _, _, c in hits} - set(vector_hits)))
```

预期输出（本机 `python3` 实跑一致）：

```text
两跳扩展命中：
  -支付渠道-> 花呗  (chunk-order)
  -支付渠道-> 订单A1001  (chunk-order)
  -退款时效-> 3 个工作日  (chunk-channel)
向量检索 top-k： ['chunk-order'] （缺少退款时效依据）
图检索补充： ['chunk-channel']
```

两点设计意图：`allowed` 白名单限制扩展关系，真实系统里这是防止图检索把无关邻域全部拖进上下文的关键；输出里出现了重复的 `chunk-order`，说明图检索必须做片段去重，否则同一段原文会被多次计费。

## 动手实验

前置条件：Python 3.9+，无需第三方包。把代码保存为 `graph_hop.py`。

步骤：

1. 运行一次，确认输出与上文一致。
2. 把 `depth` 改为 1，观察是否还能找到退款时效。
3. 从 `allowed` 中删掉 `"退款时效"`，观察结果如何退化。
4. 增加一条边“花呗 → 支持分期 → 是”，把 `depth` 设为 3，观察命中集合如何扩张。

预期结果：第 2 步只能拿到订单片段，说明一跳不够；第 3 步即使深度足够也拿不到退款依据，说明关系白名单比深度更关键；第 4 步命中数明显增加，提示需要限制邻域规模。

验证方法：对每条命中打印其来源边，人工核对是否真的与问题相关；统计“命中片段数 ÷ 上下文可用名额”，判断是否超预算。

清理方法：删除 `graph_hop.py`。真实图索引还需清理抽取任务的中间产物与模型调用日志。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 图中同一实体出现多次 | 缺少实体消歧 | 抽样看三元组中的实体名 | 归一化、别名表、实体解析 |
| 索引成本远超预期 | 每个文本单元都调用大模型抽取 | 统计抽取调用次数与 token | 先抽取高频实体、用小模型预处理 |
| 政策一改就要全量重建 | 社区报告依赖全量摘要 | 检查重建范围 | 只重建受影响社区，或图与向量分工 |
| 长上下文仍漏掉关键条款 | Lost in the Middle | 固定内容换位置做对照实验 | 分段检索、重排、把关键段落放首尾 |
| 微调后仍答旧政策 | 事实被固化进权重 | 对比新旧政策的回答 | 事实放检索，微调只学格式 |

## 安全与生产注意事项

**<u>把全部文档塞进长上下文，等于绕过检索层的权限过滤，一次提问就可能把无权文档送进模型与供应商日志。</u>** 上下文组装必须复用同一套权限裁剪逻辑，不能因为“反正放得下”就跳过过滤。

**<u>微调无法保证删除训练数据中的敏感信息，用户行使删除权时你可能无法兑现。</u>** 训练数据要先去敏，保留数据血缘；涉及个人信息的事实应放在可删除的检索层，而不是权重里。

另外两条：**<u>图抽取会把文档内容发送给模型服务，跨境或涉密文档必须先确认数据流向</u>**；**<u>全局查询的 map-reduce 会把大量摘要送入模型，成本与泄露面都要按最坏情况估算</u>**。

## 本课总结

- 选型看三件事：知识更新频率、问题跳数、答案是否需要追溯到原文。
- Graph RAG 用索引期的高成本换查询期的多跳能力，更新代价必须提前算清。
- 长上下文解决“放不下”，不解决“找得准”和“查得到权限”。
- 微调擅长风格与格式，不适合承载高频变化的事实。
- 先用向量 RAG 建立评测基线，再决定是否引入图或微调。

## 思考题

如果业务方要求“助手能回答任意跨类目的对比问题，并且答案必须能引用原文”，你会如何在 Graph RAG 与“向量检索 + 多轮查询改写”之间做选择？请写出你的验证实验设计。

参考思路：先构造 30 条跨类目问题作为评测集，分别测两种方案的 Recall@k、平均跳数与单次成本；若多跳命中率明显更高且更新频率可接受，再引入图。若问题主要是“同一实体在不同文档中的信息聚合”，多轮改写往往更便宜。验证时要固定生成模型，只比较检索层差异。

## 小测

1. Graph RAG 中 Local Search 与 Global Search 的主要区别是什么？
2. 下列哪种需求最适合微调而不是检索？  
   A. 政策条款随时更新　B. 输出必须固定为某种 JSON 结构　C. 需要引用原文　D. 多租户权限隔离
3. 为什么“上下文够长就全塞进去”在生产环境通常不成立？
4. Lost in the Middle 现象对上下文组装有什么启示？
5. 场景题：客服问题“花呗支付的生鲜订单退款时效”在向量 RAG 下经常只答出生鲜规则。请给出两种改进方案并比较代价。

## 答案与解析

1. Local 从具体实体出发，结合图邻域与原文片段回答实体级问题；Global 对全部社区报告做 map-reduce 汇总，回答数据集级问题，资源开销更大。
2. **B。** 固定输出结构属于风格与格式学习，正是微调擅长的部分。A、C 依赖可更新的外部知识，D 属于检索层与系统层的控制，都不能靠微调解决。
3. 成本随文档量线性增长；中部信息容易被忽略；绕过检索层就失去了权限过滤与引用溯源，出现问题时无法定位依据。
4. 关键信息不应埋在长上下文中间；组装时应把最相关的片段放在开头或结尾，并控制总量，而不是简单堆叠。
5. 方案一：引入图检索，沿“订单 → 支付渠道 → 退款时效”扩展，代价是抽取与图维护成本；方案二：多轮查询改写，先把“花呗”改写为支付渠道实体再检索，代价是延迟与改写准确率。前者适合关系稳定、查询频繁的场景，后者改造成本更低。
