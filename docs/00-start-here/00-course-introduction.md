# 课程导论

## 这门课解决什么问题

你可能会修改一段 Python 脚本，却不知道怎样把它变成真实业务可用的一部分。比如，业务方提出：“把商城、仓库和客服系统打通，再加一点 AI。”这句话没有说明谁来使用、数据从哪里来、谁能查看、外部系统失败怎么办，也没有说明怎样算做成功。

本课程带你把这类模糊愿望逐步变成可实施、可验证的方案。你会学习澄清需求、连接系统、处理权限和数据、测试与交付，以及上线后的排障和改进，然后再把这些能力用到 AI 场景中。

## 学习者

本课程面向会阅读和修改简单 Python 代码、但不了解企业后端和系统集成的学习者。课程会从基本概念讲起，你可以先理解一次请求或一笔数据怎样流动，再进入代码和架构设计。

## 目标角色

课程培养 **AI 解决方案架构师**：既能理解业务和交付，也能设计传统系统与 AI 能力的组合。

这里的**解决方案**不只是一个程序或一次模型调用，而是为达成业务目标而组合的技术、流程、人员和交付安排。**解决方案架构师**要连接业务、开发、安全、数据和运维等角色，明确系统边界，比较可选方案，记录关键决定，并推动团队用证据验证方案。

这有点像筹备一家餐厅：只挑一台好烤箱并不够，还要确认顾客需求、预算、厨房动线、食品安全、人员分工，以及开业后如何根据反馈改进。对应到软件方案，烤箱像单个技术组件，顾客目标像业务目标，动线和分工像流程与责任，食品安全像必须满足的安全约束，开业反馈像运行数据。架构师关注的是这些部分能否一起运转，而不只是选哪台“烤箱”。

架构师也不会替代所有专业角色。产品负责人决定价值和优先级，开发人员实现模块，安全和运维人员分别对各自专业结果负责；架构师负责保持跨系统设计的一致性。小团队可以一人兼任多个角色，但责任仍需说清楚。

## 学习顺序

先学传统解决方案，再学 AI 解决方案。AI 功能最终仍要进入真实系统：请求怎样通过网络到达服务，API（系统之间的接口）怎样约定数据和调用方式，用户能访问哪些数据，系统怎样保持可靠性并处理失败，上线后怎样发现问题，都属于传统工程基础。

在这个地基上，AI 模块再处理模型输出的不确定性、知识检索、工具权限和效果评测。换句话说，传统能力帮助系统“正确地运转”，AI 能力帮助系统在结果可能出错时仍然可用、可控、可验收。AI 不会替代这些基础，反而会更频繁地用到它们。

## 学习方式

课程通过学习目标、业务场景、概念、实验、排错、测验和下一步组织内容，不同页面的详略会有所区别。先读场景，弄清“为什么要学”，再读概念和操作步骤。

遇到代码时，先阅读整体流程，说清楚输入、处理和输出，再逐行运行和修改。读完一篇后，尝试不看正文复述核心概念，并完成实验和小测；具体的复习方法见下一篇学习指南。
