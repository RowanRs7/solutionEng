# 术语表

| 术语 | 一句话解释（含常见误区或使用场景） |
| --- | --- |
| 解决方案 | 为解决一个业务问题，把技术、流程和交付安排组合起来的一整套做法。它不是某一个软件，而是“怎么把事办成”的整体安排。 |
| 解决方案架构 | 把系统拆成哪些部分、边界在哪、彼此怎么连、受什么限制、做了哪些关键取舍，用图和文档讲清楚的设计。 |
| [利益相关者](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#利益相关者地图) | 会被方案影响、能影响方案，或者手里有关键信息的人或组织。常见误区：不只包括出钱的人。 |
| [发起人](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#利益相关者地图) | 给项目定方向、批预算、能拍板的人。项目卡住时，通常是他出面推动。 |
| [业务目标](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#目标产出和成果) | 组织真正想拿到的结果，比如“退款处理时间从 3 天降到 4 小时”。 |
| [产出](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#目标产出和成果) | 项目直接做出来的东西：功能、系统、文档。易混：做出来不等于有用，有用才是成果。 |
| [成果](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#目标产出和成果) | 产出被真正用起来之后带来的可观察变化，比如错误率下降、人工减少。 |
| [指标](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#目标产出和成果) | 能用数字衡量的判断依据，用来回答“到底做到没有”。 |
| [关注点](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#关注点与冲突) | 某位相关人特别在意的事：想保护什么、想改善什么、千万别碰什么。不同人的关注点经常互相冲突。 |
| [决策所有者](../01-traditional-solutions/01-discovery-and-requirements/02-stakeholders-and-business-goals.md#利益相关者地图) | 某类事情最后由谁拍板。找错人，决策就会反复。 |
| [解决方案架构师](../01-traditional-solutions/01-discovery-and-requirements/01-solution-architect-role.md#核心概念) | 站在业务目标和技术实现中间的人：划边界、定关键决策、盯风险、把各方的技术关系理顺。 |
| [业务流程](../01-traditional-solutions/01-discovery-and-requirements/03-current-state-and-business-process.md#核心概念) | 为了办成一件事，按顺序发生的一组活动和交接。真实流程里通常还带着等待和例外。 |
| [现状证据](../01-traditional-solutions/01-discovery-and-requirements/03-current-state-and-business-process.md#核心概念) | 能证明“现在确实是这样”的材料，比如日志、截图、工单统计、访谈记录，并注明来源。 |
| [外部参与者](../01-traditional-solutions/01-discovery-and-requirements/04-users-roles-scenarios-and-use-cases.md#核心概念) | 系统边界之外、但要和系统打交道的人、角色或系统，比如用户、合作方、支付平台。 |
| [用例](../01-traditional-solutions/01-discovery-and-requirements/04-users-roles-scenarios-and-use-cases.md#核心概念) | 参与者为了达成目标，和系统来回交互的完整过程，包含主流程、备选流程和最终结果。 |
| [场景](../01-traditional-solutions/01-discovery-and-requirements/04-users-roles-scenarios-and-use-cases.md#核心概念) | 更具体的一版描述：谁、在什么情况下、想做什么、做完看到什么结果。 |
| [功能需求](../01-traditional-solutions/01-discovery-and-requirements/05-functional-and-non-functional-requirements.md#核心概念) | 系统必须“会做”的事，比如“支持按订单号查询”。 |
| [非功能需求](../01-traditional-solutions/01-discovery-and-requirements/05-functional-and-non-functional-requirements.md#核心概念) | 系统“做得好不好”的要求：快不快、稳不稳、安不安全。通常要换算成可测的数字才管用。 |
| [质量属性](../01-traditional-solutions/01-discovery-and-requirements/05-functional-and-non-functional-requirements.md#核心概念) | 非功能需求里可以衡量的那一面，比如“99% 的请求在 300ms 内返回”。 |
| [质量属性场景](../01-traditional-solutions/01-discovery-and-requirements/05-functional-and-non-functional-requirements.md#核心概念) | 把质量要求写成固定六段：谁触发、触发什么、在什么条件下、作用于谁、系统怎么响应、响应要多少。好处是能测。 |
| [可测量需求](../01-traditional-solutions/01-discovery-and-requirements/05-functional-and-non-functional-requirements.md#工作原理) | 把条件、动作、结果、阈值和验证方法都写死的需求，团队能直接判断“达没达标”。 |
| [系统边界](../01-traditional-solutions/01-discovery-and-requirements/06-boundaries-constraints-dependencies-assumptions.md#核心概念) | 这个方案承诺负责的范围：管什么、不管什么。边界不清，后面一定扯皮。 |
| [约束](../01-traditional-solutions/01-discovery-and-requirements/06-boundaries-constraints-dependencies-assumptions.md#核心概念) | 已经定死、不能商量的条件，比如预算上限、必须用某家云、合规要求。 |
| [依赖](../01-traditional-solutions/01-discovery-and-requirements/06-boundaries-constraints-dependencies-assumptions.md#核心概念) | 需要别人先给你东西（接口、数据、决策），你才能继续往下走的关系。 |
| [上游与下游依赖](../01-traditional-solutions/01-discovery-and-requirements/06-boundaries-constraints-dependencies-assumptions.md#核心概念) | 按数据或调用方向来分：上游给你输入，下游接收你的输出。判断“谁卡谁”，先看方向。 |
| [假设](../01-traditional-solutions/01-discovery-and-requirements/06-boundaries-constraints-dependencies-assumptions.md#核心概念) | 目前还没验证、但方案暂时当作成立的前提。假设一旦错了，方案可能要跟着改。 |
| [风险](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 还没发生、但一旦发生会影响目标的事，重点在“可能”和“后果”。 |
| [问题](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 已经发生、有证据、需要处理或跟踪的事。易混：风险在未来，问题在眼前。 |
| [风险触发条件](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 能观察到的苗头，一出现就说明风险正在变成问题，该启动应对了。 |
| [风险所有者](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 盯着这个风险、推动决策、确认应对做完的人。没有名字的风险，等于没人管。 |
| [缓解措施](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 在风险发生前做的动作，目的是让它更不容易发生，或者发生后果更轻。 |
| [应急方案](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 风险已经发生时的预案：怎么止损、怎么把业务先保住。 |
| [残余风险](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 应对措施做完之后还剩的那部分风险，需要明确接受，或者继续处理。 |
| 交付物 | 某个阶段做完、要交给别人继续用的东西，比如文档、接口、镜像。 |
| [验收标准](../01-traditional-solutions/01-discovery-and-requirements/07-priorities-scope-and-acceptance.md#核心概念) | 判断“这条需求算不算做完”的可观察条件，最好能当场演示或测出来。 |
| [范围基线](../01-traditional-solutions/01-discovery-and-requirements/07-priorities-scope-and-acceptance.md#核心概念) | 双方确认过的一版范围：这期做什么、不做什么、基于哪些假设、怎么验收。之后有变更，就拿它对比。 |
| [需求优先级](../01-traditional-solutions/01-discovery-and-requirements/07-priorities-scope-and-acceptance.md#核心概念) | 排先后顺序的判断：结合目标、风险、工作量、依赖和约束，决定先做哪个。 |
| [MoSCoW](../01-traditional-solutions/01-discovery-and-requirements/07-priorities-scope-and-acceptance.md#核心概念) | 把需求分成必须有、应该有、可以有、这期不做四档的讨论方法，常用来砍范围。 |
| [Given/When/Then](../01-traditional-solutions/01-discovery-and-requirements/07-priorities-scope-and-acceptance.md#核心概念) | 写验收场景的固定句式：给定什么条件，做了什么，应该看到什么结果。 |
| [需求追踪](../01-traditional-solutions/01-discovery-and-requirements/07-priorities-scope-and-acceptance.md#核心概念) | 把目标、需求、验收条件和验证证据串成一条线，能回答“这条需求为什么存在、怎么证明做完了”。 |
| [风险登记表](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 跟踪风险的表：风险是什么、多大可能、多大影响、什么信号触发、谁负责、怎么应对、现在什么状态。 |
| [风险暴露](../01-traditional-solutions/01-discovery-and-requirements/08-risks-and-requirement-deliverables.md#核心概念) | 用概率乘影响算出的粗略排序值，用来决定先管哪个。它不是精确预测。 |
| [往返时延（RTT）](../01-traditional-solutions/02-web-and-network/01-web-architecture-and-layers.md#核心概念) | 一个报文从客户端发到服务端再回来的总时间。物理距离和路由跳数决定了它的下限。 |
| [DNS](../01-traditional-solutions/02-web-and-network/02-tcp-ip-dns-and-firewall.md#核心概念) | 把域名翻译成 IP 地址的分布式电话簿。它有多层缓存，所以改了记录不会立刻全球生效。 |
| [幂等](../01-traditional-solutions/02-web-and-network/03-http-request-response.md#核心概念) | 同一个请求做一次和做十次，最终结果一样。例：重复提交同一笔退款，不会退两次。 |
| [Cookie](../01-traditional-solutions/02-web-and-network/04-headers-cookies-and-caching.md#核心概念) | 服务端发给浏览器、浏览器存起来，之后访问同一站点时自动带上的小段键值数据。 |
| [同源策略](../01-traditional-solutions/02-web-and-network/07-cors-csrf-and-browser-security.md#核心概念) | 浏览器的隔离规则：一个站点默认不能读取另一个站点的响应、Cookie 和页面内容。 |
| [CORS](../01-traditional-solutions/02-web-and-network/07-cors-csrf-and-browser-security.md#核心概念) | 服务端用响应头明确告诉浏览器“哪些别的站点可以读我”，相当于给同源策略开了一个受控的口子。 |
| [反向代理](../01-traditional-solutions/02-web-and-network/09-reverse-proxy-load-balancer-cdn.md#核心概念) | 站在服务端前面、替后端接收请求的代理。客户端以为自己连的就是它。 |
| [CDN](../01-traditional-solutions/02-web-and-network/09-reverse-proxy-load-balancer-cdn.md#核心概念) | 把可共享的内容复制到离用户近的边缘节点，让用户就近取，减少跨地域延迟。 |
| [REST](../01-traditional-solutions/03-api-and-integration/01-api-rest-and-resource-modeling.md#核心概念) | 一套接口设计风格：把业务对象当资源、用 URL 标识、用 HTTP 方法操作、每次请求自带全部信息（无状态）。 |
| [资源建模](../01-traditional-solutions/03-api-and-integration/01-api-rest-and-resource-modeling.md#核心概念) | 把业务需求翻译成“有哪些资源、谁属于谁、支持哪些操作”的过程，是设计 API 的第一步。 |
| [API 契约](../01-traditional-solutions/03-api-and-integration/01-api-rest-and-resource-modeling.md#核心概念) | 双方约定死的调用规则。有了它，调用方不用看实现就能对接，实现方也能独立改内部。 |
| [OpenAPI 文档](../01-traditional-solutions/03-api-and-integration/02-openapi-and-contracts.md#核心概念) | 描述 HTTP API 的标准格式，通常用 YAML 或 JSON 书写，可以用来生成文档和客户端代码。 |
| [限流](../01-traditional-solutions/03-api-and-integration/04-pagination-filtering-and-rate-limits.md#核心概念) | 限制单位时间内允许的请求次数，保护服务端自己不被压垮。易混：限流保护服务，配额约束的是客户用量。 |
| [超时预算](../01-traditional-solutions/03-api-and-integration/05-timeout-retry-backoff-and-idempotency.md#核心概念) | 从对上层承诺的总时间往下倒推，每层只剩多少时间可用。传给下游的是“剩余时间”，不是固定值。 |
| [指数退避](../01-traditional-solutions/03-api-and-integration/05-timeout-retry-backoff-and-idempotency.md#核心概念) | 重试的等待时间一次比一次成倍变长，再加一点随机抖动，避免所有客户端同时重试。 |
| [幂等键](../01-traditional-solutions/03-api-and-integration/05-timeout-retry-backoff-and-idempotency.md#核心概念) | 发起方给“这一次业务意图”生成的唯一标识。服务端靠它识别重复请求，防止重复扣款。 |
| [熔断器](../01-traditional-solutions/03-api-and-integration/06-circuit-breaking-degradation-and-isolation.md#核心概念) | 调用链上的自动开关：下游失败率太高就直接快速失败，不再干等，同时给下游留出恢复时间。 |
| [死信队列](../01-traditional-solutions/03-api-and-integration/10-message-queues-pubsub-and-dlq.md#核心概念) | 重试很多次仍然处理不了的消息，被挪到这里等人工处理。它是待办清单，不是垃圾桶。 |
| [Outbox 表](../01-traditional-solutions/03-api-and-integration/11-outbox-compensation-and-eventual-consistency.md#核心概念) | 和业务表同库的待发消息表。业务改动和消息写入在同一个事务里，避免“库改了、消息却没发出去”。 |
| [补偿](../01-traditional-solutions/03-api-and-integration/11-outbox-compensation-and-eventual-consistency.md#核心概念) | 已经生效的步骤撤不回来，就再做一个语义相反的新动作把它抵掉，比如退款冲正。 |
| [最终一致性](../01-traditional-solutions/03-api-and-integration/11-outbox-compensation-and-eventual-consistency.md#核心概念) | 允许短时间内数据不一致，但只要不再有新写入，过一段时间系统会自己收敛到一致。 |
| [CDC](../01-traditional-solutions/03-api-and-integration/12-etl-elt-cdc-and-data-sync.md#核心概念) | 持续读取数据库变更日志，把某一刻之后的每一条改动同步出去，而不是定期全量拷贝。 |
| [认证](../01-traditional-solutions/04-identity-and-security/01-authentication-authorization-and-audit.md#核心概念) | 回答“你是谁”，验证身份是否属实，失败一般返回 401。易混：认证管身份，授权管权限。 |
| [授权](../01-traditional-solutions/04-identity-and-security/01-authentication-authorization-and-audit.md#核心概念) | 身份确认之后再回答“你能做什么”，判断你能不能操作某个资源。失败一般返回 403。 |
| [JWT](../01-traditional-solutions/04-identity-and-security/03-jwt-structure-and-validation.md#核心概念) | 一种令牌格式：头部、载荷、签名三段用点隔开。注意载荷只是编码不是加密，别塞敏感信息。 |
| [OAuth 2.0](../01-traditional-solutions/04-identity-and-security/04-oauth2-flows-and-pkce.md#核心概念) | 一套授权框架：让第三方应用在拿不到用户密码的前提下，获得限定范围的访问权限。 |
| [PKCE](../01-traditional-solutions/04-identity-and-security/04-oauth2-flows-and-pkce.md#核心概念) | 给授权码流程加的一道保险：发起方先生成一个秘密，换令牌时出示，防止授权码被截获后冒用。 |
| [OIDC](../01-traditional-solutions/04-identity-and-security/05-openid-connect-and-id-tokens.md#核心概念) | 建在 OAuth 2.0 之上的认证层，额外规定怎么把“这个人是谁”告诉客户端。 |
| [SAML 2.0](../01-traditional-solutions/04-identity-and-security/06-sso-saml-and-enterprise-identity.md#核心概念) | 企业单点登录常用的 XML 协议：身份提供方签名一张身份断言，由浏览器带给应用。 |
| [RBAC](../01-traditional-solutions/04-identity-and-security/07-rbac-abac-and-multi-tenant-permissions.md#核心概念) | 按角色给权限：先把权限绑到角色，再把人放进角色。适合职责清晰的场景。 |
| [ABAC](../01-traditional-solutions/04-identity-and-security/07-rbac-abac-and-multi-tenant-permissions.md#核心概念) | 按属性判断：把人、资源、动作、环境的各种属性一起放进策略里算。适合规则复杂的场景。 |
| [租户](../01-traditional-solutions/04-identity-and-security/07-rbac-abac-and-multi-tenant-permissions.md#核心概念) | 共用同一套系统、但数据彼此不可见的一批用户或组织。 |
| [信封加密](../01-traditional-solutions/04-identity-and-security/08-secrets-and-key-management.md#核心概念) | 用主密钥加密数据密钥，再用数据密钥加密正文。换密钥时只换上层，不用把所有数据重新加密。 |
| [MVCC](../01-traditional-solutions/05-data-and-architecture/02-indexes-transactions-and-migrations.md#核心概念) | 多版本并发控制：写的时候产生新版本，读的时候按快照读旧版本，所以读不挡写、写不挡读。 |
| [连接池](../01-traditional-solutions/05-data-and-architecture/02-indexes-transactions-and-migrations.md#核心概念) | 预先建好一批数据库连接反复使用。池子有多大，能同时处理的查询就大致有多少。 |
| [缓存击穿](../01-traditional-solutions/05-data-and-architecture/03-nosql-redis-and-caching.md#核心概念) | 某个被高频访问的键刚好过期，大量请求同时回源，瞬间把数据库压满。 |
| [缓存雪崩](../01-traditional-solutions/05-data-and-architecture/03-nosql-redis-and-caching.md#核心概念) | 大批键在同一时刻过期，或者缓存整体挂掉，流量一次性砸到数据库。 |
| [对象存储](../01-traditional-solutions/05-data-and-architecture/04-object-storage-and-file-management.md#核心概念) | 用 HTTP 存取整块文件的存储，一次写一个完整对象，不适合频繁修改其中一小段。 |
| [预签名 URL](../01-traditional-solutions/05-data-and-architecture/04-object-storage-and-file-management.md#核心概念) | 服务端用密钥生成、带有效期的链接。拿到链接的人，能在期限内以签发者身份读写这个对象。 |
| [API 网关](../01-traditional-solutions/05-data-and-architecture/08-api-gateway-and-service-discovery.md#核心概念) | 所有客户端请求的统一入口，集中做路由、鉴权、限流和请求改写。 |
| [服务发现](../01-traditional-solutions/05-data-and-architecture/08-api-gateway-and-service-discovery.md#核心概念) | 服务之间按名字找地址的机制：启动时登记自己，调用时查出对方当前地址。 |
| [RTO](../01-traditional-solutions/05-data-and-architecture/09-high-availability-and-disaster-recovery.md#核心概念) | 从出事到业务恢复的最长可接受时间。易混：RTO 管“停多久”，RPO 管“丢多少”。 |
| [RPO](../01-traditional-solutions/05-data-and-architecture/09-high-availability-and-disaster-recovery.md#核心概念) | 恢复之后，最多能接受丢失多长时间的数据。 |
| [ADR](../01-traditional-solutions/05-data-and-architecture/10-architecture-tradeoffs-and-adr.md#核心概念) | 一次只记录一个架构决定：背景、备选方案、最终选择、后果，外加状态（提议、通过、废弃）。 |
| [依赖锁定](../01-traditional-solutions/06-build-test-deliver/02-dependencies-config-and-secrets.md#核心概念) | 把实际用到的版本集合和校验和写进锁文件，保证换机器、换时间装出来的依赖完全一样。 |
| [结构化日志](../01-traditional-solutions/06-build-test-deliver/03-exception-handling-and-structured-logging.md#核心概念) | 每条日志都是固定字段的键值对，通常是单行 JSON，方便机器检索和统计。 |
| [语义化版本](../01-traditional-solutions/06-build-test-deliver/04-git-branching-and-code-review.md#核心概念) | 用主版本、次版本、修订号来表达兼容性：主版本变了，通常意味着不兼容。 |
| [测试金字塔](../01-traditional-solutions/06-build-test-deliver/05-test-levels-and-acceptance.md#核心概念) | 测试数量的分布建议：底层的单元测试最多，集成测试少一些，端到端测试最少。 |
| [灰度发布](../01-traditional-solutions/06-build-test-deliver/09-cicd-migrations-canary-and-rollback.md#核心概念) | 先把一小部分真实流量切到新版本，用指标对比决定继续放量还是撤回。 |
| [基础设施即代码（IaC）](../01-traditional-solutions/06-build-test-deliver/10-cloud-kubernetes-and-iac.md#核心概念) | 把服务器、网络等基础设施写成可评审、可版本管理的配置文件，交给工具执行，不靠人手动点控制台。 |
| [漂移](../01-traditional-solutions/06-build-test-deliver/10-cloud-kubernetes-and-iac.md#核心概念) | 实际运行状态和配置文件描述的状态不一致，常见原因是有人手工改了线上。 |
| [可观测性](../01-traditional-solutions/07-operate-and-optimize/01-logs-metrics-tracing-and-alerting.md#核心概念) | 只靠系统对外输出的日志、指标、链路这些信号，就能推断内部发生了什么，不用改代码加断点。 |
| [关联标识（Correlation ID）](../01-traditional-solutions/07-operate-and-optimize/02-correlation-id-and-request-tracing.md#核心概念) | 给一次业务请求发的通行证编号，从入口到出口全程不变，用来把散落各处的日志串起来。 |
| [OpenTelemetry](../01-traditional-solutions/07-operate-and-optimize/03-opentelemetry-prometheus-grafana.md#核心概念) | 一套统一的遥测标准加实现，负责产生、采集和传输日志、指标、链路数据。 |
| [SLI](../01-traditional-solutions/07-operate-and-optimize/04-sli-slo-sla-and-error-budget.md#核心概念) | 用监控数据算出的服务质量数值，通常写成“好请求数除以总请求数”。 |
| [SLO](../01-traditional-solutions/07-operate-and-optimize/04-sli-slo-sla-and-error-budget.md#核心概念) | 给 SLI 定的内部目标，比如“一个月内 99.9% 的请求成功”。它是工程目标，不是对客户的合同承诺。 |
| [错误预算](../01-traditional-solutions/07-operate-and-optimize/04-sli-slo-sla-and-error-budget.md#核心概念) | 1 减去 SLO，就是这段时间里“允许坏多少次”的额度。额度烧完，就该停下来修稳定性。 |
| [燃尽率](../01-traditional-solutions/07-operate-and-optimize/04-sli-slo-sla-and-error-budget.md#核心概念) | 当前错误率除以预算允许的错误率，表示预算消耗得多快。大于 1 就是在超支。 |
| [容量模型](../01-traditional-solutions/07-operate-and-optimize/05-performance-capacity-and-cost.md#核心概念) | 把业务峰值、单次请求耗时和资源上限放在一起算，得出系统能扛多少、瓶颈在哪。 |
| [复盘](../01-traditional-solutions/07-operate-and-optimize/06-incident-response-and-postmortem.md#核心概念) | 事故结束后的结构化回顾：时间线、影响、促成因素、改进项。目的是改系统，不是追责。 |
| [Token](../02-ai-solutions/01-ai-foundations/03-transformer-and-llm-intuition.md#核心概念) | 模型处理文本和计费的最小单位。一个汉字可能是一到两个 token，具体怎么切由分词器决定。 |
| [上下文窗口](../02-ai-solutions/01-ai-foundations/04-tokens-context-and-attention.md#核心概念) | 一次请求里输入加输出的 token 总量上限，超过就要截断或摘要。易混：提示词只是输入的一部分，窗口算的是总量。 |
| [温度](../02-ai-solutions/01-ai-foundations/05-generation-sampling-and-nondeterminism.md#核心概念) | 控制随机性的参数：调低更稳定、更保守，调高更发散、更有创意。 |
| [Top-p（核采样）](../02-ai-solutions/01-ai-foundations/05-generation-sampling-and-nondeterminism.md#核心概念) | 只在累计概率达到 p 的那一小撮候选里抽样，砍掉低质量的长尾选项。 |
| [幻觉](../02-ai-solutions/01-ai-foundations/06-hallucination-and-knowledge-boundaries.md#核心概念) | 模型说得很流畅，但内容与事实不符，或者与这次给它的材料对不上。 |
| [Embedding](../02-ai-solutions/01-ai-foundations/07-embedding-rerank-and-multimodal-models.md#核心概念) | 把文本变成一串数字向量，语义越接近，向量距离越近，方便做相似度检索。 |
| [重排（Rerank）](../02-ai-solutions/01-ai-foundations/07-embedding-rerank-and-multimodal-models.md#核心概念) | 先粗召回一批结果，再用更强的模型重新打分排序，把真正相关的顶上来。 |
| [数据出域](../02-ai-solutions/01-ai-foundations/09-cloud-open-source-local-and-hybrid.md#核心概念) | 数据离开组织可控的网络或合规边界。只要发到外部服务，就算出域。 |
| [AI 适配度](../02-ai-solutions/02-discovery-and-requirements/01-identify-ai-suitable-problems.md#核心概念) | 这个任务交给 AI 后，剩下的风险组织能不能接受。问的不只是“AI 能不能做”，还有“值不值得做”。 |
| [自动化等级](../02-ai-solutions/02-discovery-and-requirements/01-identify-ai-suitable-problems.md#核心概念) | 同一个任务，AI 可以只给建议、生成草稿，或者直接执行。等级越高越省事，风险也越大。 |
| [混合编排](../02-ai-solutions/02-discovery-and-requirements/02-rules-search-ml-or-llm.md#核心概念) | 不硬塞给一个大模型：规则归规则、检索归检索，确实需要理解语言时才交给 LLM。 |
| [人在回路](../02-ai-solutions/02-discovery-and-requirements/03-user-tasks-and-human-in-the-loop.md#核心概念) | 关键判断仍然由人确认，系统只负责出建议或草稿。 |
| [PoC（概念验证）](../02-ai-solutions/02-discovery-and-requirements/06-poc-pilot-and-production.md#核心概念) | 用最小成本回答“技术上到底行不行”，参与者一般是内部人员，不追求好用。 |
| [试点（pilot）](../02-ai-solutions/02-discovery-and-requirements/06-poc-pilot-and-production.md#核心概念) | 在真实流程里让一小批真实用户使用，验证“值不值得继续投入”。 |
| [指令层级](../02-ai-solutions/03-model-and-prompt/02-instruction-hierarchy-and-system-prompts.md#核心概念) | 多种指令冲突时谁优先：系统和开发者高于用户输入，用户输入高于检索到的资料。 |
| [System Prompt](../02-ai-solutions/03-model-and-prompt/02-instruction-hierarchy-and-system-prompts.md#核心概念) | 开发者写给模型的角色设定、行为边界和冲突处理规则，终端用户看不到。 |
| [Few-shot](../02-ai-solutions/03-model-and-prompt/03-zero-shot-few-shot-and-examples.md#核心概念) | 在提示词里放几个“输入—输出”示例，让模型照着模仿格式和尺度。 |
| [提示词模板](../02-ai-solutions/03-model-and-prompt/04-prompt-templates-and-versioning.md#核心概念) | 带占位符的固定文本，运行时把变量和上下文填进去，再发给模型。 |
| [结构化输出](../02-ai-solutions/03-model-and-prompt/05-structured-output-and-json-schema.md#核心概念) | 要求模型按约定结构（比如 JSON Schema）返回，而不是自由文本，方便程序直接使用。 |
| [流式输出](../02-ai-solutions/03-model-and-prompt/07-streaming-batch-and-async.md#核心概念) | 模型边生成边往外吐字，首字出现得更早，用户感觉没那么卡。 |
| [推理模型](../02-ai-solutions/03-model-and-prompt/08-multimodal-and-reasoning-models.md#核心概念) | 先在内部花大量不可见 token“打草稿”，再给答案的模型。通常更准，也更贵更慢。 |
| [向量索引](../02-ai-solutions/04-rag-and-knowledge/02-vector-index-and-vector-databases.md#核心概念) | 为高维向量专门建立的数据结构，用来快速找到最相近的几条。 |
| [ANN（近似最近邻）](../02-ai-solutions/04-rag-and-knowledge/02-vector-index-and-vector-databases.md#核心概念) | 不保证百分百找到最近的那条，但换来数量级的速度提升，检索场景通常够用。 |
| [片段（chunk）](../02-ai-solutions/04-rag-and-knowledge/04-chunking-and-context-preservation.md#核心概念) | 文档切分后的最小单元，也是入库、向量化和检索的基本单位。 |
| [混合检索](../02-ai-solutions/04-rag-and-knowledge/05-hybrid-search-and-query-rewriting.md#核心概念) | 关键词检索和向量检索同时跑，再把两路结果融合排序，兼顾精确匹配和语义匹配。 |
| [RRF（倒数排名融合）](../02-ai-solutions/04-rag-and-knowledge/05-hybrid-search-and-query-rewriting.md#核心概念) | 一种融合方法：只看各路结果的名次，不看原始分数，把名次取倒数再加权求和。 |
| [查询改写](../02-ai-solutions/04-rag-and-knowledge/05-hybrid-search-and-query-rewriting.md#核心概念) | 把用户的口语化问题改写成更适合检索的查询，但必须保留原话里的关键实体。 |
| [引用（citation）](../02-ai-solutions/04-rag-and-knowledge/07-citations-and-grounded-answers.md#核心概念) | 回答里标出来源位置，让人能点回去核对原文和版本。 |
| [权限感知检索](../02-ai-solutions/04-rag-and-knowledge/08-permission-aware-retrieval.md#核心概念) | 检索前先按调用者能看的范围过滤，而不是先全部查出来再删。 |
| [Graph RAG](../02-ai-solutions/04-rag-and-knowledge/11-graph-rag-and-rag-vs-alternatives.md#核心概念) | 先从文档里抽出实体和关系建成图，再在图上检索，适合需要多跳推理的问题。 |
| [Function Calling](../02-ai-solutions/05-tools-and-agents/01-function-calling-mechanics.md#核心概念) | 模型只输出“想调用哪个工具、参数是什么”，真正的校验和执行由应用侧完成。 |
| [工具描述](../02-ai-solutions/05-tools-and-agents/02-tool-schemas-and-descriptions.md#核心概念) | 写给模型看的工具说明书，直接决定模型会不会选中它、选得对不对。 |
| [Workflow](../02-ai-solutions/05-tools-and-agents/04-workflow-vs-agent.md#核心概念) | 路径由代码写死：先调模型、再查库、再调接口，按固定顺序走。 |
| [Agent](../02-ai-solutions/05-tools-and-agents/04-workflow-vs-agent.md#核心概念) | 路径由模型自己决定：它根据当前情况选下一步用什么工具，直到自己判断可以停。 |
| [自主性预算](../02-ai-solutions/05-tools-and-agents/04-workflow-vs-agent.md#核心概念) | 给 Agent 设的硬上限：最多走几步、能用哪些工具、最多花多少钱。 |
| [审批断点](../02-ai-solutions/05-tools-and-agents/05-state-machines-branches-and-approval.md#核心概念) | 流程走到这里先暂停，把状态存下来，等人点了同意再继续。 |
| [短期记忆](../02-ai-solutions/05-tools-and-agents/07-session-and-memory.md#核心概念) | 一次会话里的对话历史和中间状态，会话结束就没了。 |
| [MCP](../02-ai-solutions/05-tools-and-agents/08-mcp-and-single-vs-multi-agent.md#核心概念) | 一个开放协议，用 JSON-RPC 把外部工具和数据源标准化地接给模型应用。 |
| [沙箱](../02-ai-solutions/05-tools-and-agents/09-tool-reliability-sandbox-and-failure-modes.md#核心概念) | 给工具划出的活动范围：能碰哪些文件、能访问哪些网络、能执行哪些命令。 |
| [请求信封](../02-ai-solutions/06-ai-application-architecture/01-production-ai-request-path.md#核心概念) | 跟着请求一路传的元数据：链路 ID、租户、用户、配置版本等，方便排查和归因。 |
| [适配层](../02-ai-solutions/06-ai-application-architecture/03-model-adapter-and-ai-gateway.md#核心概念) | 把不同供应商五花八门的请求、响应和错误，翻译成自家统一格式的代码层。 |
| [AI 网关](../02-ai-solutions/06-ai-application-architecture/03-model-adapter-and-ai-gateway.md#核心概念) | 模型调用的统一入口，集中管密钥、鉴权、配额、日志和缓存。 |
| [语义缓存](../02-ai-solutions/06-ai-application-architecture/06-versioning-and-caching.md#核心概念) | 用向量相似度判断“这个问题是不是问过”，相似就复用旧答案。省成本，但有答错的风险。 |
| [版本坐标（bundle）](../02-ai-solutions/06-ai-application-architecture/06-versioning-and-caching.md#核心概念) | 把 Prompt、模型、知识库、检索配置打包成一个不可变版本号，方便回滚和对比。 |
| [成本归属](../02-ai-solutions/06-ai-application-architecture/07-rate-limiting-quota-and-cost-attribution.md#核心概念) | 把模型账单按租户、功能、模型和版本拆开，知道钱花在了谁身上。 |
| [混淆代理](../02-ai-solutions/06-ai-application-architecture/08-sso-rbac-and-permission-propagation.md#核心概念) | 高权限服务被低权限用户“借道”，替他执行了本来没资格做的操作。 |
| [黄金集（Golden Dataset）](../02-ai-solutions/07-evaluation-security-governance/02-golden-datasets-and-sample-design.md#核心概念) | 人工确认过正确答案和期望行为的样本集合，用来当评测的标尺。 |
| [忠实度](../02-ai-solutions/07-evaluation-security-governance/03-correctness-relevance-faithfulness.md#核心概念) | 回答里的每条结论都能从这次检索到的材料里推出来，没有自行发挥。 |
| [误差传播](../02-ai-solutions/07-evaluation-security-governance/04-layered-and-end-to-end-evaluation.md#核心概念) | 上游一步出错，下游拿着错的结果继续算，问题越传越大。 |
| [LLM-as-a-Judge](../02-ai-solutions/07-evaluation-security-governance/06-human-review-and-llm-as-a-judge.md#核心概念) | 用另一个模型按评分标准给回答打分，或者做两两比较，替代一部分人工评审。 |
| [回归门禁](../02-ai-solutions/07-evaluation-security-governance/07-regression-ab-and-online-evaluation.md#核心概念) | 评测不达标就拦住发布，不能靠“平均分还行”蒙混过去。 |
| [影子流量](../02-ai-solutions/07-evaluation-security-governance/07-regression-ab-and-online-evaluation.md#核心概念) | 把真实请求复制一份给新版本跑，只记录结果，不返回给用户。 |
| [Prompt Injection](../02-ai-solutions/07-evaluation-security-governance/08-prompt-injection-and-data-exfiltration.md#核心概念) | 把恶意指令伪装成普通内容塞进上下文，诱导模型做不该做的事。 |
| [间接注入](../02-ai-solutions/07-evaluation-security-governance/08-prompt-injection-and-data-exfiltration.md#核心概念) | 攻击载荷不在用户输入里，而是藏在检索文档、评论或工具返回结果中。 |
| [过度代理](../02-ai-solutions/07-evaluation-security-governance/10-excessive-agency-guardrails-and-approval.md#核心概念) | 给模型配了超出任务需要的工具、权限或自主权，一旦出错，破坏面更大。 |
| [Guardrail](../02-ai-solutions/07-evaluation-security-governance/10-excessive-agency-guardrails-and-approval.md#核心概念) | 模型之外的护栏：输入检查、输出检查、工具权限三层，任何一层都不该被绕过。 |
| [托管 API](../02-ai-solutions/08-deploy-operate-optimize/01-hosted-api-self-hosted-and-hybrid.md#核心概念) | 直接用供应商提供的模型和算力，按 token 付费，自己不用管 GPU。 |
| [自建推理](../02-ai-solutions/08-deploy-operate-optimize/01-hosted-api-self-hosted-and-hybrid.md#核心概念) | 在自己的 GPU 上部署推理引擎，模型权重和请求数据都留在自己网络里。 |
| [首 Token 延迟（TTFT）](../02-ai-solutions/08-deploy-operate-optimize/03-concurrency-throughput-and-latency.md#核心概念) | 从发出请求到收到第一个字的时间。它一高，用户就觉得“卡住了”。 |
| [goodput](../02-ai-solutions/08-deploy-operate-optimize/03-concurrency-throughput-and-latency.md#核心概念) | 真正达标的那部分吞吐。易混：吞吐看单位时间处理多少，延迟看单个请求等多久；超时的请求不算有效产能。 |
| [自耗时](../02-ai-solutions/08-deploy-operate-optimize/05-ai-tracing-and-observability.md#核心概念) | 一个 span 的总耗时减去它下面子 span 的耗时，剩下的就是它自己花掉的时间。 |
| [分层排障](../02-ai-solutions/08-deploy-operate-optimize/06-troubleshooting-prompt-retrieval-model-tools.md#核心概念) | 沿着数据流一层层验证：先确定是哪一层出了问题，再往下找根因，别一上来就猜。 |
| [模型漂移](../02-ai-solutions/08-deploy-operate-optimize/08-provider-limits-model-drift-and-runbook.md#核心概念) | 没发新版本，效果却慢慢变差：可能是线上数据变了，也可能是供应商悄悄换了模型。 |
| [Runbook](../02-ai-solutions/08-deploy-operate-optimize/08-provider-limits-model-drift-and-runbook.md#核心概念) | 值班人员能照着做的处置手册：怎么判断严重程度、第一步做什么、什么情况该升级。 |
