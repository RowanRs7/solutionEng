# 架构师交付物

先记住一句话：交付物不是越多越专业，而是让该知道的人在对的时候看到对的信息。下表按“这东西解决什么问题”来记，实际项目只挑本期真正用得上的。

| 交付物 | 用途 |
| --- | --- |
| 需求清单 | 把“要做成什么样”写清楚：目标、范围、优先级和验收条件。开工前先对齐，免得做到一半才发现理解不一致。 |
| 上下文图 | 一张图标出系统边界外有谁：用户在一边，外部系统在另一边，你的系统在中间。用来提前发现漏掉的对接方。 |
| 接口清单 | 逐个写清谁调谁、用什么协议、传哪些数据、失败怎么处理。联调扯皮时，第一份该翻的就是它。 |
| 数据流图 | 追一遍数据从哪来、经过谁、存在哪、最后怎么删。做隐私评估或排查“数据到底去哪了”时用。 |
| 风险登记表 | 把可能出事的事写下来：概率、影响、谁负责、怎么应对。它不是许愿池，需要定期回来看。 |
| ADR | 一次只记一个关键决定：当时有哪些选项、为什么选这个、代价是什么。半年后有人问“为什么这么设计”，直接给他看。 |
| Runbook | 值班人员照着就能做的操作手册：怎么启动、怎么排障、怎么恢复、什么情况该升级。目标是凌晨三点也能按步骤执行。 |
| 现状系统清单 | 盘清“现在已经有什么”：用途、负责人、数据、接口和运行限制。改造老系统前先摸家底。 |
| 现状流程 | 记录真实发生的过程，包括交接、等待、例外和返工，而不是制度上写的那套流程。 |
| 问题日志 | 把事实、假设、冲突、待回答的问题分开记，防止“猜的”被当成“确认的”。 |
| 需求交付包 | 把目标、相关人、现状、用例、需求、范围、验收、风险和决定串成一份可评审的材料，供设计、测试和业务一起看。 |
| 范围基线 | 双方确认过的一版“这期做什么、不做什么”，变更时拿它算影响。它的作用是防止范围悄悄膨胀。 |
