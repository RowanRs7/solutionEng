# Webhook、签名与重放保护

## 为什么需要学习

支付供应商把 `refund.succeeded` 推给晴空商城的退款服务，退款服务随即通知仓库回补库存。第一次推送时仓库超时，接收端返回 500；供应商 30 秒后重推同一事件，这次成功。库存被回补两次，买家收到两笔退款，工单里出现三条矛盾记录。

事故里没有黑客。接收端把“收到消息”当成“收到一次且仅一次消息”：既不验来源，也不记录处理过哪些事件。Webhook 是别人主动打进你的系统，不能假设它只敲一次门，也不能假设敲门的人就是它。

> **核心结论：** Webhook 的可靠性不来自发送方的承诺，而来自接收端的三件事——验签、限时、去重。

## 学习目标

完成本课后，你能够：

- 写出一份 Webhook 契约，固定事件 ID、时间戳、签名头、响应语义与重试策略。
- 用标准库完成 HMAC-SHA256 签名与验签，解释为何签“时间戳 + 原始报文”而非反序列化后的对象。
- 指出三层防护各自的盲区，说明缺一层会漏掉什么。
- 为一次重复投递画出“验签 → 限时 → 去重 → 快速应答 → 异步处理”的判断路径。
- 判断某个集成场景该用 Webhook 还是轮询，并给出理由。

## 业务场景

“晴空商城”的退款流程横跨四个系统，Webhook 是彼此通知的通道：

- 支付供应商在退款成功后推送 `refund.succeeded`，报文含退款单号、订单号与金额。
- 仓库在出库后向订单服务推送 `shipment.created`，失败会重试 12 小时。
- 客服平台订阅 `refund.review_required`，高额退款时弹出人工审核工单。
- 财务要求每条退款都能追溯到“哪次推送、依据哪个签名被接收”。

架构师要定的是契约而非代码：重试几次、间隔多久、签名头叫什么、密钥如何轮换、多久必须返回 2xx、4xx 是否重试。这些不写进接入文档，双方只能凭猜测上线。

## 核心概念

*Webhook* 是发送方在事件发生时向接收方登记的 URL 主动发起 HTTP 请求的集成方式，方向与普通 API 相反，也称“反向 API”。*投递*（delivery）是一次 HTTP 尝试，同一条*事件*（event）可能对应多次投递。

*事件 ID* 是发送方为同一事件生成的稳定标识，重试时不变，是去重唯一依据。*签名*是用共享密钥对报文算出的摘要，接收方重算比对以证明报文未被篡改。*时间戳容忍窗口*允许签名时间与本地时间的最大偏差，超出即拒绝。

*重放攻击*指截获合法请求后原样重发、重复触发副作用。*至少一次投递*保证不丢但可能重复，多数供应商只承诺这一级别。*死信*是重试耗尽仍需人工介入的事件。

三类防护职责互不重叠：

| 手段 | 防住什么 | 防不住什么 | 代价 |
| --- | --- | --- | --- |
| 签名校验 | 伪造来源、报文被篡改 | 合法报文的重复发送 | 需安全下发与轮换密钥 |
| 时间戳窗口 | 时间久远的重放 | 窗口内的快速重放 | 依赖双方时钟大致同步 |
| 事件去重 | 同一事件的任意次重复投递 | 携带新事件 ID 的伪造请求 | 需持久化记录并设保留期 |

**三层必须同时存在。**<u>只验签不去重，窗口内截获的请求可反复触发；只去重不验签，攻击者换个事件 ID 就能绕过。</u>

## 工作原理

一次可用的 Webhook 交互按下面的顺序发生：

1. **订阅与密钥协商**：接收方登记回调 URL，双方通过安全渠道约定密钥 `whsec_...`、签名头名称与算法。
2. **事件落库后再推送**：发送方先写入业务事实，再生成事件 ID，避免“推送成功但事务回滚”的悬空事件。
3. **构造报文**：紧凑 JSON，含事件 ID、类型、创建时间与业务数据；<u>接收端必须对原始字节验签，不能反序列化后重新序列化</u>，空格、键序与转义差异都会让摘要对不上。
4. **计算签名**：`HMAC-SHA256(secret, timestamp + "." + body)`，写入形如 `t=1760832000,v1=9f2c...` 的头部。时间戳进入被签内容，无法被单独篡改。
5. **投递**：发送方设短超时（常见 5–10 秒），2xx 成功；4xx 多为永久失败，5xx 与超时进入重试队列。
6. **接收方验签**：取出时间戳与摘要，先判时间差是否在窗口内，再重算并用恒定时间函数比对。
7. **去重判定**：把事件 ID 写入带唯一约束的表或 `SETNX` 键；写入成功是首次处理，冲突则直接返回 2xx。
8. **快速应答后异步处理**：接收端只做校验与入队，立即返回 202；回补库存、生成工单交给消费者。
9. **重试、死信与对账**：失败按指数退避重试（1 分钟、5 分钟、30 分钟、2 小时，累计 24 小时），耗尽入死信队列由运维按事件 ID 重放；每日与对方事件列表对账补拉，而不是假设“没收到就是没发生”。

两个易错点：<u>时效判断应放在摘要计算之前</u>；去重必须放在业务副作用之前。

## 架构与选型

| 场景 | 是否适用 Webhook | 理由 |
| --- | --- | --- |
| 支付、退款、发货等秒级状态变化 | 适用 | 事件驱动、延迟低，无需空转查询 |
| 对端只提供查询接口 | 不适用 | 只能轮询，或由自建适配层转成内部事件 |
| 接收方在内网、无公网入口 | 需改造 | 需反向隧道、队列中转或改为拉取 |
| 事件量极大且可容忍分钟级延迟 | 谨慎 | 高峰时回调会成为对方压力源，常改为批量拉取 |
| 要求严格有序、恰好一次 | 不适用 | 只承诺至少一次且可能乱序，需业务层补齐 |

三个取舍：

- **同步处理还是先应答再异步**：同步简单，但把接收方耗时绑进对方超时预算，容易触发重试风暴；推荐“校验 + 入队 + 返回 202”。
- **共享密钥 HMAC 还是双向 TLS**：HMAC 成本低、可跨云，但密钥泄露即可伪造；mTLS 更强，但证书轮换对中小供应商是负担。
- **推还是拉**：推送延迟低但把可用性风险转移给接收方；拉取节奏可控，代价是延迟与空查询成本。

<u>不要自创“密钥拼进 URL”或“MD5(密钥+报文)”这类方案</u>：前者把密钥写进访问日志，后者不是标准 MAC 构造。

## 最小示例

问题：给定一条事件报文，验证接收端能否区分首次投递、窗口内重放、超窗重放、报文篡改、签名伪造。环境为 Python 3.8+，只用标准库，不访问网络。

```python
import hashlib
import hmac
import json
import time

SECRET = b"whsec_demo_do_not_use_in_production"  # 真实环境读自密钥管理服务，禁止硬编码
TOLERANCE = 300  # 容忍窗口 5 分钟，覆盖时钟偏差与网络延迟


def sign(secret, ts, body):
    """签名内容 = 时间戳 + '.' + 原始报文，时间戳因此无法被单独篡改。"""
    digest = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return f"t={ts},v1={digest}"  # 逗号分隔，便于将来并存 v2 算法


def verify(secret, header, body, now=None):
    """返回 ok / malformed / stale / bad_signature，便于分别监控告警。"""
    parts = dict(p.split("=", 1) for p in header.split(",") if "=" in p)
    if not {"t", "v1"} <= parts.keys():
        return "malformed"  # 头格式不符合契约，直接拒绝
    try:
        ts = int(parts["t"])
    except ValueError:
        return "malformed"  # 时间戳不可解析，按畸形请求处理
    now = time.time() if now is None else now
    if abs(now - ts) > TOLERANCE:
        return "stale"  # 先判时效：过期报文不做 HMAC 计算
    expected = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, parts["v1"]):
        return "bad_signature"  # 恒定时间比较，不泄露前缀匹配信息
    return "ok"


seen = set()  # 真实系统用带唯一约束的表或 Redis SETNX


def first_seen(event_id):
    if event_id in seen:
        return False  # 已登记：重复投递
    seen.add(event_id)  # 首次登记，后续同 ID 一律短路
    return True


def main():
    payload = {
        "id": "evt_1001",  # 事件 ID：重试时不变，去重唯一依据
        "type": "refund.succeeded",  # 类型：决定处理分支，不参与去重
        "created": 1760832000,
        "data": {"refund_id": "rf_8801", "amount": 19900},
    }
    body = json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()  # 与发送方一致
    now = 1760832000
    header = sign(SECRET, now, body)
    cases = [
        ("首次投递", header, body, now),
        ("窗口内重放", header, body, now + 60),  # 签名有效，只能靠去重拦住
        ("超窗重放", header, body, now + 301),  # 靠时效拦住
        ("报文被改额", header, body.replace(b"19900", b"99900"), now),
        ("伪造签名", header.replace("v1=", "v1=0"), body, now),
    ]
    for name, hdr, raw, at in cases:
        verdict = verify(SECRET, hdr, raw, at)
        if verdict != "ok":
            print(f"{name} -> {verdict} -> 丢弃")
        elif first_seen(payload["id"]):
            print(f"{name} -> ok -> 处理")
        else:
            print(f"{name} -> ok -> 幂等跳过")


if __name__ == "__main__":
    main()
```

运行 `python3 webhook_guard.py`，预期输出：

```text
首次投递 -> ok -> 处理
窗口内重放 -> ok -> 幂等跳过
超窗重放 -> stale -> 丢弃
报文被改额 -> bad_signature -> 丢弃
伪造签名 -> bad_signature -> 丢弃
```

流程是：构造报文 → 签名 → 逐案调用 `verify` → 验签通过才进入去重 → 由去重结果决定处理还是跳过。三个关键设计：时间戳进入签名内容；时效判断先于摘要计算；去重先于业务副作用。第二行最能说明问题——<u>签名完全正确的请求同样可能是有害的重复请求</u>。

3. 注释掉 `first_seen(...)` 的调用，运行并记录“窗口内重放”的结果。
4. 把 `body` 改为 `json.dumps(payload).encode()`（默认带空格），签名不变，观察验签结果。
5. 把 `hmac.compare_digest` 换成 `==`，确认输出不变，再思考这在生产中是退化还是等价。

### 预期结果

把五个用例写成断言，例如 `assert verify(SECRET, header, body, now=now + 301) == "stale"`，运行 `python3 -m unittest` 全部通过，即三层防护都在生效。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 全部验签失败，对方坚称签名正确 | 对反序列化结果重新序列化再验签，字节已变 | 用 `curl -d @body.json` 保存原始报文比对摘要 | 保留原始请求体，用原始字节验签 |
| 偶发验签失败，集中在高峰 | 时钟漂移或窗口过窄，报文在队列停留过久 | 查 NTP 状态与报文 `created` 时间 | 对齐时钟，窗口匹配对方重试间隔 |
| 同一退款回补两次库存 | 未按事件 ID 去重，或去重写在业务之后 | 查去重表有无该 `event_id` 与库存变动时间 | 去重前置，为事件 ID 加唯一约束 |
| 对方持续重推，日志全是 500 | 接收端同步调用下游，超时后才返回 | 看响应耗时分布与对方重试记录 | 校验后立即返回 202，异步处理 |
| 重试耗尽后事件静默丢失 | 无死信队列、无对账任务 | 比对发送方事件列表与本地处理记录 | 建死信队列与每日对账补拉 |
| 4xx 也被反复重推 | 契约未区分永久失败与临时失败 | 查对方文档中 4xx 的重试语义 | 契约写明 4xx 不重试，先修数据 |

## 安全与生产注意事项

**<u>只验签不校验时间戳和事件 ID，等于把一次性凭证变成永久通行证。</u>**攻击者截获一份合法报文就能无限重放，在退款场景下直接造成重复打款。缓解：三层同时上线，为 `stale`、`bad_signature` 与重复投递设独立监控指标。

**<u>把共享密钥写进代码仓库、镜像或前端，泄露后任何人都能伪造合法推送。</u>**后果是伪造“退款成功”触发真实打款，日志毫无异常。缓解：密钥存密钥管理服务或环境变量、按环境隔离、支持新旧双密钥并存轮换，并审计密钥读取。

**<u>在返回 2xx 之前完成全部下游调用，会让一次事件被放大成多次业务操作。</u>**发送方通常 5–10 秒后判超时并重试，慢处理会同时收到多份同一事件。缓解：接收端只做“验签、限时、去重、入队、返回 202”，处理放消费者且消费者自身也幂等。

另有两条实践：日志只记事件 ID 与摘要前缀，<u>不记金额、账号与密钥</u>；去重记录保留期不短于对方最大重试时长（常见 24 小时到 7 天）。

## 本课总结

- **Webhook 是别人主动打进你的系统，可靠性由接收端三层防护决定：验签、限时、去重。**
- 签名要覆盖“时间戳 + 原始报文”，验签必须用原始字节与恒定时间比较。
- 时间戳窗口解决“旧报文重放”，事件去重解决“新投递重复”，两者不能互相替代。
- 至少一次投递意味着重复是常态，业务处理必须幂等，去重要前置到副作用之前。
- 接收端应“快速校验、立即应答、异步处理”，并用死信队列与每日对账兜住最后一公里。

## 思考题

支付供应商只提供“查询退款状态”接口，不提供 Webhook，且查询有每分钟 60 次限额。业务要求退款结果 3 分钟内反映到客服工单，财务要求“任何一笔退款都不能漏”。请设计组合方案：推送与拉取各承担什么职责、幂等键取自哪里、限流如何退避，以及你如何证明“没有漏”。

参考思路：由自建适配层把查询结果转换为内部事件，复用同一套验签与去重逻辑；或采用带游标的增量轮询，以退款单号为幂等键，用指数退避加 `Retry-After` 处理 429，并用“最后成功游标 + 每日全量对账”证明没有漏。评判重点是是否区分“延迟”与“丢失”、是否给出可验证的对账证据。

## 答案与解析

1. **错。** 验签只证明报文来自持密钥方且未被篡改，不能证明这是第一次投递；窗口内的合法报文同样可被重放。
2. **B。** 时间戳进入摘要才使其不可被单独篡改，从而支撑时效判断。A 漏掉时间戳完整性；C 的 URL 不承载业务事实；D 覆盖不到报文内容。
3. **C。** 去重命中说明该事件已处理或正在处理，重复执行正是要避免的副作用。A 会放大重试；B 造成重复操作；D 会让对方判为失败并重试。
4. **B。** 窗口过短会把“重试间隔 + 队列延迟 + 时钟偏差”一并判为过期。A 恰好相反；C 与时效无关；D 与去重增长无关。
5. **错。** 至少一次只保证不丢，允许重复；“只处理一次”靠接收端幂等，而不是发送方承诺。
6. 参考：一是接收端同步完成出库调用，超过对方超时阈值引发重试，应改为“校验 + 入队 + 返回 202”；二是出库记录缺少以事件 ID 为键的唯一约束、去重写在业务之后，应去重前置并加唯一索引。修复顺序：先去重（止血），再改异步应答，最后补对账与死信重放。库存只扣一次说明扣减路径另有唯一约束，恰好掩盖了问题，<u>不能因为“库存看起来对”就认为回调处理正确</u>。

动手实验参考：步骤 2 中“窗口内重放”由 `幂等跳过` 变为 `stale`，结论是窗口需匹配对方的合理重试间隔；步骤 3 中同一事件被处理两次，说明签名有效不等于只能处理一次；步骤 4 得到 `bad_signature`，说明验签对象是原始字节；步骤 5 输出不变但安全性下降，因为 `==` 的提前返回会泄露前缀匹配长度。
