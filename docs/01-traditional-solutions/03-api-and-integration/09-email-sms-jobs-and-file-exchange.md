# 邮件、短信、定时任务与文件交换

## 为什么需要学习

晴空商城的退款流程有四条不显眼的通道：退款通知邮件、到账短信、每晚的对账任务、每小时推给仓库的发货文件。它们不承载主流程，却决定主流程可信与否。

上周四它们同时出事：短信供应商返回 429 后重试代码又补发三次，买家两分钟内收到四条“退款已到账”；邮件退信率升到 12%，因为换了发件域名没配 SPF；两个对账任务都排在 02:00，其中一个超时退出，次日才发现少一天数据；SFTP 上传到 60% 断网，仓库读到半截 CSV，生成 300 条金额为零的发货单。

> **核心结论：** 这四条通道都是“尽力而为”的——提交不等于送达，触发不等于执行，文件落地不等于内容完整；架构师要为每种不确定性配一个可验证的确认手段。

## 学习目标

完成本课后，你能够：

- 区分*提交*、*送达*与*退信*，并说出邮件与短信各自通过什么渠道拿到回执。
- 为硬退信、软退信、投诉和 429 限频分别写出处理动作，并解释重试为何必须有上限。
- 写出定时任务的执行窗口、幂等键、错峰参数与漏跑检测方法。
- 说出 SFTP 交换中临时后缀、校验和、原子改名、回执四步各挡住哪种事故。

## 前置知识

- 知道 HTTP 状态码的基本含义：4xx 多为永久失败，5xx 与超时多为临时失败。

## 业务场景

“晴空商城”的退款流程要喂饱四条通道，约束各不相同：

- **邮件**：审核通过、到账各发一封，买家会截图给客服，内容须与订单状态一致。
- **短信**：提醒与验证码走运营商通道，签名和模板必须提前报备，单号码有每日上限。
- **定时任务**：02:00 生成退款对账表，每小时打库存快照，数据库在 01:30–02:30 备份。
- **文件交换**：仓库 WMS 只接受 SFTP 上传的 `shipment-YYYYMMDD.csv`；银行回单只能走邮件附件。

财务只提一句话：“任何一笔退款，我都要能拿出‘通知已发出、对方已收到’的证据。”它把状态确认、失败重试、何时执行、文件完整性绑在一起。

## 核心概念

通知类通道的状态不是布尔值，而是一条链。*提交*（submitted）指供应商接受请求并给出消息 ID；*送达*（delivered）指对方服务器或网关确认收下；*退信*（bounce）指投递失败；邮件还有*投诉*（complaint）。*硬退信*是永久失败（如 `550 5.1.1`），*软退信*是临时失败（如邮箱满）。硬退信地址必须进入*抑制列表*，否则每发一次都在损耗发送域声誉。

邮件能否进收件箱取决于发件域的三条 DNS 记录：*SPF* 声明哪些服务器可代发，*DKIM* 给邮件签名，*DMARC* 规定两者都不通过时怎么办。<u>三者缺一，别人就能用你的域名发钓鱼邮件。</u>短信的约束是*签名与模板报备*；*状态报告*（DLR）异步回传，可能延迟或丢失；超配额或限频都返回 `429`。

*定时任务*由*调度器*按时间规则触发，如 `0 2 * * *`；*执行窗口*是允许运行的时间范围；*水位*记录“处理到哪个时间点”；*漏跑*指该跑的一次没成功且无人发现；*错峰*是把同时触发的任务分散开。

*文件交换*是约定目录、文件名与格式，用文件而非 API 传数据。*SFTP* 是运行在 SSH 之上的文件传输协议，<u>不是“FTP 加个加密”，也不是 FTPS</u>。*落地区*是交换目录，也是信任边界：对面放进来的一切都会被程序读取。*交换契约*写清文件名规则、编码、分隔符与完成信号；*校验和*让接收方重算摘要判断完整性。

| 对比项 | 邮件 | 短信 |
| --- | --- | --- |
| 送达确认 | 供应商回写 `delivered`、`bounced`、`complained` | 运营商状态报告，可能延迟或丢失 |
| 典型延迟 | 秒级到数分钟 | 秒级到数分钟，高峰波动更大 |
| 单条成本 | 极低 | 按条计费，重复发送直接产生费用 |
| 内容自由度 | 高，可带 HTML 与附件 | 极低，必须用已报备模板 |
| 主要失败信号 | 硬退信、投诉、进垃圾箱 | 空号、停机、429、模板不符 |

## 工作原理

一条通知从业务事务走到“已送达”：

1. **同事务落任务**：审核通过时在同一事务里写两条通知任务，而不是直接调外部接口——否则回滚后通知已发。
2. **抢占幂等键**：用 `(业务类型, 业务主键, 通道)` 插入唯一约束表，冲突即跳过。
3. **渲染模板**：变量取自业务数据；短信必须用已报备模板，变量个数与顺序要匹配。
4. **提交**：拿到消息 ID，状态是 `submitted`，<u>只证明对方收下请求，不证明用户收到</u>。
5. **回执回写**：`delivered`、`bounced`、`complained` 或状态报告写回本地，回执自身也要幂等。
6. **分流与兜底**：硬退信进抑制列表；软退信重试 3 次后转人工；`429` 读 `Retry-After` 退避加抖动，超上限降级为站内信；每日与供应商对账。

再看定时任务与文件交换：

1. **调度触发**：cron 到点触发，但每个实例都会收到信号，多实例部署天然重复。
2. **抢锁**：取分布式锁，抢不到就退出并记“已被他人执行”，这不是错误。
3. **确定窗口**：区间是 `[上次水位, now - 安全滞后)`，滞后几分钟等未提交事务落定。
4. **分片与幂等**：按订单号切片，幂等键是 `任务名 + 窗口起点 + 分片号`。
5. **推进水位**：结果与水位同事务提交。<u>先提交结果再推进水位</u>会漏数；反过来只重复，而重复被幂等键吸收。
6. **原子落地与校验**：写 `.part` → `fsync` → 算摘要 → `os.replace`；仓库只在“正式文件 + 校验和匹配”时解析并回写 `receipt`；看门狗比较“上次成功 + 周期”与当前时间，超阈值告警并补偿——任务失败不致命，没人知道才致命。

## 架构与选型

| 通道 | 适用场景 | 不适用场景 | 判断依据 |
| --- | --- | --- | --- |
| 邮件 | 通知、对账单、需留档的长文本 | 秒级触达、确认已读 | 允许分钟级延迟且要留痕 |
| 短信 | 验证码、强提醒、到账通知 | 长文本、批量营销、含敏感数据 | 必须触达且内容极短 |
| 定时任务 | 对账、报表、清理、批量同步 | 事件驱动的实时动作 | 数据按时间批量产生 |
| SFTP 文件 | 大批量结构化数据、老系统对接 | 双向低延迟、逐条确认 | 对端无 API 或单次数据量大 |
| API 实时调用 | 即时结果与逐条状态 | 百万行批量、对端限流严格 | 延迟敏感且调用量可控 |

- **直接调用还是通知任务表**：直接调用代码少，但回滚与超时会让状态不一致；任务表换来“发不发得出去”与“业务是否成功”解耦。
- **API 还是文件**：API 逐条确认、可重放，但受限流约束；文件吞吐高、对端改造小，但延迟以小时计。常见折中是白天走 API、夜间用文件对账。
- **错峰还是缩短任务**：缩短执行时间治标，错峰治本。哈希能削掉峰值，但<u>只保证分布大致均匀，不保证最小间隔</u>；下游要硬间隔时改用“等距排布 + 抖动”。

## 最小示例

问题：一段标准库脚本演示三件事——限频时怎么退避、8 个对账任务怎么摊进 1 小时、CSV 怎么做到“要么不出现，要么完整出现”。环境为 Python 3.8+，只写本地目录。

```python
"""三个通道各取一个最小动作：退避、错峰、原子落地。只用标准库。"""
import hashlib
import os

OUT = "/tmp/delivery_demo"  # 生产中由 SFTP 服务端持有


def backoff_plan(codes, base=2, cap=60):
    """按状态码序列算每次尝试前的等待秒数。"""
    plan, wait = [], 0
    for attempt, code in enumerate(codes, start=1):
        plan.append((attempt, code, wait))
        if code in (200, 400):                     # 成功与永久失败都停止
            break
        wait = min(cap, max(wait * 2, base))       # 429 / 5xx 指数退避，且必须封顶
    return plan


def spread(window, buckets):
    """把任务按哈希摊进 window 秒，返回排序后的偏移。"""
    out = []
    for i in range(buckets):
        digest = hashlib.sha256(f"reconcile:{i}".encode()).digest()
        out.append(int.from_bytes(digest[:4], "big") % window)  # 固定偏移，可复现
    return sorted(out)


def publish(dirpath, name, rows):
    """先写 .part，再算摘要，最后原子改名。"""
    final = os.path.join(dirpath, name)
    part = final + ".part"
    body = ("\n".join(rows) + "\n").encode("utf-8")  # 编码与行尾即契约
    with open(part, "wb") as handle:
        handle.write(body)
        handle.flush()
        os.fsync(handle.fileno())                    # 先落盘再改名，避免断电留下空文件
    digest = hashlib.sha256(body).hexdigest()
    os.replace(part, final)                          # 同文件系统内 rename 原子
    with open(final + ".sha256", "w", encoding="utf-8") as handle:
        handle.write(f"{digest}  {name}\n")          # 让接收方独立验证，而非相信"文件存在"
    return final, digest


def main():
    print("1) 退避：429 -> 429 -> 500 -> 200")
    for attempt, code, wait in backoff_plan([429, 429, 500, 200]):
        print(f"   第{attempt}次 状态={code} 等待={wait}s")
    offsets = spread(3600, 8)
    gaps = [b - a for a, b in zip(offsets, offsets[1:])]
    print(f"2) 错峰偏移(s)={offsets}")
    print(f"   最小间隔={min(gaps)}s，全堆在 02:00 则为 0s")
    path, digest = publish(OUT, "shipment-20261019.csv", ["order_id,qty", "1001,2", "1002,1"])
    print(f"3) 落地={os.path.basename(path)} 摘要={digest[:12]}...")
    print(f"   目录={sorted(os.listdir(OUT))}")


if __name__ == "__main__":
    os.makedirs(OUT, exist_ok=True)
    main()
```

运行 `python3 delivery_guard.py`，预期输出：

```text
1) 退避：429 -> 429 -> 500 -> 200
   第1次 状态=429 等待=0s
   第2次 状态=429 等待=2s
   第3次 状态=500 等待=4s
   第4次 状态=200 等待=8s
2) 错峰偏移(s)=[37, 679, 766, 1292, 1789, 1915, 2650, 3403]
   最小间隔=87s，全堆在 02:00 则为 0s
3) 落地=shipment-20261019.csv 摘要=2823caebca02...
   目录=['shipment-20261019.csv', 'shipment-20261019.csv.sha256']
```

三段输出对应三个承诺：`200` 与 `400` 都停，区别是成功与永久失败；同一任务每次落在同一偏移，87 秒是实际分布而非设计保证；落地段用 `.part` 加原子改名，并用独立文件公布摘要。

## 动手实验

### 前置条件

本机有 `python3`（3.8+）与可写目录；不需要邮件服务商、短信通道、SFTP 主机或账号。

### 步骤

1. 把上面的代码保存为 `delivery_guard.py`，运行一次，核对输出与“预期输出”一致。
2. 把 `[429, 429, 500, 200]` 改为 `[400, 200]`，观察只尝试一次。
3. 把 `cap` 改为 `5` 再运行，观察最后一次等待被压到 5 秒。
4. 把 `spread(3600, 8)` 改为 `spread(600, 8)`，记录最小间隔的变化。
5. 进入 `/tmp/delivery_demo` 执行 `shasum -a 256 -c shipment-20261019.csv.sha256`，再把 CSV 截断 10 字节重跑。

### 预期结果

步骤 1 输出三段、等待为 0/2/4/8 秒；步骤 2 只输出 `第1次 状态=400 等待=0s`；步骤 3 最后一次等待由 8 变 5；步骤 4 最小间隔缩小，说明窗口越窄错峰空间越小；步骤 5 首次 `OK`，截断后 `FAILED`。

### 验证方法

把关键行为写成断言，例如 `assert backoff_plan([400, 200]) == [(1, 400, 0)]`，用 `python3 -m unittest` 跑通即三个机制都在生效。

### 清理方法

删除 `delivery_guard.py`、`__pycache__` 与 `/tmp/delivery_demo`。实验不连真实短信通道、不写远端 SFTP；若改过目录，删除前确认是本机临时路径。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 买家说没收到，系统显示“已发送” | 把提交当送达，未采集回执 | 查该消息有无 `delivered` 事件 | 补回执回写，界面区分“已提交/已送达” |
| 同一号码连收多条相同短信 | 无幂等键，重试未去重 | 按业务主键查任务表有无重复行 | 加唯一约束，按幂等键抢插 |
| 收到 429 后疯狂重试、费用翻倍 | 无退避、无上限、忽略 `Retry-After` | 看日志中相邻重试的时间间隔 | 指数退避加抖动，设上限并降级 |
| 定时任务日志出现两遍 | 多实例都执行，缺分布式锁 | 比对不同实例的开始时间 | 加锁与幂等键，抢不到锁即退出 |
| 仓库读到半截 CSV、金额为 0 | 边写边传，无临时后缀与校验和 | 检查有无 `.part`、`.done` 与摘要 | 原子落地、校验和、完成标记三件套 |

## 安全与生产注意事项

**<u>在邮件正文、短信模板或未加密附件里放完整卡号、身份证号与退款明细，等于把敏感数据永久留在第三方通道。</u>** 内容会进入供应商日志与收件人邮箱，事后无法撤回。缓解：正文只放“尾号 + 金额 + 站内链接”，明细跳到需登录页面；确需附件时用加密压缩包并分渠道发口令。

**<u>SFTP 用共享账号加永久密钥、落地区可执行或可覆盖，一次密钥泄露就能读走全部对账文件，或替换成伪造文件。</u>** 交换目录常被当作可信输入，换掉一个 `settlement.csv` 就能改动结算金额。缓解：一系统一账号、轮换密钥、`chroot` 限目录、落地区只给读写不给执行、校验主机密钥指纹。

**<u>定时任务无锁且无幂等键时会重复执行，通知、短信与对账表都会成倍放大。</u>** 短信按条计费，重复对账可能生成重复付款指令。缓解：抢锁、幂等键、最长执行时间，并告警“同一窗口被执行两次”。

另需两条控制：发件域配齐 SPF、DKIM、DMARC 并盯报告；日志里手机号与邮箱脱敏，只留消息 ID 与哈希标识。

## 本课总结

- **提交、送达、退信是三个状态**，把“已发送”当“已收到”是这类事故的共同起点。
- 硬退信进抑制列表、软退信有限重试、投诉立即处理、`429` 退避并降级，四条动作缺一不可。
- 定时任务靠三件套站住：**抢锁防重复、幂等键防副作用、水位与看门狗防漏跑**。
- 文件完整性由“.part + 校验和 + 原子改名 + 回执”保证，而不是“文件出现在目录里”。
- 错峰能削掉峰值，但只做哈希不保证最小间隔；要硬间隔时用等距排布加抖动。

## 思考题

财务要求“任一笔退款通知都要有证据”，但短信供应商只保留 7 天状态报告，业务又要求 98% 的通知 5 分钟内触达。请设计证据链：本地留哪些记录、回执丢失如何证明、指标怎么度量、通道整段不可用时退款是否暂停。

参考思路：证据分层——本地任务表记录“何时、向谁、哪个模板、由哪条事件触发”，供应商侧记录消息 ID 与提交时间，回执表记录状态与到达时间，并每日归档明细以越过 7 天保留期。回执丢失不等于未送达，可用“发送记录 + 明细对账 + 用户侧行为”组合证明，并约定哪一级可对外解释。指标要写清分母与起算点，否则 98% 无法验收。通道不可用时退款通常不暂停，但通知应降级为站内信加人工外呼。

   A. 节省带宽　B. 让接收方不会读到半截文件　C. 加快对端解析　D. 兼容 Windows 换行
5. 收到 `429` 且响应头为 `Retry-After: 30`，合理做法是？  
   A. 立刻重试直到成功　B. 等约 30 秒并加抖动，超上限后降级　C. 改发三条覆盖　D. 忽略响应继续发送
6. 场景题：夜间对账任务 02:00 执行，某天因备份锁等待 40 分钟后超时退出且无告警；次日财务用缺失数据出了报表。请指出至少三个设计缺陷并排序修复。

## 答案与解析

1. **错。** `200` 只代表供应商接受了请求，是“提交”；送达要等异步回执，回执会丢，所以另有每日对账。
2. **B。** `550 5.1.1` 是“收件人不存在”的永久失败，重试只损耗发送域声誉。A 的退避只适用于临时失败；C 绕过抑制逻辑；D 与结论相反。
3. **B。** 锁决定“谁跑”，幂等键决定“跑两次也不出错”。A 只降低重叠概率；C 与重复无关；D 仍会重复，只是更稀疏。
4. **B。** rename 在同一文件系统内原子完成，目录只有“没有文件”和“完整文件”两态。A 与文件大小无关；C 取决于格式；D 由契约约定。
5. **B。** 遵守 `Retry-After` 是尊重配额，抖动避免所有客户端同一秒恢复，上限保证不烧钱。A 放大限频；C 三倍计费且重复打扰；D 违反配额。
6. 参考：缺陷是锁等待与超时无告警、无水位与看门狗、报表不校验完整性。修复顺序：先加告警与看门狗（让问题可见），再补水位与补偿执行（把数据补回来），最后在出报表前校验记录数、金额合计与日期连续性。<u>只把时间改到 03:00 不解决问题</u>：换个时间照样可能被锁等待拖死。

动手实验参考：步骤 2 只输出一行，说明 `400` 被短路；步骤 3 等待由 8 变 5，验证封顶；步骤 4 窗口缩小后最小间隔变小，说明错峰效果取决于窗口与任务数之比；步骤 5 校验和能区分“文件存在”与“文件完整”。
