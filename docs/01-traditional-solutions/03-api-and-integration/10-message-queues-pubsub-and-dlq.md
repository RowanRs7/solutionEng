# 消息队列、发布订阅与死信队列

## 为什么需要学习

一期版本在同一个请求线程里依次调用仓库回滚、更新工单、发短信、写对账。仓库接口偶发 30 秒超时，客服页面跟着转圈；把仓库调用挪到后台线程后，进程重启丢掉一批回滚指令，商品照常发货，两天后盘点才发现。

引入队列后问题换了一批：消费者重启让同一笔退款处理两次，客户收到两条短信；仓库消费端报错那天消息堆到四十万条，退款延迟六小时；重放积压时顺序又乱，先回滚出库、后确认退款。三个现象对应三条约定：消息确认了吗？失败的去哪了？同一业务键还有序吗？

> **核心结论：** 队列把一次远程调用拆成生产、存储、投递、确认、失败处置五段，每段都要有人负责；"发出去就不用管"只是把丢失变成延迟发现。

## 学习目标

完成本课后，你能够：

- 区分至多一次、至少一次、恰好一次三种投递语义，说出各自成立的前提。
- 为一条消息画出 ack、可见性超时、重试上限、死信队列组成的处置链路，并预测消费者崩溃后的最终状态。
- 判断一个业务该用点对点队列、发布订阅还是分区事件流，并解释分区键与顺序的关系。
- 面对"队列堆积"告警，按顺序给出定位步骤与恢复动作。

## 业务场景

晴空商城退款成功后要扇出四件事，下游可靠性完全不同：

- **仓库回滚出库单**：响应 1–30 秒，超时常见，但重复回滚会把已出库商品重复入库，库存虚增。
- **更新客服工单**：1 分钟内可见即可，允许最终一致，但必须先"退款成功"再关单。
- **退款短信**：供应商限流 200 条/秒，峰值 800 条/秒，宁可延迟不可丢，重复会被投诉。
- **财务对账流水**：一条不丢，按退款单号可逐笔核对，允许延迟到次日。

约束：受理页面不能等下游；退款事件不能丢；同一退款单的副作用不能重复生效；峰值写入是平时 8 倍。

## 核心概念

*消息队列*（message queue）是*生产者*（producer）与*消费者*（consumer）之间的持久缓冲：生产者交出消息即返回，消费者按自己的节奏取走，双方互不知道对方有几个实例。*确认*（acknowledgement，ack）是消费者告诉队列"这条处理完了，可以删"。*可见性超时*（visibility timeout）也叫租约，是交出消息后等确认的期限，<u>它衡量"消费者还活着吗"，不衡量"业务做得对不对"</u>；到期未确认即视为投递失败并*重投*（redelivery）。

*投递语义*描述重复与丢失的取舍：

| 语义 | 机制 | 会丢吗 | 会重吗 | 成立条件 |
| --- | --- | --- | --- | --- |
| 至多一次 | 投递即删除 | 会 | 不会 | 可丢的日志、指标 |
| 至少一次 | 成功后确认，超时重投 | 不会 | 会 | 消费者必须幂等 |
| 恰好一次 | 确认与业务结果同事务 | 不会 | 不会 | 共事务或有可靠去重表 |

<u>多数系统实际是"至少一次投递 + 幂等消费"</u>，对外宣称恰好一次；代价是消费端必须识别重复。

*死信队列*（dead letter queue，DLQ）存放再也无法正常处理的消息：超过重试上限、消息体无法解析、被业务拒绝。它不是回收站，而是**待人工处置的工作清单**。*消息堆积*（backlog）是未消费消息量增长，堆积本身不是故障，<u>增长斜率才是</u>。

*发布订阅*（publish/subscribe）中，生产者把事件发到*主题*（topic），每个*订阅*（subscription）各得一份副本、各自确认。<u>点对点队列一条消息只给一个消费者，发布订阅里每个订阅都拿得到。</u>*分区*（partition）按*分区键*（partition key）把队列切成有序子流：分区内先进先出，跨分区无全局顺序。

| 对比项 | 点对点队列 | 发布订阅 | 分区事件流 |
| --- | --- | --- | --- |
| 一条消息几人拿到 | 一个消费者 | 每个订阅 | 每个消费组 |
| 顺序保证 | 单队列单消费者 | 订阅内有序 | 分区内有序 |
| 消费后是否保留 | 确认即删除 | 确认即删除 | 保留期内可重放 |
| 典型用途 | 任务分发、削峰 | 事件广播 | 审计、重算 |

## 工作原理

以"退款成功 → 仓库回滚出库单"为例：

1. **生产**：状态改为成功后发布 `refund.succeeded`，带 `message_id`、`partition_key`、`trace_id`。发布失败要重试或落待发表，不能只打日志。
2. **存储**：队列写入持久化存储后才返回成功，所有权转给队列。
3. **投递**：队列选一个消费者交出消息，服务端记一条租约，状态变为"在途"。
4. **处理**：消费者执行副作用（调仓库回滚），可能超时或部分成功，所以必须幂等。
5. **确认**：成功后 ack，队列删除消息。<u>确认必须在副作用之后</u>，顺序反了就是"先删证据后干活"。
6. **超时重投**：消费者崩溃或处理超时，租约到期后消息交给别的消费者，重投计数加一。
7. **上限与死信**：重投达上限转死信，附原队列、首次入队时间与最后错误，进入告警、人工判断、修复后重放。
8. **扇出**：同一事件复制到四个订阅、各自确认，<u>短信堆积拖不住财务</u>——这是拆订阅的主要理由。
9. **分区**：同一 `refund-8871` 始终落同一分区，分区内单消费者按序处理，不同退款并行。

可靠性靠两个不同的保险：队列负责"至少送到"，消费者负责"重复也无害"。只做前者会重复扣款，只做后者会丢单。

## 架构与选型

| 选项 | 适用场景 | 不适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 点对点队列（RabbitMQ、SQS 类） | 任务分发、削峰 | 多系统要同时感知同一事件 | 每个下游各发一次 |
| 发布订阅（topic + 多订阅） | 一事件扇出多下游 | 下游少且逻辑简单 | 副本多，重复面变大 |
| 分区事件流（Kafka 类） | 高吞吐、需重放与审计 | 无运维能力、量很小 | 运维复杂、延迟偏高 |
| 数据库表当队列 | 量小、要与业务同库提交 | 高并发、多消费者并行 | 轮询开销、锁竞争 |
| 同步直接调用 | 需即时结果、失败当场告知 | 下游慢、峰值超其容量 | 上游被拖死、无缓冲 |

按顺序问四个问题：

- **一事件给几个下游？** 一个用队列，多个用发布订阅。
- **要重放历史事件吗？** 要则选保留消息的事件流，否则确认即删更省事。
- **顺序要到哪一级？** 只要"同一退款单有序"就用分区键换并行；全局有序只能单分区单消费者，吞吐封顶。
- **失败消息谁处理？** 缺 DLQ、堆积告警和重放脚本的队列，只把问题推迟到更难查的地方。**没有死信处置方案的队列不要上生产。**

## 最小示例

问题：验证"至少一次 + 幂等消费"在消费者失败时的真实行为，以及死信如何产生。环境：Python 3.9+ 标准库。输入：两条消息，一条前两次失败、第三次成功，一条始终失败。输出：重投轨迹与死信清单。

```python
import json
from collections import deque


def make_message(msg_id, key, payload):
    """信封：必须带重投计数，否则进死信后无法判断失败了几次"""
    return {"id": msg_id, "key": key, "attempts": 0, "payload": payload}


class Broker:
    """最小 broker：就绪队列 + 租约 + 死信"""

    def __init__(self, lease_seconds=3, max_attempts=3):
        self.ready = deque()            # 等待投递
        self.inflight = {}              # 在途：id -> [消息, 租约到期时刻]
        self.dlq = []                   # 死信
        self.clock = 0                  # 逻辑时钟，代替真实等待
        self.lease = lease_seconds      # 可见性超时
        self.max_attempts = max_attempts

    def publish(self, message):
        self.ready.append(message)

    def poll(self):
        if not self.ready:
            return None
        message = self.ready.popleft()
        message["attempts"] += 1        # 由 broker 记账，不靠消费者自报
        self.inflight[message["id"]] = [message, self.clock + self.lease]
        return message

    def ack(self, msg_id):
        self.inflight.pop(msg_id, None)  # 只有显式确认才移出在途

    def tick(self, seconds=1):
        self.clock += seconds
        for msg_id, (message, deadline) in list(self.inflight.items()):
            if deadline > self.clock:
                continue
            del self.inflight[msg_id]
            if message["attempts"] >= self.max_attempts:
                self.dlq.append(message)     # 到上限停手，转死信
            else:
                self.ready.append(message)   # 未到上限则重投


def consume_once(broker, handler, done):
    message = broker.poll()
    if message is None:
        return "空闲"
    if message["id"] in done:            # 先查去重表再决定是否执行
        broker.ack(message["id"])
        return f"{message['id']} 已处理过，跳过"
    try:
        handler(message)
    except RuntimeError as exc:
        return f"{message['id']} 失败({exc})，等待重投"  # 故意不 ack
    done.add(message["id"])              # 结果与去重标记应同事务落库
    broker.ack(message["id"])            # 成功才确认
    return f"{message['id']} 成功，已确认"


fail_counts = {"msg-001": 2, "msg-002": 99}   # 可恢复与不可恢复两种失败


def warehouse_handler(message):
    if fail_counts.get(message["id"], 0) > 0:
        fail_counts[message["id"]] -= 1
        raise RuntimeError("仓库接口超时")


broker = Broker(lease_seconds=3, max_attempts=3)
for msg_id in ("msg-001", "msg-002"):
    broker.publish(make_message(msg_id, "refund-8871", {"action": "rollback"}))

done = set()
for second in range(1, 25):
    result = consume_once(broker, warehouse_handler, done)
    broker.tick(1)
    print(f"t={second:02d}s 就绪={len(broker.ready)} 在途={len(broker.inflight)} {result}")
    if not broker.ready and not broker.inflight:
        break

print("死信队列:", json.dumps([m["id"] for m in broker.dlq], ensure_ascii=False))
```

结构分四段：`Broker` 只做入队、带租约投递、超时后决定重投还是进死信；`consume_once` 是消费者骨架，先查去重表，成功后同事务落结果与标记、最后 ack；`warehouse_handler` 注入失败以观察重投；主循环用逻辑时钟推进。

运行 `python3 mq_demo.py`，预期输出（已实际运行核对）：

```text
t=01s 就绪=1 在途=1 msg-001 失败(仓库接口超时)，等待重投
t=02s 就绪=0 在途=2 msg-002 失败(仓库接口超时)，等待重投
t=03s 就绪=1 在途=1 空闲
t=04s 就绪=1 在途=1 msg-001 失败(仓库接口超时)，等待重投
t=05s 就绪=0 在途=2 msg-002 失败(仓库接口超时)，等待重投
t=06s 就绪=1 在途=1 空闲
t=07s 就绪=1 在途=0 msg-001 成功，已确认
t=08s 就绪=0 在途=1 msg-002 失败(仓库接口超时)，等待重投
t=09s 就绪=0 在途=1 空闲
t=10s 就绪=0 在途=0 空闲
死信队列: ["msg-002"]
```

注意两点：`msg-001` 第三次投递才成功，说明重投计数由队列维护、失败不丢消息；`msg-002` 第三次失败后进死信而不再重投，说明**上限必须有，否则毒消息会永远消耗消费者**。

真实队列投递的是信封：

```json
{
  "message_id": "msg-7f3a-0001",
  "event": "refund.succeeded",
  "occurred_at": "2026-10-19T10:12:03Z",
  "partition_key": "refund-8871",
  "idempotency_key": "refund-8871-rollback",
  "attempt": 1,
  "producer": "refund-service",
  "trace_id": "b7c1e0d2",
  "payload": {
    "refund_id": "RF-8871",
    "order_id": "SO-20431",
    "amount_cents": 19900,
    "currency": "CNY"
  }
}
```

每个字段对应一类故障：

- `message_id`：队列内唯一，用作去重表主键与检索键。
- `partition_key`：决定分区，用退款单号保证同单有序。
- `idempotency_key`：下游幂等键，仓库据此判断出库单是否已回滚。
- `attempt`、`trace_id`：区分首次与反复失败，并接回原请求链路。
- `payload`：只放必需的标识与金额，<u>不要放手机号、证件号</u>。

## 动手实验

**前置条件**：Python 3.9+；已把示例保存为 `mq_demo.py`；无需 Docker 或网络。

**步骤一：复现重复**。把 `consume_once` 的去重判断改成永不命中（如 `if False and message["id"] in done:`）再运行。

预期结果：`msg-001` 成功那一刻又被处理一次，日志出现两次"成功，已确认"。验证方法：在 `warehouse_handler` 打印"向仓库发起回滚"，数同一 `id` 出现几次。去重是消费端的责任。

**步骤二：确认提前，观察丢消息**。新增 `consume_ack_first`：`poll` 后立刻 `ack`，再调 handler，并让 handler 抛异常。

预期结果：异常时消息已不在队列，`就绪`、`在途`、死信长度全为 0。这是理解"为什么不能自动确认"最快的方式。

**步骤三：加分区键**。给 `Broker` 加 `partitions = {"refund-8871": deque(), "refund-8872": deque()}`，`publish` 按 `message["key"]` 入队，`poll` 轮转取；投 `refund-8871` 三条、`refund-8872` 两条。

预期结果：`refund-8871` 三条按发布顺序消费，两条流交错但各自有序。验证方法：打印每次消费的 `(key, 序号)`，检查同 key 序号严格递增。

**清理**：`rm mq_demo.py` 及新增临时脚本，恢复示例原状。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 客户收到两条退款短信 | 至少一次投递下消费者未幂等 | 按 `message_id` 统计处理次数 | 用幂等键加去重表，结果与标记同事务提交 |
| 消息消失且无报错 | 自动确认，或先 ack 后处理 | 比对发送数、消费成功数与 DLQ 数 | 改为成功后显式 ack，关闭自动确认 |
| 队列堆积持续增长 | 消费者不足、单条变慢、下游限流 | 看堆积斜率、消费速率与耗时 P99 | 先限流扩容，再排查下游；不要盲目重放 |
| 同一条消息被反复投递 | 处理时间超过可见性超时 | 对比处理耗时与租约，看重投计数 | 调大租约或拆长任务，设重试上限 |
| 同一订单状态顺序颠倒 | 多消费者消费同一队列，或分区键随机 | 查分区键是否为业务主键 | 统一用订单号或退款单号作分区键 |
| 死信堆了几千条无人处理 | 建了 DLQ 但没配告警与处置流程 | 查 DLQ 是否接入监控、有无 owner | 配告警、责任人与每周巡检重放 |

## 安全与生产注意事项

**<u>队列消息会被持久化并复制到多个节点，把手机号、证件号、卡号明文放进消息体，等于把敏感数据复制成第三份"数据库"，且通常没有访问审计。</u>**后果是泄露面扩大、删除请求覆盖不到副本、审计说不清谁读过。缓解：消息体只放标识与金额，PII 留在原系统按需查询；必须携带时加密并设保留期。

**<u>启用自动确认或在处理之前就 ack，会让消费者崩溃时的消息永久消失，而日志看起来"一切正常"。</u>**后果是回滚指令静默丢失、对账缺笔。缓解：显式确认、关闭自动 ack，用"消费成功数 + DLQ 数 + 未确认数"对账并告警。

另外三条同样影响生产：

- **重试必须有上限并落死信**：无上限重投会让毒消息长期占满消费者，形成"看着在消费、实际没进展"的假活状态。
- **发布与消费权限分开**：只有退款服务能发布 `refund.succeeded`；DLQ 只对排查团队可读，避免"清空队列"掩盖问题。
- **积压治理要限速**：重放积压相当于对下游发起流量攻击，需分批、限速，在下游阈值以下运行。

## 本课总结

- **队列把一次调用拆成生产、存储、投递、确认、失败处置五段**，每段有独立的失败模式。
- 至多一次会丢、至少一次会重、恰好一次要事务或可靠去重；生产上普遍是"至少一次 + 幂等消费"。
- **确认必须发生在副作用之后**，可见性超时衡量消费者是否活着，不衡量业务是否正确。
- 重投必须有上限，超过上限进死信；没有 DLQ 告警与重放流程的队列不该上生产。
- 顺序只在分区内成立：用业务主键作分区键，用并行换吞吐、用单分区换全局有序。

## 思考题

财务要求"一条不丢且按退款单号对账"，短信要求"峰值 800 条/秒不能阻塞受理"，仓库要求"同一退款只回滚一次"。请为 `refund.succeeded` 设计拓扑：拆几个主题或队列、用什么分区键、各下游的 ack 语义与重试策略、DLQ 谁负责，并指出哪一处主动接受重复、哪一处放弃全局顺序。

参考思路：按下游独立性拆四个订阅，堆积互不影响；分区键统一用退款单号，同单有序、跨单并行。仓库订阅用至少一次 + 幂等键 `refund-8871-rollback`；短信订阅加令牌桶限流守住 200 条/秒，接受分钟级延迟；财务订阅走事件流保留 7 天便于重放，DLQ 由财务与平台团队共管、按日对账。评估时应检查两条让步是否写出：短信可能重复（靠供应商侧幂等去重），跨退款单不保证先后。

## 小测

1. 至少一次投递下，消费者处理完成、尚未发 ack 时崩溃，会发生什么？  
   A. 消息丢失　B. 消息被重投，可能重复处理　C. 消息进死信　D. 队列回滚业务副作用

2. 单条消息处理需 2 分钟，可见性超时设 30 秒，且未配重试上限。最可能的结果是？  
   A. 正常完成　B. 消息被无限重投，消费者被自己压满　C. 队列自动延长租约　D. 消息立即进死信

3. 点对点队列上跑 5 个消费者，能保证严格按发布顺序处理吗？为什么？

4. 死信队列的主要作用是什么？

5. 场景判断题：支付回调要求同一订单的回调严格按顺序处理且不能丢。三个方案——A. 单队列 + 1 个消费者；B. 单队列 + 8 个消费者；C. 按 `order_id` 分区、每分区单消费者。应选哪个，为什么？选 A 要接受什么代价？

## 答案与解析

1. **B。**ack 未发出，租约到期后队列重投，不丢但会重复。A 错，丢失只发生在先 ack 后处理或自动确认。C 错，未到上限不进死信。D 错，队列不知道业务副作用，也无权回滚事务。
2. **B。**处理时间超过租约，队列每 30 秒就认为消费者失败并重投，原消费者仍在处理，形成叠加。A 错，租约覆盖处理时间才可能完成。C 错，租约不会因忙碌自动延长，需心跳或调大配置。D 错，没有上限时根本不会进死信，这才是危险之处。
3. 不能。并行取消息时投递与完成顺序都不受控，先进先出入队也保不住完成顺序。要保序只能把同一顺序域交给单消费者：单队列单消费者（吞吐封顶），或按键分区、每分区单消费者。
4. 存放无法正常处理的消息、阻止无限重投，并形成可告警、可排查、可重放的清单。它**不负责**修复业务错误，也不是归档库；<u>把 DLQ 当回收站、只看不处置，等于没有死信机制</u>。
5. **C。**它同时满足同订单有序（同键同分区、分区内单消费者）与不丢（至少一次 + 幂等）。B 错，8 个消费者并行必然打乱同一订单顺序，重复风险也上升。A 能保序与不丢，但吞吐被单消费者封顶；选 A 的代价是无法水平扩展，峰值压力全交给积压。

### 动手实验参考

步骤一的关键结论是"去重不能省"：日志里同一 `id` 两次回滚请求，真实系统里就是重复入库。步骤二的验证点是三个集合同时为空，说明 ack 提前后消息没有副本。步骤三的验收标准是同一 `key` 序号严格递增、不同 `key` 可交错；若 `refund-8871` 三条交错，说明 `poll` 未固定分区或消费者不止一个。
