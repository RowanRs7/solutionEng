# ETL、ELT、CDC 与数据同步

## 为什么需要学习

月结前一周，晴空商城的数据团队被叫去对账三次：数仓的退款成功率比订单库低 2.1 个百分点；客服搜索库还能搜到三天前已取消的订单；仓库清单里有 8 单早已退款。三条现象是同一件事——数据搬运时丢了、旧了或多出了一份。

第一版是深夜 `SELECT *` 全量导出，大促当天跑了 5 小时，把只读从库压到超时；改成扫 `updated_at` 增量后延迟降了，却开始稳定漏单：仓库回写状态不刷时间戳，取消的订单没有可扫的时间戳。团队只看"任务成功"的绿灯，从没问过"两边是否相等"。

> **核心结论：** 数据同步难的从来不是把行搬过去，而是说清变更从哪来、边界在哪、搬完之后用什么证据证明两边相等。

## 学习目标

学完本课，你能够：

- 区分全量、增量、日志 CDC，说出各自会漏掉哪类变更。
- 说明日志 CDC 如何读到前镜像与删除事件，以及"快照 + 位点"的顺序约束。
- 判断一次 Schema 变更是兼容还是破坏性的，列出消费端要改的内容。
- 用行数、校验和、主键差集三层校验，把"差 137 笔"定位到具体行。

## 业务场景

晴空商城一个订单库要服务四个下游：

- **经营报表（数仓）**：T-1 完整性优先，可延迟到次日 06:00，但日结数字必须与订单库逐笔对上。
- **客服搜索库**：1 分钟内看到最新状态（含"退款受理中"），只读不写回。
- **仓库待发货清单**：只要"已支付且未取消"，取消与退款须在 2 分钟内消失，否则货会真的发出去。
- **风控与对账流水**：保留每一次状态变更，能重放，不能只留最终态。

约束：订单库不允许长事务和大范围扫描；退款状态须分钟级到达；大促写入是平时 8 倍；取消与删除必须能被下游感知。

## 核心概念

*数据同步*（data synchronization）让两个存储对同一份业务事实达成一致，分抽取、传输、写入并校验三段。

*全量同步*（full sync）每次读出源表全部行覆盖目标；*增量同步*（incremental sync）只搬上次之后变化的部分，用*水位*（watermark）记录进度。

*ETL*（Extract-Transform-Load）在独立引擎里转换完再写入目标；*ELT* 先原样装入目标（多为列式数仓）再在目标内用 SQL 转换。分界线不是工具，而是**转换发生在落地之前还是之后**。

*CDC*（change data capture，变更数据捕获）持续取得"某一时刻之后每一条变更"。三种抓法差别远比名字大：

| 抓取方式 | 原理 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| *基于查询*（query-based） | 定时 `WHERE updated_at > 水位` | 最简单，任何库能跑 | <u>看不见删除，也看不见漏刷时间戳的更新</u> |
| *基于触发器*（trigger-based） | 源表装触发器写变更表 | 不依赖日志格式 | 侵入源库、写放大，故障拖慢业务写入 |
| *基于日志*（log-based） | 读事务日志（binlog、WAL）解析行镜像 | 低侵入、带前镜像、删除也是事件 | 需日志权限与保留期，解析器要跟随 Schema |

*位点*（offset / LSN）是"读到日志的哪一条"，是日志 CDC 唯一可靠的进度。*快照加位点*（snapshot + offset）是初始化标准姿势：先记位点，再按一致性快照导存量，最后从该位点重放。

<u>水位能表达的东西比你以为的少：它只知道"最后更新时间"，既不知道删除，也不知道哪个写入方忘了更新时间。</u>

## 工作原理

以订单 `SO-20431` 从 `paid` 变为 `refunded` 为例：

1. **按下游需求定边界**：报表要最终态，风控要每条变更历史，两者不能共用一套剪裁逻辑。
2. **建立初始快照**：记录当前位点 `LSN=1002`，再用可重复读事务或只读从库导出存量，标记为"快照 @1002"。
3. **从位点衔接**：快照落完，从 `LSN > 1002` 重放。先进快照后记位点会丢掉两者之间的变更；先记位点最坏只重复一小段，而重复能被幂等写入吃掉。
4. **解析变更事件**：`UPDATE` 带前后镜像（`paid` → `refunded`），`DELETE` 至少带主键。**删除必须作为一条事件发出，否则下游永远不知道该行消失。**
5. **按主键幂等写入**：目标端一律 `UPSERT` 而非 `INSERT`；删除按主键删，或写 `is_deleted=true` 的墓碑行。
6. **提交位点**：数据落库后再提交位点，崩溃时最坏重放一小段，不会静默丢一段。
7. **Schema 变更随事件流动**：源端加列后事件多出字段。兼容变更（加可空列、同类型加宽）可忽略未识别字段继续跑；破坏性变更（删列、改类型、改语义）必须先让消费端上线双读兼容版本再切源端，<u>顺序反了就是停摆</u>。
8. **一致性校验**：两端取同一逻辑时刻（同一 LSN 或快照时间），先比行数，再比校验和，最后按主键差集定位。

三层校验分别回答"有没有丢或多""有没有差异""是哪几行"，<u>只比行数会漏掉"行数相等而内容不同"</u>。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 夜间全量重灌 | 表小、容忍 T+1、无开发人力 | 大表、要求分钟级 | 窗口长，期间目标端读到半表数据 |
| 水位增量（查询式） | 时间戳可靠、几乎不硬删 | 多写入方、硬删除多 | 一致性靠约定而非机制 |
| 日志 CDC | 需要实时、删除与历史 | 源库不开放日志、托管服务禁读日志 | 组件与运维复杂，Schema 演进要治理 |
| 应用内双写或发事件 | 变更集中、可与业务事务同库提交 | 写入方多、有历史遗留系统 | 存量要补全量，漏写是永久缺口 |

选型问四件事：**下游要最终态还是每条变更？** 要历史就只能事件流或日志 CDC。**有硬删除吗？** 有就必须能看见删除。**延迟多少？** 分钟级以内基本只剩日志 CDC。**谁对一致性负责？** **没有校验方案的同步链路，等于把不一致交给下游用投诉来发现。**

## 最小示例

问题：同一份变更分别用水位增量与日志 CDC 同步到两张表，再校验谁与源端相等。环境：Python 3.9+ 标准库。输入：`LSN=1002` 的快照、三条变更、水位 150。输出：行数、校验和与差异清单。

```python
import hashlib
import json

# 源库真相：校验时用它当标准答案；SO-2 已被删除，任何地方再出现它都是错的
TRUTH = {
    "SO-1": {"status": "shipped", "amount": 19900},
    "SO-3": {"status": "paid", "amount": 5800},
}

# 全量初始化能拿到的内容，取自 LSN=1002 时的一致性快照
SNAPSHOT = [
    {"order_id": "SO-1", "status": "paid", "amount": 19900, "updated_at": 100},
    {"order_id": "SO-2", "status": "paid", "amount": 9900, "updated_at": 100},
    {"order_id": "SO-3", "status": "created", "amount": 5800, "updated_at": 100},
]

# 事务日志：op 取 c/u/d，seq 即 LSN 单调递增，是日志 CDC 唯一可靠的读源
CHANGES = [
    # 1003：仓库侧回写发货状态，漏刷 updated_at——水位法看不见它
    (1003, "u", {"order_id": "SO-1", "status": "shipped", "amount": 19900, "updated_at": 100}),
    # 1004：删除事件只带主键，天然没有 updated_at 可扫
    (1004, "d", {"order_id": "SO-2"}),
    # 1005：时间戳正确推进的普通更新，水位法能抓到
    (1005, "u", {"order_id": "SO-3", "status": "paid", "amount": 5800, "updated_at": 180}),
]

WATERMARK = 150            # 上次同步结束时刻，取自源库 updated_at 的最大值
BIZ = ("status", "amount")  # 校验列清单要显式声明：技术列 updated_at 不参与比对


def biz(row):
    """只投影业务列，避免把装载时间戳等实现细节算进校验"""
    return {k: row[k] for k in BIZ}


def upsert(table, row):
    """按主键覆盖写入：插入与更新同一路径，所以重放两次结果相同"""
    table[row["order_id"]] = {k: v for k, v in row.items() if k != "order_id"}


def watermark_sync(table, watermark):
    """方案一：定时扫 updated_at > 水位，只能看见确实更新过时间戳的行"""
    for _seq, op, row in CHANGES:
        if op == "d":
            continue                        # 删除没有时间戳，扫不到，这是结构性缺陷
        if row["updated_at"] <= watermark:  # 边界内或被漏刷的行一律跳过
            continue
        upsert(table, row)
    top = max(r["updated_at"] for _s, o, r in CHANGES if o != "d")
    return f"扫 updated_at > {watermark} 完成，水位推进到 {top}"


def cdc_sync(table, start_seq):
    """方案二：从日志位点顺序重放，删除也是一条事件"""
    applied = 0
    for seq, op, row in CHANGES:
        if seq <= start_seq:
            continue                        # 快照已覆盖这段，跳过才不重复搬
        if op == "d":
            table.pop(row["order_id"], None)  # 删除即删除，不留幽灵行
        else:
            upsert(table, row)                # 幂等写入，崩溃后重放安全
        applied += 1
    return f"重放 {applied} 条变更，位点推进到 {CHANGES[-1][0]}"


def fingerprint(rows):
    """把整表压成一个校验和：按主键排序后序列化，任何一行不同都会变"""
    canonical = "\n".join(
        f"{k}|{json.dumps(biz(rows[k]), sort_keys=True)}" for k in sorted(rows)
    )
    return hashlib.md5(canonical.encode()).hexdigest()[:8]


def diff(target, truth):
    """校验和不相等时按主键差集定位到行，输出可以直接贴进工单"""
    problems = []
    for key in sorted(set(target) | set(truth)):
        if key not in target:
            problems.append(f"{key} 缺失")
        elif key not in truth:
            problems.append(f"{key} 幽灵行")
        elif biz(target[key])["status"] != truth[key]["status"]:
            problems.append(f"{key} 状态漂移 {target[key]['status']}->{truth[key]['status']}")
    return problems


wm = {r["order_id"]: {k: v for k, v in r.items() if k != "order_id"} for r in SNAPSHOT}
cdc = {k: dict(v) for k, v in wm.items()}   # 两个目标表同一份快照出发，只差同步方式

print("水位增量：", watermark_sync(wm, WATERMARK))
print("CDC 重放：", cdc_sync(cdc, 1002))
print("行数 源端=%d 水位端=%d CDC端=%d" % (len(TRUTH), len(wm), len(cdc)))
print("校验和 期望=%s 水位端=%s CDC端=%s" % (fingerprint(TRUTH), fingerprint(wm), fingerprint(cdc)))
print("水位端差异：", diff(wm, TRUTH))
print("CDC端差异：", diff(cdc, TRUTH))
```

`SNAPSHOT` 与 `CHANGES` 是初始化的两个输入——存量与日志；两个 `*_sync` 是同一份变更的两种读法；`fingerprint` 把整表压成短字符串便于比对，`diff` 在失败后按主键缩小范围；两表从同一份快照出发，唯一变量是同步方式。

运行 `python3 sync_demo.py`，预期输出（已实际运行核对）：

```text
水位增量： 扫 updated_at > 150 完成，水位推进到 180
CDC 重放： 重放 3 条变更，位点推进到 1005
行数 源端=2 水位端=3 CDC端=2
校验和 期望=32f2f3dd 水位端=c409c74a CDC端=32f2f3dd
水位端差异： ['SO-1 状态漂移 paid->shipped', 'SO-2 幽灵行']
CDC端差异： []
```

水位端多出的 `SO-2` 是删除不可见的产物，叫*幽灵行*（ghost row）；`SO-1` 停在 `paid`，因为回写方没刷时间戳；CDC 端校验和一致，说明<u>日志里本来就有的信息，只有按位点重放才拿得全</u>。

真实链路搬的是带 Schema 版本的事件信封：

```json
{
  "source": "order-db.orders",
  "lsn": 1005,
  "op": "update",
  "occurred_at": "2026-10-19T10:12:03Z",
  "key": {"order_id": "SO-20431"},
  "before": {"status": "paid"},
  "after": {"status": "refunded"},
  "schema_version": 7
}
```

`lsn` 是断点续传与"校验取同一时刻"的依据；`op` 决定写入语义，删除不能折叠成普通更新；`before` 用于判断是否已处理过；`schema_version` 让消费端选择解析规则；`key` 是去重主键，<u>缺主键的变更事件无法幂等</u>。

## 动手实验

**前置条件**：Python 3.9+；示例存为 `sync_demo.py`；无需 Docker 或网络。

**步骤一：只修时间戳，看还剩什么**。把 `1003` 那行的 `updated_at` 从 `100` 改成 `160` 再运行。

预期结果：水位端差异只剩 `['SO-2 幽灵行']`。验证：对比改动前后的差异清单——`SO-2` 仍在，说明<u>补时间戳只解决一半，删除仍是水位法的死角</u>。

**步骤二：跳一段日志的代价**。把 `cdc_sync(cdc, 1002)` 改成 `cdc_sync(cdc, 1004)`。

预期结果：CDC 端差异变成与水位端相同的两条，提示 `重放 1 条变更`，行数从 2 变 3。跳过一段日志不只漏更新，还会让那段的删除一起失效，<u>位点只能前进，不能为省量跳过</u>。

**步骤三：Schema 变更后的校验盲区**。给 `1005` 的负载加 `"channel": "app"` 再运行。

预期结果：校验和仍是 `32f2f3dd`，两边依然"相等"，因为 `BIZ` 只含 `status` 与 `amount`。<u>新增列没进校验清单，就等于完全没被校验</u>；每次 Schema 变更要同时更新解析映射、`BIZ` 校验列与下游表结构。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 目标端有源端已删的幽灵行 | 时间戳增量看不到删除 | 按主键做双向差集 | 改日志 CDC，或改软删并把状态列纳入增量 |
| 每天稳定漏几笔，重跑又对上一部分 | 漏刷时间戳，或长事务提交晚于水位 | 查 `updated_at` 与提交时间的最大滞后 | 由框架统一维护时间戳，或留回退窗口 |
| 同步任务重跑后数据翻倍 | 按 `INSERT` 写入且无主键约束 | 检查主键或唯一索引，重放同一事件看行数 | 改按主键 `UPSERT` 并补唯一约束 |
| 加列后消费端报错并停止推进 | 消费端开启严格 Schema 校验 | 看错误栈字段名，对比 DDL 与 `schema_version` | 未知字段忽略或显式映射；破坏性变更双读兼容 |

## 安全与生产注意事项

**<u>给同步账号开整库读权限、把全表变更原样落到一张无访问控制的落地表，等于把交易库复制成第二份没有审计的副本。</u>**后果是手机号、地址、支付信息扩散出多份拷贝，删除请求覆盖不到，审计说不清谁读过。缓解：只授权需要的库表、按列白名单映射、敏感列脱敏，落地层配一致的访问控制与保留期。

**<u>把"全量重灌"当作修复一致性的默认手段，会在窗口期把半旧半新的数据暴露给下游，同时压满源库。</u>**后果是报表断崖下跌、仓库按半表数据发货、核心库被慢查询拖垮。缓解：走影子表加原子切换，读操作限速错峰，窗口期内让下游读上一版快照。

- **删除必须有出口，延迟与行数都要告警**：硬删除没有事件时下游只能靠全量对账发现；只监控"任务成功"会漏掉"成功但延迟一小时"。

## 本课总结

- **数据同步由抽取、传输、写入、校验四段组成**，任一段没有负责人，问题都会在下游以投诉形式出现。
- 全量重灌简单但窗口长，水位增量便宜却看不见删除；日志 CDC 是唯一同时拿到删除、前镜像与历史的方式。
- 初始化顺序是"记位点 → 快照 → 从位点重放"，位点只前进不跳段，写入按主键幂等。
- Schema 变更按兼容与破坏性分流，破坏性变更须双读兼容后再切源端。
- 校验分三层：行数看有无、校验和看差异、主键差集看是哪几行；**校验列清单要随 Schema 变更更新**。

## 思考题

大促零点后日志 CDC 延迟从 20 秒涨到 12 分钟，客服搜索库明显落后，仓库清单开始出现已退款订单。请说明诊断顺序，给出两个降级方案及其代价，并回答：延迟期间哪些校验可照常执行、哪些必须暂停？

参考思路：先分清是源端写入放大、解析落后还是目标端写入受限，看位点差、解析速率与目标端写入延迟三条曲线，避免扩容掩盖瓶颈。降级可选"只保 `orders` 主键变更并提高并行度"，或让仓库侧短暂回退到按需查订单库，代价是资源成本与核心库压力。"要求两端同一时刻"的比对在延迟期必然误报，应暂停并记录位点，归零后再跑全量校验。

## 小测

1. 水位增量同步最本质的盲区是什么？  
   A. 性能不如全量　B. 看不见删除与漏刷时间戳的更新　C. 无法处理大表　D. 不支持事务一致性

2. 日志 CDC 初始化的正确顺序是？  
   A. 先从头重放，再用快照覆盖　B. 先记位点，再导快照，然后从位点重放　C. 只导快照就够了　D. 先导快照，再从头重放并依赖去重

3. 源表新增可空列而消费端未升级，后果是什么？为什么这仍算"安全"？

4. 一致性校验为什么不能只比行数？

5. 场景判断题：客服搜索库出现已取消订单，报表又稳定漏单。三个方案——A. 全量重灌改成每 4 小时一次；B. 继续 `updated_at` 增量但要求写入方补时间戳；C. 改日志 CDC 并按位点重放。选哪个？各自代价是什么？

## 答案与解析

1. **B。** 扫描只能发现"更新时间已推进"的行，删除与漏刷时间戳的更新都扫不到。A 错，低读放大恰是增量法的优点；C 错，大表能扫只是慢；D 错，扫描可放在只读事务里。
2. **B。** 先记位点再取快照，之后的变更都能补上，最多重复一小段并被幂等吸收。A 错，重放后再覆盖会清掉结果；C 错，只导快照就永久停在一个时间点；D 错，从头重放成本随历史线性增长。
3. 多数解析器会忽略未识别字段继续运行，链路不中断，这叫*兼容变更*；但新列不同步、也不进校验清单，表现为"不报错，但新字段永远为空"。仍要补解析映射、下游表结构与 `BIZ` 校验列。
4. "多一行 + 少一行"时行数正好相等，总数对上而内容不同很常见。<u>行数只证明数量对，不证明两边是同一份事实</u>，必须配合校验和与主键差集。
5. **C。** 它同时解决删除不可见与漏刷时间戳两个根因，并可用位点精确断点与重放。A 错，只把幽灵行窗口从一天缩到四小时，还持续压源库；B 只修好一半，硬删除依旧看不见。代价是日志读取权限与解析组件运维。

### 动手实验参考

步骤一验收点是"差异少一条但没清空"：`SO-1` 追平了，`SO-2` 依然是幽灵行。步骤二应看到 CDC 端退化成与水位端相同的两条差异——跳过一段日志会把那段的删除一并跳过。步骤三应看到校验和不变，这是最危险的"通过"：说明校验清单没跟上 Schema；把 `BIZ` 改成 `("status", "amount", "channel")` 并给 `TRUTH` 补上 `channel`，校验和才重新具备分辨力。
