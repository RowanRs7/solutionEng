# 同步与异步集成模式选型

## 为什么需要学习

晴空商城退款一期把"确认退款"做成同步调用：客服点一下，请求线程依次等仓库回滚、等支付商退款。仓库平时 0.4 秒，大促那天 40 秒，客服连按三次，仓库收到三条回滚，库存虚增 6 件。二期改成提交后立刻返回"已受理"，任务失败却只留在日志里，客户问"钱到哪了"没人答得上。

两次返工都不是技术问题，而是没人回答"谁在什么时刻必须知道什么结果"。

> **核心结论：** 同步与异步不是技术偏好，而是"谁在何时必须知道结果"的业务约定；交付物是一份写明切分点、受理态与失败责任的集成 ADR。

## 学习目标

完成本课后，你能够：

- 用五个判定问题为一条集成需求选择同步或异步，并说出放弃了什么。
- 画出"同步受理 + 异步执行 + 同步查询"的边界，说明 `202` 之后谁负责收敛。
- 写出含选项、后果与复核条件的集成 ADR。
- 运行示例复现"下游已执行但上游超时"，说明幂等键与任务标识的分工。

## 业务场景

晴空商城的退款单流转为"待审核 → 已批准 → 已退款"，围绕它有四段等待方式不同的交互：

| 交互 | 谁在等 | 能等多久 | 重复一次的后果 |
| --- | --- | --- | --- |
| 客服提交退款 | 客服，用于决定是否跟进 | 2 秒内要答复 | 生成多张退款单 |
| 仓库回滚出库单 | 无人在等，库存要准 | 分钟级 | 重复入库，库存虚增 |
| 支付商退款结果 | 会员在订单页看 | 分钟到小时 | 重复退款，资金损失 |
| 财务对账流水 | 财务，次日核对 | 次日 | 重复入账，对账不平 |

约束五条：页面 P95 小于 2 秒；退款指令不能丢；同一退款单副作用只生效一次；客服要看到卡在哪一步；峰值是平时 8 倍。"2 秒"与"仓库 40 秒"正面冲突，让步写在哪里就是这个决策。

## 核心概念

*同步集成*是调用方发请求后阻塞等待，直到拿到结果或明确失败。*异步集成*是只等到"已被接收"的确认，结果通过消息、回调或后续查询另行送达。两者可共存；真正要选的是*集成切分点*：请求路径在哪一步结束，之后由谁接手。

*受理态*（accepted）表示"已承担责任、尚未完成"，*完成态*（completed）才是业务结果，`202 Accepted` 表达前者。<u>把受理态当完成态展示给用户，是这类项目最常见的事故形态。</u>

*关联标识*（correlation ID）是串起同步请求与后续异步处理的业务键，如退款单号；没有它，日志里两段处理无法证明属于同一件事。*最终一致性*承诺"足够时间后收敛到同一结果"，它需要有人负责收敛，也需要界面能解释中间态。

| 维度 | 同步集成 | 异步集成 |
| --- | --- | --- |
| 等待的对象 | 业务结果 | 受理确认 |
| 典型响应 | `200` + 结果体 | `202` + 任务标识 |
| 延迟下限 | 不小于下游 P99 | 与下游耗时解耦 |
| 失败时知道什么 | "失败"或"结果未知" | "已受理，结果待定" |
| 重复副作用风险 | 超时重试、用户连点 | 至少一次投递、任务重跑 |
| 状态权威在哪里 | 调用方常被迫缓存下游状态 | 任务或事件的所有者维护 |
| 观测难点 | 跨系统耗时归因 | 断点在哪、任务是否在推进 |
| 晴空商城示例 | 客服查询退款详情 | 仓库回滚出库单 |

## 工作原理

判定一条集成需求，按顺序问六个问题，第七步才是写下来：

1. **结果用来做什么。** 要立刻参与下一步判断（风控放行、库存扣减、支付预授权），就必须同步拿到；只用于记录、通知或事后补偿则适合异步。仓库回滚属于后者。
2. **调用方能等多久。** 对比下游 P99 与 deadline，<u>P99 超过 deadline 的三分之一，同步等待就已在赌运气</u>：页面 2 秒、仓库 40 秒，同步注定失败。
3. **失败在哪一侧被发现。** 同步失败当场知道，但要处理"结果未知"；异步失败没有人在等，必须由重试、死信与告警兜底。**异步不是消灭失败，而是把失败从请求路径移到运维路径。**
4. **重复执行代价多大。** 重复扣款、重复回滚都是副作用：同步至少要幂等键，异步还要去重表与投递语义。
5. **谁是权威状态。** 退款单状态属于退款服务，回滚状态属于仓库；<u>两边各存副本时，必须先定谁说了算</u>。
6. **写下切分点、兜底与复核条件。** 前五问的结论落成 ADR，复核条件让依赖改善后能重估。

### 混合边界：把受理留在同步，把完成推出去

常见三种形状：**同步受理 + 异步执行 + 同步查询**（提交拿到 `202` 与 `job_id`，页面查 `/refunds/{id}/job`）；**同步读 + 异步写**；**异步事件 + 同步读模型**（写侧发事件，读侧维护投影）。

三条硬规则：受理路径只做鉴权、参数校验、幂等查重、落任务，<u>再同步调用一次慢下游，等于把异步退化回同步，只换了个名字</u>；`202` 必须带任务标识与查询入口；受理侧负责"不丢、不重"，执行侧负责"最终做成"，<u>不要让用户先看到成功、再收到"补偿式失败"</u>。

## 架构与选型

六种模式覆盖了多数集成需求，差异集中在等待对象、失败责任与代价：

| 模式 | 适用场景 | 不适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 同步请求-响应 | 结果决定下一步；下游 P99 远小于 deadline | 下游抖动大、耗时超 deadline | 与下游强耦合，故障直接传导 |
| 异步受理（`202` + 任务查询） | 耗时长、要给即时反馈、结果可稍后 | 必须当场判定能否继续 | 任务表、状态机、查询接口 |
| 消息或事件驱动 | 一次操作扇出多个下游、削峰 | 只有一个下游且要即时结果 | 至少一次投递导致重复，需幂等与死信 |
| 回调 + 查询兜底 | 第三方异步通知（支付、物流） | 对方无回调且查询不可靠 | 处理签名、重放、乱序与丢通知 |
| 批量或定时同步 | 数据量大、允许小时级延迟（对账） | 需要近实时或逐笔确认 | 延迟高、失败重跑成本大 |
| 事件流与重放 | 需要审计、重算、多消费组 | 团队无运维能力、量很小 | 运维复杂、延迟偏高 |

选型依据不是"哪个更先进"，而是三件事能否同时成立：业务能否解释中间态；失败兜底有没有 owner；切分后观测链路是否连得起来。晴空商城就是"受理同步、回滚异步、退款回调、对账批量"四段各选各的。

### 集成方案 ADR

ADR 把"为什么这样切"固定下来，最小结构是背景、决策驱动、选项、决定、后果、复核条件；下面是填好的实例，可直接当模板：

```text
ADR-014：退款集成的同步/异步切分
状态：已接受（2026-10-19）　决策者：架构师、客服负责人、财务负责人

背景：客服"确认退款"同步等待仓库回滚与支付商退款；仓库 P99 40 秒，
      支付商 1–90 秒，页面 deadline 2 秒，超时后重复点击造成重复回滚。

决策驱动：页面 P95 小于 2 秒；退款指令不丢；同一退款单副作用只生效一次；
          客服要能看到卡在哪一步；不引入团队无法运维的中间件。

选项：A. 全同步，加大超时并补幂等键；
      B. 全异步，提交后只发通知；
      C. 同步受理 + 异步执行 + 同步任务查询。

决定：选 C。受理只做鉴权、参数校验、幂等查重与落任务，200ms 内返回 202 与
      job_id；仓库回滚与支付退款由 worker 执行，退避重试后进死信；客服工作台
      通过 /refunds/{id}/job 查询进度与失败原因。

后果：新增任务表、状态机、死信处置与查询接口；客服需培训"处理中"与"已退款"
      的区别；为受理耗时、任务积压、死信数量设告警；支付商超时后的未知结果
      仍需对账兜底。

复核条件：支付商提供稳定的批量退款接口，或仓库 P99 降到 2 秒以内时重估。
```

<u>没有"后果"和"复核条件"的 ADR 只是会议纪要</u>：前者写清新增成本由谁承担，后者写成可观察的触发信号。

## 最小示例

问题：验证同步超时后下游是否真的没执行，以及异步受理能否吸收重复提交。环境：Python 3.9+，仅标准库。输入：仓库耗时序列 `[0.2, 1.5]` 与 `[0.2, 0.4]`，客户端 deadline 1.0 秒。输出：每次调用的状态码与耗时，以及仓库真正回滚的次数。

```python
"""sync_vs_async.py —— 同步等待与异步受理的行为差异"""
import time
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FutureTimeout

CLIENT_DEADLINE = 1.0     # 页面等待上限，也是同步调用的超时


class Warehouse:
    """仓库接口：按序返回耗时，并记录副作用生效次数"""

    def __init__(self, delays):
        self.delays = list(delays)   # 每次调用耗时，模拟下游抖动
        self.calls = []              # 副作用落地记录，长度即回滚次数

    def rollback(self, refund_id):
        delay = self.delays.pop(0) if self.delays else 0.3
        time.sleep(delay)            # 耗时发生在下游，不在调用方
        self.calls.append(refund_id)  # 走到这行库存才算回滚
        return delay


def sync_refund(pool, warehouse, refund_id):
    """同步集成：等结果，超时即判失败，但下游可能仍在执行"""
    start = time.perf_counter()
    future = pool.submit(warehouse.rollback, refund_id)
    try:
        future.result(timeout=CLIENT_DEADLINE)   # 到点放弃等待
        return ("200 DONE", round(time.perf_counter() - start, 2))
    except FutureTimeout:
        return ("504 TIMEOUT", round(time.perf_counter() - start, 2))


JOBS = {}         # job_id -> 状态；生产上必须落库
IDEMPOTENCY = {}  # 幂等键 -> job_id，吸收重复提交


def async_accept(pool, warehouse, refund_id, idem_key):
    """异步受理：只校验、落任务、返回 202，干活交给后台"""
    start = time.perf_counter()
    if idem_key in IDEMPOTENCY:              # 重复提交命中幂等键
        return ("202 ACCEPTED", round(time.perf_counter() - start, 3),
                IDEMPOTENCY[idem_key], "重复提交，返回同一任务")
    job_id = f"job-{len(JOBS) + 1:04d}"
    IDEMPOTENCY[idem_key] = job_id
    JOBS[job_id] = "PENDING"

    def run():                               # 后台任务：独立的重试与超时
        delay = warehouse.rollback(refund_id)
        JOBS[job_id] = f"DONE({delay}s)"

    pool.submit(run)                         # 受理路径不做慢活
    return ("202 ACCEPTED", round(time.perf_counter() - start, 3), job_id, "新任务")


print("== 同步路径：下游抖动 1.5s，客户端 1.0s 超时 ==")
sync_wh = Warehouse([0.2, 1.5])
with ThreadPoolExecutor(max_workers=2) as pool:
    for i in range(1, 3):
        status, elapsed = sync_refund(pool, sync_wh, f"RF-887{i}")
        print(f"  第{i}次 {status:12s} 客户端耗时={elapsed}s")
# shutdown(wait=True) 会等后台线程跑完，才能看见真实的副作用次数
print(f"  仓库实际回滚次数={len(sync_wh.calls)}，客户看到的成功次数=1")

print("== 异步路径：受理只做校验，重复提交被幂等键吸收 ==")
async_wh = Warehouse([0.2, 0.4])
with ThreadPoolExecutor(max_workers=2) as pool:
    for i in range(1, 3):
        status, elapsed, job, note = async_accept(pool, async_wh, "RF-8871", "refund-RF-8871")
        print(f"  第{i}次 {status} 受理耗时={elapsed}s {job} {note}")
print("  任务表:", {k: v for k, v in sorted(JOBS.items())})
print(f"  仓库实际回滚次数={len(async_wh.calls)}")
```

`Warehouse` 只负责"睡够时间再落地副作用"，它既是下游也是副作用证据；`sync_refund` 到点放弃等待，但线程仍在跑；`async_accept` 把活交给同一个线程池后立即返回，幂等键决定新建还是复用任务。

运行 `python3 sync_vs_async.py`，预期输出（已实际运行核对，耗时会有 ±0.01 秒抖动）：

```text
== 同步路径：下游抖动 1.5s，客户端 1.0s 超时 ==
  第1次 200 DONE     客户端耗时=0.2s
  第2次 504 TIMEOUT  客户端耗时=1.0s
  仓库实际回滚次数=2，客户看到的成功次数=1
== 异步路径：受理只做校验，重复提交被幂等键吸收 ==
  第1次 202 ACCEPTED 受理耗时=0.0s job-0001 新任务
  第2次 202 ACCEPTED 受理耗时=0.0s job-0001 重复提交，返回同一任务
  任务表: {'job-0001': 'DONE(0.2s)'}
  仓库实际回滚次数=1
```

三处对照：同步路径第二次返回 `504` 时回滚次数已是 2，说明**上游判失败不等于下游没执行**，这是同步链路必须带幂等键的原因；异步两次提交只产生一个任务，重复被受理侧的幂等键吸收；`JOBS` 最终是 `DONE`，说明完成态另有维护者，`202` 从不承诺结果。

## 动手实验

**前置条件**：Python 3.9+；已把示例保存为 `sync_vs_async.py`；无需 Docker 或网络。

**步骤一：把 deadline 收到 0.5 秒**。修改 `CLIENT_DEADLINE = 0.5` 后重跑。预期结果：两次都返回 `504 TIMEOUT`，回滚次数仍是 2。验证方法：数 `Warehouse.calls` 长度，对照客户看到的成功次数 0——降低超时只提高"结果未知"的比例，不减少重复副作用。

**步骤二：删掉幂等判断**。把 `async_accept` 里 `if idem_key in IDEMPOTENCY:` 整段注释掉再跑。预期结果：两次提交生成 `job-0001` 与 `job-0002`，任务表两个条目。验证方法：比较任务表条目数与提交次数。重复由受理侧负责，不能指望后台任务自己识别。

**步骤三：把慢活塞回受理路径**。把 `pool.submit(run)` 改成直接调用 `run()`。预期结果：第一次受理耗时从 0.0 秒变成约 0.2 秒，`202` 返回时任务已是 `DONE`。验证方法：看受理耗时与任务状态的先后。<u>受理路径里还留着慢调用，返回的就是同步语义，`202` 只是装饰</u>。

**清理**：`rm sync_vs_async.py`，删除实验新增的临时脚本与输出文件。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 客服连点三次生成三张退款单 | 超时且无幂等键，按钮未禁用 | 按退款单号统计受理请求条数 | 幂等键加请求指纹去重，按钮置灰 |
| 页面写"退款成功"但钱未到账 | 把 `202` 受理态写进业务状态字段 | 比对退款单状态与支付商流水 | 拆受理态与完成态，文案只跟完成态 |
| 异步任务失败无人知晓 | 受理后没有死信、告警与 owner | 查死信长度与任务超时数 | 重试上限、死信、告警、巡检一起补 |
| 客服看不到进度，反复提交 | `202` 没返回任务标识，也无查询接口 | 检查响应体与 `Location` 头 | 返回 `job_id` 并提供查询或推送 |
| 对方成功、我方判失败并重复扣款 | 超时被当失败直接重试，无幂等键 | 核对下游流水时间与重试记录 | 结果未知时先查后做，幂等键贯穿两侧 |

## 安全与生产注意事项

**<u>受理成功时就写"退款成功"或给会员发"已退款"短信，是用受理态冒充完成态；后台任务一旦失败，就是资金与信任的双重事故。</u>** 后果是客户按"已退款"预期消费，实际钱没退，客诉与对账全对不上。缓解：状态机显式区分 `ACCEPTED` 与 `REFUNDED`，文案与短信只由完成态触发，完成态由支付回调或对账确认。

**<u>把异步任务只放在进程内存或手工脚本里，重启即丢又没有重放入口，等于悄悄取消了用户已看到"处理中"的退款。</u>** 后果是退款单永久停在中间态，对账缺笔且无法定位责任人。缓解：任务落持久化表或队列，设重试上限与死信，提供带审计的重放，并对"处理中超过 N 分钟"告警。

另外两条：`/refunds/{id}/job` 这类接口必须校验退款单归属，否则改一个 URL 就能看到他人退款进度；同步超时后的自动重试必须有上限并带退避，否则重试本身会变成第二次故障。

## 本课总结

- 同步与异步是"谁在何时必须知道结果"的业务决定，不是中间件选型。
- 判定顺序：结果用途 → 可等待时间 → 失败可发现性 → 重复代价 → 状态归属 → 一致性窗口，最后落成 ADR。
- 混合边界的标准形状是同步受理、异步执行、同步查询；受理路径里不能再放慢活。
- `202` 只代表受理，<u>没有任务标识与查询入口的 `202` 是甩锅</u>。
- 集成方案以 ADR 收口：选项、决定、后果与复核条件缺一不可。

## 思考题

晴空商城的"退款审核"目前同步：客服提交后等风控模型评分，模型 P99 为 3 秒。业务希望结论 1 秒内可见，风控要求保留人工复核。请判断哪一段该同步、哪一段该异步，给出切分点与 `202` 之后的收敛方式，并说明风控连续失败 10 分钟时，客服界面与会员页分别显示什么、由谁处理。

参考思路：把"审核结论"与"人工复核"拆开。同步只留快操作——参数校验、黑名单命中、金额阈值规则，200ms 内给出"通过/拒绝/转人工"三态；模型评分异步执行，未回时状态为"审核中"，由事件或查询回填。"转人工"必须是正常终态。风控连续失败时，客服界面显示"审核中，已等待 X 分钟"并给出转人工入口，会员页只显示"退款处理中"；兜底 owner 是客服值班。评价看三点：是否区分受理态与完成态、是否给人工复核留了正常出口、失败文案与责任人是否写清。

## 小测

1. `202 Accepted` 的确切含义是？  
   A. 业务已经完成　B. 已受理但结果待定　C. 请求参数有误　D. 任务已进入死信队列

2. 判定一条集成需求该不该同步等待，最先应回答哪个问题？  
   A. 下游用什么中间件　B. 结果是否立刻参与下一步判断　C. 团队会不会用 Kafka　D. 能否靠加机器扛住

3. 同步调用在 deadline 处超时，下游可能已经执行成功。这个事实对设计提出什么要求？

4. 为什么混合边界中"受理路径"不能再同步调用一次慢下游？

5. 场景判断题：团队要把"退款成功后回滚仓库出库单"改成异步，客服主管反对，理由是"改成异步就不知道到底退没退"。应如何回应，并给出 `202` 之后必须补齐的三件事？

## 答案与解析

1. **B。** `202` 表示已接受、处理未完成，不携带结果。A 错，那是 `200`/`201` 的语义；C 错，参数错误返回 `4xx`；D 错，死信是链路内部处置。
2. **B。** 结果用途决定同步的必要性，中间件与人力是实现问题。A、C 把选型提到判定之前；D 只改容量，不改 P99 与 deadline 的矛盾。
3. 必须假设"下游可能已生效"：写操作带幂等键，重试前先查实现状态，超时结果标记为"未知"而非"失败"。只加超时或重试都不解决重复副作用。
4. 受理路径耗时直接进入调用方等待时间，慢调用一进去就恢复同步语义，只是把失败点从"业务失败"挪到"受理失败"。受理路径应只做鉴权、校验、幂等查重与落任务。
5. 异步改的是"谁等结果"，不是"有没有结果"；客服要的确定状态由任务状态提供。`202` 之后必须补：任务标识与幂等键；可查询或推送的进度接口（含失败原因与重试次数）；失败兜底责任（重试上限、死信告警、重放 owner）。只做第一件，等于把不确定性从页面转移到日志。

### 动手实验参考

步骤一结论是"超时只改变谁知道，不改变谁做过"：`calls` 仍为 2。步骤二验收标准是任务表两条记录、回滚两次，证明缺少幂等键时重复会穿透到副作用。步骤三依据是受理耗时升到约 0.2 秒且返回时任务已是 `DONE`。若 `calls` 始终为 1，通常是 `pool.shutdown(wait=True)` 没等到后台线程。
