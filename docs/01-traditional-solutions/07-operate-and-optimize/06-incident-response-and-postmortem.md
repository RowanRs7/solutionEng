# 故障分级、响应与复盘

## 为什么需要学习

晴空商城的退款集成服务上线半年后，10:02 监控告警“退款受理 5xx 率 12%”。值班在群里问“有人能看下吗”，另一位同时去查慢查询，两人各改一次配置并互相覆盖；二十分钟后才发现当天 09:40 发布过支付客户端 v2.3.1，回滚只需三分钟。客服改手工登记，积压 217 笔；事后没人复盘，三周后同一问题复发。

三个问题都不是技术难题：**没人说清这次多严重、谁在指挥、何时必须升级**。响应通常失败在协调上，而不是知识上。

> **核心结论：** 响应的目标不是先找根因，而是用分级确定谁在多长时间内做什么，先止损，再用可跟踪的改进项把这次故障换成系统免疫力。

## 学习目标

完成本课后，你能够：

- 依据影响面为故障定级，写出对应的通知范围与响应时限。
- 描述四个响应角色的分工，说明止损先于根因的理由。
- 写出一次事件的声明、升级与结束条件。
- 按模板产出含时间线、影响量化、促成因素与改进项的复盘，并判断可否验收。

- 能读带时区的 ISO 8601 时间戳，例如 `2026-04-17T10:02:00+08:00`。

## 业务场景

本课继续看晴空商城的退款集成服务，侧面换成上线后的一次真实故障：

- 退款横跨商城、支付商、仓储与客服，资金在支付商一侧。
- 客服 40 人，10:00–12:00 是退款高峰，报错直接变成人工登记与积压。
- 公司只有 1 名值班工程师，白天能召回到开发与架构师。
- 管理层要求：影响资金或半数用户的事件 15 分钟内有人声明，2 小时内给客服一句可对外的口径。

架构师要交付的不是“更强的监控”，而是分级标准、角色分工表与复盘模板。

## 核心概念

*故障（incident）*是造成或即将造成业务影响、需要协调响应而非单人顺手修掉的事件。<u>一个 bug 不等于一次故障，分界是“是否需要协调”。</u>*影响面*指受影响用户比例、受损功能、资金或数据是否出错；*故障分级*把影响面映射到有限几档，每档固定通知对象与响应时限。

| 级别 | 判定口径（其一即定级） | 通知范围 | 响应与更新 | 典型情形 |
| --- | --- | --- | --- | --- |
| SEV1 | 资金或数据错误；半数用户主流程不可用 | 值班、技术、业务负责人 | 5 分钟响应，30 分钟一更 | 一笔退款被退成两次 |
| SEV2 | 一成以上用户不可用且无替代路径 | 值班、模块负责人、客服 | 15 分钟响应，60 分钟一更 | 退款提交全部 5xx |
| SEV3 | 局部受损但有替代路径 | 值班与模块负责人 | 2 小时内响应，当日更新 | 回调延迟，刷新可见 |
| SEV4 | 仅内部可见，无用户影响 | 值班 | 次工作日处理 | 对账报告晚生成 |

*止损（mitigation）*是让业务恢复可用或可控的动作：回滚、切流、限流、关开关、人工兜底，不要求找到根因。*事件指挥（Incident Commander，IC）* 是事件期间唯一决定优先级与资源的人；*升级（escalation）* 按时间或影响触发，把更强的人拉进来。

| 角色 | 负责 | 不负责 | 谁担任 |
| --- | --- | --- | --- |
| 事件指挥 IC | 定级、优先级、是否回滚 | 亲自排查 | 值班，SEV1 移交架构师 |
| 操作负责人 | 执行回滚、切流、补数据 | 决定做不做 | 支付团队开发 |
| 沟通负责人 | 对客服与供应商发布更新 | 判断技术细节 | 客服主管 |
| 记录员 | 时间、动作、结果与决定 | 参与决策 | 当班另一人 |

*复盘（postmortem）*是事件结束后对时间线、影响、促成因素与改进项的结构化回顾；*无责复盘*假定当事人在当时信息下做了合理判断，追问“什么让这个错误容易发生”而非“谁犯了错”。*促成因素* 是共同导致事件的一组条件，替代单一的“根因”；*改进项* 是带负责人、期限与验证方式的行动。

<u>级别由影响面决定，不由修复难度、系统数量或谁先发现决定。</u>只影响 3 个用户但退错钱的是 SEV1；刷新两次就正常的抖动只是 SEV4。

## 工作原理

一次故障处理按时间顺序展开为八个步骤：

1. **检测**：告警、工单、投诉、对账差异都是入口；第一个信号的时间是一切时长的起点。
2. **确认**：值班 5 分钟内判断真假，误报关掉并记录原因，否则下次没人信告警。
3. **分级**：按影响面判定，级别写进频道标题，让所有人看到同一事实。
4. **声明与组织**：按级别通知并指定角色；<u>没人认领时，第一个声明事件的人默认是 IC</u>。
5. **止损**：先做几分钟内可逆的动作降影响，动作的时间与结果都记，失败也记。
6. **升级**：时间盒到期或影响扩大就升级，如 SEV2 超 30 分钟未止损拉架构师；<u>升级不是认输</u>。
7. **恢复与观察**：指标回到阈值并持续一个观察窗（如 30 分钟）才算恢复，积压与对账在此清掉。
8. **关闭与复盘**：结束条件是积压清零、口径已发；48 小时内出时间线草稿，SEV1 五个工作日内复盘。

关键是：**先定级才有协调，先止损才有时间，先有时间线才有复盘**；跳过第 3、6 步，响应就退化成各自努力。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要权衡 |
| --- | --- | --- | --- |
| 四级分级（SEV1–SEV4） | 涉及资金、合规或 7×24 值班 | 两三人团队、故障极少 | 区分度够用，定义需季度校准 |
| 三级分级（P1–P3） | 只需区分叫醒、工作时间、次日 | 需按级别区分对外通告 | 省心，边界事件容易归错 |
| 专职值班轮转 | 请求量大、故障频繁 | 只有一名工程师 | 响应稳定，成本与疲劳并存 |
| 群聊加文档模板 | 起步阶段、零预算 | 需审计、跨时区协同 | 零成本，证据易散落 |

级别数取决于需要区分多少种“行为差异”：只需区分“叫醒与不叫醒”时三级就够；涉及资金错误则必须有一档能立刻拉业务负责人。工具只选能长期维护的，<u>买了没人用的工具比群聊更危险，它让人以为已有流程</u>。

## 最小示例

脚本把事件 JSON 算成可复述的时长与建议级别，并检查改进项是否可验收。环境为 Python 3.9+、无第三方依赖；退出码 `0` 表示合格，`1` 表示有缺项，`2` 表示时间线缺关键节点。

```python
import json              # 事件数据以 JSON 传入，便于对接工单系统
import sys               # 结论不合格时用退出码表达
from datetime import date, datetime   # 时长按分钟算，期限按日期比

# 规则按顺序匹配，第一条命中即结论；顺序体现“资金与数据优先”
GRADES = [
    ("SEV1", lambda i: i.get("money_gap_orders", 0) > 0, "资金或数据错误，只能人工补救"),
    ("SEV1", lambda i: i.get("affected_user_ratio", 0) >= 0.5, "半数以上用户主流程不可用"),
    ("SEV2", lambda i: not i.get("has_workaround", True) and i.get("affected_user_ratio", 0) >= 0.1, "无替代路径且影响至少一成用户"),
    ("SEV2", lambda i: i.get("failed_requests", 0) >= 1000, "失败请求规模已达千级"),
    ("SEV3", lambda i: i.get("affected_user_ratio", 0) > 0, "有替代路径的局部受损"),
]


def grade(impact):
    for name, rule, reason in GRADES:      # 命中即返回，避免给出两个级别
        if rule(impact):
            return name, reason
    return "SEV4", "仅内部可见或指标轻微偏移"


def first_events(entries):
    events = {}
    for entry in entries:
        ts = datetime.fromisoformat(entry["ts"])   # 带时区的时间戳可直接相减
        events.setdefault(entry["kind"], ts)       # 同类只留最早一次，重复告警不影响时长
    return events


def minutes(start, end):
    return int((end - start).total_seconds() // 60)


def lint(actions, incident_day):
    problems = []
    for action in actions:
        if not action.get("owner"):                # 没有负责人就没人对结果负责
            problems.append(f"{action['id']} 缺负责人")
        if not action.get("verify"):               # 没有验证方式就判断不了是否生效
            problems.append(f"{action['id']} 缺验证方式")
        try:
            due = date.fromisoformat(action.get("due", ""))
        except ValueError:
            problems.append(f"{action['id']} 截止日期不是 ISO 日期")
            continue
        if (due - incident_day).days > 30:         # 超过一个月的改进项常被遗忘
            problems.append(f"{action['id']} 期限超过 30 天")
    return problems


def main(path):
    data = json.load(open(path, encoding="utf-8"))
    events = first_events(data["timeline"])
    missing = [k for k in ("alert", "ack", "mitigated", "resolved") if k not in events]
    if missing:                                    # 缺节点算出的时长没有意义
        print("时间线缺少关键节点: " + ",".join(missing))
        return 2
    sev, reason = grade(data["impact"])
    print(f"{data['id']} 建议分级={sev}（{reason}）")
    print(
        f"检测到响应={minutes(events['alert'], events['ack'])}min "
        f"响应到止损={minutes(events['ack'], events['mitigated'])}min "
        f"止损到恢复={minutes(events['mitigated'], events['resolved'])}min "
        f"总影响={minutes(events['alert'], events['resolved'])}min"
    )
    incident_day = datetime.fromisoformat(data["timeline"][0]["ts"]).date()
    problems = lint(data["actions"], incident_day)
    print(f"改进项={len(data['actions'])} 待补={len(problems)}")
    for problem in problems:                       # 指到具体改进项
        print(f"  - {problem}")
    return 0 if not problems else 1


if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1]))
```

`incident.json` 记五个节点、影响面与两条改进项，A2 故意缺负责人与验证方式。

  "timeline": [

    {"ts": "2026-04-17T10:06:00+08:00", "kind": "ack", "actor": "oncall-zhang", "note": "客服确认提交失败"},

运行方式与预期输出：

```bash
$ python3 incident_review.py incident.json
INC-2026-0417 建议分级=SEV2（无替代路径且影响至少一成用户）
检测到响应=4min 响应到止损=25min 止损到恢复=34min 总影响=63min
改进项=2 待补=2
  - A2 缺负责人
  - A2 缺验证方式
$ echo "退出码=$?"
退出码=1
```

三处设计选择值得说明。**“资金或数据错误”放在第一条**，因为退错钱不可逆；`setdefault` 只留同类第一次，重复告警不会把响应算成 0；`lint` 只检 owner、verify、due 三个可机检字段。

## 动手实验

**前置条件**：本机有 `python3`（3.9+）与可写临时目录；不需要网络、依赖包或数据库。

1. 在临时目录写入 `incident_review.py` 与 `incident.json`，确认文件为 UTF-8。
2. 运行 `python3 incident_review.py incident.json`，记录级别、四段时长与退出码。
3. 把 A2 的 `owner` 改为 `icu-team`、`verify` 改为“回放 3 次历史告警只触发 1 次”，重跑并对比。
4. 把 `money_gap_orders` 改为 `2`，重跑，对照分级表解释级别为何变化。
5. 删掉 `timeline` 中 `kind` 为 `mitigated` 的行，重跑，观察退出码与提示。

**预期结果**：第 2 步为 `建议分级=SEV2`、`4 / 25 / 34 / 63` 分钟、`待补=2`、退出码 `1`；第 3 步 `待补=0`、退出码 `0`；第 4 步变为 `SEV1`；第 5 步输出 `时间线缺少关键节点: mitigated`、退出码 `2`。

**验证方法**：用 `echo $?` 读退出码；手算一段时长核对，例如 `10:06` 到 `10:31` 应为 25 分钟。

**清理方法**：删除临时目录与两个文件。**<u>不要留在共享目录里，事件材料含订单与金额信息。</u>**

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 两人同时改配置互相覆盖 | 没有唯一 IC 与操作记录 | 看频道是否有 IC 声明与逐条动作 | 声明 IC，操作与记录分离 |
| SEV1 全公司被叫醒，或没人接手 | 按系统分级，通知名单过期 | 抽 3 个历史事件核对级别与通知人 | 按影响面重写分级 |
| 复盘会开成追责会 | 无责前提未声明，管理层点评个人 | 读文档是否出现人名与“本应该” | 开场声明无责，只写系统条件 |
| 改进项 20 条，三个月完成 2 条 | 无负责人、无期限、不可验收 | 抽查每条的 owner、due、verify | 每次限 3–5 条，进看板周查 |
| 同一故障一季度内复发 | 改进项只做“加强监控” | 对比两次时间线的促成因素 | 让动作改变系统而非提醒人 |

## 安全与生产注意事项

**<u>应急期间不要在生产上直接改数据或“手工平账”而没有第二人复核与操作记录。</u>** 一笔 5000 元的冲正写成 50000 元，或删掉唯一能证明原始状态的记录，事后查不出改过哪些行。缓解办法是写操作走带参数的脚本、双人核对、先备份旧值，并记下执行人与影响行数。

**<u>复盘文档与事件频道里不要粘贴客户手机号、身份证、支付凭据或完整请求体。</u>** 复盘会发给更广的人群并长期留存，等于一次数据扩散；安全事件在修复前公开利用细节，还会给攻击者提供路线。缓解办法是用订单号与哈希化标识代替个人信息，敏感证据单独存放。

## 本课总结

- 分级依据影响面：资金或数据是否出错、影响多少用户、有无替代路径。
- 响应期的核心是**唯一指挥与角色分工**，IC 不亲自排查。
- **止损优先于根因**：先做可逆动作降影响，恢复后再追促成因素。
- 复盘要产出可验收改进项：负责人、期限、验证方式齐全。

## 思考题

晴空商城只有 1 名值班工程师，团队希望引入 SEV1–SEV4 四级分级。你会照搬吗？请说明保留几级、判定口径与通知对象，以及何时需要重新设计。

参考思路：级别数应等于团队真正会采取不同行动的种类数。若只有“叫醒第二人”“工作时间处理”“次日处理”三种行为，三级已够；但资金与数据错误必须直接触发最高级，这一条要写死在判定口径里。当值班人数增加或引入对外 SLA 时再重新评估。

## 小测

1. 故障分级最应依据什么？  
   A. 涉及的系统数量　B. 影响面与资金或数据后果　C. 修复难度　D. 谁先发现
2. 止损与根因修复的区别是什么？应急阶段为什么通常先止损？
3. 事件指挥（IC）应该亲自排查问题吗？为什么？
4. 一条可验收的改进项需要哪三个要素？请为“告警太吵”写出一条符合要求的改进项。
5. 场景题：复盘会上一位工程师说“是我把配置改错了”。主持人下列哪种回应符合无责复盘？  
   A. 记录“某某操作失误”并纳入绩效　B. 追问“当时什么信息让你认为这个改动是安全的，系统为什么允许它直接生效”　C. 跳过以免尴尬　D. 让他在全员会上道歉

## 答案与解析

1. **B。**通知范围与响应节奏只能由业务后果推出。A 系统多不代表用户受影响；C 影响小的故障不该占用最高级资源；D 与严重程度无关。
2. 止损让业务恢复可控（回滚、切流、关开关），不解释机制；根因修复从机制上消除问题。应急期先止损，因为影响在累积而定位时间不可控，<u>“先查清再动手”会把 30 分钟的故障拖成 3 小时</u>。
3. 不应该。IC 负责定级、优先级、资源与是否回滚；亲自排查会失去全局视角，也没人统一发布状态。小团队可兼任操作，但要写明“我以 IC 身份决定回滚”。
4. 负责人、期限、验证方式。示例：把“告警太吵”改成“退款 5xx 告警持续 5 分钟且错误率 ≥ 2% 才触发”，owner 为 icu-team，2026-04-24 前完成，验证方式是回放 3 次历史告警只触发 1 次。只写“加强告警”不算改进项。
5. **B。**它把个人失误转成系统问题，能产出改变系统的改进项。A 与 D 会让下次没人敢说真话；C 丢掉了最有价值的线索——当事人最清楚当时的判断依据。
