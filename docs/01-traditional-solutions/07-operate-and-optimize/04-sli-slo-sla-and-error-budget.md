# SLI、SLO、SLA 与错误预算

## 为什么需要学习

晴空商城的退款集成服务上线三个月后，团队每周都要争论一次"系统到底稳不稳定"：运维说监控可用性 100%，客服主管说昨天有 40 个客户问"退款为什么还没到"。没人能回答：昨天的故障算不算违约？剩下的可靠性额度还够不够这周发版？

没有这套语言，稳定性只能靠"有没有人投诉"判断，发布节奏由声音最大的人决定：运维倾向少发版，产品倾向多发版，争论无法收敛。

> **核心结论：** 稳定性必须写成可计算的定义、明确的目标和事先约定的决策规则，否则它只是一个形容词。

## 学习目标

完成本课后，你能够：

- 为一个用户旅程写出可计算的 SLI，并说明好事件、分母和统计窗口。
- 区分 SLI、SLO 与 SLA，说清三者分别约束谁、谁带赔偿。
- 用历史请求数据计算错误预算余额与燃尽率，并给出发布建议。
- 编写一条包含触发条件、决策人和例外通道的错误预算政策。

## 前置知识

- 知道 counter、histogram 和 p95/p99 百分位数的含义，能读懂一条 `rate()` 查询。

## 业务场景

退款集成服务把客服的退款操作转成支付指令并回写结果。用户旅程从"客服点击受理退款"到"客户银行卡收到钱"，中间跨三个系统。

本单元要处理这条旅程的稳定性侧面：

- **受理接口**：客服点击后必须在 2 秒内拿到受理编号，否则页面超时、客服重复提交。
- **完成时延**：支付供应商 SLA 承诺 99.5% 的请求 T+1 到账，大额退款还要人工审核。
- **发布节奏**：平时两周一次，黑五前连发 6 次，每次都在改退款金额校验和重试逻辑。
- **已知争议**：上个月支付回调超时 3 小时，服务端指标仍显示 100% 成功，因为超时请求被记为"已受理待回调"。

于是必须回答：3 小时回调超时该不该消耗额度？额度用完后谁有权说"这周不发版"？对商家的"两个工作日到账"和内部工程目标是不是一回事？

## 核心概念

| 概念 | 定义 | 晴空商城中的例子 |
| --- | --- | --- |
| *SLI*（服务等级指标） | 用可观测数据算出的服务质量数值，通常写成"好事件 ÷ 有效事件" | 近 28 天内 3 秒内成功受理的退款请求占比 |
| *SLO*（服务等级目标） | SLI 在指定窗口内要达到的目标值，是内部工程目标 | 28 天内受理成功率 ≥ 99.9%，时延 p95 ≤ 2 秒 |
| *SLA*（服务等级协议） | 与客户或供应商签订的合同条款，含违约责任与赔偿 | 对商家承诺两个工作日内到账，否则减免手续费 |
| *错误预算* | `1 - SLO`，一个窗口内允许出现的坏事件总量 | 99.9% 的 SLO 意味着每 1000 次请求允许 1 次失败 |
| *燃尽率*（burn rate） | 当前错误率 ÷ 预算允许的错误率，表示消耗速度 | 燃尽率 14.8 表示按此速度预算两天内烧完 |
| *错误预算政策* | 预算消耗到约定水平时自动生效的行动规则 | 剩余预算低于 25% 时冻结非紧急发布 |

**SLO 是对内的工程承诺，SLA 是对外的商业承诺。**SLO 必须比 SLA 更严格，差额用来吸收监控盲区、人工处置时间和供应商波动。<u>把 SLO 直接写成 SLA 的数值，等于放弃所有缓冲。</u>

SLI 的定义决定体系是否可信，因此要把"好事件"和"分母"写死：

| SLI 类型 | 好事件 | 分母（有效事件） | 适用场景 |
| --- | --- | --- | --- |
| 可用性 | 返回 2xx 且在阈值内完成 | 到达服务端的有效请求，排除已鉴权失败的 401 | 受理接口、查询接口 |
| 时延 | 在 2 秒内完成 | 所有成功与失败的请求 | 客服页面依赖的同步接口 |
| 正确性 | 退款金额与订单金额一致 | 已完成退款的单据数 | 资金类流程，需对账数据 |
| 新鲜度 | 状态更新时间差 ≤ 5 分钟 | 所有已变更状态的单据 | 回调、对账、仓库同步 |

时延类 SLI 用"比例"而不是"平均值"表达。<u>平均时延 300 毫秒完全可能掩盖 2% 请求耗时 30 秒。</u>

## 工作原理

稳定性治理沿一条数据流运转，从用户旅程出发，最终回到发布决策：

1. **选旅程，不选组件。** 先确定"受理退款"这条旅程，再决定看哪些服务、队列和依赖。按组件建 SLO 会得到一堆各自达标、整体仍不可用的目标。
2. **定义好事件与分母。** 与产品、客服确认：3 秒从服务端收到请求算起；超时、5xx、限流都算坏事件；客户端主动取消不计入分母。定义写进文档并评审。
3. **采集并聚合。** 应用用 counter 记录 `result`、histogram 记录耗时；Prometheus 抓取、Grafana 渲染；日志留存原始样本，供口径争议时回溯。
4. **按窗口计算 SLI。** 常用 28 天滚动窗口：每次都覆盖最近 28 天，不因月初归零而产生"月初随便花、月末再省"的博弈。
5. **换算错误预算。** 预算是数量不是百分比：`(1 - SLO) × 窗口有效请求数`。窗口内 114.7 万次请求、SLO 99.9%，预算约 1147 件坏事件。
6. **计算燃尽率。** 用 1 小时或 6 小时窗口算当前错误率，再除以预算允许的错误率。燃尽率 1 表示刚好按计划花完，14.8 表示两天就烧完。
7. **触发政策。** 余额与燃尽率共同决定发布状态：充足则正常发布，见底则冻结非紧急变更，透支则只保留回滚与修复。
8. **复盘并修正定义。** 查清预算花在哪：真实故障、供应商抖动还是口径错误。口径错误回到第 2 步，真实故障进入改进清单。

关键直觉是：**错误预算把可靠性从主观感受变成一笔可支出的额度。**发版前不必再争论风险，只看余额；额度花完后必须用工程手段赚回来。

## 架构与选型

| 决策点 | 选项 | 适用条件 | 代价与不适用 |
| --- | --- | --- | --- |
| SLI 数据来源 | 服务端指标 / 合成探测 / 客户端 RUM / 业务对账 | 指标完整用服务端；入口无埋点用探测；体验优先用 RUM；资金用对账 | 服务端指标看不见网络与客户端等待；RUM 有采样偏差；对账滞后半天 |
| 统计窗口 | 滚动 28 天 / 自然月 / 7 天 | 常规业务用滚动 28 天；与财务周期对齐用自然月；快速迭代用 7 天 | 窗口越短越容易被单次故障击穿，也越容易掩盖低频故障 |
| SLO 粒度 | 单一全局 SLO / 按旅程分级 / 按租户 | 小团队用单一；多链路用分级；大客户合同用按租户 | 分级过多导致预算分散、无人负责 |
| 政策严格度 | 软性提醒 / 硬性冻结 | 内部工具可软性；资金链路应硬性 | 软性政策在压力下常被绕过，需要决策人背书 |
| 目标值 | 99.9% / 99.95% / 99.99% | 按实测水平与用户容忍度定 | 目标高于实测能力会长期欠账，等于没有预算 |

选型先算分辨率：窗口内请求量只有 3000 次时，99.9% 的预算不足 3 件坏事件，一次重试风暴就会透支，此时应改用"每月允许 3 次失败"的错误数预算。变更频繁的团队选短窗口配硬性政策；对外承诺先由业务和法务定 SLA，再往下拆出有余量的 SLO。

供应商 SLA 不能当作自己的 SLO：对方承诺 99.5%，每月可能有 3.6 小时不可用，端到端目标必须把它算进预算，或用降级、重试和异步补偿吸收。

## 最小示例

目标：用 28 天每日聚合数据算出退款受理接口的 SLI、预算余额、燃尽率，并给出发布建议。环境为 Python 3（仅标准库），输入是内嵌 CSV。

```python
#!/usr/bin/env python3
"""退款受理接口的 SLI 与错误预算计算器（仅用标准库）。"""

import csv
import io

SLO = 0.999          # 28 天目标：99.9% 的请求在 3 秒内被成功受理
BURN_WARN = 2.0      # 燃尽率警戒线：错误速度达到预算速度的 2 倍
FREEZE_AT = 0.25     # 剩余预算低于 25% 时冻结非紧急发布

# 输入：每个自然日一条聚合记录。total 是分母（全部受理请求），good 是分子（好事件）
RAW = """date,total,good
2026-09-22,40120,40106
2026-09-23,39870,39854
2026-09-24,41720,41701
2026-09-25,42310,42295
2026-09-26,43680,43662
2026-09-27,42900,42885
2026-09-28,39640,39622
2026-09-29,38950,38937
2026-09-30,37710,37694
2026-10-01,36420,36405
2026-10-02,35880,35868
2026-10-03,37140,37124
2026-10-04,38060,38045
2026-10-05,39440,39427
2026-10-06,40890,40871
2026-10-07,41230,41212
2026-10-08,40980,40963
2026-10-09,41550,41536
2026-10-10,44120,44101
2026-10-11,43870,43849
2026-10-12,42030,42012
2026-10-13,41160,41147
2026-10-14,40620,40605
2026-10-15,41980,41958
2026-10-16,43320,43304
2026-10-17,44710,44688
2026-10-18,45260,45239
2026-10-19,41000,40395
"""


def load_rows(text):
    """把 CSV 文本解析成 (日期, 总请求数, 好事件数) 列表。"""
    reader = csv.DictReader(io.StringIO(text))
    return [(row["date"], int(row["total"]), int(row["good"])) for row in reader]


def build_report(rows, slo):
    """算出窗口 SLI、预算余额和最近一天的燃尽率。"""
    total = sum(row[1] for row in rows)                    # 窗口分母
    good = sum(row[2] for row in rows)                     # 窗口分子
    bad = total - good                                     # 实际消耗的坏事件
    allowed = total * (1 - slo)                            # 预算换算成坏事件件数才能相减
    last_total, last_good = rows[-1][1], rows[-1][2]
    burn = (last_total - last_good) / last_total / (1 - slo)  # 当前错误率 ÷ 预算错误率
    return {"total": total, "sli": good / total, "allowed": allowed,
            "remaining": allowed - bad, "burn": burn}


def decide(report):
    """把预算状态翻译成发布决策，避免每次重新争论要不要发。"""
    if report["remaining"] <= 0:                            # 透支：只允许止血
        return "FREEZE 冻结全部功能变更，仅保留回滚与可靠性修复"
    if report["remaining"] / report["allowed"] < FREEZE_AT:  # 预算见底
        return "SLOW 冻结非紧急发布，先复盘最近一次故障"
    if report["burn"] >= BURN_WARN:                         # 消耗速度失控
        return "WARN 暂停功能发布，观察 1 小时燃尽率"
    return "GO 按正常节奏发布"


def main():
    report = build_report(load_rows(RAW), SLO)
    print(f"SLO 目标        {SLO:.3%}")
    print(f"SLI 实测        {report['sli']:.4%}")
    print(f"错误预算        {report['allowed']:.0f} 件坏事件")
    print(f"预算余额        {report['remaining']:.0f} 件，占预算 {report['remaining'] / report['allowed']:.1%}")
    print(f"最近一天燃尽率  {report['burn']:.1f}x")
    print(f"发布建议        {decide(report)}")


if __name__ == "__main__":
    main()
```

运行 `python3 slo_budget.py`，预期输出：

```text
SLO 目标        99.900%
SLI 实测        99.9080%
错误预算        1147 件坏事件
预算余额        92 件，占预算 8.0%
最近一天燃尽率  14.8x
发布建议        SLOW 冻结非紧急发布，先复盘最近一次故障
```

`load_rows` 只负责解析，方便日后替换为 Prometheus 查询结果；`build_report` 把百分比换算成坏事件件数，因为只有同单位才能相减；`decide` 把预算状态映射为唯一决策，避免同一份数据被解读成不同结论。燃尽率只比较最近一天，反映当前速度，窗口平均会稀释昨天的故障。

同一份数据也可以用 PromQL 表达，便于接到 Grafana 与告警：

```promql
# 受理成功率：好事件 ÷ 全部有效请求
sum(rate(refund_requests_total{result="accepted"}[28d]))
/
sum(rate(refund_requests_total[28d]))

# 1 小时燃尽率：当前错误率 ÷ 预算允许的错误率（SLO 99.9%）
sum(rate(refund_requests_total{result!="accepted"}[1h]))
/
sum(rate(refund_requests_total[1h]))
/
0.001
```

## 动手实验

### 任务：为退款受理接口定 SLO，并看窗口与目标如何改变结论

**前置条件**：本机有 `python3`（3.8 以上）；把上面的脚本保存为 `/tmp/slo_budget.py`；不需要 Prometheus 或网络。

**步骤**：

1. 运行 `python3 /tmp/slo_budget.py`，记录 SLI、预算余额、燃尽率和发布建议。
2. 把 `SLO = 0.999` 改成 `SLO = 0.9995`，重跑，记录预算余额变化。
3. 删掉 `RAW` 中前 21 行数据，只留最后 7 天，把 SLO 改回 `0.999`，重跑。
4. 针对晴空商城写一条政策，必须包含：触发条件、生效动作、决策人、例外通道、恢复条件。

**预期结果**：

| 变体 | SLI | 预算余额 | 燃尽率 | 发布建议 |
| --- | --- | --- | --- | --- |
| 28 天，SLO 99.9% | 99.9080% | 92 件（8.0%） | 14.8x | SLOW 冻结非紧急发布 |
| 28 天，SLO 99.95% | 99.9080% | -482 件（-84.0%） | 29.5x | FREEZE 只允许回滚与修复 |
| 7 天，SLO 99.9% | 99.7604% | -416 件 | 14.8x | FREEZE 只允许回滚与修复 |

**验证方法**：第 2 步余额约减半：预算从 1147 件降到 573 件，坏事件不变；第 3 步 SLI 掉到 99.76%，低于 99.9%，说明这条链路在 7 天窗口内未达标。<u>如果两次结论相反而你说不出原因，就把窗口和目标值写进 SLO 文档。</u>

**清理方法**：`rm /tmp/slo_budget.py`，本实验不改动仓库中的任何文件。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 服务端 SLI 接近 100%，客服仍报"页面卡死" | 只统计服务端成功响应，未含客户端等待、重试和网关超时 | 对比服务端时延 p95 与浏览器端到端时延 | 增加端到端 SLI（合成探测或 RUM），网关超时计入坏事件 |
| 错误预算长期为负，但没人改变行为 | 政策只有数字，没有决策人、触发动作和例外通道 | 检查历史上是否有因预算触发的发布冻结记录 | 补全政策五要素，指定唯一决策人并公告 |
| SLO 定为 100%，团队直接放弃使用 | 目标不可达成，预算恒为零 | 查历史 90 天最好水平与最低错误率 | 按实测水平加余量设定，并说明每月允许的故障时长 |
| 一个月三次小故障就耗尽预算 | 分母过窄导致分辨率不足 | 用 `预算 ÷ (1-SLO)` 反算有效请求量 | 改用错误数预算，或拉长窗口到 28 天 |
| 告警一天触发几十次，值班开始忽略 | 直接用瞬时错误率或单点阈值告警，抖动大 | 统计一周内告警次数与其中真实故障占比 | 改用多窗口燃尽率告警，并设置最小持续时间 |

## 安全与生产注意事项

**<u>不要为了让预算看起来健康而修改 SLI 的分子、分母或统计窗口。</u>**后果是真实故障被口径抹平：3 小时的支付回调超时被记成"已受理待回调"，大盘依旧绿色，直到客户投诉才发现；历史数据也失去可比性。缓解办法是 SLI 定义评审留档，并保留原始 counter 供回溯。

**<u>错误预算耗尽却不冻结发布，等于把已知风险持续叠加到生产。</u>**连续发版若共享同一根因（例如同一段退款金额校验），故障窗口被延长，SLA 赔偿与信任损失随之放大。<u>政策必须写明触发条件、决策人、例外通道和回滚预案，否则它只是一个装饰性图表。</u>

指标标签不要写入 `order_id` 或用户标识，否则造成高基数并泄露个人信息，SLI 只按 `result` 等低基数维度切分。**SLA 赔偿条款由业务与法务确认**，工程侧只提供测量口径。

## 本课总结

- **SLI 是可计算的测量定义，SLO 是带窗口的目标值，SLA 是带赔偿的对外合同。**三者不可互换。
- 好事件与分母必须事先写死并评审，口径变更要留档。
- 错误预算等于 `(1 - SLO) × 窗口有效请求数`，把可靠性变成可支出的额度。
- 燃尽率反映消耗速度，与余额配合才能区分"已经出事"和"正在快速出事"。
- 预算是发布决策的输入：GO、WARN、SLOW、FREEZE 应事先约定。

## 思考题

支付供应商的 SLA 是 99.5%，晴空商城能否对商家承诺"退款两个工作日内到账"并给这条旅程定 99.9% 的 SLO？请说明判断依据，并指出需要补充哪些工程措施或合同条款才能让承诺成立。

参考思路：端到端目标受最弱依赖约束，供应商每年约 44 小时不可用，理论上无法在所有时段支撑 99.9% 的到账承诺。可行方向：承诺改为"受理后 T+1 完成，超时自动补偿"、增加手工放款通道、用异步重试与状态补偿吸收抖动、按受理而非到账计时，并在合同中写明例外。评价标准是能否讲清目标值、测量口径、依赖边界和补偿机制。

## 小测

1. 用一句话说明 SLI 与 SLO 的关系。
2. 28 天窗口内有效请求为 200 万次，SLO 为 99.9%，错误预算是多少？  
   A. 200 件　B. 2000 件　C. 20000 件　D. 999000 件
3. 判断：SLA 的数值应当比内部 SLO 更严格，以留出缓冲。
4. 某接口燃尽率为 6，最准确的解读是？  
   A. 预算还剩 6 倍　B. 当前错误率是预算允许错误率的 6 倍　C. 6 小时后必定耗尽　D. 窗口内发生了 6 次故障
5. 场景题：28 天 SLI 为 99.92%，高于 99.9% 的目标，但剩余预算只有 5%、最近一天燃尽率 12 倍，产品负责人要求今晚发布新功能。作为架构师，你会怎么处理？

## 答案与解析

1. **SLI 是测量值，SLO 是给这个测量值设定的目标。**SLI 回答"现在是多少"，SLO 回答"必须达到多少、在多长时间内"。
2. **B。**`2000000 × (1 - 0.999) = 2000`。A 是 99.99% 的预算，C 误把 1% 当成 0.1% 又放大十倍，D 把好事件数当成了预算。
3. **错。**方向相反：SLO 应比 SLA 更严格，内部目标要吸收监控盲区、人工处置时间和供应商波动。若 SLO 不严于 SLA，团队会在违约后才收到内部信号。
4. **B。**燃尽率是错误率与预算错误率之比，表示消耗速度。A 把倍数误解为剩余量；C 忽略请求量，同样燃尽率在不同流量下耗尽时间不同；D 把速度指标当成故障计数。
5. 应触发政策：预算见底（5% 低于 25%）意味着冻结非紧急发布，只放行修复类变更，燃尽率 12 倍的时段作为复盘输入。业务若坚持发布，须由政策指定的决策人书面接受风险，约定回滚阈值。**SLI 仍高于目标不等于安全**：SLI 是滞后结果，燃尽率和余额才是领先信号。

### 动手实验参考

第 2 步预算从 1147 件降至 573 件，坏事件 1055 件不变，余额由 +92 变为 -482，结论从 SLOW 升级为 FREEZE。第 3 步 7 天窗口只覆盖 29.8 万次请求、坏事件 714 件，SLI 为 99.7604%，直接低于目标。政策示例：剩余预算低于 25% 时冻结非紧急发布，决策人为服务负责人，例外需产品与运维双签，恢复到 50% 以上且燃尽率连续 6 小时低于 1 才解除。
