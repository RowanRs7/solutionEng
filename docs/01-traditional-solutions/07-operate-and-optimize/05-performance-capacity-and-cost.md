# 性能、容量、配额与成本

## 为什么需要学习

晴空商城的退款集成服务上线三个月后开了两次会。第一次是大促复盘：客服主管说 10:00–12:00 提交退款一直转圈，两小时退款目标拖成六小时；运维说应用 CPU 只有 35%，加机器也没用。第二次是月度预算会：财务说退款相关账单比上月涨了 42%，而退款笔数只涨了 8%，没人说得清多花的钱去了哪一层。

两次会问的是同一个问题：**这个服务在峰值时能扛多少，扛住它的每一笔要花多少钱。** 不会算在途请求，扩容就只是加机器；没有逐层上限，就找不到真正的瓶颈；没有成本归因，降本就会先砍掉最不该砍的东西。

> **核心结论：** 容量用数字回答"峰值时能否守住承诺"，成本用数字回答"守住它的每一笔值多少钱"；两者必须共用同一套口径，否则扩容与降本会互相拆台。

## 学习目标

完成本课后，你能够：

- 用利特尔法则算出峰值在途请求数，再结合冗余系数推导所需实例数并写成容量结论。
- 列出链路上四类上限（单实例并发、实例池、连接池、下游配额），指出最小那层即瓶颈。
- 为下游依赖写配额预算、限流与排队策略，并说明为什么加机器解决不了配额瓶颈。
- 用成本标签把账单归因到服务与环境，算出"元/笔"并排出优化顺序。
- 判断一次成本下降是真实提效，还是把质量、冗余或可观测性换成了钱。

## 前置知识

- 回看上一课：[SLI、SLO、SLA 与错误预算](04-sli-slo-sla-and-error-budget.md)。
- 知道 p95 延迟、吞吐量、错误率的含义，并认同平均值不能用于容量判断。
- 知道 HTTP `429` 表示调用方超出配额，`504` 表示上游没有按时返回。
- 能读懂"实例小时 × 单价"这类乘法账单，知道月账单由多项费用相加。

## 业务场景

本课继续看晴空商城的退款集成服务：订单在商城、资金在支付商、库存在仓储、沟通在客服。本单元的具体侧面是"大促前的容量与预算评审"：

- 峰值 60 QPS（40 位客服并发提交 + 自动重试），p95 ≤ 800ms，成功率 ≥ 99.5%。
- 支付商按商户号给 30 次/秒配额，超限返回 `429`，合同期内不可临时提额。
- 六个应用实例按峰值常备，实例费单列；监控与日志每月固定 300 元。
- 财务要求每个服务、每个环境看到自己的月度成本，退款业务要给出"元/笔"。
- 本季度预算只批 15% 增量，缺口必须靠排队、批量化或减少重试来补。

架构师要交付的不是一句"已扩容"，而是一句可复算的容量结论、一张逐层上限表，以及一份能指到责任人的成本归因。

## 核心概念

*容量模型*把业务峰值、请求耗时和资源上限换算成一句"可持续承载 X QPS，瓶颈在第 N 层"的判断。*在途请求*是同一时刻正在处理、尚未返回的请求数；按*利特尔法则*，`在途 = 到达速率 × 平均停留时间`。<u>用 p95 而不是平均值代入停留时间，否则算出的容量天然偏乐观。</u>*冗余系数*是给突发与实例故障预留的倍数。

*瓶颈*是链路上上限最低、最先被打满的那一层。*配额*是外部依赖按合同或平台策略给出的上限（每秒调用数、每日次数、并发数），通常不能临时调整。*限流*在超限前主动拒绝或排队，*熔断*在依赖持续失败时快速失败以保护上游。

*成本归因*是把账单里的钱指回具体的服务、环境和业务单元；*单位成本*是一个业务结果的平均成本，例如"每笔成功退款 0.0247 元"。*成本标签*是随资源创建的键值对，缺少标签的资源只能被硬分摊。

| 上限类型 | 由谁决定 | 晴空商城数值 | 超限后的表现 | 加机器能否解决 |
| --- | --- | --- | --- | --- |
| 单实例并发 | 应用线程/协程模型与内存 | 12 个在途请求 | 请求排队，p95 上升 | 能，加实例 |
| 实例池容量 | 实例数 × 单实例并发 | 6 实例 ≈ 90 QPS | 排队与超时 | 能，加实例 |
| 连接池上限 | 中间件与数据库配置 | 订单库 200 QPS | 获取连接超时 | 需改配置 |
| 下游配额 | 支付商合同 | 30 次/秒 | `429`，重试放大拥塞 | 不能，要改设计 |
| 预算上限 | 财务与业务 | 月度总额，增量 15% | 无法扩容 | 不能，要改取舍 |

**<u>四类上限里只有前两类能靠加机器解决。</u>** 把预算花在扩容上而瓶颈在配额，是容量评审中最常见的浪费。

## 工作原理

一次完整的容量与成本评审按顺序展开为十个步骤：

1. **定口径**：写清峰值 QPS 60、p95 800ms、成功判定为"返回受理编号"，统计窗口取大促峰值 3 小时。
2. **数在途**：`60 × 0.8 = 48` 个请求同时在处理。这个数字是所有资源需求的起点，比"QPS"更接近真实压力。
3. **算实例**：单实例在 p95 内可扛 12 个在途请求，`48 × 1.4 ÷ 12 = 5.6`，向上取整为 6 个，小数实例不能补缺口。
4. **逐层求上限**：实例池 `6 × 12 ÷ 0.8 = 90 QPS`，订单库 200 QPS，支付商 30 QPS，取最小值。
5. **写结论**：**"可持续承载 30 QPS，瓶颈在支付商配额；要覆盖 60 QPS 峰值，必须批量化调用或再申请一个商户号。"** 一句话含数值、瓶颈和出路。
6. **分配配额**：把 30 QPS 拆成人工受理 20、自动重试 8、日终对账 2，各自独立限流，一方打满不牵连其他两方。
7. **削峰排队**：超出配额的请求转为异步受理、返回任务号，用排队时间换吞吐，而不是直接拒绝。
8. **打标签**：实例、队列、日志按 `service=refund`、`env=prod`、`owner=payments` 打标，账单才能按维度归集。
9. **算单位成本**：`(实例费 + 支付调用费 + 固定费) ÷ 月成功退款数`，得到可跨月比较的"元/笔"。
10. **排优化顺序**：先看成本结构里占比最大的项，再决定是改重试、批量化还是缩容量。

顺序上的关键点是：**先口径再容量，先逐层上限再谈扩容，先成本结构再谈优化**。跳过第 4 步会出现"扩了容还是慢"，跳过第 9 步会出现"省了钱却说不清省在哪一层"。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要权衡 |
| --- | --- | --- | --- |
| 常备峰值容量 | 峰值可预测、失败代价高 | 峰值长期远低于配置 | 最稳，闲置成本高 |
| 弹性伸缩 | 负载波动大、实例启动快 | 启动慢或下游配额固定 | 省钱，扩容有分钟级延迟 |
| 异步排队削峰 | 业务可接受稍后完成 | 必须同步返回结果 | 保护下游，需任务状态与补偿 |
| 批量化调用 | 下游按次计费或限次数 | 每笔都需独立实时结果 | 省配额省钱，失败影响一批 |
| 预留/包年 | 基线负载稳定 | 业务方向未定 | 单价最低，锁定期长 |
| 标签展示分摊 | 需要团队建立成本意识 | 需要真实扣款与硬预算 | 推动优化，不产生实际转账 |
| 账户/项目隔离 | 需要真实计费与预算硬隔离 | 资源少、复用度高 | 最清晰，管理成本最高 |

选型依据是四项事实：峰值是否可预测决定常备还是弹性；下游配额是否可调决定削峰手段；失败代价决定冗余系数；组织是否需要真实扣款决定展示分摊还是账户隔离。晴空商城因此选择"基线常备 + 峰值弹性 + 异步排队 + 支付调用批量化 + 标签展示分摊"。

<u>不要同时启用"弹性缩容"和"固定配额"却不设队列：缩容后的一次突发会直接撞上配额，表现为大面积 `429` 而不是变慢。</u>

## 最小示例

问题：把上面的口径写成一段可复算的脚本，避免每次评审重新拍数。环境 Python 3.9+，只用标准库；输入是顶部常量（来自业务目标与合同，而非上一版报告）；输出是容量结论、配额缺口与两种容量策略的单位成本。

```python
import math                               # 只用标准库，保证结论可被任何人复算

# ---- 输入口径：业务目标与合同数字，逐项可追溯 ----
PEAK_QPS = 60.0                           # 大促峰值：40 客服并发 + 自动重试
P95_S = 0.8                               # 受理接口 p95，作为停留时间上限
HEADROOM = 1.4                            # 冗余系数：按需求的 1.4 倍备容量
PER_INSTANCE_CONCURRENCY = 12             # 单实例在 p95 内可承载的在途请求数
INSTANCE_HOURLY = 0.12                    # 单实例小时成本（元）
MONTHLY_HOURS = 730                       # 30 天折算小时数，与月账单对齐
PAY_CALL_FEE = 0.02                       # 支付商按调用次数收费（元/次）
MONTHLY_FIXED = 300.0                     # 监控与日志等固定月费
MONTHLY_REFUNDS = 1_200_000               # 月成功退款笔数，单位成本的分母
CALLS_PER_REFUND = 1.2                    # 含重试后每笔退款的支付调用次数

# 每层吞吐上限；None 表示该层由我们的实例池决定
STAGES = [("退款 API 实例池", None), ("订单库连接池", 200.0), ("支付商配额", 30.0)]


def inflight(qps, latency_s):
    """利特尔法则：在途 = 到达速率 × 停留时间。"""
    return qps * latency_s


def instances_for(qps, latency_s, concurrency, headroom):
    """按在途数反推实例数；向上取整，小数实例补不上缺口。"""
    return math.ceil(inflight(qps, latency_s) * headroom / concurrency)


def pool_capacity(count, latency_s, concurrency):
    """反向计算：这些实例最多稳定承载多少 QPS，写回容量结论。"""
    return count * concurrency / latency_s


def chain_capacity(api_capacity):
    """逐层取最小值，最小层即瓶颈；一并返回层名，便于直接写结论。"""
    stages = [(name, api_capacity if cap is None else cap) for name, cap in STAGES]
    return min(stages, key=lambda stage: stage[1])


def monthly_cost(instance_hours, calls_per_refund=CALLS_PER_REFUND):
    """把用量翻译成钱：实例按小时、支付按次数、其余为固定费。"""
    compute = instance_hours * INSTANCE_HOURLY
    pay = MONTHLY_REFUNDS * calls_per_refund * PAY_CALL_FEE
    return compute, pay, compute + pay + MONTHLY_FIXED


def unit_cost(total):
    """单位成本是唯一能与业务量一起比较的口径。"""
    return total / MONTHLY_REFUNDS


def main():
    count = instances_for(PEAK_QPS, P95_S, PER_INSTANCE_CONCURRENCY, HEADROOM)
    api_capacity = pool_capacity(count, P95_S, PER_INSTANCE_CONCURRENCY)
    bottleneck, limit = chain_capacity(api_capacity)       # 瓶颈名与上限一起取出
    print(f"在途请求={inflight(PEAK_QPS, P95_S):.1f}")
    print(f"所需实例数={count}（冗余 {HEADROOM}，单实例并发 {PER_INSTANCE_CONCURRENCY}）")
    print(f"实例池容量={api_capacity:.0f} QPS")
    print(f"链路容量={limit:.0f} QPS（瓶颈：{bottleneck}）")
    print(f"配额缺口={max(0.0, PEAK_QPS - limit):.0f} QPS")   # 缺口为 0 才说明峰值可达成

    # 方案 A：六个实例整月常备，按峰值买满 730 小时
    peak_compute, pay, peak_total = monthly_cost(MONTHLY_HOURS * count)
    # 方案 B：平时 2 实例，每天峰值 3 小时扩到 6 实例
    elastic_hours = MONTHLY_HOURS * 2 + 30 * 3 * (count - 2)
    elastic_compute, _, elastic_total = monthly_cost(elastic_hours)
    print(f"成本拆解：实例={peak_compute:.2f} 支付调用={pay:.2f} "
          f"固定={MONTHLY_FIXED:.2f} 合计={peak_total:.2f}")
    print(f"单位成本（峰值常备）={unit_cost(peak_total):.5f} 元/笔")
    print(f"单位成本（基线 2 实例 + 峰值弹性）={unit_cost(elastic_total):.5f} 元/笔")
    saving = peak_total - elastic_total
    print(f"弹性节省={saving:.2f} 元/月（{saving / peak_total:.2%}）")

    # 对照：重试的额外调用从 1.2 次降到 1.05 次能省多少
    retry_total = monthly_cost(elastic_hours, calls_per_refund=1.05)[2]
    print(f"重试 {CALLS_PER_REFUND:.2f}→1.05 节省={elastic_total - retry_total:.2f} 元/月")


if __name__ == "__main__":
    main()
```

预期输出：

```text
在途请求=48.0
所需实例数=6（冗余 1.4，单实例并发 12）
实例池容量=90 QPS
链路容量=30 QPS（瓶颈：支付商配额）
配额缺口=30 QPS
成本拆解：实例=525.60 支付调用=28800.00 固定=300.00 合计=29625.60
单位成本（峰值常备）=0.02469 元/笔
单位成本（基线 2 实例 + 峰值弹性）=0.02443 元/笔
弹性节省=307.20 元/月（1.04%）
重试 1.20→1.05 节省=3600.00 元/月
```

整体流程是：口径 → 在途 → 实例 → 逐层上限 → 瓶颈 → 成本 → 单位成本。三个设计选择值得注意：停留时间取 p95 而非平均值，结论才不偏乐观；瓶颈用 `min` 取最小值并带出层名，避免只看应用指标；成本拆解分项打印，因为**只有看见结构才能判断优化顺序**——本例弹性省 307 元，减少重试省 3600 元，是前者的 11 倍。

## 动手实验

**前置条件**：本机有 `python3`（3.9+）与可写临时目录；不需要外网、第三方包或云账号，支付费用全部按单价假设计算。

1. 在临时目录写下 `capacity.py`（内容见上），先运行 `python3 capacity.py` 记录全部十行输出。
2. 把 `HEADROOM` 改为 `1.0`，重跑，观察实例数、实例池容量与单位成本三项变化。
3. 恢复 `HEADROOM = 1.4`，把 `CALLS_PER_REFUND` 改为 `1.05`，重跑，比较节省金额与第 2 步的量级。
4. 把 `STAGES` 中支付商配额改为 `120.0`，重跑，确认瓶颈上移到哪一层、配额缺口变成多少。
5. 手工验算：`python3 -c "print(60*0.8, (6*12/0.8), (730*6*0.12+1200000*1.2*0.02+300))"`，与脚本输出对齐。

**预期结果**：第 2 步实例数由 6 降至 4、实例池容量由 90 降至 60 QPS、单位成本由 0.02469 降至 0.02454 元/笔，<u>但此时容量恰好等于峰值 60 QPS，任何抖动都会直接超目标</u>；第 2 步每月只省 175.20 元，第 3 步却省 3600.00 元/月，后者是前者的二十倍；第 4 步链路容量变为 90 QPS、瓶颈转为"退款 API 实例池"、缺口变为 0 QPS。

**验证方法**：脚本打印的"合计"与手工验算的括号表达式一致；把 `PEAK_QPS` 改为 `100.0` 后实例数变为 10、实例池容量 150 QPS，说明容量随口径线性变化；`配额缺口` 为 0 时才允许在容量结论里写"可覆盖峰值"。

**清理方法**：删除临时目录与 `capacity.py`。脚本只含假设数字，**<u>不要在其中填入真实合同单价、商户号或生产账单导出文件</u>**。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 扩容后 p95 仍超目标，实例 CPU 只有 30% | 瓶颈在连接池或下游配额，不在实例 | 打印逐层上限表，看最小值落在哪层 | 提高连接池或改批量化调用 |
| 大促开始十分钟内大量 `429`，成功率骤降 | 重试与人工流量共用同一配额，重试放大拥塞 | 按调用方拆分配额后统计各自用量 | 分管配额、加退避与熔断 |
| 账单上涨 40%，退款笔数只涨 8% | 只有总账单没有成本结构，费用项混在一起 | 按标签归因，拆分实例费、调用费与固定费 | 建标签规范，按月出单位成本 |
| 单位成本下降，但客诉与超时上升 | 用缩容量、关采样、降冗余换来的降本 | 对比同期的 p95、成功率与告警覆盖 | 把质量指标写进成本优化验收 |
| 成本分摊会开成争执，无人认账 | 标签缺失，只能按请求数硬分摊 | 抽查 10 个资源的标签完整率 | 在创建模板里强制打标，缺失即告警 |
| 配额提额后仍被限流 | 配额按实例数均分，扩容后单实例余量更小 | 看限流日志命中的是全局还是单实例配额 | 改为全局令牌桶 + 每实例预留 |

## 安全与生产注意事项

**<u>不要让所有调用方共享一个不设上限的支付配额。</u>** 后果是一个批量对账任务或一次重试风暴就能吃光 30 次/秒的全部配额，人工退款请求全部收到 `429`，积压到 SLA 违约，而监控上只显示"下游限流"。缓解办法是按调用方与用途拆分配额、保留至少 20% 缓冲、对重试加指数退避与熔断，并给配额余量单独设告警。

**<u>不要为了降低账单而关闭审计日志、缩短金额相关日志的保留期，或降低采样到无法举证的水平。</u>** 后果是发生金额争议与对账差异时拿不出证据，既无法向客户解释也无法追责，事后补不回来。缓解办法是把"合规必需"的日志与"排障用"的日志分开定级：前者按监管期限保留，只压缩存储层级；后者可以调采样率，但要在变更记录里写清影响范围。

## 本课总结

- 容量从在途请求出发：`在途 = QPS × p95`，再乘冗余系数除以单实例并发，才是实例数。
- 链路上限有四类，**最小那层就是瓶颈**；只有前两类能靠加机器解决，配额与预算要靠改设计。
- 配额要拆到调用方并留缓冲，超出部分用排队削峰，而不是让重试去撞限流。
- 成本必须先按标签归因、再算单位成本；<u>只看总账单的降本，几乎总是砍错对象</u>。
- 容量结论要写成一句含数值、瓶颈与出路的话，否则它无法被复核，也无法被否决。

## 思考题

大促还剩两周，支付商明确无法把 30 次/秒配额提上去，财务只批 15% 预算增量，而业务坚持两小时退款不能放宽。请给出你的取舍方案：哪些用技术手段解决，哪些必须回退到业务规则，哪些风险需要谁签字？请写出判断依据和你需要的证据。

参考思路：先判断哪项是不可逆损失。配额是硬约束，技术手段有批量化调用（多笔小额退款合成一次请求）、异步排队并把排队时间计入两小时口径、按优先级分配配额（人工受理优先于重试）。可回退的业务规则是部分退款改为 24 小时内到账、超阈值退款转人工审核。签字人分别为业务负责人（时效口径）、财务（预算与调用费）、支付合作负责人（配额）。需要的证据是批量接口失败率、排队时长分布与按新规则重算的单位成本。

## 小测

1. 峰值 50 QPS、p95 400ms、冗余系数 1.5、单实例可承载 10 个在途请求，至少需要几个实例？  
   A. 2　B. 3　C. 5　D. 30
2. 为什么容量计算要用 p95 而不是平均延迟？
3. 应用 CPU 只有 35%，p95 却持续超标。最可能的原因是什么？
4. 单位成本从 0.025 元降到 0.018 元，能否直接判定成本优化成功？为什么？
5. 场景题：同事提议"大促期间把监控采样率降到 1%、关闭重试日志，账单能降 6%"。你会同意吗？请说明理由并给出替代方案。

## 答案与解析

1. **B。**在途 = `50 × 0.4 = 20`，`20 × 1.5 ÷ 10 = 3`。选 A 的人漏乘冗余系数；选 C 的人用 QPS 直接除以单实例并发；选 D 的人停在"在途 × 冗余"，忘了再除以单实例并发。
2. 容量要覆盖最慢那批请求占用的资源。平均延迟被快请求拉低，算出的在途数偏小，结论天然乐观；p95 对应真实的长尾占用。
3. 瓶颈不在计算资源，而在链路上限更低的一层：连接池耗尽、下游配额触顶，或队列排队。验证方法是打印逐层上限表并看限流、连接等待指标，而不是继续扩容。
4. 不能。单位成本下降可能来自缩容量、降冗余、关采样或减少重试，这些都会把成本转移到质量上。必须同时看 p95、成功率、告警覆盖率与审计完整性；<u>没有质量指标对照的成本曲线不能作为优化证据</u>。
5. 不同意。审计与排障日志属于合规与举证能力，用 6% 的账单换掉的是事故时无法定位、争议时无法举证。替代方案：把日志分层保留（合规日志按期限、排障日志可调采样）、压缩冷存储层级、降低高基数指标标签、并把真正的成本大头（本例是支付调用次数）拿出来优化。

### 动手实验参考

第 2 步 `HEADROOM = 1.0` 时实例数为 4、实例池容量 60 QPS、单位成本 0.02454 元/笔，节省约 175 元/月，但容量刚好等于峰值，没有余量吸收抖动与单实例故障。第 3 步重试降到 1.05 次后节省 3600 元/月，因为支付调用费在总成本中占 97%，而实例费不足 2%。第 4 步把配额改为 120 次/秒后，链路容量变为 90 QPS、瓶颈上移到退款 API 实例池、缺口为 0 QPS——此时继续优化实例才真正有意义。
