# Runbook 与知识移交

## 为什么需要学习

凌晨 2:17，晴空商城「退款回调积压」告警响了。值班人是上周才接手退款服务的后端；唯一处理过这个告警的同事在休假，聊天记录里只留了一句“昨天我手动重放了一下就好了”。他用 40 分钟才找到重放入口，重放时把已经成功的 300 笔回调又发了一遍，支付商当天对账因此多出 300 笔待核对记录。

系统的监控、告警、备份都没缺，缺的是把“知道怎么做”传给下一个人的那一步。

> **核心结论：** Runbook 是写给“明天值班的那个不熟悉这套系统的人”看的操作说明；只有别人能照着它独立做完，知识才算移交完成。

## 学习目标

完成本课后，你能够：

- 写出一份包含触发条件、影响面、前置检查、处置步骤、验证与升级路径的 Runbook。
- 区分 Runbook、Playbook、架构文档与交接记录各自回答什么问题。
- 用值班交接记录和移交清单，让接班人不必追问前任即可接手未结事项。
- 判断一份文档是否已过期，并为它指定复核责任人与复核日期。

## 前置知识

- 回看上一课：[备份、恢复与业务连续性](07-backup-restore-and-business-continuity.md)。
- 知道 SLI、SLO 的基本含义，能看懂一条告警的阈值和“持续 5 分钟”这类条件。
- 熟悉本单元退款服务的状态机：`PROCESSING`、`RETRYING`、`SUCCEEDED`、`FAILED`。
- 会读 Markdown、会在终端执行命令并看懂退出码。

## 业务场景

本单元继续用晴空商城的退款集成服务，这次看它的“人”这一侧面。服务上线四个月，进入运行阶段，环境是这样的：

- 值班：5 人轮值，每人一周，覆盖 9:00–21:00，夜间由值班手机兜底。
- 未结事项：上周三起有 12 笔退款卡在 `RETRYING`，自动重试已用尽，等人工核对。
- 人员变动：退款服务原负责人月底调去新项目，运维团队要接走日常处置。
- 外部变化：支付商每月会调整一次回调报文字段，Runbook 里的示例报文容易过期。

一周内，同一份知识要转手三次：上一班给下一班、原负责人给运维、文档给下一个半夜爬起来的人。

## 核心概念

*Runbook*（运行手册）针对一个具体告警或一件具体任务，写清“什么条件下、按什么顺序、做什么、怎么确认做对了”。*Playbook* 高一层，覆盖一类场景（如“支付链路故障”），规定分级、决策顺序和升级路径，把多个 Runbook 编排起来。

*值班交接（handover）*是换班时把系统当前状态、未结事件和待办动作转交给下一班。*知识移交（knowledge transfer）*把“某个人会做的事”变成“团队能按文档和演练复现的能力”，包含文档、演练、共同值班和责任变更。

*移交清单*逐项确认这些内容是否真的可用，而不是“文件已发过去了”。<u>文档存在不等于知识可用</u>：只有没参与过的人按它完整做一遍，移交才算完成。

*知识腐化（drift）*指文档描述与系统现状逐渐不一致；*单一知识持有者*指某项操作只有一个人会做，也就是关键人风险。

| 文档 | 回答的问题 | 读者 | 典型失效方式 |
| --- | --- | --- | --- |
| Runbook | 现在按什么步骤做 | 值班人 | 命令或界面已过期 |
| Playbook | 这类故障谁决定、按什么顺序处理 | 值班负责人 | 分级和联系人没更新 |
| 架构文档 | 系统为什么这样设计 | 开发与新成员 | 只写设计，不写运行 |
| 值班交接记录 | 这一班发生了什么、接下来做什么 | 下一班 | 只写“无异常”，掩盖未结事项 |
| 复盘报告 | 为什么会发生、怎么防止再发生 | 全员 | 结论没有落到 Runbook 改动 |

## 工作原理

一条告警从响起到知识回流，按时间走九步：

1. **确认与去噪**：先判断告警是否对应真实业务影响（退款成功率下降、工单量上升），再决定是否按 Runbook 处置。纯噪声告警要去改阈值，不要写进 Runbook。
2. **定位 Runbook**：告警规则里带上 `runbook_url`，让人 30 秒内打开正确那一页，而不是在 Wiki 里猜关键词。
3. **前置检查**：确认影响面（多少笔退款受影响、有无客户投诉）、是否处在发布窗口、是否已有进行中的事件，避免两个人同时处置同一件事。
4. **分级**：按 SLO 影响与资金风险定级，定级决定要不要叫人和多久必须升级。
5. **处置**：先止损、再定位。每一步都标“可逆 / 不可逆”，不可逆步骤（批量重放、批量改状态）必须先做样本校验。
6. **验证**：用与告警相同的指标确认恢复，再补一个业务侧验证：抽 3 笔退款查状态，或与财务对账差额。
7. **记录**：边做边记时间线与执行过的命令，这些是交接和复盘的材料，事后补写必然丢细节。
8. **交接**：未结事件写清当前状态、已排除的假设、下一步动作，以及“暂时不要做的事”。
9. **回流**：复盘后把新发现的检查项和陷阱补进 Runbook，更新复核日期。**没有回流的事故会在下一次以同样的方式重演。**

知识移交是一条并行阶梯，而不是最后一场会议：撰写文档 → 影子值班（新人跟随但不动手）→ 反向影子（新人动手、原负责人在旁）→ 独立值班且原负责人可联系 → 责任人与复核日期正式变更。每级都要有可观察的退出条件，例如“独立处置过一次完整告警，含验证与记录”。

## 架构与选型

| 承载方式 | 适合 | 优势 | 代价 |
| --- | --- | --- | --- |
| 代码仓库里的 Markdown | 有工程流程的团队 | 可评审、可回滚、与代码同版本 | 值班人需要会用 Git |
| 知识库 / Wiki 页面 | 跨部门流程、非技术读者 | 易编辑、易搜索 | 容易腐化，缺少评审 |
| 告警平台内置的 Runbook 字段 | 单一告警的短处置 | 与告警同屏，不会点错 | 篇幅受限，长流程写不下 |
| 一键脚本或自动化任务 | 步骤固定、风险可控的处置 | 比文档更不容易执行错 | 要维护代码，异常分支难覆盖 |

适用与不适用：

- **适用**：重复发生、步骤相对固定、出错代价明确的处置，例如回调积压、连接池耗尽、证书到期。
- **不适用**：一次性探索任务（根因未知的排查）和需要现场判断的取舍。这类内容应写成 Playbook 里的判断要点，<u>不要把不确定的判断伪装成固定步骤</u>，否则值班人会照着做完却什么也修不好。

越具体的文档越容易被腐化。稳定的部分（顺序、判据、失败分支、不可逆标注）要写死，易变的部分（参数、地址、报文）应参数化并指向配置或脚本，用复核日期管理。**同一套步骤每月执行超过两次时，优先脚本化，而不是把 Runbook 写得更长。**

## 最小示例

先看一份可复制的 Runbook 骨架：它不解释设计动机，只回答“做什么”。

```text
# Runbook：退款回调积压
触发：refund_callback_lag_seconds > 300，持续 5 分钟
影响：退款停在 PROCESSING；已成功退款不受影响；客服工单可能上升
前置检查：① 是否在发布窗口 ② 支付商状态页是否正常 ③ 是否已有事件在处理
步骤：1) 消费者副本扩到 6  2) 抽 dead_letter 前 10 条比对状态
      3) 按幂等键重放（不可逆：已发出的回调不能撤回，需双人确认）
验证：积压归零；抽 3 笔退款确认状态为 SUCCEEDED 或 FAILED
升级：30 分钟未恢复 → 支付组值班；出现资金差错 → 财务
回滚：副本数改回 2；未发出部分可通过幂等键暂停
责任人：payments 组；本次复核 2026-10-19；下次复核 2027-01-19
```

格式对了不等于能用。下面这个脚本把“能不能交给别人”变成可检查的结论，只用 Python 标准库：

```python
#!/usr/bin/env python3
"""runbook_lint.py：检查 Runbook 是否回答得来值班人最需要的几个问题。"""
import json
import sys
from datetime import date
from pathlib import Path

# 一份可执行的 Runbook 至少要回答这些问题；缺一项，值班人就得半夜临场猜。
REQUIRED = (
    "trigger",     # 什么条件触发，避免拿错处置方案
    "impact",      # 影响谁、影响多少，决定分级
    "prechecks",   # 动手前必须先看什么
    "steps",       # 处置步骤
    "verify",      # 怎么验证已经恢复
    "escalate",    # 多久没恢复、找谁
    "rollback",    # 临时措施怎么撤回
    "owner",       # 谁维护这份文档
    "reviewed",    # 上次复核日期
)

# 支付链路每月都在变：90 天没复核的步骤按“可疑”处理，而不是按“用过就行”。
MAX_AGE_DAYS = 90

# 真实使用从 runbooks.json 读；这里内联两份样本，保证示例离线可复现。
SAMPLE = [
    {
        "title": "退款回调积压",
        "trigger": "refund_callback_lag_seconds > 300 持续 5 分钟",
        "impact": "退款停在处理中，影响客服工单量",
        "prechecks": ["确认非发布窗口", "确认支付商状态页"],
        "steps": ["扩消费者副本", "按幂等键重放失败回调"],
        "verify": "积压归零且 15 分钟内无新告警",
        "escalate": "30 分钟未恢复升级至支付组",
        "rollback": "缩回副本数，暂停重放任务",
        "owner": "payments",
        "reviewed": "2026-10-01",
    },
    {
        "title": "订单库连接池耗尽",
        "trigger": "db_pool_in_use_ratio > 0.9",
        "impact": "下单失败",
        "prechecks": [],
        "steps": ["重启应用"],
        "owner": "order",
        "reviewed": "2026-03-01",
    },
]


def load(path=None):
    """有参数就读文件，没有就用内联样本，让示例不需要额外文件就能跑。"""
    if not path:
        return SAMPLE
    return json.loads(Path(path).read_text(encoding="utf-8"))


def check(book, today):
    """返回问题列表；空列表代表这份文档可以交给一个不熟悉它的人。"""
    problems = [f"缺少 {field}" for field in REQUIRED if not book.get(field)]
    # 只“复核过”还不够：过期步骤比没有步骤更容易把人带错。
    reviewed = book.get("reviewed")
    if reviewed:
        age = (today - date.fromisoformat(reviewed)).days
        if age > MAX_AGE_DAYS:
            problems.append(f"{age} 天未复核，超过 {MAX_AGE_DAYS} 天阈值")
    return problems


def main(argv):
    today = date.fromisoformat(argv[1]) if len(argv) > 1 else date(2026, 10, 19)
    bad = 0
    for book in load(argv[2] if len(argv) > 2 else None):
        problems = check(book, today)
        # 用“可用 / 不可用”而不是打分：移交时只有这两种结论有意义。
        print(f"{'可用' if not problems else '不可用'}：{book['title']}")
        for problem in problems:
            print(f"  - {problem}")
        bad += bool(problems)
    # 非 0 退出码让流水线能拦住“文档写完了但没法用”的移交。
    return 1 if bad else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

运行与预期输出：

```console
$ python3 runbook_lint.py
可用：退款回调积压
不可用：订单库连接池耗尽
  - 缺少 prechecks
  - 缺少 verify
  - 缺少 escalate
  - 缺少 rollback
  - 232 天未复核，超过 90 天阈值
$ echo $?
1
```

流程是：检查必备字段 → 算复核日期距今的天数 → 输出结论并用退出码表达。第一份能通过，是因为连“重放需双人确认”都写了；第二份只有一句“重启应用”，值班人既不知先看什么，也不知怎么算恢复。把 `reviewed` 改成 `2026-10-15` 仍会因缺字段被判不可用：<u>新鲜度不能弥补缺失的内容</u>。

## 动手实验

### 目标

为自己团队的一条告警写 Runbook，并用校验脚本证明它“能交给别人”。

### 前置条件

Python 3.8 以上（用到 `json`、`pathlib`、`datetime` 标准库），无需网络。把上面的脚本保存为 `runbook_lint.py`。

### 步骤

1. 选一条你见过或能想象的告警，例如“证书 14 天后到期”。
2. 新建 `runbooks.json`，用 JSON 数组写一条记录，字段与 `REQUIRED` 一致。
3. 运行 `python3 runbook_lint.py 2026-10-19 runbooks.json`，先故意留空 `verify` 和 `escalate`。
4. 按输出补齐字段，再运行一次。
5. 把 `reviewed` 改成 200 天前，第三次运行。

第 3 步的预期输出：

```console
$ python3 runbook_lint.py 2026-10-19 runbooks.json
不可用：证书 14 天后到期
  - 缺少 verify
  - 缺少 escalate
```

### 预期结果

第一次输出“不可用”并列出缺项、退出码为 1；补齐后输出“可用”、退出码 0；只改旧日期后再次变回“不可用”，问题描述为“N 天未复核”。

### 验证方法

- 退出码随内容在 0 和 1 之间切换，说明结论可被 CI 使用。
- 请一位没参与写作的同事只看这份 Runbook 执行一遍，记录他卡住的句子——脚本查不出这部分。

### 清理方法

实验只新增两个文件，删除前先确认路径就在当前目录：

```console
$ ls runbook_lint.py runbooks.json
$ rm runbook_lint.py runbooks.json
```

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 值班人打开文档后仍在群里问人 | 步骤只写“检查一下”，没有命令和判据 | 让没做过的人按文档执行，记录卡住的句子 | 每步写成“命令 + 判据 + 失败分支” |
| 照着 Runbook 操作后故障加重 | 界面、参数或报文已经变了 | 对比文档复核日期与最近一次系统变更 | 加复核日期，并在变更评审中检查受影响文档 |
| 下一班重做了上一班已排除的检查 | 交接只写“无异常”，没有时间线和假设 | 抽查交接记录是否含状态、未结、下一步 | 固定交接模板，要求写“暂时不要做的事” |
| 同类事故第二次发生 | 复盘结论没落到 Runbook 和告警 | 查复盘行动项里有没有文档类改动和截止日 | 规定复盘必须产出一条 Runbook 修改 |
| 文档很多但没人用 | 入口分散，告警里没有链接 | 从告警页数几步能打开 Runbook | 告警规则带 `runbook_url`，按服务建索引 |

## 安全与生产注意事项

**<u>Runbook 里写可直接复制执行的生产口令，等于把生产权限散落到每个人的书签和聊天记录里。</u>**后果是文档泄露、截图外传，口令被粘贴到测试环境后再复用。缓解：文档只写凭据的引用名与申请方式，敏感操作走密钥管理系统；文档按最小权限授权；对仓库做密钥模式扫描。

**<u>把批量重放、批量删除这类不可逆动作写成一行命令，迟早会有人在没做前置校验时执行它。</u>**后果是重复退款与数据不可恢复，且常发生在凌晨注意力最差时。缓解：不可逆步骤默认走预览模式（dry-run）并要求双人确认，同时在文档里明确写出“哪些已发出的操作无法撤回”。

**<u>关键操作只有一个人会做时，这个人的休假、离职或失联本身就是一次单点故障。</u>**缓解：把“新人能独立完成”写进移交标准，安排影子值班与定期演练，每半年轮换文档责任人。

## 本课总结

- Runbook 面向不熟悉这套系统的人：写条件、步骤、判据和升级，不写设计动机。
- Playbook 管分级与决策，Runbook 管具体动作，交接记录管“这一班之后”。
- 知识移交的完成标准是新人独立做完一遍，而不是文档已经发出。
- 文档会随系统腐化，必须有复核日期、责任人和变更联动的机制。
- 复盘不产出 Runbook 改动，同类事故就会重演。

## 思考题

退款服务原负责人月底调岗，你只有两周。请排出移交顺序，写出取舍依据、能证明移交完成的证据，以及“如果只能完成一件事”你会选哪一件。

参考思路：按“发生频率 × 无人能处理时的损失 × 剩余可学习轮次”排序，而不是按文档是否好写排序。夜间高频且不可逆的重放应排第一：它既最高频，也唯一会直接造成资金差错。证据不是签字，而是反向影子记录、一次演练复盘，以及更新后的 Runbook 与责任人变更。只做一件时，就做重放，并要求接手人独立演练一次。

2. 下面哪项最能证明知识移交已经完成？  
   A. 文档已上传到知识库　B. 原负责人做过一次讲解　C. 没参与过的同事按文档独立完成一次处置　D. 移交清单已签字
3. 交接记录里为什么必须写“暂时不要做的事”？
4. 判断：Runbook 写得越详细越好，应该固定每个参数的具体取值。
5. 场景题：大促前一晚，值班人发现某条告警没有对应 Runbook。他应该先摸索处置，还是先等？

## 答案与解析

1. Runbook 管一个具体告警或任务的可执行步骤；Playbook 管一类场景的分级、决策顺序与升级路径。混同的后果是：有人对着决策树找命令，或对着命令找“该不该叫人”。
2. **C。**A、B、D 都能在没有真实能力时完成：上传不需理解，讲解听一遍不等于会做，签字只是流程证据。只有独立完成一次完整处置才同时验证了文档和人的组合。<u>签字是流程证据，不是能力证据</u>。
3. 因为交接最常见的事故是重复或扩大前任的动作：正在跑的批量任务、临时扩容、刚联系过的厂商，没注明就会被再做一遍。写“不要做”比写“做过什么”更值钱。
4. **错。**参数取值会过期，写死还会诱导人跳过判断。稳定的部分（顺序、判据、失败分支、不可逆标注）要具体；易变部分应参数化并指向配置和脚本，由复核日期管理。
5. 先判断影响是否在扩大、动作是否可逆，而不是先看有没有文档。影响扩大且动作可逆（扩容、限流、暂停消费）就立即处置并同步记录；只能做不可逆动作时先升级找人。事后必须补写 Runbook：**没有文档不是等待的理由，也不是冒险的许可**。

### 动手实验参考

关键不是跑通脚本，而是看到两个事实：补齐字段后结论从“不可用”翻成“可用”，说明缺项能被机械发现；只改旧日期又翻回“不可用”，说明有效期与内容完整是两件独立的事。补字段时最易漏的是 `verify`，它恰恰决定值班人能否判断“已经好了”。也别省掉“让同事照着做一遍”，脚本查不出“这步该看哪个界面”。
