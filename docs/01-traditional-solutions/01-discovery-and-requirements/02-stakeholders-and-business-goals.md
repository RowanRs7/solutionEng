# 利益相关者与业务目标

## 为什么需要学习

同一个“退款提速”项目，对客服意味着少复制数据，对财务意味着资金可追踪，对安全团队意味着权限和审计，对管理层意味着降低成本。如果只采访最先提出需求的人，方案会遗漏其他角色的决定、风险和验收条件。

> **核心结论：** 需求不是某个人的一句话，而是多个利益相关者的目标、事实、约束和冲突经过确认后的共同描述。

## 学习目标

完成本课后，你能够：

- 找到发起人、用户、运营者、控制者、数据负责人和外部供应商。
- 为每位利益相关者记录影响力、关注点和决策责任。
- 把“建设某系统”改写为业务成果和指标。
- 记录目标冲突，而不是替利益相关者暗中作决定。

## 前置知识

- 已完成[解决方案架构师的工作](01-solution-architect-role.md)。
- 理解交付物、约束和架构决策。

## 业务场景

晴空商城的运营总监发起退款集成项目。客服主管希望减少手工操作；财务要求每笔退款可核对；仓库希望避免已经出库的订单被错误退款；安全团队要求高额退款二次审批；支付供应商规定每秒最多调用 20 次。

表面上只有一个“退款”需求，实际上至少有六类利益相关者：发起人、业务用户、系统运营者、安全与合规人员、数据负责人和外部服务提供商。

## 核心概念

### 利益相关者地图

*利益相关者*是受方案影响、能够影响方案或掌握关键信息的人或组织。

| 类别 | 典型问题 | 场景示例 |
| --- | --- | --- |
| *发起人* | 为什么投入？什么结果值得继续？ | 运营总监 |
| 用户 | 谁每天使用？工作如何变化？ | 客服专员、财务人员 |
| 运营者 | 谁部署、监控、恢复？ | 平台运维团队 |
| 控制者 | 谁定义安全、法务和合规要求？ | 安全、审计、法务 |
| 数据负责人 | 谁定义数据含义和访问规则？ | 订单与支付数据负责人 |
| 外部供应商 | 哪些能力、配额和故障不受团队控制？ | 支付供应商 |

*决策所有者*是对某项决定拥有最终授权的人。参与讨论不等于拥有决定权。例如，架构师可以推荐重试策略，但财务负责人决定高额退款的业务审批规则。

### 目标、产出和成果

| 类型 | 问的问题 | 示例 |
| --- | --- | --- |
| *业务目标* | 为什么做？ | 降低退款处理时间和人工错误 |
| *产出* | 项目交付什么？ | 退款集成服务、状态页面、Runbook |
| *成果* | 使用产出后发生什么变化？ | 退款中位处理时间从两天降到两小时 |
| 方案想法 | 可能怎么做？ | 使用消息队列自动处理退款 |
| *指标* | 如何观察变化？ | P50/P95 处理时长、人工步骤数、失败率 |

<u>“上线退款平台”是产出，不是业务成果。</u>平台上线却无人使用，业务目标仍未实现。

### 关注点与冲突

*关注点*是利益相关者希望方案保护、改善或避免的事项。冲突并不代表某一方错误，而是目标或风险需要权衡。例如：客服追求速度，安全团队追求审批控制；架构师应把冲突、证据、选项和决策所有者放到同一张记录中。

## 工作原理

利益相关者与目标发现可以按五步进行：

1. 从业务流程和系统清单列出直接参与者。
2. 沿着“批准、运营、审计、提供数据、承担成本”继续寻找间接参与者。
3. 分别询问目标、痛点、证据、约束和担忧。
4. 把方案想法反问成“它要改善什么结果”。
5. 记录冲突和决策所有者，安排确认会议。

访谈问题应具体，例如：“过去四周有多少笔退款超过两天？”比“现在的体验好吗？”更容易获得证据。

## 架构与选型

利益相关者管理不是把所有人都拉进每场会议。根据影响力和关注程度选择沟通方式：

| 影响力 / 关注程度 | 建议方式 |
| --- | --- |
| 高 / 高 | 共同决策，频繁同步 |
| 高 / 低 | 关键节点确认，摘要汇报 |
| 低 / 高 | 深入访谈、试用和反馈 |
| 低 / 低 | 保持知会，按变化更新 |

当指标互相牵制时，使用成对指标。例如只追求“处理速度”可能导致错误退款，因此同时跟踪处理时长和错误退款率。

## 最小示例

一个可检查的目标声明包含对象、变化、基线、目标值和时间范围：

```text
在上线后三个月内，
将普通退款从“客服提交”到“支付方确认”的 P50 时长
从 48 小时降至 2 小时以内，
同时把错误退款率控制在 0.1% 以下。
```

整体上，这个声明回答了“谁的什么过程”“从哪里到哪里”“何时达成”和“不能牺牲什么”。如果基线尚未知，应明确把“测量基线”列为发现任务，而不是编造数字。

### 评分量表（20 分）

- 覆盖六类利益相关者：4 分。
- 影响力与关注程度有理由：4 分。
- 关注点具体而非岗位复述：4 分。
- 每项关键决定有唯一所有者：4 分。
- 沟通方式与影响力匹配：4 分。

## 常见错误与排查

| 现象 | 原因 | 验证 | 修复 |
| --- | --- | --- | --- |
| 上线后用户拒绝使用 | 未找到真实操作用户 | 检查访谈名单是否只有管理者 | 观察一线流程并邀请试用 |
| 指标漂亮但业务无改善 | 把产出当成果 | 检查指标是否只统计功能数量 | 加入处理时长、错误率等成果指标 |
| 需求反复变化 | 决策所有者不明确 | 查询谁能最终批准范围 | 为每类决定指定所有者 |
| 会议争论无法结束 | 冲突没有证据和选项 | 检查是否记录基线、约束和代价 | 写冲突记录并升级给授权者 |

## 安全与生产注意事项

**<u>不能把安全、合规、数据和运营团队当作上线前的审批关卡。</u>**他们必须在需求发现阶段提出约束，否则方案可能在临近发布时整体返工。

利益相关者表可能包含姓名、联系方式和组织敏感信息。只记录完成协作所需的信息，并限制文档访问范围。

## 本课总结

- 利益相关者包括发起人、用户、运营者、控制者、数据负责人和供应商。
- 业务目标说明“为什么”；产出说明“交付什么”；成果说明“发生什么变化”。
- 指标必须能观察成果，也要包含防止局部优化的平衡指标。
- 冲突需要记录证据、选项和决策所有者。
- 沟通频率应匹配影响力和关注程度。

## 思考题

如果运营总监要求所有退款自动通过，而安全负责人要求全部人工审批，你会如何组织下一次会议？请写出需补充的证据、至少两个中间方案和最终决策所有者。

## 小测

1. “交付一个退款微服务”属于目标、产出还是成果？
2. 谁是发起人？  
   A. 每天使用系统的人　B. 为项目提供授权和资源的人　C. 编写代码的人　D. 所有外部供应商
3. 为什么要同时跟踪退款速度和错误率？
4. 利益相关者的影响力低，就可以忽略，对还是错？
5. 场景题：财务和客服对“退款完成”的定义不同，应先选择哪一方的定义吗？

## 答案与解析

1. **产出。**它是项目交付的东西；只有它被使用后带来的处理时长或错误率变化才是成果。
2. **B。**发起人提供方向、授权或资源；他不一定每天使用系统。
3. 单独优化速度可能增加错误退款，成对指标能暴露这种副作用。
4. **错。**低影响力、高关注程度的一线用户掌握真实流程，忽略他们会导致采用失败。
5. 不应先站队。先记录两个定义及其业务后果，再由拥有业务规则决定权的人确认统一口径。
