# 功能与非功能需求

## 为什么需要学习

“系统要快、要安全、要稳定”无法直接指导设计或测试。需求必须描述条件、刺激、响应和阈值，让不同团队能判断是否达成。

## 学习目标

- 对给定要求按“系统必须执行的行为”和“行为必须满足的条件”分类，并说明判断依据。
- 为速度、运行连续性、访问控制、数据保护、修改与排障、接口版本、规则遵循和成本各写出一条包含条件、响应和数值阈值的要求。
- 将至少八条模糊要求改写为包含对象、条件、响应、数值或时限以及验证边界的要求。

- 已完成[用户、角色、场景与用例](04-users-roles-scenarios-and-use-cases.md)。

## 业务场景

退款用例规定系统必须提交退款、保存受理编号并支持人工接管。除此之外，还必须规定高峰期响应时间、权限错误处理、故障恢复、审计保存期限和供应商配额。

## 核心概念

*功能需求*说明系统在给定输入或事件下必须执行的行为，例如受理退款并返回编号。*非功能需求*说明这些行为需要满足的质量条件；工程实践中常把它们具体化为*质量属性*及其可验证阈值。性能、可用性、安全、隐私、可维护性、可运维性、兼容性、合规和成本都属于需要结合上下文定义的质量方面。

| 类型 | 示例 |
| --- | --- |
| 功能需求 | 系统为普通退款生成受理编号并展示状态。 |
| 性能 | 95% 的退款提交请求在 2 秒内返回受理结果。 |
| 可用性 | 月度可用性达到 99.9%，计划维护除外。 |
| 可扩展性 | 高峰每分钟 1,000 笔请求时仍满足响应目标。 |
| 安全与隐私 | 只有具备权限的客服可查看订单金额，日志不保存完整支付账号。 |
| 可维护性与可运维性 | 关键失败包含 Correlation ID，并可在 10 分钟内定位。 |
| 兼容性与合规 | 支持支付 API v2，审计记录保留 180 天。 |
| 成本 | 单笔自动退款基础设施成本不超过约定预算。 |

*质量属性场景*用六个要素避免“系统要好”这类无法验收的表述：

| 要素 | 要回答的问题 | 退款示例 |
| --- | --- | --- |
| 刺激源 | 谁或什么发起事件？ | 客服工作台 |
| 刺激 | 发生了什么？ | 提交一笔有效退款 |
| 环境 | 在什么运行条件下？ | 工作日高峰，每分钟 1,000 笔请求 |
| 对象 | 哪个系统或组件受到影响？ | 退款 API |
| 响应 | 系统应做什么？ | 返回受理编号，超时则给出可查询状态 |
| 响应度量 | 如何判断响应达标？ | 有效请求 P95 延迟不超过 2 秒 |

可测量需求的通用句式是：“在**环境/条件**下，**刺激源**对**对象**施加**刺激**时，系统应产生**响应**，且**度量**达到**阈值**。”真实阈值应由业务影响、基线数据、法规/合同和成本共同确定，并注明计量边界、例外和责任人。

### 常见质量属性的测量角度

| 属性 | 常见度量角度 | 退款系统示例 |
| --- | --- | --- |
| 性能 | 延迟百分位、吞吐量、资源使用 | 高峰 1,000 请求/分钟时，提交 API 的 P95 延迟不超过 2 秒。 |
| 可用性 | 时间窗口、成功率、恢复时间 | 每月退款查询成功率至少 99.9%；计划维护和依赖故障的计量规则须预先约定。 |
| 可扩展性 | 负载增长、扩容时间、扩容后质量 | 流量从每分钟 500 增至 2,000 笔时，扩容后 10 分钟内恢复 P95 不超过 2 秒。 |
| 安全 | 主体、资源、动作、控制和审计 | 无退款权限的客服提交请求时，API 返回 403，且写入含操作者、对象和时间的审计事件。 |
| 隐私 | 数据范围、用途、访问者、保存和删除 | 日志不得包含完整支付账号；退款完成 180 天后按策略删除可识别的请求明细。 |
| 易用性 | 目标用户、任务成功率、时间或错误率 | 新客服完成标准退款的首次任务成功率至少 90%，中位完成时间不超过 3 分钟。 |
| 可维护性 | 变更范围、回归风险、验证耗时 | 修改支付供应商适配器时，核心退款规则模块不需修改，相关自动化测试在 5 分钟内完成。 |
| 可运维性 | 可检测性、告警时延、诊断时间 | 支付拒绝率 5 分钟内超过 2% 时，值班人员 2 分钟内收到带服务和环境信息的告警。 |
| 兼容性 | 支持版本、协议、迁移和互操作 | 发布后至少 90 天继续接受支付 API v2 请求，并通过契约测试。 |
| 合规 | 适用规则、证据、范围和周期 | 每笔退款保存操作者、审批、金额和结果审计记录 180 天，并可按退款编号导出。 |
| 成本 | 用量假设、计费周期、预算或上限 | 月处理 100,000 笔退款时，应用基础设施成本不超过约定的每笔预算；供应商费用另行核算。 |

表中阈值是教学示例，不是行业标准。

## 工作原理

先从上一课的用例提取行为、参与者、前置条件、异常路径和后置条件，再补充质量约束。改写模糊要求时，依次补齐条件（时间、负载、数据规模或故障状态）、刺激（谁发起什么操作）、响应（系统做什么及失败时如何降级），以及度量与阈值（单位、百分位/比例、窗口、样本范围和例外规则）。性能通常用百分位而不是单一平均值；可用性必须说明计算窗口和成功定义；成本必须绑定请求量、并发、存储、保留期和预算周期。安全与隐私还要指明主体、数据、动作、控制、保存/删除规则及验证证据。

## 架构与选型

质量属性之间会冲突。更强审计可能增加延迟；更高可用性可能增加成本；更严格权限可能降低操作速度。需求文档应记录权衡，而不是假装所有指标都能最大化。

## 最小示例

模糊要求：“系统要快。”

可测量版本：“在生产高峰、每分钟 1,000 笔退款提交的条件下，系统对有效请求返回受理编号的 P95 延迟不超过 2 秒，超时请求进入可查询的处理中状态。”

这里明确了环境、刺激、响应、百分位和降级结果。

## 动手实验

**可选动手任务：**将下列八条模糊要求改写为质量属性场景。每条写明上下文、刺激、系统响应和度量/阈值；“安全”还要补充对象和控制。无需额外软件或密钥。先独立完成，再对照参考答案；把答案写入笔记或表格即可。

1. 系统要快。
2. 系统必须安全。
3. 系统不能宕机。
4. 数据要准确。
5. 用户要容易操作。
6. 系统以后要能扩展。
7. 出问题要容易排查。
8. 系统不能太贵。

每条 2 分，共 16 分：条件和刺激 0.5 分，响应 0.5 分，可测量阈值 0.5 分，范围/例外或验证方法 0.5 分。只换成“很快”“高度安全”等同义词不得分。完成后逐条检查是否有对象、条件、响应、数值/时限和验证边界；缺一项就先修订再评分。以下为参考答案，阈值仅供练习，其他合理且可验证的答案也成立。

### 参考答案与标注

| 模糊要求 | 一种可测量的改写 | 标注 |
| --- | --- | --- |
| 系统要快 | 工作日高峰、每分钟 1,000 笔有效退款提交时，退款 API 在 95% 请求中于 2 秒内返回受理编号；超时请求仍可按请求 ID 查询状态。 | 条件=高峰负载；刺激=提交；响应=受理/可查；阈值=P95 2 秒。 |
| 系统必须安全 | 普通客服提交金额超过 500 元的退款时，服务端校验财务审批权限；缺少审批返回 403，且拒绝和成功操作均在 1 分钟内写入含操作者、退款编号、动作和时间的审计记录。 | 主体/资源/动作清楚；控制=权限校验；响应码和审计时限可验证。 |
| 系统不能宕机 | 按自然月统计，HTTP 2xx 且返回有效退款状态的查询请求数 / 全部有效查询请求数至少为 99.9%；发布期间单个应用实例故障时，健康实例继续服务，并在 5 分钟内恢复每分钟 1,000 笔的目标容量。 | 明确窗口、分子分母、成功定义和故障恢复负载；可用性目标不等于绝对不宕机。 |
| 数据要准确 | 对每笔退款，以支付供应商返回的受理编号和金额为对账依据；每日对账时，最终状态/金额差异率不超过 0.1%，所有差异在 15 分钟内生成告警和待处理任务，且不得自动覆盖；对账任务完成后 24 小时内由值班人员确认差异。 | 给出准确性阈值、检测响应和人工确认时限；保留人工处理。 |
| 用户要容易操作 | 首次使用的客服在 10 名参与者的可用性测试中，无协助完成标准退款的比例至少 90%，任务中位用时不超过 3 分钟，错误提交率低于 5%。 | 指定用户、任务和测试；成功率、用时和错误率可观察。 |
| 系统以后要能扩展 | 将实例从 2 个扩至 8 个后，负载提升至每分钟 2,000 笔并持续 30 分钟时，提交 API P95 延迟仍不超过 2 秒，错误率低于 0.5%。 | 写明扩展手段、目标负载、持续时间和质量阈值。 |
| 出问题要容易排查 | 支付供应商调用失败时，每条结构化日志包含 Correlation ID、供应商名称、错误类别和时间戳，且不包含支付账号；告警在 2 分钟内到达值班渠道。 | 故障刺激、诊断信息、隐私约束和告警时限可检查。 |
| 系统不能太贵 | 在月处理 100,000 笔退款、平均每笔 3 次支付 API 调用、日志保留 180 天的假设下，应用基础设施月成本不超过 20,000 元；达到预算 80% 时发出告警。 | 成本绑定用量和周期；区分预算阈值与提前预警。 |

业务、安全、运维和财务相关人员需要在交付前确认这些基线、阈值、计量方式及例外。

## 常见错误与排查

| 现象 | 原因 | 修复 |
| --- | --- | --- |
| 测试团队无法判断通过 | 只有形容词 | 加阈值、窗口和样本 |
| 只写平均响应时间 | 长尾被隐藏 | 同时规定 P95/P99 |
| 安全需求只有“加密” | 没有威胁和控制对象 | 写访问者、数据、操作和审计 |
| 成本失控 | 没有使用量假设 | 记录流量、存储、调用和预算 |

## 安全与生产注意事项

**<u>不能把“通过安全评审”当作安全需求本身。</u>**必须描述威胁、控制、验证方法和责任人。

## 本课总结

- **功能需求描述系统做什么；质量属性说明这些行为必须满足的质量条件。**
- **质量属性场景由刺激源、刺激、环境、对象、响应和响应度量组成。**
- **可测量需求包含条件、刺激、响应、阈值和验证方法；示例阈值需要业务确认。**
- 性能、可用性、扩展性、安全、隐私、易用性、维护、运维、兼容、合规和成本都要定义适用的度量。
- 质量属性之间要记录权衡。

## 思考题

“退款状态最终必须一致”如何改写？请说明一致性的范围、允许延迟、异常时的用户可见状态和验证方法。

## 小测

1. “保存退款受理编号”属于功能还是质量需求？
2. 为什么 P95 比平均值更适合描述用户体验？
3. “安全”至少需要补充哪些对象？
4. 可用性指标必须包含时间窗口吗？
5. 成本需求应绑定哪些使用量假设？
6. 场景判断：需求写着“促销高峰每分钟 1,000 笔退款请求时，API 对 95% 有效请求在 2 秒内返回受理编号；超时可按请求 ID 查询”。这条是否可验收？还需要澄清什么边界？

## 答案与解析

1. 功能需求，因为它描述系统要执行的行为。
2. P95 给出 95% 请求延迟不超过的边界，便于约束典型用户体验的长尾；它不描述其余 5% 请求的具体延迟分布，平均值则可能掩盖长尾。
3. 访问者、资产、威胁、控制和验证方式。
4. 需要，否则无法判断在哪段时间内计算。
5. 请求量、并发、存储、保留期、供应商单价和预算周期。
6. 基本可验收：条件、对象、请求范围、响应和 P95 阈值都已写明。还应约定采样窗口、超时/错误请求是否计入分母、压测数据集与异常流量排除规则，避免不同团队得到不同结果。
