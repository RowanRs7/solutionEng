# 系统边界、约束、依赖与假设

## 为什么需要学习

上一课把业务行为和质量要求写成可检查的需求。本课进一步回答“哪些系统和责任由本项目改变”“哪些条件不能随意改变”“方案依靠谁或什么才能成立”。边界不清会造成漏项、重复建设和责任争议；未验证的假设则可能在集成或上线时变成延误、成本或安全风险。

## 学习目标

- 为给定业务目标写出包含范围内、范围外和待确认事项的边界声明。
- 区分外部参与者、系统边界以及上游和下游依赖，并说明关系方向。
- 将组织约束、技术约束、依赖和假设分别登记，包含证据或验证办法与责任人。
- 解释未验证假设如何转化为项目风险，并提出有时限的验证行动。

## 前置知识

- 已完成[功能与非功能需求](05-functional-and-non-functional-requirements.md)。

## 业务场景

在线零售企业希望缩短退款处理时间。客服工作台提交退款请求，订单服务核对订单，支付服务向支付供应商发起退款，仓储系统可能需要收到退货结果。项目团队需要判断新建的退款编排能力负责到哪里；支付供应商、订单数据和客服操作分别由谁负责；以及项目是否必须沿用现有身份平台和部署环境。

## 核心概念

*系统边界*是本方案承诺设计、交付或改变的能力与责任范围。边界不是某个网络防火墙，也不等同于一台服务器。边界声明要指出包含什么、不包含什么、哪些事项尚待决定，以及系统与外界交换什么信息。

*外部参与者*是边界之外、与系统交互的人或组织角色，例如客服、财务审批人、支付供应商。参与者可以是人，也可以是外部系统；他们发起、接收或决定某项交互，但不是因为出现在图上就自动成为项目团队负责的组件。

*上游依赖*提供本方案需要的输入、数据、服务或决策，例如订单服务提供订单状态。*下游依赖*接收本方案的输出或由本方案调用，例如支付供应商接收退款指令。上下游是相对某个方案而言的关系方向，不表示组织级别高低。一个依赖可能同时有请求和回调，因此要按具体数据流说明方向。

*组织约束*是由组织治理、合同、预算、人员、流程或政策形成的限制，例如必须由财务批准超过指定金额的退款。*技术约束*是既定技术环境或兼容性限制，例如只能部署在企业批准的云账户，或支付接口必须使用已采购的版本。约束限制可选方案，但它本身不一定是风险；如果约束不可满足或依据不明确，才需要升级处理。

*假设*是目前缺少证据、但团队暂时当作成立以便继续分析的命题，例如“支付供应商支持带幂等键的退款请求”。假设不等于已确认事实，也不等于需求。*验证责任人*是负责取得证据、安排验证并在结果出现时更新记录的具体角色或姓名；仅写“团队”通常无法确保有人跟进。

假设若未被验证，可能在设计后期或上线时被证伪。**未经验证的假设应进入风险跟踪：记录不成立的可能性、影响、验证动作、责任人和截止日期。**例如供应商不支持幂等键，会导致超时重试产生重复退款的风险，必须在接口设计前向供应商确认并以沙箱测试验证。

| 记录项 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 边界 | 本项目交付、改变和明确不做什么？ | 新增退款编排；不替换支付供应商 |
| 约束 | 哪些已确认条件限制设计？来源是什么？ | 生产部署只能使用企业批准的云账户 |
| 依赖 | 必须从谁/什么取得输入，或向谁/什么交付输出？ | 从订单服务读取状态；向支付服务提交退款 |
| 假设 | 目前缺少什么证据但暂按成立处理？ | 假设供应商支持幂等退款 |
| 验证责任 | 谁在何时用什么证据确认？ | 集成负责人于接口评审前完成供应商沙箱测试 |

## 工作原理

1. 从业务目标和已定义的功能需求出发，列出被改变的能力、数据和流程。
2. 把本方案内部的能力与边界外的人、组织和系统分开；为每项交互标注输入、输出、所有者和方向。
3. 询问组织治理与技术环境中哪些条件是确定的，并记录来源、适用范围和可变性。
4. 列出实现目标所依赖的团队、系统、数据、供应商、决策和时间窗口。
5. 对没有证据但暂时依赖的判断登记假设，指定验证动作、责任人及截止日期。
6. 评估假设不成立时的概率和影响；将重要事项转为风险，并定义规避、缓解、转移或接受的应对方式。

边界、约束、依赖和假设会互相影响。例如，假设订单服务能在 1 秒内响应，如果未验证，应先列为假设；方案依赖订单服务，则它是依赖；若性能要求和订单服务现状冲突，这项依赖会形成风险并可能迫使团队重新划分范围。

## 架构与选型

先确定业务责任，再讨论部署边界。可以采用新服务、现有订单服务中的模块或工作流平台，但每种选择都要说明由谁拥有退款状态、谁负责重试、谁审计操作，以及故障时由谁接管。

对于每一条边界外依赖，确认接口/数据、服务责任人、可用性或响应时限、变更通知机制、测试环境和故障升级路径。外部供应商无法被本项目直接控制；可以通过合同、服务级别约定、适配层、超时、幂等策略和人工兜底降低耦合风险。

约束要有来源和确认状态。“必须使用现有数据库”可能是正式企业标准，也可能只是某位同事的偏好；未确认前应作为待澄清事项，而不能据此排除方案。对可能变化的约束，记录变更成本和批准人。

## 最小示例

以下是本场景的边界声明示例：

> 本项目在客服工作台与现有订单/支付能力之间增加退款编排，负责校验退款请求、发起处理、记录状态并提供查询。项目不替换支付供应商，不重建订单主数据，不改变仓储退货验收流程。是否纳入财务审批规则和仓储退货状态回写，待业务负责人确认。

| 项目 | 类型 | 方向/影响 | 证据或验证 | 责任人 |
| --- | --- | --- | --- | --- |
| 订单服务提供订单和已退款金额 | 上游依赖 | 输入：订单状态、退款累计额 | 接口契约评审；集成环境联调 | 订单服务负责人 |
| 支付服务接收退款指令并返回结果 | 下游依赖 | 输出：金额、支付交易号、幂等键 | 供应商文档和沙箱测试 | 支付集成负责人 |
| 企业必须使用统一身份平台 | 组织约束 | 限制登录及权限方案 | 安全架构标准及安全团队确认 | 安全负责人 |
| 供应商支持相同幂等键安全重试 | 假设 | 若不成立可能重复退款 | 在沙箱重复提交相同请求并检查结果 | 支付集成负责人，接口设计评审前 |

第二表中的最后一项必须保持为“待验证”，直到测试证据确认。若截止前无法验证，应记录为开放风险并评估备用方案，而不是在架构图中把它画成确定能力。

## 动手实验

针对上述在线零售退款方案，把每个条目分类为“内部（在项目方案边界内）”“外部（边界外）”或“待定”。再写一句判断理由。分类依据是**本项目要交付或改变的责任**，不是公司是否拥有系统，也不是某系统是否与本方案联网。

| 系统或责任 | 你的分类 | 参考分类 | 判定理由 |
| --- | --- | --- | --- |
| 新增的退款请求校验与编排能力 |  | 内部 | 这是项目明确交付的主要能力。 |
| 客服在工作台发起退款请求 |  | 外部 | 客服是与系统交互的角色；除非项目范围明确包括改造工作台，否则其日常职责在边界外。 |
| 现有订单服务和订单主数据 |  | 外部 | 它提供输入但不由本项目替换；本方案依赖其数据。 |
| 支付供应商的退款处理平台 |  | 外部 | 由第三方拥有和运行，是下游服务依赖。 |
| 本项目新增的退款状态记录 |  | 内部 | 若该存储由本项目设计、交付和运维，则其能力与责任属于范围内。 |
| 仓储退货验收和库存调整 |  | 待定 | 业务背景提到仓储，但尚未确认是否需要改变仓储流程或接口。 |
| 超过 500 元退款的审批规则 |  | 待定 | 规则和阈值需由财务/业务负责人确认，不能仅凭技术团队推断。 |
| 支付供应商接口的可用性承诺 |  | 外部 | 是外部依赖的服务条件；项目可记录并设计降级，不能直接承诺供应商行为。 |

**评分参考（8 分）：**每项分类正确得 0.5 分，理由指出交付责任、所有权/控制权或待确认依据得 0.5 分。2 项未得满分时，重点检查是否把“公司拥有”误当成“项目负责”，或把未确认事项过早定为内部/外部。边界可以因项目授权变化而改变；如果你作了不同分类，必须写出明确的范围依据和待确认决策人。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 交付后双方都认为对方负责退款状态 | 边界只列系统，没有列责任 | 检查每个输出的生产者、消费者和所有者 | 补充责任人、状态主数据和交接条件 |
| 估算反复增加 | 假设或“待定”事项被当作已确认范围 | 比对估算版本和假设/决策记录 | 为待定事项定负责人和决策日期，必要时分阶段估算 |
| 联调才发现接口字段缺失 | 依赖仅写系统名称，没有接口契约 | 对照用例逐字段检查输入输出 | 补充字段、错误、时序、版本和测试环境 |
| 供应商重试造成重复退款 | 幂等能力未经验证 | 用相同业务请求和幂等键在沙箱重复测试 | 确认契约；实现去重和人工对账兜底 |
| “必须使用某技术”没有人能说明原因 | 偏好被误写为约束 | 查找标准、合同、安全意见或批准记录 | 标成待澄清，找到决策者并记录来源 |

## 安全与生产注意事项

**<u>边界声明不能把安全、隐私和审计责任留在“外部系统”这个模糊说法里。</u>**即使身份、支付或日志服务由其他团队提供，本项目仍须明确谁负责权限映射、敏感数据最小化、调用凭证、审计证据和故障响应，并确认跨边界数据的保护方式。

**<u>不要把未经验证的供应商能力当作生产保障。</u>**重试、退款幂等、数据删除和回调签名等假设应通过契约、沙箱或正式确认验证；验证失败前，应准备限流、人工审批、对账或暂停自动处理等保护措施。

## 本课总结

- **系统边界描述本项目交付和承担的责任，不由网络位置或公司所有权自动决定。**
- 外部参与者可以是人、组织或系统；上下游依赖要按数据/控制流方向说明。
- 约束应附带来源；偏好和未经确认的规则不应伪装成已批准约束。
- 假设是缺少证据的暂定判断，必须有验证方法、责任人和期限。
- **假设不成立可能造成风险；在它影响设计或承诺之前验证，并准备应对方案。**

## 思考题

如果支付供应商的沙箱一直不可用，但退款流程设计评审即将开始，你会如何记录“供应商支持幂等重试”这一假设？哪些工作可以继续，哪些承诺必须暂缓？请说明责任人、截止时间和假设失败时的保护措施。

## 小测

1. 系统边界与网络边界有什么区别？
2. “客服提交请求”是否意味着客服工作台属于项目范围？为什么？
3. 对退款编排而言，订单服务为什么通常是上游依赖，支付供应商为什么通常是下游依赖？
4. “必须使用现有数据库”何时可以登记为组织/技术约束，何时应标为待澄清？
5. 未验证假设至少应记录哪几项，以便转化为可管理的风险？
6. 场景判断：团队假设供应商会在 5 秒内响应，但没有合同、监测数据或沙箱证据。能否把“5 秒内响应”写为已确认质量要求？应如何处理？

## 答案与解析

1. 系统边界界定项目承诺改变或交付的能力和责任；网络边界界定网络隔离或流量控制范围。某个外部系统可能部署在同一网络中，但责任仍在项目边界之外；反之，项目负责的组件也可能跨越多个网络区域。
2. 不能。客服是外部参与者，发起交互不等于项目要改造工作台。只有范围声明明确包含工作台改造时，该改造能力才属于内部交付。
3. 订单服务向退款编排提供订单状态和累计退款额，是输入来源；退款编排向支付供应商发起退款，是输出消费者。实际双向回调应另行记录方向和责任。
4. 有可引用的企业标准、合同、批准决议或负责人的明确确认时，登记为约束并附来源；只有口头偏好或猜测时应标为待澄清/假设，并指定确认人。
5. 至少包括假设内容、现有证据/缺口、若不成立的可能性和影响、验证动作、验证责任人、截止日期，以及未能验证时的应对或决策路径。这样才能判断风险并跟踪关闭。
6. 不能。5 秒只是未经验证的假设，不能成为已确认要求。记录证据缺口和责任人，向供应商索取契约或在沙箱/真实监测中验证；在此之前将响应时限列为待确认，并避免对外承诺。若方案依赖该时限，应登记风险并评估超时、异步处理和用户可查询状态等缓解方式。
