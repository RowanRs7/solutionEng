# 解决方案架构师的工作

## 为什么需要学习

客户常会说：“把商城、仓库和客服系统打通，再加一点 AI。”这句话描述了愿望，却没有说明目标、边界、数据、权限、失败处理和验收方法。解决方案架构师负责把这种模糊诉求转化为团队可以共同理解、实施和验证的方案。

> **核心结论：** 架构师的价值不是画很多图，而是推动团队在约束下做出可解释、可验证的关键决策。

## 学习目标

完成本课后，你能够：

- 解释 *解决方案*、*解决方案架构*、*利益相关者*、*约束*、*交付物*和*决策*。
- 说明架构师与产品、开发、安全和运维的协作边界。
- 判断一个工作事项主要属于哪个生命周期阶段。
- 编写一条包含背景、选项、决定和后果的简短决策记录。

## 前置知识

- 已阅读[解决方案生命周期](../../00-start-here/03-solution-lifecycle.md)。
- 能理解“业务目标”和“软件系统”的日常含义。
- 本课不要求后端或云平台经验。

## 业务场景

“晴空商城”通过自建商城销售商品。订单系统、第三方支付、仓库和客服平台彼此独立。退款需要客服复制订单号、登录支付后台、通知仓库，再把结果手工写回客服工单。平均处理时间为两天，信息遗漏率约为 8%。

管理层提出：“建设一个退款集成服务，把处理时间缩短到两小时，并保留人工审核。”

架构师首先要回答的不是“用 Kafka 还是 RabbitMQ”，而是：

- 谁受到影响，谁能作决定？
- 两小时从哪个时间点计算到哪个时间点？
- 哪些退款必须人工审核？
- 哪个系统拥有订单、支付和审核状态？
- 外部支付接口失败时，业务如何继续？
- 用什么证据证明目标已经达成？

## 核心概念

| 概念 | 本课程中的含义 | 晴空商城示例 |
| --- | --- | --- |
| *解决方案* | 为达成业务目标而组合的技术、流程、人员和交付安排 | 集成服务、审核流程、监控、培训和运维手册 |
| *解决方案架构* | 对组件、边界、关系、约束和关键决策的结构化描述 | 商城、退款服务、支付、仓库和客服之间的关系 |
| *利益相关者* | 受方案影响、能影响方案或掌握关键信息的人或组织 | 客服、财务、仓库、开发、安全、支付供应商 |
| *约束* | 限制方案选择或交付方式的条件 | 支付商只允许 HTTPS API；退款超过 500 元需审核 |
| *交付物* | 某阶段产生并交给他人使用的结果 | 需求清单、上下文图、接口契约、Runbook |
| *决策* | 在多个可行选项中，根据目标和约束作出的选择 | 采用异步退款并向客服返回受理编号 |

**决策**是选择本身；*决策记录*是让他人理解选择背景、替代方案和后果的文档。<u>写下一个决定，并不能自动证明这个决定正确。</u>

## 工作原理

解决方案架构工作形成一个持续循环：

1. **发现**：听取不同角色的目标、痛点和约束。
2. **澄清**：把模糊词转成可观察的行为和指标。
3. **建模**：描述系统边界、流程、数据和依赖。
4. **权衡**：比较选项对成本、风险、速度和质量的影响。
5. **决策**：指定选择、理由、负责人和复核条件。
6. **验证**：通过评审、原型、测试或运行数据检查判断。
7. **更新**：新证据出现时修订需求或决策。

架构师并非独自完成循环，而是确保正确的人在正确时间参与。

## 架构与选型

### 生命周期中的主要责任

| 阶段 | 架构师关注点 | 典型交付物 |
| --- | --- | --- |
| 发现需求 | 目标、角色、现状、证据 | 访谈记录、现状流程、利益相关者表 |
| 定义需求 | 范围、约束、质量、验收 | 需求清单、上下文图、风险登记表 |
| 设计方案 | 组件、接口、数据、安全、权衡 | 架构图、接口契约、ADR |
| 开发与集成 | 契约一致性、跨团队问题 | 示例请求、集成清单、决策更新 |
| 测试与验证 | 业务结果和质量属性 | 验收矩阵、性能与安全结果 |
| 部署与交付 | 环境、迁移、回滚、移交 | 部署方案、培训材料、Runbook |
| 运行与优化 | SLO、告警、事件和成本 | 仪表盘、复盘、改进清单 |

### 角色边界

- **产品负责人**决定产品价值、优先级和范围取舍。
- **开发人员**设计并实现模块内部细节，对代码质量负责。
- **安全人员**定义控制要求、评估风险并验证控制效果。
- **运维或平台团队**负责环境能力、发布机制和运行标准。
- **数据负责人**定义数据含义、质量、权限和生命周期。
- **解决方案架构师**连接这些视角，维护跨系统的一致设计和关键决策。

边界不是“谁不能参与”，而是“谁最终负责什么结果”。小团队可以一人兼任多个角色，但责任仍要明确。

## 最小示例

下面是一条简化的架构决策记录，不需要代码：

```text
标题：退款请求采用异步受理
背景：支付供应商的响应时间波动为 1–90 秒，客服页面不能长时间等待。
选项：A. 同步等待；B. 异步受理并返回任务编号；C. 继续人工操作。
决定：选择 B。
理由：页面可在 2 秒内确认受理，失败任务可以重试和人工接管。
后果：需要任务状态、幂等键、通知机制、监控和补偿流程。
复核条件：供应商提供稳定的批量退款接口，或业务要求即时完成。
```

整体逻辑是：先写背景，再列真实可行的选项；决定必须对应理由；后果记录团队需要承担的新成本；复核条件避免把临时选择误当成永久真理。

## 动手实验

### 任务：制作责任映射

1. 复制下表。
2. 为每项工作填写“主责”“参与”和“知会”角色。
3. 检查是否有两个角色同时被写为最终主责。

| 工作 | 主责 | 参与 | 知会 |
| --- | --- | --- | --- |
| 定义两小时退款指标 |  |  |  |
| 选择异步集成模式 |  |  |  |
| 实现支付客户端 |  |  |  |
| 批准高额退款规则 |  |  |  |
| 设置生产告警 |  |  |  |

预期结果：每项工作有且只有一个清晰主责；参与者提供必要信息；知会对象不会被误当作审批者。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 会议很多但没有结论 | 决策问题和负责人不清楚 | 查看会议纪要是否有决定、负责人和期限 | 会前定义待决问题，会后记录决定 |
| 架构图不断返工 | 目标或边界尚未确认 | 检查不同团队对范围的描述是否一致 | 先确认上下文和范围，再细化组件 |
| 方案只包含技术组件 | 忽略流程、人员和运营 | 检查是否有审批、异常和人工接管 | 把业务流程与技术流程一起设计 |
| 架构师成为所有工作的瓶颈 | 把协同误解为亲自完成 | 检查每项任务是否都有合适主责 | 明确边界，把模块细节交给所有者 |

## 安全与生产注意事项

**<u>架构师不能仅凭“行业通常如此”假设权限、合规或恢复要求。</u>**必须由业务、安全、法务或运营负责人确认，并记录证据和责任人。

在退款场景中，金额、账户、操作人和审批记录都属于敏感业务信息。需求阶段就要识别访问者、保留期限和审计用途，不能等上线前再补安全控制。

## 本课总结

- **解决方案**同时包含技术、流程、人员和交付安排。
- **解决方案架构**描述系统边界、关系、约束和关键决定。
- 架构师连接不同角色并推动跨系统决策，不包办每个专业领域。
- 决策记录需要包含背景、选项、理由、后果和复核条件。
- 交付物的价值在于帮助下一位使用者完成工作，而不是证明“已经写过文档”。

## 思考题

如果管理层要求“一个月内上线”，而安全团队要求完成外部渗透测试，架构师应如何组织决策？请分别写出目标、约束、可选方案、应参与的角色和需要记录的后果。

参考思路：不要由架构师单方面降低安全要求。可比较缩小首发范围、调整发布日期、分阶段开放用户或采用已验证组件等方案，并由拥有业务风险和安全风险授权的人作决定。

## 小测

1. 解决方案架构只描述技术组件，对还是错？
2. 谁通常负责决定产品范围优先级？  
   A. 架构师　B. 产品负责人　C. 任意开发人员　D. 外部供应商
3. 决策记录为什么要写“后果”？
4. 下列哪项最像约束？  
   A. 希望用户满意　B. 支付商仅支持 HTTPS API　C. 画一张架构图　D. 开发人员喜欢 Python
5. 场景题：开发人员要求架构师为每个函数选择名字。架构师应该接受吗？为什么？

## 答案与解析

1. **错。**解决方案还包含流程、人员、运营和交付安排。只画技术组件会遗漏审批、人工接管和责任边界。
2. **B。**产品负责人对价值和优先级负责。架构师提供技术影响和风险信息，但不应替代业务所有者作价值决定。
3. 后果说明团队为决定承担的成本、限制和新工作，也便于以后判断是否需要复核。
4. **B。**它直接限制接口设计。A 是模糊目标；C 是活动；D 只有在组织明确规定技术栈时才可能成为约束。
5. 通常不接受。函数命名属于模块内部设计，应由开发团队负责；架构师只在名称影响公开契约或跨系统一致性时参与。

### 动手实验参考

合理答案不唯一。例如，“定义两小时退款指标”可由产品负责人主责，客服和数据负责人参与；“选择异步集成模式”可由架构师主责，开发、运维和安全参与；“实现支付客户端”由开发主责；“批准高额退款规则”由业务或风控主责；“设置生产告警”由运维主责。
