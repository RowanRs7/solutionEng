# 用户、角色、场景与用例

## 为什么需要学习

“用户可以申请退款”仍然不够具体。谁能申请？需要哪些前置条件？系统调用哪些服务？支付失败后谁接手？用例把这些问题组织成可讨论、可测试的行为。

## 学习目标

- 区分用户、角色、参与者、场景和用例。
- 写出触发、前置条件、主流程、替代流程和后置条件。
- 从真实流程识别系统外部参与者和人工接管点。

## 前置知识

- 已完成[现状调研与业务流程](03-current-state-and-business-process.md)。

## 业务场景

客服提交普通退款。商城提供订单信息，仓库确认未出库，支付系统受理退款，客服查看状态并通知客户。高额退款需要财务审批，支付失败则进入人工处理队列。

## 核心概念

| 概念 | 解释 |
| --- | --- |
| *用户* | 直接使用产品或流程的人。 |
| *角色* | 在某个场景中承担的一组职责，例如客服或财务审批人。 |
| *参与者* | 与系统交互的人、外部系统或定时器。 |
| *场景* | 在特定目标和条件下发生的一次交互故事。 |
| *用例* | 用结构化方式描述参与者为达成目标与系统交互的完整行为。 |
| *前置条件* | 用例开始前必须成立的条件。 |
| *后置条件* | 用例完成后应成立的结果。 |

## 工作原理

用例按以下顺序组织：参与者触发目标，系统验证前置条件，执行主成功流程；遇到条件变化时进入替代流程；无法恢复时进入失败流程；最终形成可检查的后置条件。

## 架构与选型

不要把每个按钮都写成用例。用例应围绕参与者目标，例如“完成退款”，而不是“点击退款按钮”。系统角色和权限角色可以不同：客服是业务角色，JWT 中的 `support_agent` 是系统授权角色。

## 最小示例

```text
用例：处理普通退款
参与者：客服、商城、仓库、支付系统
触发：客服提交订单号和退款原因
前置条件：订单存在、未完成退款、客服具备退款权限
主流程：
  1. 系统读取订单和支付状态。
  2. 系统请求仓库确认未出库。
  3. 系统向支付系统提交退款并保存受理编号。
  4. 系统显示“处理中”，客服可查询状态。
替代流程：金额超过 500 元时，转财务审批后继续。
失败流程：支付系统拒绝时，创建人工处理任务并保留失败原因。
后置条件：退款状态可追踪，审计记录包含操作者和受理编号。
```

整体重点是目标和结果，而不是技术实现细节。后续接口设计可以从主流程和异常流程提取请求、状态和事件。

## 动手实验

把“系统要支持客服快速退款”转换成一份用例，至少包含参与者、触发、三个前置条件、五步主流程、一个替代流程、一个失败流程和两个后置条件。

评分 20 分：参与者 3 分，触发与前置条件 4 分，主流程 5 分，异常路径 4 分，后置条件 2 分，目标清晰 2 分。

## 常见错误与排查

| 现象 | 原因 | 修复 |
| --- | --- | --- |
| 用例只有页面操作 | 把界面脚本当成业务目标 | 改写为参与者目标 |
| 没有异常流程 | 只描述理想路径 | 从现状流程提取失败和人工接管 |
| 角色和权限混用 | 业务职责与系统授权未分开 | 分别描述业务角色和授权角色 |
| 后置条件不可验证 | 只写“处理成功” | 写状态、编号、审计和数据结果 |

## 安全与生产注意事项

**<u>高风险操作必须在用例中显式写出权限校验、审批和审计结果。</u>**不要把“系统已登录”当作所有授权的替代品。

## 本课总结

- 用例围绕参与者目标，而不是界面按钮。
- 成功、替代和失败流程都属于真实需求。
- 前置和后置条件必须可验证。
- 业务角色和系统授权角色需要分开描述。

## 思考题

退款请求已经提交，但支付系统 30 秒没有响应。这个情况属于替代流程、失败流程还是新的用例？请说明判断依据。

## 小测

1. “财务审批人”是参与者还是数据库表？
2. 用例为什么需要后置条件？
3. “点击按钮”是否通常是用例目标？
4. 支付拒绝时为什么不能只返回错误页面？
5. 写出一个退款用例的前置条件。

## 答案与解析

1. 是参与者，具体是业务角色参与者。
2. 后置条件让团队知道完成后应观察到什么结果，并支持验收测试。
3. 通常不是。用例应描述参与者要达成的业务目标。
4. 还需要保留原因、状态和人工接管路径，避免请求既未成功又无法追踪。
5. 示例：订单存在、未完成退款、客服具备对应权限。
