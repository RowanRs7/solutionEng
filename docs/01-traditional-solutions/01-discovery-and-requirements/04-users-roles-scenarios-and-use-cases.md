# 用户、角色、场景与用例

## 为什么需要学习

“用户可以申请退款”听起来明白，真正实施时却会连续遇到问题：谁能申请？需要哪些前置条件？系统调用哪些服务？支付失败后谁接手？

用例把这些问题组织成可讨论、可测试的行为。它像一份围绕目标写成的“办事说明”，既写顺利时怎么办，也写条件不符、外部拒绝或暂时无响应时怎么办，而不只是页面上依次点哪些按钮。

## 学习目标

- 区分用户、角色、参与者、场景和用例。
- 写出触发、前置条件、主流程、替代流程和后置条件。
- 从真实流程识别系统外部参与者和人工接管点。

## 前置知识

- 已完成[现状调研与业务流程](03-current-state-and-business-process.md)。

## 业务场景

客服提交普通退款。商城提供订单信息，仓库确认未出库，支付系统受理退款，客服查看状态并通知客户。高额退款需要财务审批，支付失败则进入人工处理队列。

这里至少有两条不同路径：普通退款可以按主流程受理，高额退款要先走审批分支；支付失败也不是一句“出错了”就结束，而是要把请求转到可追踪的人工处理路径。

## 核心概念

可以用“拍戏”帮助区分前五个概念：真实的人像演员，角色是承担的职责，场景是某一次具体剧情，用例则是一份包含分支和结局的剧本。外部系统和定时器也可以是参与者，所以这个类比不能把人以外的参与者忘掉。

| 概念 | 解释 | 退款例子 |
| --- | --- | --- |
| *用户* | 直接使用产品或流程的人，指具体的人而非权限名称 | 在客服工作台操作的某位客服 |
| *角色* | 在某个场景中承担的一组职责；同一个人可在不同场景承担不同角色 | 客服、财务审批人 |
| *参与者* | 与系统交互的人、外部系统或定时器 | 客服、商城、支付系统 |
| *场景* | 在特定目标和条件下发生的一次交互故事 | 客服为某笔 300 元订单提交退款并成功受理 |
| *用例* | 用结构化方式描述参与者为达成目标与系统交互的完整行为 | 处理普通退款，含审批与失败分支 |
| *前置条件* | 用例开始前必须成立、并可检查的条件 | 订单存在且客服具备退款权限 |
| *后置条件* | 用例完成后应成立、并可检查的结果 | 退款状态可追踪，审计记录完整 |

“场景”和“用例”最容易混淆：场景更像“某一次发生了什么”，用例更像“这类目标在各种相关条件下应怎样完成”。一个用例可以覆盖多个具体场景。

## 工作原理

编写用例时，可以按以下顺序逐步补齐：

1. **先写目标与参与者**：参与者想完成什么，哪些人或外部系统参与。
2. **写触发与前置条件**：什么事件启动用例，开始前哪些条件必须为真。
3. **写主成功流程**：在最常见且满足条件的路径上，参与者和系统如何交替行动。
4. **补替代流程**：业务仍可能达成目标，但路径不同，例如高额退款增加财务审批。
5. **补失败流程**：当前目标无法由系统正常完成时，怎样保留状态、原因并安排人工接管。
6. **写后置条件**：成功或失败后分别能观察到什么状态、编号、数据和审计结果。

主流程不是“系统内部调用清单”，而是参与者可理解的交互过程。替代流程也不等于错误：需要财务审批可能完全是正常业务规则。失败流程则必须说清楚请求停在哪里、谁继续处理，不能只留下一个错误页面。

## 架构与选型

不要把每个按钮都写成用例。用例应围绕参与者目标，例如“完成退款”，而不是“点击退款按钮”。按钮、页面和接口以后可能变化，参与者的业务目标通常更稳定。

系统角色和权限角色可以不同：客服是业务角色，JWT 中的 `support_agent` 是系统授权角色。前者说明这个人在业务中负责什么，后者说明系统据此允许什么操作；两者有关联，但不能互相替代。JWT 在这里可理解为携带身份或授权信息的凭证，本课不要求掌握其内部格式。

选择用例粒度时，可以用一个简单检查：读者能否从标题看出参与者要达成的结果？“查询退款状态”可以是独立目标，“打开查询页面”通常只是实现这个动作的一个界面步骤。

## 最小示例

```text
用例：处理普通退款
参与者：客服、商城、仓库、支付系统
触发：客服提交订单号和退款原因
前置条件：订单存在、未完成退款、客服具备退款权限
主流程：
  1. 系统读取订单和支付状态。
  2. 系统请求仓库确认未出库。
  3. 系统向支付系统提交退款并保存受理编号。
  4. 系统显示“处理中”，客服可查询状态。
替代流程：金额超过 500 元时，转财务审批后继续。
失败流程：支付系统拒绝时，创建人工处理任务并保留失败原因。
后置条件：退款状态可追踪，审计记录包含操作者和受理编号。
```

这段示例的重点是目标和结果，而不是技术实现细节。读完后可以追问并检查：受理编号从哪一步产生？审批前是否允许向支付系统发送指令？失败后原请求能否继续查询？

后续接口设计可以从主流程和异常流程提取请求、状态和事件，但不要在需求阶段擅自补写未确认的数据库表或框架。

## 动手实验

把“系统要支持客服快速退款”转换成一份用例，至少包含参与者、触发、三个前置条件、五步主流程、一个替代流程、一个失败流程和两个后置条件。

写作顺序建议：先写一句“客服希望完成……”，再补开始前必须成立的条件，最后检查每条分支是否都有可观察结果。不要为了让主流程达到五步而拆分同一个无意义动作。

评分 20 分：参与者 3 分，触发与前置条件 4 分，主流程 5 分，异常路径 4 分，后置条件 2 分，目标清晰 2 分。

## 常见错误与排查

| 现象 | 原因 | 修复 |
| --- | --- | --- |
| 用例只有页面操作 | 把界面脚本当成业务目标 | 改写为参与者目标 |
| 没有异常流程 | 只描述理想路径 | 从现状流程提取失败和人工接管 |
| 角色和权限混用 | 业务职责与系统授权未分开 | 分别描述业务角色和授权角色 |
| 后置条件不可验证 | 只写“处理成功” | 写状态、编号、审计和数据结果 |

## 安全与生产注意事项

**<u>高风险操作必须在用例中显式写出权限校验、审批和审计结果。</u>**不要把“系统已登录”当作所有授权的替代品。已登录只说明身份经过某种验证，不代表此人可以退款、审批或查看任意订单。

## 本课总结

- 用例围绕参与者目标，而不是界面按钮。
- 成功、替代和失败流程都属于真实需求。
- 前置和后置条件必须可验证。
- 业务角色和系统授权角色需要分开描述。

## 思考题

退款请求已经提交，但支付系统 30 秒没有响应。这个情况属于替代流程、失败流程还是新的用例？请说明判断依据。

## 小测

1. “财务审批人”是参与者还是数据库表？
2. 用例为什么需要后置条件？
3. “点击按钮”是否通常是用例目标？
4. 支付拒绝时为什么不能只返回错误页面？
5. 写出一个退款用例的前置条件。
6. 场景题：客服已登录，但没有退款权限，仍尝试提交请求。这个请求应进入怎样的流程，后置结果至少包含什么？

## 答案与解析

1. 是参与者，具体是业务角色参与者。数据库表用于保存数据；即使系统里有一张审批人表，也不能把业务概念本身说成数据库表。
2. 后置条件让团队知道完成后应观察到什么结果，并支持验收测试。只写“流程结束”无法判断状态、数据和审计是否符合要求。
3. 通常不是。按钮只是交互手段，用例应描述参与者要达成的业务目标，例如“完成退款”。
4. 还需要保留原因、状态和人工接管路径，避免请求既未成功又无法追踪。错误页面可以存在，但不能成为全部业务处理。
5. 示例：订单存在、未完成退款、客服具备对应权限。答案必须是用例开始前能检查的条件，而不是“系统运行得很快”这类质量描述。
6. 应进入权限拒绝的失败或例外路径，不得继续向支付系统发送退款指令。后置结果至少包含明确的拒绝状态、可追踪的原因和包含操作者与时间的审计记录；具体提示内容仍需符合安全和业务要求。
