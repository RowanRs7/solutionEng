# 需求发现阶段综合测评

## 学习目标

完成本测评后，学习者能够将目标、现状、参与者、用例、需求、边界、优先级、验收和风险整理为一套彼此一致的需求交付物。建议闭卷完成概念题，再用参考答案和评分表自评。

## 知识检查清单

- [ ] 能区分业务目标、产出、成果和解决方案想法。
- [ ] 能识别赞助者、用户、运营、安全、数据所有者和决策负责人。
- [ ] 能区分事实、假设、问题和待回答问题，并用证据描述现状。
- [ ] 能为场景写出主流程、备选流程、失败结果和后置条件。
- [ ] 能将模糊质量要求改写为含条件、响应、阈值和验证边界的要求。
- [ ] 能声明范围、约束、依赖、假设、优先级和变更规则。
- [ ] 能定义 Given/When/Then 验收条件，并将其追踪到目标与证据。
- [ ] 能维护风险所有者、触发、缓解、应急和残余风险。

## 概念题

每题 2 分，共 30 分。先独立作答，再查看后面的参考答案。

1. 说明业务目标、产出和业务成果的区别，并举例说明为什么上线一个功能不等于实现成果。
2. 谁应对“是否接受首期范围”作最终决定？解决方案架构师可以提供什么，但不应独自替代谁的授权？
3. 现状访谈中“退款常常很慢”属于已验证事实吗？要把它变成证据还需要什么信息？
4. 区分用户、系统角色和外部系统参与者，并各举一个例子。
5. 功能需求和质量属性要求有什么区别？
6. 写出质量属性场景的六个组成要素。
7. 说明系统边界为什么不等同于网络边界或公司所有权。
8. 给出一个技术约束和一个假设，并说明如何避免将假设伪装成事实。
9. MoSCoW 中 Must 和 Won't this time 分别表达什么？
10. Given/When/Then 的 Then 应描述哪类结果？
11. 什么是需求追踪关系？它如何帮助评估变更？
12. 风险事件、触发条件和缓解措施分别是什么？
13. 风险所有者与缓解措施执行者是否必须是同一人？说明责任边界。
14. 为什么高影响低概率风险仍可能需要特别处理？
15. 列举需求包中至少六类必要内容，并说明至少一种应关联的验证证据。

### 常见错答分析

| 题目 | 常见错答 | 为什么不充分 | 纠正方向 |
| --- | --- | --- | --- |
| 1–2 | 把已上线功能当成业务成果，或由架构师替业务负责人接受范围。 | 产出不等于使用后的变化；建议权不等于授权权。 | 把目标写成可观察成果，并标出各领域的决策所有者。 |
| 3–4 | 把访谈意见当成事实，或把外部系统、用户和权限角色混为一谈。 | 缺少来源/样本的主张无法验证；身份、交互和系统边界回答不同问题。 | 补证据来源与上下文，分别标注参与者、用户和系统角色。 |
| 5–8 | 用“快/安全”代替阈值，或按网络/所有权推断项目边界。 | 不能验收，也可能漏掉跨组织责任。 | 补条件、响应、度量和边界责任；把未证实信息列为假设。 |
| 9–11 | 所有需求都列 Must；Then 只写内部实现；变更后不更新测试。 | 无法形成可执行取舍或判断业务结果，追踪链会断裂。 | 明确本次不做项，写可观察结果，并评估受影响的验收与证据。 |
| 12–15 | 把已发生事件列为未来风险；因概率低就忽略重大影响；需求包只堆文档不连目标。 | 风险状态失真，重大责任未决，产物难以指导验收。 | 区分问题/假设/风险，定义应对责任，并建立目标到证据的关联。 |

## 场景分析

某城市社区医疗机构准备试点线上预约和检查报告查询。前台称每天约有 300 名患者到场，但没有排队时长记录；患者希望手机端查询报告，医生要求报告只能对本人可见；现有身份系统由集团 IT 管理，接口文档尚未拿到；试点日期为两个月后。业务负责人提议同时加入自动诊断建议，医生对此尚未评估。

请区分已知事实、假设、待回答问题和解决方案想法。识别至少五类利益相关者；提出试点目标和一项候选指标；写出范围内、范围外或待定项；识别两个高优先级风险并指定验证行动。指出哪些决定必须由医疗/隐私/业务授权者确认。

## 架构师交付物练习

为上述医疗试点创建一页需求包，至少包含：

1. 目标、成果指标、决策负责人和用户/利益相关者。
2. 现状证据与证据缺口；用例主流程和一个失败/例外流程。
3. 功能需求和至少两项可测量质量要求。
4. 系统边界、组织/技术约束、依赖、假设和开放问题。
5. 首期优先级、排除项、至少两条 Given/When/Then 验收标准。
6. 两条风险记录，包含概率/影响、触发、所有者、缓解、应急和期限。
7. 目标 → 需求 → 验收 → 证据的追踪关系。

不要求画技术架构图或选择厂商。需求包应突出待授权和待验证的内容，不能用想象补全缺失事实。

## 评分标准

总分 100 分。概念题 30 分，场景分析 30 分，需求包 40 分。

| 部分 | 分值 | 满分标准 |
| --- | ---: | --- |
| 概念题 | 30 | 术语和角色边界准确，解释“为什么”，不是只背词语。 |
| 场景：事实、目标与指标 | 8 | 区分事实/假设/问题/想法；目标有候选指标并注明基线缺失。 |
| 场景：利益相关者与范围 | 7 | 覆盖患者、医生、前台、集团 IT、隐私/安全和业务决策者；将自动诊断标为待评估而非默认试点范围。 |
| 场景：需求、风险与决定 | 15 | 质量要求有条件/阈值；风险有负责人、触发、应对、期限；说明需授权者决定的事项。 |
| 需求包：内容完整与可评审 | 20 | 覆盖目标、利益相关者、证据、用例、需求、边界、优先级、验收、风险和开放问题。 |
| 需求包：验收与追踪 | 10 | Given/When/Then 有可观察结果；目标、需求、验收及证据关联。 |
| 需求包：风险与一致性 | 10 | 两条风险可执行；决策、版本、待定事项醒目，无互相矛盾的承诺。 |

## 参考答案与解析

### 概念题答案

1. 目标描述希望改变的方向，如缩短退款处理时间；产出是交付物，如退款查询页面；成果是使用后的可观察变化，如平均处理时间下降。产出完成不证明用户使用或业务指标改善。
2. 有授权的业务赞助者/产品负责人作范围和价值决定。架构师提供影响分析、选项、依赖、风险和建议，但不能代替业务、财务、安全或合规负责人接受其领域风险。
3. 不是。它是未经量化的说法/线索。需要样本范围、时间窗口、起止定义、分布（如 P50/P95）、流程观察或系统日志，并注明数据来源和局限。
4. 用户是使用系统完成任务的人，如患者；系统角色是授权模型中的权限类别，如医生；外部系统参与者是边界外交互系统，如集团身份服务。一个人可有多个角色，概念不可互换。
5. 功能需求描述系统做什么；质量属性要求描述行为在性能、安全、可用性等条件下应达到什么水平。
6. 刺激源、刺激、环境、对象、响应、响应度量。
7. 网络位置和组织所有权不决定本项目负责交付什么；边界应按承诺改变的能力、数据和责任声明。
8. 约束例：集团强制使用已批准身份平台；假设例：该平台支持单点登录回调。约束附政策/合同来源，假设标为待验证并指定负责人和期限。
9. Must 表示本次交付不可缺少且有理由的范围；Won't this time 表示本次明确不交付，不等于永远不考虑。
10. Then 描述用户或系统可观察的结果，例如拒绝越权请求并留下审计事件，而非只描述内部代码调用。
11. 将目标、需求、验收和证据关联起来。变更时可定位受影响目标、测试、责任人和范围，判断是否需要重估或交换范围。
12. 风险事件是未来可能发生并造成影响的不确定事件；触发是需要启动响应的观察信号；缓解是事前降低概率/影响的措施。
13. 不必相同。所有者对跟踪和结果负责，可将具体工作分派给执行者，但要保留状态、期限和升级路径。
14. 低概率不代表可忽略；若影响涉及患者安全、隐私、资金或法规，后果可能不可接受，应有控制、升级或正式接受决定。
15. 例如目标、利益相关者、现状证据、用例、功能/质量需求、边界约束依赖假设、范围优先级、验收、风险。验收可关联到集成测试、审计记录或用户测试结果。

### 场景分析参考思路

- 已知/待核实事实：试点两个月后；前台报告每天约 300 人，但其来源和误差未知；集团管理身份系统；尚未取得接口文档。
- 假设：线上预约可减少现场等待；身份系统允许医疗应用接入；报告已有可用电子数据。每项都需验证责任人和期限。
- 待回答问题：当前排队时间分布；报告生成和发布流程；患者如何证明身份；医生能否代理查看；隐私与保存要求；集团接口审批时长。
- 解决方案想法：手机端查询、自动诊断建议。报告查询是候选需求；自动诊断涉及临床风险，不应仅凭提议直接进入试点。
- 利益相关者：患者、医生、前台、医疗运营、集团 IT/身份平台所有者、隐私/安全负责人、业务赞助者、报告数据所有者。
- 候选目标：减少患者为查询报告而到场/来电；先建立基线，再设定试点期下降比例。不得在没有基线时捏造“下降 30%”为承诺。
- 高优先级风险：身份接口审批/能力不满足，可能阻塞试点；医生授权映射错误，可能泄露报告。前者通过集团 IT 评审和沙箱接入验证；后者由隐私/安全负责人确认权限模型并执行越权测试。
- 自动诊断列为本次范围外或待专项评估，须由临床、合规与业务负责人共同决定；患者报告访问和数据处理要求也须经隐私/安全授权。

常见错误：把“每天 300 人”直接当成准确基线；将自动诊断视为普通页面功能；认为集团拥有身份系统就能跳过接入审批；凭空给出业务收益比例。

### 需求包参考结构

| 部分 | 参考内容 |
| --- | --- |
| 目标 | 在试点范围内减少为查询报告发生的线下/电话请求；先测基线，再由业务负责人批准改善目标。 |
| 利益相关者 | 患者、医生、前台、运营、集团 IT、隐私/安全、业务赞助者、报告数据所有者。 |
| 用例 | 患者经身份验证查看已发布报告；报告未发布时显示状态并提供咨询渠道。 |
| 功能需求 | 已认证患者可查看与本人关联且已发布的报告；医生仅能按授权关系查看其负责患者的报告。 |
| 质量要求 | 试点负载下查询 P95 不超过经基线/容量评审确认的阈值；未授权访问返回拒绝且写审计记录。阈值待容量测试和安全评审定稿。 |
| 边界/依赖 | 本应用负责预约和报告访问体验；依赖集团身份、报告数据源和医院网络；自动诊断不纳入首期。 |
| 假设/开放问题 | 报告可通过稳定接口读取；集团身份团队提供测试环境；患者代理访问规则待隐私负责人确认。 |
| 验收标准 | Given 患者通过身份验证且报告已发布，When 查询本人报告，Then 返回报告及发布时间；Given 患者尝试访问他人报告，When 请求该报告，Then 返回拒绝且生成审计事件。 |
| 风险 | 身份集成延误：集团 IT 负责人在第 2 周前提供接口确认，否则评估调整试点/手工验证；越权访问：安全负责人完成威胁评审和负向权限测试。 |
| 追踪证据 | 目标 G1 → 报告查询需求 F1 → 验收 AC1 → 权限/集成测试结果及审计样本。 |

合理答案可有不同技术方案或指标，但必须标记未经确认的数字和决定，不能把建议当成已批准承诺。

- **80–100 分：**完成需求包自检后，进入[传统解决方案模块](../00-overview.md)的方案设计阶段。
