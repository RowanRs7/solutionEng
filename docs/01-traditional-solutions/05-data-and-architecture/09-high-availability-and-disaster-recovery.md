# 高可用、容错与灾难恢复

## 为什么需要学习

晴空商城把订单服务从 2 副本扩到 4 副本，全都跑在同一可用区。去年 618 上午，该可用区 18 分钟网络抖动让下单成功率从 99.8% 掉到 0：4 个副本同时失联，多出的副本没换来一秒可用性。

同一周，运维第一次真做恢复：从 02:00 全量备份加 binlog 恢复到新实例花了 6 小时 40 分，而承诺的 RTO 是 2 小时；丢失的支付回调又造成 300 多笔重复退款争议。

三个现象是一件事的三面：冗余没跨故障域、恢复时间从未被测、容量没按“少一半机器”设计。

> **核心结论：** 可用性由最弱的一环和最大的故障域决定，不由副本数量决定；灾备能力只有演练过才算存在。

## 学习目标

完成本课后，你能够：

- 用*故障域*与串联、并联模型算出年停机时间，指出只加副本却不跨域的“假冗余”。
- 为一个业务写下可验收的 *RTO* 与 *RPO*，据此选择备份频率与恢复方式。
- 判断剩余容量能否接住峰值，算出所需实例数。
- 设计一次带断言、回滚和记录的灾备演练，说明它证明了什么。

## 业务场景

晴空商城（商城、订单、支付、仓储、客服，退款流程）把可用性写进了合同，但数字还没落到设计上：

| 事实 | 数值或现象 |
| --- | --- |
| 流量 | 日常下单峰值 400 rps，大促 1200 rps |
| 部署 | 订单、库存各 2 副本；支付 3 副本；MySQL 主从异步复制 |
| 可用区 | az-a 与 az-b；订单的两个副本都在 az-b |
| 承诺 | 下单可用性 99.9%，RTO 2 小时，RPO ≤ 15 分钟 |
| 备份 | 每日 02:00 全量，binlog 每 5 分钟归档，从未演练 |

架构师要回答的不是“买几台机器”，而是：99.9% 指“下单成功”还是“页面能打开”？2 小时从谁开始计、到哪一步算恢复？**这些答案决定副本放哪、多久备份，而不是反过来。**

## 核心概念

*可用性*是观察期内可服务时间的占比，必须绑定“什么算可用”。*故障域*是一次故障能同时摧毁的最大范围：一个进程、一台主机、一个可用区、一个区域，甚至一家外部供应商。<u>副本只有在不同故障域里才是冗余，在同一域里只是同一份风险的重复。</u>*冗余*是为接替故障准备的额外能力；*单点故障*指失效即导致整体不可用的组件。

*容错*与*高可用*常被混用，差别在中断是否可被感知：

| 维度 | 容错 | 高可用 | 灾难恢复 |
| --- | --- | --- | --- |
| 目标 | 故障时仍正确服务，用户无感 | 缩短不可用时间，允许短暂切换 | 区域级灾难后重建业务 |
| 前提 | 冗余跨故障域 | 剩余容量能接住峰值 | 备份真能恢复，有人会操作 |
| 验证 | 故障注入后结果不变 | 摘除与接盘时长 | 演练测出的真实 RTO/RPO |

*RTO* 是从故障发生到业务恢复的最长时间；*RPO* 是恢复后最多允许丢失多长时间的数据：<u>RPO 为 0 几乎必然要求同步复制或“未同步就不确认”，代价是写延迟与可用性</u>。*灾备*是为区域级灾难准备的重建能力，核心产出就是这两个数字。承诺变成证据只能靠*演练*：故意制造故障、走完整恢复流程并记录实测时长的活动，也叫游戏日。

备份不能被副本替代：在线副本持续同步，误删与勒索加密会一起到达；*快照*可被同权限删除；只有离线或不可变存储上的归档备份能在错误发生前停下。<u>判断标准不是“有没有备份”，而是“能不能在隔离环境恢复出来”。</u>

*容量余量*是稳态负载之外预留的能力；*N+1* 指“坏掉一份仍够用”，<u>它约束一组副本，不是某一台机器</u>。

## 工作原理

以“az-b 抖动”为线索，按时间顺序看系统如何反应：

1. **故障发生（t=0）**：丢包率从 0.1% 升到 40%，进程却没崩溃，健康检查可能仍通过——<u>“进程活着”和“能正确服务”是两件事</u>，检查必须覆盖关键下游。
2. **探测与摘除（t+30s 到 t+2min）**：负载均衡按阈值（连续 3 次失败、间隔 10 秒）停止转发。探测间隔乘失败次数就是这段不可用时间，<u>设得过长等于自己延长故障</u>。
3. **流量重分配（t+2min）**：请求集中到健康副本；服务发现缓存或连接池仍持有旧地址时，表现为“已恢复却还有零星超时”。
4. **容量接盘**：剩余副本要承接全部峰值。订单两副本同域等于零副本；即使跨域，两域各 2 副本、水位 70%，失去一域后每台升到 140%，连接池先耗尽，<u>可用区故障扩散成整站雪崩</u>。**切换能否成功取决于余量，而不是副本数量。**
5. **状态恢复（分钟到小时）**：无状态副本重连即用；有状态组件要选主或提升从库。异步复制下未送达的事务就是 RPO 的真实损失，同步复制可能因等从库而写超时，切换后还要防旧主复活双写。
6. **数据恢复**：确认恢复点 → 准备独立环境 → 还原全量 → 回放 binlog → 一致性校验（订单数、流水、金额合计）→ 切换流量 → 业务验证。**RTO 是这条链所有步骤之和，包含申请资源与校验，不只是拷贝数据。**
7. **复盘与整改**：把每步实测时长与目标逐项对比，形成带负责人和期限的改进项，让下一次演练验证它们。

结论两条：**先看故障域，再看副本数；先测恢复总时长，再谈 RTO。**

## 架构与选型

| 方案 | 适用 | 不适用 | 典型 RTO | 成本 |
| --- | --- | --- | --- | --- |
| 同可用区多副本 | 单机故障、滚动发布、读扩展 | 机房级故障；同宿主机上的“多副本” | 秒级 | 低 |
| 跨可用区主动-被动 | 多数在线业务，目标 99.9%–99.95% | 跨区延迟敏感、无法容忍切换抖动 | 分钟级 | 中 |
| 跨区域主动-被动（温备） | 区域级灾难、监管要求异地留存 | 强一致写、预算极紧 | 小时级 | 中高 |
| 双区域主动-主动 | 99.99% 以上、要求低延迟 | 交易数据无法冲突消解；团队无多活经验 | 接近零，有冲突风险 | 高 |
| 仅备份恢复 | 内部系统、可容忍数小时中断 | 下单、支付等核心链路 | 数小时 | 最低 |

选型顺序是“先定 RTO/RPO，再定方案”。下单与支付不允许只靠备份，退款记录须接近零丢失，报表可接受小时级中断。

扩容策略按证据选：*纵向扩容*（加 CPU、内存）最快但有上限，故障域不变；*水平扩容*（加实例）要配无状态设计才能真正分摊；*自动扩缩*适合可预测的波动，但冷启动与缩容过急会吃掉余量；*削峰排队*用异步与限流摊平峰值，常比多买机器便宜。判断余量只问一句：**失去最大故障域后，剩余容量是否仍大于峰值？**

## 最小示例

问题：把“可用性、容量余量、RTO/RPO”从口号变成可复现判定。环境：任意 `python3`（3.8+），只用标准库，不联网、不连数据库。

```python
import math

YEAR_MINUTES = 365 * 24 * 60        # 525600 分钟：把百分比折成可感知的停机时长

# 每项服务：(单副本可用性, 副本数, 副本覆盖的故障域数)
SERVICES = {
    "gateway":   (0.9990, 2, 2),    # 两副本分处 az-a 与 az-b，独立故障域
    "order":     (0.9990, 2, 1),    # 两副本都在 az-b：数字上双副本，实际一个域
    "payment":   (0.9995, 3, 3),    # 三副本三域，最坏只损失一份
    "inventory": (0.9990, 2, 2),
    "mysql":     (0.9995, 2, 2),    # 主从跨域但异步复制，切换会丢最后一段写入
}

def availability(single, replicas, domains):
    """只有跨故障域的副本才是独立冗余，才配做并联概率计算。"""
    effective = min(replicas, domains)     # 同域内第二个副本不降低整体失效率
    return 1 - (1 - single) ** effective   # n 份独立冗余：全部失效才算失效

def downtime(a):
    return (1 - a) * YEAR_MINUTES          # 换算成年停机分钟数，便于横向比较

print("service      single  replicas  domains  eff  downtime_min")
total = 1.0                                # 串联系统：任一环节不可用，整体就不可用
for name, (single, replicas, domains) in SERVICES.items():
    a = availability(single, replicas, domains)
    total *= a                             # 串联相乘：最弱的一环决定全局
    note = "  <- replicas in one domain, no benefit" if domains < replicas else ""
    print(f"{name:<12} {single:<7} {replicas:<9} {domains:<8} "
          f"{min(replicas, domains):<4} {downtime(a):>8.1f}{note}")
print(f"\ntotal availability {total:.6f}  yearly downtime {downtime(total):.1f} min")

# 容量：稳态水位之外还要接得住“失去最大故障域”的流量
PEAK_RPS, INSTANCE_RPS, WATERMARK = 1200, 400, 0.7
steady = math.ceil(PEAK_RPS / (INSTANCE_RPS * WATERMARK))   # 按 70% 水位算稳态实例数
print(f"\nsteady instances needed (peak {PEAK_RPS} rps, {WATERMARK:.0%}): {steady}")
for n in (steady, steady * 2):                              # 对比“刚够稳态”与“留足接盘”
    survive = n // 2 * INSTANCE_RPS                         # 流量均分两域，失去一域只剩一半
    print(f"  {n:>2} instances -> surviving capacity {survive} rps "
          f"{'OK' if survive >= PEAK_RPS else 'OVERLOAD: cannot take over peak'}")

# RTO/RPO：恢复点看增量归档间隔，恢复时长要把所有步骤累加
TARGET_RTO_H, TARGET_RPO_MIN = 2.0, 15
BINLOG_INTERVAL_MIN = 5
FULL_RESTORE_H, BINLOG_REPLAY_H, EXTRA_H = 4.5, 1.0, 1.0
rpo = BINLOG_INTERVAL_MIN                                    # 最坏丢掉最后一个未归档间隔
rto = FULL_RESTORE_H + BINLOG_REPLAY_H + EXTRA_H             # 含申请资源与一致性校验
print(f"\nRPO {rpo} min (target <= {TARGET_RPO_MIN}) -> "
      f"{'PASS' if rpo <= TARGET_RPO_MIN else 'FAIL'}")
print(f"RTO {rto:.1f} h (target <= {TARGET_RTO_H}) -> "
      f"{'PASS' if rto <= TARGET_RTO_H else 'FAIL'}, gap {rto - TARGET_RTO_H:.1f} h")
```

```bash
python3 ha_check.py
```

预期输出：

gateway      0.999   2         2        2         0.5

脚本三段：按故障域折算有效副本数，串联相乘得全站可用性，再用峰值与恢复步骤判定容量与 RTO/RPO。结论是 `order` 的 525.6 分钟停机主导全站，**可用性被短板锁死**；5 台实例故障时只剩 800 rps，须按 10 台部署或限流；RTO 差 4.5 小时，缺口在还原与校验。

## 动手实验

前置条件：本机有 `python3`（3.8+），把上面的脚本存为 `/tmp/dsh-ha-lab/ha_check.py`，不联网、不连数据库。

1. `mkdir -p /tmp/dsh-ha-lab && cd /tmp/dsh-ha-lab`，保存脚本后运行 `python3 ha_check.py > baseline.txt`，记下基线。
2. 修故障域：把 `order` 改成 `(0.9990, 2, 2)`，重跑，记录 `order` 的年停机与全站总可用性。
3. 加外部依赖：新增 `"carrier": (0.999, 1, 1)`（快递查询一域一副本），重跑，观察总可用性的数量级变化。
4. 改恢复参数：把 `BINLOG_INTERVAL_MIN` 设为 `1`、`FULL_RESTORE_H` 设为 `2.0`，重跑，看 RPO 与 RTO 判定各自怎么变。
5. 写结论：三条改动对 99.9% 承诺的贡献排序，第 3 步为何抵消第 2 步收益。

预期结果：第 2 步后 `order` 年停机降到 0.5 分钟，全站 0.999997、约 1.7 分钟；第 3 步后回落到 0.998997、约 527 分钟，几乎抵消第 2 步收益；第 4 步 RPO 变成 1 分钟（达标），RTO 变成 4.0 小时（缺口 2.0 小时）。

验证方法：`python3 ha_check.py | diff baseline.txt -`，确认差异只出现在改过的行；再核对 `carrier` 的 `downtime` 是否约等于 525.6。清理方法：`rm -rf /tmp/dsh-ha-lab`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 副本翻倍，故障时仍全站不可用 | 副本同可用区或同宿主机 | 列出每副本所在可用区与宿主机 | 强制反亲和、跨域部署，演练只杀一域 |
| 切走一半容量后雪崩 | 稳态水位过高，接不住峰值 | 对比故障时段 QPS 与单实例极限 | 水位降到 60%–70%，预留 N+1，故障期限流 |
| 备份“成功”但恢复失败 | 只校验任务状态，从未真恢复 | 隔离环境实际恢复并跑校验 | 演练做真实恢复，校验行数与金额合计 |
| 演练很快结束，真实故障仍超时 | 只测主库拷贝，没测申请与切流 | 用秒表逐步记录耗时 | 把审批、DNS 切换、校验纳入计时 |

## 安全与生产注意事项

**<u>备份与生产共用同一把权限、同一个云账号时，勒索或误删会连备份一起消失。</u>** 后果是不可恢复的数据丢失，且往往在需要恢复的那一刻才发现。缓解：备份写入独立账号或不可变存储，恢复与删除权限分离，保留多代并定期验证可恢复性。

**<u>把生产库当演练目标，或在演练里真实切流，会把演练变成第二次事故。</u>** 后果是真实用户受影响，团队为尽快结束会跳过断言。缓解：在隔离环境或影子流量下演练，切流先在 1% 流量验证，事先写明回滚条件与决策人。容灾环境同样复制全量个人信息，需沿用生产的分类、脱敏与保留期管理。

## 本课总结

- 可用性由最弱的一环和最大的故障域决定，副本数量本身不产生可用性。
- 容错、高可用、灾备是三个目标，验证分别是故障注入、切换时长和真实演练。
- RPO 由复制方式与归档间隔决定，RTO 由恢复链上所有步骤之和决定。
- 备份不能由副本替代：误删与加密会顺着复制链路同步到每份副本。
- 切换能否成功取决于剩余容量能否接住峰值；**没有演练过的 RTO 只是愿望**。

## 思考题

晴空商城承诺下单 RTO 2 小时、RPO 15 分钟，实测 RTO 6.5 小时。团队提出：A. binlog 归档从 5 分钟改成 1 分钟；B. 采购同城温备，把恢复拆成“先浏览查单、再恢复下单”；C. 把公开承诺改成 8 小时。请判断哪个方案真正缩小了差距，另两个改变了什么，并用什么证据证明新 RTO 可达。

参考思路：A 改善 RPO，对 RTO 几乎无影响，因为耗时集中在前面的全量还原与校验；C 把技术缺口转成商务承诺，可能合理，但须由业务方基于损失量化决定并给出降级方案；只有 B 直接压缩恢复链，用预热环境缩短下单恢复。证据应是一次全流程演练的逐步计时记录。

   A. 备份文件的压缩率　B. 数据复制方式与增量归档间隔　C. 值班人数　D. CPU 主频
4. 为什么“数据库只读副本”不能替代备份？
5. 场景题：客服工单系统要求 RTO 4 小时、RPO 0。运维建议“每日全量加每 5 分钟 binlog 归档”，称 RPO 接近 0。这个建议合理吗？该怎么改？

## 答案与解析

1. **C。**`(1-0.999)×525600 ≈ 526` 分钟，约 8.76 小时。A 是月停机量级；B 是 99.99% 的年停机；D 多一个数量级。
2. **错。**同域副本会被同一次故障带走，并联公式只在独立失效时成立；有效副本数取 `min(副本数, 故障域数)`，此处为 1。
3. **B。**RPO 由复制是否同步与归档间隔决定；压缩率只影响存储与还原速度，值班人数影响 RTO，CPU 无关。
4. 只读副本持续同步主库变更，误删与勒索加密同样应用过去，几分钟后副本就是“同样错误的数据”；备份是某个时间点的独立留存。
5. 不合理。每日全量加 5 分钟 binlog 的 RPO 约 5 分钟，并非 0，还原加回放也超过 4 小时。RPO 0 需同步复制或“未同步不确认”，代价是写延迟；更常见的是把 RPO 定成 ≤1 分钟，配合同城温备与恢复演练把 RTO 压进 4 小时。

### 动手实验参考

第 2 步后全站约 0.999997（年停机 1.7 分钟），说明短板在 `order` 的故障域；第 3 步新增 `carrier`（1 副本、1 域）把总可用性拉回 0.998997（527 分钟），因为它以单点串联进主链路。第 4 步 RPO 达标而 RTO 仍为 4.0 小时，缺口在还原与校验。评分看能否把每行输出对应到“故障域、余量、恢复步骤”。
