# 时间、金额、UUID 与编码陷阱

## 为什么需要学习

晴空商城的月末对账暴露了三个偏差：退款总额比支付渠道少 0.03 元；一批"昨天"受理的退款被算进了前天的日报；同一个会员因为邮箱一条存空串、一条存 `NULL`，被重复建档两次。没有业务逻辑写错，问题全出在四个基础约定——时刻怎么存、钱怎么算、单号怎么生成、缺失值怎么表示。

这些默认值"能存但会错"：不报错、不告警，只以看似合理的数值出现在报表里，而它们往往在写第一张表时就被顺手定下。

> **核心结论：** 时间、金额、标识和文本都有"看起来能存、实际会错"的默认值；架构设计要在写第一行代码前把它们固定成团队约定。

## 学习目标

完成本课后，你能够：

- 说明内部统一以 UTC 存储时刻的理由，并写出一个带偏移量的 RFC 3339 时间戳。
- 判断金额该用整数最小货币单位还是定点小数，并指出二进制浮点的丢分位置。
- 在自增 ID、UUIDv4、UUIDv7/ULID 之间按排序与暴露需求做出选择。
- 区分 NULL、空串与占位值的语义，说明字符集与规范化各破坏什么。
- 为一个跨系统字段写出可执行约定，并指出违约时最先出错的环节。

## 业务场景

晴空商城的退款链路横跨商城前台、退款服务、支付渠道和财务对账，同一笔退款单上就压着这四个侧面：

- **时间**：客服在北京时间 23:40 受理，服务容器的时钟是 *UTC*（全球统一时间基准），财务日报按 Asia/Shanghai 的"自然日"切分。三处都"对"，切出的日期却不同。
- **金额**：599.97 元的订单按 3 件商品分摊退款，分之和必须与总额严格相等；差额只有几分钱，财务却要逐笔解释。
- **标识**：退款单号要展示给客服、回传支付渠道，还要做重复提交的幂等键——既要能对外，又要能按受理顺序分页。
- **文本与空值**：客服备注可能为空；商品标题含 emoji，从不同渠道粘贴时还可能带不同的重音字符编码。

## 核心概念

- *UTC* 是全球统一的时间基准，不受夏令时影响，系统内部唯一的时间坐标。
- *时区偏移量* 是本地时刻与 UTC 的固定差值（如 `+08:00`），只说明"展示用哪个钟"；*夏令时* 地区每年拨钟一小时，同一个壁钟时刻可能对应两个 UTC 时刻。
- *Unix 时间戳* 是从 1970-01-01T00:00:00Z 起算的秒或毫秒，本身永远是 UTC，适合差值与排序。
- *定点数* 是小数位固定、按十进制精确存储的类型（如 `DECIMAL(12,2)`）；*最小货币单位* 是货币不可再分的量，人民币为"分"。
- *UUID* 是 128 位、无需中心协调即可生成的标识；*ULID* 是 48 位毫秒时间戳加 80 位随机数的可排序变体。
- *空值（NULL）* 表示"未知或不适用"，参与三值逻辑：`NULL = NULL` 的结果是未知而非真。
- *Unicode 规范化* 把等价但码点不同的文本统一成一种形式，最常用 NFC。

| 方面 | 常见错误表示 | 推荐表示 | 晴空商城示例 |
| --- | --- | --- | --- |
| 时刻 | `2026-10-19 23:40` 无时区字符串 | 存 UTC，输出带偏移量 | 存 `2026-10-19T15:40:00Z` |
| 金额 | `float`/`double` 存 599.97 | 整数分或 `DECIMAL(12,2)` | 599.97 元存 59997 分 |
| 标识 | 自增整数直接对外 | 内部主键与对外单号分离 | 单号用 UUIDv7，主键仍自增 |
| 缺失值 | 有时空串、有时 `NULL`、有时 `-` | 全链路统一 `NULL` | 客服备注未填时为 `NULL` |
| 文本 | 依赖库默认字符集 | 显式 UTF-8（`utf8mb4`）+ NFC | 商品名含 emoji 与重音字符 |

<u>"金额用浮点"和"空值用空串"几乎是所有对账差异的源头</u>：它们不报错，只在统计时以几分钱或几条重复记录的形式出现。

## 工作原理

一笔退款从受理到进入财务日报，同一批字段要被反复换表示，而约定必须保持等价。

1. **接收回调**：支付渠道返回成交时刻，保留原始字符串（争议时举证）与解析后的带时区时刻两份。
2. **折算入库**：换算成 UTC 后写入。列类型必须能承载时区；若只能存 `timestamp`，则约定它恒为 UTC。
3. **生成单号**：在事务开始前生成 *UUIDv7*。前 48 位是毫秒时间戳，按字符串排序即近似按受理时间排序；同毫秒内的随机后缀避免泄漏业务量。
4. **幂等登记**：把（订单号、退款批次）写成唯一约束作为业务幂等键；UUIDv7 只是"这次请求的唯一名字"。
5. **金额分摊**：从订单行读出 `DECIMAL(12,2)`，先转成"分"的整数再按比例分摊；余数用*最大余数法*逐分补齐，保证分之和等于总额。
6. **处理空值**：备注、渠道流水号"未发生"时一律写 `NULL`；只有"明确提交了空字符串"才存空串，并在字段注释写清区别。
7. **规范化文本**：入库前对商品名做 NFC 规范化再以 UTF-8 存储；比较、去重、匹配全部基于规范化后的值。
8. **对外输出与对账**：接口按调用方时区输出带偏移量的时间，金额以字符串加货币代码输出；财务按 UTC 边界求和、按展示时区切日。

## 架构与选型

| 决策点 | 适用方案 | 不适用场景 | 代价与权衡 |
| --- | --- | --- | --- |
| 时刻存储 | 全库 UTC + 带时区列类型 | 纯单机、无跨时区报表的内部工具 | 展示层需要统一转换函数 |
| 金额 | 整数最小单位（分） | 多币种混合、汇率连续计算 | 精确、跨语言一致，但展示点都要除以 100 |
| 金额 | `DECIMAL(12,2)` | 极小单位或加密货币 | 库内可聚合，但应用层仍不能先转浮点 |
| 标识 | 自增整数做内主键 | 主键对外暴露、分库分表、离线批量生成 | 写入局部性好、体积小，但可枚举且依赖单点分配 |
| 标识 | UUIDv4 | 作为聚簇主键写入密集的表 | 不可枚举，但索引随机写、不可按时间排序 |
| 标识 | UUIDv7 / ULID | 需要"绝无时间信息"的对外标识 | 可排序、索引友好，但泄漏毫秒级生成时刻 |
| 缺失值 | 统一 `NULL` | 字段同时有"零"与"未知"两种业务含义 | 语义清晰，但需处理三值逻辑 |

选型依据是三个问题：字段会不会对外暴露？需不需要在库内按时间排序？历史数据能否承受一次迁移？只要有一个答案是"会"，就优先选可排序且不可枚举的标识。

## 最小示例

脚本用 Python 3 标准库演示四类陷阱。环境为 Python 3.10 及以上（`uuid.uuid7()` 需要 3.14+，更早版本可用 `uuid6` 或 ULID 库）；输入是四个硬编码样例值，输出是每类陷阱的对照结果。

```python
# 场景：晴空商城把一笔 599.97 元的退款登记入账，并生成对外单号。
from datetime import datetime, timezone, timedelta
from decimal import Decimal, ROUND_HALF_UP
import unicodedata
import uuid

# ① 时间：入口时刻必须自带偏移量，入库前统一折算成 UTC
paid_at = datetime(2026, 10, 19, 23, 40, tzinfo=timezone(timedelta(hours=8)))  # 客服在北京时间看到的受理时刻
print("入口:", paid_at.isoformat())                        # 偏移量随时刻一起保存，才不会被误读
print("入库:", paid_at.astimezone(timezone.utc).isoformat())  # 只存 UTC，展示时再换回本地时区
print("纪元秒:", int(paid_at.timestamp()))                 # 与支付渠道对账时常用的整数形式

# ② 金额：内部只用"分"的整数，绝不经过二进制浮点
print("浮点丢分:", int(4.35 * 100))                        # 4.35 在 float 里是 434.999…，截断后少 1 分
total = Decimal("599.97")                                  # 用字符串构造 Decimal，避免把浮点误差带进十进制
print("定点数:", total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))  # 显式指定舍入规则
print("转成分:", int(total * 100))                         # 十进制乘法不丢精度，转分安全

# ③ 标识：退款单号用 UUIDv7，前缀是毫秒时间戳，因此可按受理顺序排序
refund_id = uuid.uuid7()                                   # 每次运行都不同，但前缀随时间递增
print("退款单号:", refund_id)

# ④ 文本与空值：比较前先做 NFC 规范化；长度要区分字符数与字节数
title = "晴空 cafe\u0301 🧋"                                # 从不同渠道粘贴来的商品名，重音用了组合字符
print("规范化后相等:", unicodedata.normalize("NFC", title) == "晴空 café 🧋")
print("字符数/字节数:", len("晴空🧋"), len("晴空🧋".encode("utf-8")))  # 展示按字符算，存储按字节算
```

运行命令：

```bash
python3 time_money_refund.py
```

预期输出（单号每次运行不同）：

```text
入口: 2026-10-19T23:40:00+08:00
入库: 2026-10-19T15:40:00+00:00
纪元秒: 1792424400
浮点丢分: 434
定点数: 599.97
转成分: 59997
退款单号: 01a1535e-02e0-7xxx-8xxx-xxxxxxxxxxxx
规范化后相等: True
字符数/字节数: 3 10
```

流程是：先把同一时刻换成 UTC 与整数两种表示并验证等价；再用截断取整暴露浮点丢分，用 `Decimal` 展示正确做法；接着生成可排序的对外标识；最后验证两段"看起来一样"的文本规范化前并不相等。

三处关键设计选择：时间用 `timezone(timedelta(hours=8))` 而非无时区 `datetime(...)`，因为只有带偏移量的值才能无歧义换算；金额从字符串构造 `Decimal` 而非 float 字面量，因为误差在构造时就已存在；文本比较前显式 `normalize("NFC")`，而非依赖各层"看起来正常"。

## 动手实验

### 任务：亲手制造并修复四类数据偏差

前置条件：本机有 `python3`（3.10+）。

1. 把"最小示例"的脚本保存为 `/tmp/time_money_refund.py` 并运行，确认 `入库` 以 `Z` 结尾、`浮点丢分` 为 `434`、`转成分` 为 `59997`、`字符数/字节数` 为 `3 10`。
2. 把 `timedelta(hours=8)` 改成 `timedelta(hours=-5)` 重跑："入口"变了，而 `纪元秒` 与"入库"没变——偏移量只影响展示，不影响时刻本身。
3. 把 `Decimal("599.97")` 改成 `Decimal(599.97)` 重跑：输出变成一长串 `599.970000000000027…`，说明浮点误差在构造时就已固入。
4. 去掉第 ④ 段的 `normalize("NFC", title)` 直接比较：结果为 `False`，这正是"同一商品被重复建档"的机制。

预期结果：日期偏移、金额丢分、标识不可排序、文本重复这四类偏差都能复现，并各用一行改动修复。

验证方法：第 2 步 `纪元秒` 保持 `1792424400` 不变即为通过；第 3 步输出出现连续的 `0000000000` 小数即为通过；第 4 步输出 `False` 即为通过。

清理方法：`rm /tmp/time_money_refund.py`。实验不写数据库，也不产生持久状态。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 日报里同批退款被算进不同日期 | 库内存无时区本地时间，却按 UTC 边界切日 | 取三条记录，比较原值与 UTC 换算值 | 统一存 UTC，统计时显式指定展示时区 |
| 退款总额与渠道差几分钱 | 金额列是 `float`/`double`，分摊时逐笔舍入 | 查列类型；用整数分重算一遍 | 改为整数分或 `DECIMAL(12,2)`，分摊用最大余数法 |
| 新单号在列表末尾才出现 | 主键是 UUIDv4，随机分布 | 看主键前 8 位是否随机变化 | 换 UUIDv7/ULID，或另加 `created_at` 索引 |
| 唯一约束挡不住重复邮箱 | 空串与 `NULL` 混用，`NULL` 不参与唯一约束 | `SELECT COUNT(*), COUNT(DISTINCT email) FROM member` | 未知统一存 `NULL`，用部分唯一索引或业务校验兜底 |

## 安全与生产注意事项

**<u>把金额存成二进制浮点，会在多笔分摊和长期累加后产生无法解释的差额，对账失败时只能人工写调账凭证。</u>** 更严重的是重复退款：幂等判断若依赖"金额相等"，浮点比较可能把同一笔判成两笔。缓解办法是把金额固定为整数最小单位或定点小数，等值比较先转整数。

**<u>用可预测的自增 ID 或毫秒时间戳裸号作为对外单号，会泄漏业务量，并能被顺序枚举他人订单和退款记录。</u>** 缓解办法是内部主键与对外单号分离，对外用 UUIDv7/ULID，并在接口层按用户维度鉴权与限流。

**<u>把 NULL 与空串当成同义词，会让唯一约束、聚合和下游同步同时失效，甚至用空值覆盖已有真实数据。</u>** 在"最后写入者获胜"的同步里，一个未填写的字段就可能把客户已提交的手机号清空。缓解办法是在契约里固定缺失值语义，并区分"字段未提供"与"显式置空"。

## 本课总结

- 时刻只有一个真实值，表示方式可以有很多种；**系统内部存 UTC，展示层带偏移量**。
- 金额的本质是整数计数，浮点只是近似；**内部用最小货币单位的整数或定点小数**，舍入规则要显式写出。
- 标识的选型由用途决定：**不可枚举、可排序、可离线生成**三者优先级不同，UUIDv7/ULID 常是兼顾项。
- 空值是一种语义而不是一种写法；**NULL 表示未知，空串表示空内容**，混用会同时破坏唯一约束和聚合。
- 文本比较前必须规范化；字符集选错，数据会以 `?` 或乱码永久丢失。

## 思考题

晴空商城要新增"门店自提"：顾客可在任何时区下单，到北京、新加坡或伦敦的门店取货。凭证要打印"请在 2026-10-20 18:00 前到店"，系统要判断是否超时，财务要按门店当地自然日统计自提量。

请为下单时刻、截止时刻、超时判断、统计口径各写一条字段级约定：类型、时区、精度、是否保留原始输入；并说明门店实行夏令时时哪一处最容易出错。

参考思路：两个时刻都存 UTC，并额外保存生成截止时刻所用的门店时区标识（如 `Asia/Shanghai`）与原始输入字符串；超时判断用 UTC 时间差，不比本地壁钟；统计时先把门店时区的自然日边界换算成 UTC 区间再聚合。最容易出错的是夏令时：从"本地 18:00"反推时，时钟回拨那天会有两个 18:00，或某个 18:00 根本不存在，换算必须交给按 IANA 规则实现的时区库。

## 小测

1. 系统内部统一用 UTC 存储时刻，主要是为了解决什么问题？
   A. 节省存储空间　B. 消除时刻表示的多义性　C. 避免使用时间戳　D. 让数据库读写更快
2. 下列关于金额的说法，哪一项正确？
   A. `float` 只要保留两位小数就不会丢精度
   B. 金额应存为字符串
   C. 整数"分"与 `DECIMAL(12,2)` 都能精确表示两位小数金额
   D. 舍入规则无所谓，只要最后显示对
3. UUIDv7 相比 UUIDv4 的关键差异是什么？
4. 表中 `email` 列有唯一约束，却出现了两条 `email` 为 `NULL` 的记录。这一定违反约束吗？为什么？
5. 场景题：某团队把标题列定义为 `VARCHAR(50)`、字符集 `utf8`（3 字节），上线后含 emoji 的标题写入失败，于是决定"截断到 50 个字符再写入"。这个方案能解决问题吗？请说明理由并给出更好的做法。

## 答案与解析

1. **B。**UTC 让"同一时刻"只有一种数值表示，展示时才引入偏移量。A 与 D 与时间语义无关；C 恰好相反，时间戳本身就是 UTC 的一种表示。
2. **C。**整数分与定点小数都按十进制精确表示。A 错在浮点误差来自二进制表示，与保留几位小数无关；B 错在字符串无法可靠参与数值聚合与比较；D 错在舍入规则不一致会让分摊后总额与原始金额不等。
3. UUIDv7 的高 48 位是毫秒级 Unix 时间戳，其余为随机位，按字符串排序近似按生成时间排序，作索引主键时写入更集中；UUIDv4 全随机、不可排序，代价是 UUIDv7 前缀会泄漏生成时刻。
4. **不一定违反。**`NULL` 表示"未知"，唯一约束通常允许多行 `NULL`，因为两个未知值不能判定相等。这正是不能用 `NULL` 兼作"空内容"的原因；若业务不允许重复空值，应改用部分唯一索引。
5. 不能。3 字节 UTF-8 根本无法编码 emoji，截断只是让失败"看起来不报错"，实际会丢弃或替换字符，使商品名永久失真。更好的做法是把字符集与连接字符集统一改为 `utf8mb4`，长度上限按字符计，入库前做 NFC 规范化，并在校验层对超长或非法码点显式报错。

### 动手实验参考

第 2 步"入口"变为 `2026-10-19T10:40:00-05:00`，而 `纪元秒` 与"入库"不变，说明偏移量只是同一时刻的另一种写法。第 3 步的长小数说明误差在 float 字面量转 `Decimal` 时已固化。顺带验证 `round(2.675, 2)` 得到 `2.67`：依赖浮点舍入不可靠。
