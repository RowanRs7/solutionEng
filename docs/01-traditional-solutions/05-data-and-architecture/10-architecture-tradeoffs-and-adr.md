# 架构权衡、ADR 与容量成本

## 为什么需要学习

上一课给退款链路定下了同城双可用区、RPO 5 分钟、RTO 30 分钟。第二次评审会上，另外三个诉求同时压了上来：客服要求退款查询 P95 低于 800 毫秒，财务要求审计记录留存 7 年且不可删改，管理层要求这条链路的月度基础设施费用不超过 8000 元。开发提议加缓存，DBA 提议加只读库，运维提议把副本翻倍。

会开了三次没有结论。第三次结束时，级别最高的人说“用最稳的那个”，于是三项要求都按最高规格实现。三个月后账单是预算的两倍；有人问为什么这么选，谁都答不上来：讨论只留在会议里，容量按“感觉够用”估，成本没人算过。半年后同样的争论又从零开始。

> **核心结论：** 架构权衡不是选出“最好”的方案，而是用同一组可比较的指标暴露取舍、把取舍写成可被取代的记录，并用容量与成本数字证明它撑得住。

## 学习目标

完成本课后，你能够：

- 用一张加权评分表比较三个架构选项，并说明每项权重由谁确认。
- 写出含背景、选项、决定、后果与复核条件的 ADR，正确标注状态与取代关系。
- 按峰值 QPS、停留时间、冗余系数估算副本数，按保留期与副本因子估算存储与月成本。
- 判断一个决策该写成 ADR，还是留在设计文档或风险登记表里。

## 业务场景

晴空商城（自建商城、订单、支付、仓储、客服，退款流程横跨这几个系统）的退款链路第二次评审。可用的事实来自压测与上一季度账单：

1. 退款查询峰值 40 QPS，日均 4 QPS，单次查询在服务端停留约 120 毫秒。
2. 退款状态读多写少，读写比约 12:1，写入峰值 3 QPS。
3. 每日新增退款审计记录 1.2 万条，单条约 2 KB，财务要求留存 7 年且不可删改。
4. 客服要求查询 P95 低于 800 毫秒；上一课已定同城双可用区、RPO 5 分钟、RTO 30 分钟。
5. 管理层给出的月度基础设施预算上限是 8000 元。

评审桌上三个候选：A 沿用直连主库、只加本地缓存；B 增加独立只读库与缓存；C 引入事件流与物化视图。三个都“能跑”，差别只在代价——需要被权衡的正是这些代价。

## 核心概念

*架构权衡*（architecture trade-off）是在一组互相冲突的*质量属性*之间做显式取舍：提升可用性通常要花钱，压低延迟通常要付一致性代价。

*质量属性*是可测量、可设阈值的非功能指标，句式是“谁、在什么条件下、达到什么数值”。“P95 低于 800 毫秒、在网关侧测量”是质量属性，“性能要好”不是。

*ADR*（Architecture Decision Record）是只讲一个决策的短记录，固定回答背景、选项、决定、后果，并带*状态*（proposed、accepted、superseded、deprecated）。<u>改了决定却不改状态，ADR 就从决策依据退化成历史谣言</u>。

*容量估算*（capacity estimation）是从业务量推出峰值、并发、副本数与存储增长的过程。*冗余系数*（redundancy factor）是为故障切换和峰值波动预留的倍数；*单位成本*（unit cost）是“一次请求”或“1 GB 一个月”的价格；*总拥有成本*（TCO）还要加上人力、迁移与退出成本。

*利特尔法则*（Little's law）给出并发、到达率与停留时间的关系：并发 = 到达率 × 停留时间。它是把 QPS 换算成“需要几台”的桥。

| 要表达的内容 | 该写在哪 | 不该只写在哪 |
| --- | --- | --- |
| 一个跨系统、代价高、以后可能要改的选择 | ADR | 会议纪要 |
| 组件、接口、数据流的当前结构 | 架构图与设计文档 | ADR（ADR 不画图） |
| 尚未发生、还没有决定的风险 | 风险登记表 | ADR 的“决定”一节 |
| 排期、人员、预算分配 | 项目计划 | ADR |

| 冲突对 | 最危险的错误假设 | 晴空商城的表现 |
| --- | --- | --- |
| 成本 ↔ 可用性 | “多副本一定更稳” | 副本翻倍挡不住主库这个单点 |
| 一致性 ↔ 延迟 | “只读库的复制延迟可以忽略” | 客服刚受理完就看到旧状态 |
| 交付速度 ↔ 可运维性 | “先上线，监控以后再补” | 事件堆积没人看，没人敢切换流量 |

## 工作原理

### 从诉求走到一条 ADR

1. 把诉求转成质量属性：谁、在什么条件下、达到什么数值，并写清测量点是在网关还是在服务端。
2. 找出冲突对。成本与可用性、一致性与延迟、交付速度与可运维性；找不到冲突的就不是权衡，直接做。
3. 列候选，且必须包含“什么都不做”。少了这个基线，选项集就是不完整的。
4. 用同一组指标算每个候选：峰值并发 → 副本数 → 资源量 → 月成本。指标不一致的方案不能并排比较。
5. 加权评分。**权重必须由各约束方确认并当场记录**，架构师提供数据与后果，不替业务方定权重。
6. 决定并写 ADR：状态、决策者、背景、选项、决定、后果、复核条件。
7. 用运行数据复核。触发条件出现时新写一条 ADR，并把旧条目标成 `superseded by ADR-0xx`。

### 从业务量走到账单

1. 取业务峰值：日退款查询量除以峰值分钟占比，得到峰值 QPS，而不是拿日均值直接乘。
2. 算并发：40 × 0.12 = 4.8，这是同一时刻在服务端处理中的请求数，不是 QPS。
3. 算需求副本：并发 × 冗余系数 ÷ 单副本安全并发，向上取整；再被高可用下限（跨可用区至少 2 个）抬高。
4. 算存储：日增 × 保留天数 × 副本因子 × 膨胀系数。
5. 算月成本：资源量 × 单价 + 固定项（备份、日志、流量、许可）。
6. 用第二套权重重算评分，看结论是否翻转。<u>一换权重就翻盘的决策，说明权重才是真正的决策点</u>。

## 架构与选型

| 候选 | 适合 | 不适合 | 主要代价 |
| --- | --- | --- | --- |
| A 直连主库 + 本地缓存 | 读量小、要最快上线 | 读流量与写流量争抢同一份资源 | 主库是单点，扩容上限低 |
| B 独立只读库 + 缓存 | 读多写少、需要隔离读流量 | 强一致读、复制延迟不可接受 | 多一套库、一条同步链路与一份运维 |
| C 事件流 + 物化视图 | 需要重放、下游多、审计驱动 | 团队小、没有事件运维经验 | 交付周期长，必须自建堆积监控 |

选型依据不是“哪个分最高”，而是三项：权重由谁确认、估算用的假设是什么、复核条件是什么。评分低的方案往往不是方案差，而是权重不合当次目标。

| 判据 | 值得写 ADR | 留在设计文档即可 |
| --- | --- | --- |
| 影响面 | 跨两个以上系统或团队 | 单个模块内部 |
| 可逆性 | 改回去要迁移数据或改对外契约 | 改回去只是改配置 |
| 代价 | 涉及采购、许可与长期人力 | 一次性人力投入 |
| 争议 | 评审中存在明确反对意见 | 团队一致同意 |

## 最小示例

问题：把这次权衡变成可复算的数字，同时得到容量、成本与两套权重下的评分。

环境：Python 3.8 以上，只用标准库；不需要网络、账号或云资源。输入是峰值 QPS、停留时间与单价假设，输出是并发、存储以及每个候选的副本数、月成本与得分。

```python
"""容量与成本估算 + 加权评分：把一次架构权衡变成可以复算的数字。"""
import math  # 副本数必须向上取整，用 int() 截断会把余量算没了

PEAK_QPS = 40             # 退款查询峰值 QPS：来自大促压测，不是日均值
STAY_SECONDS = 0.12       # 单次查询的服务端停留时间，用来把 QPS 换成并发
REDUNDANCY = 1.5          # 冗余系数：给故障切换和峰值波动留余量
MIN_HA = 2                # 跨两个可用区，少于两个副本时单区故障即全挂

DAILY_ROWS = 12000        # 每日新增退款审计记录条数
ROW_BYTES = 2048          # 单条记录大小（已含索引估算）
RETAIN_DAYS = 7 * 365     # 财务要求留存 7 年，按成本要乘进容量
COPY_FACTOR = 3           # 主库 + 备份 + 异地，各存一份
BLOAT = 1.4               # 更新与索引膨胀系数

PRICE = {                 # 假设单价（元/月）：真实报价必须换成合同价并写进 ADR
    "replica": 900, "read_replica": 2600, "cache": 700,
    "event_stream": 1400, "storage_gb": 0.8,
}

CANDIDATES = [            # 每个选项只写“与别人不同的参数”，其余共用上面的假设
    {"name": "A 直连主库+本地缓存", "per_replica": 3, "read_replica": False,
     "cache": False, "stream": False,
     "score": {"成本": 5, "可用性": 2, "延迟": 3, "交付速度": 5, "可运维性": 4}},
    {"name": "B 只读库+缓存", "per_replica": 8, "read_replica": True,
     "cache": True, "stream": False,
     "score": {"成本": 3, "可用性": 4, "延迟": 4, "交付速度": 3, "可运维性": 3}},
    {"name": "C 事件流+物化视图", "per_replica": 8, "read_replica": True,
     "cache": True, "stream": True,
     "score": {"成本": 2, "可用性": 4, "延迟": 5, "交付速度": 1, "可运维性": 2}},
]

WEIGHTS = {               # 第一套权重：以成本为第一优先的评审会确认
    "成本": 30, "可用性": 25, "延迟": 20, "交付速度": 15, "可运维性": 10}
WEIGHTS_ALT = {           # 第二套权重：可用性负责人带入上一课的 RTO 要求后重算
    "成本": 15, "可用性": 35, "延迟": 20, "交付速度": 15, "可运维性": 15}


def concurrency() -> float:
    return PEAK_QPS * STAY_SECONDS      # 利特尔法则：并发 = 到达率 × 停留时间


def replicas(per_replica: int) -> int:
    need = concurrency() * REDUNDANCY / per_replica   # 按单副本能力折算出需求副本
    return max(MIN_HA, math.ceil(need))               # 再被高可用下限抬到至少 2


def audit_gb() -> float:
    raw = DAILY_ROWS * ROW_BYTES * RETAIN_DAYS / 1024 ** 3   # 原始量，单位 GB
    return raw * COPY_FACTOR * BLOAT                         # 副本与膨胀都要付钱


def monthly_cost(c: dict) -> int:
    total = replicas(c["per_replica"]) * PRICE["replica"]     # 应用副本是主要变动成本
    total += PRICE["read_replica"] if c["read_replica"] else 0
    total += PRICE["cache"] if c["cache"] else 0
    total += PRICE["event_stream"] if c["stream"] else 0
    total += audit_gb() * PRICE["storage_gb"]                 # 存储随保留期线性增长
    return round(total)


def weighted(c: dict, weights: dict) -> float:
    return sum(c["score"][k] * w for k, w in weights.items()) / sum(weights.values())


print(f"峰值并发 {concurrency():.1f}，审计存储 {audit_gb():.0f} GB")
for c in CANDIDATES:                                   # 逐行打印，避免中英文混排对不齐
    print(f'{c["name"]}：副本 {replicas(c["per_replica"])}，'
          f'月成本 {monthly_cost(c)} 元，'
          f'W1 {weighted(c, WEIGHTS):.2f}，W2 {weighted(c, WEIGHTS_ALT):.2f}')
best1 = max(CANDIDATES, key=lambda c: weighted(c, WEIGHTS))["name"]        # W1 下的首选
best2 = max(CANDIDATES, key=lambda c: weighted(c, WEIGHTS_ALT))["name"]    # W2 下的首选
print(f"W1 首选 {best1}；W2 首选 {best2}；结论翻转 {best1 != best2}")        # 翻转说明权重才是决策点
```

分四段读：`concurrency` 只做一次乘法，回答“同一时刻有多少请求在途”；`replicas` 把在途请求、冗余和单副本能力折成整数副本，再用高可用下限兜底；`monthly_cost` 把副本、附加组件与存储相加，存储项随保留期线性增长，这是 7 年留存最容易被忽略的部分；`weighted` 把同一批评分套到两套权重上，用来发现结论对权重的敏感度。

运行 `python3 capacity.py`，实测输出：

```text
峰值并发 4.8，审计存储 246 GB
A 直连主库+本地缓存：副本 3，月成本 2896 元，W1 3.75，W2 3.40
B 只读库+缓存：副本 2，月成本 5296 元，W1 3.45，W2 3.55
C 事件流+物化视图：副本 2，月成本 6696 元，W1 2.95，W2 3.15
W1 首选 A 直连主库+本地缓存；W2 首选 B 只读库+缓存；结论翻转 True
```

输出里能读到三条：三个候选都低于 8000 元预算，所以“预算”不构成区分项，真正的差别在可用性与交付速度；B、C 的副本数都是 2 而不是 1，因为高可用下限先于成本生效；<u>W1 选 A、W2 选 B，同一批数据得出相反结论——所以 ADR 里必须写明用的是哪套权重、由谁确认</u>。

决定落成一条记录，仍然用纯文本，方便进 Git 一起评审：

```text
ADR-014 退款查询采用独立只读库
状态：accepted（2026-10-19），取代 ADR-009“退款查询直连主库”
决策者：架构师（主责）、DBA、财务负责人、客服负责人

背景：峰值 40 QPS、读写比 12:1；上一课已定 RTO 30 分钟、同城双可用区；
客服要求 P95 < 800ms；月度预算上限 8000 元。

选项：A 直连主库 + 本地缓存，月成本 2896 元，评分 3.40–3.75；
B 独立只读库 + 缓存，月成本 5296 元，评分 3.45–3.55；
C 事件流 + 物化视图，月成本 6696 元，评分 2.95–3.15。

决定：选择 B。权重采用可用性优先的一套（成本 15、可用性 35），由客服与 DBA 共同确认。

后果：新增一套只读库及其同步链路，客服查询可能读到最多 2 秒前的状态；
需要在页面上标注状态更新时间；只读库故障时回退主库，需限流保护。

复核条件：只读延迟持续超过 200ms、月成本超过 8000 元、或退款查询峰值翻倍时重开评审。
```

## 动手实验

前置条件：已装 `python3`；`/tmp/qk-adr` 可写；不需要网络、账号或云资源。

1. 建实验目录：
   ```bash
   mkdir -p /tmp/qk-adr && cd /tmp/qk-adr
   ```
2. 把最小示例的脚本存为 `capacity.py`，跑出基线：
   ```bash
   python3 capacity.py
   ```
3. 复制一份做压力变体，把峰值改成 80、冗余系数改成 2.0，再运行：
   ```bash
   sed 's/^PEAK_QPS = 40/PEAK_QPS = 80/; s/^REDUNDANCY = 1.5/REDUNDANCY = 2.0/' \
     capacity.py > capacity_stress.py && python3 capacity_stress.py
   ```
4. 把上面那条 ADR 存为 `ADR-014.md`，再把检查器存为 `adr_check.py`：
   ```python
   """ADR 完整性检查：缺字段就报错，避免“写过记录”被当成“记录可用”。"""
   import pathlib  # 用路径对象而不是字符串，便于批量检查
   import sys      # 用退出码表达结果，可以直接挂进 CI

   MARKERS = [     # 七项都是复核所必需的信息，顺序与上面的 ADR 一致
       "状态：", "决策者：", "背景：", "选项：", "决定：", "后果：", "复核条件：",
   ]

   path = pathlib.Path(sys.argv[1] if len(sys.argv) > 1 else "ADR-014.md")
   text = path.read_text(encoding="utf-8") if path.exists() else ""
   missing = [m for m in MARKERS if m not in text]   # 逐项比对，缺哪项报哪项
   if missing:
       print(f"{path.name} 缺少：{'、'.join(missing)}")
       sys.exit(1)
   print(f"{path.name} 字段齐全，可以提交评审")
   ```
5. 运行检查器，再删掉 `复核条件：` 那一行重跑，观察退出码变化：
   ```bash
   python3 adr_check.py ADR-014.md; echo "exit=$?"
   grep -v '^复核条件：' ADR-014.md > ADR-bad.md; python3 adr_check.py ADR-bad.md; echo "exit=$?"
   ```

预期结果：步骤 2 输出 `峰值并发 4.8，审计存储 246 GB`，A 为 `副本 3，月成本 2896 元`。步骤 3 输出 `峰值并发 9.6`，A 变成 `副本 7，月成本 6496 元`，B 变成 `副本 3，月成本 6196 元`——峰值翻倍后成本排名反转，A 从最便宜变成比 B 贵。步骤 5 第一条输出 `字段齐全，可以提交评审`、`exit=0`，第二条报缺少 `复核条件：`、`exit=1`。

验证方法：步骤 3 的最优项在两套权重下不变，但成本最优项换了，说明“便宜”是相对峰值说的；步骤 5 的 `exit=1` 说明缺字段能被自动拦住，可以把这个检查挂进提交前钩子。

清理方法：`rm -rf /tmp/qk-adr`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 评审开三次仍无结论 | 待决问题没有写成可测量的质量属性 | 看会议纪要里有没有“数值 + 测量点” | 会前把每条诉求改写成质量属性并指定确认人 |
| 评分表算出来但没人服 | 权重由架构师单方设定 | 追问每项权重是谁确认的 | 权重由约束方确认并写进 ADR，架构师只给数据 |
| 容量估算上线即打满 | 用日均 QPS 而不是峰值，或漏算重试放大 | 对比压测峰值与估算输入 | 用峰值 × 冗余系数，并把重试倍数（常见 1.2–3 倍）显式加进去 |
| 账单远超预算 | 只算计算资源，漏了存储保留期、流量与备份 | 按资源类型列出明细，与账单逐项对 | 把存储、流量、备份列为固定项，容量估算时就计入 |
| ADR 一年后没人敢改 | 状态从不更新，被当成永久结论 | 搜同一主题是否有多条互相矛盾的 ADR | 新决定新写一条，旧条目标 superseded 并注明取代者 |

## 安全与生产注意事项

**<u>ADR 里直接写真实内网地址、账号、合同折扣与客户数据样本，决策库会变成攻击情报源。</u>** 后果是任何有仓库读权限的人都能拼出内网拓扑与采购底价。缓解：只写组件角色与量级（“只读库 × 1，2 核 8 GB 规格档”），价格写区间或引用内部报价单编号，敏感数据用脱敏样例替代。

**<u>容量估算漏掉重试与重放流量，大促时下游会按设计容量的数倍被打穿。</u>** 客户端超时重试、消息重投与补偿任务都会放大真实 QPS，而冗余系数只覆盖故障切换，不覆盖重试放大。缓解：把重试倍数写成显式参数，压测时用真实重试策略打，并对下游设独立限流与熔断。

**<u>为了压成本删掉备份、缩短审计留存，等于把可恢复性和合规性换成账单数字。</u>** 后果是一次误删就从“可恢复”变成“不可恢复”，且财务审计无法通过。缓解：成本优化只在副本规格、存储分层、非生产环境上做；留存期变更必须由财务与合规书面确认，并作为 ADR 记录。

另外两条日常约束：估算用的单价与规格必须标注复核日期，云商调价后旧结论失效；<u>ADR 里的“决策者”要写角色加具体人，只写“架构组”会让复核时找不到负责人</u>。

## 本课总结

- 权衡的前提是把模糊诉求转成带数值与测量点的质量属性，没有可比较的指标就没有权衡。
- ADR 只讲一个决策，必须带状态、决策者、选项、后果与复核条件；决定变了就新写一条并标注取代。
- 并发 = 到达率 × 停留时间；副本数 = 并发 × 冗余系数 ÷ 单副本能力，再被高可用下限兜底。
- 存储成本随保留期与副本因子线性增长，7 年留存往往比计算资源更早撞上预算。
- 权重由约束方确认并写进记录；一换权重就翻转的结论，说明权重本身就是决策点。

## 思考题

晴空商城准备把退款链路的审计记录从 7 年缩短到 3 年，理由是“云上存储太贵，能省一半”。请写出你的处理过程：需要哪些数据、要谁确认、估算怎么改、ADR 里怎么写后果与复核条件，以及你会怎样证明这个决定不是单纯的成本转移。

参考思路：先算清实际节省额（存储只占月成本的一小部分，缩短保留期省下的远不到“一半”）；再让合规与法务确认强制留存期限，这属于业务风险授权范围，架构师不能单方决定；然后列出替代方案（冷归档、压缩、只保留关键字段），用同一组指标比较；ADR 里写清各方案的成本、可恢复性变化与复核条件，并把“监管要求恢复 7 年时如何在 30 天内补齐”写进后果。

## 小测

1. 下列哪一项最不适合写进 ADR？  
   A. 被否决的选项与否决理由　B. 决策者与状态　C. 详细的接口字段定义　D. 触发重开评审的条件
2. 峰值 60 QPS、平均停留 200 毫秒时，同一时刻在途请求约为多少？
3. 冗余系数可以替代重试放大系数。对还是错？
4. ADR 的“后果”一节应该写什么？至少说出两类内容。
5. 场景题：评审会上，财务要求成本最低，客服要求可用性最高，两条要求互相冲突。架构师应该怎样推进，才能让最终决定既被接受又可复核？

## 答案与解析

1. **C。**接口字段属于设计文档，写进 ADR 会让一条记录变成会持续变形的规格书。A、B、D 都是“为什么这样决定、以后什么时候重新决定”所必需的信息，正是 ADR 的存在理由。
2. 约 12。按利特尔法则 60 × 0.2 = 12；<u>把 60 直接当并发去选副本，会严重高估或低估资源</u>，两者的区别在于停留时间。
3. **错。**冗余系数覆盖的是故障切换与峰值波动；重试、消息重投与补偿任务会额外放大真实请求量，必须作为独立参数显式加进估算，否则下游会按设计容量的数倍被打穿。
4. 两类即可：一是团队要承担的新工作与新组件（多一套只读库、同步链路、监控）；二是决策带来的新限制（客服可能读到 2 秒前的状态、只读库故障要回退并限流）。写清后果，复核时才能判断成本是否已超出当初设想。
5. 参考：先把两条要求都转成数值与测量点，把“成本最低”变成月度上限、把“可用性最高”变成 P95 与 RTO；再用两套权重重算同一批评分，把结论翻转的事实摆上桌面；权重由财务与客服共同确认并记录；最后写复核条件。**不要替业务方选权重**，也不要因为争不出结果就选规格最高的方案——那是把决策成本转成长期账单。

### 动手实验参考

步骤 2 的基线说明：三个候选都低于 8000 元预算，预算不构成区分项，区分项是可用性与交付速度。步骤 3 说明容量假设一改，成本排名就可能反转，所以“哪个最便宜”必须连着峰值与冗余系数一起说。步骤 5 的 `exit=1` 证明缺字段能被自动拦住。
