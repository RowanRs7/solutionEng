# NoSQL、Redis 与缓存失效

## 为什么需要学习

晴空商城在大促开场十分钟内，商品详情页 QPS 从 200 涨到 12000，数据库 CPU 打满，连同订单和退款接口一起变慢。团队临时加了一层 Redis，页面立刻恢复，但新的投诉出现了：客服看到“已退款”，财务系统里仍是“退款中”，两笔退款被重复打款。

缓存修好了吞吐，却把问题从“慢”换成了“什么时候的数据才是对的”。只会写 `SET` 和 `GET` 的团队，会在这两者之间反复救火。

> **核心结论：** 缓存不是“加一层 Redis”，而是用可控的短暂不一致换取吞吐，并在失效、穿透和故障时守住数据库。

## 学习目标

完成本课后，你能够：

- 区分 *Cache-Aside*、*Read-Through*、*Write-Through* 和 *Write-Behind* 的读写责任与一致性代价。
- 为商品、订单、退款三类数据选择 Redis 数据类型，并写出带 TTL 的存取方案。

## 业务场景

晴空商城的读流量集中在三个侧面，它们对“能不能旧”的容忍度完全不同：

- **商品详情页**：SKU 标题、图片、描述读多写少，允许几十秒陈旧；但价格和可售库存一旦过期，会引发下单失败和客诉。
- **订单与退款进度**：客服每次刷新工单都查一次，读多写少，涉及金额。缓存陈旧会让客服重复操作或漏跟进。
- **大促库存计数**：请求量最高、写也最密，需要原子扣减，但最终数量必须以数据库为准。

约束是：只有一套主库；财务对账只认数据库；退款状态不允许“缓存已退款、库里未退款”；Redis 是共享集群，不能被单一场景打满。

## 核心概念

*缓存*是把昂贵查询的结果放到更快存储、后续请求直接读取的机制。*命中率*等于命中次数除以总请求数，是最基础的健康指标。

*NoSQL* 指不以关系表和 JOIN 为中心的存储家族，包括键值、文档、宽列与图数据库，用部分查询与事务能力换取扩展性。Redis 是最常见的*键值型内存存储*。

*TTL* 是键的存活时间，到期后由 Redis 自动删除，它是缓存与数据库之间最终一致的兜底手段。*Cache-Aside* 指应用自己读写缓存、缓存本身不感知数据库的模式。

| 模式 | 读责任 | 写责任 | 一致性 | 主要风险 |
| --- | --- | --- | --- | --- |
| Cache-Aside | 应用先查缓存，未命中回源并回填 | 应用写库后删除缓存 | 秒级最终一致 | 删除失败会残留旧值 |
| Read-Through | 缓存组件负责回源与回填 | 由缓存组件代理写 | 秒级最终一致 | 组件行为不透明，排障困难 |
| Write-Through | 同上 | 同步写缓存与后端 | 较强 | 写延迟高，写入放大 |
| Write-Behind | 同上 | 先写缓存，异步刷库 | 弱，可能丢写 | 缓存宕机丢数据 |

三个失效问题有各自的触发条件：

- *穿透*：查询的数据本来不存在，缓存永远不会命中，请求全部落到数据库；随机 ID 扫描和错误参数会放大它。
- *击穿*：某个热点键恰好过期，瞬间大量并发同时回源，把连接池打满。
- *雪崩*：大批键在同一时刻过期，或 Redis 整体不可用，流量一次性压到数据库。

*最终一致性*指允许短时间不一致，但在没有新写入后各副本会收敛到同一值。*热键*是单位时间内访问量远超其它键的键，它决定了缓存集群的流量倾斜。

| Redis 类型 | 适用访问模式 | 晴空商城用法 | 边界 |
| --- | --- | --- | --- |
| String | 整体读写、计数 | 商品详情 JSON、库存计数 | 大对象反复序列化，成本高 |
| Hash | 按字段读写 | 订单摘要、退款状态字段 | 字段过多时不便整体过期 |
| List | 有序队列、时间线 | 待处理退款任务队列 | 随机索引访问慢 |
| Set | 去重与集合运算 | 已参与过活动的用户 | 无顺序、无分数 |
| Sorted Set | 按分数排序 | 热销榜、延迟重试队列 | score 语义要自己定义清楚 |

## 工作原理

以商品详情页的 Cache-Aside 读路径为例，请求按下面的顺序流动：

1. 应用拼接 key，例如 `sku:10086:detail:v3`；版本号写进 key，结构变更时整体切换命名空间。
2. 执行 `GET`，命中则反序列化直接返回，并累加命中计数。
3. 未命中时先尝试 `SET lock:sku:10086:v3 <token> NX EX 3`，只有拿到锁的请求才允许回源。
4. 拿到锁的请求查库：查到就写正缓存并设 TTL；查不到就写*负缓存*，用短 TTL 占位值表示“不存在”。
5. 没拿到锁的请求短暂等待后重读缓存，而不是继续查库，这是击穿防护的关键一步。
6. 回源完成后释放锁；释放失败也无妨，锁自身的 TTL 会兜底。

写路径的顺序比读路径更容易出错：

1. 先在数据库完成写入并提交事务。
2. 再删除缓存中的对应键，而不是更新缓存。
3. 删除失败或需要更强保证时，投递一次延迟删除（延迟双删），或由数据库变更日志驱动的补偿任务重删。
4. TTL 始终存在，作为所有补偿都失效时的最后兜底。

**删除缓存优于更新缓存**：两个并发写者如果各自更新缓存，旧值的写入可能后到达并长期驻留；删除是幂等操作，最多造成一次多余回源。<u>先删缓存再写库的顺序更糟</u>：读请求会在“已删缓存、未提交写库”的窗口里回源，把旧值重新回填，且这次回填会一直存活到 TTL 到期。

## 架构与选型

| 用途 | 适用 | 不适用 | 权衡与依据 |
| --- | --- | --- | --- |
| 商品详情 | 读多写少、可容忍几十秒陈旧 | 价格与库存等强时效字段不能整体套用 | 用同一份 JSON 降低回源成本，价格单独短 TTL |
| 会话与令牌 | 短生命周期、需集中失效 | 需要跨机房强一致的授权判断 | 集中失效的便利性优先于极致延迟 |
| 秒杀库存计数 | 高频原子扣减 | 作为最终账目或对账依据 | 用 `DECR` 挡住大部分流量，落库仍以数据库为准 |
| 订单与退款状态 | 只做展示加速 | 作为金额判断或审批依据 | 允许秒级陈旧，写操作一律回源 |

选型前先回答四个问题：这份数据能否从权威源重建？允许的最大陈旧时间是多少？写频率是否接近读频率？不一致会不会影响金额、权限或对外承诺？<u>写多读少的数据通常不值得缓存</u>。

## 最小示例

问题：验证负缓存能否挡住“查询不存在的订单”造成的穿透。环境是 Python 3.11 标准库，不需要安装 Redis；`FakeRedis` 只实现 `GET`、`SET` 与 `EX` 语义，用来复现真实行为。

```python
import time  # 用单调时钟模拟 Redis 过期时间，不受系统时间调整影响

class FakeRedis:  # 只实现 GET/SET 与 EX 语义的最小键值存储
    def __init__(self):
        self.data = {}  # key -> (value, expire_at)；expire_at 为 None 表示永不过期
        self.hits = 0  # 对应 Redis INFO 的 keyspace_hits
        self.misses = 0  # 对应 keyspace_misses，命中率 = hits / (hits + misses)
    def set(self, key, value, ex=None):  # 对应 SET key value EX seconds
        expire_at = None if ex is None else time.monotonic() + ex  # 换算成绝对过期时刻
        self.data[key] = (value, expire_at)  # 覆盖写，等同 Redis 的 SET 语义
    def get(self, key):  # 对应 GET；惰性过期，读到已过期键视为不存在
        item = self.data.get(key)  # 取出值与其过期时刻
        if item is None or (item[1] is not None and item[1] <= time.monotonic()):
            self.misses += 1  # 未命中计数，便于观察穿透
            return None
        self.hits += 1  # 命中计数
        return item[0]

DB_CALLS = 0  # 全局计数：模拟真实数据库被回源的次数

def load_from_db(order_id):  # 替代 SQL 查询，返回 None 表示订单不存在
    global DB_CALLS
    DB_CALLS += 1  # 每调用一次代表一次真实数据库访问
    return None  # 用一个不存在的订单号复现“穿透”场景

def get_order(cache, order_id, negative_cache):  # Cache-Aside 读路径
    key = f"order:{order_id}:v1"  # key 带版本号，结构变更时整体切换命名空间
    value = cache.get(key)  # 先查缓存
    if value is not None:
        return value  # 命中即返回，不接触数据库
    value = load_from_db(order_id)  # 回源
    if value is None and negative_cache:
        cache.set(key, "NULL", ex=60)  # 负缓存：把“不存在”也缓存成短 TTL 的占位值
    if value is not None:
        cache.set(key, value, ex=300)  # 正缓存：TTL 是最终一致性的兜底
    return value

for negative_cache in (False, True):  # 先跑无防护版本，再跑带负缓存版本
    cache = FakeRedis()  # 每组使用独立缓存，避免相互影响
    DB_CALLS = 0  # 重置数据库计数
    for _ in range(10):  # 连续 10 次查询同一个不存在的订单
        get_order(cache, 404, negative_cache)
    print(f"负缓存={negative_cache}: 命中 {cache.hits} 次, 数据库查询 {DB_CALLS} 次")
```

运行 `python3 cache_lab.py`，预期输出：

```text
负缓存=False: 命中 0 次, 数据库查询 10 次
负缓存=True: 命中 9 次, 数据库查询 1 次
```

整体流程是：读路径先查缓存，未命中才回源；回源结果为空时写一个短 TTL 的占位值；第二次以后的相同请求直接命中占位值。关键设计选择有三点：负缓存 TTL 明显短于正缓存，避免新数据被“不存在”挡住；key 带版本号，便于整体失效；命中与未命中分开计数，否则无法判断防护是否生效。

对应的真实 Redis 命令与预期输出：

```bash
redis-cli SET sku:10086:detail:v3 '{"price":1999}' EX 60  # 写正缓存并设置 60 秒 TTL
redis-cli TTL sku:10086:detail:v3                          # 预期输出：60
```

### 任务：给商品详情页加一层可验证的缓存

前置条件：Python 3.11 及以上；可选 Docker（用于对照真实 Redis）；不需要任何付费服务或密钥。

1. 新建 `cache_lab.py`，复制上面的代码，在 `load_from_db` 开头加 `time.sleep(0.05)` 模拟 50ms 的库查询延迟，返回值仍为 `None`，以保留穿透场景。
2. 把循环改成 `range(20)`，先跑 `negative_cache=False`，记录总耗时和数据库调用次数（约 20 次调用、1 秒以上）。
3. 打开负缓存重跑同样 20 次请求，对比两组数字（约 1 次调用、50ms 左右）。
4. 把负缓存的 TTL 从 60 改成 1，在循环里插入 `time.sleep(1.1)`，观察命中率如何随过期周期性塌陷，这就是击穿窗口。
5. 可选：用 `docker run -d --name qingkong-redis -p 6379:6379 redis:7` 启动真实 Redis，用同样的 key 命名执行上面的 `SET` 与 `TTL`。

预期结果：数据库调用次数从 20 降到 1，总耗时从 1 秒以上降到 50ms 左右；负缓存 TTL 改成 1 秒后会出现规律性的未命中尖刺；key 名称可读、可批量巡检。

验证方法：打印 `hits`/`misses` 与 `DB_CALLS`；用 `redis-cli --scan --pattern 'order:*'` 确认键数量；用 `TTL` 抽查，返回 `-1` 说明漏设过期时间。

清理方法：删除本地 `cache_lab.py`；执行 `docker rm -f qingkong-redis`；若使用了共享集群，用 `redis-cli DEL` 精确删除实验键，不要执行 `FLUSHDB`。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 整体命中率很高，数据库 QPS 仍翻倍 | 少数热键未命中，或请求根本没走缓存 | 按 key 前缀分桶统计命中率，抓慢查询看回源来源 | 拆分热键、启动预热、加本地多级缓存 |
| 客服看到的状态与财务不一致 | 删除缓存失败，或用了“先删后写库”的顺序 | 抽样比对库值与缓存值，查删除日志 | 改为写库后删缓存，加延迟双删或变更日志补偿 |
| Redis 内存持续上涨，出现大面积淘汰 | 写缓存时漏设 TTL，或 key 无界累积 | `INFO memory`、抽样 `TTL`、`--bigkeys` | 统一封装强制 TTL，设置 `maxmemory-policy` |
| 每到整点出现短促的数据库尖刺 | 大批键 TTL 相同，同时过期造成雪崩 | 对比过期时间分布与回源 QPS 曲线 | TTL 加随机抖动、分批预热、下游限流降级 |
| 新创建的订单短时间查不到 | 负缓存 TTL 过长，挡住了刚写入的数据 | 检查负缓存键的值与剩余 TTL | 负缓存单独设置 30–60 秒 TTL，写入后主动删除 |

## 安全与生产注意事项

**<u>不要把身份证号、完整手机号、收货地址或支付令牌以明文长期存放在共享 Redis 中。</u>** 共享实例通常同网段可访问，缺少 ACL 或密码时任何服务都能读取全量数据，泄露后难以追溯。缓解方式是只缓存脱敏字段、按业务划分实例并配置 ACL 与传输加密，同时给敏感键设置较短 TTL。

**<u>退款、支付等金额相关状态不能只以缓存为准。</u>** 缓存被淘汰或残留旧值时，客服会重复退款或漏退款，损失不可逆。缓解方式是缓存只承担展示加速，所有写操作与最终判断都回源数据库，必要时用版本号或状态机二次校验。

另外两项生产约定：提前决定 `maxmemory-policy`（`noeviction` 会让写入直接报错，`allkeys-lru` 可能淘汰不该丢的键）；Redis 故障时必须有降级方案，否则缓存失效会直接变成数据库故障。

## 本课总结

- 缓存用可控的短暂不一致换取吞吐；没有 TTL 和回源保护的缓存只是把故障转移给了数据库。
- Cache-Aside 的写路径应“先写库提交、再删缓存”，TTL 是所有补偿失效后的兜底。
- 穿透用参数校验与负缓存，击穿用互斥回源或逻辑过期，雪崩用 TTL 抖动、多级缓存与降级。
- Redis 数据类型要匹配访问模式，Hash 省内存但字段规模要有上限，Sorted Set 适合排序类场景。
- 金额、权限与审批以数据库为权威源，缓存只负责让读取更快。

## 思考题

晴空商城大促期间商品详情页缓存命中率 96%，但数据库 QPS 仍是平时的三倍，同时退款状态偶发不一致。请写出你的排查顺序，说明先改哪一层、为什么，以及用什么证据验证改动有效。

参考思路：先分层定位而不是直接调大缓存。对那 4% 未命中的请求按 key 前缀分桶，判断是热键、穿透还是缓存被绕过，并确认 TTL 分布是否集中。退款不一致先与业务确认权威源和可接受的陈旧时间，再比较删除缓存、延迟双删与变更日志补偿。验证方式是前后对比回源 QPS、命中率、缓存与库值差异采样，以及主动重启 Redis 观察降级。

## 小测

1. 在 Cache-Aside 中，下列哪种写入顺序更能减少长期残留旧值？
   A. 先删缓存再写库　B. 先写库提交再删缓存　C. 只更新缓存不写库　D. 先写库再更新缓存
2. 缓存穿透和缓存击穿的核心区别是什么？
3. 商品热销排行榜最适合用哪种 Redis 类型，为什么？
4. 一个键只执行 `SET` 而不设置 TTL，会带来什么生产风险？
5. 场景题：客服要求退款列表“实时一致”，你会直接给这个列表加 5 分钟 TTL 吗？请说明理由。

## 答案与解析

1. **B。** 先提交数据库再删缓存，最坏结果只是一次多余回源。A 会在“已删缓存、未提交”的窗口里被读请求回填旧值，并存活到 TTL 到期；C 会丢数据；D 在并发写入下可能让旧值后到并覆盖新值，而且每次写都要重算缓存。
2. 穿透是“数据本来不存在”，缓存永远无法命中，常见于随机 ID 扫描；击穿是“数据存在，但热点键过期瞬间被并发回源”。前者靠参数校验加负缓存，后者靠互斥回源或逻辑过期。
3. Sorted Set。成员唯一且按 score 排序，`ZINCRBY` 累加销量、`ZREVRANGE` 直接取榜单；List 只有插入顺序没有分数，Set 无序。
4. 键永不释放，内存持续上涨并触发淘汰，可能挤掉其他业务数据，最终出现 OOM 或大面积未命中。所有写缓存的路径都应强制 TTL，并定期巡检 `TTL` 返回 `-1` 的键。
5. 不应该。先问“实时”的业务代价与权威源：退款涉及金额，判断必须以数据库为准。可以缓存列表但 TTL 压到秒级、写后主动删除，单笔状态回源；若要求强一致，应优化库查询，而不是用缓存假装实时。

### 动手实验参考

参考方向：数据库调用次数应从 20 降到 1，说明负缓存生效；把负缓存 TTL 改成 1 秒后会出现规律性尖刺，这是击穿窗口的可观察证据；删掉负缓存分支则退化回第一组数字。清理后确认没有遗留无 TTL 的实验键。
