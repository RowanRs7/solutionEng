# 数据与架构阶段综合测评

## 学习目标

本测评检验你能否把十课合成一份可评审的设计。建议闭卷完成概念题与场景题，再对照评分表自评，最后按失分题号回看课程。

## 知识检查清单

- [ ] 能按关系选表结构，并说明主键与自然键的取舍。
- [ ] 能指出哪些规则必须落到库级约束，而不只写在 ORM 里。
- [ ] 能为查询设计复合索引，判断是否回表、是否用上最左前缀。
- [ ] 能用 expand-contract 描述一次不停机迁移与回滚。
- [ ] 能说清 Cache-Aside 写路径，以及穿透、击穿、雪崩的区别。
- [ ] 能区分公有 URL、预签名 URL 与 CDN 鉴权的暴露面。
- [ ] 能说明时刻、日期、金额、标识的表示与舍入规则。
- [ ] 能按五个维度写数据质量规则，并区分校验与约束。
- [ ] 能用变更耦合、数据所有权与扩容曲线判断架构形态。
- [ ] 能解释网关“鉴权、限流、路由”的顺序与租约窗口。
- [ ] 能判断副本是否跨故障域，并给出 RTO、RPO 与验证方式。
- [ ] 能把模糊诉求写成带阈值的质量属性，并写出 ADR。

## 概念题

共 15 题，40 分：第 1–10 题四选一，每题 2 分；第 11–15 题简答，每题 4 分。

1. 【知识点：表设计与参照完整性】关于外键与约束，哪项正确？
   A. ORM 声明了外键就不必建库约束
   B. 外键对所有写入通道生效，能拦住孤儿行
   C. `CHECK` 能写子查询做跨表校验
   D. 多对多可用逗号拼接一列替代连接表

2. 【知识点：索引与最左前缀】复合索引建在 `(status, created_at)`，查询条件是 `WHERE created_at > '2026-10-01'`，通常如何？
   A. 走覆盖索引并免回表
   B. 仍走索引，只是排序变慢
   C. 跳过最左列，索引基本失效
   D. 数据库会自动重排索引列

3. 【知识点：隔离级别】“读已提交”能防住哪类异常？
   A. 只防脏读
   B. 防脏读与不可重复读
   C. 四类全部防住
   D. 一类不防，只把锁换成快照

4. 【知识点：缓存失效】促销开场大批键在同一秒过期，请求全部回源打满连接池，属于？
   A. 穿透
   B. 击穿
   C. 雪崩
   D. 热键

5. 【知识点：缓存写路径】Cache-Aside 为何“先写库提交、再删缓存”？
   A. 反过来读请求会把旧值回填
   B. 先写库即强一致
   C. 删除失败时 TTL 会失效
   D. 应更新而非删除缓存

6. 【知识点：对象存储】关于对象存储，哪项正确？
   A. 有目录，可原子重命名文件夹
   B. `ETag` 可作业务幂等键
   C. 签名 URL 过期前等同通行证，签发须锁对象与动作
   D. 公有 URL 可按用户撤销

7. 【知识点：时间与金额】哪种表示最可靠？
   A. 金额用定点或整数分，舍入规则显式写出
   B. 时刻存本地时间字符串，便于展示
   C. 缺失值用空串，比 `NULL` 省事
   D. 对外单号用自增主键，天然不可枚举

8. 【知识点：去重】去重结果可靠的关键是什么？
   A. 插入前先查询，查到就跳过
   B. 应用层校验足够严
   C. 唯一索引关掉并发窗口
   D. 日终对账能阻止重复扣款

9. 【知识点：架构形态】关于单体与微服务，哪项正确？
   A. 目录改名成 `services/` 即得到服务
   B. 可共享表，跨库 JOIN 不影响独立性
   C. 先还清共享表与循环依赖，否则得到分布式单体
   D. 冷启动只影响平均延迟

10. 【知识点：网关与发现】关于统一入口与实例列表，哪项正确？
    A. 限流应先于鉴权
    B. 租约过期即下线，强杀后条目多活一个周期
    C. 就绪检查只探端口即可
    D. 业务编排与长事务适合放进网关

11. 【知识点：高可用与灾备】两个副本在同一可用区，可用性会提升吗？RPO 与 RTO 各由什么决定？

12. 【知识点：ADR】一条可评审的 ADR 至少含什么？决定改变后怎么处理？为什么“性能要好”不能作为权衡输入？

13. 【知识点：校验与约束】应用层校验与库级约束各拦什么、拦不住什么？跨行规则为何不能靠 `CHECK`，应靠什么？

14. 【知识点：一致性边界】一致性边界怎么划？为何不可逆副作用必须同事务，跨系统只能最终一致加对账？

15. 【知识点：权威源】缓存、对象存储、备份的权威源与失效或恢复责任有何不同？各举一个判断错误的后果。

## 常见错答分析

| 误解 | 为什么错 | 正确理解 |
| --- | --- | --- |
| 多副本即高可用；库存先扣 Redis 更快 | 同域副本只是同一风险的重复；缓存宕机或误删会抹掉已确认的承诺 | 冗余要跨故障域；库存、金额、权限以库为权威源 |
| 约束写在模型里就够，校验全了不必加唯一索引 | ORM 只管应用路径，批处理与运维 SQL 能绕过；“先查再插”在并发下有窗口 | 校验给可读理由，约束对所有写入通道生效；去重靠唯一索引 |
| 先拆服务，共享表以后再说；ADR 事后补 | 带着共享表与循环依赖拆，只会得到分布式单体；事后补只剩结论，没有选项与代价 | 先加固、模块化、抽异步任务再拆写路径；ADR 当场写，改决定要新写一条并标注取代 |

## 场景分析

「山岚民宿」直连房东，三处院子共 46 间房，要上线房东自助上架改价、提前预订折扣和春节线上下单。约束：旺季瞬时每分钟 900 次下单，全压在同一个房源日历上，平时不足 20 次；照片单张 8MB、每房源最多 40 张，其中含门锁密码照片；清洁费按晚计，押金退房后原路退回，佣金按月与房东结算；取消政策写“入住前 72 小时免费取消”；预算只够一个主库加两个应用实例，没有专职 DBA。

1. 给出防超卖的核心表与至少三处约束，说明“先查再写”为何失效，并给出两种可落库的拦截方式及各自代价。
2. 可售日历要不要缓存？给键设计、失效顺序，以及穿透、击穿、雪崩各一条措施，并指出权威源。
3. 该不该拆微服务？给三条依据；用利特尔法则估算并发与实例数（假设自写）；说明网关与服务发现的职责。
4. 给结算链路的 RTO、RPO 与验证方式（含一个演练动作），并挑一项必须写 ADR 的决策，说明复核条件。

## 架构师交付物练习

输出《预订与房态设计决策包》，用表格承载，至少包含：

1. 数据契约表：表名、主键、一到三处库约束，以及“这条约束拦住了哪次具体错误写入”。
2. 索引清单：查询、列顺序、能否覆盖、写入代价。
3. 缓存键与失效表：键模板、TTL、失效触发点、失败兜底。
4. 一致性边界表：跨哪些表或系统、强一致还是最终一致、兜底手段。
5. 选型矩阵：模块化单体与按域拆服务两种方案，行含交付速度、扩容粒度、故障域、运维成本。
6. 两份 ADR：含背景、选项、决定、后果、状态、决策者、复核条件，其中一份为“房态是否缓存”。
7. 恢复与演练卡：RTO、RPO、归档间隔、一次演练步骤与通过判据。

提示：先列“事实与约束”小节，再逐表填写；没有依据的数字标“待压测确认”，不要写成承诺。

## 参考答案与解析

### 概念题

1–10 答案：B、C、A、C、A、C、A、C、C、B。

1. B。库级执行才拦得住批处理与手工 SQL；C 的 `CHECK` 不能写子查询。
2. C。条件不用首列，后列无法单独定位；数据库不会替你重排。
3. A。不可重复读与幻读仍在；B 是可重复读，C 是串行化。
4. C。大批键同时到期即雪崩；穿透是查不存在的数据，击穿是单个热点键过期。
5. A。先删缓存会让读请求把旧值回填；TTL 正是删除失败后的兜底。
6. C。签名 URL 是限定对象与动作的票据；没有目录，`ETag` 只比对字节。
7. A。金额是整数计数；本地时间丢时区，空串破坏唯一约束，自增可枚举。
8. C。先查再插在并发下有窗口，唯一索引让第二次插入直接失败。
9. C。共享表与循环依赖让“独立部署”变成“必须一起发布”。
10. B。租约到期才摘除；鉴权应先于限流，只探端口会把依赖耗尽当成健康。

11. 不会。同域副本只是同一风险的重复；RPO 由复制方式与归档间隔决定，RTO 是恢复链各步骤之和；只有演练测出的数字才算证据。
12. 含背景、选项与代价、决定、后果、状态、决策者、复核条件；改决定应新写一条并标注取代。“性能要好”没有条件与阈值，无法比较。
13. 校验给可读理由，但拦不住绕过接口的写库与并发重复；约束对所有写入通道生效，却表达不了跨行规则。`CHECK` 只看单行，跨行要用事务加锁、条件更新或唯一约束，并配重试与超时。
14. 边界是可被一次成败判定覆盖的最大范围：内可强一致，外只能最终一致加对账。扣款等不可逆副作用无法用重试抹平，必须同事务；跨系统只能靠幂等键与对账收敛。
15. 缓存是派生副本，库是权威源，失效靠“提交后删加 TTL”；对象存储是字节权威源，失效表现为生命周期与权限；备份是恢复用副本，靠演练验证。误判后果：缓存当库存导致超卖；签名 URL 当权限导致照片外流；副本当备份导致误删同步。

### 场景分析参考思路

1. 表：`room_types`、`calendar(room_type_id, stay_date, remaining)`、`orders`、`order_nights`。约束：`calendar` 两组列主键、`CHECK (remaining >= 0)`、`order_nights` 唯一约束表达“同一房间同一晚只被一单占用”。先查再写失效，是因为两步之间没有互斥。拦截一：条件更新 `UPDATE ... SET remaining = remaining - 1 WHERE ... AND remaining >= 1`，看影响行数，代价是热点行排队、事务必须短；拦截二：按“房间 × 夜”占位依赖唯一约束，代价是行数随夜数增长、取消要释放，夜间按半开区间展开。
2. 可缓存，但它只是近似视图，库才是权威源。键 `avail:{room_type_id}:{yyyy-mm}`，TTL 分钟级加抖动；写路径是提交后删除、TTL 兜底。穿透：日期限制在可售窗口并写短 TTL 负缓存；击穿：热点房源互斥回源；雪崩：TTL 抖动加本地缓存，超载时降级为“咨询房东”而不是返回错误的可售量。
3. 依据：订单与房态常一起改，先做模块化单体；两者共享表，硬拆会变成分布式事务；扩容只在旺季尖峰，适合限流排队加临时扩容。利特尔法则：900 次/分钟即 15 RPS，停留 300 毫秒，并发约 4.5；按单实例 8 并发、水位 70%，一台够用，预算内两台做 N+1 与发布不中断。网关管鉴权、按身份分桶限流与路由；发现管注册、续期与摘除，租约窗口内会有短暂误发。
4. 若接受“数小时中断、最多丢 5 分钟”，RPO 取归档间隔 5 分钟，RTO 取还原、回放、校验之和；演练动作是每季度从备份在隔离环境恢复并跑对账，判据是实测达标且差异可解释。须写 ADR 的如“房态扣减用库内条件更新还是 Redis 预扣”，复核条件是压测结果、超卖工单数与失效复盘。
   常见错误：不换算 QPS 直接套并发；把 Redis 扣减当成库存正确；只写“72 小时”不写按哪个时区的时刻判定。

### 交付物参考结构

| 部分 | 参考内容 |
| --- | --- |
| 数据契约 | `calendar(room_type_id, stay_date, remaining)`，两组列主键；`CHECK (remaining >= 0)` 拦住扣成负数；`order_nights` 唯一约束拦住一夜两单。 |
| 索引 | “按月查可售”用 `(room_type_id, stay_date)` 覆盖所需列；“按状态查超时未付”用 `(status, created_at)`，代价是每次改状态都要维护树。 |
| 缓存 | `avail:{room_type_id}:{yyyy-mm}`，TTL 3 分钟加抖动，提交后删除；删除失败记日志并补偿。 |
| 一致性边界 | 订单与占位同事务；佣金结算走日终对账，差异分“只有我方、只有对方、值不符”；照片元数据入库、字节入桶，清理靠生命周期。 |
| 选型矩阵 | 模块化单体在交付速度与运维成本占优；按旺季尖峰与两人团队，结论是先模块化、把异步任务抽出去。 |
| ADR | 例：房态扣减以库内条件更新为权威，Redis 仅做读缓存；状态 accepted；决策者为技术负责人与业务负责人；复核条件为旺季压测与超卖工单数。 |
| 恢复卡 | RPO 5 分钟、RTO 4 小时；每日全量加 5 分钟增量；演练为隔离环境恢复后跑对账脚本。 |
