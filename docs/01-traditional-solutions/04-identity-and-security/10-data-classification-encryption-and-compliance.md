# 数据分类、脱敏与合规基础

## 为什么需要学习

晴空商城没被入侵，却连出三起“事故”：客服把退款工单导出成 Excel 发进个人网盘；工程师把生产快照恢复进测试环境；日志平台开放检索后，搜 `138` 就翻出几万条手机号。

共同点不是“没加密”，而是没人说得清：哪些字段最要紧、谁能看原值、多久必须删。

> **核心结论：** 数据保护不是“把数据库加密”，而是先分级、按级配控制，并留下人和监管都读得懂的证据。

## 学习目标

完成本课后，你能够：

- 用泄露影响、访问范围与保留期限给字段定级，并写出该级的最小控制集。
- 说明*加密*、*脱敏*、*哈希*与*令牌化*各防住哪种泄露，失效边界在哪。
- 写出审计记录的必要与排除字段，为一次导出设计留存与追责路径。
- 判断一条要求属于平台、商家、支付商还是云厂商，并指出哪些结论不能由架构师定。

- 知道认证、授权与审计各自回答的问题；必要时回看[认证、授权与审计](01-authentication-authorization-and-audit.md)。

## 业务场景

订单数据散在订单库、支付回调、仓库面单、客服工单与录音里，另有一份供 AI 客服检索的摘要。接入三十家品牌商后，矛盾集中到四点：

- 客服要按完整手机号搜单，却只该看到后四位；页面打码救不了接口返回全量。
- 仓库打面单要完整地址与电话，但不需要退款金额。
- 支付商要求平台不留完整卡号；风控却想留全量。
- 品牌商要求“注销即删除”，而报表、备份、归档仍有副本；录音与凭证留多久，财务与法务没有结论。

架构师要交付：字段分级表、“谁看原值、谁看掩码”的矩阵、审计留痕规则、责任边界表。

## 核心概念

*数据分类分级*先问三件事：泄露后谁受影响、谁能看原值、必须保留多久。答案把数据归入有限几级，级别决定控制、审批与保留。**分级不是贴标签，而是让“该配什么控制”可被检查。**

| 级别 | 判定依据 | 晴空商城示例 | 最小控制 |
| --- | --- | --- | --- |
| 公开 | 泄露无影响 | 商品标题、门店地址 | 完整性校验 |
| 内部 | 影响运营，不涉及个人 | 库存水位、成本价 | 登录可见，按角色授权 |
| 敏感 | 可识别到个人 | 姓名、手机号、地址 | 加密、展示脱敏、访问审计 |
| 极敏感 | 直接导致盗刷或失守 | 完整卡号、身份证号、密钥 | 令牌化或字段级加密、双人审批 |

*个人信息*指与已识别或可识别的自然人有关的信息；*敏感个人信息*是其中泄露后容易危害人格尊严或财产安全的部分（《个人信息保护法》第二十八条）。法律管“是不是”，工程分级还要管“影响多大、留多久”。

*去标识化*后不借助额外信息无法识别个人，但保留映射仍可复原，仍是个人信息；*匿名化*后无法识别且不能复原，才不再算个人信息；用假名替换原始标识则叫假名化，仍可关联。**把“删掉姓名”当成“已匿名”是最常见的误读。**

| 手段 | 可逆性 | 防住什么 | 防不住什么 | 典型用法 |
| --- | --- | --- | --- | --- |
| 静态加密 | 持密钥者可逆 | 介质、备份被拷走 | 应用被入侵后解密；有查询权限的 DBA | 数据库、备份 |
| 展示脱敏 | 原值仍在 | 窥屏、截图外泄 | 接口仍返回全量 | 页面、导出预览 |
| 哈希 | 设计上不可逆 | 无需原值的比对 | 手机号等低熵值可被穷举 | 密码、去重比对 |
| 令牌化 | 凭映射表可逆 | 跨系统传递的信息拼图 | 映射表被拿走 | 支付卡 token、日志标识 |

*审计日志*记录谁在何时对哪条数据做了什么、结果如何；*留存期*既是“留多久”，也是“到期必须删”。审计数据往往比业务数据更敏感。

## 工作原理

数据从进入到删除，“哪一步配什么控制”是固定顺序：

1. **登记与定级**：字段进入数据字典时就带级别与责任人；上线后补分级等于先泄露再补作业。
2. **最小化采集**：下单不需要身份证就不采；只存末四位；卡号交给支付商令牌化。
3. **传输保护**：对外只有 TLS；服务之间的敏感字段再加密，不默认内网可信。
4. **静态加密与密钥分离**：数据用数据密钥（DEK）加密，DEK 由密钥管理服务的主密钥（KEK）包裹，两者不同库、不同权限。
5. **按角色投影**：响应前按角色裁剪：客服拿掩码，财务拿金额但拿不到卡号，仓库拿地址但拿不到金额。
6. **导出与共享**：导出单独授权，文件带水印与有效期，记录用途与接收方；跨商家只给令牌或聚合。
7. **审计与留存**：记录访问、导出、解密、删除事件；按级别设保留期，到期删除并留证据。
8. **删除与验证**：删除覆盖主库、索引、缓存、数仓与备份，并抽样验证，而不是相信工单已关闭。

第 5、8 步最常被跳过：前者解释“掩码为何不能只做在页面上”，后者解释“删除为何常常等于没删”。

## 架构与选型

| 方案 | 适用场景 | 不适用或需注意 | 主要权衡 |
| --- | --- | --- | --- |
| 云盘或数据库透明加密 | 满足“介质被拷走”这类要求 | 挡不住有查询权限的账号 | 开启即生效，对内部越权几乎无效 |
| 应用层字段级加密 | 极敏感字段单独保护 | 影响范围查询与索引，密钥管理复杂 | 收益最高，成本也最高 |
| 令牌化服务 | 卡号、证件号跨系统传递 | 多一个依赖，映射表成为高价值目标 | 把风险集中到一处 |
| 不采集、不落库 | 没有明确用途的字段 | 需要业务方接受功能损失 | 最彻底，也最需要产品决断 |

选型顺序倒过来问：**先问“能不能不存”，再问“能不能只存不可逆形式”，然后问“谁能看原值”，最后才问“用哪种加密”。** 从算法选起，通常得到昂贵但漏风的控制。

边界：加密不解决越权；脱敏不解决接口，直接调 API 就绕过页面；审计不阻止操作，只让操作可复盘。

## 最小示例

问题：实现“字段分级 + 按角色投影 + 日志假名化 + 审计哈希链”，并证明极敏感字段对任何角色都不返回原值。环境为 Python 3.9+ 标准库，不联网。

```python
import hashlib
import hmac
import json
import secrets

# 字段策略：级别 + 可看原值的角色。None 表示没有任何角色能看原值
FIELDS = {
    "order_id": ("internal", "*"),
    "amount": ("sensitive", "finance"),
    "phone": ("sensitive", "cs"),
    "card_last4": ("sensitive", "finance"),
    "id_card": ("restricted", None),
}

# 掩码规则按字段定制：客服要能核对后四位，所以只遮中间四位
MASKS = {
    "phone": lambda v: v[:3] + "****" + v[-4:],
    "card_last4": lambda v: "****",
    "id_card": lambda v: v[:4] + "**********" + v[-4:],
}


def project(order, role):
    # 默认掩码、白名单放行：新增字段忘配置时，结果是看不到而不是泄露
    out = {}
    for name, (level, owner) in FIELDS.items():
        if name not in order:
            continue
        value = order[name]
        if level == "restricted" or (owner != "*" and role != owner):
            out[name] = MASKS.get(name, lambda v: "***")(value)
        else:
            out[name] = value
    return out


AUDIT_KEY = secrets.token_bytes(32)  # 演示用；生产从密钥管理服务取，各环境独立


def pseudonym(value):
    # 用 HMAC 而不是裸 SHA-256：没有密钥就无法拿手机号字典反查
    return hmac.new(AUDIT_KEY, value.encode(), hashlib.sha256).hexdigest()[:16]


def append_audit(chain, actor, action, field, result):
    # 只记假名、字段名与结果，不记字段值：日志本身不能成为泄露源
    event = {"actor": actor, "action": action, "field": field, "result": result}
    payload = json.dumps(event, sort_keys=True, ensure_ascii=False)
    prev = chain[-1]["hash"] if chain else "GENESIS"  # 上一条的哈希构成链
    digest = hashlib.sha256((prev + payload).encode()).hexdigest()
    chain.append({**event, "prev": prev, "hash": digest})


def verify(chain):
    prev = "GENESIS"
    for index, event in enumerate(chain):
        payload = json.dumps(
            {key: event[key] for key in ("actor", "action", "field", "result")},
            sort_keys=True,
            ensure_ascii=False,
        )
        # 任一条被改动，它自己的 hash 或下一条的 prev 必然对不上
        if event["prev"] != prev or hashlib.sha256((prev + payload).encode()).hexdigest() != event["hash"]:
            return f"审计链断点: #{index}"
        prev = event["hash"]
    return "审计链完整"


ORDER = {
    "order_id": "SO-20261019-0042",
    "amount": 8800,
    "phone": "13800138000",
    "card_last4": "4242",
    "id_card": "110101199001011234",  # 教学构造的假号码，不是真实身份信息
}

for role in ("cs", "warehouse", "finance", "admin"):
    # 同一订单、不同角色，输出必须不同：这是服务端投影，不是前端隐藏
    print(role, json.dumps(project(ORDER, role), ensure_ascii=False))

chain = []
append_audit(chain, pseudonym("cs-1024"), "export", "phone", "allow")
append_audit(chain, pseudonym("cs-1024"), "export", "card_last4", "deny")
print("手机号假名可关联:", pseudonym("13800138000") == pseudonym("13800138000"))
print(verify(chain))
chain[1]["result"] = "allow"  # 模拟有人事后把“拒绝”改成“允许”
print(verify(chain))
```

运行 `python3 data_guard.py` 的预期输出：

```text
cs {"order_id": "SO-20261019-0042", "amount": "***", "phone": "13800138000", "card_last4": "****", "id_card": "1101**********1234"}
warehouse {"order_id": "SO-20261019-0042", "amount": "***", "phone": "138****8000", "card_last4": "****", "id_card": "1101**********1234"}
finance {"order_id": "SO-20261019-0042", "amount": 8800, "phone": "138****8000", "card_last4": "4242", "id_card": "1101**********1234"}
admin {"order_id": "SO-20261019-0042", "amount": "***", "phone": "138****8000", "card_last4": "****", "id_card": "1101**********1234"}
手机号假名可关联: True
审计链完整
审计链断点: #1
```

四处设计值得记住：默认掩码让漏配的结果是“看不到”而非“全泄露”；`restricted` 分支先于角色判断，管理员也拿不到原值；假名带密钥，社内可关联、无密钥不可反查；审计链改一条要改后面全部。

## 动手实验

前置条件：已完成最小示例，Python 3.9+。只用构造数据，不接触真实顾客信息。

1. 打印四个角色的投影，用正则 `1[3-9]\d{9}` 与 `\d{17}[\dXx]` 扫描输出，记录命中位置。
2. 把 `phone` 的可见角色从 `"cs"` 改成 `"finance"`，重跑，观察命中如何转移。
3. 同一手机号调用两次 `pseudonym()`，再换密钥调用一次，比较三个结果。
4. 把审计链第 2 条改成 `"allow"`，运行 `verify()`，记录断点。
5. 把 `id_card` 改成 `"sensitive"`、可见角色 `"admin"`，确认管理员能看到原值——这正是应被评审拦下的改动。

预期结果：明文手机号只在 `cs` 输出出现一次；改可见角色后命中转移到 `finance`，策略表之外无代码需改；同密钥两次假名相同、换密钥后不同；审计断点报 `#1`；第 5 步让身份证号出现在输出里，必须否决。

验证方法：命中集合应与授权表逐字一致，而非“越少越好”——零命中也可能意味着业务已无法工作；断点应指向被改的那条，而非笼统报失败。

清理方法：删除临时脚本与含构造数据的输出文件；不要把假号码或真实数据复制进仓库或工单。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 页面已打码，抓包仍见完整手机号 | 脱敏做在前端模板 | `curl` 直连接口看响应体 | 服务端按角色投影，字段白名单 |
| 手机号“哈希过了”却被反查 | 低熵字段裸哈希可被穷举 | 用号段字典比对哈希结果 | 改带密钥的 HMAC，或只存末四位 |
| 开了透明加密仍被判不合规 | 混淆介质加密与访问控制 | 用 DBA 账号直接 `select` | 极敏感字段应用层加密，密钥分离 |
| 测试库能搜到真实顾客 | 用生产快照代替造数 | 抽样扫描测试库手机号 | 合成数据或脱敏后的子集 |
| 注销工单已关闭，信息仍能搜到 | 删除只覆盖主库 | 到索引、缓存、数仓、备份各查一次 | 删除清单加到期验证与删除证据 |

## 安全与生产注意事项

**<u>把生产库快照整库恢复到测试环境，等于把最高级别的泄露风险复制到防护最弱的地方。</u>** 测试环境常账号共享、无审计、无保留策略，甚至办公网可直达；一旦被拖库，影响与生产相同却难被发现。缓解：禁止跨环境直连生产存储，用合成数据或脱敏子集造数。

**<u>审计日志记录明文个人信息且留得比业务数据更久，会把“合规证据”变成新的泄露源。</u>** 日志往往汇聚到检索平台，权限更宽、保留更长。缓解：只记字段名、主体假名、资源标识与结果；独立密钥、只追加写入，保留期按“能否支撑追责”设定。

**<u>“顾客要求删除”时只删主库，索引、数仓与备份里的副本仍在，等于没有删除。</u>** 后果是复访、投诉或抽查时仍能查到，团队也无法举证。缓解：维护跨系统数据位置清单，删除覆盖主库、索引、缓存、数仓并按备份过期兑现，保留执行证据。

## 本课总结

- **分级先于控制**：先判断泄露影响、可见范围与保留期限，再决定加密、脱敏与审批强度。
- **加密、脱敏、令牌化各守一段链路**，都不能单独回答“谁有权看原值”。
- **脱敏与权限一样必须在服务端执行**，页面隐藏只是体验。
- **审计要能回答问题**：记字段名与结果，不记值，只追加，有留存期。
- **合规是责任分配**：平台、商家、支付商、云厂商各担一部分，边界必须书面确认。

## 思考题

晴空商城要上线 AI 客服：读订单摘要回答“快递到哪了”，质检还要回放录音。产品希望模型看到完整手机号与地址，“回答更自然，少一次转人工”。

请设计这两个场景的分级、脱敏与留存，说明哪些字段可以给模型、哪些只给掩码，责任落在平台、商家还是模型供应商，并列出至少三条必须由法务书面确认的问题。

参考思路：按“模型是否真的需要”裁剪——物流进度只需订单号、承运商、状态与大致区域，手机号与地址没有增益。再看责任：平台是处理决定者，模型供应商是受托方，需合同约束用途、留存与二次训练；商家只看到自己订单的聚合与掩码信息。需确认的是录音保留期与告知方式、跨供应商传输是否允许、删除请求如何在模型侧兑现。

## 小测

1. 数据分级最直接的作用是什么？  
   A. 给数据起正式名称　B. 让控制强度与数据影响匹配并可被检查　C. 满足加密算法要求　D. 降低存储成本
2. 客服必须按完整手机号搜索、但只能看到后四位，最合适的组合是？  
   A. 全库明文加页面打码　B. 存带密钥的 HMAC 供精确匹配，展示层掩码　C. 所有字段应用层加密　D. 只存后四位
3. 开启数据库透明加密后，仍能读到明文的主体通常是？  
   A. 拿到备份介质的外部人员　B. 拥有查询权限的数据库账号　C. 网络中间人　D. 存储厂商
4. 为什么审计日志不应记录字段值？
5. 场景题：物流商要每天收到完整收货信息，品牌商要求平台不得把顾客数据给第三方。架构师应如何处理？

## 答案与解析

1. **B。** 分级的产出是“哪个级别配哪些控制”，可检查、可审计。A 只是命名；C 把分级缩成加密；D 保留期由用途决定。
2. **B。** 精确匹配需要可计算的索引值，HMAC 无密钥不能反查，展示层再掩码。A 的接口仍返回全量；C 加密后无法等值查询；D 会让完整号码搜索失效。
3. **B。** 透明加密加密的是落盘文件，数据库引擎解密后按权限返回。A 正是它能挡的；C 属传输层，由 TLS 负责；D 与权限无关。
4. 日志常被集中采集、长期保留、权限更宽，记明文会让“证据”变成泄露面；追责只需知道谁在何时对哪个字段做了什么、结果如何。
5. 先限定“派送必需字段”：姓名、电话、地址，可能加订单号，金额与历史订单不给；传输加密，接收方与用途留痕，优先用隐私面单；合同明确只能用于派送、不得留存转售。“平台是处理者还是控制者”须由法务确认。

### 动手实验参考

第 1 步命中集合应与授权表一致：`cs` 命中手机号一次，其余为零，`id_card` 在任何角色下都不应命中。第 2 步改一行策略就转移可见性，说明判定依据集中而非散落。第 3 步同密钥结果相同、换密钥不同，即“可关联、不可跨环境反查”。第 4 步断点应报 `#1`；若篡改后仍完整，通常是漏算 `prev` 或把 `hash` 也放进了被哈希的内容。第 5 步确认“能改”不等于“该改”。
