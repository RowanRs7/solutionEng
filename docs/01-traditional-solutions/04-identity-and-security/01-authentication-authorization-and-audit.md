# 认证、授权与审计

## 为什么需要学习

晴空商城的退款系统上线三个月后，三件事被同时翻出来：一名离职客服的账号还在用，导出了两万多条收货地址；退款接口只要求“已登录”，任何内部账号都能对任意订单发起退款；追责时日志里只有一行“退款成功”，没人能证明是谁把可退金额从 500 元改成了 50000 元。

根源只有一个：把“登录了”当成“什么都能做”，把“做完了”当成“有记录”。

> **核心结论：** 认证回答“你是谁”，授权回答“你能做什么”，审计回答“你实际做了什么”；三者缺一，事故要么发生，要么发生之后无法解释。

## 学习目标

完成本课后，你能够：

- 分别说明认证、授权、审计回答的问题，并判断一条请求缺了哪一层。
- 把“客服只能处理自己的单、超过 500 元要主管批”改写成可判定的权限规则。
- 比较 RBAC 与 ABAC，为退款审批选出模型并说明理由与代价。
- 写出一条最小可用的审计记录，列出必需字段与必须排除的字段。

## 前置知识

- 回看上一单元：[API 与系统集成](../03-api-and-integration/00-overview.md)。
- 知道 `401` 与 `403` 的区别，能读懂一次 REST 请求的方法、路径与请求头。

- 理解“幂等”指重复执行与执行一次结果相同。

## 业务场景

“晴空商城”的退款流程横跨商城、订单、支付、仓储与客服平台，身份规则是：

- 客服只能看到分配给自己的工单对应的订单；单笔退款 500 元以内可直接提交，超过须主管审批。
- 仓库需要收货地址，但不需要看到金额与买家联系方式。
- 客服平台以“代客操作”调用退款服务，事后必须能区分“谁点的”和“以谁的名义”。
- 合规要求：任何一笔退款的审批链 5 分钟内能还原，记录保留 180 天。

架构师要交付的不是登录页，而是五个决定：谁是主体、权限按什么粒度判定、越权在哪层拦住、审计记哪些字段、记录存在谁能改。

## 核心概念

*认证*（authentication）验证主体声称的身份是否成立。*授权*（authorization）在身份确定后，判断该主体能否对某个资源执行某个动作。*审计*（audit）留下“谁在何时对什么做了什么”的可追溯证据。

*主体*（principal）是发起请求的实体，可以是员工、后台服务或设备，它需要稳定标识而不是可变的用户名。*资源*（resource）是被访问的对象，如一张订单、一笔退款。*动作*（action）是对资源的操作，如 `order:read`、`refund:apply`。*权限*（permission）是“某主体在特定条件下可对某类资源执行某动作”的完整表述。*角色*（role）按岗位聚合权限，员工通过被授予角色间接获得权限。*最小权限*要求只授予完成当前工作必需的范围。*默认拒绝*指没有规则明确允许时一律拒绝。*对象级授权*（object-level authorization）要求判定具体到某条记录。

| 维度 | 认证 | 授权 | 审计 |
| --- | --- | --- | --- |
| 回答的问题 | 你是谁 | 你能对什么做什么 | 你实际做了什么 |
| 失败时的正确信号 | `401`，要求重新登录 | `403`，身份有效但无权 | 不阻断请求，但留下记录 |
| 发生时机 | 每个请求开始时 | 每次访问资源时，含对象级 | 判定与副作用完成后 |
| 典型实现 | 密码加 Session、OIDC、API Key | 策略判定、角色、属性规则 | 结构化日志与只追加存储 |
| 晴空商城的反例 | 多人共用客服账号 | 只在前端隐藏退款按钮 | 只记“退款成功”不记操作人 |

**认证通过不代表有权。**<u>把 `401` 当 `403` 用，用户会反复登录却始终失败；把 `403` 当 `401` 用，则泄露了“这个资源存在”。</u>

## 工作原理

一次“客服提交 880 元退款”的请求，按下面的顺序被处理：

1. **建立信任通道**：请求经 TLS 到达客服平台，携带会话 Cookie 或 Bearer 令牌。
2. **认证**：校验会话或令牌签名，得到主体标识 `u_1001`。用稳定 ID 而非用户名，因为用户名会重复、会改。
3. **装配主体上下文**：加载角色、名下订单集合与认证强度，均来自服务端或受信声明，<u>不能读客户端传来的 `role` 请求头</u>。
4. **解析资源**：从路径或报文取出 `order_id`，**先按 ID 加载资源**，再判断主体与这条记录的关系。顺序反了就只能做功能级判断。
5. **授权判定**：默认拒绝，同时覆盖功能级（能否调用退款接口）与对象级（能否对这张单退款、金额是否超限）。
6. **执行副作用**：在同一事务里写退款单与状态变更，并附带审计事件，避免“业务成功、日志丢失”。
7. **写审计记录**：请求 ID、主体、代理关系、动作、资源、决定、原因码、时间、来源地址。
8. **返回结果**：通过则 `201` 或 `202`；未认证 `401`；已认证无权 `403`，且不透露资源是否存在。
9. **留存与消费**：审计事件进入只追加存储，按保留期归档。

三个层次各有边界：网关做认证与粗粒度路由，业务服务做功能级与对象级授权，数据访问层用租户条件兜底。**授权必须发生在拥有这份资源的服务里**，因为只有它知道“客服 A 与订单 42”之间有没有关系。

## 架构与选型

| 模型 | 适用场景 | 不适用场景 | 晴空商城用法 |
| --- | --- | --- | --- |
| 直接 ACL（按对象授权） | 少量对象需单独共享 | 对象与主体持续增长时维护失控 | 临时协作者访问单个工单 |
| RBAC（基于角色） | 岗位职责稳定、权限可枚举 | 表达不了“自己的单”“金额上限”等条件 | 客服、主管、仓库、财务四个角色 |
| ABAC / ReBAC（基于属性或关系） | 判定依赖归属关系、金额、时间、租户 | 规则复杂又缺少测试时变成黑盒 | 主管审批上限、跨租户隔离 |

选型看三件事：变更频率（岗位在变还是规则在变）、可解释性（能否回答“为什么他被拒”）、审计成本（历史决定能否复盘）。实用组合是**RBAC 打底、关键动作叠加属性条件**：角色负责“这类岗位能做什么”，属性负责“这张单能不能退、上限多少”。

三种取舍要写进决策记录：策略写死在代码里最快，但每次调整都要发版；外置到统一授权服务一致性好，代价是多一跳延迟；把角色塞进令牌省一次查询，代价是变更无法即时生效。

## 最小示例

问题：用 Python 标准库实现“默认拒绝 + 角色 + 对象与金额条件”的判定器，并为每条决定写审计记录。环境 Python 3.8+，不访问网络。

```python
import json

# 策略表以 (角色, 动作) 为键：只声明允许什么，没声明的动作一律拒绝
POLICY = {
    ("support", "order:read"): {"scope": "own_order"},
    ("support", "refund:apply"): {"scope": "own_order", "max_amount": 50_000},
    ("supervisor", "order:read"): {"scope": "all"},
    ("supervisor", "refund:approve"): {"scope": "all", "max_amount": 500_000},
    ("warehouse", "address:read"): {"scope": "own_order"},
}

# 主体只存稳定标识与归属关系；真实系统里角色来自目录服务
SUBJECTS = {
    "u_1001": {"roles": ["support"], "own_orders": {"SO-8801"}},
    "u_2002": {"roles": ["supervisor"], "own_orders": set()},
    "u_3003": {"roles": ["warehouse"], "own_orders": {"SO-8801"}},
}

AUDIT = []  # 真实系统写只追加存储；这里用列表收集以便断言


def authorize(subject_id, action, order_id, amount):
    subject = SUBJECTS.get(subject_id)
    if subject is None:
        return "deny:unauthenticated"  # 认证层没给出主体，应由 401 处理
    for role in subject["roles"]:  # 多角色取并集，任一命中即放行
        rule = POLICY.get((role, action))
        if rule is None:
            continue  # 该角色未声明此动作，继续看下一个角色
        if rule["scope"] == "own_order" and order_id not in subject["own_orders"]:
            continue  # 对象级校验不过：视为该角色不适用，而不是放行
        limit = rule.get("max_amount")
        if limit is not None and amount is not None and amount > limit:
            return "deny:amount_exceeds_policy"  # 上下文条件不满足
        return "allow"
    return "deny:no_permission"  # 默认拒绝：一条规则都没命中


def decide(request_id, subject_id, action, order_id, amount, now):
    verdict = authorize(subject_id, action, order_id, amount)
    # 拒绝同样写入审计：越权尝试的价值往往高于成功操作
    AUDIT.append(
        {
            "ts": now,  # 统一 UTC 时间，跨系统才能对齐顺序
            "request_id": request_id,  # 串联网关、服务与下游日志
            "actor": subject_id,  # 主体 ID，不是用户名
            "action": action,  # 动作，与策略表同名
            "resource": f"order:{order_id}",  # 资源类型加 ID
            "decision": verdict,  # 决定加原因码，便于告警分流
        }
    )
    return verdict


NOW = "2026-10-19T09:30:00Z"  # 固定时间，保证输出可复现
cases = [
    ("req-1", "u_1001", "refund:apply", "SO-8801", 19_900),
    ("req-2", "u_1001", "refund:apply", "SO-8801", 99_900),
    ("req-3", "u_1001", "order:read", "SO-9902", None),
    ("req-4", "u_2002", "refund:approve", "SO-9902", 199_000),
    ("req-5", "u_3003", "refund:apply", "SO-8801", 19_900),
    ("req-6", None, "order:read", "SO-8801", None),
]

for rid, sid, act, oid, amt in cases:
    print(f"{rid:6} {decide(rid, sid, act, oid, amt, NOW)}")

print("audit_records:", len(AUDIT))
print(json.dumps(AUDIT[1], ensure_ascii=False, sort_keys=True))
```

运行 `python3 authz_demo.py`，预期输出：

```text
req-1  allow
req-2  deny:amount_exceeds_policy
req-3  deny:no_permission
req-4  allow
req-5  deny:no_permission
req-6  deny:unauthenticated
audit_records: 6
{"action": "refund:apply", "actor": "u_1001", "decision": "deny:amount_exceeds_policy", "request_id": "req-2", "resource": "order:SO-8801", "ts": "2026-10-19T09:30:00Z"}
```

流程是：认证给出主体 → 逐角色匹配策略 → 先过对象归属 → 再过金额条件 → 未命中即拒绝 → 每条决定落审计。三个设计点：`req-3` 与 `req-5` 同为 `deny:no_permission`，但一个是越权读他人订单、一个是动作未授权，告警阈值应不同；`req-6` 用独立原因码把“未认证”与“无权限”分开，避免前端一律弹重新登录；金额存整数分，避免浮点误差让 500 元上限形同虚设。

## 动手实验

### 前置条件

本机有 `python3`（3.8+）和一个可写目录；不需要第三方库、真实账号或网络。

### 步骤

1. 把上面的代码保存为 `authz_demo.py`，运行一次，对照“预期输出”逐行核对。
2. 删除 `POLICY` 中 `("support", "refund:apply")` 这一行再运行，观察 `req-1` 的变化。
3. 把 `refund:apply` 规则的 `scope` 从 `own_order` 改为 `all`，再运行，观察 `req-3` 的变化。
4. 新增“同一退款单不得由同一人既申请又审批”的规则：返回 `allow` 前检查 `AUDIT` 中是否已有该主体的申请记录，命中则返回 `deny:segregation_of_duties`。
5. 加断言 `assert len(AUDIT) == len(cases)`，确认拒绝也有审计记录。

### 预期结果

步骤 2 中 `req-1` 变为 `deny:no_permission`、其余不变，说明默认拒绝生效；步骤 3 中 `req-3` 变为 `allow`，越权读取被复现；步骤 4 新增用例返回职责分离原因码，原六条不变；步骤 5 断言通过，审计条数始终等于请求数。

### 验证方法

把结论写成断言，例如 `assert decide("r", "u_1001", "order:read", "SO-9902", None, NOW) == "deny:no_permission"`；`python3 -m unittest` 全绿即说明策略表与判定逻辑一致。再打印 `AUDIT`，确认每条都含 `request_id`、`actor`、`action`、`resource`、`decision`。

### 清理方法

删除 `authz_demo.py` 与 `__pycache__`。实验只写内存列表，不落库。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 用户刚登录就被提示无权 | 只做了认证，没装配角色 | 查角色列表与策略表是否有对应项 | 补角色与策略，而非放宽成“登录即可” |
| 客服能打开别人的订单 | 缺少对象级归属判断 | 换别人的订单 ID 直接请求接口 | 加载资源后校验归属，统一返回 403 |
| 拒绝的请求无法解释 | 判定函数只返回布尔值 | 看日志是否只有 403 没有原因码 | 返回结构化原因码并写入审计 |
| 审计里查不到操作人 | 多人共用账号，只记服务名 | 统计 `actor` 取值分布 | 一人一账号，调用带代操作主体 |
| 权限调整后不生效 | 角色缓存进会话或令牌 | 对比角色表与令牌内容 | 短期令牌加服务端复核 |
| 日志中出现密码与卡号 | 直接记录整个请求体 | 正则扫描日志样本 | 白名单字段，敏感值脱敏 |

## 安全与生产注意事项

**<u>只在前端隐藏按钮、服务端不做对象级授权，等于把权限判断交给攻击者。</u>** 浏览器能任意改请求，把 `order_id` 换成别人的就能发起退款或读地址。缓解：每个资源请求都按归属判定，拒绝统一返回 403，并用自动化用例覆盖“访问他人资源”。

**<u>审计日志允许业务账号修改或删除，或记录了密码与完整证件号，会让审计从证据变成新的泄露源。</u>** 前者无法举证“谁批了这笔退款”，后者违反个人信息最小化。缓解：只追加存储、写入账号与业务账号分离、明确保留期、按白名单字段脱敏后再写。

**<u>把认证当成授权，给后台服务发放长期全权密钥。</u>** 服务被滥用时，日志里只剩“某服务”，无法定位到人。缓解：每个服务独立主体、按动作与资源范围授权、使用短期凭证，并记录完整代理链。

## 本课总结

- **认证证明身份，授权决定权限，审计保留证据，三者不能互相替代。**
- 权限规则写成“主体 + 动作 + 资源范围 + 条件”，默认拒绝，并在拥有资源的服务里做对象级判定。
- RBAC 管岗位，ABAC 或 ReBAC 管归属与条件；先能解释一个拒绝，再谈灵活性。
- 审计的最小字段集是请求 ID、主体、代理关系、动作、资源、决定与原因、时间。
- 拒绝也要记录，日志本身要受保护、脱敏并设定保留期。

## 思考题

主管要求“代客操作”：主管登录后能以某个客服的身份提交退款。请说明审计写谁、写几个主体、授权以谁为准，并给出两条防滥用约束。

参考思路：区分操作人（actor）与权限主体（effective subject），两者都记录并用代理字段串起链条；授权同时校验“主管是否有代理权”和“客服本人是否有这笔退款权”；约束包括代理有时限与范围、被代理人事后可见、不得审批自己提交的单据。

## 小测

1. 用户已登录，访问退款审批接口收到 `403`，说明什么？  
   A. 认证失败　B. 授权失败　C. 审计失败　D. 网络失败
2. “客服只能对分配给自己的订单提交 500 元以下退款”包含哪些要素？（多选）  
   A. 主体　B. 动作　C. 资源范围　D. 上下文条件
3. 判断：把角色写进令牌后，管理员调整角色会立即在所有端生效。
4. 下列哪项最不应出现在审计日志里？  
   A. 请求 ID　B. 操作人主体 ID　C. 用户明文密码　D. 决定与原因码
5. 判断：网关已经校验了角色，下游微服务可以不重复校验权限。
6. 场景题：运营反馈“仓库账号能打开财务的退款对账页面”，排查发现两个岗位角色都是 `internal`。请指出设计缺陷与三步修复顺序。

## 答案与解析

1. **B。** `403` 表示身份已识别但无权执行。A 对应 `401`；C 的审计不参与放行决定；D 表现为连接错误，而非带业务语义的 `403`。
2. **A、B、C、D。** 主体是客服，动作是提交退款，资源范围是“分配给自己的订单”，条件是“金额不超过 500 元”。<u>缺 C 就退化成“任一客服可退任意订单”。</u>
3. **错。** 令牌是签发时刻的快照，过期前一直有效；改库后旧令牌仍带旧角色。要立即生效需短有效期配合服务端复核或吊销。
4. **C。** 密码进入日志即等于长期泄露，直到用户改密。A、B、D 是追溯的必需字段。
5. **错。** 网关只能做认证与粗粒度路由，判断不了“客服 A 与订单 42”的关系；<u>越权常发生在被跳过的服务内部</u>。
6. 缺陷一是用 `internal` 这种过粗角色承载跨职能权限；缺陷二是只隐藏入口，接口没有对象级校验。顺序：先给对账接口加对象级授权（止血）→ 拆角色为 `finance` 与 `warehouse` → 补自动化用例与审计告警。

### 动手实验参考

步骤 2 中 `req-1` 变为 `deny:no_permission`，证明“未声明即拒绝”；步骤 3 中 `req-3` 由拒绝变放行，复现越权读取，说明角色粒度不等于对象粒度；步骤 4 的检查放在返回 `allow` 之前，并新增独立原因码便于告警；步骤 5 的断言说明拒绝同样写入审计，这正是事后追溯的前提。
