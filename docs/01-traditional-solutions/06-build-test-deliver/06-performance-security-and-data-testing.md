# 性能、安全与数据质量测试

## 为什么需要学习

晴空商城的退款集成服务通过了功能与验收测试，然后在大促首日出了问题：客服 40 人同时提交退款时，网关在 2 秒切断请求，界面显示“提交失败”，而支付商侧其实已受理了一部分；三天后安全同事用别人的退款单号请求了一次，读到了不属于自己的记录；月末对账又发现一笔 120 元退款在订单库里找不到对应订单，客服手工平账。

功能测试全部通过，却没有任何环节回答过：压力下它守不守承诺、换一个身份还能不能读它、数据变脏后会不会静默吞下。这三种承诺分别属于性能、安全和数据质量，功能测试并不覆盖。

> **核心结论：** 性能回答“压力下是否守承诺”，安全回答“边界是否真实存在”，数据质量回答“脏数据会不会被无声接受”；三者都要给出可复核的证据，而不是一句“测过了”。

## 学习目标

完成本课后，你能够：

- 用 p95、吞吐量、错误率和饱和度写出可复核的性能验收条件，并解释平均值为何不能用于验收。
- 设计一次含基线、阶梯加压与停止条件的压测，给出可复述的容量结论。
- 区分 SAST、DAST、SCA、渗透测试和模糊测试能发现的问题与执行位置。
- 为退款数据写出至少 4 条可自动执行的质量规则，并指出违反时的业务后果。
- 判断一次压测或安全测试该用哪个环境、哪类数据，失败时阻断发布还是仅告警。

## 业务场景

本课继续看晴空商城的退款集成服务：订单在商城、资金在支付商、库存在仓储、沟通在客服。本单元的具体侧面是“上线前的质量门”：

- 客服峰值 40 人并发提交，退款受理接口的目标是 p95 ≤ 800ms、受理成功率 ≥ 99.5%。
- 退款单含金额、订单号、客服工号与收货手机号，属于敏感业务数据，测试环境不应出现未脱敏的真实记录。
- 财务要求每笔 `approved` 退款都能在订单库找到金额一致的订单，差异逐条列出。
- CI 跑源码与依赖检查，预发承载压测与动态扫描，生产只允许影子流量与日终对账。

架构师要交付的不是“测试通过”，而是能被重算的数字、可追溯的违规清单和明确的阻断结论。

## 核心概念

*性能指标*是描述服务在负载下表现的量化口径：*吞吐量*是单位时间成功完成的请求数；*延迟分位数*把延迟排序后取某个百分比处的值；*错误率*是失败请求（含超时）占比；*饱和度*是 CPU、连接池等资源的占用程度。*基线*是未加压时测得的参照值；*容量结论*是“能承载多少并发、瓶颈在哪里”的判断。

*负载测试*在预期峰值下验证是否达标；*压力测试*持续加压直到失效，用来找拐点；*浸泡测试*在中等负载下跑数小时，暴露内存与连接泄漏。

*SAST* 是静态应用安全测试，扫描源码里的危险写法；*DAST* 是动态应用安全测试，对运行中的服务发真实请求；*SCA* 是软件成分分析，检查依赖库的已知漏洞；*渗透测试*由人把多个小问题组合成一次利用；*模糊测试*用畸形输入撞校验边界。<u>静态扫描看不见运行期的授权判断，动态扫描看不见未被触发的代码路径。</u>

*数据质量规则*是把“数据应该长什么样”写成可执行的断言：*完整性*要求必填字段齐全，*准确性*要求数值与事实一致，*唯一性*要求同一对象不重复，*一致性*要求跨系统对同一事实给出相同答案。*对账*是按固定口径比对两侧结果并输出差异清单。

| 指标 | 定义 | 退款服务验收口径 | 为什么不能只看平均值 |
| --- | --- | --- | --- |
| 吞吐量 | 每秒成功完成的请求数 | ≥ 60 次/秒（覆盖 40 客服并发） | 错误率高时有效处理量可能接近 0 |
| 延迟 p95 | 95% 的请求快于此值 | ≤ 800ms | 平均值被大量快请求拉低，长尾被抹平 |
| 错误率 | 非成功响应与超时占比 | < 0.5% | 只统计成功请求的延迟，会漏掉最慢的一批 |
| 饱和度 | 连接池、CPU、数据库连接占用 | 峰值 ≤ 70% | 接近 100% 时延迟阶跃上升，而非线性变慢 |

## 工作原理

一次“上线前质量门”按时间顺序展开为九个步骤：

1. **定义口径**：写清指标名、统计窗口、成功判定与采样点，例如“预发、每级 3 分钟、取最后 1 分钟 p95，超时计为失败”。
2. **备好基线与夹具**：记录单实例空载延迟与资源占用；用合成或脱敏数据造出接近生产量级的订单与退款单，并指定测试商户号。
3. **阶梯加压**：并发按 10 → 20 → 40 → 80 逐级上升，每级稳定后再采数，避开冷启动与缓存预热。
4. **记满四个口径**：分位数、吞吐量、错误率、饱和度，缺一项就分不清“系统慢”还是“施压机慢”。
5. **找拐点**：并发上升而吞吐不再增长、p95 开始阶跃处即为拐点；达不到目标就停止加压，先定位瓶颈。
6. **静态检查进 CI**：每次合并运行 SAST 与 SCA，只对新增问题阻断，历史问题建基线并登记修复期限。
7. **动态检查在预发**：DAST 与越权用例用两个客服账号互查退款单，验证认证、对象级授权与注入。
8. **数据规则分两层**：写入前用应用校验与数据库约束拦截单条脏数据；每天用对账任务比对退款与订单。
9. **给结论**：汇总为“达标或不达标 + 瓶颈 + 残余风险 + 谁签字”，失败时明确阻断发布。

顺序上的关键点是：**先有口径再有数字，先有基线才有对比，先有阻断条件才有质量门**。跳过第 1 步和第 5 步，压测报告就只是“跑了一下”。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要权衡 |
| --- | --- | --- | --- |
| 预发全链路压测 | 验证整条退款链路与下游配额 | 下游只有共享沙箱 | 最接近生产，数据量级偏小 |
| 生产小流量灰度压测 | 新版本容量未知、风险可承受 | 金额敏感、无法区分压测单 | 数据最真，须带压测标识 |
| SAST + SCA 在 CI | 每次合并拦截危险写法与漏洞依赖 | 需要运行期上下文的越权 | 反馈快，误报多 |
| DAST + 渗透测试在预发 | 验证认证、授权、注入等攻击面 | 服务未部署或无稳定入口 | 最接近攻击者视角，耗人力 |
| 应用校验 + 数据库约束 | 阻止单条脏数据落库 | 跨系统的口径不一致 | 拦截最早，会让写入失败 |
| 日终离线对账 | 发现跨系统不一致与漏单 | 需要实时止损的资金流 | 覆盖最广，只能事后发现 |

选型依据是三项事实：数据敏感度决定能否使用生产流量；失败代价决定规则阻断还是告警；下游配额决定压测放在哪里。晴空商城因此选择“预发全链路压测 + CI 静态扫描 + 预发动态扫描与渗透 + 应用校验与日终对账”。

## 最小示例

脚本用标准库做两件事：按名次法算 p95，并校验退款记录的 5 条质量规则。环境为 Python 3.9+；输入是一行一条 JSON 的夹具；输出是汇总加逐条违规。

```python
import json          # 每行一条 JSON 记录，便于逐条定位问题行
import math          # 用 ceil 计算分位数的名次，避免取整造成口径偏差
import sys           # 结论不通过时用非零退出码真正阻断流水线

# 一条退款记录必须具备的字段，缺失即无法评估后续规则
REQUIRED = ("claim_id", "order_id", "amount", "order_amount", "status", "latency_ms")
# 允许的状态取值，用来发现上游写入了未约定的枚举
STATUSES = {"pending", "approved", "rejected"}


def load(path):
    rows = []
    for lineno, line in enumerate(open(path, encoding="utf-8"), start=1):
        if not line.strip():
            continue                      # 忽略空行，避免夹具末尾换行造成误报
        row = json.loads(line)            # 坏 JSON 直接抛出，说明夹具本身不可用
        row["_line"] = lineno             # 记住行号，报错时能指回原始记录
        rows.append(row)
    return rows


def check(rows):
    problems = []
    seen = set()                          # 用 claim_id 做去重，模拟唯一约束
    for row in rows:
        missing = [k for k in REQUIRED if row.get(k) in (None, "")]
        if missing:                       # 缺字段时后续规则无法计算，先记录再跳过
            problems.append((row["_line"], "缺失字段", ",".join(missing)))
            continue
        if row["claim_id"] in seen:       # 同一理赔单重复提交会让退款翻倍
            problems.append((row["_line"], "重复理赔单", row["claim_id"]))
        seen.add(row["claim_id"])
        amount = round(float(row["amount"]), 2)           # 金额按分对齐，避免浮点尾差
        if amount <= 0:                                   # 非正金额说明上游取值越界
            problems.append((row["_line"], "金额非正", str(row["amount"])))
        if amount > float(row["order_amount"]):           # 退款不得超过订单实付金额
            problems.append((row["_line"], "退款超订单", f"{amount}>{row['order_amount']}"))
        if row["status"] not in STATUSES:                 # 状态越界会让下游分支漏处理
            problems.append((row["_line"], "状态越界", row["status"]))
    return problems


def p95(values):
    if not values:
        return None
    ordered = sorted(values)               # 分位数只取决于排序后的位置，不做插值
    rank = math.ceil(len(ordered) * 0.95)  # 名次法：取第 ceil(0.95n) 个，口径可复核
    return ordered[max(rank, 1) - 1]


def main(path):
    rows = load(path)
    problems = check(rows)
    latencies = [int(r["latency_ms"]) for r in rows if str(r.get("latency_ms", "")).isdigit()]
    print(f"记录数={len(rows)} 违规数={len(problems)} p95={p95(latencies)}ms")
    for line, rule, detail in problems:    # 每条违规给出行为、规则名和证据
        print(f"  第{line}行 [{rule}] {detail}")
    return 0 if not problems else 1        # 有违规即返回 1，让门禁真的生效


if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1]))
```

`refunds.jsonl` 只需 6 行，各埋一类缺陷（重复理赔、退款超订单、状态越界、金额为 0、缺 `status`），并把一条记录的延迟写成 920ms 制造长尾：

```text
{"claim_id":"C-1001","order_id":"O-9001","amount":"99.00","order_amount":"199.00","status":"approved","latency_ms":"180"}
{"claim_id":"C-1002","order_id":"O-9002","amount":"120.00","order_amount":"100.00","status":"approved","latency_ms":"240"}
{"claim_id":"C-1003","order_id":"O-9003","amount":"30.00","order_amount":"300.00","status":"done","latency_ms":"310"}
{"claim_id":"C-1001","order_id":"O-9001","amount":"99.00","order_amount":"199.00","status":"approved","latency_ms":"150"}
{"claim_id":"C-1005","order_id":"O-9005","amount":"0.00","order_amount":"260.00","status":"pending","latency_ms":"920"}
{"claim_id":"C-1006","order_id":"O-9006","amount":"12.50","order_amount":"50.00","latency_ms":"205"}
```

运行方式与预期输出：

```bash
$ python3 check_refunds.py refunds.jsonl
记录数=6 违规数=5 p95=920ms
  第2行 [退款超订单] 120.0>100.00
  第3行 [状态越界] done
  第4行 [重复理赔单] C-1001
  第5行 [金额非正] 0.00
  第6行 [缺失字段] status
$ echo "退出码=$?"
退出码=1
```

设计要点：`p95` 用名次法而不插值，口径可被复算；每条违规附带原始行号，报告可追溯到具体记录；退出码把“数据不干净”变成流水线失败。`C-1005` 的 920ms 单独决定了 p95，这就是平均值掩盖长尾的具体形态。

## 动手实验

**前置条件**：本机有 `python3`（3.9+）和可写临时目录；不需要外网、依赖包或数据库。

1. 在临时目录写下 `check_refunds.py` 与 `refunds.jsonl`（内容见上），确认文件为 UTF-8、每行一条合法 JSON。
2. 运行 `python3 check_refunds.py refunds.jsonl`，记录记录数、违规数、p95 与退出码。
3. 删掉第 5 行（920ms 且金额为 0 的那条）后重跑，对比违规数与 p95 的变化。
4. 手工核对口径：`python3 -c "import math; v=sorted([180,240,310,150,205]); print(v, math.ceil(len(v)*0.95))"`，确认第 3 步的 p95 就是排序后的第 5 个值。
5. 把某条 `amount` 改成字符串 `"99.999"` 再跑一次，观察规则是否仍然生效。

**预期结果**：第 2 步输出 `记录数=6 违规数=5 p95=920ms` 与 5 条明细、退出码 `1`；第 3 步输出 `记录数=5 违规数=4 p95=310ms`——p95 由尾部少数样本决定；第 5 步 `"99.999"` 被 `round` 成 `100.0`，若订单金额为 100 则规则通过，<u>这正是浮点存金额最容易漏掉的误差</u>。

**验证方法**：`echo $?` 能读到退出码并被 CI 判定；违规行号与原始文件一致；换成只含合法记录的夹具时退出码为 `0`。

**清理方法**：删除临时目录与夹具。**<u>不要把生产导出的退款单留在本机或测试目录。</u>**

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 报告“平均延迟 200ms”很好看，上线后大量超时 | 只看平均值，长尾被快请求拉低 | 在同一份原始数据上重算 p95、p99 | 报告固定输出分位数 |
| 加到 80 并发吞吐不升、延迟暴涨，服务器 CPU 只有 30% | 施压机打满或连接池耗尽，施压端成了瓶颈 | 看施压机 CPU 与目标端连接池等待数 | 分离施压与承载，提高连接池配额 |
| 安全报告几百条高危，三个月一条没修 | 无分级、无误报标记、无修复期限 | 检查是否区分新增与存量、有无豁免签字 | 建基线，只对新增问题阻断合并 |
| 双账号互查能读到别人的退款单，静态扫描从不报警 | SAST 看不到运行期的对象级授权 | 用两个账号对同一接口发请求对比返回 | 补 DAST 越权用例与逐对象授权断言 |
| 退款金额出现 1 分钱误差 | 浮点或字符串存金额，各处舍入方向不同 | 检查字段类型与每次舍入的位置 | 改用定点小数 |

## 安全与生产注意事项

**<u>绝不能把压测流量指向生产支付通道的真实退款接口。</u>** 后果是真实资金被重复提交：脚本重试与幂等键不一致时同一笔订单会被扣两次，只能靠人工对账退汇补救。缓解办法是只连支付商沙箱或压测专用商户号，请求带压测标识头，服务端对标识做白名单。

**<u>绝不能把生产数据整库拷到测试环境做压测或安全测试。</u>** 后果是姓名、手机号、退款金额扩散到权限更低、审计更弱的环境，一次导出就是一次泄露，删文件也挽不回。缓解办法是用合成数据或脱敏子集，字段级遮蔽姓名与电话，并对测试环境同样开启访问审计。安全测试报告里的利用步骤与真实账号同样敏感，只发给需要修复的人。

## 本课总结

- 性能验收要落在分位数、吞吐量、错误率和饱和度上；**平均值不能作为验收口径**。
- 压测的价值来自口径、基线与拐点，容量结论要写成一句可复述的判断。
- 安全测试是互补视角：SAST 与 SCA 看代码和依赖，DAST 与渗透测试看运行中的服务，<u>越权通常只有带身份的动态用例才能暴露</u>。
- 数据质量用可执行规则表达：在线校验拦单条脏数据，离线对账发现跨系统不一致。
- 质量门的意义在于失败时真的阻断，退出码与修复期限都是它的一部分。

## 思考题

大促前两周，压测 p95 已达 900ms（目标 800ms）但错误率为 0；安全扫描有 3 条中危未修；对账连续两天各差 12 元。你会按什么顺序处理，哪些风险可以带病上线？请写出判断依据、需要的证据和需要谁签字。

参考思路：先看哪一项会造成不可逆损失。对账差异属于资金正确性问题，先定位是漏单、重复还是口径不一致，未解释清楚前不放行自动退款；p95 超标可比较“降并发、加实例、缩小首发范围”的代价，要求给出新的容量结论；中危项逐条评估未授权用户能否触达，能用开关屏蔽的先屏蔽。可带病上线的是有监控、有回退、有责任人的项。

## 小测

1. 下列哪个指标最能暴露长尾延迟问题？  
   A. 平均延迟　B. p50　C. p95　D. 总请求数
2. 负载测试、压力测试和浸泡测试各自回答什么问题？
3. 团队想知道某个依赖库是否有已知漏洞，应先用哪类检查？  
   A. SAST　B. SCA　C. DAST　D. 模糊测试
4. “每笔 `approved` 退款都能在订单库找到金额一致的订单”属于哪个数据质量维度？为什么应用层校验不够？
5. 场景题：同事说“预发压测已经达标，生产就不用再压了”。你同意吗？请说明理由，并写出你会补充的两项证据。

## 答案与解析

1. **C。**p95 表示 95% 的请求快于此值，尾部 5% 的慢请求直接抬高它。A 平均值被快请求拉低；B p50 只看中位数；D 只反映规模。
2. 负载测试在峰值下验证是否达标；压力测试加压到失效，找拐点；浸泡测试用中等负载跑数小时，暴露内存与连接泄漏。三者分别给承诺、上限与稳定性。
3. **B。**SCA 比对依赖清单与漏洞库，正是“第三方库已知漏洞”。A 只看自己写的源码；C 只能触发运行期可见行为；D 只撞输入边界。
4. 属于**一致性**（也涉及准确性）：同一事实在退款库与订单库中必须给出相同金额。应用层校验只看本次请求的字段，无法确认另一侧是否漏单，因此还要跨系统对账。
5. 不同意。预发与生产在数据量、下游配额与流量分布上都不同，结论不能迁移。可补两项证据：生产量级的容量结论，以及影子流量下的 p95 与下游拒绝率。

### 动手实验参考

第 2 步应为 `记录数=6 违规数=5 p95=920ms`、退出码 `1`；第 3 步删除第 5 行后应为 `记录数=5 违规数=4 p95=310ms`（剩余 5 个延迟值排序后第 5 个是 310ms）；第 5 步 `"99.999"` 被舍入成 `100.0`，若订单金额恰好 100 则不再报错——浮点承载金额时两位小数并不保证“分”级精确，应改用定点小数。
