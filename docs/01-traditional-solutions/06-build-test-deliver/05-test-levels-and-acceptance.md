# 单元、集成、契约、端到端与验收测试

## 为什么需要学习

晴空商城的退款集成服务上线前，团队有一套“能跑通”的测试：开发在本地手工点页面，QA 在共享环境跑十几个端到端用例。上线第一周暴露三类问题：退款把运费也退了；商城侧把 `refund_id` 改成 `refundId`，直到联调才发现；端到端用例三天两头失败，团队习惯性重跑，真正的回归被淹没。月底对账又发现 12 笔重复退款——“同一退款单不能重复执行”从未在集成层验证过。

这些缺陷都不是“没测”，而是**测在了错误的那一层**。

> **核心结论：** 测试层级不是为了凑数量，而是让每一类缺陷在**最便宜、最稳定**的那一层被拦住。

## 学习目标

完成本课后，你能够：

- 为金额规则、报文改名、跨系统流程这类变更指定测试层级，并说明不在更高层重复覆盖的理由。
- 描述消费者驱动契约的完整流程，指出它覆盖什么、不覆盖什么。
- 把一条验收标准改写成含“给定/当/那么”与证据要求的 UAT 剧本，并配套可清理的测试数据。

## 前置知识

- 回看上一课：[Git、版本与代码审查](04-git-branching-and-code-review.md)。
- 能读懂 Python `unittest` 的断言与夹具。
- 知道 HTTP 状态码、JSON 字段类型与“接口契约”的日常含义。

## 业务场景

退款链路横跨四个系统：商城（发起）、退款集成服务（编排与审核）、支付商（执行）、仓储（拦截未发货出库），客服平台承接工单。测试对象就是这条链路：

- 退款资格与金额是纯计算：运费不退、已退不能超过已付、300 元以上进入人工审核。规则随促销频繁调整，每次改都跑完整链路成本过高。
- 报文由双方契约约定；支付商升级接口时只承诺“字段兼容”，不承诺行为不变。
- 客服只有在“退款到账 + 工单闭环”时才算完成，这条路径必须由人按剧本验收。
- 测试订单要与别的用例隔离，且不能用真实客户的手机号与流水。

## 核心概念

*测试层级*按“被测对象的范围”划分，而不是按目录或工具划分。*测试金字塔*把层级按数量排成下宽上窄：大量快速的单元测试、较少的集成测试、个位数的端到端测试。

*单元测试*只验证一个函数或类，不启动网络、数据库与文件系统；外部依赖由*测试替身*代替——*桩（stub）*返回固定值，*模拟对象（mock）*记录调用并可断言，*伪实现（fake）*是可工作的简化版。

*集成测试*验证代码与真实依赖的协作：数据库唯一约束、消息重投、对沙箱服务的调用。*契约测试*是它的特化：不验证业务结果，只验证消费者期望的报文与提供者实际给出的报文是否一致，因此能在联调前发现不兼容。

*端到端测试（E2E）*从用户入口出发穿过所有真实系统，验证一条完整业务路径。*用户验收测试（UAT）*由业务方按验收标准判断方案是否可接受，关心“业务上对不对”。*验收标准*是可判定真假的完成条件，*UAT 剧本*把它翻译成“给定…当…那么…”的步骤并规定证据。

*测试数据管理*指测试数据的生成、隔离与清理；*测试数据工厂*是确定性构造数据的函数，同样输入永远得到同样记录。

| 层级 | 被测范围 | 典型数量 | 单次耗时 | 失败说明什么 | 晴空商城示例 |
| --- | --- | --- | --- | --- | --- |
| 单元 | 一个函数或类 | 数百 | 毫秒 | 计算或分支写错 | 运费不退、已退金额上限 |
| 集成 | 代码 + 一个真实依赖 | 数十 | 秒 | 与依赖的协作假设错了 | 退款单落库、幂等键唯一约束 |
| 契约 | 服务之间的报文 | 每对接口若干 | 秒 | 双方对接口理解不一致 | `refund_id` 改名、必填字段缺失 |
| 端到端 | 整条业务路径 | 个位数 | 分钟 | 装配、配置或流程编排错 | 客服发起 → 支付退款 → 工单闭环 |
| UAT | 业务可接受性 | 按剧本 | 小时到天 | 需求理解或业务规则错 | 两小时到账率、人工审核分支 |

**层级越高越真实，但也越慢、越脆、越难定位**；判断标准不是“测得全不全”，而是“这条缺陷最早能在哪一层被稳定发现”。

## 工作原理

一次退款规则变更（自动退款上限从 500 元下调到 300 元）会按顺序穿过各层：

1. **先定验收标准**：产品与客服确认“299 元自动退款、300 元进入人工审核”，并约定证据：退款单状态、工单备注、到账时间。
2. **单元测试固化规则**：用边界值 29900、30000、30001 分断言，不到一秒跑完；规则理解错在这一层暴露最便宜。
3. **集成测试验证持久化**：用真实数据库证明唯一约束拦住重复请求，同一幂等键提交两次只产生一条退款单。
4. **契约测试对齐报文**：消费者把期望发布成契约，提供者在 CI 中回放样本，校验字段名、类型、枚举与错误码；任一侧改名，构建立刻变红。
5. **端到端只留冒烟**：保留 2–3 条全链路路径（成功退款、审核后放行、失败补偿），其余分支在第 2–4 层覆盖。
6. **UAT 由业务方判定**：客服按剧本执行并记录到账时间与工单状态，逐条对照验收标准；不通过就回到第 1 步改标准。
7. **数据收尾**：每层用带命名空间的数据（`t-<用例>-<运行号>`），跑完执行清理脚本；失败保留数据，超期由定时任务清除。

关键是顺序：**标准自上而下定义，防线自下而上建立**。第 4 步最容易被跳过，也最能解释“每层都绿、一联调就炸”。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要权衡 |
| --- | --- | --- | --- |
| 以单元测试为主体（金字塔） | 业务规则密集、变更频繁的核心域 | 主要风险在系统装配与外部接口 | 反馈最快，但证明不了装配正确 |
| 以集成测试为主体 | 数据库约束、消息语义是主要风险 | 规则分支极多、需要密集边界覆盖 | 接近真实，但需要可控的真实依赖 |
| 消费者驱动契约测试 | 多团队多服务、接口频繁演进 | 单服务内部模块之间、无外部接口 | 能提前发现不兼容，但要维护契约版本 |
| 少量端到端冒烟 | 发布前确认“整体装配能跑起来” | 覆盖分支逻辑、性能、大量异常路径 | 置信度最高，但慢、脆、定位成本高 |
| 人工 UAT 剧本 | 业务规则、合规、客服流程的最终判定 | 高频回归、细节逻辑 | 判定权威，但不可自动化、周期长 |

选型依据是三个问题：**能拦住哪类缺陷、这类缺陷在本系统多不多、失败一次要花多少时间定位**。晴空商城的结论是：规则交给单元测试，持久化与幂等交给集成测试，跨系统报文交给契约测试，全链路只留冒烟，到账率与审核分支交给 UAT。

## 最小示例

下面的脚本只用 Python 标准库：用 `unittest` 写单元测试，用一份手写契约做契约校验，并用数据工厂生成确定性订单。环境 Python 3.9+；输入是工厂构造的订单与回调报文；输出是一次测试运行结果。

```python
import unittest  # 标准库测试框架，无需第三方依赖即可演示断言与用例发现

# ---------- 被测逻辑：退款资格与金额。纯函数，不碰网络、数据库和时钟 ----------
def refundable_cents(order):
    # 运费属于履约成本，退款一律不退，所以先从可退金额里扣掉运费
    paid = order["paid_cents"] - order["refunded_cents"]  # 只退尚未退过的部分
    return max(paid - order["shipping_cents"], 0)          # 已退超过实付时归零，杜绝负数退款

def needs_manual_review(order, limit_cents=30000):
    # 阈值用“分”表达，整数比较不会出现浮点误差，也避免 300.00 与 299.99 的舍入争议
    return refundable_cents(order) > limit_cents

# ---------- 测试数据工厂：同样的输入永远生成同样的记录，失败可以原样复现 ----------
def make_order(suffix, paid=0, refunded=0, shipping=0):
    return {
        "order_id": f"SK-2026-{suffix:04d}",   # 带可预测后缀，便于按前缀批量清理
        "paid_cents": paid,                    # 实付金额（分）
        "refunded_cents": refunded,            # 已退金额（分）
        "shipping_cents": shipping,            # 运费（分）
    }

# ---------- 契约：消费者（退款服务）对支付回调的最小期望 ----------
CONTRACT = {
    "required": ["event_id", "refund_id", "amount_cents", "status"],
    "types": {"event_id": str, "refund_id": str, "amount_cents": int, "status": str},
    "enum": {"status": ["succeeded", "failed", "pending"]},
}

def verify_callback(payload, contract):
    # 返回违规清单而不是布尔值：失败信息本身就是给对端的修复指令
    errors = []
    for field in contract["required"]:
        if field not in payload:
            errors.append(f"缺少必填字段 {field}")
            continue  # 字段缺失时不再做类型检查，避免报出两条互相干扰的错误
        expected = contract["types"][field]
        if not isinstance(payload[field], expected):
            errors.append(f"字段 {field} 类型应为 {expected.__name__}")
    for field, allowed in contract["enum"].items():
        if field in payload and payload[field] not in allowed:
            errors.append(f"字段 {field} 取值不在 {allowed}")
    return errors

class TestRefundRules(unittest.TestCase):  # 单元层：只测规则，不启动任何外部资源
    def test_shipping_is_not_refunded(self):
        # 12000 分实付、1500 分运费，可退金额必须是 10500
        self.assertEqual(refundable_cents(make_order(1, paid=12000, shipping=1500)), 10500)

    def test_partial_refund_is_subtracted(self):
        self.assertEqual(refundable_cents(make_order(2, paid=12000, refunded=5000)), 7000)

    def test_fully_refunded_order_is_zero(self):
        self.assertEqual(refundable_cents(make_order(3, paid=12000, refunded=12000)), 0)

    def test_manual_review_boundary(self):
        # 边界三连：阈值下、阈值、阈值上，专抓 > 写成 >= 这类错误
        self.assertFalse(needs_manual_review(make_order(4, paid=29900)))
        self.assertFalse(needs_manual_review(make_order(5, paid=30000)))
        self.assertTrue(needs_manual_review(make_order(6, paid=30001)))

class TestPaymentCallbackContract(unittest.TestCase):  # 契约层：不测金额算得对，只测报文合不合约定
    def test_valid_callback_passes(self):
        payload = {"event_id": "evt-1", "refund_id": "rf-1",
                   "amount_cents": 10500, "status": "succeeded"}
        self.assertEqual(verify_callback(payload, CONTRACT), [])

    def test_renamed_field_is_rejected(self):
        # 模拟支付商把 refund_id 改成 refundId：契约必须先红，而不是等联调
        payload = {"event_id": "evt-1", "refundId": "rf-1",
                   "amount_cents": 10500, "status": "succeeded"}
        self.assertIn("缺少必填字段 refund_id", verify_callback(payload, CONTRACT))

if __name__ == "__main__":
    unittest.main(verbosity=2)  # -v 打印每个用例名，失败时能直接定位到哪条规则
```

保存为 `test_levels.py` 后运行，预期输出：

```bash
$ python3 test_levels.py
test_renamed_field_is_rejected (__main__.TestPaymentCallbackContract.test_renamed_field_is_rejected) ... ok
test_valid_callback_passes (__main__.TestPaymentCallbackContract.test_valid_callback_passes) ... ok
test_fully_refunded_order_is_zero (__main__.TestRefundRules.test_fully_refunded_order_is_zero) ... ok
test_manual_review_boundary (__main__.TestRefundRules.test_manual_review_boundary) ... ok
test_partial_refund_is_subtracted (__main__.TestRefundRules.test_partial_refund_is_subtracted) ... ok
test_shipping_is_not_refunded (__main__.TestRefundRules.test_shipping_is_not_refunded) ... ok

----------------------------------------------------------------------
Ran 6 tests in 0.000s

OK
```

设计要点：被测函数不依赖外部资源，6 个用例毫秒级跑完，可挂在每次保存时；契约校验返回违规清单而非布尔值，让失败信息本身可执行。<u>这段代码替代不了集成测试与端到端测试</u>——数据库约束、沙箱支付与跨系统装配只能用真实环境验证。

## 动手实验

**前置条件**：本机有 `python3`（3.9+）与一个可写临时目录；把上面的代码保存为 `test_levels.py`。不需要外网、不需要数据库。

1. 跑通示例并确认结论：

   ```bash
   python3 test_levels.py 2>&1 | tail -3
   ```

2. 把 `needs_manual_review` 的比较符由 `>` 改成 `>=` 后重跑，看清哪条用例变红，再改回来。

3. 给契约补一条规则：`amount_cents` 必须大于 0。先写用例（`amount_cents: 0` 应报错）看它失败，再在 `verify_callback` 里补实现，直到两者都通过。

4. 写三条退款 UAT 剧本，覆盖 299 元自动退款、300 元进入人工审核后放行、支付商返回 `failed` 后的补偿与工单通知。每条都要有“给定/当/那么”与证据要求（退款单号、到账时间、脱敏截图）。

5. 设计测试数据矩阵：订单状态（未支付 / 已支付未发货 / 已发货 / 已完成）× 金额档（299 / 300 / 500 元以上）× 是否已部分退款，每格标注使用层级、数据来源与清理责任人。

**预期结果**：第 1 步末尾输出 `Ran 6 tests` 与 `OK`；第 2 步失败的是 `test_manual_review_boundary`；第 3 步新用例先红后绿；第 4 步三条剧本都能被第三人独立判定通过或不通过。

**验证方法**：请没参与编写的同事只看剧本，说出“什么算通过”；检查矩阵每行都能对应到一个层级与一个清理责任人。

**清理方法**：删除 `test_levels.py`；若在共享环境执行过剧本，按订单号前缀与退款单号撤销测试退款，并在工单注明“测试数据已清理”。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 单元测试全绿，线上金额仍算错 | 只断言实现细节，或把被测逻辑也 mock 掉了 | 看用例断言业务规则，还是“某方法被调用过” | 改为对纯函数做输入输出断言，减少 mock 层数 |
| 每层都通过，联调仍返工 | 缺契约测试，字段靠口头约定 | 并排对比双方样本报文：字段名、类型、枚举 | 引入消费者驱动契约，纳入双方 CI |
| 端到端用例隔天随机失败 | 多个用例共享同一环境与同一批数据 | 重复运行同一用例，看失败是否与顺序相关 | 每用例独立命名空间数据，跑完清理 |
| UAT 变成产品演示 | 剧本没有判据，只展示界面 | 检查每条剧本是否有预期结果与证据 | 按验收标准写“给定/当/那么”，逐条留证 |
| 测试库出现真实手机号与卡号 | 直接复制生产库当测试数据 | 在测试库抽样检索手机号、地址、流水号 | 合成数据或脱敏子集，记录来源与保留期 |

## 安全与生产注意事项

**<u>禁止把生产数据库整库复制到测试环境。</u>** 后果是客户手机号、地址与支付流水在权限更松的环境里被开发、外包与临时账号读到，一次泄露即构成无法撤回的合规事件。缓解办法是默认用数据工厂生成合成数据，确需真实分布时只取字段级脱敏子集，并记录来源、脱敏规则与保留期限。

**<u>测试与预发环境绝不能持有生产支付凭据，也不能指向生产支付网关。</u>** 后果是一次误跑的端到端用例就是一笔真实退款，且常因金额小而不被立刻发现。缓解办法是只发沙箱凭据、启动时断言网关地址、在网关层对测试环境加白名单与金额上限。

验收截图常被贴进工单与聊天群，**<u>证据必须脱敏后再归档</u>**，否则一次疏忽就把泄露面扩大到没有仓库权限的人。

## 本课总结

- 测试层级按**被测范围**划分，选层依据是“这类缺陷最早能在哪一层被稳定发现”。
- 单元测试守住业务规则，集成测试守住与真实依赖的协作，契约测试守住跨服务报文。
- **消费者驱动契约能把大部分跨服务不兼容拦在联调之前**，它替代重复的端到端用例，不替代业务结果验证。
- 端到端只留个位数冒烟路径，UAT 由业务方判定，测试数据要能生成、隔离与清理。

## 思考题

退款服务只有两名维护者，支付商不提供稳定测试环境，只能对着文档和一个时好时坏的沙箱开发。你会怎样分配单元、集成、契约、端到端、UAT 的投入，既保持发布节奏，又不把风险留给财务？请说明放弃了哪些层级、用什么替代、残余风险由什么信号兜住。

参考思路：优先把规则与报文做成可离线验证的对象——单元测试覆盖金额与资格规则，契约测试回放录制的真实报文，集成测试用真实数据库但不依赖支付商；端到端与 UAT 只留发布前一次少量路径。必须写明残余风险：支付商的真实行为变化只能靠上线后的对账差异与到账告警发现，因此要配套差异监控与人工复核阈值。

## 小测

1. 测试金字塔为什么建议单元测试最多、端到端最少？请从反馈速度与定位成本两个角度说明。
2. 下列哪一项最该由契约测试而不是端到端测试覆盖？  
   A. 退款金额是否扣掉运费　B. 支付商把 `refund_id` 改名后双方是否还能解析　C. 客服能否在两小时内闭环工单　D. 重复提交是否只产生一条退款单
3. 消费者驱动契约里的“消费者”指谁？为什么要求提供者回放消费者发布的契约？
4. UAT 剧本中的“证据要求”解决了什么问题？去掉它会怎样？
5. 场景题：团队为了“测得真实”，把生产库复制到测试环境，并让端到端用例直连沙箱之外的备用支付网关。作为架构师，你会先阻止哪一件事？请给出替代方案与需要记录的风险。

## 答案与解析

1. 单元测试毫秒级返回、失败点唯一，改一行就能定位；端到端测试分钟级、跨系统，失败后先要分辨是环境、数据还是代码。<u>层数越高，越不能靠数量弥补定位成本</u>，所以分支覆盖放低层，高层只留少量高价值路径。
2. **B。**字段改名是双方对接口理解不一致，正是契约测试的靶心。A 是纯规则，属单元层；D 是持久化与并发约束，属集成层；C 是业务可接受性，属 UAT。
3. 消费者是**调用方**，即依赖该接口完成自身功能的服务（此处是退款服务调用支付商适配层）。契约由需求方写成，只有提供者按消费者的真实期望自证一次，不兼容才会在发布前暴露。
4. 它把“通过”变成可复核的事实，避免 UAT 退化成演示，也避免事后争论“当时到底测没测”。缺了它，验收结论只靠口头描述，既无法审计，也无法在回归时复用。
5. 应先阻止**复制生产库**：个人信息泄露面最大且不可撤回，替代方案是合成数据加脱敏子集。第二个阻断项是“端到端直连非沙箱网关”，须改用沙箱凭据并断言地址。需要记录的风险是沙箱与生产的行为差异，以及由此产生的上线后对账依赖。

### 动手实验参考

第 1 步应看到 `Ran 6 tests` 与 `OK`；第 2 步失败的是 `test_manual_review_boundary`，因为 `>=` 让 30000 分也进入人工审核；第 3 步可在 `verify_callback` 中增加 `if payload.get("amount_cents", 0) <= 0` 的检查并返回原因；第 4 步的合格标准是“第三人只看剧本就能判定通过与不通过”；第 5 步矩阵应做到每格都有归属层级与清理责任人。
