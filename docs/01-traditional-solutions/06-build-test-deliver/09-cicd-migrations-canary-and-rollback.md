# CI/CD、变更、灰度与回滚

## 为什么需要学习

晴空商城的退款集成服务要发 v2.3：支付商超时后自动重试，最多三次。上一次发版在大促前夜，团队手工 SSH 到三台机器 `git pull` 并重启；一台机器配置漏改，约三分之一的退款回调落进旧逻辑，财务次日对账发现 47 笔重复退款。同一晚为赶进度直接在生产库建索引，订单表被锁六分钟，商城首页 502。

两次事故看似无关，缺的是同一样东西：**一条把构建、变更、放量和撤回串起来的机制**。

> **核心结论：** 发布不是“把新版本推上去”，而是在可观测、可回退的前提下**逐步改变生产状态**；数据库变更往往比代码变更更难撤回。

## 学习目标

完成本课后，你能够：

- 为一个具体变更列出流水线阶段，并说明每个阶段失败时会拦住哪类缺陷。
- 判断一条数据库变更是否向后兼容，写出扩展-收缩（expand-contract）的迁移顺序。
- 为一灰度批次指定分流方式、门禁指标和最小样本门槛，并写出回滚触发条件。
- 区分回滚应用、回滚配置与回滚数据，说明各自的前提和代价。

## 前置知识

- 回看上一课：[Docker 与 Docker Compose](08-docker-and-compose.md)。
- 能读懂一个 Dockerfile，并知道 `docker compose up` 之后容器、镜像、端口的关系。
- 知道 HTTP 健康检查、状态码和 JSON 报文的含义。
- 会写基础 SQL（`ALTER TABLE`、`CREATE INDEX`），并大致理解事务与表锁的作用。

## 业务场景

本单元聚焦退款服务 v2.3 的“发布”侧面，这次变更两侧都要动：

- 应用侧：状态机新增 `RETRYING`，加入重试执行器，按 1、5、30 分钟退避。
- 数据侧：`refund` 表新增 `retry_count`、`next_retry_at`；`refund_event` 表新增按 `refund_id` 与创建时间的索引。

约束来自四个角色：财务要求任何时刻都能查清一笔退款状态；客服要求退款单不能因重试在处理中停留超过两小时；运维规定每月 1–3 日大促冻结期禁止破坏性变更；支付商要求重试复用同一幂等键。

## 核心概念

*流水线（pipeline）*把“从提交到可发布”的检查步骤固化成自动序列。*持续集成*要求每次提交都跑到流水线前半段；*持续交付*要求通过门禁的版本随时可发布；*持续部署*进一步要求自动发布。<u>持续交付不等于持续部署</u>——前者保留了“人决定何时放量”的环节。

*构建产物（artifact）*是一次构建的不可变结果，通常是带 digest 的镜像。*环境晋级*指同一产物走到生产，只换配置不重新构建；<u>重新构建会让“测过的”和“上线的”不是同一个东西</u>。

*数据库迁移（migration）*是随版本发布、有序且只向前执行的库结构变更脚本。*向后兼容变更*指新结构下旧代码仍能正常读写。*扩展-收缩（expand-contract）*把不兼容变更拆成三步：加新结构、双写回填并切读、后续版本删旧结构。

*灰度发布（canary release）*先把少量真实流量切到新版本，用指标对比决定放量还是撤回。*蓝绿部署*保留两套完整环境，靠切换入口换版。*发布门禁（release gate）*是必须满足才能继续的判定条件，可以是自动指标，也可以是人工审批。

*回滚（rollback）*把运行版本退回上一个已知良好状态；*前滚（roll-forward）*是发布修复版本继续向前。<u>代码可以回滚，写进库里的数据通常只能前滚补偿</u>。

| 策略 | 切换方式 | 资源成本 | 回滚速度 | 爆炸半径 | 明显不适用 |
| --- | --- | --- | --- | --- | --- |
| 停机重建 | 停旧起新 | 最低 | 分钟级 | 全量 | 有 7×24 要求的交易链路 |
| 滚动更新 | 逐批替换实例 | 低 | 分钟级 | 逐步扩大 | 新旧版本无法共存 |
| 蓝绿部署 | 切换流量入口 | 双倍 | 秒级 | 全量但瞬时 | 资源紧张或有状态迁移 |
| 灰度发布 | 按比例或人群分流 | 低 | 秒级 | 部分用户 | 流量太小、样本不足 |

| 数据库变更 | 对旧版本是否兼容 | 能否直接撤回 | 建议做法 |
| --- | --- | --- | --- |
| 加可空列或带默认值的列 | 兼容 | 可留可删 | 直接加，旧代码不写该列也能跑 |
| 加索引 | 兼容 | 可删索引 | 并发建索引，避开写锁 |
| 改列类型或缩小长度 | 通常不兼容 | 不可靠 | 加新列、回填、切读、再删旧列 |
| 重命名列 | 不兼容 | 不可靠 | 视作“加新列 + 删旧列”两步 |
| 删列或删表 | 不兼容 | 不能 | 至少延后一个发布周期，先确认无读取方 |

## 工作原理

一次可回退的发布按时间顺序分十步，前六步在生产之外。

1. **触发**：评审通过后合入主干，流水线自动启动；生产发布时点由人工确认。
2. **构建一次**：产出带 digest 的镜像与迁移脚本清单，之后所有环境只用它。
3. **自动化门禁**：单元与契约测试、依赖与镜像扫描、静态检查，失败即拦住缺陷。
4. **迁移预检**：在生产数据规模的副本上执行迁移并计时。**<u>“预发库 3 秒跑完”不能证明“生产库 3 秒跑完”。</u>**
5. **环境晋级**：同一镜像部署到预发，跑冒烟与关键验收剧本。
6. **变更评审**：确认迁移是否向后兼容、灰度分批与门禁指标、回滚步骤与负责人。
7. **执行扩展**：生产上只做向后兼容的部分——加列、加索引、回填；旧代码继续正常服务。
8. **灰度放量**：1% → 10% → 50% → 100%，每批至少观察一个业务周期。**下一批是否放量由门禁判定，不由“看着还行”判定。**
9. **对比判定**：灰度组与同时段基线的错误率、P95 延迟、退款成功率、工单量同口径比较，任一项越界即停止放量。
10. **收缩**：确认新版本稳定且无旧版本实例后，在**下一个**发布周期删旧列或旧代码。

门禁比较的是灰度组与基线的*相对差*，而不是绝对阈值：退款的绝对错误率会随支付商状态整体波动，只看绝对值会把行业性抖动误判成自己的问题。

## 架构与选型

| 场景 | 推荐策略 | 理由 | 代价 |
| --- | --- | --- | --- |
| 退款状态机这类核心资金链路 | 灰度 + 自动门禁 | 出错时只影响少量订单，可秒级缩量 | 需要分流能力和领域指标 |
| 内部报表、无状态工具页 | 滚动更新 | 不值得为它建灰度体系 | 发布期间短暂混跑 |
| 需要整体换版且资源充足 | 蓝绿 | 回滚最快，切换清晰 | 双倍资源，数据库仍需兼容两版 |
| 单机部署的小型交付项目 | 停机重建 + 备份 | 简单、可解释 | 有停机窗口，需提前公告 |

选型可归成四个问题：变更的**爆炸半径**多大、**回滚窗口**要多短、能否承担**双版本并存**、**流量规模**是否足以支撑判断。前两个决定要不要灰度，后两个决定灰度能否成立——每天只有几十笔退款时，1% 流量没有统计意义，应改用人工审批加小范围白名单。

灰度不是默认答案。**<u>没有足够样本量就宣称“灰度通过”，比不灰度更危险，因为它给了团队虚假的安全感。</u>**

## 最小示例

下面用 Python 3 标准库写一个发布门禁判定器：输入灰度组与基线的三项指标，输出放量、观察或回滚。

```python
#!/usr/bin/env python3
"""canary_gate.py：对比灰度组与基线的指标，决定放量、观察还是回滚。"""
import sys

# 阈值固化在代码里并走评审，避免发布当晚有人临时调参放宽门禁。
LIMITS = {
    "error_delta_max": 0.005,  # 灰度组错误率最多比基线高 0.5 个百分点
    "p95_ratio_max": 1.20,     # 灰度组 P95 延迟最多是基线的 1.2 倍
    "min_samples": 200,        # 少于 200 次请求时任何比例都不可信
}

# 真实环境里这两个字典来自指标接口；这里内联，便于离线复现。
SAMPLE = {
    "baseline": {"requests": 5000, "errors": 25, "p95_ms": 180},
    "canary": {"requests": 800, "errors": 9, "p95_ms": 205},
}


def evaluate(baseline, canary):
    """返回 (结论, 原因列表)，结论只有 continue / hold / rollback 三种。"""
    reasons = []

    # 样本量必须先判：样本不足时最危险的动作是"再等等就宣布成功"。
    if canary["requests"] < LIMITS["min_samples"]:
        return "hold", [f"样本仅 {canary['requests']} 次，低于 {LIMITS['min_samples']} 次"]

    # 用比例而不是次数比较，否则两组流量规模不同就完全无法对照。
    error_canary = canary["errors"] / canary["requests"]
    error_baseline = baseline["errors"] / baseline["requests"]
    delta = error_canary - error_baseline
    # 用差值而不是比值：基线错误率接近 0 时比值会爆炸，差值更稳定。
    if delta > LIMITS["error_delta_max"]:
        reasons.append(
            f"错误率 {error_canary:.3%}，比基线 {error_baseline:.3%} 高 {delta:.3%}"
        )

    # 延迟看倍率：延迟天然是正数分布，绝对毫秒差会随业务周期漂移。
    ratio = canary["p95_ms"] / baseline["p95_ms"]
    if ratio > LIMITS["p95_ratio_max"]:
        reasons.append(f"P95 延迟 {canary['p95_ms']}ms，是基线的 {ratio:.2f} 倍")

    return ("rollback", reasons) if reasons else ("continue", ["所有门禁指标在阈值内"])


def main():
    verdict, reasons = evaluate(SAMPLE["baseline"], SAMPLE["canary"])
    print(f"结论：{verdict}")
    for reason in reasons:
        print(f"- {reason}")
    # 用退出码表达结论，让流水线直接失败，而不是等人去读日志。
    return 0 if verdict == "continue" else 1


if __name__ == "__main__":
    sys.exit(main())
```

运行与预期输出：

```console
$ python3 canary_gate.py
结论：rollback
- 错误率 1.125%，比基线 0.500% 高 0.625%
$ echo $?
1
```

流程是：先卡样本量 → 再算错误率差值与延迟倍率 → 越界即输出 `rollback` 并非 0 退出。把 `SAMPLE["canary"]["requests"]` 改成 `150` 会走 `hold`：<u>样本不足时不允许给出“通过”</u>。

配套的扩展迁移 SQL 只做向后兼容的部分（PostgreSQL 12 及以上）：

```sql
-- 扩展：新列可空，旧版本 INSERT 不带这两列也能成功
ALTER TABLE refund ADD COLUMN retry_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE refund ADD COLUMN next_retry_at TIMESTAMPTZ;

-- 索引必须并发创建，否则会持有写锁、阻塞退款写入
CREATE INDEX CONCURRENTLY idx_refund_event_refund_created
    ON refund_event (refund_id, created_at);
```

## 动手实验

### 目标

在 SQLite 上走一遍扩展阶段，并验证“代码回滚后，新库结构仍能支持旧版本运行”。

### 前置条件

Python 3.8 以上（含 `sqlite3` 标准库），无需网络和数据库服务。所有操作在内存库中完成，不落盘。

### 步骤

1. 建立旧版本表结构和两行存量数据。
2. 执行扩展迁移：新增带默认值的 `retry_count`。
3. 用旧版本代码的写法（只写自己知道的字段）插入一行，检查是否成功。
4. 分别用旧查询和新查询读取，确认两者都能工作——这就是“应用回滚后库结构仍兼容”的验证。

```console
$ python3 - <<'PY'
import sqlite3

# 内存库：实验结束即消失，不污染工作目录
con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE refund (id TEXT PRIMARY KEY, amount_cents INTEGER NOT NULL);
INSERT INTO refund VALUES ('R-1001', 12800), ('R-1002', 4500);
""")

# 扩展：NOT NULL 必须配 DEFAULT，否则旧版本 INSERT 会直接失败
con.execute("ALTER TABLE refund ADD COLUMN retry_count INTEGER NOT NULL DEFAULT 0")

# 旧版本代码不知道新列存在，只写自己知道的字段
con.execute("INSERT INTO refund (id, amount_cents) VALUES ('R-1003', 9900)")

print("旧查询:", con.execute("SELECT id, amount_cents FROM refund ORDER BY id").fetchall())
print("新查询:", con.execute("SELECT id, retry_count FROM refund WHERE id='R-1003'").fetchone())
PY
```

### 预期结果

```text
旧查询: [('R-1001', 12800), ('R-1002', 4500), ('R-1003', 9900)]
新查询: ('R-1003', 0)
```

### 验证方法

- 第 3 步未抛异常，说明加列向后兼容；去掉 `DEFAULT 0` 再跑会得到 `NOT NULL constraint failed`，这正是不可回滚变更的典型症状。
- 旧查询读到新行，说明旧版本代码无需改动即可继续服务。
- 新查询对历史行返回 `0`，说明默认值起到回填作用；若列可空会得到 `None`，应用必须处理空值。

### 清理方法

内存库随进程退出销毁。若改用文件库，实验结束执行 `rm refund_demo.db`，并确认路径是本目录下这个文件。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 流水线全绿，生产立刻 500 | 生产与测试的配置或依赖不同 | 比对线上镜像 digest 与配置版本 | 同一产物晋级，配置纳入版本管理 |
| 迁移预发秒过，生产锁表数分钟 | 数据量差异，未用并发建索引 | 在生产规模副本上计时并看锁等待 | `CREATE INDEX CONCURRENTLY`，回填分批 |
| 灰度指标正常，客服仍在投诉 | 门禁只看技术指标，没看领域指标 | 对比灰度组退款成功率与工单量 | 领域指标加入门禁，与技术指标同权 |
| 回滚应用后报错更多 | 库已做破坏性变更，旧代码读不到 | 检查旧版本是否引用被删改的列 | 改扩展-收缩顺序，回滚时前滚补偿数据 |
| 灰度结论反复横跳 | 分流不稳定，同一用户在两版间切换 | 检查分组键是否为稳定标识 | 用稳定分桶键，并设最小观察窗口 |

## 安全与生产注意事项

**<u>流水线凭据等价于生产权限，泄露一次就等于交出了生产环境。</u>**流水线通常持有镜像仓库写、集群部署和库迁移权限。缓解：凭据只注入流水线运行环境、按环境分权、发布留审计日志；凭据一旦出现在日志或镜像层中即视为已泄露并立即轮换。

**<u>在业务高峰执行不可逆的数据库变更，可能造成远超发布本身的资金与口碑损失。</u>**删列、改类型、大批量回填都属于这一类。缓解：设变更冻结期，破坏性变更至少延后一个发布周期，回填按批限速且可随时停下，并保留可演练恢复的备份。

还有一条常被忽略：**<u>发布审批不能由提交者本人完成</u>**——资金链路的放量决定，需要一个不在本次改动里的人负责。

## 本课总结

- 流水线的价值在于把“每次发布都要重新想一遍的检查”变成一次定义、每次执行。
- 构建只做一次，之后所有环境使用同一个不可变产物，只替换配置。
- 数据库变更按“扩展-收缩”拆到多个发布周期；不兼容变更无法靠回滚撤销，只能前滚补偿。
- 灰度成立的前提是能把流量稳定分到不同版本，且样本量足以支撑统计判断。
- 门禁要让技术指标与领域指标同权，并用退出码等明确结果驱动流水线，而不是靠人看日志。

## 思考题

退款服务 v2.3 上线两天后，灰度组错误率与基线持平，但客服反馈“有些退款单重试三次后卡在 `RETRYING`，既没成功也没失败”。此时应继续放量、暂停观察还是回滚？请写出判断依据、需要补充的证据，以及一个能防止同类问题再流入生产的门禁改动。

参考思路：这是“领域指标缺失”，不是“技术指标正常所以没问题”。先暂停放量并保持当前比例——缩量与回滚都有成本，而现状已被限制在小流量。证据应查 `refund_event` 中 `RETRYING` 超时记录数、支付商返回码分布、是否还有实例跑旧版本。门禁上补一条“`RETRYING` 超时占比不得高于基线”，并检查状态机有无无出口的转移路径：这是设计缺陷，回滚代码只能掩盖症状。

5. 场景题：团队每天只有约 40 笔退款，仍决定按 1% 流量灰度。作为架构师，你会提出什么问题？

## 答案与解析

1. **持续交付**要求版本随时可发布，由人决定何时放量；**持续部署**要求通过门禁后自动发布。差别只在最后一步由谁触发；当成同义词，结果是在资金链路上取消了本该保留的人工确认。
2. **C。**类型改变通常不向后兼容：旧代码按整数读取会失败或得到错误值，已回填的数据也无法无损还原。A 旧代码可忽略新列；B 只需删索引即可撤回；D 只是多一张表，不影响旧版本读写。
3. 因为绝对值会随外部因素漂移。支付商抖动时两组错误率一起上升，绝对阈值会误报；相对差才能回答“新版本是否比现在更差”，代价是需要足够样本，否则噪声会盖过差异。
4. **错。**自动化门禁只覆盖可量化的部分；放量时点、变更窗口、风险接受度属于业务与运维判断。<u>把门禁当成免责凭证，是发布事故的常见起点</u>。
5. 40 笔的 1% 不足一笔，分流没有意义；还要问门禁在什么样本量下才有统计效力、是否改用客户白名单先跑、谁观察多久、受影响客户的客服与财务是否知情。合理结论往往是用小范围白名单加人工复核替代按比例灰度。

### 动手实验参考

实验的关键不是敲对 SQL，而是看到两个事实：带 `DEFAULT` 的新列让旧代码无需改动即可运行；去掉默认值后旧代码立刻失败。前者是“可回滚”的技术条件，后者说明破坏性变更为什么必须排到后续版本。若进一步尝试 `DROP COLUMN`，会发现数据真的消失了——这正是“数据不能回滚”的含义。
