# 客户端、服务端与网络分层

## 为什么需要学习

晴空商城的退款工作台在客服中心打开要 4 秒，换到开发机上只要 0.8 秒。前端说“接口慢”，后端说“数据库 20 毫秒就返回了”，运维说“带宽还空着”。三种说法都能测出来，却指向不同的层：客服中心到机房的往返时延约为 180 毫秒，首屏要发 42 个请求，每个请求都要排一次队。团队缺的不是监控，而是一套共同的拆解方式。

> **核心结论：** 一次请求的耗时是分层叠加的结果；不把耗时拆到层上，优化就只能靠猜。

## 学习目标

完成本课后，你能够：

- 用分层模型（应用层、传输层、网络层、链路层）说明一次 HTTPS 请求在各层分别发生了什么。
- 划分客户端与服务端的职责，并指出状态、校验和信任边界应落在哪一侧。
- 用“往返次数 × RTT + 字节数 ÷ 带宽 + 服务端处理”估算耗时，判断瓶颈属于延迟还是带宽。
- 根据测量结果选择一种优化手段，并说明它缩小的是公式里的哪一项。

## 前置知识

- 回看上一单元：[需求发现与定义](../01-discovery-and-requirements/00-overview.md)。
- 知道 URL、域名、IP 地址和浏览器各自是什么。
- 能在终端执行命令，并读懂简单的 Python 3 代码。
- 不需要网络工程或运维经验。

## 业务场景

退款工作台用一个页面串起四个系统：页面框架由商城 Web 服务返回，退款单详情来自订单服务，支付流水来自支付查询接口，仓库回执来自仓储接口。客服点开一条退款单，浏览器先取回页面、脚本、样式和头像，再发起三次接口调用。

约束来自三条真实线索：

- 客服中心到机房单程约 90 毫秒，往返时延约 180 毫秒。
- 首屏共 42 个请求，脚本与图片合计 1.5 MB。
- 业务要求“点开退款单到可以点审核”不超过 2 秒。

架构师要回答的不是“要不要升级网络”，而是：这 4 秒里多少花在等往返、多少花在传字节、多少花在服务端处理——答案不同，该做的事也不同。

## 核心概念

*客户端*是主动发起请求、依赖对方返回结果才能继续的一方，退款场景里就是客服的浏览器。*服务端*是监听端口、等待请求并给出响应的一方，例如商城 Web 服务。*协议*是双方约定的报文格式与交互顺序，不一致就互相看不懂。

*分层*是把“把网页送到屏幕上”拆成若干层，每层只解决一类问题，且只与相邻层打交道；上层数据交给下层时，下层加上自己的头部，叫*封装*，接收端逐层去掉头部叫*解封装*。

*往返时延*（RTT）是一个报文从客户端到服务端再回来的时间，由物理距离、路由跳数和链路质量决定，与文件大小无关。*带宽*是单位时间能通过的比特数，决定大文件传多久。两者常被混为一谈：延迟决定“多久开始”，带宽决定“多久传完”。

| 层 | 本课关注的问题 | 晴空商城中的例子 | 出问题时的症状 |
| --- | --- | --- | --- |
| 应用层 | 报文语义：方法、路径、状态码、头部、正文 | `GET /orders/SO-20261019-0001/refund` | 404、401、字段缺失 |
| 传输层 | 端口、连接、可靠性与重传 | 浏览器连 `443`，服务端按连接分发 | 连接被拒、超时、抖动 |
| 网络层 | IP 寻址与路由 | 客服中心出口 IP 到机房 IP | 路由绕行、丢包、跨区延迟 |
| 链路与物理层 | 把比特送过一段介质 | 办公 Wi-Fi、专线、光纤 | 无线丢包、带宽跑满 |
| 名字解析 | 把域名换成 IP（跨层依赖） | `mall.sky.example` → 10.20.0.15 | 首次访问莫名卡住数秒 |

职责划分不是“谁写代码”，而是“谁对什么负责”：

| 关注点 | 客户端 | 服务端 |
| --- | --- | --- |
| 交互与呈现 | 渲染、输入、状态与错误提示 | 不负责 |
| 业务规则 | 提前提示，不能作为最终判定 | 最终判定与落库 |
| 身份与权限 | 携带凭据 | 校验凭据、判定权限 |
| 数据可信度 | 全部不可信 | 唯一可信来源 |
| 性能责任 | 资源体积、渲染、请求数量 | 处理时间、查询、序列化 |

**客户端负责体验，服务端负责真相。**

## 工作原理

以客服点击“查看退款单”为例，按时间顺序：

1. 浏览器解析 URL，查本地缓存与 hosts；没有再走 DNS 拿到服务端 IP。这一步失败会表现为“域名打不开”，而不是“接口报错”。
2. 传输层发起 TCP 三次握手：SYN、SYN+ACK、ACK。握手完成前一个业务字节都传不了，所以至少消耗一个 RTT。
3. 若是 HTTPS，还要做 TLS 握手：验证证书、协商密钥；TLS 1.3 通常再花一个 RTT。
4. 浏览器把请求报文写入连接：请求行（方法、路径、版本）、头部（`Host`、`Cookie`、`Accept`）和可选正文。
5. 请求先到达负载均衡或反向代理，由它选一台后端实例再转发给商城 Web 服务。
6. 服务端依次处理：解析报文、校验身份与权限、查询订单与支付数据、组装并序列化响应。
7. 服务端返回状态行、响应头和正文；响应头里的长度和缓存策略，决定浏览器能否复用这次结果。
8. 浏览器解析 HTML，发现脚本、样式和图片，再为每个子资源重复第 2 至 7 步，可能复用连接。
9. 页面可交互后，脚本再发起三次接口调用，每次调用又是一次完整的请求—响应。
10. 连接按策略复用或关闭；`keep-alive` 与多路复用能省掉后续请求的握手成本。

这条时间线可以直接折算成公式：

> **核心结论：** 总耗时 ≈ 往返次数 × RTT + 字节数 ÷ 带宽 + 服务端处理时间 + 客户端渲染时间。

四个加数对应四类瓶颈：RTT 高而字节少，问题在往返次数；字节多而 RTT 低，问题在带宽；两者都不高却仍然慢，就该看服务端处理或客户端渲染。首字节时间（TTFB）大致就是“一次往返 + 服务端处理”，是外部观察这两项最省事的指标。

## 架构与选型

| 手段 | 主要缩小 | 什么情况下有效 | 什么情况下无效或代价高 |
| --- | --- | --- | --- |
| CDN 分发静态资源 | RTT + 传输时间 | 用户分散、资源体积大 | 动态接口无法缓存 |
| 连接复用、HTTP/2 多路复用 | 往返次数 | 单页请求多、集中同一域名 | 跨域名仍要分别建连 |
| 压缩与图片格式优化 | 字节数 | 首屏 1.5 MB 这类场景 | 单次 RTT 200 毫秒时收益有限 |
| 合并与削减请求 | 往返次数 | 42 个碎片化小请求 | 过度合并会放大单点失败 |
| 服务端缓存、查询优化 | 服务端处理 | 数据库慢、重复计算多 | 缓存一致性与失效成本 |
| 边缘节点、就近部署 | RTT | 客服与机房跨国 | 成本高，还要解决数据同步与合规 |
| 骨架屏、分步呈现 | 感知延迟 | 真实耗时短期降不下来 | 不减少真实耗时，不能用来达标验收 |
| 直接增加带宽 | 传输时间 | 大文件、批量下载 | 瓶颈在往返次数或服务端时几乎无改善 |

选型依据只有一条：先测出四个加数各占多少，再选缩小最大那项的手段。<u>没有测量就选方案，等于把预算押在猜测上。</u>

## 最小示例

问题：把一次请求拆成建连、首字节、传输三段实测，再用公式估算远程场景。环境：Python 3.9+，只用标准库，无需联网。输出：真实响应头、三段耗时和一张估算表。

```python
# 演示：一次请求在时间上被拆成哪几段
import socket, threading, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

BODY = b"hello-from-sky-mall" * 128  # 固定 2432 字节，便于观察传输量

class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"     # 声明 1.1，才支持定长响应与复用

    def do_GET(self):
        time.sleep(0.03)              # 模拟服务端处理 30ms
        self.send_response(200)       # 状态行：200 表示成功
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(BODY)))  # 定长，客户端读满即可停
        self.send_header("Connection", "close")             # 明确边界，读完就断开
        self.end_headers()
        self.wfile.write(BODY)        # 正文写在头部之后

    def log_message(self, fmt, *args):
        pass                          # 关掉访问日志

server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)  # 端口 0 = 系统分配空闲端口
threading.Thread(target=server.serve_forever, daemon=True).start()  # 后台收请求
port = server.server_address[1]

# 手写请求文本，才能看到应用层发出的字节
request = (
    "GET /orders/SO-20261019-0001/refund HTTP/1.1\r\n"
    f"Host: 127.0.0.1:{port}\r\n"
    "User-Agent: sky-mall-lab/1.0\r\n"
    "Accept: text/plain\r\n"
    "Connection: close\r\n"
    "\r\n"                        # 空行表示头部结束，之后才是正文
).encode("ascii")

sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # 直接用传输层套接字
start = time.perf_counter()
sock.connect(("127.0.0.1", port))                        # 三次握手发生在这里
connect_ms = (time.perf_counter() - start) * 1000

sent_at = time.perf_counter()
sock.sendall(request)            # 应用层报文被封装进 TCP 段发出
first_byte_ms, chunks = None, []
while True:
    chunk = sock.recv(4096)      # 每次最多读 4096 字节
    if chunk and first_byte_ms is None:
        first_byte_ms = (time.perf_counter() - sent_at) * 1000  # 首字节 = 等待 + 服务端处理
    if not chunk:                # 对端已关闭，读出空串
        break
    chunks.append(chunk)
sock.close()
total_ms = (time.perf_counter() - sent_at) * 1000

head, _, body = b"".join(chunks).partition(b"\r\n\r\n")  # 头部与正文按空行切开
print("--- 响应头 ---")
print(head.decode("iso-8859-1"))
print(f"TCP 建连: {connect_ms:.1f} ms")
print(f"首字节: {first_byte_ms:.1f} ms")
print(f"整体: {total_ms:.1f} ms，响应体 {len(body)} 字节")

# 用公式估算远程场景：往返次数 × RTT + 字节 / 带宽
print("\nRTT(ms) 带宽(Mbps) 往返数 载荷(KB) 估算耗时(ms)")
for rtt, bw, round_trips, kb in [
    (10, 100, 4, 1500),   # 同城办公网
    (80, 10, 4, 1500),    # 跨省、窄带
    (80, 100, 4, 1500),   # 跨省、宽带
    (200, 10, 4, 1500),   # 跨国客服中心
    (80, 10, 4, 300),     # 跨省、窄带，资源已压缩
]:
    transfer_ms = kb * 1024 * 8 / (bw * 1000)  # 千字节换比特，再除以每秒比特（得毫秒）
    print(f"{rtt:<7} {bw:<9} {round_trips:<7} {kb:<9} {round_trips * rtt + transfer_ms:.0f}")
```

运行 `python3 lab_latency.py`。预期输出（毫秒数随机器波动，只需看结构与量级）：

```text
--- 响应头 ---
HTTP/1.1 200 OK
Server: BaseHTTP/0.6 Python/3.14.7
Date: Mon, 19 Oct 2026 08:29:32 GMT
Content-Type: text/plain; charset=utf-8
Content-Length: 2432
Connection: close
TCP 建连: 0.1 ms
首字节: 31.0 ms
整体: 31.0 ms，响应体 2432 字节

RTT(ms) 带宽(Mbps) 往返数 载荷(KB) 估算耗时(ms)
10      100       4       1500      163
80      10        4       1500      1549
80      100       4       1500      443
200     10        4       1500      2029
80      10        4       300       566
```

读法：回环地址的 RTT 接近 0，首字节那 31 毫秒几乎全是服务端处理加调度开销。估算表里 80 毫秒 RTT 的场景，四次往返就占 320 毫秒；第三行把带宽提十倍，总耗时从 1549 落到 443；第五行把载荷降到五分之一，窄带下同样落到 566。<u>同样是 1500 KB，窄带时带宽是主要矛盾，宽带时往返次数才是。</u>

## 动手实验

前置条件：Python 3.9+，一个可写的临时目录（不要放在 `docs/` 下），无需联网。

1. 在临时目录创建 `lab_latency.py`，粘贴上一节的完整代码。
2. 运行 `python3 lab_latency.py`，记录“建连”和“首字节”两个数字。
3. 把 `time.sleep(0.03)` 改成 `time.sleep(0.3)`，重跑，看首字节是否增加约 270 毫秒而建连不变。
4. 把 `BODY` 改成 `b"hello-from-sky-mall" * 5120`（约 97 KB），重跑，看整体耗时涨多少。
5. 把 `(200, 10, 4, 1500)` 中的往返数改成 `8`，重跑，观察总耗时变化。

预期结果：第 3 步只有首字节变化，说明它包含服务端处理；第 4 步回环地址上几乎不涨，说明本机复现不了真实带宽；第 5 步每多一个往返就多 200 毫秒。

验证方法：`建连 + 首字节` 应接近“整体”耗时，且首字节随 `sleep` 变化；两次数值完全一致就是改动没生效。

清理方法：删除 `lab_latency.py`。服务端线程是 `daemon`，脚本退出即释放端口。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| 开发机 0.8 秒，客服现场 4 秒 | 两地 RTT 不同，请求数把它放大 | 看网络面板里首个请求的等待时间 | 就近部署或 CDN，并减少首屏请求数 |
| 带宽翻倍后仍然慢 | 瓶颈是往返次数或服务端处理 | 对比“首字节”与“内容下载”两段耗时 | 连接复用、合并请求、优化服务端 |
| 首次访问慢，刷新后正常 | DNS、TLS 或连接未被复用 | 清空缓存后对比首次与二次加载 | 预热、`preconnect`、合理缓存头 |
| 服务端日志 50 毫秒，页面仍要 3 秒 | 客户端渲染慢或资源过多 | 在性能面板看加载与空闲时间占比 | 缩减资源、服务端渲染、骨架屏 |
| 前端加了校验，接口仍接受非法值 | 只在前端校验，服务端没有复核 | 用 `curl` 绕过页面直接调接口传越界参数 | 服务端补齐校验与鉴权 |

## 安全与生产注意事项

**<u>客户端完全由用户控制，任何来自客户端的数据都不可信。</u>** 隐藏字段、前端算出的金额、`X-Forwarded-For` 头部都能被改写。若退款服务相信前端传来的“可退金额”，一次请求就能把 500 元改成 50000 元。缓解：金额、权限和状态一律由服务端用可信数据重算，客户端只负责展示。

**<u>明文 HTTP 会把退款单号、手机号和会话 Cookie 暴露在链路上，并可被中间人篡改。</u>** 在客服中心的共享 Wi-Fi 上，抓一次包就能复用他人会话查看退款记录。缓解：全站 HTTPS 加 HSTS，Cookie 设置 `Secure`、`HttpOnly`、`SameSite`，内网链路也不要默认信任。

另外，<u>只有确认过可信代理链，才能用代理追加的转发头部做限流或审计</u>，否则伪造来源 IP 就能绕过。

## 本课总结

- 分层把“网页到达屏幕”拆成各管一类问题的层，故障必须落到具体层上定位。
- 客户端负责体验，服务端负责真相：状态、校验和权限的最终依据永远在服务端。
- 一次请求的耗时 ≈ 往返次数 × RTT + 字节数 ÷ 带宽 + 服务端处理 + 客户端渲染。
- 延迟决定“多久开始”，带宽决定“多久传完”，两者要用不同手段解决。
- 优化顺序是测量、定位最大加数、再选手段；反过来做，只是把预算花在猜测上。

## 思考题

客服中心在海外，打开退款单要 3.2 秒：约 1.6 秒是往返等待，约 1.1 秒是 1.5 MB 资源下载，其余是服务端处理。预算只够做一件事——加边缘节点，还是把首屏资源压到 400 KB？请给出判断、所需补充数据和上线后的验证指标。

参考思路：先算两个方案各缩小哪个加数。压资源把 1.1 秒降到约 0.3 秒，改善所有用户；加边缘节点主要压低 RTT，四次往返省约 0.8 秒，但要解决数据同步、缓存一致与合规。补充数据是用户地域分布、资源能否缓存、是否已压缩。验证指标取首屏可交互时间的 P75，而不是平均值。

## 小测

1. 判断：把带宽从 10 Mbps 提到 100 Mbps，能缩短 TCP 握手时间。
2. 单选：把域名解析成 IP 地址，由哪一层或哪类机制负责？  
   A. 应用层 HTTP　B. 传输层 TCP　C. 名字解析机制（DNS）　D. 链路层
3. 简答：为什么“前端已经校验过”不能成为服务端跳过校验的理由？
4. 单选：首字节时间（TTFB）主要包含什么？  
   A. 只有服务端处理　B. 只有传输字节的时间　C. 一次往返加服务端处理　D. 客户端渲染时间
5. 场景题：首屏有 42 个请求，每个请求 RTT 150 毫秒，总字节 500 KB，链路 10 Mbps。运维建议“加带宽”，这个建议合理吗？

## 答案与解析

1. **错。** 握手时间由 RTT 和丢包决定，与带宽无关；带宽只影响握手之后传数据的速度。
2. **C。** DNS 在建立连接之前完成名字解析。A 的 HTTP 只管报文语义；B 的 TCP 管端口与可靠传输；D 的链路层只管介质上的比特。
3. 客户端在用户机器上，用户可以绕过界面直接构造请求。<u>前端校验只改善体验，不构成安全边界</u>；服务端必须用可信数据重新校验参数、身份与权限。
4. **C。** 从发出请求到收到第一个字节，中间至少一次往返，再加服务端解析、鉴权、查询和组装的时间。A 漏掉网络等待；B 说的是下载阶段；D 发生在响应到达之后。
5. 不合理。500 KB 在 10 Mbps 下约 0.4 秒，而 42 个请求若串行、各等一次往返就是 6.3 秒，瓶颈是往返次数。应先合并请求、启用连接复用与并行加载，再看带宽是否仍是瓶颈。

### 动手实验参考

第 3 步首字节约为 330 毫秒（原 31 毫秒加 270 毫秒），建连仍在 1 毫秒以内；第 4 步在回环地址上的增长远小于真实网络；第 5 步往返数从 4 变成 8，总耗时增加 4 × 200 = 800 毫秒，正是“每个往返都要单独付费”。
