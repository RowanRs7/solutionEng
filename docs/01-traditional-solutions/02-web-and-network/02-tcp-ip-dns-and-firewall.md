# TCP/IP、DNS 与防火墙

## 为什么需要学习

晴空商城退款服务上线第一周，客服页面开始间歇性出现“退款请求超时”。开发在自己机器上 `curl` 是通的；运维说安全组“已经放行”；客服说重试几次有时能成功。三方都有证据，却没人能回答一个更基本的问题：这条请求的流量究竟停在哪一段？

“网络通了”不是一个可验证的结论。一次调用至少要穿过五道关卡：名字能解析成地址、地址可路由、端口有进程监听、沿途防火墙放行、握手能完成。任何一关卡住，上层看到的都只是“超时”。

> **核心结论：** 把“网络不通”拆成解析、路由、放行、监听、握手五段分别验证，比争论谁配置没问题更快定位故障。

## 学习目标

完成本课后，你能够：

- 解释 IP 地址、端口、TCP 连接、DNS 解析、路由和防火墙各自负责哪一段。
- 使用 `dig`、`nc`、`lsof` 和 `python3` 标准库，把“连不上”判成解析失败、被拒绝或被丢弃。
- 为一次跨系统调用写出连通性检查清单，逐项包含五元组、DNS 记录与放行规则。
- 指出把内网域名当作访问控制、或为排障放宽安全组带来的生产风险。

## 业务场景

晴空商城的退款链路分布在三处：商城前端与退款服务在商城 VPC 内，客服平台在第二个 VPC，两者通过 *VPC 对等连接* 互通；支付供应商只提供公网 HTTPS 接口。

退款服务使用内网域名 `refund.svc.qingkong.internal`、监听 `8443`，客服平台的回调地址里写的正是这个域名。上周运维把它从 A 可用区迁到 B 可用区，IP 从 `10.20.2.31` 变成 `10.20.3.11`，同时换了个新建的安全组。于是出现三份矛盾的证据：

- 客服平台日志：`connection timed out after 30000 ms`，重试偶有成功。
- 退款服务日志：没有一条来自客服平台网段的请求记录。
- 运维后台：新安全组入站只放行商城前端的 `10.20.1.0/24`，而客服平台在 `10.30.5.0/24`。

三条已足够推断：报文被丢在目的主机的入口，从未到达进程；剩下的是按顺序验证每一段。

## 核心概念

| 概念 | 含义 | 晴空商城中的实例 |
| --- | --- | --- |
| *IP 地址* | 网络中一块网卡接口的编号，IPv4 写成四段十进制 | 退款服务新地址 `10.20.3.11` |
| *端口* | 主机上区分不同服务的 16 位编号（0–65535） | 退款服务 `8443`，SSH 管理用 `22` |
| *五元组* | 源 IP、源端口、目的 IP、目的端口、传输层协议 | `10.30.5.20:51234 → 10.20.3.11:8443 TCP` |
| *TCP* | 面向连接、可靠、有序的传输层协议，靠*三次握手*（SYN → SYN-ACK → ACK）建连 | 退款回调不能重不能漏，因此用 TCP |
| *DNS* | 把域名解析成地址的分层、带缓存的分布式数据库 | 把 `refund.svc.qingkong.internal` 解析成 `10.20.3.11` |
| *A 记录* / *AAAA 记录* | 域名到 IPv4 / IPv6 地址的映射；*CNAME* 是别名 | 内网域名一条 A 记录，公网接口一条 CNAME |
| *TTL* | 域名记录可被缓存的秒数 | 内网记录 TTL 60 秒，迁移后一分钟内生效 |
| *子网* / *默认网关* / *CIDR* | 主机用掩码判断是否同网段，不同网段交给网关；CIDR 是“地址 + 前缀长度” | 商城 VPC `10.20.0.0/16`，网关 `10.20.0.1` |
| *防火墙* | 按规则决定放行或丢弃报文的设备或软件 | 安全组入站规则只放行 `10.20.1.0/24` |
| *安全组* | 绑定实例或网卡、按五元组**有状态**放行的虚拟防火墙 | 退款服务实例绑定的新安全组 |

**一条连接的本质就是一个五元组。** 防火墙、连接跟踪表与 `ss` 输出都以它为单位，排障时先写出五元组再谈其他。

<u>DNS 的 TTL 以秒计，IP 报文头的 TTL 以“还能经过几跳”计，两者只是重名。</u>把后者当缓存时长，会得出完全错误的结论。

| 对比项 | 无状态包过滤 | 有状态防火墙（含安全组） |
| --- | --- | --- |
| 判断依据 | 只看单个报文的五元组 | 五元组 + 已建立连接的跟踪表 |
| 回程流量 | 需显式放行反向规则 | 自动放行已建立连接的回程包 |
| 常见坑 | 忘放行返回端口，出现“单向通” | 长连接被表项超时回收，需心跳保活 |

## 工作原理

按一次调用的时间顺序，机制分成八步：

1. **确定目标。** 应用只有名字和端口：`refund.svc.qingkong.internal` 与 `8443`。名字换成地址之前，谈不上任何连接。
2. **查本地缓存。** 先看 `hosts` 与本机 DNS 缓存，命中就直接用。容器里常见的是 `hosts` 写死了旧 IP，改了 DNS 也不生效。
3. **递归解析。** 未命中时，本机把问题交给 *递归解析器*（VPC 内通常是 `10.20.0.2`）；它无缓存时依次问根、顶级域与该域名的权威服务器，最后拿到 A 记录与 TTL。
4. **得到地址。** 解析结果为 `10.20.3.11`，TTL 60 秒。返回多条 A 记录时，客户端按顺序或轮询使用，不同记录可能指向不同可用区。
5. **判断路由。** 客服平台主机 `10.30.5.20` 用掩码判断目的不在 `10.30.5.0/24` 内，于是交给默认网关。对等连接两侧的路由表都必须含对端网段，否则包在网关处无处可去。
6. **过防火墙。** 包到达退款服务实例绑定的安全组，规则按五元组匹配；源网段 `10.30.5.0/24` 不在放行列表里，报文被**静默丢弃**。关键在于丢弃不回应，客户端只能等到超时，于是表现成 `timed out` 而非 `refused`。
7. **三次握手。** 若规则放行，SYN 到达 `8443`，服务端回 SYN-ACK，客户端回 ACK，连接进入 `ESTABLISHED`。此时 `lsof` 或 `ss` 能看到它，应用才开始发数据——HTTP 报文属于下一课。
8. **结束与回收。** 正常结束走 FIN 四次挥手，异常时发 RST 中断。有状态防火墙靠连接跟踪表放行回程包；表项超时或进程重启后，老连接被丢弃，表现为“刚才还通，现在不通”。

压缩成一句数据流：**名字 → 地址 → 路由 → 放行 → 握手**。每一步都有独立的验证手段，因此不必靠猜。

## 架构与选型

| 方案 | 适用场景 | 不适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 调用方使用域名 | 需要迁移、扩缩容、多可用区 | 引导阶段要求零依赖 | 多一层故障点与缓存延迟 |
| 调用方硬编码 IP | 临时验证、本地回环测试 | 云上实例、容器等地址会变 | 地址一变即全量改配置，难回滚 |
| 安全组引用安全组 | 同一 VPC 内服务间调用 | 跨 VPC 且无对等连接 | 依赖命名与归属治理 |
| 安全组引用 CIDR | 跨 VPC、专线、固定出口 IP | 对端出口地址频繁变化 | 网段写错一位就整段不通 |
| 公网直连 + TLS | 面向供应商、外部 SaaS | 高频内部调用、需私有链路 | 暴露面扩大，需长期加固入口 |
| 专线或 VPN | 稳定、量大、合规敏感的互联 | 临时联调、低频调用 | 开通周期长、成本高、双端运维 |

选型依据可归结为三个问题：这段连接会否因扩缩容而换地址（域名还是 IP）、对端是否在同一信任域（引用安全组还是 CIDR）、链路是否承载敏感数据（公网还是专线）。<u>先用最窄的放行范围跑通，再逐条加宽</u>，比先全开再收紧更容易得到可追溯的规则集。

## 最小示例

问题：客服平台报超时，服务本身可能完全健康。需要一个不依赖第三方包、也不改动线上配置的工具，把“连不上”分成“解析失败”“被拒绝”“被丢弃”三类。

环境：Python 3.9 及以上，只用标准库。输入是主机名或 IP 加端口，输出一行分类结论，并用退出码把结论交给脚本复用。

```python
# probe.py —— 把“连不上”拆成可分别验证的两段：先解析，再连端口
import socket   # 标准库同时提供 DNS 解析与 TCP 连接，无需安装任何依赖
import sys      # 从命令行取目标，使同一份脚本能在客服平台主机上复现问题
import time     # 用单调时钟测耗时，避免系统时间调整影响判断


def probe(host: str, port: int, timeout: float = 3.0) -> int:
    try:
        # getaddrinfo 走系统解析器（含 hosts 文件与缓存），返回该名字的全部候选地址
        infos = socket.getaddrinfo(host, port, type=socket.SOCK_STREAM)
    except socket.gaierror as exc:      # 名字不存在、或解析器不可达，都会落到这里
        print(f"[DNS] 解析失败: {exc}")
        return 2                        # 退出码 2 声明故障在“名字 → 地址”这一段

    for family, _, _, _, sockaddr in infos:
        # 打印全部候选：出现多个地址说明后端可能分布在不同可用区
        print(f"[DNS] family={family} addr={sockaddr}")

    # 只对第一个候选发起连接，让每次运行的行为可预测、可对比
    family, socktype, proto, _, sockaddr = infos[0]
    start = time.monotonic()
    try:
        # with 保证成功或失败都关闭套接字，排障脚本本身不该泄漏文件描述符
        with socket.socket(family, socktype, proto) as sock:
            sock.settimeout(timeout)    # 超时是结论的一部分：没有它脚本会挂住，什么也说明不了
            sock.connect(sockaddr)      # 触发三次握手；执行到下一行即表示握手完成
            print(
                f"[TCP] 连接成功 本地={sock.getsockname()} "
                f"远端={sock.getpeername()} 耗时={time.monotonic() - start:.3f}s"
            )
            return 0
    except ConnectionRefusedError:
        # 对端回 RST：包到了主机，但该端口没有进程监听
        print("[TCP] 连接被拒绝(端口未监听或监听地址不匹配)")
        return 3
    except socket.timeout:
        # 没有 RST：包在途中被丢弃，最常见原因是安全组或防火墙未放行
        print("[TCP] 连接超时(常见于安全组或防火墙静默丢包)")
        return 4
    except OSError as exc:
        # 本地无路由、网络不可达、地址族不支持等，归为其他错误以免掩盖信息
        print(f"[TCP] 其他错误: {exc}")
        return 5


if __name__ == "__main__":
    # 把结论编码进退出码，方便在巡检脚本或 CI 里直接判断
    sys.exit(probe(sys.argv[1], int(sys.argv[2])))
```

整体流程：解析失败立即返回第二类结论；解析成功就把候选地址打印出来作为证据；随后只对第一个地址设超时并尝试握手；最后按异常类型给出互不重叠的结论。三处关键设计：用 `getaddrinfo` 而非 `gethostbyname`，因为前者覆盖 IPv4 与 IPv6；显式设超时，让“没有回应”成为可记录的结论；把 `refused` 与 `timeout` 分开，这正是判断“包是否到达”的分界线。

运行本机一个未监听的端口，预期输出：

```text
$ python3 probe.py 127.0.0.1 1
[DNS] family=2 addr=('127.0.0.1', 1)
[TCP] 连接被拒绝(端口未监听或监听地址不匹配)
```

解析一个公网域名，预期输出（地址与耗时随网络变化）：

```text
$ python3 probe.py example.com 443
[DNS] family=2 addr=('104.20.23.154', 443)
[DNS] family=30 addr=('2606:4700:10::6814:179a', 443, 0, 0)
[TCP] 连接成功 本地=('192.168.13.172', 64774) 远端=('104.20.23.154', 443) 耗时=0.246s
```

## 动手实验

### 任务：在本机复现三种连通性结论

前置条件：macOS 或 Linux；`python3`、`dig`（或 `nslookup`）、`nc`、`lsof`（Linux 可用 `ss`）可用；把上节代码保存为 `probe.py`。

1. **确认解析正常。** 执行 `dig example.com +noall +answer`，记录 A 记录与 `TTL` 字段。
2. **起一个只监听回环的服务。** 后台执行 `python3 -m http.server 18080 --bind 127.0.0.1`。
3. **确认监听地址是回环。** 执行 `lsof -nP -iTCP:18080 -sTCP:LISTEN`。
4. **从外部确认可连。** 执行 `nc -vz 127.0.0.1 18080`。
5. **对比开放与关闭端口。** 分别执行 `python3 probe.py 127.0.0.1 18080` 与 `python3 probe.py 127.0.0.1 18081`。
6. **改成所有网卡再观察差异。** 结束进程后改用 `--bind 0.0.0.0` 重启，重复第 3、4 步。

预期结果：第 1 步看到形如 `example.com. 300 IN A 104.20.23.154` 的应答行；第 3 步显示 `TCP 127.0.0.1:18080 (LISTEN)`；第 4 步输出 `Connection to 127.0.0.1 port 18080 [tcp/*] succeeded!`；第 5 步 `18080` 成功、`18081` 被拒绝；第 6 步监听地址从 `127.0.0.1` 变成 `*`。

验证方法：`lsof` 的监听地址要与 `nc` 结果一致；`probe.py` 退出码应为 `0`（开放）与 `3`（拒绝）。若第 4 步成功而第 5 步超时，说明脚本选中的地址族与实际监听不一致，这在 IPv6 优先解析时常见。

清理方法：结束 `http.server` 进程（`pkill -f "http.server 18080"`），用 `lsof -nP -iTCP:18080 -sTCP:LISTEN` 确认无输出，再删除临时 `probe.py`。本实验不写配置文件，无需回滚。

## 常见错误与排查

| 现象 | 可能原因 | 验证方法 | 修复方向 |
| --- | --- | --- | --- |
| `connection timed out`，对端无访问日志 | 安全组或防火墙静默丢包，包未到达进程 | 源主机 `nc -vz 目标 端口`；核对入站网段是否含源地址 | 放行正确源 CIDR 或引用源安全组，只加最小规则 |
| `connection refused` | 端口无进程监听，或只监听 `127.0.0.1` | 在目标主机执行 `lsof -nP -iTCP:端口 -sTCP:LISTEN` | 让服务监听业务网卡或 `0.0.0.0`，确认启动顺序 |
| `could not resolve host` | 记录缺失、解析器地址错、容器 `hosts` 写死旧地址 | `dig 域名 +short`，再 `dig @解析器 域名` 对比 | 修正记录或解析器配置，清掉手工 `hosts` 条目 |
| 迁移后时通时不通 | 缓存里仍是旧 IP，或多 A 记录轮询到未就绪节点 | 连续多次 `dig` 看返回地址；分别探每个地址 | 缩短 TTL 等旧值过期，用健康检查摘除未就绪节点 |
| 同网段一台能通、另一台不能 | 路由表或对等连接缺对端网段 | 在该主机查路由表，确认网关与对端网段条目 | 补齐两侧路由，注意路由必须双向 |

## 安全与生产注意事项

**<u>排障时先把安全组改成 `0.0.0.0/0` 再“回头收紧”，是云上最典型的敞口事故。</u>**后果是数据库与管理端口几分钟内就可能被公网扫描命中并尝试爆破，而“回头收紧”常因下班而拖数天。缓解：只临时放行排障主机的 `/32` 地址，写清到期时间并设提醒，管理操作走会话管理而非公网 SSH。

**<u>把“内网域名只有内部才知道”当作访问控制，等于没有访问控制。</u>**DNS 只负责寻址、不负责授权，能进入同一 VPC 或对等网段的人都能绕过域名直连 IP 与端口。缓解：安全组与应用层身份校验共同把关，域名只承担可迁移性。

**<u>把 DNS 的 TTL 设成 24 小时，却又要求分钟级故障切换，是把恢复时间签给了缓存。</u>**后果是故障时客户端仍解析旧地址，切换动作看似完全无效。缓解：按切换目标倒推 TTL，切换前先降低 TTL 并等旧值过期。

## 本课总结

- 一次调用要穿过解析、路由、放行、监听、握手五段，任何一段失败都只暴露成“超时”。
- 一条连接由五元组唯一确定，防火墙、连接跟踪与排障命令都以它为单位。
- `refused` 说明包到了但没人接，`timed out` 说明包被丢弃或路由不通，这是最快的分诊结论。
- DNS 负责寻址、安全组负责放行、应用负责授权，三者职责不可互相替代。
- 迁移前先降 TTL、迁移后按五段逐项验证，比事后凭日志猜原因更可靠。

## 思考题

退款服务要从单可用区扩到三个可用区，客服平台的回调地址仍只写一个域名。你会让域名返回多条 A 记录、改用 CNAME 指向负载均衡、还是保持不变？请写出选择依据、需要哪个角色确认，以及故障切换时要付的代价。

参考思路：多 A 记录实现简单、不新增组件，但切换速度受客户端缓存与重试策略限制，且无法感知节点健康；CNAME 指向负载均衡由专门组件做健康检查，代价是多一层运维对象和费用；保持不变最省事，等于放弃可用性目标。

## 小测

1. 一条 TCP 连接由哪些字段唯一确定？
2. DNS 的 TTL 与 IP 报文头中的 TTL 分别表示什么？
3. `connection refused` 与 `connection timed out` 在“包是否到达对端”上有何差别？
4. 安全组入站只放行 `10.20.1.0/24`，而客户端在 `10.30.5.20`，客户端最可能看到哪种错误？
5. 场景题：开发说在商城 VPC 的跳板机上 `nc -vz refund.svc.qingkong.internal 8443` 是通的，但客服平台回调依然超时。以下哪项最应先验证？  
   A. 退款服务是否支持 HTTPS  
   B. DNS 记录是否已更新到新地址  
   C. 安全组是否放行了客服平台所在的 `10.30.5.0/24`  
   D. 退款服务代码是否有异常日志

## 答案与解析

1. 源 IP、源端口、目的 IP、目的端口、传输层协议，共五项。只答“IP 和端口”会漏掉协议与源端口，而防火墙按完整五元组匹配。
2. DNS 的 TTL 是记录可被缓存的秒数；IP 头的 TTL 是报文还能经过的路由跳数上限，每跳减一，减到零被丢弃。两者只是重名，混用会误判“改了记录多久生效”和“能走多远”。
3. `refused` 说明 SYN 到达主机并收到 RST，即包到了但端口无人监听；`timed out` 说明没收到任何回应，包大概率在途中被丢弃。所以前者查进程与监听地址，后者查防火墙与路由。
4. `connection timed out`。报文在安全组处被静默丢弃，客户端收不到 RST，只能等到超时。只有平台配置成显式拒绝并回 RST 时才表现为拒绝，不能把“超时”一律归因于对端宕机。
5. **C。** 跳板机在 `10.20.1.0/24` 内，它的成功恰恰证明放行只覆盖商城前端网段，无法证明客服平台网段可用；先验证 C 才能解释“跳板机通、客服平台不通”这组矛盾证据。A 与 D 属应用层问题，连接都建不起来就不会产生应用日志；B 与证据不符，跳板机用同一域名能连通，说明解析已指向新地址。

### 动手实验参考

合理结论应含三段对照：`lsof` 的监听地址与 `nc` 结果一致；开放端口返回 `0`、关闭端口返回 `3`；改成 `0.0.0.0` 后监听地址从 `127.0.0.1` 变为 `*`。只记“成功/失败”而不记监听地址，就无法区分“服务没起”和“服务起在错误的网卡上”，这正是本实验要训练的区别。
